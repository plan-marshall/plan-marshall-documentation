== Overview

The use cases describe what a person does with `PM-MCP` and what they get out of it, from their point of view and in their words. They come before the link:Requirements.adoc[Requirements]: a use case names the requirements that serve it, and a use case that no requirement serves yet shows what the requirements still lack. The operator acts only in the two clients, the web app and the terminal client; a coding agent is a worker the runtime runs, never a place where the operator is asked or answers (link:use-cases/05-starting-work.adoc#change-clients-only[All Interaction in the Operator's Clients]). There is one set of use cases for both clients: a use case says what the operator achieves, never how a client shows it. How each client shows it is worked out in its design, which is the specification of the client's implementation and lives with its code (link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/README.adoc[`pm-mcp-clients`, Design]); how the system does it, in the link:Specification.adoc[Specification].

== Conventions

* *Identifier*: every use case has a stable anchor `[#UC-<AREA>-<N>]` and the heading `== UC-<AREA>-<N>: <title>`. A number is never reused.
* *One module per area*: `use-cases/NN-<area>.adoc`, listed in <<index>>.
* *Client-neutral*: a use case is cut by subject, never by client; it names a client at most as where the operator acts ("in the web app or in the terminal client"), never its screens, commands, or keys.
* *Status*: each use case states one of `DRAFT` (being written, open points named), `AGREED` (the operator agreed to it; requirements and design may be derived from it).
* *Processes*: a use case whose process the server runs is modelled as a workflow, and a step of it that is a process of its own as a sub-workflow with a use case of its own. Its flow is drawn as an ASCII state diagram in a `[source,text]` block: one line per state, named as the state would be named in the workflow unit, marked `[S]` when the server acts, `[O]` when the operator chooses, and `[M]` when a model acts through a role task; the arrows carry the outcomes. The diagram shows the process, never a screen.
* *Shape*: each use case has the parts of the template below; a part that does not apply is left out, never filled with filler.

[source,asciidoc]
----
[#UC-<AREA>-<N>]
== UC-<AREA>-<N>: <title>

Status:: `DRAFT`
Actor:: who does it (the operator, a reviewer, ...).
Goal:: what they want to achieve, in one sentence.
Trigger:: what makes them start.
Preconditions:: what holds before.
Flow:: the steps, numbered, as the actor experiences them.
Variations:: other ways through, and what happens when something fails.
Outcome:: what holds afterwards.
Open points:: what is not decided yet.
Changes:: the changes of the requirements and specifications it needs, each modelled as the fix of a gap.
Requirements:: the requirements that serve it (link:Requirements.adoc[Requirements]).
Design:: the design documents that show it, per client (link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/README.adoc[`pm-mcp-clients`, Design]).
----

== Use Case Areas

[cols="1,1,3",options="header"]
|===
|Area |Module |What it covers

|`UC-ONB`
|link:use-cases/01-onboarding.adoc[01-onboarding.adoc]
|Making a machine ready, guided or automatically: the languages, the harnesses (one scan, one default), the models for the work, the models of the roles, where credentials are kept, the providers of the machine, and how plans run by default.

|`UC-ENT`
|link:use-cases/02-entry.adoc[02-entry.adoc]
|Getting to work: the first command after installing, the onboarding when the machine is not ready, the web app connected from a desktop or over SSH; managing the paired devices.

|`UC-PLN`
|link:use-cases/03-plans.adoc[03-plans.adoc]
|Working with running plans and epics: seeing what runs across projects, following a plan down to its parts, deciding what a plan asks, designing a plan's process, and following an epic; the work that ended.

|`UC-PRJ`
|link:use-cases/04-projects.adoc[04-projects.adoc]
|Bringing a project in and finding it again: onboarding a project (enrolment and setup, the machine's values as the proposal), and releasing a project; exploring the projects with favourites, recent and most used, from which an epic or a plan is started.

|`UC-STA`
|link:use-cases/05-starting-work.adoc[05-starting-work.adoc]
|Starting work: a plan or an epic from its sources (descriptions, documents, issues of GitHub, GitLab, or Codeberg, lessons, local changes, pull requests), gathered and stored by the server in a source directory; running a recipe; decomposing an epic into plans with the operator.

|`UC-CTL`
|link:use-cases/06-controlling-work.adoc[06-controlling-work.adoc]
|Controlling work: pausing, starting, cancelling, and abandoning a plan, its epic always told; an epic's next plan, cancel, and archive once it is through; reviewing an epic's findings and watches item by item with its planning role; resolving what holds a plan.
|===
