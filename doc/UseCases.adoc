== Overview

The use cases describe what a person does with `PM-MCP` and what they get out of it, from their point of view and in their words. They come before the link:Requirements.adoc[Requirements]: a use case names the requirements that serve it, and a use case that no requirement serves yet shows what the requirements still lack. The operator acts only in the two clients, the web app and the terminal client; a coding agent is a worker the runtime runs, never a place where the operator is asked or answers (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/workflow-dsl/02-units-jobs-decisions.adoc#clients-only[Workflow DSL & Engine Specification, All Interaction in the Operator's Clients]). There is one set of use cases for both clients: a use case says what the operator achieves, never how a client shows it. How each client shows it is worked out in its design, which is the specification of the client's implementation and lives with its code (link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/README.adoc[`pm-mcp-clients`, Design]); how the system does it, in the link:Specification.adoc[Specification].

== Conventions

* *Identifier*: every use case has a stable anchor `[#UC-<AREA>-<N>]` and the heading `== UC-<AREA>-<N>: <title>`. A number is never reused.
* *One module per area*: `use-cases/NN-<area>.adoc`, listed in <<index>>.
* *Client-neutral*: a use case is cut by subject, never by client; it names a client at most as where the operator acts ("in the web app or in the terminal client"), never its screens, commands, or keys. The two exceptions are bound to one client by their nature: link:use-cases/02-entry.adoc#UC-ENT-1[UC-ENT-1], whose first command after installing is typed in a terminal, so it is bound to the terminal client and names its steps; and link:use-cases/03-plans.adoc#UC-PLN-3[UC-PLN-3], designing a process, which needs a unit's text beside its structure and is offered by the web app only.
* *Status*: each use case states one of `DRAFT` (not yet agreed by the operator; its open points named where there are any), `AGREED` (the operator agreed to it; requirements and design may be derived from it).
* *Flow form*: the form of a flow follows what the use case is. A use case whose process the server runs has a state diagram (*Processes*, below). A use case that only shows something, a view the operator reads with no process of the server behind it, has numbered steps, one per part of the view as the operator reads it (link:use-cases/03-plans.adoc#UC-PLN-1[UC-PLN-1], link:use-cases/03-plans.adoc#UC-PLN-4[UC-PLN-4], link:use-cases/03-plans.adoc#UC-PLN-5[UC-PLN-5], link:use-cases/04-projects.adoc#UC-PRJ-2[UC-PRJ-2], link:use-cases/07-system.adoc#UC-SYS-2[UC-SYS-2]).
* *Processes*: a use case whose process the server runs is modelled as a workflow, and a step of it that is a process of its own as a sub-workflow with a use case of its own, or with the specification that defines it, as `chat` in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue.adoc#chat[State Catalogue, Chatting with the Planning Role: `chat`]. Its flow is drawn as an ASCII state diagram in a `[source,text]` block: one line per state, named as the state would be named in the workflow unit; the arrows carry the outcomes. The diagram shows the process, never a screen. One legend holds for every diagram, and no diagram repeats it:
** `[S]` the server acts.
** `[O]` the operator chooses; every choice offered to the operator is `[O]`.
** `[M]` a model acts through a role task.
** `[C]` the operator's client acts on its own (only in UC-ENT-1).
** `↳` a call of a sub-workflow.
** `[O]⇄[M]` an exchange between the operator and a model.
** `←` after an option: the option preselected.
** `done`, or `<unit>.done` where the unit names its end state (`language.done`, `harness.done`): the process ends; a sub-workflow returns to its caller.
** an unmarked state at the end (`init.*`, `epic.active`, `plan.paused`): the process hands over to that state of its workflow (`init.*`: the plan's first phase).
* *No macros in diagrams*: a `[source,text]` block renders no cross reference (`&lt;&lt;…&gt;&gt;`) and no `link:`; a diagram names a use case or a state by its plain id (`UC-STA-5`), and where a link helps, the prose below the diagram carries it.
* *Requirements*: the part names first the requirements that serve the use case, each linked to its anchor in its domain file with what it serves, and after them where the parts are specified; where no requirement serves the use case, or a part of it, it says "none yet". A requirement is never named that does not exist.
* *Design*: the part lists, in this order, the shared design (what both clients show) where there is one, the terminal client's, and the web app's; where the web app has no design document yet, the line says so in one phrase, "the web app: no design document yet; designed by its package", and links the package of `pm-mcp-clients` that designs it.
* [[changes]]*Changes*: a use case states what it needs. While it is `DRAFT`, the changes of the requirements and specifications it needs are written in a _Changes to the Specification_ part of its module, each the fix of a gap, and named in its _Changes_; once it is `AGREED`, they are written into the requirements and specifications, and the part is removed.
* *Shape*: each use case has the parts of the template below; a part that does not apply is left out, never filled with filler.

[source,asciidoc]
----
[#UC-<AREA>-<N>]
== UC-<AREA>-<N>: <title>

Status:: `DRAFT`
Actor:: who does it (the operator, a reviewer, ...).
Goal:: what they want to achieve, in one sentence.
Trigger:: what makes them start.
Preconditions:: what holds before.
Flow:: the state diagram of the process the server runs; for a view, the steps, numbered, as the actor experiences them.
Variations:: other ways through, and what happens when something fails.
Outcome:: what holds afterwards.
Open points:: what is not decided yet.
Changes:: the changes of the requirements and specifications it needs, each modelled as the fix of a gap (while DRAFT; *Changes*, above).
Requirements:: the requirements that serve it (link:Requirements.adoc[Requirements]).
Design:: the design documents that show it, per client (link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/README.adoc[`pm-mcp-clients`, Design]).
----

[#open-points]
== Open Points

An open point lives where it arises: in the _Open points_ part of a use case, or, where it waits for a decision of the operator that the requirements and specifications depend on, in link:discussions/open-questions.adoc[Open Questions]. This section lists every one of them; it holds no open point of its own. What the use cases do not cover yet is decided before a use case is written for it.

* `UC-ONB`: whether a maker's icon may be shown at all, and which icons may be bundled, a legal question (link:discussions/open-questions.adoc#harness-icons[Open Questions, Showing a Maker's Icon]); the message format of the catalogue of the interface's texts, plurals and arguments (link:discussions/open-questions.adoc#message-format[Open Questions, The Message Format of the Catalogue]).
* `UC-PLN`: designing a unit for one plan only and promoting it to the project, and a model's help in designing, are not offered now (link:use-cases/03-plans.adoc#UC-PLN-3[UC-PLN-3], _Open points_).
* `UC-SYS`: which credential the runtime presents to the organisation's registry, and the form of a release in it (link:discussions/open-questions.adoc#registry-credential[Open Questions, The Credential for the Organisation's Registry and the Form of a Release]); which library implements the registry of the runtime's metrics, a dependency decision of the operator (link:discussions/open-questions.adoc#metrics-library[Open Questions, The Library of the Runtime's Metrics]).
* `UC-ENT`, `UC-PRJ`, `UC-STA`, `UC-CTL`: nothing open.

Not offered, by the operator's decision: pausing an epic as a whole. Its plans are paused one by one (link:use-cases/06-controlling-work.adoc#UC-CTL-1[UC-CTL-1]); a pausing or paused plan keeps its place among the epic's running plans, and switching automatic off stops new starts (link:use-cases/06-controlling-work.adoc#UC-CTL-2[UC-CTL-2]).
