= Use Cases: Projects (UC-PRJ)
:toc: left
:toclevels: 2
:nofooter:

link:../UseCases.adoc[Use Cases] » Projects

The operator brings a project into `PM-MCP` and finds it again: onboarding a project (its enrolment and its setup, with the machine's values as the proposal), and exploring the enrolled projects, from which the operator starts an epic or a plan, or looks at the project's running work. The operator does this in the web app or in the terminal client; how each shows it is its design (link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/README.adoc[`pm-mcp-clients`, Design]).

[#UC-PRJ-1]
== UC-PRJ-1: Onboard a Project

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client.
Goal:: get from a repository checkout to a project in which plans and epics can run, in one guided run: enrolled, set up for the team, and configured for the operator, starting from what the machine already provides and asking only for what the project needs of its own.
Trigger:: the operator adds a project in the explorer (<<UC-PRJ-2>>); a client started in a checkout proposes that checkout. A later run of one aspect of a project starts from the project in the explorer.
Preconditions:: the machine is onboarded (link:01-onboarding.adoc#UC-ONB-1[UC-ONB-1]).
Flow::
+
[source,text]
----
  [O] project.checkout         the checkout of the repository: a path; a
       │                       client started in a checkout proposes it
       ▼
  [O] project.consent          may the server look at the checkout? (its git
       │                       configuration, build wrappers, host tools,
       │                       language servers, project scripts: it reads
       │                       the checkout and runs the host tools' version
       │                       probes; changes nothing)
       ├── no ──────────────► stays at project.consent
       ▼ yes | yes, don't ask again
  [S] project.detect           the remote, the base branch, the build wrappers,
       │                       the host tools the project uses, the language
       │                       servers, the scripts; a check line for each
       ├── something of the checkout must run to be known ──►
       │      [O] project.run-consent   may the server run these scripts of
       │           │                    the checkout? (each named with its
       │           │                    arguments, confined like a job)
       │           ├── no ──► project.identity, what needs the scripts
       │           │          unknown; not asked again in this run
       │           ▼ yes | yes, for this project
       │      [S] project.probe          the named scripts, confined
       ▼
  [O] project.identity         the project's id, proposed from the remote's
       │                       name; its display name; while this version of
       │                       PM-MCP keeps the plan lifecycle closed (the
       │                       lifecycle gate), whether the project is a
       │                       pilot, and what that means
       ▼
  [O] project.enrolment        everything to be enrolled, each with where it
       │                       comes from (detected, the machine, the default);
       │                       the container engine only as a separate choice
       │                       with its warning
       ▼
  [S] project.enrol            the enrolment and the project's machine store
       ▼
  [S] setup.entry,             the run recorded as a first run; .marshall/config/
      setup.prepare-workspace, created, holding no unit copy (the project takes
      setup.check-operator-files  the machine's or the default unit until its
                               team places one); the operator file and the
                               role set validated
       ▼
  [O] project.operator         the operator's values of the project, each with
       │                       the machine's value as the proposal: the model
       │                       language, the allowed models, the role
       │                       assignment, the method and asking axes, the
       │                       integration variant and credential of each
       │                       provider, the commit identity
       ├── models, roles ────► ↳ the model catalogue (UC-ONB-5) and the role
       │                         assignment (UC-ONB-6) of the project ─►
       │                         project.operator
       ▼
  [S] setup.probe-integration-variants,   each integration's variant valid,
      setup.verify-credentials            its credential or CLI tool acting
       ├── a variant invalid ──► project.operator, its findings named
       ├── a credential missing, a check fails ──► [O] setup.needs-repair
       │                         names the credential and the act that enters
       │                         or replaces it; retry runs the check again
       ▼
  [O] setup.project-settings   the team's settings: base branch, branch
       │                       prefix, lanes
       ▼
  [S] setup.detect-domains     the domains that apply (Java, Python,
       │                       JavaScript, documentation, ...) from their
       │                       descriptors and files
       ▼
  [S] setup.discover-modules   the modules the parser of each build system
       │                       finds (Maven, Gradle, npm, Python)
       ▼
  [O] setup.seed-build-map     the build map derived from the modules,
       │                       confirmed or its routes customised
       ▼
  [O] setup.select-providers   the team's providers: the CI provider derived
       │                       from the remote (or overridden), the code
       │                       analysis providers, the review bots
       ▼
  [O] setup.configure-finalize the finalize steps and the landing variant
       │                       (landing.pull-request, landing.main,
       │                       landing.files); a machine default that does
       │                       not fit the project is refused with the reason
       ▼
  [S] setup.probe-merge-queue  only where the base branch has no enforced
       │                       merge queue and could have one:
       │                       [O] setup.merge-queue (recheck | skip)
       ▼
  [S] setup.probe-qualification  the roles to grade and the expected tokens of
       │                       their grading
       ├── nothing to grade ─► setup.probe-enrichment
       ▼ roles to grade
  [O] setup.qualify-consent    the qualification's expected tokens (consent
       │                       kind model_cost)
       ├── no ──► setup.probe-enrichment, the qualification skipped with
       │          its reason, to be run later
       ▼ yes
  [M] setup.qualify-roles      role qualification, the grading's worker jobs
       ▼
  [S] setup.probe-enrichment   the modules to describe, whether the role
       │                       enrich is qualified, the expected tokens
       ├── nothing to describe, or enrich unqualified ──►
       │      setup.commit-changes (the unenriched modules named, offered
       │      again by a later run once enrich qualifies)
       ▼ modules to describe
  [O] setup.enrich-consent     the enrichment's expected tokens (model_cost)
       ├── no ──► setup.commit-changes, the description skipped with its
       │          reason, to be run later; the project is ready without
       ▼ yes
  [M] setup.enrich-architecture  each module's responsibility, purpose, and
       │                       key packages, by the role enrich, one task per
       │                       module; the architecture is written to
       │                       .marshall/project-architecture/
       ▼
  [O] setup.commit-changes     the team's configuration to commit, or to leave
       ├── leave ───────────► project.completed, left to commit
       ▼ commit
  [S] setup.land-changes       one commit, pushed where there is a push remote
       ▼
  project.completed            names what comes next: an epic, a plan,
                               or the project's running work
----
Variations::
* *Machine values as the proposal.* Every value the project can take from the machine is proposed from it and marked so; accepting it records nothing for the project, which keeps following the machine. Only a changed value is recorded for the project (link:01-onboarding.adoc#machine-defaults[The machine sets defaults]).
* *The architecture is the setup workflow's work, typed by the project*: the domain descriptors and the build systems the project uses decide what is detected, discovered, and enriched (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/domain-extensions/01-four-axis-architecture.adoc[Four-Axis Domain Architecture], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/domain-extensions/03-module-discovery.adoc[Module Discovery]); a project of a type no other descriptor covers is set up with the domain `general-dev`; a later run of the setup reconciles the architecture with the checkout.
* *A later run of one aspect* opens its states with the project's current values, as the first run and a later change are one process. A later run of the whole setup takes the reconcile path of the Setup State Machine, unchanged (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/domain-extensions/04-setup-state-machine.adoc#project-setup-state-machine[Project Setup State Machine]).
* *Two workflows, one flow*: the flow draws the project's onboarding (`project.*`) and the setup it calls (`setup.*`) as one run. The onboarding calls the setup at its entry `first_run` after the enrolment, runs `project.operator` when the setup asks for the operator's values, and calls the setup again at `integrations`; a later run of the whole setup takes the entry `reconcile`, and one aspect alone the entry `aspect` (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/15-project-onboarding.adoc#state-catalogue-project-onboarding[State Catalogue, Project Onboarding]).
* *A step that cannot pass* (a credential refused, a tool missing, the modules not discoverable) shows its check line with the cause and the fix and waits for the operator in `setup.needs-repair`, whose retry runs the step again; the project is enrolled but not ready until it passes.
* *An enrolled project without setup*, such as one enrolled with `pm-operator enrol`, continues at its setup.
* *A released project* is offered to be enrolled again, which reopens its plan lifecycle.
* *An operator value changed in two clients at once* is refused against an older value with `conflict`, as in link:01-onboarding.adoc#UC-ONB-10[UC-ONB-10] (link:../specification/cli-and-security/01-cli-and-installer.adoc#concurrent-changes[CLI, Coordination & Security Specification, Concurrent Changes of a Setting]).
Outcome:: the project is enrolled and set up, its architecture discovered and described (or the description skipped, to be run later); its team configuration is committed or left to commit; it takes from the machine what it does not set itself.
Requirements:: link:../requirements/15-extensions-and-recipes.adoc#PM-EXT-8[PM-EXT-8] (the onboarding as one process, the operator's values of the project), link:../requirements/08-security.adoc#PM-SEC-8[PM-SEC-8] (the consents `inspect_checkout`, `run_checkout_scripts`, `model_cost`), link:../requirements/15-extensions-and-recipes.adoc#PM-EXT-3[PM-EXT-3] (module discovery, build map, architecture enrichment), link:../requirements/15-extensions-and-recipes.adoc#PM-EXT-6[PM-EXT-6] (team and operator values), link:../requirements/06-execution.adoc#PM-EXEC-2[PM-EXEC-2] (the enrolment as the source of execution), link:../requirements/11-migration.adoc#PM-MIG-1[PM-MIG-1] (the lifecycle gate), link:../requirements/01-architecture.adoc#PM-ARCH-11[PM-ARCH-11] (concurrent changes); the onboarding is specified in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#project-onboarding[Credentials & Enrolment Specification, Onboarding a Project as One Process] with its states in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/15-project-onboarding.adoc#state-catalogue-project-onboarding[State Catalogue, Project Onboarding], the enrolment in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#enrolment-lifecycle-release[Enrolment, Lifecycle Gate & Release], the setup in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/domain-extensions/04-setup-state-machine.adoc#project-setup-state-machine[Setup State Machine], the levels in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/08-project-configuration-local.adoc#project-levels[Project Values over Machine Values].
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/project-onboarding.adoc[Project Onboarding] (shared); link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/17-projects.adoc[Terminal Client, Projects]; the web app: no design document yet; designed by its package link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/plans/implemented/web-projects.adoc[`web-projects`]

[#UC-PRJ-2]
== UC-PRJ-2: Explore Projects

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client.
Goal:: find a project among many quickly, see its state at a glance, and from it start an epic, start a plan, or look at its running work.
Trigger:: the operator opens the projects of the machine.
Flow::
. *Favourites first*: the projects the operator marked as favourites, in the operator's order.
. *Recent*: the projects the operator worked with last, newest first.
. *All projects*: every enrolled project, ordered by name, with a filter; and as a second order, the most used: the projects the operator worked with most over the last weeks.
. *A project* shows its display name, whether it is ready (set up, or what its setup still needs), whether something in it needs the operator, its active plans and epics, and when it was last active.
. *Selecting a project* offers its actions: _add an epic_ (link:05-starting-work.adoc#UC-STA-2[UC-STA-2]), _add a plan_ (link:05-starting-work.adoc#UC-STA-1[UC-STA-1]), _running work_ (the project's level of link:03-plans.adoc#UC-PLN-4[UC-PLN-4]), _ended work_ (its ended plans and epics, newest first), and its setup (<<UC-PRJ-1>>, a later run), from which it is also released or unenrolled (<<UC-PRJ-3>>). A project that is not ready offers its setup first.
. *Being added*: a project whose onboarding has not reached its enrolment has no project id yet; it is listed apart, by the path of its checkout and the step it waits at, only while there is one, to continue where it stopped or to abandon (<<UC-PRJ-1>>).
. *Marking*: the operator marks and unmarks a favourite and orders the favourites; the marks are the operator's, the same in both clients.
Variations:: a project that is released is listed with that mark and offers to be enrolled again; an unenrolled project is not listed. _Recent_ and _most used_ count what the operator did in a project in either client: opening it, starting an epic or a plan, answering a decision, changing its configuration.
Outcome:: the operator has found the project and is on the way to an epic, a plan, or its running work.
Requirements:: link:../requirements/01-architecture.adoc#PM-ARCH-11[PM-ARCH-11] (the projects of the machine with display name, readiness, running work, favourites, and recent use), link:../requirements/08-security.adoc#PM-SEC-7[PM-SEC-7] (the dependable view); the projects are specified in link:../specification/runtime-model/01-processes-and-transport.adoc#project-explorer[Runtime & Interaction Model Specification, The Projects of the Machine] and link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/12-machine-stores.adoc#explorer-store[The Operator's Projects (`explorer.json`)].
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/project-explorer.adoc[Project Explorer] (shared); link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/17-projects.adoc[Terminal Client, Projects]; the web app: no design document yet; designed by its package link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/plans/implemented/web-projects.adoc[`web-projects`]

[#UC-PRJ-3]
== UC-PRJ-3: Release a Project

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client.
Goal:: take a project out of `PM-MCP`'s work, for a while (release) or for good (unenrol), knowing what happens to its running work.
Trigger:: the operator chooses _Release_ or _Unenrol_ in the project's setup (<<UC-PRJ-2>>).
Preconditions:: the project is enrolled; for _Release_, it is not released.
Flow::
+
[source,text]
----
  [O] project.release-confirm  what it does: releasing ends every plan of
       │                       the project with the outcome released,
       │                       whatever its state, and every epic with the
       │                       reason released, each archived in the
       │                       project's machine store (an epic's ledger
       │                       stays in .marshall/epics/); it deletes
       │                       the pending entries, ends a running onboarding
       │                       of the project, and closes its plan lifecycle;
       │                       unenrolling is refused while work runs and
       │                       removes the enrolment; the reason
       ├── unenrol, work runs ──► refused, the running work listed, each
       │                          leading to its actions
       ▼ confirm
  [S] project.release-wait     a running short landing of the project
       │                       (git.land-removal, git.land-unit) finishes
       │                       first, within its bound
       ├── not finished in its bound ──► refused, nothing ended; the
       │                                 landing named
       ▼
  [S] project.release          the pending entries deleted with their
       │                       sources, a running onboarding ended, every
       │                       plan and epic ended as released, then the
       │                       lifecycle closed; or the enrolment removed,
       ▼                       the project's machine store kept
  released | unenrolled        a released project stays listed, offering to
                               be enrolled again; an unenrolled one leaves
                               the list
----
Variations::
* *Plans in every state*: a running, pausing, paused, waiting, or held plan ends alike, with the outcome `released`, never `cancelled` or `abandoned`, and is archived; its branch stays.
* *Epics*: an epic ends with the `terminal_reason` `released`; its plans end with the release, so nothing is left to tell it. It is archived in the project's machine store only: its ledger stays in `.marshall/epics/` as it is, nothing is committed, and no epic landing runs.
* *Pending entries*: an entry not yet started as a plan or an epic is deleted with the sources it holds.
* *A running onboarding of the project* (a later run of one of its aspects, <<UC-PRJ-1>>) is ended where it stands; the next run starts afresh.
* *A running short landing* (`git.land-removal`, the landing of a moved source, link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/filesystem-layout/03-project-store.adoc#source-directory[Filesystem Layout Specification, The Source Directory (`sources/`)]; `git.land-unit`, the landing of a placed workflow unit, link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/workflow-dsl/04-ast-node-model.adoc#process-designer[Workflow DSL & Engine Specification, Designing a Process]) is let finish before anything ends, so no landing is left half done; the release waits for it within its bound (`release.landing_wait_seconds`) and is refused, ending nothing, when the landing does not finish in it.
* *What stays and what goes*: neither act touches the repository; its `.marshall/` (the team's configuration, the epics' ledgers, the architecture) belongs to the team and stays as it is. Unenrolling removes the enrolment and nothing else: the project's machine store (`<PM_MCP_BASE>/projects/<project_id>/`), with the archive of its ended plans and epics, stays byte for byte until the operator deletes it in the cleanup, as a whole, once it has been unenrolled for its duration (link:07-system.adoc#UC-SYS-3[UC-SYS-3]; link:../concepts/enrolment.adoc#unenrol[Enrolment, Unenrol]; link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#enrolment-lifecycle-release[Enrolment, Lifecycle Gate & Release]). Enrolling the project again from the same checkout finds its store and its archive again; from another checkout it is refused (`project_store_root_mismatch`). Once the cleanup deleted the store, enrolling again starts a new one.
Outcome:: the project runs no work of `PM-MCP`; released, it can be enrolled again with its values.
Requirements:: link:../requirements/11-migration.adoc#PM-MIG-5[PM-MIG-5] (the release), link:../requirements/06-execution.adoc#PM-EXEC-2[PM-EXEC-2] (the unenrolment), link:../requirements/02-workflow.adoc#PM-WF-23[PM-WF-23] (operator acts on plans and epics), link:../requirements/01-architecture.adoc#PM-ARCH-10[PM-ARCH-10] (the unenrolled store as a cleanup item); the release is specified in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#project-release[Credentials & Enrolment Specification, Releasing Ends Work as the Operator Ends It], the unenrolment in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#enrolment-lifecycle-release[Enrolment, Lifecycle Gate & Release], the archives in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/filesystem-layout/03-project-store.adoc#archives[Filesystem Layout Specification, Archives], the bound in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/timeouts/01-job-budgets-and-waits.adoc#release-landing-wait[Release Landing Wait].
