= Use Cases: Starting Work (UC-STA)
:toc: left
:toclevels: 2
:nofooter:

link:../UseCases.adoc[Use Cases] » Starting Work

The operator starts a plan or an epic in a project from what the work comes from: a description, documents, issues, a lesson, the checkout's local changes, a pull request, or a recipe. The operator does this in the web app or in the terminal client, which are the only places where the operator acts (<<change-clients-only>>); how each shows it is its design (link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/README.adoc[`pm-mcp-clients`, Design]).

[#principles]
== Principles

[#machinery-gathers]
Machinery gathers, models read:: Gathering a source is the server's work: it fetches, checks, creates the directories, and stores every source of a plan or an epic in its source directory. The only model step while a source comes in is the screening of what came from outside the machine. A model works with a source only once it is stored locally, and an external one only once it is screened.
[#local-is-own]
What is on this machine is the operator's own:: The operator's description and the documents on this machine are trusted as the checkout's code is trusted, and are not screened; what comes from outside the machine (an issue, a pull request) is untrusted until screened.
[#sources-first]
Sources first, the rest when needed:: Starting asks only what the work comes from. What the plan or the epic needs beyond that (its posture, its base branch, the outline review) is asked where it is first needed, and not at all where the project or the machine sets a value. How many plans an epic runs at once is never asked: it is the project's setting, raised by the operator later.

[#UC-STA-1]
== UC-STA-1: Start a Plan

Status:: `DRAFT`
Actor:: the operator, in the web app or in the terminal client.
Goal:: start a plan in a project from everything it should start from, in one guided run, and see it run.
Trigger:: the operator chooses _Add a plan_ on a project (link:04-projects.adoc#UC-PRJ-2[UC-PRJ-2]), after a project's onboarding (link:04-projects.adoc#UC-PRJ-1[UC-PRJ-1]), or in the terminal client in a checkout, whose project is the proposal; or accepts a follow-up plan in a chat about ended work (link:03-plans.adoc#change-ended-work[Ended Work]), which opens the start with its description stored.
Preconditions:: the project is enrolled and ready; the machine is onboarded.
Flow::
+
[source,text]
----
  [S] start.open               the setup gate (the machine onboarded, the
       │                       project ready); the entry of the project and
       │                       its source directory, empty; the facts:
       │                       the project's recipes, its unclaimed lessons,
       │                       whether the checkout has local changes
       ▼
  [O] start.choose             a plan from sources, or a recipe
       ├── recipe ───────────► ↳ recipe (UC-STA-5)
       ▼ sources
  [O] start.sources            the sources gathered so far, each with its
       │                       state; add one, remove one, chat, start;
       │                       only the kinds that combine with those
       │                       already there are offered: a pull request
       │                       or the local changes only with descriptions
       │                       and documents, and never both
       ├── description ──────► [S] start.store-description ─► start.sources
       ├── chat ─────────────► ↳ chat (UC-CTL-1) with the role refine, over
       │                         the entry; an accepted description
       │                         ─► start.store-description
       ├── documents ────────► ↳ source-documents (UC-STA-3) ─► start.sources
       ├── issue ────────────► ↳ source-issue (UC-STA-4) ─────► start.sources
       ├── lesson ───────────► ↳ source-lesson (UC-STA-8) ────► start.sources
       ├── local changes ────► ↳ source-local-changes (UC-STA-9) ► start.sources
       ├── pull request ─────► ↳ source-pr (UC-STA-7) ────────► start.sources
       ▼ start, every source stored and none unscreened
  [O] start.ready              what the plan starts from, its title and id
       │                       proposed from the sources, both changeable
       ├── the landing does not fit the sources ──► the reason; start.ready
       ▼ create
  [S] start.create             re-checks what creation needs; creates the
       │                       plan; the source directory becomes the plan's
       ├── something changed meanwhile ──► start.ready, with the cause
       ▼
  init.*                       the plan runs (UC-PLN-1); what it needs and
                               has no value for is asked where it is first
                               needed
----
+
The sub-workflows are the recipe (<<UC-STA-5>>), the chat (link:06-controlling-work.adoc#UC-CTL-1[UC-CTL-1]), and the sources: documents (<<UC-STA-3>>), an issue (<<UC-STA-4>>), a lesson (<<UC-STA-8>>), the local changes (<<UC-STA-9>>), a pull request (<<UC-STA-7>>). The plan then runs as in link:03-plans.adoc#UC-PLN-1[UC-PLN-1], and what it still needs is asked when needed (<<change-options-when-needed>>).
Variations::
* *Several sources*: a plan starts from any number of descriptions, documents, issues, and lessons together; each is stored on its own in the source directory (<<change-source-directory>>). A pull request and the local changes decide how the plan runs (it adopts the pull request, or it lands the changes) and therefore start a plan alone or with descriptions and documents only; `start.sources` offers only the kinds that combine with those already in the list.
* *A landing that does not fit the sources* is refused at `start.ready` with the reason: a plan from the local changes needs a landing that commits, so `landing.files` is refused for it (<<UC-STA-9>>).
* *A source that fails* (an issue not found, a document not readable) stays in the list with its cause, to be tried again or removed; the plan cannot start while a source is not stored, or an external one not screened or accepted.
* *Leaving*: the entry keeps its sources while the operator is away, in either client; abandoning it deletes its source directory, and nothing of a plan exists before `start.create`. An entry never expires: like a decision it has no time limit, and it stays among the project's open entries, offered to continue in either client, until it is started or abandoned (<<change-start-from-clients>>).
* *A lesson* is checked against the current checkout first; one whose premise no longer holds is shown with its evidence, to be used anyway or retired (link:../specification/state-catalogue/09-bootstrap-and-lessons.adoc#state-catalogue-source[Source States]).
* *A chat about the entry* is offered once a source is stored and every external one screened, never for a recipe, and disabled with its reason while the role `refine` does not qualify: what the model understood, what is unclear, what is out of scope. Its one change is a description, rewritten or added, stored after its read-back; it never touches another source, and starting never waits for it. Its transcript stays with the entry, becomes the plan's at `start.create` without being a source, and is deleted with an abandoned entry; a chat still open then is ended first, its transcript complete (link:06-controlling-work.adoc#change-chat[Chatting with the Planning Role]).
* *An epic's plan* is started by the epic itself, without the operator; its source is the epic's staged section, stored in the plan's source directory like any other.
Outcome:: the plan exists, with every source it starts from in its source directory, and runs; the operator sees it in Running Work (link:03-plans.adoc#UC-PLN-4[UC-PLN-4]).
Changes::
* *All interaction in the operator's clients* (<<change-clients-only>>).
* *Starting from the clients* (<<change-start-from-clients>>), with a chat about the entry (link:06-controlling-work.adoc#change-chat[Chatting with the Planning Role]).
* *The source directory* (<<change-source-directory>>).
* *Asked when needed* (<<change-options-when-needed>>).
Requirements:: link:../requirements/02-workflow.adoc#PM-WF-10[PM-WF-10], link:../requirements/02-workflow.adoc#PM-WF-15[PM-WF-15]; the bootstrap is specified in link:../specification/state-catalogue/09-bootstrap-and-lessons.adoc#state-catalogue-bootstrap[Bootstrap States], the sources in link:../specification/phase-workflows/01-planning-phases-1-2.adoc[Planning Phases 1–2] (Plan Source Contracts).
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/starting-work.adoc[Starting Work]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/18-starting.adoc[Terminal Client, Starting Work]; the web app: no design document yet; designed by its package link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/plans/web-start.adoc[`web-start`]

[#UC-STA-2]
== UC-STA-2: Start an Epic

Status:: `DRAFT`
Actor:: the operator, in the web app or in the terminal client.
Goal:: start an epic for an initiative that needs several plans, from everything that describes it, and let it cut the work into plans.
Trigger:: the operator chooses _Add an epic_ on a project (link:04-projects.adoc#UC-PRJ-2[UC-PRJ-2]).
Preconditions:: the project is enrolled and ready; the machine is onboarded.
Flow::
+
[source,text]
----
  [S] start-epic.open          the entry and its source directory, empty
       ▼
  [O] start-epic.sources       the sources gathered so far, as in UC-STA-1:
       │                       descriptions, documents, issues; add one,
       │                       remove one, chat, start
       ├── description ──────► [S] start-epic.store-description
       ├── chat ─────────────► ↳ chat (UC-CTL-1) with the role decompose,
       │                         as in UC-STA-1
       ├── documents ────────► ↳ source-documents (UC-STA-3)
       ├── issue ────────────► ↳ source-issue (UC-STA-4)
       ▼ start, every source stored and none unscreened
  [O] start-epic.ready         the epic's title and id, proposed
       │                       from the sources, both changeable; its
       │                       mode (automatic or not) shown as the value
       │                       in force, never asked
       ▼ create
  [S] start-epic.create        the ledger, into which the source directory
       │                       moves, committed and landed; the epic's
       │                       machine store
       ▼
  ↳ decomposition              the role decompose drafts the workstreams
       │                       and the staged plans from the stored sources;
       │                       the operator reviews and shapes them before
       │                       anything is committed (UC-STA-6)
       ▼
  epic.*                       the epic runs and, with automatic on, starts
                               its plans; how many run at once is the
                               project's setting (machine default 1), never
                               asked
----
+
The sub-workflows are the chat (link:06-controlling-work.adoc#UC-CTL-1[UC-CTL-1]), the sources (<<UC-STA-3>>, <<UC-STA-4>>), and the decomposition (<<UC-STA-6>>).
Variations::
* *Documents are the usual source* of an epic: a concept, a specification, a directory of them. They are stored as they are; a directory keeps its tree.
* *Adopting* an epic that exists in the ledger but not on this machine (another machine started it) is offered instead of a new one, as today (link:../specification/state-catalogue/09-bootstrap-and-lessons.adoc#state-catalogue-bootstrap-epic[Epic Bootstrap]).
* *Its plans and the epic communicate through the server*: a plan sends to its epic's inbox, and the epic to a plan's mailbox (link:../specification/model-work/08-epic-coordination.adoc#plan-scope-outbox-link[Plan-Scope Outbox Link], link:../specification/model-work/08-epic-coordination.adoc#plan-mailbox[Plan Mailbox]); no text passes from one to the other through the operator.
* *How many plans run at once* is the project's `epic.parallelization_scope`, its machine default 1, and is never asked at the start. The operator raises it through the epic's _Next plan_, which offers to raise it by one when the scope is full (link:06-controlling-work.adoc#UC-CTL-2[UC-CTL-2]), or in the project's settings (<<change-options-when-needed>>).
* *Whether the epic starts its plans by itself* is the project's `epic.auto_start`, its machine default on, and is never asked at the start: the ready step shows the value in force, and the operator switches it on the epic at any time (link:06-controlling-work.adoc#UC-CTL-2[UC-CTL-2]).
* A source that fails, a chat about the entry (with the role `decompose`), leaving, and abandoning are as in <<UC-STA-1>>.
Outcome:: the epic exists with its sources stored and listed in its ledger, its workstreams and plans drafted from them and agreed by the operator; with automatic on it starts its plans as they become launchable, up to how many may run at once, and with it off it reports them as launchable and waits for the operator's _next plan_.
Changes::
* *All interaction in the operator's clients* (<<change-clients-only>>).
* *Starting from the clients* (<<change-start-from-clients>>), with a chat about the entry (link:06-controlling-work.adoc#change-chat[Chatting with the Planning Role]).
* *The source directory* (<<change-source-directory>>), including the epic's sources.
* *The decomposition is reviewed* (<<change-decomposition-review>>).
* *Asked when needed* (<<change-options-when-needed>>).
* *An epic runs by itself* (link:06-controlling-work.adoc#change-epic-auto[An Epic Runs by Itself]), for the mode shown at the ready step.
Requirements:: the epic workflow is specified in link:../specification/model-work/08-epic-coordination.adoc#epic-workflow[Epic Workflow], its ledger in link:../specification/store-schemas/04-epic-and-change-ledger.adoc#epic-header[Epic Header].
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/starting-work.adoc[Starting Work]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/18-starting.adoc[Terminal Client, Starting Work]; the web app: no design document yet; designed by its package link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/plans/web-start.adoc[`web-start`]

[#UC-STA-3]
== UC-STA-3: Bring in Documents

Status:: `DRAFT`
Actor:: the operator, in the web app or in the terminal client, while starting a plan or an epic.
Goal:: make one or more files, or a directory, a source of the work, copied or moved, without a model touching them on the way.
Trigger:: the operator adds documents in <<UC-STA-1>> or <<UC-STA-2>>.
Flow::
+
[source,text]
----
  [O] source-documents.pick     files or a directory on this machine; the
       │                        checkout's files first
       ▼
  [S] source-documents.check    each is a regular file, readable, within the
       │                        bounds of size and count; a directory is
       │                        listed with what it holds; links that lead
       │                        out of it are not followed
       ├── something fails ──► source-documents.pick, with the cause per file
       ▼
       ├── the machine sets copy or move ──► source-documents.store
       ▼ ask
  [O] source-documents.mode     copy or move, copy preselected; always
       │                        stores the choice as the machine's
       ▼
  [S] source-documents.store    copies or moves them into the source
       │                        directory, a directory with its tree; records
       │                        each with where it came from, its size, and
       │                        its digest
       ├── moved, and git tracks some of them ──►
       │      ↳ git.land-removal    a short landing: one commit that removes
       │                            them from git, landed by the project's
       │                            landing (landing.pull-request or
       │                            landing.main); with landing.files the
       │                            removal stays uncommitted in the
       │                            working tree
       ▼
  done                          the documents are a source, trusted
----
Variations::
* *Copy*: the originals stay where they are and are not managed: a later change of an original does not reach the source, and the source does not reach the original.
* *Move*: the documents leave where they were. A file outside git is deleted there; a file git tracks is removed from git by the short landing, so that the repository and the source never hold two versions of it. The source is stored at once, and the work may start while the landing runs; the landing shows in the project's running work until it is landed, and waits for the operator if it fails.
* *The machine's default* (`sources.documents_mode`) is _ask_: the operator chooses each time, with _copy_ preselected. Choosing _always_ with an answer stores _copy_ or _move_ as the machine's default, after which the choice is no longer asked; the machine's settings change it back (link:01-onboarding.adoc#UC-ONB-10[UC-ONB-10]).
* *Not screened*: documents on this machine are the operator's own (<<change-local-trusted>>); the deterministic level-1 validator does not run on them either, since nothing about them is external.
Outcome:: the documents are stored in the source directory, listed in its manifest; a moved document is gone from where it was, and from git once its removal is landed.
Changes::
* *Documents as a source* (<<change-documents>>).
* *What is on this machine is trusted* (<<change-local-trusted>>).
Requirements:: link:../requirements/08-security.adoc#PM-SEC-1[PM-SEC-1] (what is trusted); the sources are specified in link:../specification/state-catalogue/09-bootstrap-and-lessons.adoc#state-catalogue-source[Source States].
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/starting-work.adoc#documents[Starting Work, Documents]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/18-starting.adoc#plan[Terminal Client, Starting a Plan]; the web app: no design document yet; designed by its package link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/plans/web-start.adoc[`web-start`]

[#UC-STA-4]
== UC-STA-4: Bring in an Issue

Status:: `DRAFT`
Actor:: the operator, in the web app or in the terminal client, while starting a plan or an epic.
Goal:: make an issue of GitHub, GitLab, or Codeberg a source of the work, from the project's own repository or another one, fetched by the server and screened before any model reads it.
Trigger:: the operator adds an issue in <<UC-STA-1>> or <<UC-STA-2>>.
Flow::
+
[source,text]
----
  [O] source-issue.name        the issue: a number (the project's own
       │                       repository) or its URL
       ▼
  [S] source-issue.resolve     the forge (GitHub, GitLab, Codeberg or another
       │                       Forgejo), the repository, the provider, the
       │                       credential; a number becomes the issue's URL
       │                       in the project's repository
       ├── another repository, not granted ──► [O] source-issue.grant
       │                                          may the server read the
       │                                          issues of <owner/repo>?
       │                                          once, or for this project
       │                                          ─► source-issue.fetch;
       │                                          no ─► source-issue.failed
       ├── no credential for the forge ─────► source-issue.fetch without
       │                                       one: a public issue is read;
       │                                       another fails, naming the
       │                                       credential to add
       ▼
  [S] source-issue.fetch       a bounded job of the forge's provider: title,
       │                       body, labels, milestone, assignees, state, URL
       ├── fails ─────────────► [O] source-issue.failed   the cause (not
       │                             found, not readable, not granted, no
       │                             credential, rate limited until its
       │                             reset, provider unavailable); try
       │                             again, or remove it
       ▼
  [S] source-issue.store       the level-1 validator over title and body,
       │                       every change reported; stored in the source
       │                       directory, marked untrusted and unscreened
       ▼
  [M] source-issue.screen      the screener over the stored copy: the only
       │                       model step of bringing in a source
       ├── suspicious ────────► [O] source-issue.flagged   the flagged spans;
       │                             accept (recorded with its reason) or
       │                             remove it
       ├── the screener fails, or none qualifies ──► [O] source-issue.unscreened
       │                             the cause; the source stays unscreened:
       │                             try again, remove it, or accept it as
       │                             untrusted (recorded with its reason)
       ▼ clean
  done                         the issue is a source; models of the plan
                               read it as untrusted text
----
Variations::
* *Rate limited*: a fetch the forge refuses for its rate limit, with or without a credential, fails with the cause `rate_limited` and the time the limit resets. The operator tries again then, or, where the fetch ran without a credential, adds one for the forge, whose limit is higher (link:01-onboarding.adoc#UC-ONB-8[UC-ONB-8], or later link:01-onboarding.adoc#UC-ONB-10[UC-ONB-10]); the entry keeps the source in the list with its cause meanwhile.
* *A pull request* comes in the same way, through its own source (<<UC-STA-7>>).
* *The screening fails closed*: a screener that fails, or a role with no qualified configuration, leaves the source unscreened with the cause; no model reads it until it is screened again or the operator accepts it explicitly as untrusted (<<change-screen-stored>>).
* *Writing back* (the clarified request and the approved outline posted as comments) goes only to an issue of the project's own repository, and only where the project's team configuration enables it.
Outcome:: the issue is stored in the source directory with its fields and its screening verdict; nothing outside the screener has read it before.
Changes::
* *Issues by number or URL* (<<change-issues>>).
* *Codeberg and Forgejo* (<<change-forgejo>>).
* *Screened once stored* (<<change-screen-stored>>).
Requirements:: link:../requirements/08-security.adoc#PM-SEC-1[PM-SEC-1] (the two-level guard); the issue source is specified in link:../specification/state-catalogue/09-bootstrap-and-lessons.adoc#state-catalogue-source[Source States], the guard in link:../specification/model-work/07-untrusted-text-screening.adoc#two-level-guard[Two-Level Guard].
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/starting-work.adoc#issue[Starting Work, An Issue]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/18-starting.adoc#flagged[Terminal Client, A Flagged Issue]; the web app: no design document yet; designed by its package link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/plans/web-start.adoc[`web-start`]

[#UC-STA-5]
== UC-STA-5: Run a Recipe

Status:: `DRAFT`
Actor:: the operator, in the web app or in the terminal client.
Goal:: run a recurring kind of work the project or a domain has named and shaped as a workflow of its own (a coverage push, a dependency update, an audit), giving only its parameters.
Trigger:: the operator chooses a recipe in <<UC-STA-1>>.
Flow::
+
[source,text]
----
  [O] recipe.choose            the project's recipes, each with what it does;
       │                       the domain's and the project's own
       ▼
  [O] recipe.parameters        the recipe's parameters, each with its
       │                       options as the server resolves them (the
       │                       modules, the domains, a scope) and a proposal
       ├── a request-scoped recipe ──► start.sources of UC-STA-1, then here
       ▼
  [O] start.ready              as in UC-STA-1: the recipe and its
       │                       parameters, the title and id proposed from
       │                       the recipe and the time, both changeable
       ▼ create
  [S] recipe.create            re-checks what creation needs; creates the
       │                       plan, whose process is the recipe's workflow
       ├── something changed meanwhile ──► start.ready, with the cause
       ▼
  <recipe>.*                   the recipe's own phases, as sub-workflows
----
Variations::
* *A parameter without an option* (no module the recipe can work on, no domain of it in the project) is shown with its reason; the recipe cannot run, and the operator chooses another or leaves.
* *A recipe that is gone or changed* by the time of creation (its domain or the project removed or changed it), an id that was taken, or a gate that no longer holds returns to `start.ready` with the cause; nothing is created.
* *A request-scoped recipe* gathers its sources as in <<UC-STA-1>>, with their failures and screening; a chat is not offered for a recipe.
* *Leaving* keeps the entry with the recipe and the parameters chosen, in either client; abandoning it deletes the entry, as in <<UC-STA-1>>.
Outcome:: a plan runs the recipe's workflow with the parameters given.
Changes::
* *A recipe is a workflow* (<<change-recipe-workflow>>).
Requirements:: the recipes are specified in link:../specification/domain-extensions/05-recipes-and-extension-points.adoc[Recipes & Extension Points].
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/starting-work.adoc#recipe[Starting Work, A Recipe]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/18-starting.adoc#recipe[Terminal Client, Running a Recipe]; the web app: no design document yet; designed by its package link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/plans/web-start.adoc[`web-start`]

[#UC-STA-6]
== UC-STA-6: Decompose an Epic

Status:: `DRAFT`
Actor:: the operator, in the web app or in the terminal client, with the epic's planning role.
Goal:: get from what the epic starts from to its workstreams and plans, cut the way the operator wants them, before any plan starts.
Trigger:: a new epic (<<UC-STA-2>>); the operator's _decompose again_ (link:06-controlling-work.adoc#UC-CTL-2[UC-CTL-2]); or the epic's own finding that staged rows are stale (`epic.recut`).
Flow::
+
[source,text]
----
  [M] decomposition.draft      the role decompose reads the sources (and, on
       │                       a later run, the ledger: what shipped, what
       │                       runs, the operator's instruction) and drafts
       │                       the workstreams and per workstream the staged
       │                       plans: objective, deliverables, expected
       │                       surface, dependencies, order
       ▼
  [S] decomposition.check      the server's checks: the surfaces of plans
       │                       that may run together are disjoint, the
       │                       dependencies form no cycle, every plan has a
       │                       workstream; each finding shown with its plan
       ▼
  [O] decomposition.review     the workstreams and their plans, as a tree,
       │                       with the checks; per plan: keep, edit, drop;
       │                       add a plan in the operator's words; chat; or
       │                       for the whole: draft again with an instruction
       ├── edit, add ─────────► [O] decomposition.instruct   the operator's
       │                             words for the plan
       │                             ─► [M] decomposition.rewrite   the role
       │                             drafts or rewrites the plan
       │                             ─► [O] decomposition.read-back   old
       │                             against new: accept ─► decomposition.check;
       │                             instruct again ─► decomposition.instruct;
       │                             discard ─► decomposition.review
       ├── chat ──────────────► ↳ chat (UC-CTL-1) with the role decompose,
       │                             over the draft; an accepted change goes
       │                             into the draft ─► decomposition.check
       ├── draft again ───────► decomposition.draft, with the instruction
       ▼ agree, every check passing
  [S] decomposition.commit     the workstreams and the staged plans written
       │                       to the ledger and landed
       ▼
  epic.next-work               automatic on: the epic starts the plans
                               that can start, up to the scope; off: it
                               leaves them staged, reports them launchable
                               (epic.launchable), and waits for next plan
                               (UC-CTL-2)
----
+
The chat is the sub-workflow of link:06-controlling-work.adoc#UC-CTL-1[UC-CTL-1].
Variations::
* *A later run* keeps what shipped, what runs, and what is paused; it changes only staged plans, and the review shows each change against the staged plan it replaces.
* *A failing check* blocks _agree_ and names the plans concerned; the operator edits, drops, or has the plan drafted again.
* *Leaving* keeps the draft and the decisions made on it; the review continues where it stopped, in either client. The epic starts no plan before the first decomposition is agreed.
* *The operator's words* are interpreted with a read-back as in a decision (link:03-plans.adoc#change-own-words[Own Words]); a chat is the one of a plan or an epic (link:06-controlling-work.adoc#change-chat[Chatting with the Planning Role]).
Outcome:: the epic's workstreams and staged plans are in its ledger as the operator agreed them; the epic starts its plans from them by itself with automatic on, and with it off on the operator's _next plan_ (link:06-controlling-work.adoc#UC-CTL-2[UC-CTL-2]).

* *The decomposition is reviewed* (<<change-decomposition-review>>).

Trigger:: the operator adds a pull request in <<UC-STA-1>>.

+

----
  [O] source-pr.name           a number or the URL of a pull request of the

  [S] source-pr.observe        a bounded job: open? its head branch writable
       │                       by the agent identity? its title, body, and
       │                       changed files

       │      [O] source-pr.failed   the cause; try again, or remove it
       ▼
  [S] source-pr.store          title and body level-1 validated, stored
       │                       unscreened; the changed files stored as the
       │                       pull request's head, marked untrusted unless
       │                       the operator authored it

       │                                                or remove it

[#changes]
== Changes to the Specification

The changes these use cases need, each modelled as the fix of a gap; written into the requirements and specifications once the use case is `AGREED`.

[#change-clients-only]
=== All Interaction in the Operator's Clients

Gap:: the operator acts through a coding agent: `pm-mcp enter` opens an entry from the agent's shell, the agent's session drives the bootstraps and the project setup, the agent's model maps the user's words onto the links of a bootstrap ("choosing what to work on is the user's intent relayed by the model"), and a decision may be answered in the entry session (channel `session`). What the operator sees, is asked, and answers then depends on a harness and a model, which the system cannot make dependable, and the same step has two shapes, one for a session and one for the clients.
Fix::
* *The operator's clients are the only place of interaction with the operator*: the web app and the terminal client. Everything the operator is asked, chooses, or answers is an operator wait (link:03-plans.adoc#change-operator-wait[Waiting for the Operator]) served to them; no harness, no session, and no model relays the operator's words or choices.
* *A harness is a worker only*: the runtime runs it for the tasks of a role, and it never acts for the operator. The session-driven units, the entry session, the channel `session` of answers, and the host-facing verb `pm-mcp enter` as the operator's way to start work are removed; `pm-mcp serve` stays, for the workers.
* *Every way to start work* (a plan, an epic, a recipe, a project's onboarding and setup) runs in the clients (<<change-start-from-clients>>, link:04-projects.adoc#change-project-onboarding[Onboarding a Project as One Process]).
* The interpretation of the operator's own words in a decision (link:03-plans.adoc#change-own-words[Own Words]) is not relaying: the operator wrote in a client, and confirms what was understood there.
* *What of the session goes*: the session relay of a host (`pm-mcp serve --client`) and its MCP surface, the session generations and `sessions.jsonl`, the host entry commands (`/mcp-plan-marshall`, `/mcp-plan-orchestrator`, `/mcp-marshall-steward`) and their bundle files, and the interactive session as an optional worker (`PM-WORK-5`); what stays of a host is the worker it runs (`pm-mcp serve --job`).
* *No elicitation*: MCP elicitation is no channel of the operator; the setup's and the bootstraps' choices that used it are operator waits, and the channel enums keep `web`, `cli`, and `quorum`.

[#change-start-from-clients]
=== Starting from the Clients

Gap:: a plan or an epic is started only by `pm-mcp enter` and the bootstrap a session drives; a pending entry without a session is invalid unless an epic starts its own plan; the choice `start.choose` takes exactly one source, and the description (`new_request`) is a link with no state of its own.
Fix::
* `POST /api/v1/projects/{project_id}/entries` with the kind `plan` or `epic` opens an entry, which is then addressed at the top level by its id (`/api/v1/entries/{entry_id}`, its events at `/api/v1/entries/{entry_id}/events`, link:03-plans.adoc#change-event-streams[Events per Scope]); its states are operator waits served to both clients; the pending entry record needs no session.
* `start.choose` offers a plan from sources or a recipe; `start.sources` and `start-epic.sources` hold a list of sources, to which every source sub-workflow adds and from which the operator removes, and offer a chat about the entry whose one change is a description (link:06-controlling-work.adoc#change-chat[Chatting with the Planning Role]); the description is stored by the main workflow itself (`start.store-description`), since it needs nothing gathered.
* `start.ready` and `start-epic.ready` show the title and the id proposed from the sources; the other commit options of today (posture, outline review, base branch) leave the start (<<change-options-when-needed>>).
* `epic_slug`, `title`, and `vision` of `start-epic.define` become the sources and the title of `start-epic.ready`; the vision is a description like any other.
* The facts of `start.open` stay local listings (recipes, unclaimed lessons, local changes); issues and pull requests are named, never listed (link:../later-improvements.adoc[Later Improvements], L-6).
* *An entry never expires*: a pending entry has no time limit and is never discarded by time; it stays among the project's open entries, offered to continue in both clients, until it is started or abandoned, or deleted with the release of its project (link:04-projects.adoc#UC-PRJ-3[UC-PRJ-3]). The maximum age of a pending entry record and its removal by the periodic sweep go.
* `POST /api/v1/entries`, the request of `pm-mcp enter`, goes; its codes `project_not_enrolled` and `lifecycle_closed` answer the new request.
Affects:: link:../specification/state-catalogue/09-bootstrap-and-lessons.adoc[Bootstrap & Lessons States], link:../specification/phase-workflows/01-planning-phases-1-2.adoc[Planning Phases 1–2] (Plan Source Contracts), link:../specification/runtime-model/01-processes-and-transport.adoc#local-api[Local API], link:../specification/store-schemas/01-format-and-session-log.adoc#pending-entry-record[Pending Entry Record], link:../specification/timeouts/02-runtime-leases-operator-web.adoc#pending-entry-max-age[Pending Entry Record Maximum Age] and its sweep, link:../specification/runtime-model/02-startup-recovery-drain.adoc#periodic-sweep[Periodic Sweep].

[#change-source-directory]
=== The Source Directory

Gap:: a plan's sources live only in its pending entry, as one source object, and are then flattened into `request.md`; no plan or epic keeps a source as it came in, an epic keeps none at all (its header has no origin, and `epic.decompose` reads "the epic's vision and source" from nowhere), and a plan cannot start from more than one source.
Fix::
* *Every entry has a source directory*, created by the server with the entry (`pending/<entry_id>/sources/`) and moved with the creation into the plan (`plans/<plan_id>/sources/`) or the epic's ledger (`.marshall/epics/<epic_id>/sources/`, committed and landed with it):
+
[source,text]
----
sources/
├── sources.json            the manifest: per source its id, kind, reference
│                           (an issue's or a pull request's URL),
│                           where it came from, trust, digest, size, added
│                           at, and for an external one its screening verdict
├── description-<n>.md      a description, as written
├── documents/<n>/…         documents, as copied or moved; a directory with
│                           its tree
├── issues/<forge>-<owner>-<repo>-<number>/
│   ├── issue.md            title and body, level-1 validated
│   └── issue.json          labels, milestone, assignees, state, URL
├── pull-request/           as an issue, with the changed files
├── lesson-<id>.md          the lesson as claimed
└── local-changes.json      the captured changes
----
* *The manifest is the record of the sources*: `origin` of `mcp/status.json` names the sources by their ids (a list), each resolving in the manifest to its kind and reference (for an issue or a pull request its URL), and the epic header lists them (kind, reference, digest) so that the ledger says what the epic started from on every machine.
* `request.md` keeps its sections; its original input is composed by the server from the descriptions and a reference to each other source; the models of the plan read the sources in the source directory.
* The issue's reference lives in the manifest and in `origin`; `references.json` gains no field for it.
* A source is never changed once stored; a source added later (a description during refine) is a new entry of the manifest.
* *An epic's sources are in its ledger*: they move into `.marshall/epics/<epic_id>/sources/` and are committed and landed with the ledger, so that another machine that adopts the epic, and every later decomposition, reads them; the epic's machine store keeps none. An external source in the ledger is kept in its level-1-validated form with its verdict, as everywhere.
Affects:: link:../specification/filesystem-layout/03-project-store.adoc#machine-store[Per-Project Machine Store], link:../specification/store-schemas/01-format-and-session-log.adoc#pending-entry-record[Pending Entry Record], link:../specification/store-schemas/02-workflow-state-store.adoc[Workflow State Store] (`origin`), link:../specification/store-schemas/04-epic-and-change-ledger.adoc#epic-header[Epic Header], link:../specification/model-work/08-epic-coordination.adoc#epic-workflow[Epic Workflow] (`epic.decompose`), link:../specification/phase-workflows/01-planning-phases-1-2.adoc[Planning Phases 1–2] (`request.md`), link:../specification/filesystem-layout/01-repository-workspace.adoc[Repository Workspace] (the ledger's `sources/`).

[#change-documents]
=== Documents as a Source

Gap:: there is no way to start from documents: no source kind, no unit, no place to keep them. `plan-marshall` starts a plan from one file pointer and reads an epic's documents where they lie, so a moved or edited document changes what the work started from.
Fix::
* A source unit `source-documents` (<<UC-STA-3>>) with the source kind `documents`: the server checks the files or the directory (regular files, readable, the bounds of size and count, no link followed out of a directory), and copies or moves them into the source directory.
* *Copy or move* follows the machine key `sources.documents_mode`: `copy`, `move`, or `ask`, by default `ask`. With `ask` it is an operator wait with _copy_ preselected; choosing _always_ there stores `copy` or `move` as the machine's value, after which it is not asked; the machine's settings change it (link:01-onboarding.adoc#UC-ONB-10[UC-ONB-10]). A copy is not managed: nothing keeps it and its original in step. A move deletes a file outside git where it was, and removes a file git tracks from git through a short landing (`git.land-removal`: one commit, landed by the project's landing, `landing.pull-request` or `landing.main`, as the epic's ledger is landed; with `landing.files` the removal stays uncommitted in the working tree), which runs on after the source is stored.
* The web app picks the files through a listing of the server, confined to the checkout and the operator's home directory; the terminal client sends paths, resolved against its working directory.
* *Loopback only*: the listing of files, a move, and the choice of documents outside the checkout are accepted only from the terminal client and from a browser on the loopback listener, never from a device on the network, like the entry of secrets; a move is the only deletion of the operator's files the runtime makes, and only on the operator's choice.
Affects:: link:../specification/state-catalogue/09-bootstrap-and-lessons.adoc#state-catalogue-source[Source States], link:../specification/store-schemas/12-machine-stores.adoc#machine-config[Machine Configuration Store], link:../specification/runtime-model/01-processes-and-transport.adoc#local-api[Local API] (the listing), link:../specification/workflow-dsl/06-reusable-sub-workflows.adoc[Reusable Sub-Workflows] (`git.land-removal`), link:../specification/runtime-model/01-processes-and-transport.adoc[Processes & Transport] (the files the runtime writes outside its stores), link:../specification/cli-and-security/03-web-server.adoc#web-listener[Web Listener], link:../requirements/08-security.adoc[PM-SEC].

[#change-local-trusted]
=== What Is on This Machine Is Trusted

Gap:: `PM-SEC-1` asks to treat all external content "including repository code, build definitions" as untrusted, while the source units treat the project's own content (a lesson, a recipe, the local changes) as validated only, and documents from the checkout or the operator's machine have no place in the rule at all. `plan-marshall` also screens third-party text the user pastes into a description, which was a workaround for a system without a server between the operator and the models.
Fix::
* *Trusted*: what the operator wrote in a client (a description, an answer), and what is on this machine (the checkout, documents the operator chose). They are never screened; a model reads them as the operator's and the project's own, as it reads the code.
* *Untrusted until screened*: what comes from outside the machine: issues, pull requests, review comments and bot findings, analysis messages, results of upstream MCP servers. The two-level guard stays for them unchanged.
* *A pull request's changed files* are code from outside the machine, possibly from a fork: stored as the pull request's head and marked untrusted unless the operator authored the pull request; no model reads them as instructions, and the plan's own gates (its review, its integrity checks) apply to them.
* A description is not searched for pasted third-party text: what the operator puts into a client is the operator's.
Affects:: link:../requirements/08-security.adoc#PM-SEC-1[PM-SEC-1], link:../specification/model-work/07-untrusted-text-screening.adoc#two-level-guard[Two-Level Guard for External Text].

[#change-screen-stored]
=== Screened Once Stored

Gap:: the screening of a source runs over text held in the pending entry, and the order of fetching, storing, and screening is stated per source unit. A screener that fails makes every item `suspicious`, so a failure looks like a flagged source, and nothing says what happens while no configuration of the role qualifies.
Fix::
* *One order for every external source*: fetch by a bounded job, the level-1 validator, store in the source directory marked unscreened, then the screener over the stored copy; the verdict is written into the manifest. No model but the screener reads a source before its verdict is `clean` or the operator accepted it.
* *Fail closed*: a screener that fails, or a role `screener` with no qualified configuration, leaves the source unscreened with the cause (`source-<kind>.unscreened`): the operator tries again, removes it, or accepts it explicitly as untrusted, recorded with its reason like an accepted flagged source.
* The batch of a source is built from the stored files; the batch kinds stay as they are.
Affects:: link:../specification/model-work/07-untrusted-text-screening.adoc#two-level-guard[Two-Level Guard for External Text], link:../specification/state-catalogue/09-bootstrap-and-lessons.adoc#state-catalogue-source[Source States].

[#change-issues]
=== Issues by Number or URL

Gap:: an issue is named only by its number and read only from the project's own repository by its CI provider; `plan-marshall` also starts from an issue's URL in another repository. Only title and body are kept; labels, milestone, and assignees are lost. The plan source promises to post back to the issue through asynchronous mirror jobs that no operation specifies.
Fix::
* `source-issue` takes a number (the project's own repository) or a URL; the server resolves the forge, the repository, and the provider from it.
* *The URL is always stored*: an issue's reference, in the manifest, in `origin`, and wherever the issue is named later, is its URL; a number is resolved to the URL of the issue in the project's repository before anything is fetched. The same holds for a pull request.
* *Another repository* is read only with the operator's grant, once or for the project, recorded like the cross-repository reads (link:../specification/cli-and-security/02-credentials-and-operator.adoc#cross-repository-reads[Cross-Repository Reads]), with the credential of that forge, or without one for a public issue.
* *Rate limits*: a fetch of an issue or a pull request that the forge refuses for its rate limit, with or without a credential, fails with the cause `rate_limited` and the time the limit resets (`resets_at`, from the forge's answer); it is not retried by itself, and the operator tries again or adds a credential for the forge.
* *The fields*: title and body as text through the guard; labels, milestone, assignees, state, and URL as structured fields in `issue.json`, never as text for a model to follow.
* *The links* of an issue keep their targets when they lead to the issue's own forge: the level-1 allowlist gains the origin of the forge the source came from.
* *Writing back* is the operation `ci.issue-comment` of the CI contract, only for an issue of the project's own repository and only when the team's configuration enables it; it posts the clarified request after Phase 2 and the approved outline after Phase 3.

[#change-forgejo]
=== Codeberg and Forgejo

Gap:: the providers are GitHub and GitLab only (`ci_provider`, the integrations, the credential keys, the provider modules); Codeberg and other Forgejo or Gitea forges are not known anywhere.
Fix::
* A provider `forgejo` for Codeberg and every Forgejo or Gitea forge: the module `pm-provider-forgejo` with the CI contract over the Forgejo REST API, the value `forgejo` in `ci_provider` and the integrations, the host detection (`codeberg.org`, else a probe of `/api/v1/version`), the credential key `forgejo` with its host, and its place in the machine's provider defaults (link:01-onboarding.adoc#change-provider-defaults[Machine Provider Defaults]).
* It serves the issue source first; as the CI provider of a project whose remote is on a Forgejo forge, it follows the same contract as the others.
Affects:: link:../specification/module-structure.adoc[Module Structure], link:../specification/store-schemas/07-project-configuration.adoc[Project Configuration] (`ci_provider`), link:../specification/store-schemas/09-derived-facts-and-build-timings.adoc[Derived Facts] (the detection), link:../specification/identifiers/02-registry-stores-to-web.adoc[Identifier Registry] (the credential key), link:../specification/cli-and-security/02-credentials-and-operator.adoc#operator-credential-cli[Operator Credential CLI].

[#change-recipe-workflow]
=== A Recipe Is a Workflow

Gap:: a recipe is a source of a plan that the plan's phases then route around: special states (`init.recipe-selected`, `outline.recipe-entry`, `outline.recipe-confirm`, `outline.empty-harvest`), a forced lane, a forced confidence. The recipe's work is spread over the general plan's workflow instead of being a workflow of its own.
Fix::
* *A recipe is a named workflow* of its domain or project: its phases are sub-workflows (link:03-plans.adoc#change-phase-sub-workflows[Phases as Sub-Workflows]), its own where it differs and the plan's shared ones (finalize, the landing) where it does not; it declares its parameters and whether it takes the sources of a request.
* Starting a recipe (<<UC-STA-5>>) creates a plan whose process is the recipe's workflow; the recipe routes inside the plan's workflow go.
Affects:: link:../specification/domain-extensions/05-recipes-and-extension-points.adoc[Recipes & Extension Points], link:../specification/phase-workflows/01-planning-phases-1-2.adoc[Planning Phases 1–2] (the recipe source, the recipe states), link:../specification/workflow-dsl/09-plan-instance.adoc#plan-instance[Plan Instance].

[#change-options-when-needed]
=== Asked When Needed

Gap:: the bootstrap asks the plan's options before the plan exists (posture, outline review, base branch, slug), and `plan-marshall` asks more during its init (the domain, the lane); the operator decides them before knowing whether they matter, and an epic's `parallelization_scope` is fixed at its definition.
Fix::
* *The start asks only the sources*, and the title and id proposed from them.
* *Every other option is an operator wait at the state that first needs it*, with its proposal: the posture where the plan's lane is chosen, the base branch before the plan's branch is created, the outline review when the outline is ready. An option the project or the machine sets (link:01-onboarding.adoc#change-plan-axes[Plan Behaviour Axes]) is not asked.
* *An epic's `parallelization_scope`* is a project key (`epic.parallelization_scope`, its machine default 1) and is never asked: a new epic takes the project's value. The operator raises it through the epic's _Next plan_, which offers to raise it by one when the scope is full (link:06-controlling-work.adoc#change-epic-actions[An Epic's Actions]), or in the project's settings; a raise of an epic is a ledger write of its header, landed like every ledger write.
* *The outline review* is asked only where the plan's asking axis does not set it (link:01-onboarding.adoc#change-plan-axes[Plan Behaviour Axes]).
Affects:: link:../specification/state-catalogue/09-bootstrap-and-lessons.adoc#state-catalogue-bootstrap[Bootstrap States], link:../specification/phase-workflows/01-planning-phases-1-2.adoc[Planning Phases 1–2], link:../specification/model-work/08-epic-coordination.adoc#epic-workflow[Epic Workflow] (`parallelization_scope`), link:../specification/model-work/08-epic-coordination.adoc#server-started-plans[Server-Started Plans] ("never a configuration default"), link:../specification/store-schemas/07-project-configuration.adoc[Project Configuration].

[#change-decomposition-review]
=== The Decomposition Is Reviewed

Gap:: `epic.decompose` and `epic.recut` serve one task of the role `decompose`, whose submits are committed by `epic.commit-decomposition` without anyone seeing them: the cut of an initiative into plans, the decision that shapes all the epic's work, is never shown to the operator, who can neither shape it nor ask for another cut.
Fix::
* *A sub-workflow `decomposition`* of the epic: the role's draft, the server's checks (surface disjointness, dependencies without a cycle, a workstream per plan), and the operator wait `decomposition.review`, in which the operator keeps, edits, drops, or adds plans, chats with the role through the sub-workflow `chat` (link:06-controlling-work.adoc#change-chat[Chatting with the Planning Role]) over the draft, or has it draft again with an instruction; every change a model proposes reaches the draft only through the operator's read-back; nothing is committed before the operator agrees and every check passes.
* `epic.decompose` and `epic.recut` call it; a later run (the operator's _decompose again_, or stale rows) changes only staged rows and shows each change against the row it replaces.
* The epic starts no plan before its first decomposition is committed.
Affects:: link:../specification/model-work/08-epic-coordination.adoc#epic-workflow[Epic Workflow], link:../specification/state-catalogue/06-setup-epic-other.adoc[Epic States] (`epic.decompose`, `epic.commit-decomposition`, `epic.recut`), link:../specification/model-work/08-epic-coordination.adoc#epic-surface-disjointness[Staging-Time Surface Disjointness], link:../specification/model-work/01-roles-and-configuration.adoc#default-roles[Default Role Set] (the submits of `decompose` for a rewrite and in a chat).

[#change-lesson-claim]
=== A Claimed Lesson Ends with the Landing

Gap:: the claim of a lesson ends by the plan's outcome: the lesson is retired only when the plan ends `merged`, and released on every other end. With the landing axis (link:01-onboarding.adoc#change-plan-axes[Plan Behaviour Axes]) a plan also lands its changes by a push on the base branch (`landing.main`), which is no merge, and hands its changes back uncommitted (`landing.files`).
Fix::
* *Retired when the plan lands its changes*: the merge of `landing.pull-request`, or the push of `landing.main`; the verdict stays `applied`, `by` the `plan_id`.
* *Released when the plan ends without landing them*: handed back with `landing.files`, cancelled, abandoned, released with its project, aborted, or deleted; the lesson stays `active`.
Affects:: link:../specification/store-schemas/10-job-and-lesson-records.adoc#lesson-record[Lesson Record] (Claim), link:../specification/state-catalogue/09-bootstrap-and-lessons.adoc#state-catalogue-lessons[Lessons].
