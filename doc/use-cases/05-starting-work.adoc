= Use Cases: Starting Work (UC-STA)
:toc: left
:toclevels: 2
:nofooter:

link:../UseCases.adoc[Use Cases] » Starting Work

The operator starts a plan or an epic in a project from what the work comes from: a description, documents, issues, a lesson, the checkout's local changes, a pull request, or a recipe. The operator does this in the web app or in the terminal client, which are the only places where the operator acts (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/workflow-dsl/02-units-jobs-decisions.adoc#clients-only[Workflow DSL & Engine Specification, All Interaction in the Operator's Clients]); how each shows it is its design (link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/README.adoc[`pm-mcp-clients`, Design]).

[#principles]
== Principles

[#machinery-gathers]
Machinery gathers, models read:: Gathering a source is the server's work: it fetches, checks, creates the directories, and stores every source of a plan or an epic in its source directory. The only model step while a source comes in is the screening of what came from outside the machine. A model works with a source only once it is stored locally, and an external one only once it is screened.
[#local-is-own]
What is on this machine is the operator's own:: The operator's description and the documents on this machine are trusted as the checkout's code is trusted, and are not screened; what comes from outside the machine (an issue, a pull request) is untrusted until screened.
[#sources-first]
Sources first, the rest when needed:: Starting asks only what the work comes from. What the plan or the epic needs beyond that (its posture, its base branch, the outline review) is asked where it is first needed, and not at all where the project or the machine sets a value. How many plans an epic runs at once is never asked: it is the project's setting, raised by the operator later.

[#UC-STA-1]
== UC-STA-1: Start a Plan

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client.
Goal:: start a plan in a project from everything it should start from, in one guided run, and see it run.
Trigger:: the operator chooses _Add a plan_ on a project (link:04-projects.adoc#UC-PRJ-2[UC-PRJ-2]), after a project's onboarding (link:04-projects.adoc#UC-PRJ-1[UC-PRJ-1]), or in the terminal client in a checkout, whose project is the proposal; or accepts a follow-up plan in a chat about ended work (link:../specification/runtime-model/01-processes-and-transport.adoc#ended-work[Runtime & Interaction Model Specification, Ended Work]), which opens the start with its description stored.
Preconditions:: the project is enrolled and ready; the machine is onboarded.
Flow::
+
[source,text]
----
  [S] start.open               the setup gate (the machine onboarded, the
       │                       project ready); the entry of the project and
       │                       its source directory, empty; the facts:
       │                       the project's recipes, its unclaimed lessons,
       │                       whether the checkout has local changes
       ├── the machine not onboarded, or the project not ready ──► the
       │      reason and where to fix it (UC-ONB-1, UC-PRJ-1); nothing is
       │      created
       ▼
  [O] start.choose             a plan from sources, or a recipe
       ├── recipe ───────────► ↳ recipe (UC-STA-5)
       ▼ sources
  [O] start.sources            the sources gathered so far, each with its
       │                       state; add one, remove one, chat, start;
       │                       only the kinds that combine with those
       │                       already there are offered: a pull request
       │                       or the local changes only with descriptions
       │                       and documents, and never both; the local
       │                       changes not while the project's landing is
       │                       landing.files, with that reason
       ├── description ──────► [S] start.store-description ─► start.sources
       ├── chat ─────────────► ↳ chat (UC-CTL-1) with the role refine, over
       │                         the entry; an accepted description
       │                         ─► start.store-description
       ├── documents ────────► ↳ source-documents (UC-STA-3) ─► start.sources
       ├── issue ────────────► ↳ source-issue (UC-STA-4) ─────► start.sources
       ├── lesson ───────────► ↳ source-lesson (UC-STA-8) ────► start.sources
       ├── local changes ────► ↳ source-local-changes (UC-STA-9) ► start.sources
       ├── pull request ─────► ↳ source-pr (UC-STA-7) ────────► start.sources
       ▼ start, every source stored and none unscreened
  [O] start.ready              what the plan starts from, its title and id
       │                       proposed from the sources, both changeable
       │                       (the id of a recipe's plan and of an adopted
       │                       pull request's is derived, not changeable)
       ▼ create
  [S] start.create             re-checks what creation needs; creates the
       │                       plan; the source directory becomes the plan's
       ├── something changed meanwhile ──► start.ready, with the cause
       ▼
  init.*                       the plan runs (UC-PLN-1); what it needs and
                               has no value for is asked where it is first
                               needed
----
+
The sub-workflows are the recipe (<<UC-STA-5>>), the chat (link:06-controlling-work.adoc#UC-CTL-1[UC-CTL-1]), and the sources: documents (<<UC-STA-3>>), an issue (<<UC-STA-4>>), a lesson (<<UC-STA-8>>), the local changes (<<UC-STA-9>>), a pull request (<<UC-STA-7>>). The plan then runs as in link:03-plans.adoc#UC-PLN-1[UC-PLN-1], and what it still needs is asked when needed (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/09-bootstrap-and-lessons.adoc#options-when-needed[State Catalogue, Asked When Needed]).
Variations::
* *Several sources*: a plan starts from any number of descriptions, documents, issues, and lessons together; each is stored on its own in the source directory (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/filesystem-layout/03-project-store.adoc#source-directory[Filesystem Layout Specification, The Source Directory (`sources/`)]). A pull request and the local changes decide how the plan runs (it adopts the pull request, or it lands the changes) and therefore start a plan alone or with descriptions and documents only; `start.sources` offers only the kinds that combine with those already in the list.
* *A landing that does not fit the sources*: a plan from the local changes needs a landing that commits. While the project's landing in force is `landing.files`, `start.sources` does not offer the local changes and shows the reason, naming the project's setting `landing` (<<UC-STA-9>>).
* *The machine or the project not ready*: the setup gate of `start.open` refuses with the reason and where to fix it, the machine's onboarding (link:01-onboarding.adoc#UC-ONB-1[UC-ONB-1]) or the project's (link:04-projects.adoc#UC-PRJ-1[UC-PRJ-1]); nothing is created.
* *A source that fails* (an issue not found, a document not readable) stays in the list with its cause, to be tried again or removed; the plan cannot start while a source is not stored, or an external one not screened or accepted.
* *Leaving*: the entry keeps its sources while the operator is away, in either client; abandoning it deletes its source directory, and nothing of a plan exists before `start.create`. An entry never expires: like a decision it has no time limit, and it stays among the project's open entries, offered to continue in either client, until it is started or abandoned (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/09-bootstrap-and-lessons.adoc#start-from-clients[State Catalogue, Start of a Plan]).
* *A lesson* is checked against the current checkout first; one whose premise no longer holds is shown with its evidence, to be used anyway or retired (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/09-bootstrap-and-lessons.adoc#state-catalogue-source[Source States]).
* *A chat about the entry* is offered once a source is stored and every external one screened, never for a recipe, and disabled with its reason while the role `refine` does not qualify: what the model understood, what is unclear, what is out of scope. Its one change is a description, rewritten or added, stored after its read-back; it never touches another source, and starting never waits for it. Its transcript stays with the entry, becomes the plan's at `start.create` without being a source, and is deleted with an abandoned entry; a chat still open then is ended first, its transcript complete (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue.adoc#chat[State Catalogue, Chatting with the Planning Role: `chat`]).
* *An epic's plan* is started by the epic itself, without the operator; its source is the epic's staged section, stored in the plan's source directory like any other (`epic-row.md`, the kind `epic_row`, link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/filesystem-layout/03-project-store.adoc#source-directory[Filesystem Layout Specification, The Source Directory (`sources/`)]).
Outcome:: the plan exists, with every source it starts from in its source directory, and runs; the operator sees it in Running Work (link:03-plans.adoc#UC-PLN-4[UC-PLN-4]).
Requirements:: link:../requirements/02-workflow.adoc#PM-WF-10[PM-WF-10] (a plan only through a start, its list of sources, the source directory), link:../requirements/02-workflow.adoc#PM-WF-20[PM-WF-20] (the start's choices as operator waits of the clients, an entry that never expires), link:../requirements/01-architecture.adoc#PM-ARCH-11[PM-ARCH-11] (the two clients), link:../requirements/02-workflow.adoc#PM-WF-24[PM-WF-24] (the chat about the entry), link:../requirements/02-workflow.adoc#PM-WF-25[PM-WF-25] (the options asked where first needed), link:../requirements/02-workflow.adoc#PM-WF-15[PM-WF-15] (an epic's plan through `epic_row`); the start is specified in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/09-bootstrap-and-lessons.adoc#state-catalogue-bootstrap[Start of a Plan] (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/09-bootstrap-and-lessons.adoc#start-from-clients[Starting from the Clients], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/09-bootstrap-and-lessons.adoc#options-when-needed[Asked When Needed]), the entry in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/01-format-and-session-log.adoc#pending-entry-record[Pending Entry], the sources in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/filesystem-layout/03-project-store.adoc#source-directory[The Source Directory] and link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/phase-workflows/01-planning-phases-1-2.adoc#_plan_source_contracts[Plan Source Contracts], the clients' part in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/workflow-dsl/02-units-jobs-decisions.adoc#clients-only[All Interaction in the Operator's Clients].
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/starting-work.adoc[Starting Work]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/18-starting.adoc[Terminal Client, Starting Work]; the web app: no design document yet; designed by its package link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/plans/web-start.adoc[`web-start`]

[#UC-STA-2]
== UC-STA-2: Start an Epic

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client.
Goal:: start an epic for an initiative that needs several plans, from everything that describes it, and let it cut the work into plans.
Trigger:: the operator chooses _Add an epic_ on a project (link:04-projects.adoc#UC-PRJ-2[UC-PRJ-2]).
Preconditions:: the project is enrolled and ready; the machine is onboarded.
Flow::
+
[source,text]
----
  [S] start-epic.open          the setup gate (as in UC-STA-1); the entry
       │                       and its source directory, empty
       ├── the machine not onboarded, or the project not ready ──► the
       │      reason and where to fix it (UC-ONB-1, UC-PRJ-1); nothing is
       │      created
       ▼
  [O] start-epic.sources       the sources gathered so far, as in UC-STA-1:
       │                       descriptions, documents, issues; add one,
       │                       remove one, chat, start; or adopt an epic that
       │                       exists in the ledger but not on this machine
       ├── adopt ────────────► [S] start-epic.adopt   the ledger read and
       │                             │                validated; only the
       │                             │                machine's scope created
       │                             ├── unreadable, invalid, or terminal ──►
       │                             │      [O] start-epic.adopt-failed   the
       │                             │      file and the cause; retry once
       │                             │      the ledger is repaired through git,
       │                             │      or back, or abandon
       │                             ▼ adopted: the epic runs at its
       │                               decomposition, or, with a queue,
       │                               at epic.next-work
       ├── description ──────► [S] start-epic.store-description
       ├── chat ─────────────► ↳ chat (UC-CTL-1) with the role decompose,
       │                         as in UC-STA-1
       ├── documents ────────► ↳ source-documents (UC-STA-3)
       ├── issue ────────────► ↳ source-issue (UC-STA-4)
       ▼ start, every source stored and none unscreened
  [O] start-epic.ready         the epic's title and id, proposed
       │                       from the sources, both changeable; its
       │                       mode (automatic or not) shown as the value
       │                       in force, never asked
       ▼ create
  [S] start-epic.create        the ledger, into which the source directory
       │                       moves, written, not yet committed; the
       │                       epic's machine store
       ├── something changed meanwhile ──► start-epic.ready, with the cause
       ▼
  ↳ decomposition              the role decompose drafts the workstreams
       │                       and the staged plans from the stored sources;
       │                       the operator reviews and shapes them before
       │                       anything is committed; once agreed, the
       │                       ledger with its sources is committed
       │                       (decomposition.commit, UC-STA-6) and landed
       │                       onto the base branch by epic.landing
       ▼
  epic.*                       the epic runs and, with automatic on, starts
                               its plans; how many run at once is the
                               project's setting (machine default 1), never
                               asked
----
+
The sub-workflows are the chat (link:06-controlling-work.adoc#UC-CTL-1[UC-CTL-1]), the sources (<<UC-STA-3>>, <<UC-STA-4>>), and the decomposition (<<UC-STA-6>>).
Variations::
* *Documents are the usual source* of an epic: a concept, a specification, a directory of them. They are stored as they are; a directory keeps its tree.
* *Adopting* an epic that exists in the ledger but not on this machine (another machine started it) is offered instead of a new one (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/09-bootstrap-and-lessons.adoc#state-catalogue-bootstrap-epic[Epic Bootstrap]).
* *Its plans and the epic communicate through the server*: a plan sends to its epic's inbox, and the epic to a plan's mailbox (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/08-epic-coordination.adoc#plan-scope-outbox-link[Plan-Scope Outbox Link], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/08-epic-coordination.adoc#plan-mailbox[Plan Mailbox]); no text passes from one to the other through the operator.
* *How many plans run at once* is the project's `epic.parallelization_scope`, its machine default 1, and is never asked at the start. The operator raises it through the epic's _Next plan_, which offers to raise it by one when the scope is full (link:06-controlling-work.adoc#UC-CTL-2[UC-CTL-2]), or in the project's settings (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/09-bootstrap-and-lessons.adoc#options-when-needed[State Catalogue, Asked When Needed]).
* *Whether the epic starts its plans by itself* is the project's `epic.auto_start`, its machine default on, and is never asked at the start: the ready step shows the value in force, and the operator switches it on the epic at any time (link:06-controlling-work.adoc#UC-CTL-2[UC-CTL-2]).
* A source that fails, a chat about the entry (with the role `decompose`), leaving, abandoning, and the setup gate are as in <<UC-STA-1>>.
Outcome:: the epic exists with its sources stored and listed in its ledger, its workstreams and plans drafted from them and agreed by the operator; with automatic on it starts its plans as they become launchable, up to how many may run at once, and with it off it reports them as launchable and waits for the operator's _next plan_.
Requirements:: link:../requirements/02-workflow.adoc#PM-WF-15[PM-WF-15] (the epic's start, its sources in the ledger, the reviewed decomposition, the plans it starts, the adoption), link:../requirements/02-workflow.adoc#PM-WF-10[PM-WF-10] (the start and its sources), link:../requirements/02-workflow.adoc#PM-WF-24[PM-WF-24] (the chat about the entry), link:../requirements/02-workflow.adoc#PM-WF-23[PM-WF-23] (raising the scope through _next plan_, switching automatic); the start is specified in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/09-bootstrap-and-lessons.adoc#state-catalogue-bootstrap-epic[Start of an Epic], the epic workflow in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/08-epic-coordination.adoc#epic-workflow[Epic Workflow] and link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/08-epic-coordination.adoc#epic-auto[An Epic Runs by Itself], its ledger in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/04-epic-and-change-ledger.adoc#epic-header[Epic Header], its sources in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/filesystem-layout/03-project-store.adoc#source-directory[The Source Directory].
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/starting-work.adoc[Starting Work]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/18-starting.adoc[Terminal Client, Starting Work]; the web app: no design document yet; designed by its package link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/plans/web-start.adoc[`web-start`]

[#UC-STA-3]
== UC-STA-3: Bring in Documents

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client, while starting a plan or an epic.
Goal:: make one or more files, or a directory, a source of the work, copied or moved, without a model touching them on the way.
Trigger:: the operator adds documents in <<UC-STA-1>> or <<UC-STA-2>>.
Flow::
+
[source,text]
----
  [O] source-documents.pick     files or a directory on this machine; the
       │                        checkout's files first
       ▼
  [S] source-documents.check    each is a regular file, readable, within the
       │                        bounds of size and count; a directory is
       │                        listed with what it holds; links that lead
       │                        out of it are not followed
       ├── something fails ──► source-documents.pick, with the cause per file
       ▼
       ├── the machine sets copy or move ──► source-documents.store
       ▼ ask
  [O] source-documents.mode     copy ← or move, each with "always", which
       │                        stores the choice as the machine's
       ▼
  [S] source-documents.store    copies or moves them into the source
       │                        directory, a directory with its tree; records
       │                        each with where it came from, its size, and
       │                        its digest
       ├── moved, and git tracks some of them ──►
       │      ↳ git.land-removal    a short landing: one commit that removes
       │                            them from git, landed by the project's
       │                            landing (landing.pull-request or
       │                            landing.main); with landing.files the
       │                            removal stays uncommitted in the
       │                            working tree
       ▼
  done                          the documents are a source, trusted
----
Variations::
* *Copy*: the originals stay where they are and are not managed: a later change of an original does not reach the source, and the source does not reach the original.
* *Move*: the documents leave where they were. A file outside git is deleted there; a file git tracks is removed from git by the short landing, so that the repository and the source never hold two versions of it. The source is stored at once, and the work may start while the landing runs; the landing shows in the project's running work until it is landed, and waits for the operator if it fails.
* *The machine's default* (`sources.documents_mode`) is _ask_: the operator chooses each time, with _copy_ preselected. Choosing _always_ with an answer stores _copy_ or _move_ as the machine's default, after which the choice is no longer asked; the machine's settings change it back (link:01-onboarding.adoc#UC-ONB-10[UC-ONB-10]).
* *Where documents come from*: files of the checkout or of the operator's home directory, the checkout's files first; a path outside both is refused. Choosing files outside the checkout, and a move, are offered only in the terminal client and in a browser on the loopback listener, never to a device on the network (link:../specification/cli-and-security/03-web-server.adoc#loopback-only[Loopback-Only Acts]).
* *Not screened*: documents on this machine are the operator's own (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/07-untrusted-text-screening.adoc#local-trusted[Model Work Specification, What Is on This Machine Is Trusted]); the deterministic level-1 validator does not run on them either, since nothing about them is external.
Outcome:: the documents are stored in the source directory, listed in its manifest; a moved document is gone from where it was, and from git once its removal is landed.
Requirements:: link:../requirements/02-workflow.adoc#PM-WF-10[PM-WF-10] (the source `documents`: checked, copied or moved), link:../requirements/08-security.adoc#PM-SEC-1[PM-SEC-1] (what is on this machine is trusted), link:../requirements/08-security.adoc#PM-SEC-7[PM-SEC-7] (the listing and the move from the loopback listener only); the source is specified in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/09-bootstrap-and-lessons.adoc#documents-source[Documents as a Source], its mode in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/12-machine-stores.adoc#machine-config[Machine Configuration Store], the removal from git in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/18-plan-unit-axes-short-landings.adoc#state-catalogue-short-landings[Short Landings], the loopback restriction in link:../specification/cli-and-security/03-web-server.adoc#loopback-only[Loopback-Only Acts].
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/starting-work.adoc#documents[Starting Work, Documents]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/18-starting.adoc#plan[Terminal Client, Starting a Plan]; the web app: no design document yet; designed by its package link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/plans/web-start.adoc[`web-start`]

[#UC-STA-4]
== UC-STA-4: Bring in an Issue

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client, while starting a plan or an epic.
Goal:: make an issue of GitHub, GitLab, or Codeberg a source of the work, from the project's own repository or another one, fetched by the server and screened before any model reads it.
Trigger:: the operator adds an issue in <<UC-STA-1>> or <<UC-STA-2>>.
Flow::
+
[source,text]
----
  [O] source-issue.name        the issue: a number (the project's own
       │                       repository) or its URL
       ▼
  [S] source-issue.resolve     the forge (GitHub, GitLab, Codeberg or another
       │                       Forgejo), the repository, the provider, the
       │                       credential; a number becomes the issue's URL
       │                       in the project's repository
       ├── another repository, not granted ──► [O] source-issue.grant
       │                                          may the server read the
       │                                          issues of <owner/repo>?
       │                                          once, or for this project
       │                                          ─► source-issue.fetch;
       │                                          no ─► source-issue.failed
       ├── no credential for the forge ─────► source-issue.fetch without
       │                                       one: a public issue is read;
       │                                       another fails, naming the
       │                                       credential to add
       ▼
  [S] source-issue.fetch       a bounded job of the forge's provider: title,
       │                       body, labels, milestone, assignees, state, URL
       ├── fails ─────────────► [O] source-issue.failed   the cause (not
       │                             found, not readable, not granted, no
       │                             credential, rate limited until its
       │                             reset, provider unavailable); try
       │                             again, or remove it
       ▼
  [S] source-issue.store       the level-1 validator over title and body,
       │                       every change reported; stored in the source
       │                       directory, marked untrusted and unscreened
       ▼
  [M] source-issue.screen      the screener over the stored copy: the only
       │                       model step of bringing in a source
       ├── suspicious ────────► [O] source-issue.flagged   the flagged spans;
       │                             accept (recorded with its reason) or
       │                             remove it
       ├── the screener fails, or none qualifies ──► [O] source-issue.unscreened
       │                             the cause; the source stays unscreened:
       │                             try again, remove it, or accept it as
       │                             untrusted (recorded with its reason)
       ▼ clean
  done                         the issue is a source; models of the plan
                               read it as untrusted text
----
Variations::
* *Rate limited*: a fetch the forge refuses for its rate limit, with or without a credential, fails with the cause `rate_limited` and the time the limit resets. The operator tries again then, or, where the fetch ran without a credential, adds one for the forge, whose limit is higher (link:01-onboarding.adoc#UC-ONB-8[UC-ONB-8], or later link:01-onboarding.adoc#UC-ONB-10[UC-ONB-10]); the entry keeps the source in the list with its cause meanwhile.
* *A pull request* comes in the same way, through its own source (<<UC-STA-7>>).
* *The screening fails closed*: a screener that fails, or a role with no qualified configuration, leaves the source unscreened with the cause; no model reads it until it is screened again or the operator accepts it explicitly as untrusted (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/07-untrusted-text-screening.adoc#screen-stored[Model Work Specification, Screened Once Stored]).
* *Writing back* (the clarified request and the approved outline posted as comments) goes only to an issue of the project's own repository, and only where the project's team configuration enables it.
Outcome:: the issue is stored in the source directory with its fields and its screening verdict; nothing outside the screener has read it before.

== UC-STA-5: Run a Recipe

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client.
Goal:: run a recurring kind of work the project or a domain has named and shaped as a workflow of its own (a coverage push, a dependency update, an audit), giving only its parameters.
Trigger:: the operator chooses a recipe in <<UC-STA-1>>.
Flow::
+
[source,text]
----
  [O] recipe.choose            the recipes, each with what it does: those of
       │                       the project's domains, of the machine, and of
       │                       the project, a project's recipe in place of
       │                       one of the same key
       ▼
  [O] recipe.parameters        the recipe's parameters, each with its
       │                       options as the server resolves them (the
       │                       modules, the domains, a scope) and a proposal
       ├── a request-scoped recipe ──► start.sources of UC-STA-1, then here
       ▼
  [O] start.ready              as in UC-STA-1: the recipe and its
       │                       parameters, the title proposed and
       │                       changeable; the id derived from the recipe
       │                       and the time
       ▼ create
  [S] recipe.create            re-checks what creation needs; creates the
       │                       plan, whose process is the recipe's workflow
       ├── something changed meanwhile ──► start.ready, with the cause
       ▼
  <recipe>.*                   the recipe's own phases, as sub-workflows
----
Variations::
* *A parameter without an option* (no module the recipe can work on, no domain of it in the project) is shown with its reason; the recipe cannot run, and the operator chooses another or leaves.
* *The id* of a recipe's plan is derived from the recipe's key and the time (`recipe-{recipe_key}-{timestamp}`) and is not changeable; only the title is.
* *A recipe that is gone or changed* by the time of creation (its domain or the project removed or changed it), an id that was taken, or a gate that no longer holds returns to `start.ready` with the cause; nothing is created.
* *A request-scoped recipe* gathers its sources as in <<UC-STA-1>>, with their failures and screening; a chat is not offered for a recipe.
* *Leaving* keeps the entry with the recipe and the parameters chosen, in either client; abandoning it deletes the entry, as in <<UC-STA-1>>.
Outcome:: a plan runs the recipe's workflow with the parameters given.

[#UC-STA-6]
== UC-STA-6: Decompose an Epic

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client, with the epic's planning role.
Goal:: get from what the epic starts from to its workstreams and plans, cut the way the operator wants them, before any plan starts.
Trigger:: a new epic (<<UC-STA-2>>); the operator's _decompose again_ (link:06-controlling-work.adoc#UC-CTL-2[UC-CTL-2]); or the epic's own re-cut that adds, drops, or re-scopes a plan (`epic.recut`).
Flow::
+
[source,text]
----
  [M] decomposition.draft      the role decompose reads the sources (and, on
       │                       a later run, the ledger: what shipped, what
       │                       runs, the operator's instruction) and drafts
       │                       the workstreams and per workstream the staged
       │                       plans: objective, deliverables, expected
       │                       surface, dependencies, order
       ├── infeasible, lost ─► [O] decomposition.held   the reason; the epic
       │                       holds (UC-CTL-4)
       ▼
  [S] decomposition.check      the server's checks: the surfaces of plans
       │                       that may run together are disjoint, the
       │                       dependencies form no cycle, every plan has a
       │                       workstream; each finding shown with its plan
       ▼
  [O] decomposition.review     the workstreams and their plans, as a tree,
       │                       with the checks; per plan: keep, edit, drop;
       │                       add a plan in the operator's words; chat; or
       │                       for the whole: draft again with an instruction
       ├── keep, drop ────────► decomposition.check
       ├── edit, add ─────────► [O] decomposition.instruct   the operator's
       │                             words for the plan
       │                             ─► [M] decomposition.rewrite   the role
       │                             drafts or rewrites the plan; infeasible,
       │                             lost ─► decomposition.review
       │                             ─► [O] decomposition.read-back   old
       │                             against new: accept ─► decomposition.check;
       │                             instruct again ─► decomposition.instruct;
       │                             discard ─► decomposition.review
       ├── chat ──────────────► ↳ chat (UC-CTL-1) with the role decompose,
       │                             over the draft; an accepted change goes
       │                             into the draft ─► decomposition.check
       ├── draft again ───────► decomposition.draft, with the instruction
       ▼ agree, every check passing
  [S] decomposition.commit     the workstreams and the staged plans written
       │                       to the ledger (on the first run with the
       │                       epic's sources) and committed in the epic's
       │                       worktree, not pushed; the epic's landing
       │                       lands the ledger onto the base branch
       ├── stepped out ──────► decomposition.review   the draft kept;
       │                       agreeing commits again
       ▼
  [S] epic.next-work           automatic on: the epic starts the plans
                               that can start, up to the scope; off: it
                               leaves them staged, reports them launchable
                               (epic.launchable), and waits for next plan
                               (UC-CTL-2)
----
+
The chat is the sub-workflow of link:06-controlling-work.adoc#UC-CTL-1[UC-CTL-1].
Variations::
* *A later run* keeps what shipped, what runs, and what is paused; it changes only staged plans, and the review shows each change against the staged plan it replaces.
* *A failing check* blocks _agree_ and names the plans concerned; the operator edits, drops, or has the plan drafted again.
* *Leaving* keeps the draft and the decisions made on it; the review continues where it stopped, in either client. The epic starts no plan before the first decomposition is agreed.
* *The operator's words* in _edit_ and _add_ are not interpreted: the role works from them, and the plan it proposes passes a read-back, old against new, before it enters the draft, as in a decision (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/06-envelopes-questions-deadlines.adoc#own-words[Model Work Specification, Answers in the Operator's Own Words]); a chat is the one of a plan or an epic (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue.adoc#chat[State Catalogue, Chatting with the Planning Role: `chat`]).
Outcome:: the epic's workstreams and staged plans are in its ledger as the operator agreed them; the epic starts its plans from them by itself with automatic on, and with it off on the operator's _next plan_ (link:06-controlling-work.adoc#UC-CTL-2[UC-CTL-2]).
Requirements:: link:../requirements/02-workflow.adoc#PM-WF-15[PM-WF-15] (the reviewed decomposition, the surface disjointness of staged plans, the re-cut), link:../requirements/02-workflow.adoc#PM-WF-24[PM-WF-24] (the chat over the draft), link:../requirements/02-workflow.adoc#PM-WF-20[PM-WF-20] (the review as an operator wait), link:../requirements/02-workflow.adoc#PM-WF-21[PM-WF-21] (`epic.launchable` reported); the decomposition is specified in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/08-epic-coordination.adoc#decomposition-review[The Decomposition Is Reviewed], its states in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/17-epic-decomposition-and-review.adoc#state-catalogue-decomposition[Decomposition], the checks in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/08-epic-coordination.adoc#epic-surface-disjointness[Staging-Time Surface Disjointness], the start of the plans in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/08-epic-coordination.adoc#epic-auto[An Epic Runs by Itself].

== UC-STA-7: Adopt a Pull Request

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client, while starting a plan.
Goal:: have a plan take over an open pull request of the project and bring it to its landing.
Trigger:: the operator adds a pull request in <<UC-STA-1>>.
Flow::
+
[source,text]
----
  [O] source-pr.name           a number or the URL of a pull request of the
       │                       project's own repository; stored as its URL
       ▼
  [S] source-pr.observe        a bounded job: open? its head branch writable
       │                       by the agent identity? its title, body, and
       │                       changed files
       ├── not open, head not writable, not found, rate limited ──►
       │      [O] source-pr.failed   the cause; try again, or remove it
       ▼
  [S] source-pr.store          title and body level-1 validated, stored
       │                       unscreened; the changed files stored as the
       │                       pull request's head, marked untrusted unless
       │                       the operator authored it
       ▼
  [M] source-pr.screen         the screener over the stored title and body
       ├── suspicious ────────► [O] source-pr.flagged   accept with a reason,
       │                                                or remove it
       ├── the screener fails, or none qualifies ──► [O] source-pr.unscreened
       │                             the cause; try again, remove it, or
       │                             accept it as untrusted (with a reason)
       ▼ clean
  done                         the plan will adopt the pull request: it runs
                               the adopt lane on the pull request's branch
----
Variations::
* *Alone*: a plan that adopts a pull request starts from it alone, with descriptions and documents at most (<<UC-STA-1>>).
* *The changed files are code from outside*, possibly from a fork: they are stored as the pull request's head and marked untrusted unless the operator authored the pull request, and no model reads them as instructions. The plan's own gates (its review, its integrity checks) apply to them as to every change the plan lands.
* *The screening fails closed*, as for an issue (<<UC-STA-4>>).
* *Rate limited*: the observation fails with the cause `rate_limited` and the time the limit resets, as for an issue (<<UC-STA-4>>).
Outcome:: the pull request is a source; the plan, once started, works on its branch.
Requirements:: link:../requirements/02-workflow.adoc#PM-WF-10[PM-WF-10] (the source `pr` and the `adopt` lane), link:../requirements/08-security.adoc#PM-SEC-1[PM-SEC-1] (screened once stored; the changed files untrusted unless the operator authored the pull request); the source is specified in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/09-bootstrap-and-lessons.adoc#state-source-pr.name[Source Units, `source-pr`] and link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/phase-workflows/01-planning-phases-1-2.adoc#_plan_source_contracts[Plan Source Contracts], the lane in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/phase-workflows/02-planning-lanes-phases-3-4.adoc#adopt-lane[Adopt Lane], the trust in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/07-untrusted-text-screening.adoc#local-trusted[What Is on This Machine Is Trusted].

== UC-STA-8: Bring in a Lesson

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client, while starting a plan.
Goal:: start a plan from a lesson a former plan recorded, after checking that it still holds.
Trigger:: the operator adds a lesson in <<UC-STA-1>>.
Flow::
+
[source,text]
----
  [O] source-lesson.choose     the project's unclaimed lessons, newest first
       ▼
  [S] source-lesson.resolve    the lesson read from the lesson store; the
       │                       premise check: do the files and symbols it
       │                       cites still exist?
       ├── unavailable (claimed, retired, store damaged) ──►
       │      source-lesson.choose, with the cause
       ├── premise no longer holds ──► [O] source-lesson.premise   the
       │                                    │   evidence: use it anyway (the
       │                                    │   evidence goes into the plan),
       │                                    │   retire the lesson, or remove it
       │                                    ├── retire, remove ──► done,
       │                                    │      nothing added; back at
       │                                    │      start.sources, the entry
       │                                    │      not abandoned
       │                                    ▼ use it anyway
       │                               source-lesson.store
       ▼ holds
  [S] source-lesson.store      the lesson stored in the source directory;
       │                       claimed for the plan when the plan is created
       ▼
  done                         the lesson is a source
----
Variations::
* *Unavailable*: a lesson that another plan claimed meanwhile, one that was retired, or one whose store is damaged is not stored; the choice is shown again with the cause, and the operator chooses another lesson or leaves the choice.
* *Premise no longer holds*: the files or symbols the lesson cites are gone, and the evidence is shown. _Use it anyway_ stores the lesson, and the evidence goes into the plan with it; _retire_ retires the lesson in the lesson store, and nothing is added; the entry goes on at `start.sources` and is not abandoned; _remove_ adds nothing and leaves the lesson as it is, for a later plan.
* *Several lessons*: each is brought in on its own, as every source (<<UC-STA-1>>).
Outcome:: the lesson is a source, claimed by the plan once it exists. The lesson is retired when the plan lands its changes (the merge of `landing.pull-request`, or the push of `landing.main`), and released on every other end: `returned`, `handed_back` (whatever its cause, `landing.files` among them), `no_change`, `cancelled`, `abandoned`, `released`, `aborted`, or deleted.
