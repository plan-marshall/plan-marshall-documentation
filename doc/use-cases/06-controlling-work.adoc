= Use Cases: Controlling Work (UC-CTL)
:toc: left
:toclevels: 2
:nofooter:

link:../UseCases.adoc[Use Cases] » Controlling Work

The operator steers work that exists: pauses, starts, cancels, or abandons a plan, or changes its settings; has an epic start its next plan, cancels or archives it; reviews what an epic has found and keeps under watch; and chats with the planning role of a plan or an epic, also about one that ended. The operator does this in the web app or in the terminal client, from the plan or the epic wherever it is shown (Running Work, the plan view, the project); how each client offers the actions is its design (link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/README.adoc[`pm-mcp-clients`, Design]).

[#principles]
== Principles

[#actions-by-state]
Actions follow the state:: A plan or an epic offers the actions its state allows, and only those; an action that does not apply is not offered, and one that applies but cannot run now is offered disabled with its reason.
[#epic-informed]
The epic always knows:: Whatever the operator does to a plan that an epic started reaches that epic, without the operator saying so; the epic reacts in its own workflow, as it does to every other event of its plans.
[#ending-archives]
Ending archives:: A plan that the operator cancels or abandons is archived, with its outcome and the reason; an epic is archived with its outcome when it is through, or when the operator cancels it.

[#UC-CTL-1]
== UC-CTL-1: Control a Plan

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client.
Goal:: stop a plan for a while, let it go on, end it, change its settings, or chat with its planning role about it, and know what that does to its work and to its epic.
Trigger:: the operator selects a plan in Running Work (link:03-plans.adoc#UC-PLN-4[UC-PLN-4]), in its plan view (link:03-plans.adoc#UC-PLN-1[UC-PLN-1]), or names it.
Flow::
+
[source,text]
----
  [S] plan.actions             the actions of the plan's state:
       │                       running: pause, cancel, chat, settings
       │                       pausing: start (the pause is withdrawn),
       │                         cancel, chat, settings
       │                       paused: start, abandon, chat, settings
       │                       waiting for the operator: those of running,
       │                         beside the decision it waits for (UC-PLN-2)
       │                       held (stalled, or another hold): those of
       │                         running, and the acts of its hold
       │                         (UC-CTL-4), whose end of the plan is cancel
       │                       ended: its view and a read-only chat
       ├── chat ─────────────► ↳ chat               with the plan's planning
       │                             │              role replan, over the
       │                             │              whole plan
       │                             ▼
       │                        [S] chat.open       the plan's facts, as data:
       │                             │              the outline, the tasks with
       │                             │              their status, the done
       │                             │              deliverables, the footprint
       │                             ▼
       │                        [O]⇄[M] chat.turn   the operator's message; the
       │                             │              role answers and may propose
       │                             │              a change; again, until the
       │                             │              operator ends the chat
       │                             ├── a change ──► [O] chat.read-back   the
       │                             │                proposed change in one
       │                             │                sentence beside the
       │                             │                operator's message: accept,
       │                             │                or reject ─► chat.turn
       │                             │                     │
       │                             │                     ▼ accept
       │                             │                [S] chat.apply   a revision
       │                             │                through the guards of a
       │                             │                first plan ─► chat.turn
       │                             ▼ end
       │                        [S] chat.end        the transcript kept with
       │                                            the plan
       ├── settings ─────────► the plan's own values (UC-CTL-5)
       ├── pause ────────────► [O] plan.pause-when   when it holds:
       │                             │             • now: running tasks are
       │                             │               withdrawn, running jobs
       │                             │               stopped; both run again on
       │                             │               start
       │                             │             • after the current task ←:
       │                             │               what runs finishes, nothing
       │                             │               new starts
       │                             │             • after the current phase:
       │                             │               the phase runs to its end
       │                             ▼
       │                        [S] plan.pausing   runs until that point, then
       │                             │             holds
       │                             ▼
       │                        plan.paused
       ├── start ────────────► [S] plan.start      runs on from where it rests
       ├── cancel ───────────► [O] plan.confirm-end   what ends: the running
       │                             │                work, the open pull
       ├── abandon ──────────►       │                request (close it, or
       │                             │                leave it open), the reason
       │                             ▼ end it
       │                        [S] plan.end        its tasks withdrawn, its
       │                             │              workers and jobs ended, its
       │                             │              lesson claim released; then
       │                             │              archived as cancelled or
       │                             ▼              abandoned, with the reason
       │                        plan.archived
       ▼ every action, where an epic started the plan
  [S] plan.inform-epic         the act reaches the epic's inbox: paused,
                               started, cancelled, abandoned, revised in a
                               chat, settings changed, with the reason
----
+
The settings are <<UC-CTL-5>>, a decision is answered in link:03-plans.adoc#UC-PLN-2[UC-PLN-2], and a hold is resolved in <<UC-CTL-4>>; the chat is the sub-workflow of <<change-chat>>.
Variations::
* *An operator wait* of the plan (a decision) stays open while the plan is paused; answering it does not start the plan. A pause after the current task or phase holds at an operator wait, too, since nothing runs there.
* *The runtime stops or the machine restarts*: a paused plan stays paused, a pausing plan holds at its point once it runs again, and a running plan runs on from its last committed state; an operator wait stays open (<<change-plan-pause>>).
* *A plan always runs once it exists*: a plan the operator starts (link:05-starting-work.adoc#UC-STA-1[UC-STA-1]) and a plan an epic starts run at once; the only plan that exists and does not run is a paused one.
* *Cancel* and *abandon* are the same end, named by the state the plan was in: a running or pausing plan, and one waiting for the operator or held, is cancelled, a paused one abandoned. Only the cancel of a plan held by an integrity pause is that pause's resolution _abort_, and ends the plan with the outcome `aborted` (<<change-plan-end>>).
* *Its epic reacts* in its own workflow: it may stage the plan's row again, hold the rows that depend on it, or ask the operator (<<UC-CTL-2>>); a plan the epic started is never ended by the epic itself.
* *A plan that runs no longer* (it has ended) offers no action but its view and a chat about it: read-only, with the role `replan` over its archived record, whose one proposal may be a follow-up plan (link:03-plans.adoc#change-ended-work[Ended Work], <<change-chat>>).
* *A chat on a running plan*: a question never touches the plan; an accepted revision takes effect at the next task boundary: what runs finishes, the revision is applied, the plan runs on. The revision is the operator's own act and does not spend the plan's re-planning budget; the server never starts a chat.
* *Chat is offered disabled*, with its reason, while no configuration of the role `replan` qualifies.
* *The operator's messages* in a chat are not interpreted: the role answers them. Only a change the role proposes passes a read-back (link:03-plans.adoc#change-own-words[Own Words]) before it applies; the role reads the plan as data, and nothing changes without _accept_.
* *A settings change* (<<UC-CTL-5>>) applies from where the plan next reads the value, and its epic is told (`settings changed`).
Outcome:: the plan is paused, running, revised, with its settings changed, or archived as the operator chose, and its epic knows.
Changes::
* *Pausing and starting a plan* (<<change-plan-pause>>).
* *Cancelling and abandoning archive* (<<change-plan-end>>).
* *The epic is told* (<<change-epic-informed>>).
* *Chatting with the planning role* (<<change-chat>>).
Requirements:: link:../requirements/02-workflow.adoc#PM-WF-12[PM-WF-12] (ending a plan, `abort`, an operator override), link:../requirements/08-security.adoc#PM-SEC-3[PM-SEC-3] (only through the operator's channel), link:../requirements/02-workflow.adoc#PM-WF-17[PM-WF-17] (the revision of a running plan); the operator abort is specified in link:../specification/phase-workflows/01-planning-phases-1-2.adoc[Planning Phases 1–2] (Operator Abort), the terminal states in link:../specification/state-catalogue/04-plan-finalize-terminal.adoc#state-catalogue-terminal[Terminal States], the revision of a running plan in link:../specification/phase-workflows/08-dynamic-re-planning.adoc#dynamic-re-planning[Dynamic Re-Planning]; for pausing a plan none yet.
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/work-actions.adoc#plan-actions[Actions on Plans and Epics, A Plan's Actions]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/19-actions.adoc#plan[Terminal Client, A Plan]; the web app: no design document yet; designed by its package link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/plans/web-actions.adoc[`web-actions`]

[#UC-CTL-2]
== UC-CTL-2: Control an Epic

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client.
Goal:: let an epic start its plans by itself or have it start its next plan now, end it, or archive it once it is through, review what it found and watches, and chat with its planning role about it.
Trigger:: the operator selects an epic in Running Work, or names it.
Flow::
+
[source,text]
----
  [S] epic.actions             the actions of the epic's state:
       │                       running: next plan, automatic on/off,
       │                         decompose again, findings review, watches
       │                         review, archive, cancel, chat
       │                       waiting for the operator: those of running,
       │                         beside what it waits for (a decomposition,
       │                         a decision: UC-PLN-2)
       │                       held: those of running, and the acts of its
       │                         hold (UC-CTL-4), whose end is cancel
       │                       landing: those of running; archive offered
       │                         disabled until the ledger has landed
       │                       ended: its view and a read-only chat
       ├── chat ─────────────► ↳ chat (as in UC-CTL-1), with the epic's
       │                         planning role decompose, over the whole
       │                         epic; an accepted change staged through the
       │                         epic's checks (surfaces disjoint,
       │                         dependencies without a cycle)
       ├── automatic on/off ─► [S] epic.auto   the epic's mode switched,
       │                                       told in its events; on: it
       │                                       starts what is launchable
       │                                       now ─► epic.next-work
       ├── decompose again ──► ↳ decomposition (UC-STA-6), with the
       │                         operator's instruction
       ├── next plan ────────► [S] epic.next-work   the next launchable row in
       │                             │              the queue's order: the plan
       │                             │              started from its staged
       │                             │              section, implicitly created
       │                             ├── none launchable ──► why, per row (a
       │                             │                       dependency, a lock,
       │                             │                       the scope full, an
       │                             │                       overlap with a
       │                             │                       running plan)
       │                             ├── scope full ──► [O] epic.raise-scope
       │                             │                  raise the scope by one
       │                             │                  ─► epic.next-work, or
       │                             │                  leave it
       │                             ▼
       │                        the plan runs (UC-CTL-1 controls it)
       ├── findings review ──► ↳ review (UC-CTL-3), the findings
       ├── watches review ───► ↳ review (UC-CTL-3), the watches
       ├── archive ──────────► [M] epic.review-completion   first, only
       │                             │                  when it has not run
       │                             │                  yet (automatic off)
       │                             ▼
       │                        [S] epic.archive-check   tests that it is
       │                             │                  through: no plan
       │                             │                  running or paused, every
       │                             │                  row shipped or ended, no
       │                             │                  open (undecided)
       │                             │                  finding, the ledger
       │                             │                  landed, the completion
       │                             │                  review done; lists the
       │                             │                  kept findings and the
       │                             │                  watches it carries
       │                             ├── not through ──► what is open, each
       │                             │                   leading to it
       │                             ▼ through
       │                        [S] epic.archive    the ledger, its kept
       │                                            findings and watches with
       │                                            it, moved to the archive
       │                                            and landed
       ├── cancel ───────────► [O] epic.confirm-cancel   its running and paused
       │                             │                   plans: cancel them too,
       │                             │                   or let them run on
       │                             │                   without the epic; the
       │                             │                   reason
       │                             ▼
       │                        [S] epic.cancel     its tasks withdrawn, its
       │                                            plans as chosen, its ledger
       │                                            archived as cancelled
       ▼
  epic.active                  the epic rests between its events
----
+
The chat is the one of <<UC-CTL-1>> (<<change-chat>>), the decomposition link:05-starting-work.adoc#UC-STA-6[UC-STA-6], the review <<UC-CTL-3>>, a hold <<UC-CTL-4>>.
Variations::
* *Automatic on* (the project's `epic.auto_start`, machine default on): the epic starts its plans itself, as many as its `parallelization_scope` admits (link:../specification/model-work/08-epic-coordination.adoc#server-started-plans[Server-Started Plans]), whenever a place frees or a row becomes launchable; _next plan_ is the operator starting the next one now. *Automatic off*: the epic starts nothing by itself; when a plan becomes launchable the operator gets a report of it, leading to the epic and its _next plan_ (link:03-plans.adoc#UC-PLN-6[UC-PLN-6]), and starts each plan with _next plan_; everything else the epic does still runs. The operator switches it at any time; the epic's events say so (<<change-epic-auto>>).
* *No pause of the epic*: an epic is not paused as a whole; its plans are paused one by one (<<UC-CTL-1>>), and a pausing or paused plan keeps its place in the `parallelization_scope`, so the epic starts no plan in its stead; to stop new starts, the operator switches automatic off.
* *How many plans run at once*: the `parallelization_scope` is the upper limit of the epic's running plans. It is never asked at the start: it is the project's `epic.parallelization_scope`, whose machine default is 1. The operator raises it here, where _next plan_ with the scope full says so and offers to raise it by one, or in the project's settings.
* *Too many common changes*: a launchable plan starts beside the running ones only while its declared surface shares no more files than the epic allows (by default none; the project's setting, which the operator changes on the epic like the automatic mode) with what each running plan declared and has changed. Over that, it waits (_waits: overlap with_ the plan) until that plan has ended; it is never started beside it, by the epic or by _next plan_. Two running plans whose changes come to overlap beyond it are reported and the epic is told; neither is stopped, and the one that lands second is re-planned or rebased onto the first.
* *When a plan of the epic ends*, the epic reacts by itself, in both modes: a landed plan is recorded and analysed, and the staged plans it affects are re-ordered or re-cut; a change that only re-orders them or amends a staged plan's surface or prerequisites is applied once the server's checks pass, one that adds, drops, or re-scopes a plan waits for the operator in the decomposition's review (link:05-starting-work.adoc#UC-STA-6[UC-STA-6]). A plan that ended without landing holds the plans that depend on it, and the operator is asked (<<UC-CTL-1>>). Then, with automatic on, the next launchable plans start; with it off, the epic shows what is launchable now.
* *Through*: when every plan is shipped or ended, an epic with automatic on runs its completion review and reports it; one with automatic off reports that it is through, and the operator's _archive_ runs the completion review first, then the archive check. Archiving stays the operator's act in both modes. Every start, wait, overlap, re-cut, and end is also a report to the operator (link:03-plans.adoc#UC-PLN-6[UC-PLN-6]).
* *Kept findings and watches* when the epic is through are listed by the archive check as carried; they do not hold the archive, and archiving keeps them in the archived ledger, so nothing the epic found or watched is lost. Only an open finding, one not decided yet, holds it.
* *An epic task waiting for the operator* (a held item, a decision) is shown with the actions and reached from them (link:03-plans.adoc#UC-PLN-2[UC-PLN-2]).
* *Chat is offered disabled*, with its reason, while no configuration of the role `decompose` qualifies; a chat changes only staged rows, never a plan that runs. An ended epic offers its view and a read-only chat with `decompose` over its archive, as an ended plan does (<<UC-CTL-1>>).
Outcome:: the epic runs by itself or waits for the operator's _next plan_, as the operator chose; it has started its next plan, has its staged rows changed in a chat, is archived because it is through, or is cancelled with its plans as the operator chose.
Changes::
* *An epic's actions* (<<change-epic-actions>>).
* *An epic runs by itself* (<<change-epic-auto>>).
* *An epic's findings and watches* (<<change-findings-watches>>).
* *The decomposition is reviewed* (link:05-starting-work.adoc#change-decomposition-review[The Decomposition Is Reviewed]).
* *Chatting with the planning role* (<<change-chat>>).
Requirements:: link:../requirements/02-workflow.adoc#PM-WF-15[PM-WF-15] (the epic starts its launchable plans itself), link:../requirements/02-workflow.adoc#PM-WF-12[PM-WF-12] (ending an epic, `abort`, an operator override), link:../requirements/02-workflow.adoc#PM-WF-13[PM-WF-13] (an archived epic's records stay readable); the epic workflow is specified in link:../specification/model-work/08-epic-coordination.adoc#epic-workflow[Epic Workflow], its states in link:../specification/state-catalogue/06-setup-epic-other.adoc[Epic States].
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/work-actions.adoc#epic-actions[Actions on Plans and Epics, An Epic's Actions], link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/epic-view.adoc[Epic View]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/19-actions.adoc#epic[Terminal Client, An Epic]; the web app: no design document yet; designed by its package link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/plans/web-actions.adoc[`web-actions`]

[#UC-CTL-3]
== UC-CTL-3: Review an Epic's Findings or Watches

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client, with the epic's planning role.
Goal:: go through what the epic found (findings: what its landings and plans surfaced that no plan owns yet) or keeps under watch, and decide each item: keep it, drop it, make a plan of it, or reshape it with a model's help.
Trigger:: the operator chooses _findings review_ or _watches review_ on an epic (<<UC-CTL-2>>), or follows the note that new findings wait.
Flow::
+
[source,text]
----
  [S] review.open              the items of the kind, open ones first: each
       │                       with its statement, its rules (what makes a
       │                       watch fire, what a finding requires), its
       │                       origin (a landing, a plan's message, an
       │                       observation), since when, and the planning
       │                       role's proposal for it
       ▼
  [O] review.item              per item: keep, drop, promote, edit, chat; or
       │                       accept the remaining proposals, or finish
       ├── keep ─────────────► [S] review.keep   kept as a finding (to be
       │                            fixed) or as a watch, moved to the
       │                            other register where the kind changes
       ├── drop ─────────────► [S] review.drop   dropped, with the operator's
       │                            reason
       ├── promote ──────────► [M] review.draft-plan   the planning role
       │                             │                 drafts a staged plan
       │                             │                 from the item: objective,
       │                             │                 deliverables, surface,
       │                             │                 dependencies
       │                             ▼
       │                        [O] review.confirm-plan   stage it, edit it,
       │                             │                    or back
       │                             ├── back ──► review.item
       │                             ├── edit ──► [O] review.instruct-plan
       │                             │            what to change in the
       │                             │            drafted plan
       │                             │                 │
       │                             │                 ▼
       │                             │            [M] review.redraft-plan
       │                             │            the planning role drafts
       │                             │            the plan again
       │                             │                 │
       │                             │                 ▼
       │                             │            [O] review.read-back-plan
       │                             │            the plan, old against new:
       │                             │            accept ─► review.confirm-plan
       │                             │            with the new draft; instruct
       │                             │            again ─► review.instruct-plan;
       │                             │            discard ─► review.confirm-plan
       │                             │            with the draft before
       │                             ├── stage, a check fails ──►
       │                             │            review.confirm-plan, the
       │                             │            finding with its plan
       │                             ▼ stage
       │                        review.item, the item promoted
       ├── edit ─────────────► [O] review.instruct   what to adapt or add to
       │                             │               the item's statement and
       │                             │               rules
       │                             ▼
       │                        [M] review.rewrite   the planning role
       │                             │               rewrites them
       │                             ▼
       │                        [O] review.read-back   the change, old against
       │                                               new: accept ─►
       │                                               review.item, the change
       │                                               applied; instruct again
       │                                               ─► review.instruct;
       │                                               discard ─► review.item,
       │                                               the item unchanged
       ├── chat ─────────────► ↳ chat (as in UC-CTL-1), with the planning
       │                         role decompose, over the item or the whole
       │                         register; an accepted change applied as the
       │                         item's disposition or rewrite ─► review.item
       ▼ finish
  [S] review.commit            the dispositions written to the epic's ledger
                               and landed; a promoted item is a staged row
----
+
The chat is the one of <<UC-CTL-1>> (<<change-chat>>).
Variations::
* *Usually interactive*: the operator decides item by item; _accept the remaining proposals_ takes the planning role's proposal for every item not decided yet, after one confirmation that lists them.
* *Leaving* keeps the decisions made so far; the review continues where it stopped, in either client.
* *The operator's words* in _edit_ and _chat_ are not interpreted: the planning role works from them, and what it proposes (a rewrite, a redrafted plan, a change in the chat) passes a read-back (link:03-plans.adoc#change-own-words[Own Words]) before it applies; the planning role reads the items as data, and a finding that came from outside the machine stays marked untrusted.
Outcome:: every reviewed item is kept as a finding, moved to the watches, dropped, or staged as a plan, its statement and rules as the operator shaped them, recorded in the epic's ledger.
Changes::
* *An epic's findings and watches* (<<change-findings-watches>>).
* *The review* (<<change-epic-review>>).
* *Chatting with the planning role* (<<change-chat>>).
Requirements:: none yet; the epic's coordination is specified in link:../specification/model-work/08-epic-coordination.adoc[Epic Coordination].
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/work-actions.adoc#review[Actions on Plans and Epics, Reviewing]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/19-actions.adoc#review[Terminal Client, A Review]; the web app: no design document yet; designed by its package link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/plans/web-actions.adoc[`web-actions`]

[#UC-CTL-4]
== UC-CTL-4: Resolve What Holds a Plan

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client.
Goal:: see why a plan, an epic, or a project's landing does not go on, when no decision is asked, and resolve it.
Trigger:: Running Work marks a hold (link:03-plans.adoc#change-needs-operator[What Needs the Operator]), one of the kinds `stalled` (a plan stalled), `condition` (a condition that needs an operator act), `integrity_pause`, `held` (an item of an epic held), and `landing_failed` (a failed landing of an epic or of a move).
Flow::
+
[source,text]
----
  [S] hold.show                what holds, from a closed list, with its
       │                       cause, since when, what was tried, and the
       │                       acts that resolve it:
       │                       • stalled: retry now, recycle the worker
       │                       • condition: the act it names (grant access,
       │                         add a credential, raise a budget), each as
       │                         a dialogue of the clients
       │                       • integrity_pause: the tampered file with
       │                         its recorded and current size and digest;
       │                         accept it
       │                       • held, landing_failed: retry, or the
       │                         item's own acts; for the removal of moved
       │                         documents from git also give it up (the
       │                         files stay tracked; the source keeps its copy)
       │                       • and always, for a plan or an epic: cancel
       │                         (UC-CTL-1, UC-CTL-2); for an integrity
       │                         pause the cancel is its abort: a plan
       │                         ended as aborted, an epic as cancelled
       ▼
  [O] hold.resolve             the operator's act, confirmed where it cannot
       │                       be undone
       ▼
  [S] hold.apply               the act applied
       ├── still held ───────► hold.show   what still holds, with its cause
       ▼ released
  hold.released                the plan, the epic, or the landing goes on
----
Variations:: an act that today needs the operator's terminal (granting access, accepting an edit) is offered in both clients; an integrity pause shows no diff and offers no restore, since the prior content is not kept: the operator accepts the file as it is, or cancels; a hold that clears by itself (a provider back) disappears without an act.
Outcome:: what held is resolved, or the plan or the epic is ended; nothing waits without the operator knowing why.
Changes::
* *Holds and their acts* (<<change-holds>>).
Requirements:: link:../requirements/02-workflow.adoc#PM-WF-3[PM-WF-3] (the conditions on a state and how they are resolved), link:../requirements/01-architecture.adoc#PM-ARCH-7[PM-ARCH-7] (a stalled plan or epic reported to the operator); the conditions are specified in link:../specification/state-catalogue/01-conventions-generic-conditions.adoc[Generic Conditions], stalled plans in link:../specification/runtime-model/04-sessions-and-workers.adoc#stalled-plans[Stalled Plans].
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/work-actions.adoc#holds[Actions on Plans and Epics, Holds]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/19-actions.adoc#holds[Terminal Client, What Holds a Plan]; the web app: no design document yet; designed by its package link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/plans/web-actions.adoc[`web-actions`]

[#UC-CTL-5]
== UC-CTL-5: Change a Plan's Settings

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client.
Goal:: give one plan its own value of an aspect (how it lands, works, and asks; a role's harness, model, or effort; an integration's variant or an optional provider) without changing the project's or the machine's, and know from where it applies.
Trigger:: the operator chooses _settings_ on a plan (<<UC-CTL-1>>), in any state until the plan has ended.
Preconditions:: the plan has not ended.
Flow::
+
[source,text]
----
  [S] plan-settings.open       the plan's values per aspect, each with where
       │                       it comes from (the plan, the project, the
       │                       machine): the plan defaults (landing, method,
       │                       asking), the roles, the providers
       ▼
  [O] plan-settings.aspect     the aspect to change, or close
       │
       ▼
  [O] plan-settings.value      the plan's own value, the current one
       │                       preselected ←; or remove the plan's value, so
       │                       that the project's or the machine's applies
       ▼
  [S] plan-settings.validate   the validation of the machine values: an
       │                       enrolled harness, an allowed model, an
       │                       available provider, a landing variant that
       │                       fits the project and the plan
       ├── refused ──► the reason ─► plan-settings.value
       ▼ valid
  [S] plan-settings.apply      the value written to the plan's overrides
       │                       and audited; a new instance version
       │                       composed, under the position rule, from
       │                       which the plan reads the value where it next
       │                       needs it
       ├── too late ──► the reason: the version would not contain the
       │                plan's position ─► plan-settings.aspect
       ├── changed meanwhile ──► conflict: the current value
       │                          ─► plan-settings.value
       ▼
  [S] plan.inform-epic         where an epic started the plan, its inbox
                               is told: settings changed, with the aspect
----
Variations::
* *Set where first needed*: a value the plan asks where it first needs it (link:05-starting-work.adoc#change-options-when-needed[Asked When Needed]) is the same plan value; this use case changes it later, or sets it before it is asked, so that it is not asked.
* *A running plan* goes on while its settings change; what runs keeps the value it started with, and the new value applies from where the plan next reads it (a task started after it, the call site of an axis not yet reached).
* *Too late*: a change whose new version would not contain the plan's current state and its call stack (the landing variant while the plan lands, for example) is refused with the reason; what has already run is not run again.
* *Changed in two clients at once*: the first change wins; a later one made against an older value is refused with `conflict`, the current value shown, and the operator may apply theirs again on top of it (link:01-onboarding.adoc#concurrent-changes[Operator Choices in the Web App and the Terminal, Concurrent Changes]).
* *Refused values*: a landing variant that cannot run for the project (`landing.pull-request` without a provider, `landing.main` on a protected base branch) or for the plan (`landing.files` for a plan from local changes, link:05-starting-work.adoc#UC-STA-9[UC-STA-9]) is refused with the reason; so is a harness, model, or provider the machine does not allow.
Outcome:: the plan has its own value of the aspect, a new instance version shows it, the change is audited, and its epic knows.
Changes::
* *Plan overrides* (link:01-onboarding.adoc#change-plan-overrides[Plan Overrides]).
* *Concurrent changes of a setting* (link:01-onboarding.adoc#concurrent-changes[Operator Choices in the Web App and the Terminal, Concurrent Changes]).
* *The epic is told* (<<change-epic-informed>>).
Requirements:: link:../requirements/14-implementation.adoc#PM-IMPL-5[PM-IMPL-5] (the plan instance, composed again for a change), link:../requirements/02-workflow.adoc#PM-WF-14[PM-WF-14] (a worker's harness, model, and effort from its role); the plan instance and its composition events are specified in link:../specification/workflow-dsl/09-plan-instance.adoc#plan-instance[Plan Instance], the harness of a role in link:../specification/model-work/04-worker-launch.adoc#harness-selection[Harness Selection]; for a plan's own values none yet.
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/work-actions.adoc#plan-actions[Actions on Plans and Epics, A Plan's Actions]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/19-actions.adoc#plan[Terminal Client, A Plan]; the web app: no design document yet; designed by its package link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/plans/web-actions.adoc[`web-actions`]

== Changes to the Specification

The changes these use cases need, each modelled as the fix of a gap; when and by whom a fix is written is the convention link:../UseCases.adoc#changes[Changes].

[#change-plan-pause]
=== Pausing and Starting a Plan

Gap:: the operator can only abort a plan (`pm-operator abort plan`); there is no pause, no state of a plan that exists but does not run, and the state _paused_ of Running Work (link:03-plans.adoc#UC-PLN-4[UC-PLN-4]) has nothing behind it; the specification states that no operator verb stops, continues, or steers a plan between phases.
Fix::
* A plan is *running*, *pausing* (running until the point its pause names), or *paused*. A plan always runs once it exists: starting a plan, by the operator or by its epic, creates and runs it in one act, and the epic's plans are never created to wait; _emit_ is not a step of its own.
* *Pause* is an operator act over the local API with the point where the plan holds: *now* (running tasks withdrawn as on a recycle, running jobs stopped, both run again on start), *after the current task* (the default: what runs finishes and its result is kept, nothing new starts), or *after the current phase* (the phase's sub-workflow runs to its end, the next phase is not entered). The plan's operator waits stay open.
* *Start* resumes a paused plan from its current state; on a pausing plan it withdraws the pause.
* *A pause survives a restart*: the pause and its point are part of the plan's state; after a restart of the runtime a paused plan stays paused and a pausing plan holds at its point.
Affects:: link:../requirements/02-workflow.adoc#PM-WF-1[PM-WF-1] ("the only pause is an integrity breach": the operator's pause joins it), link:../requirements/02-workflow.adoc#PM-WF-12[PM-WF-12] ("influence a running plan only through waivers": pausing and starting join them), link:../specification/runtime-model/04-sessions-and-workers.adoc[Sessions & Workers] (the withdrawal of a task), link:../specification/store-schemas/02-workflow-state-store.adoc[Workflow State Store] (the plan's activity), link:../specification/runtime-model/01-processes-and-transport.adoc#local-api[Local API], link:../specification/cli-and-security/02-credentials-and-operator.adoc[Operator CLI], link:../specification/phase-workflows/07-questions-waivers-operator-influence.adoc[Questions, Waivers & Operator Influence] ("no operator verb stops, continues, or steers a plan"), link:../specification/domain-extensions/04-setup-state-machine.adoc[Setup State Machine] ("no in-run operator decision remains"), link:../requirements/08-security.adoc[PM-SEC-3], link:../specification/runtime-model/02-startup-recovery-drain.adoc[Startup, Recovery & Drain].

[#change-plan-end]
=== Cancelling and Abandoning Archive

Gap:: `pm-operator abort plan` moves a plan to `plan.aborted`, which is never archived: the aborted plan stays among the project's plans. Its open pull request is left as it is. Every end through `plan.aborted` has the one outcome `aborted`, whether the operator ended the plan, resolved an integrity pause by aborting it, or released the project (reason `project_released`).
Fix::
* *Cancel* (a running or pausing plan, and one waiting for the operator or held) and *abandon* (a paused one) end the plan through `plan.aborted` with the outcome `cancelled` or `abandoned` and the operator's reason, then archive it like a completed plan; its lesson claim is released as today.
* *The pull request*: the operator chooses in the confirmation whether an open pull request of the plan is closed (with a comment naming the reason) or left open; its branch stays.
* `pm-operator abort plan` becomes the shell form of cancel and abandon.
* *Four outcomes of an operator's or the project's end* join the closed list of plan outcomes beside `merged`, `handed_back`, `returned`, and `no_change`: `cancelled` and `abandoned` (above); `released`, set by the release of the project on every plan that has not ended, whatever its state, never `cancelled` or `abandoned`; and `aborted`, which stays the outcome of the integrity abort (the resolution _abort_ of an `integrity_breach`). All four are archived the same way, with their reason.
Affects:: link:../specification/state-catalogue/04-plan-finalize-terminal.adoc#state-catalogue-terminal[Terminal States], link:../specification/filesystem-layout/03-project-store.adoc#archives[Archives], link:../specification/phase-workflows/01-planning-phases-1-2.adoc[Planning Phases 1–2] (Operator Abort), link:03-plans.adoc#change-running-work[Running Work] (an aborted plan is not active), link:../specification/cli-and-security/02-credentials-and-operator.adoc#operator-abort[Operator Abort] and `delete-plan`, link:../specification/cli-and-security/02-credentials-and-operator.adoc#enrolment-lifecycle-release[Release] (the release aborts every plan), link:../specification/store-schemas/13-leases-integrity-testing.adoc[Integrity] (the integrity abort), link:../requirements/02-workflow.adoc[PM-WF] (the closed list of plan outcomes), link:../specification/runtime-model/01-processes-and-transport.adoc#local-api[Local API].

[#change-epic-informed]
=== The Epic Is Told

Gap:: an epic learns a plan's outcome from the plan's events (`plan_outcome`) only once the plan ends in a terminal state; an operator's pause or start of its plan does not reach it, and nothing says what an epic does with a plan the operator ended.
Fix::
* Every operator act on a plan whose `origin.epic_id` names a live epic appends a record to the epic's inbox (`paused`, `started`, `cancelled`, `abandoned`, `revised` by a chat, `settings_changed` by a change of its settings (<<UC-CTL-5>>), with the reason and the operator's channel), and the queue row follows the plan's state.
* The epic's `coordinate` task decides on it as on every inbox message: re-stage the row, hold the rows that depend on it, leave it, or raise a decision for the operator; the epic never ends a plan itself.
* The queue row's status gains `pausing`, `paused`, and `cancelled`, following its plan. `abandoned` keeps its meaning (a pull request closed after hand-back, and the plan outcome `aborted`) and also covers a paused plan the operator abandoned. A plan's outcome `released` changes no queue row: the release leaves the epic's ledger untouched and records the outcome in the machine's archive only (link:04-projects.adoc#change-project-release[Releasing Ends Work as the Operator Ends It]).
* *A pausing or paused plan keeps its place*: its row counts toward the epic's `parallelization_scope` like a `running` one, so the epic starts no plan in its stead; to stop new starts the operator switches automatic off (<<change-epic-auto>>).
* The release of the project is no act on one plan: it ends the epic with its plans (<<change-epic-actions>>), so nothing is left to tell it.
Affects:: link:../specification/model-work/08-epic-coordination.adoc#plan-scope-outbox-link[Plan-Scope Outbox Link], link:../specification/store-schemas/04-epic-and-change-ledger.adoc#epic-inbox-record[Epic Inbox Record], link:../specification/store-schemas/04-epic-and-change-ledger.adoc#epic-queue-row[Queue Row], link:../specification/model-work/08-epic-coordination.adoc#server-started-plans[Server-Started Plans] (Admission: a pausing or paused row keeps its place).

[#change-epic-actions]
=== An Epic's Actions

Gap:: the operator can only abort an epic (`pm-operator abort epic`, which sets `terminal_reason` `abandoned`, also when the release of the project aborts it); it starts its plans only by itself, archives only when its completion review says so, and has nothing to show the operator why it is or is not through.
Fix::
* *Next plan*: an operator act that has `epic.next-work` start the next launchable row now (which creates its plan implicitly), in the queue's order, under the same admission tests (dependencies, surfaces, locks); with no launchable row it answers why per row; with the scope full it offers to raise `parallelization_scope` by one.
* *Decompose again*: the operator's instruction starts `decomposition` (link:05-starting-work.adoc#change-decomposition-review[The Decomposition Is Reviewed]) over the staged rows.
* *Archive*: the operator's request runs `epic.review-completion` first where it has not run yet (an epic with automatic off, <<change-epic-auto>>), then the archive check (no plan running or paused, every row shipped or ended, no open finding, the ledger landed, the completion review done) and archives through `epic.archive` only when it passes; otherwise it answers what is open. Only an `open` finding, one not decided yet, holds the archive; kept findings and the watches go into the archive with the epic, and the check lists them as carried.
* *Cancel*: `pm-operator abort epic` with the operator's choice for its plans: cancel them too (each through <<change-plan-end>>), or let them run on detached (link:../specification/model-work/08-epic-coordination.adoc#server-started-plans[Children of a Terminal Epic]).
* *Endpoints*: the acts are operator endpoints of the epic resource (link:03-plans.adoc#change-epic-resource[The Epic as a Resource]).
* *Outcome*: the epic's `terminal_reason` is `completed`, set by the archive; `cancelled`, set by cancel, the value `abandoned` of today renamed (before 1.0, without a shim), so that an epic ends in the words of a plan ended while it runs; or `released`, new, set by the release of the project, which ends the epic and its plans together (each plan `released`, <<change-plan-end>>); the release archives the epic on the machine only and leaves its ledger in `.marshall/epics/` untouched (link:04-projects.adoc#change-project-release[Releasing Ends Work as the Operator Ends It]).
Affects:: link:../specification/model-work/08-epic-coordination.adoc#epic-workflow[Epic Workflow], link:../specification/state-catalogue/06-setup-epic-other.adoc[Epic States] (`epic.next-work`, `epic.archive`, `epic.review-completion`), link:../specification/cli-and-security/02-credentials-and-operator.adoc[Operator CLI], link:../specification/cli-and-security/02-credentials-and-operator.adoc#enrolment-lifecycle-release[Release] (`released`), link:../specification/store-schemas/04-epic-and-change-ledger.adoc#epic-header[Epic Header] (`terminal_reason`, `parallelization_scope`).

[#change-epic-auto]
=== An Epic Runs by Itself

Gap:: `epic.next-work` always starts every launchable row the `parallelization_scope` admits; the operator cannot have an epic wait for the go-ahead, and the specification rules out a setting for it (*deliberate change vs. `plan-marshall`*: `orchestrator.auto_emit` does not exist, link:../specification/model-work/08-epic-coordination.adoc#server-started-plans[Server-Started Plans]). Its admission compares no surfaces: disjointness is checked only between declared surfaces when a row is staged, and the drift of a running plan, its realized changes beyond its declared surface, is only noted at its landing (link:../specification/model-work/08-epic-coordination.adoc#epic-surface-disjointness[Staging-Time Surface Disjointness], items 3 and 5), so a row whose surface a running plan has already changed starts beside it. What the epic does once a plan ended is not one rule: the landing task judges the downstream impact, every re-cut waits for the operator in `decomposition.review` whatever it changes (link:05-starting-work.adoc#change-decomposition-review[The Decomposition Is Reviewed]), and `epic.review-completion` with `complete` archives the epic by itself, which <<change-epic-actions>> makes the operator's act.
Fix::
* *The epic's mode*: the epic header gains `auto_start` (boolean), taken at the epic's creation from the project key `epic.auto_start` (machine default `true`, so the specified behaviour stays the default) and never asked at the start: `start-epic.ready` shows the value in force (link:05-starting-work.adoc#UC-STA-2[UC-STA-2]). The operator switches it at any time with the epic's action _Automatic: on/off_, an operator endpoint of the epic resource (link:03-plans.adoc#change-epic-resource[The Epic as a Resource]); the switch is a ledger write of the header, landed like every ledger write, told in the epic's events, and an `operator_action` that re-enters `epic.next-work`. `parallelization_scope` stays the upper limit of the epic's running plans (link:05-starting-work.adoc#change-options-when-needed[Asked When Needed]).
* *On*: whenever a place frees or a row becomes launchable, `epic.next-work` starts every launchable row up to the limit, as specified; a pausing or paused row holds its place like a `running` one (<<change-epic-informed>>), so pausing a plan frees no place. *Off*: `epic.next-work` starts nothing by itself and reports each row that became launchable (`epic.launchable`); the operator's _next plan_ (<<change-epic-actions>>) starts the next launchable row under the same admission; every other step of the epic (its tasks, its landings, the reactions below) runs in both modes.
* *Overlap at admission*: a launchable row is admitted beside the running plans of the epic only while its declared surface shares at most `overlap_max_files` files with each running plan's declared surface and with its realized changes (the realized footprint, link:../specification/phase-workflows/03-q-gate-and-execute.adoc#_task_envelope_execution_independent_server_verification[Task Envelope Execution]). Over it, the row waits with the reason `overlap` naming that plan (_waits: overlap with <plan>_), beside `dependency`, `lock`, and `scope`, derived on read like them, until that plan has ended; it is never started in parallel, by the epic or by _next plan_. The staging check between declared surfaces stays as it is.
* *`overlap_max_files`*: a project key `epic.overlap_max_files` with a compiled upper bound and the machine default `0` (any common file makes the row wait), not a unit declaration, since the epic unit is compiled only (link:../specification/workflow-dsl/04-ast-node-model.adoc#project-owned-units[Project-Owned Workflow Units]). A new epic takes the project's value into its header, like `auto_start`, and the operator changes the epic's value at any time from the epic's settings, like the automatic switch: a ledger write of the header, told in the epic's events and re-entering `epic.next-work`.
* *Overlap found while running*: when a running plan's realized changes come to overlap another running plan's declared surface or realized changes beyond `overlap_max_files`, the server records it in the epic, tells the epic in its events, and reports it (link:03-plans.adoc#change-reports[Reports to the Operator], `epic.overlap_found`); neither plan is stopped, since drift never blocks. The plan that lands second meets the base-advanced trigger of re-planning (link:../specification/phase-workflows/08-dynamic-re-planning.adoc#replan-triggers[Triggers & Detection], `PM-WF-17`) where the overlap reaches its threshold `base_overlap_min_files`, otherwise its rebase and `remediation.merge-conflict`.
* *An ended plan* reaches the epic's inbox as today (landed or merged, and the operator's acts, <<change-epic-informed>>), and the epic reacts in its workflow, in both modes: for a landed plan it records the landing and runs the landing task's downstream impact judgment; the staged rows it affects are re-ordered or re-cut through `epic.recut`, where a change that only re-orders rows or amends a staged row's surface or prerequisites is applied once the server's checks pass (the staging check, dependencies without a cycle) and reported (`epic.recut_applied`), and one that adds, drops, or re-scopes a plan waits for the operator in `decomposition.review`. For a plan that ended without landing (cancelled, abandoned, handed back, released, aborted) the rows that depend on it are held with that reason and the operator is asked (<<change-epic-informed>>). Then `epic.next-work` runs: with automatic on it starts the next launchable rows up to the limit; with it off it reports each row that became launchable (`epic.launchable`), and its view and its events show what is launchable now.
* *Through*: the epic is through when every row is shipped or ended. With automatic on, it then runs `epic.review-completion` and reports it (`epic.through`); with it off, it reports that it is through, and the completion review runs before the archive check of the operator's _archive_. `complete` no longer enters `epic.archive`: archiving stays the operator's act (<<change-epic-actions>>).
Affects:: link:../specification/model-work/08-epic-coordination.adoc#epic-workflow[Epic Workflow] (`epic.next-work`, `epic.recut`, `epic.review-completion`), link:../specification/model-work/08-epic-coordination.adoc#server-started-plans[Server-Started Plans] (Admission, the deliberate change), link:../specification/model-work/08-epic-coordination.adoc#epic-surface-disjointness[Staging-Time Surface Disjointness] (items 3 and 5), link:../specification/model-work/08-epic-coordination.adoc#server-derived-landing-facts[Server-Derived Landing Facts] (Running Rows Are Not Re-Scoped), link:../specification/state-catalogue/06-setup-epic-other.adoc#state-catalogue-epic[Epic States], link:../specification/store-schemas/04-epic-and-change-ledger.adoc#epic-header[Epic Header] (`auto_start`, `overlap_max_files`), link:../specification/store-schemas/04-epic-and-change-ledger.adoc#epic-queue-row[Queue Row] and link:03-plans.adoc#change-epic-resource[The Epic as a Resource] (the wait reason `overlap`), link:../specification/store-schemas/08-project-configuration-local.adoc#local-config[Operator Local Configuration] and link:../specification/store-schemas/12-machine-stores.adoc#machine-config[Machine Configuration Store] (`epic.auto_start`, `epic.overlap_max_files`, `project_defaults`), link:05-starting-work.adoc#change-decomposition-review[The Decomposition Is Reviewed] (a re-cut that only re-orders or amends rows), link:../requirements/02-workflow.adoc#PM-WF-15[PM-WF-15].

[#change-findings-watches]
=== An Epic's Findings and Watches

Gap:: the epic routes each message of its inbox (`coordinate`: transferred, re-scoped, left alone) and analyses each landing, but keeps nothing of what they surface: no problem that no plan owns yet, no observation to check again later. `plan-marshall` keeps both in its epic narrative, by hand.
Fix::
* The epic keeps two registers in its ledger: *findings* (a problem no plan owns yet, to be fixed) and *watches* (an observation to check again, with the trigger that checks it). Each item has an id, its statement, its rules, its origin (a landing, a plan's message, an observation), when it was opened, and its state (open, kept, dropped, promoted with the row it became); _open_ is an item not decided yet, and keeping an item keeps it as a finding or moves it to the watches.
* `epic.analyze-landing` and `coordinate` add items instead of only routing; a watch whose trigger fires (a landing, an advance of the default branch) is re-checked by the epic's task and becomes a finding or is closed.
* New findings are a kind of `needs_operator` of the epic, so the operator learns of them in Running Work.
Affects:: link:../specification/model-work/08-epic-coordination.adoc[Epic Coordination], link:../specification/store-schemas/04-epic-and-change-ledger.adoc[Epic & Change Ledger] (the registers), link:../specification/state-catalogue/06-setup-epic-other.adoc[Epic States], link:03-plans.adoc#change-needs-operator[What Needs the Operator].

[#change-epic-review]
=== The Review

Gap:: nothing lets the operator decide an epic's items: an epic task decides alone, and the operator only reads the ledger.
Fix::
* A sub-workflow `review` over one register, of operator waits and tasks of the epic's planning role (the role `decompose`, which drafts the epic's plans): its proposal per item, the draft of a staged plan for _promote_, the rewrite of an item for _edit_; _chat_ calls the sub-workflow `chat` with the item or the register as its scope (<<change-chat>>); every change a model proposes reaches the register only through the operator's read-back.
* Its dispositions are written to the ledger in one write and landed like every ledger write; a promoted item stages a row under the same surface checks as `epic.decompose`.
Affects:: link:../specification/model-work/08-epic-coordination.adoc[Epic Coordination], link:../specification/model-work/01-roles-and-configuration.adoc#default-roles[Default Role Set] (the planning role's tasks), link:03-plans.adoc#change-own-words[Own Words] (the read-back).

[#change-chat]
=== Chatting with the Planning Role

Gap:: the operator chats with a planning role only inside the decomposition's review and the review of an epic's items, each with an exchange of its own; nothing lets the operator ask a plan or an epic about itself, or steer a running plan in words: a plan is re-planned only when the server's checkpoints raise a trigger, and re-planning never asks the operator (`PM-WF-17`). Nor can the operator ask back before answering a decision (an answer names an option, or is the operator's words alone), talk over what a start's sources say before the work exists, or ask an ended plan or epic why it ended.
Fix::
* *One sub-workflow `chat`*, a compiled unit like the source and epic units, its states `chat.<state>`; a plan calls it, and the chat has the phase of the phase sub-workflow on its call stack, the phase it is called in; an epic, `decomposition.review`, `review`, a decision (`decision.answer`), a start (`start.sources`, `start-epic.sources`), and the ended work call it too, each with its subject (a plan, an epic, an entry, or a project's workspace for a setup decision) and a scope: the whole plan, the whole epic, the decomposition's draft, one item of a register, the whole register, one decision, a start's entry, or an ended plan's or epic's archived record.
* *It routes to the subject's planning role*: for a plan the role `replan`, whose facts are those of a re-planning task without a trigger (the outline's deliverables with their state, the plan tasks with their status, the declared and the realized footprint); for an epic, its decomposition, and its review the role `decompose`; for a decision a worker asked, the role of the task that asked, and for one a server rule raised or a quorum escalated, the subject's planning role; for a workspace decision a worker asked, that role, while one the setup's workflow raised has no planning role, and _chat_ is offered disabled with that reason; for a start, `refine` for a plan's entry and `decompose` for an epic's; for ended work, `replan` for a plan and `decompose` for an epic. A plan and an epic offer _chat_ in every state, an ended one read-only; every caller offers it disabled with its reason while no configuration of the routed role qualifies.
* *Its states*: `chat.open` (server) assembles the facts of the scope as data, an untrusted item still marked untrusted; `chat.turn`, an operator wait for the operator's message, which is not interpreted, then one task of the routed role that answers and may propose changes, again until the operator ends the chat; `chat.read-back`, an operator wait that shows each proposed change as a read-back (link:03-plans.adoc#change-own-words[Own Words]) to accept or reject; `chat.apply` (server); `chat.end`, which keeps the transcript with the subject for the audit and sends it nowhere else. Nothing changes without _accept_.
* *An accepted change goes through the caller's own path and its checks*: for the decomposition into the draft and the server's checks; for a review as the item's disposition or rewrite; for an epic as staged rows through the epic's checks (surfaces disjoint, dependencies without a cycle); for a plan as a revision through the guards of a first plan (the outline validation, the derivation dry-run, the task graph, the Q-Gate's mechanical checks), applied as `replan.apply` applies one and composing a plan instance version of the event `replan`, its re-planning record naming the operator's chat as who decided.
* *A running plan*: a question never touches it; an accepted revision takes effect at the next task boundary (what runs finishes, the revision is applied, the plan runs on). The revision is the operator's own act and does not spend `replan_budget`; `PM-WF-17` stays true, since the operator starts a chat and the server never does.
* *The epic is told* of a revision of a plan it started (<<change-epic-informed>>).
* `decomposition.review` and `review` lose their own exchanges and call `chat`.
* *In a decision* (link:03-plans.adoc#UC-PLN-2[UC-PLN-2]): `decision.answer` offers _chat_ beside own words, _none fits_, and _later_, to ask back before answering. The scope is the decision: its question, why now, the evidence, what it blocks, how reversible it is, its parts and options, and the recommendation and the quorum's votes, which the chat may explain. The chat never answers: an answer it proposes is offered to the operator as the operator's own words and passes `decision.interpret` and `decision.read-back` unchanged, the interpretation still never seeing the recommendation or the votes. A revision of the plan it proposes goes through the guards of a plan's chat (above); the decision stays open, unless the revision removes the task or state that asked it, in which case the server closes it `withdrawn`, with the reason. The plan waits during the chat as for any decision, without a time limit; the transcript is kept with the decision, and its record says the answer followed a chat. A waiver request offers no chat (a waiver is an override, never a content answer); an answer in another channel closes the decision and ends the chat.
* *While starting* (link:05-starting-work.adoc#UC-STA-1[UC-STA-1], link:05-starting-work.adoc#UC-STA-2[UC-STA-2]): `start.sources` and `start-epic.sources` offer _chat_ once a source is stored and every external one screened, never for a recipe. The scope is the entry: its stored sources, an untrusted one still marked, and its descriptions; nothing of a plan exists yet. The one change the chat may propose is a description, a rewrite of one or an addition, which after its read-back the main workflow stores through `start.store-description` as a new description of the source directory; it never changes, adds, or removes another source. Starting never waits for a chat. The transcript stays with the entry (`pending/<entry_id>/chat/`) and moves with the source directory at `start.create` into the plan's machine store (`plans/<plan_id>/chat/`), or into the epic's machine store, never into its ledger; it is no source and no model of the plan reads it. Abandoning the entry deletes it.
* *About ended work* (link:03-plans.adoc#change-ended-work[Ended Work]): an ended plan or epic offers a read-only chat over its archived record (outcome, reason, history, decisions, re-planning records, events), read through the archive's read access by id; it runs in the project's workspace scope and never changes the archive. Its one change is a *follow-up plan*: a description drafted in the chat which, once read back, opens the start of a new plan (link:05-starting-work.adoc#UC-STA-1[UC-STA-1]) with that description stored and the ended plan or epic named in it, from where the operator goes on at `start.sources`. The transcript is kept beside the archived record in the machine store (`archive/<plan_id>/chat/`, an epic's in its machine store `epics/<epic_id>/chat/`), never in a ledger. There is no lesson to propose: the specification has no operator path that records one.

[#change-holds]
=== Holds and Their Acts

Gap:: what holds a plan without a decision (a stall, a condition that names an operator command, an integrity pause, a held item, a failed landing) is reported as a condition with an operator command as text (`facts.operator_command`); the acts are terminal verbs, several of them unavailable in the web app, and none is described for a client.
Fix::
* Each hold is a record of the scope with its kind, from the closed list `stalled`, `condition`, `integrity_pause`, `held`, `landing_failed` (the same kinds in `needs_operator`), cause, since when, attempts, and the acts that resolve it, each act an operator endpoint of both clients with its arguments; an operator command as relay text goes.
* A hold that clears by itself ends its record and its event says so.
* Beside its own acts, a hold of a plan or an epic offers *cancel* (<<change-plan-end>>, <<change-epic-actions>>); for an integrity pause the cancel is its resolution _abort_, which ends a plan with the outcome `aborted` and an epic as `cancelled`. `paused` is no hold: a paused plan shows by its state.
