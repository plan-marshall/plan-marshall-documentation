= Use Cases: Controlling Work (UC-CTL)
:toc: left
:toclevels: 2
:nofooter:

link:../UseCases.adoc[Use Cases] » Controlling Work

The operator steers work that exists: pauses, starts, cancels, or abandons a plan, or changes its settings; has an epic start its next plan, cancels or archives it; reviews what an epic has found and keeps under watch; and chats with the planning role of a plan or an epic, also about one that ended. The operator does this in the web app or in the terminal client, from the plan or the epic wherever it is shown (Running Work, the plan view, the project); how each client offers the actions is its design (link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/README.adoc[`pm-mcp-clients`, Design]).

[#principles]
== Principles

[#actions-by-state]
Actions follow the state:: A plan or an epic offers the actions its state allows, and only those; an action that does not apply is not offered, and one that applies but cannot run now is offered disabled with its reason.
[#epic-informed]
The epic always knows:: Whatever the operator does to a plan that an epic started reaches that epic, without the operator saying so; the epic reacts in its own workflow, as it does to every other event of its plans.
[#ending-archives]
Ending archives:: A plan that the operator cancels or abandons is archived, with its outcome and the reason; an epic is archived with its outcome when it is through, or when the operator cancels it.

[#UC-CTL-1]
== UC-CTL-1: Control a Plan

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client.
Goal:: stop a plan for a while, let it go on, end it, change its settings, or chat with its planning role about it, and know what that does to its work and to its epic.
Trigger:: the operator selects a plan in Running Work (link:03-plans.adoc#UC-PLN-4[UC-PLN-4]), in its plan view (link:03-plans.adoc#UC-PLN-1[UC-PLN-1]), or names it.
Flow::
+
[source,text]
----
  [S] plan.actions             the actions of the plan's state:
       │                       running: pause, cancel, chat, settings
       │                       pausing: start (the pause is withdrawn),
       │                         cancel, chat, settings
       │                       paused: start, abandon, chat, settings
       │                       waiting for the operator: those of running,
       │                         beside the decision it waits for (UC-PLN-2)
       │                       held (stalled, or another hold): those of
       │                         running, and the acts of its hold
       │                         (UC-CTL-4), whose end of the plan is cancel
       │                       ended: its view and a read-only chat
       ├── chat ─────────────► ↳ chat               with the plan's planning
       │                             │              role replan, over the
       │                             │              whole plan
       │                             ▼
       │                        [S] chat.open       the plan's facts, as data:
       │                             │              the outline, the tasks with
       │                             │              their status, the done
       │                             │              deliverables, the footprint
       │                             ▼
       │                        [O]⇄[M] chat.turn   the operator's message; the
       │                             │              role answers and may propose
       │                             │              a change; again, until the
       │                             │              operator ends the chat
       │                             ├── a change ──► [O] chat.read-back   the
       │                             │                proposed change in one
       │                             │                sentence beside the
       │                             │                operator's message: accept,
       │                             │                or reject ─► chat.turn
       │                             │                     │
       │                             │                     ▼ accept
       │                             │                [S] chat.apply   a revision
       │                             │                through the guards of a
       │                             │                first plan ─► chat.turn;
       │                             │                a guard that fails: the
       │                             │                finding is shown ─►
       │                             │                chat.turn
       │                             ▼ end
       │                        [S] chat.end        the transcript kept with
       │                                            the plan
       ├── settings ─────────► the plan's own values (UC-CTL-5)
       ├── pause ────────────► [O] plan.pause-when   when it holds:
       │                             │             • now: running tasks are
       │                             │               withdrawn, running jobs
       │                             │               stopped; both run again on
       │                             │               start
       │                             │             • after the current task ←:
       │                             │               what runs finishes, nothing
       │                             │               new starts
       │                             │             • after the current phase:
       │                             │               the phase runs to its end
       │                             ▼
       │                        [S] plan.pausing   runs until that point, then
       │                             │             holds
       │                             ▼
       │                        plan.paused
       ├── start ────────────► [S] plan.start      runs on from where it rests
       ├── cancel ───────────► [O] plan.confirm-end   what ends: the running
       │                             │                work, the open pull
       ├── abandon ──────────►       │                request (close it, or
       │                             │                leave it open), the reason
       │                             ▼ end it
       │                        [S] plan.end        its tasks withdrawn, its
       │                             │              workers and jobs ended, its
       │                             │              lesson claim released; then
       │                             │              archived as cancelled or
       │                             ▼              abandoned, with the reason
       │                        plan.archived
       ▼ every action, where an epic started the plan
  [S] plan.inform-epic         the act reaches the epic's inbox: paused,
                               started, cancelled, abandoned, revised in a
                               chat, settings changed, with the reason
----
+
Where the chat is called from another flow (a decision's answer, the sources of a start, ended work), its accepted proposal is not applied here but returned to the caller (`chat.carried`). The settings are <<UC-CTL-5>>, a decision is answered in link:03-plans.adoc#UC-PLN-2[UC-PLN-2], and a hold is resolved in <<UC-CTL-4>>; the chat is the sub-workflow of link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue.adoc#chat[State Catalogue, Chatting with the Planning Role: `chat`].
Variations::
* *An operator wait* of the plan (a decision) stays open while the plan is paused; answering it does not start the plan. A pause after the current task or phase holds at an operator wait, too, since nothing runs there.
* *The runtime stops or the machine restarts*: a paused plan stays paused, a pausing plan holds at its point once it runs again, and a running plan runs on from its last committed state; an operator wait stays open (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/runtime-lifecycle/02-plan-pause-and-stalled-plans.adoc#plan-pause[Runtime Lifecycle Specification, Pausing and Starting a Plan]).
* *A revision from a chat*: a chat proposes a revision of the plan once the plan has tasks, in Phase 5 or in finalize before the merge; earlier, while the plan is still being written, the chat answers but proposes no revision.
* *A plan always runs once it exists*: a plan the operator starts (link:05-starting-work.adoc#UC-STA-1[UC-STA-1]) and a plan an epic starts run at once; the only plan that exists and does not run is a paused one.
* *Cancel* and *abandon* are the same end, named by the state the plan was in: a running or pausing plan, and one waiting for the operator or held, is cancelled, a paused one abandoned. Only the cancel of a plan held by an integrity pause is that pause's resolution _abort_, and ends the plan with the outcome `aborted` (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/04-plan-finalize-terminal.adoc#plan-end[State Catalogue, Cancelling and Abandoning Archive]).
* *Its epic reacts* in its own workflow: it may stage the plan's row again, hold the rows that depend on it, or ask the operator (<<UC-CTL-2>>); a plan the epic started is never ended by the epic itself.
* *A plan that runs no longer* (it has ended) offers no action but its view and a chat about it: read-only, with the role `replan` over its archived record, whose one proposal may be a follow-up plan (link:../specification/runtime-model/01-processes-and-transport.adoc#ended-work[Runtime & Interaction Model Specification, Ended Work], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue.adoc#chat[State Catalogue, Chatting with the Planning Role: `chat`]).
* *A chat on a running plan*: a question never touches the plan; an accepted revision takes effect at the next task boundary: what runs finishes, the revision is applied, the plan runs on. The revision is the operator's own act and does not spend the plan's re-planning budget; the server never starts a chat.
* *Chat is offered disabled*, with its reason, while no configuration of the role `replan` qualifies.
* *The operator's messages* in a chat are not interpreted: the role answers them. Only a change the role proposes passes a read-back (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/06-envelopes-questions-deadlines.adoc#own-words[Model Work Specification, Answers in the Operator's Own Words]) before it applies; the role reads the plan as data, and nothing changes without _accept_.
* *A settings change* (<<UC-CTL-5>>) applies from where the plan next reads the value, and its epic is told (`settings changed`).
Outcome:: the plan is paused, running, revised, with its settings changed, or archived as the operator chose, and its epic knows.
Requirements:: link:../requirements/02-workflow.adoc#PM-WF-23[PM-WF-23] (pausing, starting, cancelling, and abandoning a plan), link:../requirements/02-workflow.adoc#PM-WF-24[PM-WF-24] (the chat with the planning role), link:../requirements/02-workflow.adoc#PM-WF-17[PM-WF-17] (a revision from a chat as the operator's own act), link:../requirements/02-workflow.adoc#PM-WF-1[PM-WF-1] (the outcomes `cancelled`, `abandoned`, `aborted`), link:../requirements/02-workflow.adoc#PM-WF-12[PM-WF-12] (the operator influences a running plan only by operator acts), link:../requirements/02-workflow.adoc#PM-WF-15[PM-WF-15] (the epic told of every act, its row following the plan), link:../requirements/08-security.adoc#PM-SEC-3[PM-SEC-3] (only through the operator's channel), link:../requirements/02-workflow.adoc#PM-WF-13[PM-WF-13] (an ended plan's archived records stay readable); pausing and starting are specified in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/runtime-lifecycle/02-plan-pause-and-stalled-plans.adoc#plan-pause[Pausing and Starting a Plan], ending in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/04-plan-finalize-terminal.adoc#plan-end[Cancelling and Abandoning Archive], the chat in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue.adoc#chat[Chatting with the Planning Role] and link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/phase-workflows/08-dynamic-re-planning.adoc#replan-chat[Revision from a Chat], the epic told in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/08-epic-coordination.adoc#epic-informed[The Epic Is Told].
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/work-actions.adoc#plan-actions[Actions on Plans and Epics, A Plan's Actions]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/19-actions.adoc#plan[Terminal Client, A Plan]; the web app: no design document yet; designed by its package link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/plans/web-actions.adoc[`web-actions`]

[#UC-CTL-2]
== UC-CTL-2: Control an Epic

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client.
Goal:: let an epic start its plans by itself or have it start its next plan now, end it, or archive it once it is through, review what it found and watches, and chat with its planning role about it.
Trigger:: the operator selects an epic in Running Work, or names it.
Flow::
+
[source,text]
----
  [S] epic.actions             the actions of the epic's state:
       │                       running: next plan, automatic on/off, common
       │                         files, decompose again, findings review,
       │                         watches review, archive, cancel, chat
       │                       waiting for the operator: those of running,
       │                         beside what it waits for (a decomposition,
       │                         a decision: UC-PLN-2)
       │                       held: those of running, and the acts of its
       │                         hold (UC-CTL-4), whose end is cancel
       │                       landing: those of running; archive offered
       │                         disabled until the ledger has landed
       │                       ended: its view and a read-only chat
       ├── chat ─────────────► ↳ chat (as in UC-CTL-1), with the epic's
       │                         planning role decompose, over the whole
       │                         epic; an accepted change staged through the
       │                         epic's checks (surfaces disjoint,
       │                         dependencies without a cycle)
       ├── automatic on/off ─► [S] epic.auto   the epic's mode switched,
       │                                       told in its events; on: it
       │                                       starts what is launchable
       │                                       now ─► epic.next-work
       ├── common files ─────► the most files a launchable plan may share with
       │                       a running one, changed like the mode; written
       │                       to the epic's header ─► epic.next-work
       ├── decompose again ──► ↳ decomposition (UC-STA-6), with the
       │                         operator's instruction
       ├── next plan ────────► [S] epic.next-work   the next launchable row in
       │                             │              the queue's order: the plan
       │                             │              started from its staged
       │                             │              section, implicitly created
       │                             ├── none launchable ──► why, per row (a
       │                             │                       dependency, a lock,
       │                             │                       the scope full, an
       │                             │                       overlap with a
       │                             │                       running plan, a
       │                             │                       stale row, a held
       │                             │                       item)
       │                             ├── scope full ──► [O] epic.raise-scope
       │                             │                  raise the scope by one
       │                             │                  ─► epic.next-work, or
       │                             │                  leave it
       │                             ▼
       │                        the plan runs (UC-CTL-1 controls it)
       ├── findings review ──► ↳ review (UC-CTL-3), the findings
       ├── watches review ───► ↳ review (UC-CTL-3), the watches
       ├── archive ──────────► [M] epic.review-completion   first, only
       │                             │                  when it has not run
       │                             │                  yet (automatic off)
       │                             ├── continue ──► the completion review
       │                             │                staged new rows: the
       │                             │                epic is not through, the
       │                             │                request is answered with
       │                             │                them ─► epic.active
       │                             ├── infeasible, lost ──► epic.active, the
       │                             │                completion review held
       │                             ▼ complete
       │                        [S] epic.archive-check   tests that it is
       │                             │                  through: no plan
       │                             │                  running or paused, every
       │                             │                  row shipped or ended, no
       │                             │                  open (undecided)
       │                             │                  finding, the ledger
       │                             │                  landed, the completion
       │                             │                  review done; lists the
       │                             │                  kept findings and the
       │                             │                  watches it carries
       │                             ├── not through ──► what is open, each
       │                             │                   leading to it
       │                             ▼ through
       │                        [S] epic.archive    the ledger, its kept
       │                             │              findings and watches with
       │                             │              it, moved to the archive
       │                             ▼              and landed
       │                        epic.archived       (completed)
       ├── cancel ───────────► [O] epic.confirm-cancel   its running and paused
       │                             │                   plans: cancel them too,
       │                             │                   or let them run on
       │                             │                   without the epic; the
       │                             │                   reason
       │                             ▼
       │                        [S] epic.cancel     its tasks withdrawn, its
       │                             │              plans as chosen, its ledger
       │                             │              archived as cancelled
       │                             ▼
       │                        epic.aborted        (cancelled)
       ▼ every other action
  epic.active                  the epic rests between its events
----
+
The chat is the one of <<UC-CTL-1>> (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue.adoc#chat[State Catalogue, Chatting with the Planning Role: `chat`]), the decomposition link:05-starting-work.adoc#UC-STA-6[UC-STA-6], the review <<UC-CTL-3>>, a hold <<UC-CTL-4>>.
Variations::
* *Automatic on* (the project's `epic.auto_start`, machine default on): the epic starts its plans itself, as many as its `parallelization_scope` admits (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/08-epic-coordination.adoc#server-started-plans[Server-Started Plans]), whenever a place frees or a row becomes launchable; _next plan_ is the operator starting the next one now. *Automatic off*: the epic starts nothing by itself; when a plan becomes launchable the operator gets a report of it, leading to the epic and its _next plan_ (link:03-plans.adoc#UC-PLN-6[UC-PLN-6]), and starts each plan with _next plan_; everything else the epic does still runs. The operator switches it at any time; the epic's events say so (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/08-epic-coordination.adoc#epic-auto[Model Work Specification, An Epic Runs by Itself]).
* *What a row waits for* is shown in the epic's view as well (link:03-plans.adoc#UC-PLN-5[UC-PLN-5]); _next plan_ names the reason per row from the same list.
* *No pause of the epic*: an epic is not paused as a whole; its plans are paused one by one (<<UC-CTL-1>>), and a pausing or paused plan keeps its place in the `parallelization_scope`, so the epic starts no plan in its stead; to stop new starts, the operator switches automatic off.
* *How many plans run at once*: the `parallelization_scope` is the upper limit of the epic's running plans. It is never asked at the start: it is the project's `epic.parallelization_scope`, whose machine default is 1. The operator raises it here, where _next plan_ with the scope full says so and offers to raise it by one, or in the project's settings.
* *Too many common changes*: a launchable plan starts beside the running ones only while its declared surface shares no more files than the epic allows (by default none; the project's setting, which the operator changes on the epic like the automatic mode) with what each running plan declared and has changed. Over that, it waits (_waits: overlap with_ the plan) until that plan has ended; it is never started beside it, by the epic or by _next plan_. Two running plans whose changes come to overlap beyond it are reported and the epic is told; neither is stopped, and the one that lands second is re-planned or rebased onto the first.
* *When a plan of the epic ends*, the epic reacts by itself, in both modes: a landed plan is recorded and analysed, and the staged plans it affects are re-ordered or re-cut; a change that only re-orders them or amends a staged plan's surface or prerequisites is applied once the server's checks pass, one that adds, drops, or re-scopes a plan waits for the operator in the decomposition's review (link:05-starting-work.adoc#UC-STA-6[UC-STA-6]). A plan that ended without landing holds the plans that depend on it, and the operator is asked (<<UC-CTL-1>>). Then, with automatic on, the next launchable plans start; with it off, the epic shows what is launchable now.
* *Through*: when every plan is shipped or ended, an epic with automatic on runs its completion review and reports it; one with automatic off reports that it is through, and the operator's _archive_ runs the completion review first, then the archive check. Archiving stays the operator's act in both modes. Every start, wait, overlap, re-cut, and end is also a report to the operator (link:03-plans.adoc#UC-PLN-6[UC-PLN-6]).
* *Kept findings and watches* when the epic is through are listed by the archive check as carried; they do not hold the archive, and archiving keeps them in the archived ledger, so nothing the epic found or watched is lost. Only an open finding, one not decided yet, holds it.
* *An epic task waiting for the operator* (a held item, a decision) is shown with the actions and reached from them (link:03-plans.adoc#UC-PLN-2[UC-PLN-2]).
* *Chat is offered disabled*, with its reason, while no configuration of the role `decompose` qualifies; a chat changes only staged rows, never a plan that runs. An ended epic offers its view and a read-only chat with `decompose` over its archive, as an ended plan does (<<UC-CTL-1>>).
Outcome:: the epic runs by itself or waits for the operator's _next plan_, as the operator chose; it has started its next plan, has its staged rows changed in a chat, is archived because it is through, or is cancelled with its plans as the operator chose.
Requirements:: link:../requirements/02-workflow.adoc#PM-WF-23[PM-WF-23] (the acts on an epic: next plan, decompose again, automatic mode, archive, cancel), link:../requirements/02-workflow.adoc#PM-WF-15[PM-WF-15] (automatic mode, overlap admission, the reaction to an ended plan, through), link:../requirements/02-workflow.adoc#PM-WF-21[PM-WF-21] (launchable, overlap, re-cut, and through reported), link:../requirements/02-workflow.adoc#PM-WF-24[PM-WF-24] (the chat with `decompose`), link:../requirements/02-workflow.adoc#PM-WF-13[PM-WF-13] (an archived epic's records stay readable), link:../requirements/01-architecture.adoc#PM-ARCH-5[PM-ARCH-5] (the ledger changed in the shared epic worktree, landed by the epic's landing); the acts are specified in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/08-epic-coordination.adoc#epic-actions[An Epic's Actions], the automatic mode and the overlap in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/08-epic-coordination.adoc#epic-auto[An Epic Runs by Itself] and link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/08-epic-coordination.adoc#server-started-plans[Server-Started Plans], the epic workflow in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/08-epic-coordination.adoc#epic-workflow[Epic Workflow], its states in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/06-setup-epic-other.adoc#state-catalogue-epic[Epic States], the endpoints in link:../specification/runtime-model/01-processes-and-transport.adoc#epic-resource[The Epic as a Resource].
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/work-actions.adoc#epic-actions[Actions on Plans and Epics, An Epic's Actions], link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/epic-view.adoc[Epic View]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/19-actions.adoc#epic[Terminal Client, An Epic]; the web app: no design document yet; designed by its package link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/plans/web-actions.adoc[`web-actions`]

[#UC-CTL-3]
== UC-CTL-3: Review an Epic's Findings or Watches

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client, with the epic's planning role.
Goal:: go through what the epic found (findings: what its landings and plans surfaced that no plan owns yet) or keeps under watch, and decide each item: keep it, drop it, make a plan of it, or reshape it with a model's help.
Trigger:: the operator chooses _findings review_ or _watches review_ on an epic (<<UC-CTL-2>>), or follows the note that new findings wait.
Flow::
+
[source,text]
----
  [S] review.open              the items of the kind, open ones first: each
       │                       with its statement, its rules (what makes a
       │                       watch fire, what a finding requires), its
       │                       origin (a landing, a plan's message, an
       │                       observation), since when, and the planning
       │                       role's proposal for it
       ▼
  [O] review.item              per item: keep, drop, promote, edit, chat; or
       │                       accept the remaining proposals, or finish
       ├── keep ─────────────► [S] review.keep   kept as a finding (to be
       │                            fixed) or as a watch, moved to the
       │                            other register where the kind changes
       ├── drop ─────────────► [S] review.drop   dropped, with the operator's
       │                            reason
       ├── promote ──────────► [M] review.draft-plan   the planning role
       │                             │                 drafts a staged plan
       │                             │                 from the item: objective,
       │                             │                 deliverables, surface,
       │                             │                 dependencies
       │                             ▼
       │                        [O] review.confirm-plan   stage it, edit it,
       │                             │                    or back
       │                             ├── back ──► review.item
       │                             ├── edit ──► [O] review.instruct-plan
       │                             │            what to change in the
       │                             │            drafted plan
       │                             │                 │
       │                             │                 ▼
       │                             │            [M] review.redraft-plan
       │                             │            the planning role drafts
       │                             │            the plan again
       │                             │                 │
       │                             │                 ▼
       │                             │            [O] review.read-back-plan
       │                             │            the plan, old against new:
       │                             │            accept ─► review.confirm-plan
       │                             │            with the new draft; instruct
       │                             │            again ─► review.instruct-plan;
       │                             │            discard ─► review.confirm-plan
       │                             │            with the draft before
       │                             ├── stage, a check fails ──►
       │                             │            review.confirm-plan, the
       │                             │            finding with its plan
       │                             ▼ stage
       │                        review.item, the item promoted
       ├── edit ─────────────► [O] review.instruct   what to adapt or add to
       │                             │               the item's statement and
       │                             │               rules
       │                             ▼
       │                        [M] review.rewrite   the planning role
       │                             │               rewrites them
       │                             ▼
       │                        [O] review.read-back   the change, old against
       │                                               new: accept ─►
       │                                               review.item, the change
       │                                               applied; instruct again
       │                                               ─► review.instruct;
       │                                               discard ─► review.item,
       │                                               the item unchanged
       ├── chat ─────────────► ↳ chat (as in UC-CTL-1), with the planning
       │                         role decompose, over the item or the whole
       │                         register; an accepted change applied as the
       │                         item's disposition or rewrite ─► review.item
       ▼ finish
  [S] review.commit            the dispositions written to the epic's ledger
                               and committed in the epic's worktree, not
                               pushed (the epic's landing lands them); a
                               promoted item is a staged row
----
+
The chat is the one of <<UC-CTL-1>> (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue.adoc#chat[State Catalogue, Chatting with the Planning Role: `chat`]).
Variations::
* *Usually interactive*: the operator decides item by item; _accept the remaining proposals_ takes the planning role's proposal for every item not decided yet, after one confirmation that lists them.
* *Leaving* keeps the decisions made so far; the review continues where it stopped, in either client.
* *The operator's words* in _edit_ and _chat_ are not interpreted: the planning role works from them, and what it proposes (a rewrite, a redrafted plan, a change in the chat) passes a read-back (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/06-envelopes-questions-deadlines.adoc#own-words[Model Work Specification, Answers in the Operator's Own Words]) before it applies; the planning role reads the items as data, and a finding that came from outside the machine stays marked untrusted.
Outcome:: every reviewed item is kept as a finding, moved to the watches, dropped, or staged as a plan, its statement and rules as the operator shaped them, recorded in the epic's ledger.
Requirements:: link:../requirements/02-workflow.adoc#PM-WF-15[PM-WF-15] (the findings and watches registers, decided by the operator in a review with read-back), link:../requirements/02-workflow.adoc#PM-WF-24[PM-WF-24] (the chat over an item or the register), link:../requirements/01-architecture.adoc#PM-ARCH-5[PM-ARCH-5] (the dispositions committed in the shared epic worktree), link:../requirements/08-security.adoc#PM-SEC-1[PM-SEC-1] (a finding from outside the machine stays untrusted); the registers are specified in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/08-epic-coordination.adoc#findings-watches[An Epic's Findings and Watches] and link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/04-epic-and-change-ledger.adoc#epic-registers[Findings and Watches Registers], the review in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/08-epic-coordination.adoc#epic-review[The Review] and link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/17-epic-decomposition-and-review.adoc#state-catalogue-review[Review], new findings in link:../specification/runtime-model/01-processes-and-transport.adoc#needs-operator[What Needs the Operator].

[#UC-CTL-4]
== UC-CTL-4: Resolve What Holds a Plan

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client.
Goal:: see why a plan, an epic, or a project's landing does not go on, when no decision is asked, and resolve it.
Trigger:: Running Work marks a hold (link:../specification/runtime-model/01-processes-and-transport.adoc#needs-operator[Runtime & Interaction Model Specification, What Needs the Operator, at a Glance]), one of the kinds `stalled` (a plan stalled), `condition` (a condition that needs an operator act), `integrity_pause`, `held` (an item of an epic held), and `landing_failed` (a failed landing of an epic, of a moved source, or of a placed workflow unit).
Flow::
+
[source,text]
----
  [S] hold.show                what holds, from a closed list, with its
       │                       cause, since when, what was tried, and the
       │                       acts that resolve it:
       │                       • stalled: retry now, recycle the worker
       │                       • condition: the act it names (grant access,
       │                         add a credential, raise a budget, commit or
       │                         restore a configuration file), each as a
       │                         dialogue of the clients
       │                       • integrity_pause: the tampered file with
       │                         its recorded and current size and digest;
       │                         accept it
       │                       • held, landing_failed: retry, or the
       │                         item's own acts; for the removal of moved
       │                         documents from git also give it up (the
       │                         files stay tracked; the source keeps its copy)
       │                       • and always, for a plan or an epic: cancel
       │                         (UC-CTL-1, UC-CTL-2); for an integrity
       │                         pause the cancel is its abort: a plan
       │                         ended as aborted, an epic as cancelled
       ▼
  [O] hold.resolve             the operator's act, confirmed where it cannot
       │                       be undone
       ▼
  [S] hold.apply               the act applied
       ├── still held ───────► hold.show   what still holds, with its cause
       ▼ released
  hold.released                the plan, the epic, or the landing goes on
----
Variations:: an act that today needs the operator's terminal (granting access, accepting an edit) is offered in both clients; an integrity pause shows no diff and offers no restore, since the prior content is not kept: the operator accepts the file as it is, or cancels; a hold that clears by itself (a provider back) disappears without an act.
Outcome:: what held is resolved, or the plan or the epic is ended; nothing waits without the operator knowing why.
Requirements:: link:../requirements/02-workflow.adoc#PM-WF-23[PM-WF-23] (holds of a closed list with their acts, cancel beside them), link:../requirements/02-workflow.adoc#PM-WF-3[PM-WF-3] (the conditions that need the operator and the integrity pause), link:../requirements/01-architecture.adoc#PM-ARCH-7[PM-ARCH-7] (a stalled plan or epic reported to the operator), link:../requirements/08-security.adoc#PM-SEC-3[PM-SEC-3] (every act in both clients), link:../requirements/14-implementation.adoc#PM-IMPL-7[PM-IMPL-7] (the integrity pause: the tampered file with its digests, accept or abort), link:../requirements/08-security.adoc#PM-SEC-2[PM-SEC-2] (access granted as the act of a hold), link:../requirements/07-credentials.adoc#PM-CRED-4[PM-CRED-4] (a credential added by the operator in a client); holds are specified in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/01-conventions-generic-conditions.adoc#holds[Holds and Their Acts], the conditions in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/01-conventions-generic-conditions.adoc[Generic Conditions], stalled plans in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/runtime-lifecycle/02-plan-pause-and-stalled-plans.adoc#stalled-plans[Stalled Plans], the kinds in link:../specification/runtime-model/01-processes-and-transport.adoc#needs-operator[What Needs the Operator].
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/work-actions.adoc#holds[Actions on Plans and Epics, Holds]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/19-actions.adoc#holds[Terminal Client, What Holds a Plan]; the web app: no design document yet; designed by its package link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/plans/web-actions.adoc[`web-actions`]

[#UC-CTL-5]
== UC-CTL-5: Change a Plan's Settings

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client.
Goal:: give one plan its own value of an aspect (how it lands, works, and asks; a role's harness, model, or effort; an integration's variant or an optional provider) without changing the project's or the machine's, and know from where it applies.
Trigger:: the operator chooses _settings_ on a plan (<<UC-CTL-1>>), in any state until the plan has ended.
Preconditions:: the plan has not ended.
Flow::
+
[source,text]
----
  [S] plan-settings.open       the plan's values per aspect, each with where
       │                       it comes from (the plan, the project, the
       │                       machine): the plan defaults (landing, method,
       │                       asking), the roles, the providers
       ▼
  [O] plan-settings.aspect     the aspect to change, or close
       │
       ▼
  [O] plan-settings.value      the plan's own value, the current one
       │                       preselected ←; or remove the plan's value, so
       │                       that the project's or the machine's applies
       ▼
  [S] plan-settings.validate   the validation of the machine values: an
       │                       enrolled harness, an allowed model, an
       │                       available provider, a landing variant that
       │                       fits the project and the plan
       ├── refused ──► the reason ─► plan-settings.value
       ▼ valid
  [S] plan-settings.apply      the value written to the plan's overrides
       │                       and audited; a new instance version
       │                       composed, under the position rule, from
       │                       which the plan reads the value where it next
       │                       needs it
       ├── too late ──► the reason: the version would not contain the
       │                plan's position ─► plan-settings.aspect
       ├── changed meanwhile ──► conflict: the current value
       │                          ─► plan-settings.value
       ▼
  [S] plan.inform-epic         where an epic started the plan, its inbox
                               is told: settings changed, with the aspect
----
Variations::
* *Set where first needed*: a value the plan asks where it first needs it (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/09-bootstrap-and-lessons.adoc#options-when-needed[State Catalogue, Asked When Needed]) is the same plan value; this use case changes it later, or sets it before it is asked, so that it is not asked.
* *A running plan* goes on while its settings change; what runs keeps the value it started with, and the new value applies from where the plan next reads it (a task started after it, the call site of an axis not yet reached).
* *Too late*: a change whose new version would not contain the plan's current state and its call stack (the landing variant while the plan lands, for example) is refused with the reason; what has already run is not run again.
* *Changed in two clients at once* is refused against an older value with `conflict`, the current value shown, as in link:01-onboarding.adoc#UC-ONB-10[UC-ONB-10] (link:../specification/cli-and-security/01-cli-and-installer.adoc#concurrent-changes[CLI, Coordination & Security Specification, Concurrent Changes of a Setting]).
* *Refused values*: a landing variant that cannot run for the project (`landing.pull-request` without a provider, `landing.main` on a protected base branch) or for the plan (`landing.files` for a plan from local changes, link:05-starting-work.adoc#UC-STA-9[UC-STA-9]) is refused with the reason; so is a harness, model, or provider the machine does not allow.
Outcome:: the plan has its own value of the aspect, a new instance version shows it, the change is audited, and its epic knows.
Requirements:: link:../requirements/02-workflow.adoc#PM-WF-25[PM-WF-25] (a plan's own values, validated, audited, a new instance version), link:../requirements/14-implementation.adoc#PM-IMPL-5[PM-IMPL-5] (the plan instance, composed again for a change), link:../requirements/02-workflow.adoc#PM-WF-14[PM-WF-14] (a worker's harness, model, and effort from its role, the plan's override included), link:../requirements/02-workflow.adoc#PM-WF-15[PM-WF-15] (the epic told `settings_changed`), link:../requirements/15-extensions-and-recipes.adoc#PM-EXT-6[PM-EXT-6] (each value with its level, a change against an older revision refused with `conflict`); a plan's own values are specified in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/workflow-dsl/09-plan-instance.adoc#plan-overrides[Plan Overrides] and link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/14-plan-instance-waivers-questions.adoc#plan-overrides-store[Plan Overrides (`overrides.json`)], the plan instance in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/workflow-dsl/09-plan-instance.adoc#plan-instance[Plan Instance], the harness of a role in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/04-worker-launch.adoc#harness-selection[Harness Selection].
