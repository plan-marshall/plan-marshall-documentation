= Use Cases: System (UC-SYS)
:toc: left
:toclevels: 2
:nofooter:

link:../UseCases.adoc[Use Cases] » System

The operator looks after the runtime itself: stops it, starts it, restarts it, and upgrades it to a newer version, sees what it is doing: its version, how long it runs, what it uses of the machine, the work it carries, and the tokens the models use, and cleans up the work history the machine keeps. The operator does this in the web app or in the terminal client; how each client offers it is its design (link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/README.adoc[`pm-mcp-clients`, Design]).

[#principles]
== Principles

[#nothing-lost]
Nothing is lost by stopping:: Whatever stops the runtime, and however fast, the work resumes from its last committed state on the next start, by the recovery the specification defines (link:../specification/runtime-model/02-startup-recovery-drain.adoc#per-project-recovery[Per-Project Recovery]); stopping only decides how much of what runs is finished first.
[#measured-where-it-happens]
Figures are kept, not searched:: The runtime counts its figures where things happen, as metrics, and a client reads them; no figure is computed by reading the stores on each request. A figure the runtime cannot measure here is shown as unavailable, never as `0`.
[#one-cleanup]
Work history goes only when the operator says so:: There is one cleanup of the machine, and it is the only place where work history is deleted: archived plans and epics, the logs of ended work, read reports, and the stores of unenrolled projects go only after the operator confirms it (<<UC-SYS-3>>). What the runtime leaves behind as technical residue it removes by itself, and only counts.

[#UC-SYS-1]
== UC-SYS-1: Manage the Runtime

Status:: `DRAFT`
Actor:: the operator, in the web app or in the terminal client; stopping, restarting, and upgrading are privileged acts of the operator's channels: the terminal client's verbs, or a paired device (link:../specification/cli-and-security/03-web-server.adoc#web-operator-channel[Every Paired Device Is an Operator Channel]).
Goal:: stop the runtime, start it, restart it, or upgrade it to a newer version, knowing what that does to the work that runs.
Trigger:: the operator chooses one of these in a client's system view (<<UC-SYS-2>>), the clients show that a newer version is available, or the relay or a client reports a version mismatch after an installation by hand.
Preconditions:: the runtime is installed (link:../specification/cli-and-security/01-cli-and-installer.adoc#installation-layout[Installation Layout]); for an upgrade, the installation is one the runtime installed and switches (versioned directories, the two `PATH` links).
Flow::
+
[source,text]
----
  [S] runtime.actions          the runtime's state, its version, and the
       │                       acts it offers:
       │                       running: stop, restart, check for a newer
       │                         version, upgrade (when one is known)
       │                       draining: stop now, withdraw (a stop the
       │                         operator asked; never one of a signal)
       │                       upgrading: its step; stop now
       │                       not running: start, from the terminal
       │                         client only; the web app says how
       ├── stop ─────────────► [O] runtime.confirm-stop   what runs (plans,
       │                             │                epics, tasks, jobs,
       ├── restart ──────────►       │                workers), and when:
       │                             │                • drain ←: nothing new
       │                             │                  starts, what runs
       │                             │                  finishes its task or
       │                             │                  job, up to the drain
       │                             │                  timeout
       │                             │                • now: tasks withdrawn,
       │                             │                  jobs stopped; all of
       │                             │                  it resumes on the next
       │                             │                  start
       │                             ▼
       │                        [S] runtime.draining   every client told;
       │                             │                what still runs, live
       │                             ├── stop now ──► runtime.draining, what
       │                             │                still runs stopped
       │                             ├── withdraw ──► runtime.actions,
       │                             │                running again
       │                             ▼ drained
       │                        [S] runtime.stopped    the runtime exits;
       │                             │                the web app cannot
       │                             │                reach it
       │                             ▼ restart
       │                        [S] runtime.start      the successor starts,
       │                             │                recovers, and every
       │                             │                plan resumes; the web
       │                             │                app reconnects
       │                             ▼
       │                        done
       ├── start ────────────► [S] runtime.start (as above)
       ├── check ────────────► [O] runtime.update-consent   check_updates:
       │                             │               ask the organisation's
       │                             │               registry for a newer
       │                             │               version; yes, yes and
       │                             │               don't ask again, no
       │                             ▼
       │                        [S] runtime.check-update   the installed
       │                                                   version against
       │                                                   the newest, with
       │                                                   its release notes
       │                                                   ─► runtime.actions
       ├── upgrade ──────────► [O] runtime.confirm-upgrade   the version, its
       │                             │                notes, what runs, and
       │                             │                when: drain ←, or now
       │                             ▼
       │                        [S] runtime.fetch      the release fetched
       │                             │                and its digest verified
       │                             ├── failed ──► the reason; nothing
       │                             │              changed ─► runtime.actions
       │                             ▼
       │                        [S] runtime.install    unpacked into a new
       │                             │                versioned directory,
       │                             │                the PATH links switched
       │                             ▼
       │                        runtime.draining ─► runtime.stopped
       │                             │
       │                             ▼
       │                        [S] runtime.start      on the new version
       │                             ├── fails ──► [S] runtime.rollback   the
       │                             │             links switched back, the
       │                             │             previous version started,
       │                             │             the reason told
       │                             ▼
       │                        done
       ▼
  runtime.running              the runtime runs, on the version shown
----
+
What runs while it drains and the figures of the runtime are the system view of <<UC-SYS-2>>; the stop and the upgrade are <<change-runtime-lifecycle>>.
Variations::
* *Drain or now*: a drain lets every running task and job finish, bounded by the drain timeout (link:../specification/timeouts/02-runtime-leases-operator-web.adoc#drain-timeout[Drain Timeout]); at the timeout the runtime stops what still runs, as specified. _Stop now_ is the drain without the wait: the tasks are withdrawn, the jobs stopped, and both run again after the next start, as after a crash. Neither ends a plan: a running plan runs on, a paused one stays paused (link:06-controlling-work.adoc#UC-CTL-1[UC-CTL-1]).
* *It does not stop in time*: while it drains, the clients show what still runs and offer _stop now_; a client's own wait ends at the bound defined with the drain timeout and says that the runtime is still draining, with _stop now_.
* *Withdrawn*: a drain the operator asked in a client can be withdrawn while it runs; the runtime runs on and starts new work again. A drain started by a signal (the shell's `pm-operator drain`, the service manager, the OS shutting down) cannot.
* *Several devices*: every client and every paired device sees the runtime draining, stopping, and upgrading, as it happens; an act from one is seen by all.
* *Start*: the terminal client starts a stopped runtime, as every command that needs it does (link:../specification/runtime-model/01-processes-and-transport.adoc#_start_modes[Start Modes]). The web app is served by the runtime: a stopped runtime cannot be reached from a browser, and the open web app says so and how to start it.
* *Restart*: the stop, then a start of the same version; under the service manager the restart goes through it. The web app shows that the runtime restarts and reconnects by itself.
* *The service manager*: where the runtime runs under the per-user service (link:../specification/runtime-model/01-processes-and-transport.adoc#_start_modes[Start Modes], Service-managed), a stop leaves the service installed, and an upgrade rewrites its unit to name the new version.
* *A newer version*: the check needs the operator's consent (`check_updates`, link:01-onboarding.adoc#consents[Consents]), since it asks the organisation's registry over the network; once remembered, the clients show a newer version when they open. With _no_, nothing is asked, and the upgrade is offered only for a version the operator installs by hand.
* *What runs during an upgrade* is treated like a restart: it finishes (drain) or is stopped (now), and resumes on the new version. No store is migrated; a store whose format the new version does not read is refused by name where it is read (link:../requirements/01-architecture.adoc#PM-ARCH-6[PM-ARCH-6]).
* *A failed upgrade*: a failure before the links are switched (no network, a digest that does not match, no space) leaves everything as it was. A new version that does not start within the start timeout is undone: the links are switched back and the previous version starts again, and the reason is told. The previous installation stays as the way back until the next upgrade.
* *Stop while an upgrade runs*: before the links are switched, a stop withdraws the upgrade, and the runtime stops on its version; after it, _stop now_ shortens the drain, and the runtime starts on the new version.
* *An installation the runtime cannot upgrade* (installed by hand elsewhere, or `PM_MCP_HOME` set): the clients show the newer version and the steps by hand of the specification (link:../specification/cli-and-security/01-cli-and-installer.adoc#installation-layout[Installation Layout], Upgrade); the upgrade is offered disabled with its reason.
* *Versions apart*: after an upgrade, the relays of open host sessions are still the old binaries and forward normally; the mismatch is told to the operator only (link:../specification/runtime-model/02-startup-recovery-drain.adoc#_drain_stop_upgrade[Drain, Stop & Upgrade]). An open terminal client of the old version says that it is older than the runtime and asks to be restarted; the web app loads the new version when it reconnects.
Outcome:: the runtime is stopped, runs again, or runs on the new version, as the operator chose; the work that ran resumes, nothing is lost, and every client knows.
Changes::
* *The runtime's lifecycle* (<<change-runtime-lifecycle>>).
Requirements:: the lifecycle is required by link:../requirements/01-architecture.adoc#PM-ARCH-7[PM-ARCH-7] and the upgrade by link:../requirements/10-distribution.adoc#PM-DIST-1[PM-DIST-1] and link:../requirements/10-distribution.adoc#PM-DIST-4[PM-DIST-4]; the drain is specified in link:../specification/runtime-model/02-startup-recovery-drain.adoc#_drain_stop_upgrade[Drain, Stop & Upgrade], the start in link:../specification/runtime-model/01-processes-and-transport.adoc#_start_modes[Start Modes].
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/system.adoc[System]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/25-system.adoc[Terminal Client, System]; the web app: no design document yet; designed by its package link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/plans/web-system.adoc[`web-system`]

[#UC-SYS-2]
== UC-SYS-2: See What the Runtime Is Doing

Status:: `DRAFT`
Actor:: the operator, in the web app or in the terminal client.
Goal:: see at a glance how the runtime is, what work it carries, and the tokens the models use, and get from a figure to what it counts.
Trigger:: the operator opens the system view of a client, or comes to it from managing the runtime (<<UC-SYS-1>>).
Preconditions:: the runtime runs.
Flow::
+
[source,text]
----
  [S] system.open              a snapshot of the runtime's metrics:
       │                       • the runtime: version and build, started
       │                         at, uptime, memory (heap, resident), CPU
       │                         where available, disk use of the machine
       │                         store, the listeners (socket, web on
       │                         loopback or LAN)
       │                       • the work, across projects or per project:
       │                         plans and epics running, waiting, held,
       │                         paused; tasks queued and running; workers
       │                         by role, harness, and model, busy or idle;
       │                         jobs (builds, tests) running and queued,
       │                         with their slots; locks held
       │                       • the models, per model and per role: calls,
       │                         tokens in and out and their total, errors
       │                         and retries, over the
       │                         last hour ←, today, or the last 7 days
       ▼
  [O] system.view              read; choose the window or the project, or
       │                       follow a figure
       ├── window, project ──► system.open with it
       ├── a figure ─────────► what it counts: the running plans in
       │                       Running Work (UC-PLN-4), a plan, an epic,
       │                       the workers, the jobs
       ▼ live
  [S] system.update            the figures that changed, from the
                               runtime's stream ─► system.view
----
+
A figure leads to what it counts, the running plans to Running Work (link:03-plans.adoc#UC-PLN-4[UC-PLN-4]); the acts on the runtime are <<UC-SYS-1>>.
Variations::
* *Live*: the view follows the runtime's stream and shows each figure as it changes; a client that loses the stream says so and reads the snapshot again when it is back.
* *Under load*: the view is a read of kept figures and costs the runtime nothing that grows with the work; it never waits for a project's recovery, and a project still recovering is shown as such.
* *A figure unavailable* on this machine (CPU on a platform that does not report it, a token figure its harness does not report) is shown as unavailable, never as `0`; the tokens count only what was measured, say how many calls were not, and a total over them is shown as at least its value. No figure is money, and none is a limit (link:03-plans.adoc#change-token-usage[Tokens, Not Money]; link:../specification/store-schemas/05-metrics-and-quality-report.adoc#metrics-store[Metrics Store], "unmeasured is never `0`").
* *Over a restart*: uptime starts again; the work and the models over a window do not, since they are taken from the stores at the start.
* *A paired device* sees the same view as the terminal client.
* *The runtime is stopped*: the terminal client shows that it is not running and offers to start it (<<UC-SYS-1>>); the web app cannot reach it and says so.
* *The draining runtime* shows its state, and what still runs counts down.
Outcome:: the operator knows how the runtime is, what it does, and the tokens the models use, and has reached what a figure counts.
Changes::
* *The runtime's metrics* (<<change-runtime-metrics>>).
* *Tokens, not money* (link:03-plans.adoc#change-token-usage[Tokens, Not Money]): the one token figure with its split, and no cost.
Requirements:: link:../requirements/02-workflow.adoc#PM-WF-14[PM-WF-14] (the usage of every task, from the harness's own output), link:../requirements/08-security.adoc#PM-SEC-7[PM-SEC-7] (the dependable view of every plan, epic, worker, and task); the requirement of the metrics is drafted in <<change-runtime-metrics>>; the usage of a task is specified in link:../specification/model-work/09-completion-usage-and-spend.adoc#job-result-schema[Worker Result & Usage Parsing], the runtime status in link:../specification/runtime-model/01-processes-and-transport.adoc#local-api[Local API].
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/system.adoc[System]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/25-system.adoc[Terminal Client, System]; the web app: no design document yet; designed by its package link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/plans/web-system.adoc[`web-system`]

[#UC-SYS-3]
== UC-SYS-3: Clean Up

Status:: `DRAFT`
Actor:: the operator, in the web app or in the terminal client; deleting is a privileged act of the operator's channels, like the acts of <<UC-SYS-1>>.
Goal:: get rid of the work history the operator no longer needs, all of it in one place, seeing what goes before it goes, and nothing deleted without the operator's word.
Trigger:: the report that work history can be deleted (link:03-plans.adoc#UC-PLN-6[UC-PLN-6]), whose detail is the cleanup job; or the operator opens the cleanup from the system view (<<UC-SYS-2>>) or by its own command.
Preconditions:: the runtime runs.
Flow::
+
[source,text]
----
  [S] cleanup.check            once a day and at the start: the work
       │                       history whose end (archived, read,
       │                       unenrolled) is older than its duration,
       │                       without the kept items and the items of an
       │                       open or postponed job
       ├── nothing new due ──► done
       ▼ due since the last job
  [S] cleanup.report           one cleanup job, its items fixed; one
       │                       report system.cleanup_due ("12 plans,
       │                       2 epics and 40 logs can be deleted"), its
       │                       detail the job
       ▼ the job opened (its report, the system view, its command)
  [O] cleanup.job              summary: plans, epics, logs, reports,
       │                       unenrolled projects, and the space it frees
       │                       details, by project: each plan or epic with
       │                       its title, outcome, when it ended, and its
       │                       size, its logs counted; each read-only to
       │                       open; each checked ←
       │                       delete, ask me again in 3 days, ignore,
       │                       or leave
       ├── delete ───────────► [O] cleanup.confirm   the counts of what is
       │                             │               checked; it cannot be
       │                             │               undone
       │                             ├── back ──► cleanup.job
       │                             ▼ delete
       │                        [S] cleanup.delete   every checked item
       │                                             deleted, each audited;
       │                                             an unchecked one kept
       │                                             for good ─► done
       ├── ask me again ─────► [S] cleanup.remind    nothing deleted; the
       │                                             same items come back
       │                                             as a new job in 3 days
       │                                             ─► done
       ├── ignore ───────────► [S] cleanup.keep      nothing deleted; the
       │                                             items kept for good,
       │                                             never offered again
       │                                             ─► done
       ▼ leave
  done                         the job stays open, in the system view
----
+
The report is the one of link:03-plans.adoc#UC-PLN-6[UC-PLN-6]: it is read when the job is opened, like every report's detail, and deciding the job closes it. The settings are <<change-cleanup>>.
Variations::
* *What is work history*: the archived plans, each with everything its archive holds (its records, history, decisions, transcripts, and metrics rows); the archived epics, each with its store on the machine; the logs of ended work (the logs of ended jobs, and the worker and session logs of archived plans), counted per plan; the reports the operator has read; and the machine stores of unenrolled projects, each with its archive. Only these are offered, and only through the job.
* *Technical residue* (temporary files, caches, the directories of ended jobs' workers, stale locks and leases, fenced generations, the workspace's technical rows, retired lesson bodies, rotated audit files) is removed by the runtime by itself, each removal audited; the cleanup view shows what it removed and when, as figures, and never asks.
* *The durations*: one per kind, 30 days each by default, at least 7, or _never_; changed in the cleanup view and among the machine's settings (link:01-onboarding.adoc#UC-ONB-10[UC-ONB-10]); a project may have its own for its plans, epics, and logs, set in its settings. A shorter duration makes more due at the next check, never at once.
* *Never offered*: what still runs (a live plan or epic, a pending entry), an unread report, and an archived plan that still owes the operator something (a retained capture ref not dropped); such an item becomes due when that ends.
* *One job at a time*: what becomes due while a job is open or postponed waits for the next job; the job never grows while the operator looks at it.
* *Ask me again*: the same items, and only those, come back as a new job and a new report after the reminder's days (3 by default, a setting).
* *Ignore and unchecked items*: the items are kept for good and listed as _kept_ in the cleanup view, where the operator releases any of them back to the cleanup; a released item is offered again in the next job.
* *What is never touched*: a plan's branch, its pull request, and the remote; an epic's archived ledger in the repository, which is the team's record (removing it is a change of the repository, not the cleanup); the audit log.
* *After the delete*: a deleted plan or epic leaves ended work, and its reports' detail says "deleted" with the date; its id is never given again. The token figures of the system view (<<UC-SYS-2>>) stay as they were: what a deleted plan used is kept as an aggregate, so no figure goes down.
* *An item no longer due* when the delete runs (a project enrolled again, a kept item) is left out and named; an item that cannot be deleted stays, with its reason, and comes back in the next job; the rest is deleted.
* *Several devices*: the job is decided once for the machine; a decision from another device on a decided job is answered with the decision taken.
* *A stop during the delete*: the delete goes on after the next start; what was deleted stays deleted.
Outcome:: what the operator chose is deleted, postponed, or kept, the deletion audited; nothing of work history went without the operator's word.
Changes::
* *One cleanup* (<<change-cleanup>>).
* *Reports to the operator* (link:03-plans.adoc#change-reports[Reports to the Operator]): the kind `system.cleanup_due`.
Requirements:: link:../requirements/06-execution.adoc#PM-EXEC-2[PM-EXEC-2] (today's retention purge, `sweep`), link:../requirements/02-workflow.adoc#PM-WF-13[PM-WF-13] (archived records readable as long as they are kept); the requirement of the one cleanup is drafted in <<change-cleanup>>; today's retention is specified in link:../specification/timeouts/03-retention-host-config.adoc#retention-days[Retention & Rotation] and link:../specification/store-schemas/13-leases-integrity-testing.adoc#evidence-based-removal-sweeps[Evidence-Based Removal Sweeps].
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/system.adoc[System]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/25-system.adoc[Terminal Client, System]; the web app: no design document yet; designed by its package link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/plans/web-system.adoc[`web-system`]

[#changes]
== Changes to the Specification

The changes these use cases need, each modelled as the fix of a gap; written into the requirements and specifications once the use case is `AGREED`.

[#change-runtime-lifecycle]
=== The Runtime's Lifecycle

Gap:: the runtime stops only on a signal (`pm-operator drain`, the service manager, the OS) and always by its drain: there is no stop without the wait, a drain cannot be withdrawn, and drain is no resource of the Local API, so the web app can neither stop nor restart the runtime (link:../specification/runtime-model/01-processes-and-transport.adoc#local-api[Local API], "Drain is no resource"). There is no restart: after a drain, the next command that needs the runtime starts it. An upgrade is done by hand: a new release unpacked beside the current one, the `PATH` links switched, then `pm-operator drain` (link:../specification/cli-and-security/01-cli-and-installer.adoc#installation-layout[Installation Layout], Upgrade); nothing says where a release comes from, nothing checks for a newer one, and nothing undoes an upgrade whose new version does not start. The runtime's version is in `state/runtime.json` and, only when they differ, beside the relay's in the runtime status.
Fix::
* *Requirement (changed)*: link:../requirements/01-architecture.adoc#PM-ARCH-7[PM-ARCH-7] gains the operator's lifecycle acts in both clients: "The system must let the operator stop the runtime by its drain or at once, withdraw a drain the operator asked while it runs, restart it, and upgrade it to a newer release from the organisation's registry, through operator endpoints of the local API usable from the operator CLI and from a paired device, tell every client of each step, and undo an upgrade whose new release does not start." The upgrade bullet of link:../requirements/10-distribution.adoc#PM-DIST-1[PM-DIST-1] names the runtime as the one that installs a release and switches the links. Both are written by the implementing package.
* *Operator endpoints* under `/api/v1/operator/runtime/`: `stop` with `when` (`drain`, the default, or `now`) and `then` (`exit` or `restart`); `stop` withdrawn (`DELETE`) while a drain the operator asked runs, answered `409` once it can no longer be withdrawn; `upgrade` with the version and `when`; `upgrade` withdrawn (`DELETE`) while the release is fetched and verified, answered `409` once the links are switched; `upgrade/check`, the check for a newer version behind the consent `check_updates`, which refreshes the version state of the status. Each is privileged (`[op]`), accepted from `pm-operator` and from a paired device, and audited with its channel. `pm-operator drain` stays the signal that works whatever state the runtime is in; a drain it starts cannot be withdrawn.
* *Now*: the drain with the wait cut to zero: what still runs is stopped and settled as after the drain timeout (tasks offered again after the next start, jobs recorded `killed`), so the recovery resumes it. _Stop now_ during a drain cuts the wait the same way.
* *Restart*: after its drain the runtime releases the singleton lock and has its successor started, detached, by the on-demand start procedure; the successor waits for the singleton lock and starts. A runtime run by the service manager is restarted through the service manager instead, so the successor runs under the service unit.
* *State and events*: the runtime status (`GET /api/v1/status`) carries the runtime's version, its lifecycle state (`running`, `draining` with who asked it and whether it can be withdrawn, `upgrading` with its step), the version state (the newest version known with when it was checked, a failed check with its reason, whether the installation can be upgraded by the runtime, and the link to the release notes), and an upgrade's last result. The release notes of a version known are a read, `GET /api/v1/system/release-notes` with the version, as plain text, no operator act. The runtime-wide stream `GET /api/v1/events` announces `runtime.draining`, `runtime.drain_withdrawn`, `runtime.stopping`, `runtime.upgrading`, `runtime.upgraded`, and `runtime.upgrade_failed`.
* *Where releases come from*: the organisation's registry of link:../requirements/10-distribution.adoc#PM-DIST-1[PM-DIST-1], the only place a release is delivered. A check asks it for the newest release of the machine's platform, under the consent `check_updates` (rememberable for the machine; with _no_ nothing is fetched), at most once a day while remembered and on the operator's _check_; nothing about the machine is sent beyond the request itself (link:../requirements/01-architecture.adoc#PM-ARCH-2[PM-ARCH-2], no telemetry). The consent kind joins the closed list (link:01-onboarding.adoc#consents[Consents]).
* *Upgrade*: the runtime fetches the release through its outbound HTTPS client, verifies its digest, unpacks it into a new versioned installation directory beside the current one, rewrites the service unit where one is installed, switches both `PATH` links, then drains (or stops now) with `then: restart`, and its successor is the new `pm-mcpd`. A failure before the switch changes nothing; a new runtime that does not answer within the runtime start timeout makes the exiting runtime switch the links back, rewrite the unit back, and start the previous version, with `runtime.upgrade_failed` and the reason. The previous installation directory stays as the way back until the next upgrade removes it. An installation not laid out in versioned directories with the two links, or reached through `PM_MCP_HOME`, is not upgraded by the runtime: the upgrade is refused with its reason, and the steps by hand stay as specified.
* *Versions apart*: the rules of link:../specification/runtime-model/02-startup-recovery-drain.adoc#_drain_stop_upgrade[Drain, Stop & Upgrade] stay: a relay of another version forwards, and the mismatch is operator-only. A client of the operator compares its version with the runtime's on its first request and says so when they differ.
* *Open point*: which credential the runtime presents to the organisation's registry, which needs authentication for a package of the private organisation (a provider credential of GitHub with read access to packages, or one of its own), and the form of a release in it (the native binaries per platform with their digests).

[#change-runtime-metrics]
=== The Runtime's Metrics

Gap:: the runtime keeps no figures of its own: the runtime status lists the runtime, projects, plans, epics, workers, tasks, slots, and jobs item by item (link:../specification/runtime-model/01-processes-and-transport.adoc#local-api[Local API], Resources), with no count, no uptime, no memory, CPU, or disk use, and no figure over time. The usage of the models is recorded per task in each scope's metrics store (link:../specification/store-schemas/05-metrics-and-quality-report.adoc#metrics-store[Metrics Store]) and aggregated per plan in views, never across the machine.
Fix::
* *Requirement (new)*, in link:../requirements/01-architecture.adoc[Core Architecture (PM-ARCH)], the next free id, the ninth of the area: "The system must keep the figures of the runtime as metrics, counters, gauges, and timers from a closed catalogue, each maintained where the event it counts happens and never computed by reading the stores on a request; must serve them to both clients of the operator as a snapshot and as live updates; must show a figure it cannot measure as unavailable, never as zero; and must keep them on the machine, never sending them anywhere." It is written by the implementing package, like every requirement of a change.
* *The registry*: one registry in the runtime of named counters, gauges, and timers, each name with one writer, its unit, and its labels (project, role, harness, model) from a closed catalogue in the specification; a metric's name is distinct from the names of the metrics store, whose rule of one writer per name it follows.
* *The catalogue*, first version: the runtime (`runtime.version` and build, `runtime.started_at`, `runtime.uptime`, `runtime.memory.heap`, `runtime.memory.resident`, `runtime.cpu`, `runtime.disk.machine_store`, the listeners and their state); the work (plans and epics by activity and project, tasks queued and running, workers by role, harness, model, and busy or idle, jobs running and queued by kind, build and model slots in use and their caps, locks and leases held); the models (calls, `tokens_in`, `tokens_out`, and their total `total_tokens` with their coverage, errors and retries by cause class, per model and role; no money figure, link:03-plans.adoc#change-token-usage[Tokens, Not Money]).
* *Where they come from*: the work's gauges are kept by the transitions, the queue, the supervisor, and the slots, where things happen, and set from the recovered state at the start; the models' figures are counted per hour where a task row is written, and filled at the start from the task rows of the metrics stores, which stay the truth (link:../requirements/01-architecture.adoc#PM-ARCH-6[PM-ARCH-6]: process memory is a cache); the disk use is measured by the periodic sweep, with when; memory and CPU are read from the process (`/proc` on Linux, the task information on macOS), and a value the platform does not give is `unavailable`. Unmeasured usage is counted as such, never as `0`.
* *Local API*: `GET /api/v1/system` answers the snapshot of the system view, the windows (`hour`, `today`, `7d`) and the project as parameters; `GET /api/v1/system/metrics` answers every metric of the catalogue with its labels; the runtime-wide stream `GET /api/v1/events` carries `system.metrics` with the figures that changed, at most once a second. Both read endpoints never wait for a project's recovery and mark a recovering project. A paired device reads them like every resource.
* *Exposition*: an option, not required: `GET /api/v1/system/metrics` answered in the OpenMetrics text format for a tool of the operator that holds the runtime token. It is served on the runtime's socket only; a TCP listener of its own on loopback is excluded by link:../requirements/08-security.adoc#PM-SEC-4[PM-SEC-4].
* *Open point*: which library implements the registry (a metrics library of the runtime's stack or a registry of its own) is a dependency decision of the operator, taken by the implementing package before it adds anything.
Affects:: link:../requirements/01-architecture.adoc[PM-ARCH] (the new requirement), link:../specification/runtime-model/01-processes-and-transport.adoc#local-api[Local API] (the resources, the event), link:../specification/runtime-model/02-startup-recovery-drain.adoc#periodic-sweep[Periodic Sweep] (the disk use), link:../specification/runtime-model/02-startup-recovery-drain.adoc#per-project-recovery[Per-Project Recovery] (the gauges set from the recovered state), link:../specification/store-schemas/05-metrics-and-quality-report.adoc#metrics-store[Metrics Store] (the rows the models' figures are filled from, one writer per name), link:../specification/model-work/09-completion-usage-and-spend.adoc#job-result-schema[Worker Result & Usage Parsing], link:../specification/store-schemas/13-leases-integrity-testing.adoc#machine-lease-stores[Machine Lease Stores] (slots and leases), link:../specification/runtime-model/04-sessions-and-workers.adoc[Sessions & Workers] (the workers by role and state), link:../requirements/01-architecture.adoc#PM-ARCH-2[PM-ARCH-2] (kept on the machine), link:../requirements/08-security.adoc#PM-SEC-4[PM-SEC-4] (no listener of its own).

[#change-cleanup]
=== One Cleanup

Gap:: work history and technical residue share one mechanism. The retention purges, archived plans with the machine store `epics/<epic_id>/` of an archived epic (`retention.archived_plans_days`), job records with their logs (`retention.job_logs_days`), the workspace's rows (`retention.workspace_rows_days`, metrics rows among them), retired lesson bodies, daemon store directories, and, with `--machine`, rotated audit files, run only through `pm-operator sweep --apply`, which lists or removes them all alike; only the pending-record and fenced-generation steps of the periodic sweep run by themselves (link:../specification/store-schemas/13-leases-integrity-testing.adoc#evidence-based-removal-sweeps[Evidence-Based Removal Sweeps]; link:../specification/runtime-model/02-startup-recovery-drain.adoc#periodic-sweep[Periodic Sweep]). The keys are per project in the operator's `local-config.json`, 5 days by default (link:../specification/timeouts/03-retention-host-config.adoc#retention-days[Retention & Rotation]); nothing tells the operator that something could go, and neither client offers it. Read reports are kept without a way to remove them (<<UC-SYS-3>>, link:03-plans.adoc#change-reports[Reports to the Operator]), and an unenrolled project's store is removed only outside `PM-MCP`, by deleting its directory. Residue that needs no judgement waits for the operator's verb as well.
Fix::
* *Requirement (new)*, in link:../requirements/01-architecture.adoc[Core Architecture (PM-ARCH)], the next free id after the one of <<change-runtime-metrics>>: "The system must delete work history (archived plans, archived epics' machine stores, the logs of ended work, read reports, and the machine stores of unenrolled projects) only through one cleanup the operator confirms in either client: it must find once a day what has been ended for longer than its configured duration, tell the operator by one report, show what would be deleted as a summary and item by item, and delete, postpone, or keep it as the operator chooses, auditing every deletion; and it must remove technical residue by itself, each removal audited." It is written by the implementing package, like every requirement of a change.
* *Two classes*. _Work history_ is deleted only by the cleanup job: an archived plan with its whole archive entry (records, history, decisions, transcripts, metrics rows, and the workspace's metrics rows of the plan); an archived epic's machine store `epics/<epic_id>/`; the logs of ended work (the logs of ended jobs, the worker and session logs of archived plans), the job records staying with their plan; read reports; and the machine store of an unenrolled project, whole. _Technical residue_ is removed by the periodic sweep by itself from now on, each removal audited under the rules of the evidence-based sweeps (keep-rules, never on absence of evidence, the source of every value): pending entry records and fenced generations as today, the workspace's technical rows (`retention.workspace_rows_days`, without the plans' metrics rows), retired lesson bodies (`retention.retired_lesson_bodies_days`), daemon store directories of a write-set digest no longer the project's, worker directories of ended jobs, stale leases, temporary files and caches, and rotated audit files older than `audit_rotation.retain_days`, their index entries kept. The quiet-window retirement of `arch-constraint` lessons is a verdict on a lesson, not residue: it stays an act of `pm-operator sweep --apply`.
* *The verbs*: `pm-operator sweep [<project_id>] [--machine] [--apply]` stays for technical residue: it lists what the next automatic pass would remove, with its evidence, runs that pass at once with `--apply`, and retires the quiet `arch-constraint` lessons only then. `pm-operator cleanup [--delete|--remind|--ignore] [--yes]` is the cleanup job of the terminal client; the work history is never a candidate of `sweep`.
* *The durations*, in days, an integer of at least `7` or `never`: `cleanup.plans_after_days`, `cleanup.epics_after_days`, `cleanup.logs_after_days`, `cleanup.reports_after_days` (read reports), and `cleanup.unenrolled_after_days`, each `30` by default; `cleanup.remind_after_days`, at least `1`, default `3`. They are machine values in `machine-config.json` `cleanup`; a project's own value of the first three is kept in its `local-config.json` `cleanup` and wins for its items (link:04-projects.adoc#change-project-levels[Project Values over Machine Values]); reports and unenrolled projects belong to the machine only. `retention.archived_plans_days` and `retention.job_logs_days` go; the other `retention` keys stay for residue and the quiet-window retirement. An item is due when its end (archiving, reading, unenrolment) is older than its duration; the floor of `7` days keeps every window of the system view (at most 7 days) untouched by a deletion.
* *Never due*: live work, a pending entry, an unread report, an archived plan with an undischarged owed item (a retained capture ref, link:../specification/cli-and-security/02-credentials-and-operator.adoc#operator-drop-capture[Capture Ref Removal]), a kept item, and an item of an open or postponed job.
* *The check*: the first pass of the periodic sweep after the start and the first of each new UTC day compute the items due. When there are items not yet in a job, and no job is open or postponed, they form a new job, fixed from then on, and the runtime writes one report `system.cleanup_due` with the counts per kind, whose detail is the job; one report per job, never one per item. Items that become due while a job is open or postponed wait for the next job.
* *The store*: one append-only journal of the machine scope, `<PM_MCP_BASE>/state/cleanup.jsonl`, with its own leaf lock like `state/reports.jsonl`. Its events: `job` (the job with its items: kind, id, project, title, outcome, ended at, size, the duration and its source), `decided` (`delete` with the unchecked items, `remind` with when it comes back, or `ignore`; the channel, the device, and when), `deleted` and `delete_failed` per item (with the reason), `kept` and `released` per item. A job's state (`open`, `postponed`, `deleting`, `done`) and the kept list are the fold of its events. A job is identified by `job_id`, store-assigned `cln-NNNN`, never reused; it is no job of the job runtime: it starts no process and has no job record.
* *The decisions*: _delete_ deletes the checked items, the unchecked ones kept for good; _remind_ deletes nothing and, after `cleanup.remind_after_days`, opens a new job of the same items with a new report; _ignore_ deletes nothing and keeps every item for good. The first decision of a job is the one taken; a later one on a decided job is answered with the decision taken, unchanged. A released kept item is due again at the next check.
* *Deleting*: item by item, each in its own journaled transaction with one audit record `cleanup_deleted` (category `store`; the kind, the id, the project, `job_id`, the channel, the size). An archived plan's directory `archive/<plan_id>/` is replaced by a tombstone `archive/<plan_id>/deleted.json` (its `plan_id`, title, outcome, when it ended, `deleted_at`, `job_id`), so its id is never allocated again, ended work leaves it out, and its reports' detail resolves to "deleted" with the date; an epic's `epics/<epic_id>/` likewise by `epics/<epic_id>/deleted.json`. Read reports leave `state/reports.jsonl` by a journaled rewrite under its lock; their ids are never reused. An unenrolled project's store goes as a whole; enrolling the project again starts a new store. Before a plan's metrics rows go, what it used is added to the machine's usage aggregate `<PM_MCP_BASE>/state/usage-aggregate.jsonl` (per day, project, model, and role, in tokens with their coverage), from which the system view's figures are filled at the start beside the metrics stores, so no figure goes down. An item no longer due (a project enrolled again) is skipped and named; a failure keeps the item with its reason for the next job. A delete cut by a stop goes on after the next start from its journal.
* *Unenrolment*: `pm-operator unenrol` records `unenrolled_at` in the store's `store.json`; enrolling again removes it. The store is a cleanup item from then on, never a sweep candidate.
* *Local API*: `GET /api/v1/system/cleanup` answers the open or postponed job (its summary with the counts per kind and the space it frees, its items by project, each linked read-only to its ended view), the durations with their sources, the count of kept items, and what the automatic pass removed and when; `POST /api/v1/system/cleanup/{job_id}/delete` with the unchecked items, `…/remind`, and `…/ignore` decide the job; `GET /api/v1/system/cleanup/kept` lists the kept items and `PUT /api/v1/system/cleanup/kept` writes the list, an item left out released. Each write is privileged (`[op]`), accepted from `pm-operator` and from a paired device, and audited with its channel. The runtime-wide stream `GET /api/v1/events` announces `cleanup.job_opened`, `cleanup.decided`, `cleanup.progress`, and `cleanup.done`.
* *The report*: the kind `system.cleanup_due` joins the catalogue of link:03-plans.adoc#change-reports[Reports to the Operator]; its `from` is the machine, with no project; its detail is the job, and opening it reads the report.
* *Recurring waivers* are counted over the `waiver_waived` records of the audit log of the last 90 days, whatever has been deleted since, instead of over the plans `archived_plans_days` retains (link:../specification/phase-workflows/02-planning-lanes-phases-3-4.adoc[Planning Lanes & Phases 3–4], Recurring Waivers).
