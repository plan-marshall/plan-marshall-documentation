= Use Cases: Onboarding (UC-ONB)
:toc: left
:toclevels: 2
:nofooter:

link:../UseCases.adoc[Use Cases] » Onboarding

The operator makes a machine ready for `PM-MCP`: the languages it speaks, the harnesses it works with, the models plans may use, a model for every role, where credentials are kept, the providers the machine can reach, and how plans run by default. Everything here is machine level; a project's own setup (link:../specification/domain-extensions/04-setup-state-machine.adoc#project-setup-state-machine[project setup]) follows per project, and a project or a single plan may override what the machine provides (<<machine-defaults>>).

Each use case is a process the server runs as a workflow: <<UC-ONB-1>> is the onboarding workflow, each of <<UC-ONB-2>> to <<UC-ONB-9>> is a sub-workflow it calls, and <<UC-ONB-10>> changes later what they recorded. The flows below are those processes, not screens; the states are named as they would be in the workflow unit. The operator takes the choices in the web app or in the terminal: both render the same states, and each use case is designed for both. What each use case needs of the requirements and specifications is named in its _Requirements_.

[#preselect-first]
*Preselect as much as possible, hide nothing.* Every choice opens with a proposal the operator can accept as it is: the defaults, the found harnesses, the detected tools. The operator sees the whole of what will be recorded in one overview and can change any part of it; the detail is one step away, never in the way.

[#verify-reports]
*Every verification reports back.* A state that checks something (a harness, a profile, a credential store, a provider) shows each check as its own line that ends in a checkmark or in an error; an error names what failed, the answer that was received, and the fix. No check passes silently, and none fails without saying why.

[#consent-first]
*Nothing happens until the operator says so.* Every action that looks at the machine or acts on it (looking for programs, running a found program, asking a model) is preceded by a consent state in which the operator is asked first. The answers are _yes_, _yes and don't ask again_ for this action, and _no_. With _no_ the process stays where it is: nothing is looked at, nothing is run, nothing is recorded, and the onboarding does not progress past that point until the operator says yes; only where the action is optional (an icon, an advice, a script whose result can stay unknown, the description of modules) does the process go on without it. What the operator does with their own hands needs no consent: a credential the operator types is stored on that act alone. Every kind of consent, where it is asked, and whether it can be remembered is listed in <<consents>>; a remembered consent can be withdrawn in the machine settings at any time (<<UC-ONB-10>>, link:../specification/store-schemas/12-machine-stores.adoc#consent[Store Schemas Specification, Consent Before Acting (`<PM_MCP_BASE>/consents.json`)]).

[#machine-defaults]
*The machine sets defaults, not final values.* Every value the onboarding records is the default of every project, and a project may set its own: the model language, the allowed models, the role assignment, the providers, and the plan defaults. Only what is a fact of the machine itself has no project value: the interface language (the operator's own), the enrolled harnesses (the programs installed here, with their paths and digests), and the credential store (where this machine keeps its secrets). A plan overrides what link:../specification/workflow-dsl/09-plan-instance.adoc#plan-overrides[Workflow DSL & Engine Specification, Plan Overrides] names.

[#consents]
== Consents

The closed list of the consent kinds, for every use case that asks one (link:../specification/store-schemas/12-machine-stores.adoc#consent[Store Schemas Specification, Consent Before Acting (`<PM_MCP_BASE>/consents.json`)]). The consent pattern, its texts, and the listing of the remembered consents are designed once for both clients (link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/consents.adoc[Consents]); the remembered ones are listed and withdrawn in the machine settings of either client.

[cols="2,4,3,2,2",options="header"]
|===
|Kind |What the operator allows |Asked in |Remembered |With _no_

|`scan_harnesses` |look for the executables of the harnesses the profiles know, and run their version probe |`harness.consent` (<<UC-ONB-4>>) |yes, for the machine |stays
|`fetch_icons` |download the makers' icons of the found harnesses, once, through the runtime |`harness.icons-consent` (<<UC-ONB-4>>) |yes, for the machine |goes on with monograms
|`probe_harness_login` |run the login probe of each chosen harness: its command, or one minimal headless call with its token cost |`harness.probe-consent` (<<UC-ONB-4>>) |yes, for the machine |stays
|`verify_harness_profile` |run a harness the binary does not know, to verify its draft profile, with the token cost of its stages |`harness.add-consent` (<<UC-ONB-4>>) |never |stays
|`probe_harness_models` |run the model probe of each enrolled harness |`catalogue.consent` (<<UC-ONB-5>>) |yes, for the machine |stays
|`model_advice` |a task of the steward, with the tokens it is expected to use |`catalogue.consent` (<<UC-ONB-5>>), `roles.consent` (<<UC-ONB-6>>) |yes, for the machine |goes on without the advice
|`check_credential_store` |write, read, and delete one test entry in the chosen OS credential store (the keychain) |`store.consent` (<<UC-ONB-7>>) |yes, for the machine |stays
|`scan_providers` |look for the CLI tools of the providers and the credentials already stored |`providers.consent` (<<UC-ONB-8>>) |yes, for the machine |stays
|`verify_providers` |call each chosen provider with its credential, and run its CLI tool |`providers.verify-consent` (<<UC-ONB-8>>, <<UC-ONB-10>>) |yes, for the machine |stays
|the automatic run |every consent of <<UC-ONB-4>> to <<UC-ONB-8>> that the run needs, listed in full, for this run only |`auto.consent` (<<UC-ONB-2>>) |never |back to `onboard.mode`
|`inspect_checkout` |read a project's checkout (git configuration, build wrappers, host tools, language servers, scripts) and run the host tools' version probes from the absolute directories of the login `PATH`; changes nothing |`project.consent` (link:04-projects.adoc#UC-PRJ-1[UC-PRJ-1]) |yes, for the project |stays
|`run_checkout_scripts` |run the named scripts of a project's checkout, each with its arguments, confined like a job |`project.run-consent` (link:04-projects.adoc#UC-PRJ-1[UC-PRJ-1]) |yes, for the project and the digest of each script, in `consents.json` (never in the enrolment) |goes on, what needs the scripts unknown
|`model_cost` |a role task whose expected tokens are shown first: the qualification of the roles, the description of the modules |`setup.qualify-consent`, `setup.enrich-consent` (link:04-projects.adoc#UC-PRJ-1[UC-PRJ-1]) |yes, for the project |goes on without: the step is skipped with its reason and can be run later
|`check_updates` |ask the organisation's registry, over the network, for a release newer than the installed one |`runtime.update-consent` (link:07-system.adoc#UC-SYS-1[UC-SYS-1]) |yes, for the machine |goes on: no newer version is known
|===

A grant is not a consent: reading the issues of another repository (link:05-starting-work.adoc#UC-STA-4[UC-STA-4]) is a cross-repository read grant, kept with the grants.

[#UC-ONB-1]
== UC-ONB-1: Onboard a Machine

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client.
Goal:: get from a freshly installed `PM-MCP` to a machine on which the first project can be set up, in one guided run.
Trigger:: the operator enters on a machine that is not fully onboarded (link:02-entry.adoc#UC-ENT-1[UC-ENT-1]) and chooses to go on in the terminal or in the web app. A later run of one aspect starts from the machine settings of either client (<<UC-ONB-10>>).
Preconditions:: the binaries are installed (link:../specification/cli-and-security/01-cli-and-installer.adoc#installation-layout[Installation Layout]); the runtime can be started.
Flow::
+
[source,text]
----
  [S] onboard.entry            the first run
       ▼
  [O] onboard.mode             guided, or automatic
       │ guided                      │ automatic ──► ↳ auto (UC-ONB-2),
       │                             │               then onboard.completed
       ▼
  ↳ onboard.language           UC-ONB-3   first: every later text is in it
       ▼
  ↳ onboard.harnesses          UC-ONB-4   one scan, every harness found; no
       ▼                                  model yet: server and operator only
  ↳ onboard.models             UC-ONB-5   from here on a model may advise
       ▼
  ↳ onboard.assign-roles       UC-ONB-6
       ▼
  ↳ onboard.credential-store   UC-ONB-7   before any credential is entered
       ▼
  ↳ onboard.providers          UC-ONB-8   uses the credential store of UC-ONB-7
       ▼
  ↳ onboard.plan-defaults      UC-ONB-9   how plans run unless a project or
       ▼                                  a plan says otherwise
  onboard.completed            names the next step: enrol and set up a project;
                               the machine settings (UC-ONB-10) are reached
                               from here, and every later run returns here
----
Variations:: the operator stops at any state; the next run resumes there, in the web app or the terminal alike. The remembered consents are listed in the machine's settings, where the operator withdraws any of them (<<UC-ONB-10>>). A later run of one aspect starts its sub-workflow with the current values as the proposal: the first run and a later change are one process, as the project setup's `first_run` and `reconcile`.
Outcome:: the languages chosen, the harnesses enrolled with one of them the default, the catalogue of allowed models recorded, every role assigned a harness and a model, the credential store chosen, the machine's providers recorded, and the default way plans run.
Requirements:: link:../requirements/02-workflow.adoc#PM-WF-26[PM-WF-26] (the onboarding as one resident process of the machine scope, each aspect a sub-workflow), link:../requirements/01-architecture.adoc#PM-ARCH-11[PM-ARCH-11] (the choices in the web app and the terminal alike), link:../requirements/08-security.adoc#PM-SEC-8[PM-SEC-8] (consent before acting), link:../requirements/08-security.adoc#PM-SEC-3[PM-SEC-3] (the machine's configuration only through the operator's channel), link:../requirements/08-security.adoc#PM-SEC-7[PM-SEC-7] (the web app as a channel of the operator); specified in link:../specification/workflow-dsl/01-grammar.adoc#machine-scope[Machine Scope], link:../specification/cli-and-security/01-cli-and-installer.adoc#two-channels[Operator Choices in the Web App and the Terminal], link:../specification/state-catalogue/14-machine-onboarding.adoc[State Catalogue, Machine Onboarding].
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/consents.adoc[Consents] (the consent states of every step); link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/README.adoc[Terminal Client]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/web-app/onboarding.adoc#frame[Web App, Onboarding]

[#UC-ONB-2]
== UC-ONB-2: Onboard Automatically

Status:: `AGREED`
Actor:: an operator who does not want to weigh options, in the web app or in the terminal client.
Goal:: get every setting of the onboarding decided in one go, and see afterwards what was decided.
Trigger:: <<UC-ONB-1>>, `onboard.mode` with _automatic_, in the web app or in the terminal alike.
Flow::
+
[source,text]
----
  [O] auto.consent             one consent for everything the automatic run
       │                       does, listed in full: the consents of UC-ONB-4
       │                       to UC-ONB-8, for this run only, and that it
       │                       starts no role task
       ├── no ──────────────► onboard.mode   nothing was done
       ▼ yes
  [S] auto.run                 each sub-workflow with its proposal accepted:
       │                       the system language for both languages,
       │                       every supported harness found, the first one
       │                       the default, and their models, the default
       │                       role assignment, the OS credential store where
       │                       available, the providers whose tools are
       │                       found, the default plan behaviour; every check
       │                       reports ✓ or ✗
       ├── needs the operator ─► the state that needs it (a login, a token,
       │                         no harness found, the model ids of a harness
       │                         that cannot list its models), then auto.run
       │                         continues
       ▼
  [O] auto.result              everything that was decided, per step, with
       │                       the reason and a link to change it there
       ▼
  onboard.completed
----
Variations:: a step whose proposal fails its check stops the run in that step's own state, which names the failure and the fix; the run continues after it. The consent kinds the run covers are those of <<consents>>.
Outcome:: as <<UC-ONB-1>>, with every value the automatic run chose shown to the operator.
Requirements:: link:../requirements/02-workflow.adoc#PM-WF-26[PM-WF-26] (the automatic run: every proposal accepted under one consent, stopping only where the operator is needed, ending with every value and its reason), link:../requirements/08-security.adoc#PM-SEC-8[PM-SEC-8] (the run's one consent, never remembered); specified in link:../specification/cli-and-security/01-cli-and-installer.adoc#auto[Automatic Onboarding] and link:../specification/store-schemas/12-machine-stores.adoc#consent[Consent Before Acting] (`auto_run`).
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/consents.adoc#auto[Consents, The Automatic Run's One Consent]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/05-transcripts-entry.adoc#t-auto[Terminal Client, The Automatic Run]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/web-app/onboarding-steps-4-7.adoc#auto[Web App, Onboarding]

[#UC-ONB-3]
== UC-ONB-3: Choose the Languages

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client.
Goal:: choose the language the system speaks to the operator, and, separately, the language of the content a model writes and reads.
Trigger:: <<UC-ONB-1>>, state `onboard.language`, the first step; or a later reconfiguration.
Flow::
+
[source,text]
----
  [S] language.detect          the system's locale (LANG, the browser's
       │                       languages) and the language packs shipped
       ▼
  [O] language.choose          two choices, each preselected from the
       │                       system's locale where a pack exists:
       │                       • the interface language: web app and the
       │                         texts of pm-operator and pm-mcp
       │                       • the model language: what a model is told
       │                         to write in (content, questions, answers)
       │                       with a note why the second is separate
       ▼
  [S] language.record          both as machine settings; every later text
       ▼                       in the interface language
  language.done
----
Variations:: the model language _same as the interface_ follows a later change of the interface language; any other value stays.
Outcome:: the interface language and the model language recorded.
Requirements:: link:../requirements/01-architecture.adoc#PM-ARCH-11[PM-ARCH-11] (one message catalogue, the interface and the model language kept apart), link:../requirements/15-extensions-and-recipes.adoc#PM-EXT-6[PM-EXT-6] (`language.*` as operator values of the machine and the project), link:../requirements/02-workflow.adoc#PM-WF-26[PM-WF-26] (the languages as an aspect of the onboarding); specified in link:../specification/module-structure.adoc#i18n[Languages and Internationalisation], link:../specification/store-schemas/12-machine-stores.adoc#machine-config[Machine Configuration Store] (`language`), link:../specification/store-schemas/08-project-configuration-local.adoc#local-config[Operator Local Configuration] (`language.model`).
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/texts-and-languages.adoc[Texts and Languages]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/06-transcripts-steps-1-3.adoc#t-language[Terminal Client, Languages]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/web-app/onboarding.adoc#language[Web App, Onboarding]

[#UC-ONB-4]
== UC-ONB-4: Enrol the Harnesses

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client.
Goal:: have every harness of this machine that the operator wants to work with enrolled, from one scan, with one of them the default the later steps of onboarding use.
Trigger:: <<UC-ONB-1>>, state `onboard.harnesses`, or a later run of it from the machine settings (a harness installed since, or one to remove).
Preconditions:: on a first run no harness is enrolled yet, so no state of this step may start a role task.
Flow::
+
[source,text]
----
  [O] harness.consent          may the server look for harnesses on this
       │                       machine and run their version probe?
       │                       (consent kind scan_harnesses)
       ├── no ──────────────► stays at harness.consent; nothing else happens
       │                      (skipped when the consent is remembered)
       ▼ yes | yes, don't ask again
  [S] harness.scan             one scan: the executables of every harness the
       │                       profiles know, with their versions
       ├── none found ──────► [O] harness.none     no usable harness: names how
       │                            │                to install a known one, and
       │                            │                offers to add another
       │                            │ recheck ──► harness.scan
       │                            │ add another ──► harness.add
       │                            │ later ──► the onboarding rests here; its
       │                            │           next run resumes here
       ▼ found one or more
  [O] harness.icons-consent    may the server fetch the makers' icons of the
       │                       found harnesses? (consent kind fetch_icons)
       ├── no ──────────────► the harnesses are shown with their monograms;
       │                      the step goes on (an icon is no condition)
       ▼ yes | yes, don't ask again   (skipped when remembered)
  [S] harness.fetch-icons      each icon fetched once and stored; a failed
       │                       fetch leaves the monogram
       ▼
  [O] harness.choose           every found harness, each with version,
       │                       supported or not, worker-eligible or not,
       │                       what it reports of its token usage;
       │                       every supported one preselected, the first of
       │                       them as the default
       ├── add another ──► harness.add
       ▼ the chosen ones, one of them the default
  [O] harness.probe-consent    may the server run the login probe of each
       │                       chosen harness? (each command, or a minimal
       │                       headless call and its token cost; consent
       │                       kind probe_harness_login)
       ├── no ──────────────► stays at harness.probe-consent
       ▼ yes | yes, don't ask again   (skipped when remembered)
  [S] harness.probe            per chosen harness: version in the supported
       │                       range, logged in; each check ✓ or ✗ with its
       │                       cause
       ├── one fails ───────► [O] harness.blocked  names the harness, the cause,
       │                            │              and the fix
       │                            │ recheck ──► harness.probe
       │                            │ leave it out (not the last) ──►
       │                            │     harness.confirm without it
       │                            │ choose again ──► harness.choose
       ├── every chosen one fails ──► harness.none
       ▼ every chosen one passes
  [O] harness.confirm          per harness: path, version and digest to be
       │                       recorded; the default marked
       ▼
  [S] harness.enrol            writes the harness enrolments and the default
       ▼
  harness.done

  Adding a harness the binary does not know:

  [O] harness.add              the executable (path), a name, and how it is
       │                       called headless: a draft profile, started
       │                       from the template of the closest known harness
       ▼
  [O] harness.add-consent      may the server run it to verify the draft?
       │                       (the stages, and their token cost; consent
       │                       kind verify_harness_profile, never remembered)
       ├── no ──────────────► stays at harness.add-consent
       ▼ yes
  [S] harness.verify-profile   profile verification, one line per stage,
       │                       each ending in ✓ or ✗ with its finding
       ├── a stage fails ────► harness.add   the stage, its finding, the
       │                                     field of the draft to fix
       ▼ all pass
  [O] harness.add-confirm      the verified profile to be installed
       ▼
  [S] harness.install-profile  into the machine profile set
       ▼
  harness.choose               the added harness among the found ones
----
Variations::
* *What a harness reports of its usage*: each harness is shown with what this harness and version reports of its token usage, complete, partial (naming what is missing, "no cache figure"), or not reported, from its profile and, for a verified profile, from its verification; a harness that reports less is still enrolled, and the figures of its tasks say what was not measured (link:../specification/client-profiles/01-profile-schema.adoc#token-usage[Client Profiles & Bundle Manifest Specification, Tokens, Not Money]).
* A known harness that is not found where it is looked for can be pointed at by its path in `harness.add`; its shipped profile is used and no draft is asked for.
* The step cannot finish without one usable harness: the last chosen harness cannot be left out, and when every chosen harness fails its probe the step goes to `harness.none`, where the operator rechecks, adds one, or leaves the onboarding to continue later.
* A later run scans again: a harness found that is not enrolled is offered, an enrolled one no longer found is shown as missing and offered for removal; the default can change, a harness that is the default cannot be removed before another is chosen, and a harness that roles use cannot be removed before they are reassigned (<<UC-ONB-6>>).
Outcome:: every harness the operator chose is enrolled on the machine, one of them the default.
Requirements:: link:../requirements/06-execution.adoc#PM-EXEC-1[PM-EXEC-1] (a model job only through a harness the operator enrolled, found by the scan: its path, version probe, and digest), link:../requirements/13-client-profiles.adoc#PM-CLIENT-5[PM-CLIENT-5] (install locations, version and login probe, icon, and a profile verified from a draft entered as a form), link:../requirements/08-security.adoc#PM-SEC-8[PM-SEC-8] (the scan, the icons, the probes, and running an unknown harness on consent), link:../requirements/08-security.adoc#PM-SEC-3[PM-SEC-3] (enrolling a harness an operator act); specified in link:../specification/client-profiles/01-profile-schema.adoc#harness-scan[Harness Scan], link:../specification/client-profiles/01-profile-schema.adoc#login-probe[Login Probe], link:../specification/client-profiles/01-profile-schema.adoc#harness-icons[Harness Icons], link:../specification/client-profiles/01-profile-schema.adoc#unknown-harness[Unknown Harness], link:../specification/cli-and-security/02-credentials-and-operator.adoc#operator-enrol-harness[Harness Enrolment], link:../specification/store-schemas/11-enrolment-store.adoc#harness-enrolment-store[Harness Enrolment Store], link:../specification/store-schemas/12-machine-stores.adoc#machine-config[Machine Configuration Store] (`harnesses.default`).
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/consents.adoc#pattern[Consents, The Consent State]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/06-transcripts-steps-1-3.adoc#t-harness[Terminal Client, Harnesses]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/web-app/onboarding.adoc#harness[Web App, Onboarding]

[#UC-ONB-5]
== UC-ONB-5: Choose the Models for the Work

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client, advised by a model.
Goal:: decide which models of the enrolled harnesses the server may use for the roles of every plan.
Trigger:: <<UC-ONB-1>>, state `onboard.models`, or a later run of it.
Preconditions:: <<UC-ONB-4>> done: the harnesses are enrolled, one of them the default.
Flow::
+
[source,text]
----
  [O] catalogue.consent        may the server run the model probes of the
       │                       enrolled harnesses, and ask a model for
       │                       advice? (two consents, each shown with its
       │                       tokens: probe_harness_models, model_advice)
       ├── no to the probes ──► stays at catalogue.consent
       ▼ yes | yes, don't ask again
  [S] catalogue.models         the models each enrolled harness offers, from
       │                       its model probe, or none where it cannot list
       │                       them
       ├── no to the advice ──► catalogue.select, without a recommendation
       ▼
  [M] catalogue.advise         a role task of the steward on the default
       │                       harness: which models suit which kind of work,
       │                       with their limits and a recommendation
       ▼
  [O] catalogue.select         the models to allow per harness; the
       │                       recommendation preselected; model ids typed
       │                       for a harness that cannot list them
       ▼
  [S] catalogue.record         records the allowed models per harness
       ▼
  catalogue.done
----
Variations:: the model task fails or is left: `catalogue.select` is shown without a recommendation. A harness whose models the operator allows none of is enrolled but used by no role.
Outcome:: a recorded catalogue of the models allowed on each enrolled harness.
Requirements:: link:../requirements/16-model-work.adoc#PM-WORK-1[PM-WORK-1] (the model catalogue of the machine, a project's own replacing it, `model_not_allowed`; the steward that advises), link:../requirements/16-model-work.adoc#PM-WORK-6[PM-WORK-6] (the steward exempt from qualification), link:../requirements/08-security.adoc#PM-SEC-8[PM-SEC-8] (the model probes and the advice on consent); specified in link:../specification/store-schemas/12-machine-stores.adoc#model-catalogue[Model Catalogue], link:../specification/client-profiles/01-profile-schema.adoc#model-tiers[Model Tiers] (`headless.models_probe`), link:../specification/model-work/01-roles-and-configuration.adoc#steward-role[Steward Role].
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/consents.adoc#pattern[Consents, The Consent State]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/06-transcripts-steps-1-3.adoc#t-models[Terminal Client, Models]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/web-app/onboarding.adoc#models[Web App, Onboarding]

[#UC-ONB-6]
== UC-ONB-6: Assign Models to the Roles

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client, optionally advised by a model.
Goal:: give every role a harness, a model, and an effort from the catalogue, starting from the default assignment.
Trigger:: <<UC-ONB-1>>, state `onboard.assign-roles`, or a later reconfiguration.
Preconditions:: <<UC-ONB-5>> done.
Flow::
+

  [S] roles.load               the roles with their class, tools and form,

  [S] roles.default            applies the shipped default assignment to the

[#UC-ONB-7]
== UC-ONB-7: Choose Where Credentials Are Kept

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client.
Goal:: decide, knowingly, whether the machine keeps its credentials in the operating system's credential store or in protected files, and keep that choice until the operator changes it.
Trigger:: <<UC-ONB-1>>, state `onboard.credential-store`, or a later reconfiguration.
Flow::
+
[source,text]
----
  [S] store.detect             which stores this machine offers now:
       │                       macOS Keychain, Linux Secret Service (session
       │                       bus reachable, collection unlocked), files
       ▼
  [O] store.choose             each offered store with what protects a secret
       │                       in it and what does not; the recommendation
       │                       is preselected (the OS store where one is
       │                       available, else files)
       ├── an OS store not available now ──► [O] store.unavailable
       │                                         names why (locked, no session
       │                                         bus over SSH) and the fix
       │                                         │ recheck ──► store.detect
       │                                         │ choose another ──► store.choose
       ▼ an OS store, or files (consent skipped)
  [O] store.consent            may the server write, read and delete one
       │                       test entry in it? (consent kind
       │                       check_credential_store)
       ├── no ──────────────► stays at store.consent
       ▼ yes | yes, don't ask again   (skipped when remembered,
       │                               and for the files)
  [S] store.check              writes, reads and deletes a test entry;
       │                       each ✓ or ✗ with its cause
       ├── fails ───────────► store.unavailable
       ▼ passes
  [S] store.record             the chosen store, as a machine setting
       ▼
  store.done
----
Variations:: a later run that changes the store moves every entry to the new store after the operator confirmed the count, deletes each from the old one only once it reads back from the new one, and records the new store last; the enrolment integrity key moves last of all, once the HMAC sidecars verify under it in the new store; an interrupted move is resumed by the next run, so a secret is never in both stores after a completed move and never in neither.
Outcome:: the machine's credential store is recorded; every credential and the enrolment integrity key are kept there.
Requirements:: link:../requirements/07-credentials.adoc#PM-CRED-2[PM-CRED-2] (the store the operator chose, never another, the move), link:../requirements/07-credentials.adoc#PM-CRED-3[PM-CRED-3] (the file store when chosen), link:../requirements/08-security.adoc#PM-SEC-8[PM-SEC-8] (the check of an OS store on consent); specified in link:../specification/cli-and-security/02-credentials-and-operator.adoc#credential-store-choice[Credential Store as an Operator Choice], link:../specification/cli-and-security/02-credentials-and-operator.adoc#os-keyring-backends[Credential Stores], link:../specification/store-schemas/12-machine-stores.adoc#machine-config[Machine Configuration Store] (`credentials.store`).
Design:: link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/shared/consents.adoc#pattern[Consents, The Consent State]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/terminal-client/07-transcripts-steps-4-7.adoc#t-credentials[Terminal Client, Credential Store]; link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/web-app/onboarding-steps-4-7.adoc#credential-store[Web App, Onboarding]

[#UC-ONB-8]
== UC-ONB-8: Choose the Providers of the Machine

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client.
Goal:: decide which providers (git hosting and CI, code analysis, review bots) this machine can reach, how (native or through a CLI tool), and with which credentials, as the default for every project and plan.
Trigger:: <<UC-ONB-1>>, state `onboard.providers`, or a later reconfiguration.
Preconditions:: <<UC-ONB-7>> done: the credential store is chosen.
Flow::
+
[source,text]
----
  [O] providers.consent        may the server look for CLI tools and stored
       │                       credentials on this machine? (consent kind
       │                       scan_providers)
       ├── no ──────────────► stays at providers.consent
       ▼ yes | yes, don't ask again   (skipped when remembered)
  [S] providers.scan           the CLI tools found (git, gh, glab, ...) and the
       │                       credentials already stored
       ▼
  [O] providers.select         the providers available on this machine and
       │                       the variant of each (native or CLI)
       ▼
  [O] providers.credentials    each missing credential, entered by the
       │                       operator only, never through a model; stored
       │                       on that act, without a consent
       ▼
  [O] providers.verify-consent may the server call each selected provider
       │                       with its credential, and run its CLI tool?
       │                       (consent kind verify_providers)
       ├── no ──────────────► stays at providers.verify-consent
       ▼ yes | yes, don't ask again   (skipped when remembered)
  [S] providers.verify         every selected provider, one line per check,
       │                       each ending in ✓ or ✗ with its cause:
       │                       reachable; the credential authenticates and
       │                       as whom; its permissions and expiry; for the
       │                       CLI variant the tool's version and that it is
       │                       logged in as the same identity
       ├── a check fails ───► [O] providers.failed   the failed checks with the
       │                            │                provider's answer and the fix
       │                            │ fix credential ──► providers.credentials
       │                            │ check again ──► providers.verify
       │                            │ continue without it ──► providers.record
       │                            │   (recorded as not available)
       ▼ all pass
  [S] providers.record         the machine's provider defaults
       ▼
  providers.done
----
Variations:: the operator selects no provider: projects work with what their own setup selects. A credential is rotated or replaced later in the machine settings (<<UC-ONB-10>>).
Outcome:: the machine's providers recorded as defaults; a project's setup and a single plan may override them.
Requirements:: link:../requirements/06-execution.adoc#PM-EXEC-5[PM-EXEC-5] (the native and the CLI variant, settled from the machine's provider defaults), link:../requirements/15-extensions-and-recipes.adoc#PM-EXT-6[PM-EXT-6] (`providers` and `host-tools.json` as operator files of the machine), link:../requirements/07-credentials.adoc#PM-CRED-1[PM-CRED-1] (a provider verified as a whole), link:../requirements/07-credentials.adoc#PM-CRED-4[PM-CRED-4] (a secret entered by the operator only, in the web app on the loopback listener only), link:../requirements/08-security.adoc#PM-SEC-8[PM-SEC-8] (the scan and the verification on consent), link:../requirements/02-workflow.adoc#PM-WF-25[PM-WF-25] (a plan's override of providers); specified in link:../specification/store-schemas/12-machine-stores.adoc#provider-defaults[Machine Provider Defaults], link:../specification/cli-and-security/02-credentials-and-operator.adoc#provider-verification[Provider Verification], link:../specification/cli-and-security/03-web-server.adoc#web-credentials[Credentials in the Web App], link:../specification/domain-extensions/04-setup-state-machine.adoc#setup-integration-variants[Integration Variants].

[#UC-ONB-10]
== UC-ONB-10: Change the Machine's Settings

Status:: `AGREED`
Actor:: the operator, in the web app or in the terminal client.
Goal:: change later what the onboarding recorded for the machine: one aspect, a remembered consent, the default of how documents are taken, a credential, the cleanup's durations, or the paired devices.
Trigger:: the operator opens the machine settings of either client; or a credential has expired or is about to (reported by the status, or a plan held by it, link:06-controlling-work.adoc#UC-CTL-4[UC-CTL-4]).
Preconditions:: the onboarding has completed once (<<UC-ONB-1>>, resting in `onboard.completed`).
Flow::
+
[source,text]
----
  [O] settings.choose          what the machine recorded, per aspect, with
       │                       the remembered consents, the documents mode,
       │                       the cleanup's durations, the credentials
       │                       with their status, and the paired devices
       ├── reconfigure <aspect> ──► ↳ the aspect's sub-workflow (UC-ONB-3 to
       │                              UC-ONB-9) as a later run, its current
       │                              values the proposal ─► settings.choose
       ├── withdraw a consent ───► [O] settings.withdraw   the consent, and
       │                              │                    where it will be
       │                              │                    asked again
       │                              ├── keep ──► settings.choose
       │                              ▼ withdraw
       │                         [S] settings.remove-consent  removed from
       │                                consents.json, audited ─► settings.choose
       ├── documents mode ───────► [O] settings.documents-mode  copy | move |
       │                              │                         ask
       │                              ▼
       │                         [S] settings.record   the machine setting,
       │                                               audited ─► settings.choose
       ├── cleanup durations ────► [O] settings.cleanup-durations  one per
       │                              │                kind, and the
       │                              │                postponement
       │                              ▼
       │                         [S] settings.record   the durations of
       │                                               UC-SYS-3, audited
       │                                               ─► settings.choose
       ├── paired devices ───────► ↳ devices (UC-ENT-2) ─► settings.choose
       ▼ a credential
  [O] settings.credential      rotate (a new secret for the entry, its other
       │                       fields kept) or replace (a new entry, another
       │                       kind of credential); entered by the operator
       │                       only, stored on that act, without a consent
       ▼
  [S] settings.store-credential  into the recorded store; every token
       │                         derived from the old secret dropped
       ▼
  [O] providers.verify-consent as in UC-ONB-8 (verify_providers)
       ▼
  [S] providers.verify         every provider that uses the credential
       │                       ✓ or ✗ (UC-ONB-8)
       ├── a check fails ───► [O] providers.failed   as in UC-ONB-8
       ▼ all pass
  settings.choose              a plan held by the old credential goes on
                               (UC-CTL-4)
----
Variations::
* Withdrawing a consent changes nothing that was recorded with it; the consent state is asked again the next time its action runs.
* The documents mode is the machine's `sources.documents_mode` (`copy`, `move`, or `ask`, the default; link:../specification/state-catalogue/09-bootstrap-and-lessons.adoc#documents-source[State Catalogue, Documents as a Source]); answering _always_ in a plan's start writes the same setting.
* A credential that has expired holds every plan that needs it as a condition; the hold names the act that resolves it, which is this flow, and the plan goes on once the new credential verifies (link:06-controlling-work.adoc#UC-CTL-4[UC-CTL-4]).
* In the web app a secret is entered only on the loopback listener; on the LAN listener the form names the terminal command (link:../specification/cli-and-security/03-web-server.adoc#web-credentials[CLI, Coordination & Security Specification, Credentials in the Web App]).
* *The cleanup's durations*: how long archived plans, archived epics, the logs of ended work, read reports, and unenrolled projects are kept before the cleanup offers them, and after how many days a postponed cleanup asks again, are machine settings changed here, as in the cleanup view (link:07-system.adoc#UC-SYS-3[UC-SYS-3]); a project's own duration for its plans, epics, and logs is set in its settings.
* An aspect a project sets for itself is changed in that project's setup, never here.
* *Changed in two clients at once*: the first change wins; a later one made against an older value is refused with `conflict`, the current value shown, and the operator may apply theirs again on top of it (link:../specification/cli-and-security/01-cli-and-installer.adoc#concurrent-changes[CLI, Coordination & Security Specification, Concurrent Changes of a Setting]).
Outcome:: the changed value is recorded for the machine and audited; every project and plan that follows the machine's value uses it from its next read.
Requirements:: link:../requirements/02-workflow.adoc#PM-WF-26[PM-WF-26] (every aspect changed alone later, its current values the proposal), link:../requirements/01-architecture.adoc#PM-ARCH-11[PM-ARCH-11] (both clients; a change against an older revision refused with `conflict`), link:../requirements/08-security.adoc#PM-SEC-8[PM-SEC-8] (the remembered consents listed and withdrawn), link:../requirements/07-credentials.adoc#PM-CRED-4[PM-CRED-4] (the credential acts, a secret entered by the operator only), link:../requirements/07-credentials.adoc#PM-CRED-1[PM-CRED-1] (a changed credential verified again), link:../requirements/01-architecture.adoc#PM-ARCH-10[PM-ARCH-10] (the cleanup's durations), link:../requirements/08-security.adoc#PM-SEC-3[PM-SEC-3] (the machine's configuration only through the operator's channel); specified in link:../specification/workflow-dsl/01-grammar.adoc#machine-scope[Machine Scope] (`settings.choose`), link:../specification/store-schemas/12-machine-stores.adoc#consent[Consent Before Acting], link:../specification/cli-and-security/01-cli-and-installer.adoc#concurrent-changes[Concurrent Changes of a Setting], link:../specification/cli-and-security/02-credentials-and-operator.adoc#operator-credential-cli[Credentials] (`rotate`, `set`), link:../specification/cli-and-security/02-credentials-and-operator.adoc#credential-store-move[The Store Move].
