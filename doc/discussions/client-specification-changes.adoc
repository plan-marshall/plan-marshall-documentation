= Proposal: Specification Changes for the Clients
:toc: left
:toclevels: 2
:nofooter:

xref:../Requirements.adoc[Requirements] » xref:README.adoc[Discussions] » Specification Changes for the Clients

What the specifications must gain so that the runtime gives the two clients of the operator, the terminal client and the web app, the input their designs show (link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/README.adoc[`pm-mcp-clients`, Design]). It analyses the changes the use cases propose (link:../use-cases/01-onboarding.adoc#changes[Onboarding], link:../use-cases/02-entry.adoc#changes[Entry], link:../use-cases/03-plans.adoc#changes[Plans]), names what they leave out, and cuts the work into packages. It is deleted once its content is written into the specifications.

[#decided]
== Decided

* *Waiting for the operator is normal behaviour*, defined once in the workflow language, and the specification's principle that no state waits for an operator decision is wrong. An operator wait halts its own scope only; the onboarding's wait is the one that halts the system (link:../use-cases/03-plans.adoc#change-operator-wait[Waiting for the Operator]). That removing time limits touched some 35 places showed the waits were sliced wrongly: each place defined its own.
* *A decision is the question set*, named by its first question's id; across plans and epics it is addressed as `<scope_id>/<question_id>` (`fix-relay/Q-007`); no new identifier kind, and the name _decision record_ (`D-NNNN`) keeps its meaning, the record of a decision taken.
* *The console's preferences* (`console.notify`, `console.full_screen`) are keys of the runtime's machine configuration.

[#foundations]
== Foundational Findings

. *Operator waits* (settled above): every operator step of the onboarding and of a decision needs a state that waits for the operator in a unit the entry session does not drive; today the workflow language forbids it.
. *The operator's links over the local API have no form*: no representation of a state for a client (its id, kind, step, level, facts, proposal, items, links), no scheme of link ids and endpoints. Every link of today's hypermedia format is model-facing.
. *No event catalogue*: the event streams are a list of contents in prose; no event has a name or a payload schema, so no client can follow a decision, an overview, or a check line.
. *Texts of the runtime*: a client shows only catalogue texts, but representations carry prose (a check's cause and fix, a reason). The contract must say which fields are message keys with arguments and which are verbatim external or model text (a provider's answer, a harness's error text, question content).
. *The client's environment*: three steps need what only the client sees (its locale, the operator's login `PATH`, an SSH session), while the runtime's own environment is never an input (link:../specification/runtime-model/01-processes-and-transport.adoc#_environment[Environment]); the request must carry them.
. *Client-owned files*: the terminal client keeps its history and the overview's selection in its state directory, outside `<PM_MCP_BASE>`; the closed list of the files a CLI binary reads (link:../specification/cli-and-security/01-cli-and-installer.adoc#cli-file-reads[Direct File Reads]) needs that exception.

UC-PLN-3 (designing a plan's process) proposes no change yet: its building blocks are open points of the use case, to be worked out there before any specification. It builds on link:../use-cases/03-plans.adoc#change-phase-sub-workflows[Phases as Sub-Workflows] of UC-PLN-1.

[#conflicts]
== Conflicts Between the Changes

* The plan axes keep `questions.*`; Waiting for the Operator removes its modes and waits.
* Operator Choices and Answers from the Terminal Client both edit Operator Channel Isolation, item 1: one edit.
* The steward's harness against the resolution order of the role assignment.
* The entry opens the loopback listener first, then the LAN on a yes; today's lifecycle refuses the second exposure.
* Machine Scope's gate names the web app; the design names both clients.
* The messages endpoint has two paths.

The runtime and the engine implement each specification in their own packages, planned in `pm-mcp-core` and `plan-marshall-mcp` once the contract is written; the clients build against the mock runtime meanwhile. The client packages wait on their contract: `cli-onboarding` and `web-onboarding` on `onboarding-contract` and `entry-contract`, `cli-decisions` and `web-decisions` on `decision-contract`, `cli-overview` and `web-overview` on `overview-contract`, `cli-plan-view` and `web-plan-view` on `process-contract`, `cli-projects` and `web-projects` on `project-contract`.
