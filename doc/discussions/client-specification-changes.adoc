:toc: left
:toclevels: 2
:nofooter:

xref:../Requirements.adoc[Requirements] » xref:README.adoc[Discussions] » Specification Changes for the Clients

What the specifications must gain so that the runtime gives the two clients of the operator, the terminal client and the web app, the input their designs show (link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/README.adoc[`pm-mcp-clients`, Design]). It analyses the changes the use cases propose (link:../use-cases/01-onboarding.adoc#changes[Onboarding], link:../use-cases/02-entry.adoc#changes[Entry], link:../use-cases/03-plans.adoc#changes[Plans], link:../use-cases/04-projects.adoc#changes[Projects], link:../use-cases/05-starting-work.adoc#changes[Starting Work], link:../use-cases/06-controlling-work.adoc#changes[Controlling Work], link:../use-cases/07-system.adoc#changes[System]), names what they leave out, and cuts the work into packages. It is deleted once its content is written into the specifications.

[#decided]
== Decided

* *Waiting for the operator is normal behaviour*, defined once in the workflow language, and the specification's principle that no state waits for an operator decision is wrong. An operator wait halts its own scope only; the onboarding's wait is the one that halts the system (link:../use-cases/03-plans.adoc#change-operator-wait[Waiting for the Operator]). That removing time limits touched some 35 places showed the waits were sliced wrongly: each place defined its own.
* *A decision is the question set*, named by its first question's id; across plans and epics it is addressed as `<scope_id>/<question_id>` (`fix-relay/Q-007`); no new identifier kind, and the name _decision record_ (`D-NNNN`) keeps its meaning, the record of a decision taken.
* *The operator acts only in the two clients* (link:../use-cases/05-starting-work.adoc#change-clients-only[All Interaction in the Operator's Clients]): a harness is a worker, never a channel of the operator. The session-driven units, the entry session, the channel `session` of answers, and `pm-mcp enter` as the operator's way to start work go; every place that relays the user's choice through a model is rewritten as an operator wait.
* *Sources are gathered by the server and kept in a source directory* (link:../use-cases/05-starting-work.adoc#change-source-directory[The Source Directory]); the only model step of bringing in a source is the screening of external content, over the stored copy; what is on this machine is trusted (link:../use-cases/05-starting-work.adoc#change-local-trusted[What Is on This Machine Is Trusted]).
* *One name for the multi-plan tier: epic.* The clients and the documents no longer call it _orchestrator_; the ledger lives in `.marshall/epics/` and `.marshall/archived-epics/`, its phase value is `epic`. The names of `plan-marshall`'s own tools (`plan-orchestrator`) and the linkage values `orchestrated` and `not_orchestrated` stay.
* *The console's preferences* (`console.notify`, `console.full_screen`) are keys of the runtime's machine configuration.

[#foundations]
== Foundational Findings

. *Operator waits* (settled above): every operator step of the onboarding and of a decision needs a state that waits for the operator, in every unit and scope; today the workflow language forbids it.
. *The operator's links over the local API have no form*: no representation of a state for a client (its id, kind, step, level, facts, proposal, items, links), no scheme of link ids and endpoints. Every link of today's hypermedia format is model-facing.
. *No event catalogue*: the event streams are a list of contents in prose; no event has a name or a payload schema, so no client can follow a decision, an overview, or a check line.
. *Texts of the runtime*: a client shows only catalogue texts, but representations carry prose (a check's cause and fix, a reason). The contract must say which fields are message keys with arguments and which are verbatim external or model text (a provider's answer, a harness's error text, question content).
. *The client's environment*: three steps need what only the client sees (its locale, the operator's login `PATH`, an SSH session), while the runtime's own environment is never an input (link:../specification/runtime-model/01-processes-and-transport.adoc#runtime-environment[Environment]); the request must carry them.
. *Client-owned files*: the terminal client keeps its history and the overview's selection in its state directory, outside `<PM_MCP_BASE>`; the closed list of the files a CLI binary reads (link:../specification/cli-and-security/01-cli-and-installer.adoc#cli-file-reads[Direct File Reads]) needs that exception.

[#conflicts]
== Conflicts Between the Changes

* The plan axes keep `questions.*`; Waiting for the Operator removes its modes and waits.
* Operator Choices and Answers from the Terminal Client both edit Operator Channel Isolation, item 1: one edit.
* The steward's harness against the resolution order of the role assignment.
* The entry opens the loopback listener first, then the LAN on a yes; today's lifecycle refuses the second exposure.
* Machine Scope against Onboarding a Project as One Process: a project's onboarding no longer runs in the machine scope but in a scope of its own (corrected there), so that several projects are onboarded at once.
* The messages endpoint has two paths.
* All Interaction in the Operator's Clients against Onboarding a Project as One Process, which let the entry session drive the setup (corrected there), and against the package `enter-command`, which builds `pm-mcp enter` as the entry of a host.
* Starting from the Clients against L-6: the clients name an issue, as the bootstrap does; a list of issues to pick from stays a later improvement.

The runtime and the engine implement each specification in their own packages, planned in `pm-mcp-core` and `plan-marshall-mcp` once the contract is written; the clients build against the mock runtime meanwhile. The client packages wait on their contract: `cli-onboarding` and `web-onboarding` on `onboarding-contract` and `entry-contract`, `cli-decisions` and `web-decisions` on `decision-contract`, `cli-overview` and `web-overview` on `overview-contract`, `cli-plan-view` and `web-plan-view` on `process-contract`, `cli-projects` and `web-projects` on `project-contract`, `cli-start` and `web-start` on `start-contract`, `cli-actions` and `web-actions` on `control-contract`, the client packages of the reports on `report-contract`, `cli-system` and `web-system` on `system-contract`.
