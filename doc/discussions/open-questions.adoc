Questions that wait for a decision of the operator, each with what it blocks, the options, and a recommendation. A question is removed from this document when it is decided and the decision is written into the requirements, the specifications, the link:../roadmap.adoc[Roadmap], the link:../developer/project-setup.adoc[Project Setup], or the work packages; the document itself is deleted with its last question.

Undecided points of the design that an implementation has to settle are not listed here: they are watch items marked _Open_ or _Undecided_ in the link:../ImplementationWatch.adoc[Implementation Watch] (<<recorded-elsewhere>>).

== Working Rules

[#claude-md-pointers]
=== The Reference in the Code Repositories

Question:: Shall the `CLAUDE.md` of `pm-mcp-clients`, `pm-mcp-core`, and `plan-marshall-mcp` point to link:../developer/project-setup.adoc[Project Setup] and drop what they repeat of it?
Why it is open:: Project Setup says every repository's `CLAUDE.md` points to it. Only the one of this repository does.
Options:: (1) Add the pointer and keep the files as they are. (2) Add the pointer and remove the sections the reference now covers (the git workflow, the publishing rule), so that there is one place to change.
Recommendation:: 2, in one pull request per repository.
Blocks:: nothing; until then the statement in Project Setup is ahead of the files.

== Planning and Order

[#default-units-before-private]
=== Default Workflow Units Before the Repository Is Private

Question:: The exit of roadmap Milestone 3 names `DefaultUnitInvariantTest` and `StateCatalogueDriftTest`, which run over the default workflow units. Those units are model-facing content, and no such content is committed to `plan-marshall-mcp` before it is private, which the roadmap schedules for Milestone 7. Which of the two gives way?
Options:: (1) Switch `plan-marshall-mcp` to private when the work package starts, four milestones earlier than planned, and with it give up free CI minutes, static analysis and reviews for that repository from then on. (2) Run the two tests of the Milestone 3 exit over fixture units; the default units and the tests over them arrive with Milestone 7.
Recommendation:: 2. It keeps the repository public for as long as planned, and the tests prove the mechanism either way.
Blocks:: the work package `default-units-and-drift-tests` of `plan-marshall-mcp`, and the wording of the Milestone 3 exit.

== Tools and Machines

[#python-for-differential-tests]
=== A Python Interpreter in the Test Environment

Question:: The differential test harness (`PM-TEST-2`) runs the Python reference scripts of `plan-marshall` against the Java primitives. May the test environment of `pm-mcp-core`, CI included, require a Python interpreter and a checkout of `plan-marshall` at the commit the migration inventory pins?
Options:: (1) Yes, behind a Maven profile of its own, so that the regular build needs neither. (2) No; the reference outputs are recorded once as fixture files and the harness compares against those, re-recorded when the pin advances.
Recommendation:: 2 for the build, with the recording itself as a documented manual step. The regular build stays free of a second language, and the oracle is still the real script.
Blocks:: the work package `differential-test-harness` of `pm-mcp-core`, and with it the exit of Milestone 4 (Stage 1 criteria).

[#wsl2-machine]
=== A Machine with WSL2

Question:: Who verifies Landlock on WSL2, carried over from Milestone 0, and on which machine?
Options:: (1) The operator provides a Windows machine with WSL2 for one measurement. (2) WSL2 is recorded as unverified and served on the evidence of native Linux until someone runs it.
Recommendation:: 2 until a machine is at hand; the confinement level is reported per job in any case, so an unconfined WSL2 would show.
Blocks:: the work package `landlock-on-wsl2` of `pm-mcp-clients`.

== Module Structure

[#http-base]
=== The HTTP Base of the Provider Modules

Question:: `pm-provider-sonar` depends on `pm-provider-ci` only to reuse the shared HTTP base, although a code analysis provider is not a CI provider. Does the HTTP base move to a place of its own?
Options:: (1) Leave it; the dependency is a build fact with no effect on behaviour. (2) A module of its own in `pm-providers` for the HTTP base, which `pm-provider-ci` and every provider adapter depend on. (3) A package of `pm-runtime`, which already depends on `cui-http`; the provider modules would then depend on the runtime module.
Recommendation:: 2 when the first analysis adapter is implemented, not before; 3 would turn the dependency direction around.
Blocks:: nothing now; it shapes the Sonar adapter of roadmap Milestone 6.

[#web-app-toolchain]
=== The Front-End Toolchain of `pm-web-app`

Question:: `pm-web-app` needs `frontend-maven-plugin`, a pinned Node and npm, and the packages of the web application. May these dependencies be added, and when is the module created?
Options:: (1) Create the module now with an empty application shell, so that the structure of Milestone 1 is complete. (2) Create it with the web access of Milestone 11, when it has something to serve.
Recommendation:: 2. An application shell is an empty module, which the project avoids, and the toolchain would be kept current for a year without use.
Blocks:: the items of Milestone 1 that name `pm-web-app`; with option 2 they move to Milestone 11.

== Skills and Tool Surface

[#announcement-skills]
=== Operational Announcement Skills for External Tools

Question:: `PM-SKILL-2` requires minimal operational announcement skills for external tools (for example build skills) that describe the capability verbs and outcome meanings. No specification defines such a skill, its `skill://pm/` address, or the rule that puts it into a task's required skill set; the tool descriptions of `pm_build` and `pm_lsp` already announce their verbs. Does the requirement stay?
Options:: (1) Remove the bullet; the tool schemas and descriptions announce the capability. (2) Keep it and specify the skill per tool, its address, and when a task's required skill set contains it.
Recommendation:: 1. A second text beside the tool description would have to be kept equal to it.
Blocks:: the wording of `PM-SKILL-2` and the skill catalogue in the MCP Tools Specification.

[#machine-scope-skills]
=== The Skill Catalogue of a Machine-Scope Worker

Question:: A worker of a task of the machine scope has no project, yet it may call `pm_skills`, `pm_skill`, and `pm_skill_file` with `plan_id: "NO_PLAN"` and read `skill://pm/…` resources. The skill tools resolve `NO_PLAN` against the project's workspace scope and its enabled domains, which such a worker does not have. Which skills does it see?
Options:: (1) The compiled worker-protocol skills (core, task protocol, role) and the machine's extension skills that name no domain; no domain skill. (2) Only the compiled worker-protocol skills.
Recommendation:: 1, because a machine-scope role may name an extension skill as its contract.
Blocks:: the rendering and scope rules of the skill tools and of `resources/read` in the MCP Tools Specification, and `PM-SKILL-3`.

[#skill-resource-read-errors]
=== The Error of an Unreadable Skill Resource

Question:: A resource read that fails answers the JSON-RPC error `-32002` with one of two codes, `scope_not_found` and `path_traversal_rejected` (`PM-TOOL-4`). `resources/read` also serves `skill://` documents, which can become unreadable after they were listed (the skill tools answer `file_unreadable`), and a machine-scope worker is refused a `pm://` resource. Which code does the read answer?
Options:: (1) Add `file_unreadable` and a code for the refused resource to the closed set. (2) Answer both with `scope_not_found`; the cause is in the audit record only.
Recommendation:: 2. The set stays two codes, and a worker can do nothing different for the other cause.
Blocks:: `PM-TOOL-4`, the resource contract of the MCP Tools Specification, and its error table.

== Operations

[#nightly-failures]
=== Who Sees a Failed Nightly Build

Question:: The nightly builds of `pm-mcp-core` and `plan-marshall-mcp` show an upstream break by the next morning only if someone learns of the failure. Does a failed scheduled run reach the operator?
What is known:: a failed scheduled run is listed in the Actions tab; whether it sends a notification depends on the operator's GitHub notification settings, which were not checked.
Options:: (1) Rely on GitHub's notification of the account that last changed the workflow file. (2) Let a failed nightly open an issue in its repository.
Recommendation:: check the notification once; 2 only if it does not arrive.
Blocks:: nothing; without it the nightly build protects less than it seems to.

== Use Cases

[#harness-icons]
=== Showing a Maker's Icon

Question:: May the clients show the icon of a harness's maker at all, and which icons may be bundled with the release?
Why it is open:: it is a legal question, kept with the business documents of the operator; the research is in link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/web-app/harness-icons.adoc#icons[Web App, Harness Icons].
Options:: (1) Bundle the makers' icons where their terms allow it. (2) Bundle no maker's icon; every harness shows the neutral icon, and the operator may place an icon of their own on the machine.
Recommendation:: 2 until the legal question is answered; the operator's own icon covers the need.
Blocks:: the bundled icon set of the clients (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/client-profiles.adoc[Client Profiles Specification]).

[#registry-credential]
=== The Credential for the Organisation's Registry and the Form of a Release

Question:: Which credential does the runtime present to the organisation's registry when it checks for and downloads a newer version, and in which form is a release published there?
Why it is open:: a package of the private organisation needs authentication; either a provider credential of GitHub with read access to packages, or a credential of its own.
Options:: (1) The GitHub provider credential the machine already keeps, with the scope to read packages. (2) A credential of its own for the registry, kept in the machine's credential store.
Recommendation:: 1, with the native binaries per platform and their digests as the release's assets; one credential less to keep.
Blocks:: the check for updates and the upgrade of the runtime (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/runtime-lifecycle/01-startup-recovery-drain.adoc[Runtime Lifecycle Specification, Startup, Recovery & Drain]).

[#metrics-library]
=== The Library of the Runtime's Metrics

Question:: Which library implements the registry of the runtime's metrics?
Why it is open:: it adds a dependency, and no dependency is added without the operator's approval.
Options:: (1) The metrics library of the runtime's stack (Micrometer, as Quarkus integrates it). (2) A small registry of its own over the stores the runtime already keeps.
Recommendation:: 1 if its native-image support holds for the runtime binary; otherwise 2.
Blocks:: the metrics of the runtime (link:../specification/runtime-model.adoc[Runtime Model Specification]).

[#message-format]
=== The Message Format of the Catalogue

Question:: The message catalogue lives in `pm-api`, which depends only on `jackson-core` streaming. How does it format a message with arguments (plurals, selections) in the two languages?
Why it is open:: ICU4J would add a large dependency to the module every client and the runtime share; no dependency is added without the operator's approval.
Options:: (1) Implement the small subset of the ICU message syntax the catalogue uses (arguments, `plural` and `select`) in `pm-api`. (2) Allow ICU4J in `pm-api`.
Recommendation:: 1; the catalogue's texts use only that subset, and a test over every key proves it.
Blocks:: the message catalogue (link:../specification/module-structure.adoc[Module Structure Specification]).

[#uncovered-operator-acts]
=== Operator Acts Without a Use Case

Question:: Two requirements give the operator something to do or to see that no use case shows: allowing and denying an upstream MCP server of a project, with its credential (link:../requirements/05-services.adoc#PM-SVC-3[PM-SVC-3], `pm-operator upstream allow|deny` or the same act in the web app), and an extension skill refused on its check, whose reason is reported to the operator (link:../requirements/03-skills.adoc#PM-SKILL-5[PM-SKILL-5]). Do they get use cases?
Why it is open:: a use case is agreed by the operator, and the clients design only what a use case shows; without one, neither client offers the upstream act nor shows the refusal.
Options:: (1) A new use case for the upstream servers of a project (in link:../use-cases/04-projects.adoc[Projects]) and the refused extension skill as a report of link:../use-cases/03-plans.adoc#UC-PLN-6[UC-PLN-6]; both start as `DRAFT`. (2) The upstream act stays a terminal verb only and the refusal a line of the runtime's status; no use case.
Recommendation:: 1; the requirement already names the act in the web app.
Blocks:: the design of both acts in the clients.
