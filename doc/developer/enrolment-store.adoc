= Enrolment Store
:toc: left
:toclevels: 2
:toc-title: Table of Contents

link:../DeveloperGuide.adoc[Developer Guide] » Enrolment Store

The enrolment store is split between the foundation `pm-core` and the library module `pm-runtime` of https://github.com/plan-marshall/pm-mcp-core[`pm-mcp-core`]: the package `de.planmarshall.core.store` holds the typed record, its codec, the sidecar record, the store and the lifecycle gate, and holds no key; the package `de.planmarshall.runtime.enrolment` holds the integrity key, the HMAC, the per-use checks, the check and the operator writes. Why the enrolment works this way is explained in link:../concepts/enrolment.adoc[Concepts § Enrolment].

[#schema-and-codec]
== Schema and Codec
_Requirements: link:../Requirements.adoc#PM-EXEC-2[PM-EXEC-2], link:../Requirements.adoc#PM-MIG-2[PM-MIG-2], link:../Requirements.adoc#PM-IMPL-2[PM-IMPL-2]_

`ProjectEnrolment` is the schema. Its nested records (`Wrapper`, `PinnedFile`, `HostTool`, `Build`, `Argv`, `ProviderVerification`, `ProjectScript`, `Binding`, `ArgumentSchema`, `LanguageServer`) and enums (`WrapperName`, `HostToolName`, `Interpreter`, `BuildSystem`, `Provider`, `WorkerKind`, `ContainerEngine`, …) carry the patterns, closed name sets and bounds; an instance that exists is one the schema admits. `project_root` is a normalized absolute path, an argument vector has at least one element and at most one module-argument group, a wrapper `pw` is run by `python3` and every other wrapper by none, a project script has a budget of at least ten seconds, a budget at least one second. What only the enrolment verb can decide (shell metacharacters in an argument vector, a write path below `<PM_MCP_BASE>`, a refused environment name) is not checked here; `EnrolmentPolicy` of `pm-runtime` checks part of it before an enrolment is signed (see <<operator-writes>>). The constants of `Provider` are named after the CLI each provider runs, `GIT`, `GH` and `GLAB`, like those of `HostToolName`, because no member of `pm-core` may name a provider (PM-IMPL-1, guarded by `ProviderNeutralityArchTest`); the wire names in the enrolment file stay `git`, `github` and `gitlab`.

The maps are copied into a stable order in the constructor (the declaration order of an enum key, the natural order of a string key). `EnrolmentCodec.write` relies on that: it writes every field, defaults included, in the order of the schema, so the same enrolment always gives the same bytes. Those are the bytes the HMAC is computed over; never compute it over bytes from anywhere else.

`EnrolmentCodec.read(file, content)` and `EnrolmentSidecar.read(file, content)` read through `StrictJson` like every codec of the package (link:store-substrate.adoc#format-versions[Store Substrate § Format Versions and Refusals]): the version first (`format_outdated` or `format_newer` naming the file), every field at most once, no undeclared field at any level of nesting, every required field, one JSON type per field. The optional fields `pilot`, `container_engine`, `released_at` and the `interpreter` of a host tool read as their defaults when absent. A `StoreRefusal` from the sidecar names the sidecar file.

`EnrolmentSidecar` pairs a `StoreDigest` (size and SHA-256) with the HMAC, 64 lowercase hexadecimal digits. `matches(content)` compares the size and SHA-256 only; the HMAC is the runtime's to verify.

[#store]
== The Store
_Requirements: link:../Requirements.adoc#PM-EXEC-2[PM-EXEC-2], link:../Requirements.adoc#PM-IMPL-7[PM-IMPL-7]_

`EnrolmentStore(base)` names the paths below the base directory: `file(projectId)` is `enrolments/<project_id>.json`, `sidecar(projectId)` is `enrolments/<project_id>.json.hmac`, and `lockKey(projectId)` is `LockKey.enrolment(base, projectId)`, the lock file `locks/enrolments/<project_id>.lock` of the machine store level, ordered by project id (link:locks-and-leases.adoc[Developer Guide § Locks and Leases]). `base()` returns the base directory, absolute and normalized; the runtime compares the write paths of an enrolment with it and takes the key-creation lock from it. A project id outside the identifier pattern is refused before it becomes part of a path. The store does not create `enrolments/`.

* `projectIds()` lists the enrolled projects without a lock: every file `<project_id>.json` with a valid id; sidecars, audit intents, staged and temporary files and anything else are not enrolments, and a missing directory lists none.
* `readFile` and `readSidecar` return the exact bytes, empty when the file does not exist; `decode(projectId, content)` reads them as the project's enrolment and refuses one whose `project_id` is not the name of its file as `unreadable`; `decodeSidecar` reads a sidecar record.
* `write(transaction, enrolment, sidecar)` writes the canonical bytes and the sidecar as one pair. It refuses a sidecar whose size and SHA-256 are not those of the canonical bytes, before anything is written. It settles a stopped write of the pair first (`recoverPair`), then stages the file as `<project_id>.json.tmp.<transaction id>` and the sidecar as `<project_id>.json.hmac.tmp.<transaction id>` (one `TransactionId` for both, each written new and synced, mode `0600`), forces the directory, and only then renames the file and the sidecar into place, the file first, and forces the directory again. The staged sidecar is complete before the first rename, which is what makes a stop after it completable.
* `recoverPair(transaction, projectId)` settles the stopped writes of the pair, under the project's lock, without a key and without signing anything: it only completes or discards a pair a write already produced. It groups the project's staged names by transaction id and processes them in ascending order: a staged file with a staged sidecar that reads strictly and matches it is moved into place (`PairRecovery.Completed`, logged `PM_MCP-64`); a staged file whose staged sidecar is missing, torn, unreadable or does not match it is deleted with the sidecar (`PairRecovery.Discarded`, logged `PM_MCP-166`), and the enrolment is as it was; a staged sidecar alone, after the file was already replaced, is moved into place when it reads strictly and matches the current file, and otherwise deleted, which leaves the file to the check. It returns one entry per stopped write, empty when nothing was staged or the directory does not exist.
* `writeSidecar(transaction, projectId, sidecar)` replaces only the sidecar: the re-baseline. It settles nothing itself; its caller settles a stopped write of the pair first, under the same lock, as the re-baseline does with `recoverPair` before it reads and signs the file (see <<operator-writes>>).
* `remove(transaction, projectId)` deletes the staged files of every stopped write of the pair first, so an unenrolled project is never rolled forward later, then the file and its sidecar, nothing else, forces the directory to disk, and reports whether the file or the sidecar existed. The file is deleted before the sidecar: its removal is the commit point of an unenrol, and a stop between the two deletions leaves a sidecar without its file, which `projectIds()` does not list, beside the record the unenrol owes; the background pass of the recovery settles it (see <<recovery>>).

A staged name belongs to a project only when it is exactly `<project_id>.json.tmp.<id>` or `<project_id>.json.hmac.tmp.<id>` for a transaction id: the project `ab` never claims or deletes the staged names of `ab-c`, and the temporary `<store>.tmp.<uuid>` of `AtomicStoreFile`, which `writeSidecar` uses, is not a staged name of a transaction. The transaction journal is not reused for the pair: it is bound to the scopes of the per-project machine store (a closed set of scope types, a digests sidecar, owned directories whose staged files a recovery deletes), and in the flat `enrolments/` directory the recovery of one project would delete the staged files of another project's write in flight.

The owed audit record of a write that the recovery rolls forward stays the unconfirmed record (`failed`, `not_confirmed`): the mutation completed, its completion was not recorded.

The audit intent of the operator writes (see <<operator-writes>>) is the file `enrolments/<project_id>.json.audit-intent`. It exists only while a record is owed, is touched only under the project's lock, and is not an enrolment: `projectIds()` lists only `.json` names. Its document is the one of the intent files of the JSONL stores, `{"format_version": 1, "owed_events": [<owed event>]}`, read and written by the package-private `AuditIntentFile` that both stores share (link:store-substrate.adoc#audit-records[Store Substrate § Audit Records]).

* `auditIntent(projectId)` is the path of the intent file.
* `oweAudit(transaction, projectId, event)` writes the record durably to the intent before the mutation; a record whose `transaction_id` is already owed is not owed twice, and a detail an intent cannot hold is refused before anything is written.
* `owedAudit(transaction, projectId)` returns the records still owed, in order.
* `deliverOwedAudit(transaction, projectId, sink)` hands the owed records over in order and returns those handed over. It stops at the first record the sink refuses with an `UncheckedIOException`, which the substrate logs as `PM_MCP-160` and keeps owed, and never throws for it; any other failure of the sink propagates. The intent file is removed once every record was handed over, and rewritten with the rest after a partial hand-over.
* `auditOwingProjectIds()` lists, without a lock, the projects whose intent file exists (valid ids only, a missing directory lists none): what the recovery iterates.
* `exists(transaction, projectId)` answers whether the file or its sidecar exists, under the lock, so `unenrol` decides whether anything is owed before it removes.
* `hasStagedWrite(transaction, projectId)` answers, under the project's lock, whether a stopped write of the pair left a staged name of the project, with the name matching of `recoverPair` and `remove`; a missing directory answers `false`, a directory that cannot be listed is an `UncheckedIOException`. `unenrol` asks it besides `exists`, so a first enrolment that was staged and stopped, with neither file nor sidecar in place, is still cancelled.
* `hasEnrolmentFile(transaction, projectId)` answers, under the project's lock, whether the enrolment file alone exists: exactly the fact `projectIds()` lists the project for; the sidecar, a staged name and the intent do not count. Where `exists` answers for the file or the sidecar, this one tells an enrolment from the orphan sidecar of an interrupted unenrol. `Enrolments.replayOwedAuditOfUnenrolledProjects()` asks it to leave a project with an enrolment file to that project's own recovery.
* `removeOrphanSidecar(transaction, projectId)` deletes, under the project's lock, the sidecar of a project whose enrolment file is gone, forces the directory and reports whether a sidecar was deleted; while the file exists it touches nothing and returns `false`. It touches no staged name, no audit intent and nothing of another project; a sidecar that cannot be deleted is an `UncheckedIOException` naming the project. `Enrolments.replayOwedAuditOfUnenrolledProjects()` calls it after it handed the project's owed records over.

Every read and write takes the transaction and refuses it as an internal fault unless it holds the project's own lock; the lock of another project does not count. An intent file that is unreadable or of another format version is refused as a `StoreRefusal` naming it and is left in place.

[#lifecycle-gate]
== The Lifecycle Gate
_Requirements: link:../Requirements.adoc#PM-MIG-1[PM-MIG-1], link:../Requirements.adoc#PM-MIG-5[PM-MIG-5]_

`LifecycleGate.RELEASE` is the gate of the release. Its position is the private constant `OPEN_IN_THIS_RELEASE`, `false` today; the constructor is package-private, so only the release constant and the tests of the open position build a gate. `decide(enrolment)` returns `LIFECYCLE_CLOSED` (`lifecycle_closed`) for a released enrolment, `ADMITTED` for an open gate or a pilot, and `LIFECYCLE_CLOSED` otherwise. It takes a verified enrolment: read it through `EnrolmentCheck`, never with `EnrolmentStore.decode` alone, or an edited `pilot: true` would open the gate.

[#integrity-key]
== The Integrity Key
_Requirements: link:../Requirements.adoc#PM-EXEC-2[PM-EXEC-2], link:../Requirements.adoc#PM-SEC-5[PM-SEC-5]_

`EnrolmentKey(store, stateDirectory, user, random)` reads the key from the active `SecretStore`. Where that is a keyring, the key is the entry `CredentialAccount.global("enrolment-integrity-key")`; where it is the fallback file store, it is the file `<state>/enrolment-hmac.key`, read only after `EnrolmentFileCheck` passed it. The key is 32 random bytes kept base64url without padding.

* `read()` is tri-state: the key, empty when it does not exist, or a `SecretStoreException` when it exists and cannot be read (an insecure or malformed key file, a failing keyring). Never treat the exception as an absent key.
* `readOrCreate()` is the path of a write: it reads first, and creates the key only where none exists. A key that exists but cannot be read (an insecure, partial or malformed key file) is the `SecretStoreException` of the read and is never replaced; no path deletes or overwrites an existing key file. A keyring write replaces an existing secret, so after writing the keyring entry `readOrCreate()` reads it back and returns the key it holds: a writer that bypassed the lock and wrote between the read and the write wins, and its key is adopted. An entry that vanished after the write is `SecretStoreException` with `FAILED`.
* `creationLock(base)` is `LockKey.credentials(base)`, the lock file `locks/credentials.lock`: the existing machine-level lock of credential writes, because the key is a credential. The caller of `readOrCreate()` holds it. Its id `credentials` sorts before every enrolment lock id `enrolments/<project_id>`, so a transaction takes it first and never after a project's lock; asking for it while a project's lock is held is a lock order violation.
* The key file is created atomically. The key is written to the temporary file `enrolment-hmac.key.tmp.<uuid>` in the state directory, opened with `CREATE_NEW` and mode `0600`, written completely and forced to disk; `Files.createLink` then publishes it as `enrolment-hmac.key`, and the state directory is forced to disk. The temporary file is deleted in a `finally` block on success and on failure. A hard link, not an atomic move, publishes the key because a rename on POSIX silently replaces an existing file: of two writers that race for the first key, the second would replace the key the first created, and every HMAC written under it would be stranded. The link fails with `FileAlreadyExistsException` instead, and the losing writer reads the winner's key. Any other failure, a file system without hard links included, is `SecretStoreException` with `FAILED`; there is no non-atomic fallback. A crash leaves the complete key or no key file; a temporary file it leaves holds only key material at mode `0600` and is read by no path.
* A failure is logged as `PM_MCP-260` naming the source and the reason code (link:../LogMessages.adoc[Log Messages]); the key itself is never in a record or a message.

Within one instance the methods are synchronized. Across runtime instances `Enrolments.enrol` and the re-baseline acquire `creationLock` before the project's lock, so two first writes never create two keys in a keyring; the read-back after the write adopts a key another writer won. The key file path was safe without the lock already: its hard link never replaces an existing file.

[#check]
== The Enrolment Check
_Requirements: link:../Requirements.adoc#PM-EXEC-2[PM-EXEC-2], link:../Requirements.adoc#PM-SEC-4[PM-SEC-4], link:../Requirements.adoc#PM-SEC-5[PM-SEC-5]_

`EnrolmentCheck.verify(transaction, projectId)` acquires the project's lock in the caller's transaction (it may hold it already) and returns the verified `ProjectEnrolment`. The project's recovery runs it as its first step (`EnrolmentIntegrityStep`, see <<recovery>>) before the project is first served; the verify-not-resolve check of the project's jobs, the `enter` request and the operator verbs must run it too and do not yet, because no job, `enter` or operator-verb path exists in the runtime. The order of its steps is the one of link:../concepts/enrolment.adoc#check[Concepts § Enrolment, The Check]: the no-follow snapshot of the file, then of the sidecar, with their per-use checks; the pair, the sidecar record, size and SHA-256, the HMAC, the enrolment. Every later step uses the bytes of the two snapshots; nothing reads the files again.

The package-private `EnrolmentFileCheck.snapshot(file)` binds the per-use checks to the one read of the file, with JDK means only:

. It reads the attributes with `Files.readAttributes(file, PosixFileAttributes.class, NOFOLLOW_LINKS)`. A file that does not exist is an absent snapshot, not an exception.
. It applies the per-use checks to those attributes (`symbolic link`, `foreign owner <owner>, not <user>`, `mode <mode> broader than 0600`); a file that fails one is refused without being opened, so the bytes of a link target or of an insecure file are never read.
. It opens the file with `Files.newInputStream(file, NOFOLLOW_LINKS)` and reads every byte from that stream. When the open or the read fails, it reads the attributes again: a symbolic link there is refused as `symbolic link`, a file that is gone as `file replaced or changed while it was read`, anything else is an `UncheckedIOException`.
. It reads the attributes again with `NOFOLLOW_LINKS` and refuses the snapshot as `file replaced or changed while it was read` (the constant `EnrolmentFileCheck.CHANGED_WHILE_READ`) unless the file key, the size (against the bytes read) and the last-modified time are those of the first read; then it applies the per-use checks to the second attributes too, so a mode or owner changed during the read is refused with the ordinary reason.
. Otherwise the snapshot holds the bytes read.

The JDK has no `fstat` on an open handle, so the identity of the opened file is inferred from the attributes read before the open and after the read. This narrows the window between check and read; it does not close it, and the mode of the operator-owned `enrolments/` directory stays the outer boundary (see <<known-limits>>). The path-based `EnrolmentFileCheck.violation(file)` remains the check of the integrity key file, and `check(file)` is used by the tests only; no read of an enrolment file or sidecar calls either.

`verify` throws:

* `StoreRefusal` as `ENROLMENT_INSECURE`, naming the file or sidecar and the reason of its snapshot (a symbolic link, a foreign owner with both user names, a mode broader than `0600` with both modes, `file replaced or changed while it was read`);
* `StoreRefusal` as `ENROLMENT_TAMPERED`, whose message names the reason and the command `pm-operator accept-edit enrolment <project_id>`; the reasons are the constants of `EnrolmentCheck` (`sidecar without its enrolment file`, `enrolment file without its sidecar`, `size or SHA-256 differs from the sidecar record`, `HMAC differs from the sidecar record`, `the integrity key does not exist in the active key source (keyring or key file); a switch of the key source strands the enrolments written under the other one`);
* `StoreRefusal` as `absent` when neither file nor sidecar exists, and as `unreadable`, `format_outdated` or `format_newer` for the sidecar or the file;
* `SecretStoreException` when the key exists and cannot be read.

The two integrity refusals are logged (`PM_MCP-161`, `PM_MCP-162`) and handed to the `AuditSink`; when the sink fails, its exception is added to the refusal as suppressed and the refusal is thrown all the same. A refusal of the strict read of the sidecar or the file (`unreadable`, `format_outdated`, `format_newer`) is logged as `PM_MCP-165` and audited as `enrolment_invalid` with the reason `<outcome code> in <file name>`, and thrown with its own outcome and message unchanged. Four package-private static helpers of `EnrolmentCheck` carry this, and `Enrolments` refuses through them too, so a refusal reads and is recorded the same wherever it arises:

* `tampered(auditSink, file, projectId, reason)` builds, logs (`PM_MCP-161`) and audits an `enrolment_tampered` refusal;
* `insecure(auditSink, file, projectId, reason)` builds, logs (`PM_MCP-162`) and audits an `enrolment_insecure` refusal;
* `invalid(auditSink, file, projectId, reason)` builds, logs (`PM_MCP-165`) and audits an `enrolment_invalid` refusal: the refusal of an enrolment that violates the enrolment policy;
* `recorded(auditSink, refusal, event)` appends the audit event of any refusal directly, adds an `UncheckedIOException` of the sink to the refusal as suppressed, and returns the refusal for the caller to throw; the three above, the strict-read refusals and `unenrol`'s `scope_active` refusal use it.

[#operator-writes]
== The Operator Writes
_Requirements: link:../Requirements.adoc#PM-EXEC-2[PM-EXEC-2], link:../Requirements.adoc#PM-MIG-1[PM-MIG-1], link:../Requirements.adoc#PM-IMPL-7[PM-IMPL-7]_

`Enrolments` opens its own transaction per write and acquires the project's lock in it; `enrol` and the re-baseline acquire the credentials lock (`EnrolmentKey.creationLock(store.base())`) first and the project's lock second, unconditionally, because either may create the integrity key (see <<integrity-key>>). `unenrol` and the replays take neither the key nor the credentials lock. Once both locks are held, the re-baseline first settles a stopped write of the pair (`store.recoverPair`) before it reads anything. Each write owes its audit record and runs in the order owe, mutate, confirm, hand over, all four inside that transaction: `store.oweAudit` writes the record, with a new transaction id of the write (`TransactionId.generate`), to the project's intent before the mutation, `store.confirmAudit` replaces it after the mutation by the record of the success, and `store.deliverOwedAudit` hands it over. Each write is logged after the transaction closed.

What is owed before the mutation is the unconfirmed form of the record, `AuditEvent.notConfirmed()`: the same event, category, `project_id` and `transaction_id`, outcome `failed`, `reason` `not_confirmed`. The mutation of an operator write is not redone by a recovery (unlike a roll-forward or a tail repair, which the next recovery or repair completes), so the record may claim `succeeded` only after the mutation completed; `confirmAudit` then replaces the owed record of the same `transaction_id` by the succeeded one, in place and written durably like the owing. The mutation and the confirmation are not atomic, so the design rests on what each outcome of a stop leaves: a mutation that fails, or a stop before the confirmation, leaves the unconfirmed record, which is handed over as `failed`/`not_confirmed` (logged `PM_MCP-164`); a stop after the confirmation leaves the succeeded record. The one inexact case is a stop in the window between the end of the mutation and the confirmation: the write took effect and its record says `not_confirmed`, which is true (its completion was not recorded) and is resolved by the enrolment file and its sidecar. The record never claims a success the runtime did not see.

A sink that refuses the record (`UncheckedIOException`, the declared failure of `AuditSink.append`) does not fail the write: the substrate logs `PM_MCP-160` naming the record and the intent, and the record stays owed. A stop between the confirmation and the hand-over leaves the succeeded record owed, and a mutation that fails after the record was owed keeps the unconfirmed record, so an attempted operator write is audited, as what is known of it, rather than lost. The next write of the project and the replays hand an owed record over; a record handed over of another transaction than the current write's is logged as `PM_MCP-63`. Delivery is at least once: a record handed over again after a stop between the accepted append and the removal of the intent carries the same `transaction_id`, by which the audit store drops the duplicate (link:../concepts/store-integrity.adoc#audit-delivery[Concepts § Store Integrity, Audit Records of a Store Change]). The refusals (`enrolment_tampered`, `enrolment_insecure`, `enrolment_invalid`, `unenrol_refused`) changed nothing and recur with the next attempt; they are appended to the sink directly and are not owed.

`enrol` and the re-baseline check the enrolment against `EnrolmentPolicy.violations(enrolment, store.base())` before they sign it: `enrol` the enrolment as written, before the key is resolved, a record is owed or anything is written; the re-baseline the enrolment decoded from its snapshot, before the key and before anything is owed, so it never blesses a file that violates the rules. A violation is refused through `EnrolmentCheck.invalid` as `enrolment_invalid`, its reasons joined with `; ` (logged `PM_MCP-165`, audited, nothing owed, nothing written, no key created). The policy checks only the rules the specification states in concrete terms, in a deterministic order (canonical templates, discovery templates, providers, write paths, environment names):

* Placeholders of an argument vector (`build.canonical_templates`, `build.discovery_templates`, `providers[].verify_argv`): a placeholder is a brace-delimited token `{...}`; any placeholder in a literal argument, `{module}` included, and any placeholder other than `{module}` in the module-argument group is a violation naming the vector and the token. A lone brace and `{}` are not placeholders.
* Write paths: an absolute write path is not judged by its lexical form alone. The policy walks up the path as given to its longest existing ancestor (`Files.exists` with `NOFOLLOW_LINKS`, so a dangling symbolic link counts as existing; the file system root ends the walk), resolves that ancestor with `toRealPath()`, which follows every link and resolves a `..` inside it as the file system does, and appends the names below it that do not exist yet. The resolved path and the normalized path are each judged against the base and its real path: one that is the base directory, lies below it or contains it (`/` included) is a violation naming the path (`write_paths: <path> is, lies below or contains the base directory <base>`). So a missing leaf below a symbolic link into the base is refused, and an ordinary missing leaf outside the base is admitted. Two further refusals have a reason of their own: a `..` below the last existing ancestor, which nothing exists to resolve against (`… goes through '..' below its last existing ancestor <ancestor>`), and a path whose longest existing ancestor cannot be resolved, such as a dangling or looping link or one without permission (`… cannot be resolved below its last existing ancestor <ancestor>`): the policy fails closed there. A path that is not absolute is not judged, and neither is one that does not parse.
* Build environment names: a name that ends with `_TOKEN`, `_PASSWORD`, `_SECRET` or `_KEY` is a credential variable, and `DBUS_SESSION_BUS_ADDRESS`, `XDG_RUNTIME_DIR` and `MVND_DAEMON_STORAGE` are refused by name; the match is case-sensitive, as the schema admits upper-case names only.

The shell metacharacters of an argument vector, whether the forbidden free flags apply to enrolled templates, the full list of credential variable patterns, and the uniqueness of the project root are not checked (see <<known-limits>>).

* `enrol(enrolment, pilot)` writes the enrolment with `pilot` taken from the argument alone and `released_at` cleared, with the sidecar `EnrolmentHmac.sidecar(key, EnrolmentCodec.write(written))`, after the policy admitted it. The key is chosen under the credentials lock and the project's lock: `key.read()` first; if the key is absent and `store.projectIds()` is not empty, the write is refused through `EnrolmentCheck.tampered` as `ENROLMENT_TAMPERED` for the first enrolled project (its file, reason `EnrolmentCheck.KEY_ABSENT`, logged `PM_MCP-161`, audited `enrolment_tampered`); only when the key is absent and no enrolment file exists does `key.readOrCreate()` create it. A sidecar without any enrolment file does not count. When the key cannot be read or created, or the write is refused, nothing is written and nothing is owed. Otherwise it owes `enrolment_written` unconfirmed, writes the pair through the atomic pair write of the store, confirms the record and hands it over; logs `PM_MCP-60`. A stopped write is settled by the project's recovery (`EnrolmentIntegrityStep`) or by the next write of the project; the check refuses a mismatched pair.
* `unenrol(projectId)` asks `LiveWork.of(projectId)` while it holds the lock. Live work throws `Enrolments.ScopeActiveException` (`CODE` `scope_active`), naming each item as `<kind> <id>`, after logging `PM_MCP-163` and auditing `unenrol_refused` through `EnrolmentCheck.recorded`; nothing is removed and nothing is owed. When the audit append fails, the caller still gets the `ScopeActiveException` with its live work items; the sink's `UncheckedIOException` is its suppressed exception. Otherwise, if the file, its sidecar or a staged name of a stopped write exists (`store.exists` or `store.hasStagedWrite`), it owes `enrolment_removed` unconfirmed, removes them (`store.remove` deletes the staged files first, then the file and the sidecar), confirms the record and logs `PM_MCP-61`; a first enrolment that was staged and stopped is thus cancelled and audited and cannot be rolled forward later by a recovery or a write. In every case it hands over what the project owes, so a record an earlier write still owes is flushed. It returns `true` when the file, the sidecar or a staged name existed, and `false` without a record when nothing of the enrolment existed.
* `rebaseline(projectId)` first settles a stopped write of the pair with `store.recoverPair` once both locks are held: a completely staged pair is rolled forward, an incomplete one discarded (logged `PM_MCP-64` and `PM_MCP-166` by the store), so a staged pair of an earlier stopped `enrol` can never replace the re-baselined pair later, unreported. A staged file that cannot be listed, read, moved or deleted fails it with an `UncheckedIOException` and nothing signed. It then takes one no-follow snapshot of the settled file (`EnrolmentFileCheck.snapshot`) inside its transaction: a refused snapshot throws `EnrolmentCheck.insecure` (`ENROLMENT_INSECURE`, logged `PM_MCP-162`, audited `enrolment_insecure`, nothing owed, nothing written; a symbolic link is refused, never followed), an absent one `absent`. It decodes the bytes of that snapshot strictly and checks the decoded enrolment against the policy, reads the old sidecar record where one is readable (for the display only), owes `enrolment_rebaselined` unconfirmed, writes a new sidecar over the same bytes, confirms the record and hands it over; the checks, the strict read and the signature cover one read of the file. It returns `Enrolments.Rebaseline(file, recorded, current, settled)`, the values the operator's display shows, which describe the settled file; `recorded` is empty without a readable old record. `settled` is the list `recoverPair` returned before the signing, copied and never `null`: one `PairRecovery.Completed` or `PairRecovery.Discarded` per stopped write, in the order of the transaction ids, empty when nothing was staged, the normal case. A `Completed` entry means the signed file is the recovered write, whose bytes may differ from the bytes the operator reviewed in place; the operator verb, outside `pm-mcp-core`, shows it as a warning. Logs `PM_MCP-62`. A refusal (absent, insecure, unreadable, invalid) owes nothing. It keeps `key.readOrCreate()`: the re-baseline is the operator's explicit act and the one write that creates the key over existing enrolments, the way out of the `enrol` refusal after a key-source switch. The other enrolments, written under the old key, then fail their own check with `HMAC differs from the sidecar record`, naming `accept-edit` for their project, and are re-baselined one by one.
* `replayOwedAudit(projectId)` hands over what one project owes, in a transaction of its own under the project's lock, and returns the number of records handed over; a record the sink refuses again stays owed and is not counted, a refused or failing intent file propagates as it is. Step 2 of the project's recovery calls it (`OwedEnrolmentAuditStep`, see <<recovery>>).
* `replayOwedAuditOfUnenrolledProjects()` is the sweep below for the projects that are no longer enrolled: a project whose enrolment file exists (`store.hasEnrolmentFile`) is skipped, because its recovery hands its own records over; a file without a sidecar is such a project, which the check refuses. Every other project gets its owed records handed over (an unconfirmed `enrolment_removed` as `failed`/`not_confirmed`, logged `PM_MCP-164`) and then the orphan sidecar an interrupted unenrol left removed (`store.removeOrphanSidecar`), so it ends with no file, no sidecar and no intent; when the hand-over throws, the sidecar is left for the next pass. The background pass of the recovery calls it.
* `replayOwedAudit()` is the sweep of the owed records of every project: for every project of `store.auditOwingProjectIds()`, in the order of the ids, it opens a transaction of its own, acquires the project's lock and hands over what the project owes, logging each record `PM_MCP-63`. It returns the number of records handed over, reads no enrolment, creates no key and removes nothing. An intent file of one project that is unreadable or of another format version (`StoreRefusal`), or that cannot be read, rewritten or removed (`UncheckedIOException`), does not stop the replay for the projects after it: the file is kept, the replay goes on, and after the last project the first failure in the order of the project ids is thrown as its own type, every later failure of either type added to it as a suppressed exception; the records of the other projects have been handed over by then and are logged `PM_MCP-63`, but the count of a replay that threw is not returned. Any other failure, a stopped process for one, ends the replay at once. `replayOwedAuditOfUnenrolledProjects()` shares this loop and its failure handling. The operator verbs, which would call the sweep of every project, have no caller yet.

[#audit-records]
=== Audit Records

[cols="1,1,1,2", options="header"]
|===
|Event |Category |Outcome |Details

|`enrolment_tampered` |`security` |`refused` |`project_id`, `reason`
|`enrolment_insecure` |`security` |`refused` |`project_id`, `reason`
|`enrolment_invalid` |`security` |`refused` |`project_id`, `reason`
|`enrolment_written` |`operator` |`succeeded` |`project_id`, `transaction_id`
|`enrolment_removed` |`operator` |`succeeded` |`project_id`, `transaction_id`
|`enrolment_rebaselined` |`operator` |`succeeded` |`project_id`, `transaction_id`
|`enrolment_written`, `enrolment_removed`, `enrolment_rebaselined` |`operator` |`failed` |`project_id`, `transaction_id`, `reason` (`not_confirmed`)
|`unenrol_refused` |`operator` |`refused` |`project_id`, `reason` (`scope_active`)
|===

The `transaction_id` of a succeeded write is the transaction of the write; a record handed over again carries the same one. The `failed` form of the three records is the same write whose completion was not recorded (`AuditEvent.notConfirmed()`); it carries the same `transaction_id` as the `succeeded` form would have, and only one of the two is ever handed over for a transaction. The operator command that resolves a tampered enrolment is named by the refusal, not by its audit record. The names and keys are constants of `AuditEvent`; use the factories, never build an enrolment record by hand.

[#recovery]
== The Recovery
_Requirements: link:../Requirements.adoc#PM-SEC-5[PM-SEC-5], link:../Requirements.adoc#PM-IMPL-7[PM-IMPL-7], link:../Requirements.adoc#PM-ARCH-7[PM-ARCH-7]_

The project's recovery (link:runtime-lifecycle.adoc[Developer Guide § Runtime Lifecycle]) has eleven steps, in the order of `RecoveryStep.Name`; the two enrolment steps come first:

. `EnrolmentIntegrityStep` (`ENROLMENT_INTEGRITY`, constructor `(EnrolmentStore, EnrolmentCheck, LockManager)`) opens a transaction, acquires the project's enrolment lock, settles a stopped write of the pair with `store.recoverPair` and then runs `check.verify` in the same transaction. It reports `Done("enrolment verified")`, with `, a stopped write was settled (<n>)` appended when `recoverPair` reported stopped writes. A `StoreRefusal` is a `Failed` with the message of the refusal, which names the file and the code (the check already logged and audited a tampered, insecure or invalid enrolment; `absent` means the project vanished from the store, a failure too, because only enrolled projects are recovered); a `SecretStoreException` is `Failed("integrity key unavailable: <reason code>")`, never with the key; an `UncheckedIOException` is `Failed("enrolment cannot be read: …")`. An invalid project id and an internal fault propagate, and the recovery records them as a failed step. The step never signs anything and never creates a key. A failed step stops the recovery of that project only.
. `OwedEnrolmentAuditStep` (`OWED_ENROLMENT_AUDIT`, constructor `(Enrolments)`) calls `enrolments.replayOwedAudit(projectId)` and reports `Done("<n> owed audit records handed over")`. A record the sink refuses again stays owed and is not a failure; an intent file that is unreadable, of another format version or cannot be read, rewritten or removed is a `Failed` naming the failure, and the intent is kept.

`OwedEnrolmentAuditStep.unenrolledPass()` is the background pass for an intent whose project is no longer enrolled: a `Runnable` that calls `Enrolments.replayOwedAuditOfUnenrolledProjects()`, which hands over what every project without its enrolment file owes and removes the orphan sidecar an interrupted unenrol left; it catches exactly `StoreRefusal` and `UncheckedIOException` and logs them as `PM_MCP-167` with the exception first; the intent, or the sidecar, of the failing project stays in place, and the other projects are settled all the same. Any other failure, a stop of the sink for one, propagates. The project's recovery does not see a project without its enrolment file, because `EnrolledProjects` lists enrolment files only; the background pass is its route.

`EnrolledProjects.of(store)` is the population of the recovery and the periodic sweep: the ids `store.projectIds()` lists at each call, as a copy; `EnrolledProjects.NONE` stays the seam while no store is given.

`ProjectRecovery.withEnrolment(store, check, enrolments, lockManager, steps, executor)` builds the recovery with the two enrolment steps, `EnrolledProjects.of(store)` and `unenrolledPass()` as the background task; a step of either enrolment name in the given list, such as the seam of a list written before the enrolment store, is replaced by the built one. The constructor `ProjectRecovery(enrolled, steps, executor, backgroundPassTask)` takes a background task, which `startBackgroundPass()` submits once to the executor after it started the recoveries of the enrolled projects; the three-argument constructor submits no task. Every constructor fills a missing `ENROLMENT_INTEGRITY` or `OWED_ENROLMENT_AUDIT` with a seam that does nothing, so a step list written before the enrolment store keeps working, and the enrolment check then does not run; any other missing name is an `IllegalArgumentException` naming it. The assembly does not construct the recovery yet; to run the check it must build it with `withEnrolment` or pass the two steps.

The reporting of a project whose recovery failed, on stderr and in `pm-operator status`, is the assembly's.

[#known-limits]
== Known Limits

* *The check-to-read window is narrowed, not closed.* The JDK has no `fstat` on an open handle, so `EnrolmentFileCheck.snapshot` infers the identity of the opened file from the attributes read before the open and after the read (file key, size, last-modified time). A change between the two attribute reads that leaves the file key, the size and the last-modified time as they were is not seen. The mode of the operator-owned `enrolments/` directory stays the outer boundary: only its owner can replace a file in it. Follow-up: none; the snapshot is as far as the JDK reaches without a handle-based `fstat`.
* *The operator writes do not authorize their caller.* `enrol`, `unenrol` and `rebaseline` neither authenticate their caller nor check that the caller owns the project, because the operator verbs have no caller yet. Follow-up: the package that wires the operator verbs authenticates the caller and authorizes the ownership of the project before it calls `Enrolments`.
* *`unenrol` prevents stranded work only with the help of every producer.* `unenrol` asks `LiveWork` under the project's enrolment lock. That prevents stranding only if every path that creates live work reads the enrolment under the same lock (`LockKey.enrolment`, through `EnrolmentStore.lockKey`, and `EnrolmentCheck.verify` in that transaction); no producer of live work exists yet. Follow-up: the first scope-creation path does it.
* *Only the recovery runs the check.* The verify-not-resolve check of a project's jobs, the `enter` request and the operator verbs must run `EnrolmentCheck.verify` too and do not, because none of these paths exists in the runtime yet. Follow-up: each of them runs the check when it is built.
* *The project root is not checked for uniqueness.* `enrolment_root_conflict` (two enrolments with one `project_root`) and `project_store_root_mismatch` are refused nowhere yet. Follow-up: the operator verb `enrol` and the project's recovery.
* *The policy is not complete.* `EnrolmentPolicy` checks placeholders, write paths and environment names only. The shell-metacharacter set of an argument vector, whether the forbidden free flags (`-D`, `-f`, `--file`, `-s`, `--settings`, `--init-script`) apply to enrolled templates at all (the specification's own example template holds `-DskipTests`), the full list of credential variable patterns (the specification's list ends with an ellipsis) and a write path that is not absolute are open in the specification. The write paths are judged when the enrolment is signed: a symbolic link created later is not seen, and what holds at run time is the Landlock confinement of the job. Follow-up: the specification decides the open points, then the policy implements them.
* *The directories of the enrolment and the key are not protected by the runtime.* `<PM_MCP_BASE>/enrolments/` and `<PM_MCP_BASE>/state/` (which holds the integrity key file) must belong to the operator and be closed to every other identity: the HMAC proves that the runtime wrote a file, but nothing prevents whoever can write the directory from deleting or replacing the pair or the key file. `EnrolmentStore` and `EnrolmentKey` neither create these directories nor check their owner and mode; the per-use checks cover the files only. Follow-up: the installer or assembly that creates the base directory creates both owner-only, and the startup of the runtime refuses a wider mode or a foreign owner.
* *The audit store must drop a replayed duplicate.* Delivery of an owed audit record is at least once: a record handed over again after a stop between the accepted append and the removal of the intent carries the same `transaction_id`, and the design relies on the audit store dropping the duplicate by that id. No audit store exists in this slice, and the `AuditSink` contract used here does not deduplicate. Follow-up: the audit store that implements `AuditSink` drops a record whose `transaction_id` it already holds, and a test of that package proves it.
* *An interrupted `unenrol` is settled later, not at once.* A stop between the removal of the file and of the sidecar leaves an orphan sidecar and the owed record; the background pass of the recovery hands the record over and removes the sidecar after the next start or the next pass, not at the moment of the stop. An orphan sidecar without an owed record is not discovered; it strands nothing, because it is not an enrolment. Follow-up: none.
* *The assembly does not construct the recovery yet.* Without `ProjectRecovery.withEnrolment` or the two enrolment steps, the recovery fills them with seams and runs no check. Follow-up: the assembly in `plan-marshall-mcp` builds the recovery with the enrolment steps.

The follow-ups are listed in the pull request of this slice.

[#pitfalls]
== Pitfalls

* *Unenrol must not strand live work.* An `unenrol` that runs while the project has a non-terminal plan, a non-terminal epic or a running job leaves that work without its enrolment. Ask `LiveWork` under the project's enrolment lock, in the same transaction as the removal, and remove only the file and its sidecar: the project's machine store stays byte for byte. Guarded by `EnrolmentsTest` (a live plan, epic and job each named in the refusal; a permitted `unenrol` leaves `projects/<project_id>/` byte-identical).
* *The gate must not be openable from outside the release.* A gate that a configuration key, an environment variable or an edited enrolment file could open would let a release before Stage 4 create plans everywhere. Keep the position a compiled constant, never read it from configuration, and feed `decide` only verified enrolments. Guarded by `LifecycleGateTest` (the release constant is closed; a non-pilot refused `lifecycle_closed`, a pilot admitted; open position admits both) and `EnrolmentCheckTest` (an enrolment edited to `pilot: true` with a forged size and SHA-256 is refused by its HMAC).
* *Compute the HMAC over the canonical bytes.* Bytes re-serialized by another writer, or read and written through a tolerant parser, differ from the canonical ones, and every check fails. Use `EnrolmentCodec.write` and `EnrolmentHmac.sidecar` together, as `Enrolments.enrol` does.
* *Never read an absent key from an exception.* A key file that is insecure or malformed is a `SecretStoreException`; a caller that turns it into "no key yet" creates a second key and makes every enrolment tampered.
* *Never create a key while enrolment files exist.* A key that is absent while enrolment files exist was lost or lives in the other key source; a new key would strand every enrolment written under the old one and hide the cause. `enrol` refuses instead; only the re-baseline creates the key then. In a keyring the same holds across runtime instances only under the credentials lock, because a keyring write replaces an existing entry. Guarded by `EnrolmentsTest` (a key-source switch in both directions is refused and creates no key; the re-baseline is the way out) and `EnrolmentKeyTest` (two instances write one keyring entry).
* *Never publish a key file with a rename.* A rename replaces an existing key file a racing writer created. Publish with a hard link from a synced temporary file, which fails on an existing file; a keyring has no such primitive, so its entry is read back after the write and the key it holds is adopted. Guarded by `EnrolmentKeyTest` (a racing writer's key is kept; no temporary file remains; a foreign keyring entry written after ours is adopted).
* *Never create the integrity key outside the credentials lock.* Two runtime instances that both read "absent" would each create a key, and the second would strand every HMAC written under the first. `enrol` and the re-baseline acquire `EnrolmentKey.creationLock` before the project's lock; never after it, which is a lock order violation. Guarded by `EnrolmentKeyTest` (the second instance waits while the first is paused inside its create; one keyring write; the lock order) and `EnrolmentsTest`.
* *Never rename the pair one file after the other without staging both.* A stop between two renames of files written one after the other leaves a pair the check refuses, and the operator must accept-edit. Stage the file and the sidecar completely, then rename. Guarded by `EnrolmentStoreTest` (a stop after each step is settled to the old or the new pair, never a half-new one).
* *Sign only what the policy admits.* A template with a foreign placeholder, a write path into the base directory or a credential variable in the build environment must never be blessed by an HMAC. Check the enrolment against `EnrolmentPolicy` before the key is resolved, at `enrol` and at the re-baseline. Guarded by `EnrolmentPolicyTest` and `EnrolmentsTest` (a violation refused as `enrolment_invalid` before a key, an intent or a file exists).
* *Settle a stopped pair before the check.* The check refuses a pair that a stopped write left half new; recovering the pair first completes a write that was staged completely and discards one that was not. Guarded by `EnrolmentIntegrityStepTest` (each stop shape settled, then verified).
* *Settle a stopped pair before you sign over it.* A re-baseline that signs the file in place while a completely staged pair of an earlier stopped write is still on disk is undone by the next recovery or write, which rolls the staged pair forward over the re-baselined one, unreported. The re-baseline calls `recoverPair` under both locks before it snapshots, checks and signs, and its outcome reports what was settled (`Rebaseline.settled`), so the operator is told when the signed bytes are the recovered write rather than the file they reviewed. Guarded by `EnrolmentsTest` (a complete staged pair, a torn staged sidecar and a staged sidecar alone are settled first and reported as `Completed`, `Discarded` and `Completed`, the sidecar and the reported digest describe the settled file, and a following recovery changes nothing).
* *Discover recovery work apart from enrolment eligibility.* A sweep that skips a project because any file of its enrolment exists, the sidecar included, hides the project an interrupted unenrol left: the orphan sidecar is not an enrolment, so the project's recovery never sees it either, and its owed record is never handed over. The listing of the enrolled projects is for trust, the listing of the owed records is for recovery; skip a project only when its enrolment file exists (`hasEnrolmentFile`). Guarded by `EnrolmentsTest` (an interrupted unenrol settled by the background pass and left in place by the sweep of every project, a project with its file left alone, a sidecar that cannot be removed failing only its project) and `OwedEnrolmentAuditStepTest` (`unenrolledPass` on an orphan sidecar).
* *Resolve a write path through its longest existing ancestor.* A check of the whole path alone misses a missing leaf below a symbolic link into the base: the path does not exist, so it has no real path, and its lexical form lies outside. Resolve the longest existing ancestor and append the missing names; refuse a `..` below it and an ancestor that cannot be resolved. Guarded by `EnrolmentPolicyTest` (a missing leaf below a link into the base or below it refused, below a link outside admitted, `..` resolved physically or refused, a dangling link refused) and `EnrolmentsTest` (such a write path refused at `enrol` before anything exists).
* *Cancel staged state at unenrol too.* A first enrolment that was staged completely and stopped has neither a file nor a sidecar, so a check of those two alone finds nothing to remove, and a later recovery or write rolls the enrolment forward although the operator unenrolled it. `unenrol` asks `hasStagedWrite` besides `exists`, removes and audits. Guarded by `EnrolmentsTest` (a staged pair, a staged file and a staged sidecar alone cancelled, audited and not rolled forward by a later recovery) and `EnrolmentStoreTest` (`hasStagedWrite` true for a stopped first enrolment that does not exist yet, false once settled or removed, and isolated from projects whose ids begin alike).
* *An audit append after the mutation can be lost.* A record appended only after the enrolment was written is gone for good when the audit log refuses it or the process stops in between. Owe the record in the project's intent before the mutation and hand it over after it; never catch a refused append and drop the record. Guarded by `EnrolmentStoreTest` (the intent kept through a refused, partial or stopped hand-over and removed only after every record was handed over) and `EnrolmentsTest` (a refused or stopped append leaves the record owed and the replay hands it over once with the same transaction id; a refusal owes nothing).
* *Never owe the success of a mutation nobody redoes.* A record owed as `succeeded` before the mutation is handed over as a success by the next write or the replay even when the mutation failed or the process stopped before it. A recovery completes a roll-forward or a tail repair, so their records come true; an operator write is not completed by anyone. Owe the unconfirmed form (`AuditEvent.notConfirmed()`) and confirm it with `store.confirmAudit` only after the mutation completed. Guarded by `EnrolmentsTest` (a failed `enrol` and a failed `unenrol` keep their record owed as `failed`/`not_confirmed`, and the replay and the next write hand over that record and never a succeeded one), `EnrolmentStoreTest` (`confirmAudit` replaces the record of its transaction in place, keeps the others, owes afresh when none is owed) and `AuditEventTest` (the unconfirmed form).
* *One bad intent file must not stop the replay.* `replayOwedAudit()` runs over every owing project; an intent file that is refused or fails on I/O is kept and reported after the last project, never allowed to leave the loop. Catch exactly `StoreRefusal` and `UncheckedIOException`, so a stop still ends the replay. Guarded by `EnrolmentsTest` (a project whose intent is unreadable, of another version or a directory that cannot be read, ordered before others, does not keep the later projects' records owed; the first failure is thrown as its own type, the later one suppressed in either order; a stopped process still stops the replay).
* *Never check a path and then read it.* A check of a path is not bound to the file that is opened afterwards: between the two, the file can be replaced by a link or by another file, and the bytes read are not the ones checked. Read through `EnrolmentFileCheck.snapshot`, which checks the attributes, reads from one no-follow open and compares the attributes after the read. Guarded by `EnrolmentFileCheckTest` (a link is refused without reading its target; a file replaced, swapped for a link or loosened during the read is refused), `EnrolmentCheckTest` (a symlinked enrolment file is refused although its target is the recorded file) and `EnrolmentsTest` (the re-baseline refuses a symlinked enrolment file and leaves the target and the sidecar byte-identical).
* *One audited path per refusal.* A refusal is logged and audited through `EnrolmentCheck.tampered`, `insecure` or `recorded`, never by a direct `fileCheck.check` that throws past the log and the audit, or a direct `auditSink.append` whose failure replaces the refusal. Guarded by `EnrolmentCheckTest` (every refusal logged and audited, a failing sink suppressed) and `EnrolmentsTest` (the re-baseline's insecure refusal logged and audited and kept against a failing sink; the `scope_active` refusal kept against a failing sink with the failure suppressed).
* *Decide the integrity under the lock.* `EnrolmentStore.projectIds()` is lock-free and only lists; everything a decision rests on goes through `EnrolmentCheck.verify` in a transaction that holds the project's lock.
