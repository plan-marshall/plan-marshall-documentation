== Command-Line Binaries (`pm-mcp`, `pm-operator`) & Installation Layout

[#PM-WATCH-CLI-10]
=== PM-WATCH-CLI-10: Siblings are started by path, never through PATH

Anchor:: link:../specification/cli-and-security/01-cli-and-installer.adoc#installation-layout[CLI & Security § Installation Layout],
link:../Requirements.adoc#PM-DIST-1[PM-DIST-1]
Hazard:: A binary looked up through `PATH` lets any same-named executable earlier on `PATH` run as the runtime, and a
`PM_MCP_HOME` derived from an unresolved symlink points at the user bin directory instead of the installation.
Guard:: Fixture with a `pm-mcpd` and a `pm-exec` earlier on `PATH` that each write a sentinel: neither is ever
started, by `pm-mcp`, by `pm-operator`, or by the runtime, and the started processes are the ones in
`<PM_MCP_HOME>/bin/`; `pm-mcp` and `pm-operator`, each reached through a symlink in a user bin directory (and through
a chain of two symlinks), resolve `PM_MCP_HOME` to the installation directory.
Source:: design review.

[#PM-WATCH-CLI-11]
=== PM-WATCH-CLI-11: An upgrade never mixes releases

Anchor:: link:../specification/cli-and-security/01-cli-and-installer.adoc#installation-layout[CLI & Security § Installation Layout] (Upgrade),
link:../specification/cli-and-security/01-cli-and-installer.adoc#cli-daemon-access[CLI & Security § Runtime Access & On-Demand Start] (Version),
link:../Requirements.adoc#PM-DIST-4[PM-DIST-4]
Hazard:: After the symlink switch the new `pm-operator` installed its bundles against the old runtime, the old installation
directory was removed while the old runtime still started jobs through its own `pm-exec`, or a worker of the old runtime
connected through the new release's relay.
Guard:: Fixture with an old runtime running and the symlinks switched to a new release (the runtime's own upgrade
before its restart, or an upgrade by hand of a layout the runtime does not upgrade): `pm-operator client update` is
refused with the version mismatch and writes nothing; a job the old runtime starts after the switch runs through the old
installation's `pm-exec` until the old runtime has exited; a worker the old runtime starts after the switch gets a composed
MCP configuration whose relay command is the old installation's `pm-mcp` by its absolute path (never a bare `pm-mcp`
resolved through `PATH`, whose symlink names the new release); after its exit the successor (or the next on-demand start) is the new `pm-mcpd`.
Source:: design review.

== Client Bundle Installer (`pm-operator client`)

[#PM-WATCH-CLI-12]
=== PM-WATCH-CLI-12: The installer touches only the elements it owns

Anchor:: link:../specification/cli-and-security/01-cli-and-installer.adoc#client-installer[CLI & Security § Client Bundle Installer],
link:../specification/host-integration/02-bundle-manifest.adoc#_ownership_digest_verification_on_installupdateremove[Client Profiles § Ownership & Digest Verification],
link:../Requirements.adoc#PM-DIST-2[PM-DIST-2]
Hazard:: Ownership recorded per file or per key let `client remove` delete a permission rule the user had authored
with the same value, and let `client update` overwrite a recorded rule the user had edited.
Guard:: Fixture with a user-authored rule identical to a bundle rule before `client install`: it is not recorded as
owned and survives `client remove`; a recorded element edited on disk is listed as modified and left untouched by
`client update` and `client remove` without `--force`; `--force` together with `--yes` is rejected before any write.
Source:: design review.

[#PM-WATCH-CLI-13]
=== PM-WATCH-CLI-13: Weakening an enforcement rule always needs the terminal

Anchor:: link:../specification/cli-and-security/01-cli-and-installer.adoc#client-operator-gate[CLI & Security § Operator Gate for Security-Weakening Changes],
link:../Requirements.adoc#PM-SEC-3[PM-SEC-3]
Hazard:: A change plan that weakened an enforcement rule through a path the gate did not classify (a list move, a
narrowed pattern, an overriding allow rule) was applied under `--yes` from a model-driven shell.
Guard:: Table test over bundle versions that move an `enforcement` rule from `deny` to `allow`, narrow it, and add an
`allow` rule overriding it: each trips the TTY gate, is rejected with `--yes` without a terminal, and applies nothing;
matched control: a change that keeps or strengthens every `enforcement` rule, and a changed `convenience` rule, apply
under `--yes`.
Source:: design review.

== Token-Lane Credential Architecture & OS Keyring Integration

[#PM-WATCH-CLI-28]
=== PM-WATCH-CLI-28: A job token is redacted by value and, after a restart, by its `pmj_` shape

Anchor:: link:../specification/cli-and-security/02-operator-channel.adoc#operator-credential-cli[CLI, Coordination & Security § Operator-Only Credential CLI & Runtime Secret Redaction] (Runtime Secrets),
link:../Requirements.adoc#PM-SEC-6[PM-SEC-6]
Hazard:: A job token registered only by value is no longer known after a runtime restart, because only its SHA-256
survives; a worker that still holds it and echoes it into a log line or an argument leaks it unredacted.
Guard:: Test: a job token minted for a worker is redacted by value from log, audit, and representation output;
after a runtime restart the same token, now unknown by value, is redacted by its `pmj_` shape; the token reaches no
job but the worker's relay (`PM_MCP_JOB_TOKEN`). Matched control: a string that only resembles the shape without the
`pmj_` prefix is not redacted.
Source:: design review.

[#PM-WATCH-CLI-22]
=== PM-WATCH-CLI-22: `pm-operator waive` accepts only what the waivable gate list declares

Anchor:: link:../specification/cli-and-security/02-operator-channel.adoc#operator-channel-isolation[CLI & Security § Operator Channel Isolation] (Waivers)
Hazard:: A waiver verb that forwards its arguments unchecked waives a gate outside the closed list (a security
finding, a footprint guard), raises a budget beyond its compiled hard cap, lands after the gate's fallback was
taken, or revokes a waiver that was already consumed.
Guard:: `waive` with a gate outside the closed waivable grammar or on the non-waivable list (`not_waivable`), with
`--raise` beyond the compiled hard cap (`raise_out_of_range`), for a plan whose fallback was taken or that ended

request consumes and ends it `waived`. No verb `decide`, `authorize-merge`, or `force-gate` exists (closed verb table test).
Source:: design review.

[#PM-WATCH-CLI-24]
=== PM-WATCH-CLI-24: A model-relayed operator action is refused

Anchor:: link:../specification/cli-and-security/02-operator-channel.adoc#operator-channel-isolation[CLI & Security § Operator Channel Isolation],
link:../Requirements.adoc#PM-SEC-3[PM-SEC-3]
Hazard:: The model runs `pm-operator waive` from its shell, or submits an operator choice (an integration
variant, a waiver) as link arguments, and the runtime treats it as the operator's own act; a host deny rule that
names sub-commands misses a verb added later, and one that also matches `pm-mcp` cuts a worker off from its job
relay.
Guard:: Tests: `pm-operator waive`, `unwaive`, and `plan cancel` invoked with an agent environment marker or without a
terminal are refused before any request; every shipped bundle carries one `enforcement` rule that denies the whole
binary `pm-operator` and names no sub-command (rule-matching test per host: every verb of `pm-operator` matches it,
and `pm-mcp serve --job` matches no deny rule); no `pm_do` link accepts a waiver, a cancel, an answer of an operator
wait, or an operator-configuration value (link fuzzing over every catalogued state), and no MCP request is taken as
an operator act; matched control: the same verb from an interactive terminal writes the waiver.
Source:: design review.

== Web Access & Pairing (`pm-operator web`)

[#PM-WATCH-CLI-15]
=== PM-WATCH-CLI-15: A pairing code is a single, short-lived, rate-limited secret

Anchor:: link:../specification/cli-and-security/03-web-server.adoc#web-pairing[CLI & Security § Pairing Protocol],
link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/timeouts/02-runtime-leases-operator-web.adoc#web-access[Timeouts & Budgets § Web Access],
link:../Requirements.adoc#PM-SEC-7[PM-SEC-7]
Hazard:: A pairing code of about 34.5 bits stays guessable when failures are not counted per pairing, when the error
tells an expired code from a wrong one, when it survives a restart, or when it reaches a log.
Guard:: After five failed redemptions the sixth redemption fails even with the right code; a wrong, an expired, a
consumed, and a superseded code each get the identical `400` (`pairing_invalid`) body; a runtime restart invalidates
the open code; a canary code appears in no `audit.jsonl` or `daemon.log` line.
Source:: design review.

[#PM-WATCH-CLI-16]
=== PM-WATCH-CLI-16: A device secret exists only as its hash

Anchor:: link:../specification/cli-and-security/03-web-server.adoc#web-proxy[CLI & Security § API Access & Device Secret] (Logging),
link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/12-machine-stores.adoc#web-access-records[Store Schemas § Web Access Records],
link:../Requirements.adoc#PM-SEC-7[PM-SEC-7]
Hazard:: A bearer secret logged by a request or access logger of the web listener or by an error message, or stored
in clear in the device store, stays valid until revoked and grants operator rights.
Guard:: Pair a device and drive requests, a failing request, and an event stream with a canary `pmw_` secret on the
web listener: the canary is absent from `daemon.log`, `audit.jsonl`, and `state/web-devices.json`, which holds only
its SHA-256.
Source:: design review.

[#PM-WATCH-CLI-17]
=== PM-WATCH-CLI-17: Revocation and idle expiry take effect at once

Anchor:: link:../specification/cli-and-security/03-web-server.adoc#web-devices[CLI & Security § Paired Devices],
link:../Requirements.adoc#PM-SEC-7[PM-SEC-7]
Hazard:: A validity cache in the runtime's web adapter, or an event stream authenticated only on connect, keeps a
revoked device working after the operator removed it.
Guard:: With an open event stream, `pm-operator web devices revoke <id>` ends the device's stream within one event cycle
and its next request is answered `401`; no cache exists to wait out; a device whose `last_used_at` lies 90 days back
(clock fixture) has its streams ended with `stream.closed` (`device_expired`), is answered `401`, and is removed
with `reason: idle_expired`, while one a minute short of it still works.
Source:: design review.

[#PM-WATCH-CLI-18]
=== PM-WATCH-CLI-18: Every web response carries every security header

Anchor:: link:../specification/cli-and-security/03-web-server.adoc#web-security-headers[CLI & Security § Request Validation & Security Headers],
link:../Requirements.adoc#PM-SEC-7[PM-SEC-7]
Hazard:: Headers set by a filter on one route type only leave the error pages, the fallback page, or the event stream
without anti-framing or CSP, and those responses become the framing or injection target.
Guard:: For a static file, the SPA fallback page, API responses of every status the web listener produces (`200`,
`401`, `403`, and `404` among them), and an SSE stream, the `Content-Security-Policy` header equals the specified
value exactly, and `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, and `Referrer-Policy: no-referrer` are
present.
Source:: design review.

[#PM-WATCH-CLI-19]
=== PM-WATCH-CLI-19: Foreign hosts and origins are refused before routing

Anchor:: link:../specification/cli-and-security/03-web-server.adoc#web-security-headers[CLI & Security § Request Validation & Security Headers] (Host validation, No CORS),
link:../Requirements.adoc#PM-SEC-7[PM-SEC-7]
Hazard:: Host validation after routing, or an `Origin` check only on some methods, leaves the runtime's web listener
open to DNS rebinding and cross-site requests carrying a stored device secret.
Guard:: A request with a foreign `Host` on the web listener is answered `403` before routing: a spy records no route
handler invocation and no device-store lookup; a `POST` with a cross-origin `Origin` is answered `403`; no response
of any kind carries an `Access-Control-*` header, and a preflight `OPTIONS` is refused.
Source:: design review.

[#PM-WATCH-CLI-20]
=== PM-WATCH-CLI-20: The runtime checks the device secret on every request, and never takes the runtime token over TCP

Anchor:: link:../specification/cli-and-security/03-web-server.adoc#web-proxy[CLI & Security § API Access & Device Secret] (Device secret, No runtime token),
link:../specification/runtime-model/01-processes-and-transport.adoc#local-api[Runtime Model § Local API],
link:../Requirements.adoc#PM-SEC-7[PM-SEC-7]
Hazard:: A web adapter that checks a device secret once per connection or keeps a validity cache lets a revoked
device through; one that reuses the local adapter's authentication accepts the runtime token on the TCP listener, so
the machine-local secret becomes a network credential with operator rights.
Guard:: A device revoked while its keep-alive connection stays open is rejected on its next request on that
connection; a well-formed but unknown `pmw_` secret is answered `401` (the runtime's audit record shows the refusal);
a request on the web listener carrying the valid runtime token as `Authorization: Bearer`, or a running job's token,
is answered `401` on every `/api/v1/` path; a request without a device secret is answered `401` everywhere under
`/api/v1/` except pairing redemption (`POST /api/v1/pair`); a valid device secret presented on the Unix socket is
answered `401`; matched control: the runtime token on the Unix socket is accepted.
Source:: design review.

[#PM-WATCH-CLI-21]
=== PM-WATCH-CLI-21: A web listener exists only while enabled and never routes `/mcp`

Anchor:: link:../specification/cli-and-security/03-web-server.adoc#web-proxy[CLI & Security § API Access & Device Secret] (Route restriction),
link:../specification/cli-and-security/03-web-server.adoc#web-server-lifecycle[CLI & Security § Lifecycle],
link:../Requirements.adoc#PM-SEC-4[PM-SEC-4], link:../Requirements.adoc#PM-SEC-7[PM-SEC-7]
Hazard:: A second HTTP server that shares the routes of the Unix-socket listener, or a route match before path
normalization (`/api/v1/../../mcp`, `/api/v1/%2e%2e/mcp`, `//mcp`), puts the model's tool surface on a TCP listener; a
listener that is open while `web.enabled` is false, or stays open after `pm-operator web disable`, exposes the
runtime without the operator's decision.
Guard:: Table test on each web listener over `/mcp`, `/mcp/`, encoded, double-encoded, dot-segment, duplicate-slash,
and case variants, and over every path the Unix-socket listener serves outside `/api/v1/`: each is refused with a
valid device secret as with the runtime token, and a spy on the MCP endpoint records zero requests from the TCP
listener; listener test: with `web.enabled` false a `pm-mcpd` whose local adapter runs on the Unix socket holds no
listening TCP socket, across a restart too;
`pm-operator web enable` opens exactly the loopback listener and `web enable --lan` the LAN listener beside it, a
restart reopens each enabled one; `pm-operator web disable` closes both and ends their open streams while `state/web-devices.json`, running plans, and running jobs stay untouched,
and a stream open on the Unix-socket listener keeps delivering across the open and the close.
Source:: design review.
Observation:: The native `WebListenerIT` and `WebListenerTest.shouldServeLanOverTls` failed intermittently with two
symptoms: a `409` on `PUT /api/v1/web`, and the test's TLS client reporting `SSLHandshakeException: Remote host
terminated the handshake`. First measurements, on 8 October 2026 on macOS `arm64`, each run a fresh native daemon, on
a machine that was never idle (load average 10 to 12 from other applications):
+
[cols="3,3,1,1",options="header"]
|===
|Code |Condition |Runs |Failures
|`c293087`, before `pm-runtime` was extracted |no build running |25 |2
|`c293087` |no build running |60 |0
|`9494b84` |no build running |26 |0
|`9494b84` |a native build running in parallel |19 |6
|`9494b84`, with a pause of a few hundred milliseconds before the listener is opened |the same parallel build |17 |0
|===
+
*Cause*, found on 9 October 2026 on the JVM (`WebListenerTest.shouldServeLanOverTls`, one Maven run per test run):
both symptoms come from the port the tests chose and from the listener's bind with address reuse, on macOS.
The tests took their port from `new ServerSocket(0)`. That socket sets `SO_REUSEADDR` and binds the wildcard address,
and for such a bind the kernel hands out a port on which another process already listens on `127.0.0.1` (ports are
handed out in sequence, so the probe meets every such listener the counter passes). The listener bound with address
reuse too, the Vert.x default: in LAN mode its wildcard bind succeeded beside the other listener, and IPv4 loopback
connections went to that listener, which closed them on the TLS ClientHello (symptom two); in loopback mode the bind
of `127.0.0.1` failed (symptom one, a correct `409`). Load raised the rate only through the number of loopback
listeners that other processes open.
+
[cols="4,1,1,2",options="header"]
|===
|Run of `WebListenerTest.shouldServeLanOverTls` (JVM, before the fix) |Runs |Failures |Load average (1 min)
|unchanged test, certificate and key of every run kept |80 |5 |5 to 10
|with `javax.net.debug=ssl:handshake` and Netty at `DEBUG` |60 |1 |4 to 8
|with probes of the port after the test (four loops) |130 |9 |4 to 8
|===
+
*Evidence.* In every failed run the daemon logged one open of the listener and its close after the client had failed.
With TLS debugging the daemon's TLS engine logged nothing after the open, while a passing run shows it consuming the
ClientHello: the connection never reached the daemon. Four further handshakes on the same port after the failure all
failed within 2 to 7 ms: the state lasts for the run and is no race at the open. A plain HTTP request to
`127.0.0.1:<port>` in a failed run was answered by another process (`400`, "This is an explicit proxy server", and
in one run `404` on port 64342, the fixed port of the IDE's local server, where the TLS client reported
`Unrecognized SSL message, plaintext connection?`), while `[::1]:<port>` behaved as the daemon's TLS listener. A
JUnit experiment with a listener held on `127.0.0.1:X` reproduced each step without chance: `ServerSocket(0)` returned
`X` in 5 of 5 passes of the port counter; a Vert.x listener on the wildcard address and `X` with address reuse
bound, and a connection to `127.0.0.1:X` reached the other socket; without address reuse the bind was refused, and so
it was beside a listener on `::1` and on a non-loopback IPv4 or IPv6 address; a Vert.x listener on port `0` was
handed `X` by the kernel in 5 of 5 passes, with and without address reuse.
+
*Refuted.* An invalid certificate or key from the DER encoder of `pm-runtime`: certificate and key of all 15 failed
runs parse, match, and verify with `openssl`, and a test over 2000 generated key pairs in `pm-mcp-core` (`WebTlsTest`)
finds no invalid encoding. A second open or a close of the listener during the handshake: one open per failed run, the
close after the client's failure. The address family of `localhost`: it resolves to `127.0.0.1` first. A certificate
or key left by another test or run, or read while written: every test JVM has a fresh base, and the material is
written before the listener opens.
+
*Fix.* The listener binds without address reuse, so a port held on any local address is `web_listener_conflict`; port
`0` is served by a bounded selection among candidates that are bound explicitly, and the bound port is reported
(link:../specification/cli-and-security/03-web-server.adoc#web-listener-bind[CLI & Security § Listener Exposure]). The
tests open on port `0` and probe no port.
+
*The reverse case, considered and not closed.* While the LAN listener is open, macOS lets a socket of the same user
that sets `SO_REUSEADDR` bind `127.0.0.1`, `::1`, or an address of an interface on the listener's port, whether the
listener set address reuse or not, and that socket then receives the connections to its address; without
`SO_REUSEADDR` the bind is refused. Two remedies were measured or weighed and not taken: (2) the listener holds
`127.0.0.1` and `::1` itself beside the wildcard socket, which refuses the foreign bind on loopback (measured) but
needs address reuse on the listener's own three sockets, a check bind before them, and leaves the addresses of the
interfaces open; (3) no wildcard socket, one socket per address, which serves no address that appears later and is a
redesign. Neither gains anything against a process of the same user, which is no boundary
(link:../specification/cli-and-security/03-web-server.adoc#web-threats[CLI & Security § Threat Notes]). A
characterisation test (`WebListenerTest.characterisesForeignBindBesideOpenLanListener`) records the platform's
behaviour. Not verified: a process of another user.
+
*Verification* of the fix on 9 October 2026, macOS `arm64`:
+
[cols="4,1,1,2",options="header"]
|===
|Run |Runs |Failures |Load average (1 min)
|`WebListenerTest.shouldServeLanOverTls` on the JVM, one Maven run each |100 |0 |7 to 23
|native `WebListenerIT` (three tests), a fresh native daemon each, native builds of `pm-mcpd` running in parallel |20 |0 |38 to 84
|===
+
The three tests with a listener held on `127.0.0.1`, `::1`, and a non-loopback address fail without the fix on macOS
(`200` instead of `409`) and pass with it; on Linux (CI) they pass, since Linux refuses a bind beside a listening
socket with and without address reuse. The characterisation test measured on Linux (CI) that the bind beside the
open LAN listener is refused with and without `SO_REUSEADDR`.
+
*Logging.* The listener logs every request to open it and every close with the cause, and a connection that fails
before its first request (a failed TLS handshake included) as a warning. That warning would not have shown this
defect, since the connection never reached the daemon. The local address the operating system reports for the bound
socket is not logged: Vert.x exposes the bound port, which is logged, and no accessor for the address.

[#PM-WATCH-CLI-26]
=== PM-WATCH-CLI-26: The listener decides what is web-originated, never a header

[#PM-WATCH-CLI-27]
=== PM-WATCH-CLI-27: The route table of the web listener is a closed allowlist
