== Build & Subprocess Execution (PM-EXEC)

[#PM-EXEC-1]
=== PM-EXEC-1: Wrapper-First Execution & Enrolled Host Tools

All project builds and external tool invocations must execute through enrolled repository wrappers, verified by their location, enrolled name, and SHA-256 digest, or cryptographically pinned host binaries.

* The system must execute project builds using the enrolled build wrapper (`mvnw`, `gradlew`, `pw`, or equivalent) located at the root of the plan's worktree.
* The system must require build systems that lack a wrapper concept (such as `npm`) to execute via an explicitly enrolled host tool pinned to its absolute filesystem path and SHA-256 binary digest.
* The system must never search the `PATH` environment variable at job execution time, preventing writable `PATH` directories from shadowing enrolled binaries.
* The system must reject any attempt to invoke an unenrolled toolchain executable.
* The system must validate all build arguments against the enrolled argument schema associated with the wrapper or host tool before spawning the subprocess; this guards against injection through link parameters only.
* The system must pin, together with each wrapper, every repository file that decides which tool runs and with which flags (wrapper jar and properties, `.mvn/maven.config`, `.mvn/jvm.config`, `gradle.properties`), require `distributionSha256Sum` for downloading wrappers, and refuse a build whose pinned files changed since enrolment until the operator re-enrols them.
* The system must start an interpreter-based wrapper (such as `pw`) through its enrolled interpreter, never through the wrapper's shebang.
* The system must run a model job (job kind `llm`, `PM-WF-5`) only through a harness command line the operator enrolled on the machine (in the harness step of the machine's onboarding, `PM-WF-26`, which scans for the executables the profiles name and runs only their version probe before the operator chooses, or by `pm-operator enrol-harness <client>`: absolute path, version probe, and SHA-256 digest recorded in `<PM_MCP_BASE>/harnesses.json`, with the machine's default harness recorded in `machine-config.json`, and nothing else: no credential and no environment value of the harness is captured, stored, or exported, so a harness that is not logged in by its own login simply fails its job; the only handling of a harness login is the copy of the harness's own login file into a worker's per-worker data directory where its client profile declares one, `PM-SEC-5`); because harnesses update themselves, a changed digest or version inside the supported version range of the harness's client profile is accepted and audited (the runtime rewrites the file and its sidecar with the new version and digest), and one outside that range is refused (`harness_version_unsupported`). `harnesses.json` carries its own HMAC sidecar (`PM-EXEC-2`): on a mismatch the runtime refuses the model job before spawn (reason `harness_tampered`) with the `security` audit record `enrolment_tampered`; the refusal counts as a start failure of the role on that harness (`PM-WORK-3`), and the operator's clients offer the harness's enrolment again (`pm-operator enrol-harness <client>`), which shows path, version, and digest and then rewrites the file and its sidecar with the named client only (every other client must be enrolled again); a tampered harness enrolment never pauses a scope and has no `accept-edit` form.

See the link:specification/job-runtime.adoc[Job Runtime Specification] for implementation details.

[#PM-EXEC-2]
=== PM-EXEC-2: Operator Enrolment & Verify-Not-Resolve Contract

Project execution capabilities must be strictly opt-in via operator enrolment, and every job must be verified against enrolment constraints prior to launch.

* The system must enforce a strictly opt-in execution policy, serving a project only after the human operator has enrolled it, in the project's onboarding (`PM-EXT-8`) in either client or by the direct verb `pm-operator enrol`, into its own enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json`, a closed, versioned record of the project root, pinned wrappers (with the files that decide their flags) and host tools, the canonical and discovery command templates, provider verification overrides, enrolled project scripts (with binding, argument schema, and maximum timeout), operator command budgets, write paths, the captured build environment, the container-engine opt-in (`PM-EXEC-4`), and the `pilot` flag (`PM-MIG-1`).
* The system must restrict all enrolment creation and modification operations exclusively to operator acts (`PM-SEC-3`), ensuring enrolment is never reachable from model tool calls or workflow links. The project's onboarding (`PM-EXT-8`) proposes what the enrolment records (the remote, the base branch, the build wrappers with their pinned files, the host tools, the language servers, the project scripts, the build environment) from the checkout only on the operator's consent (`PM-SEC-8`), each probe a confined job, and the operator confirms it; the captured build environment is the operator's login environment as the terminal client sends it, never the runtime's own (`PM-ARCH-1`).
* The system must refuse the unenrolment of a project (an operator act of either client, or `pm-operator unenrol`) while the project has non-terminal plans or epics or running jobs, naming them; an unenrol removes only the enrolment file and its sidecar, records the unenrolment in the per-project machine store `<PM_MCP_BASE>/projects/<project_id>/`, and leaves the store otherwise untouched, to be deleted only by the operator's cleanup (`PM-ARCH-10`); the periodic sweep removes only its technical residue, and `pm-operator sweep [<project_id>] [--machine] [--apply]` lists without `--apply` what the next automatic pass would remove, with its evidence, and with `--apply` runs that pass at once, each removal with one audit record, never offering work history. The per-project machine store records its `project_root`, and enrolling the same `project_id` again reuses the store only for the same root and is refused otherwise (`project_store_root_mismatch`).
* The system must protect the integrity of every enrolment file and of the harness enrolment `<PM_MCP_BASE>/harnesses.json`: every write the runtime performs (on an operator verb, and for `harnesses.json` also on an accepted harness self-update, `PM-EXEC-1`), under the file's own lock, stores an HMAC-SHA-256 over the canonical file content in the file's own sidecar, keyed with a secret held in the OS keyring (`PM-MCP` namespace, operator lane) or, on hosts without a keyring, in a `0600` file under `<PM_MCP_BASE>/state/`; the runtime verifies a project's HMAC before first serving the project after a start and before every verify-not-resolve check, refuses with `enrolment_tampered` and an `audit.jsonl` record on mismatch, and accepts a re-baselining only through the operator CLI. A tampered, insecure, or invalid enrolment file blocks only its own project; `harnesses.json` is verified before every model-job launch, a mismatch blocks only model jobs, and `pm-operator enrol-harness` re-baselines it (`PM-EXEC-1`).
* The system must enforce a verify-not-resolve contract before launching any job (`build`, `git`, `ci`, `project_script`, `llm`): verify that the target directory is the enrolled project root or a live linked worktree thereof (for a `zero_tool` worker, the screener or the judge, and a qualification item that carries corpus context, their empty job-private directory), verify the executable's absolute path and SHA-256 digest against the enrolment record (for a harness, within its version range), and validate the argument vector against the enrolled schema (for a model job, against the server-composed launch of its client profile's template).
* The system must immediately refuse any job that fails enrolment verification and report `status: refused` as a distinct outcome state in the workflow representation, never conflating enrolment refusals with build failures (`failed`).

See the link:specification/job-runtime.adoc[Job Runtime Specification] and link:specification/store-schemas.adoc[Store Schemas Specification] for implementation details.

[#PM-EXEC-3]
=== PM-EXEC-3: Python Interpreter Pinning & Hash Verification

Jobs whose executable runs under a host interpreter (project scripts, `PM-EXT-5`, interpreter-based wrappers such as `pw`, and enrolled host tools that are scripts, such as `asciidoctor`) must be bound to an enrolled interpreter and verified script digests. `PM-MCP` never executes `plan-marshall` scripts (`PM-MIG-2`).

* The system must require every host interpreter (`python3`, and `ruby` for the enrolled host tool `asciidoctor`) used by a `project_script` job, an interpreter-based wrapper, or an enrolled host tool that is a script to be enrolled with its resolved absolute path and SHA-256 binary hash, and must start such a script through its enrolled interpreter, never through its shebang.
* The system must verify both the interpreter's SHA-256 digest and the enrolled script's, wrapper's, or script host tool's SHA-256 digest before executing the job.
* The system must validate every `project_script` job against the project's enrolled script allowlist and its arguments against that script's registered argument schema.
* The system must refuse the job (`status: refused`) if an interpreter update or file modification causes a hash mismatch, requiring the operator to refresh the enrolment before execution can proceed.

See the link:specification/job-runtime.adoc[Job Runtime Specification] for implementation details.

[#PM-EXEC-4]
=== PM-EXEC-4: Direct Host Subprocess Management & Process-Group Isolation

All jobs must run as direct child subprocesses of the daemon in isolated OS process groups with deterministic lifecycle and outcome semantics.

* The system must spawn all job executables (`build`, `git`, `ci`, `project_script`, `llm`) directly via operating system process creation APIs using an explicit argument vector, strictly prohibiting shell interpolation (`sh -c`).
* The system must place every spawned job into its own isolated operating system process group so that cancellation or timeout signals (`SIGTERM` followed by `SIGKILL`) terminate the entire subprocess tree cleanly.
* The system must redirect child standard input (`stdin`) from `/dev/null` by default, or stream an explicit in-memory UTF-8 payload over an OS pipe and immediately close the stream when an operation supplies a `stdin` body.
* The system must enforce an explicit environment variable allowlist and an execution budget for every job, allocated per job type and operation with engine floors that no configuration undercuts.
* The system must let build subprocesses use warm build daemons (Gradle daemon, `mvnd`) only through the project's own daemon store, which the runtime names in the job environment (`<PM_MCP_BASE>/projects/<project_id>/daemons/`), so that a job reaches only daemons started by jobs of its own project under the same confinement and never a daemon of the operator or of another project (`PM-SEC-5`); the declared toolchain caches stay shared.
* The system must give build subprocesses access to the host's container engine (Docker, Docker Compose, Testcontainers) only for a project whose enrolment opts in (`container_engine: docker`, confirmed by the operator at `pm-operator enrol` after being told that such jobs hold the authority of the Docker group, which reaches every host path including `<PM_MCP_BASE>`, and audited); without the opt-in the job environment carries no container variable and the engine's socket path is outside the job's read set, and with it every job of the project records its confinement as `partial(container_engine)` (`PM-SEC-5`).
* The system must classify every completed job using a closed outcome enumeration: `succeeded`, `failed`, `failed_unparsed` (build jobs only), `refused`, `cancelled`, `timed_out`, `killed`, and `indeterminate`, derived by the runtime from its own evidence (refusal before spawn, the signal it sent and why, exit status or terminating signal, and log parse), never adopted from a status the job reports about itself.
* The system must mark any job interrupted by an external signal or daemon crash as `killed` and must never automatically retry `killed` jobs without explicit workflow transition logic.
* The system must never fold `indeterminate` outcomes into `succeeded` or `failed`, and must emit zero located code errors or findings for `timed_out`, `killed`, or `indeterminate` jobs.

See the link:specification/job-runtime.adoc[Job Runtime Specification] and link:specification/timeouts.adoc[Timeouts & Budgets Specification] for implementation details.

[#PM-EXEC-5]
=== PM-EXEC-5: Git & Provider Operations: Native and CLI Variants

All version control and CI provider operations must execute through one contract per operation (typed input, closed outcome enumeration), served by the project's integration variant: the native in-process implementation acting with an agent identity, or verified jobs of the host's enrolled `git` and official CI command-line tools acting with the operator's identity.

* The system must serve each integration (`git`, `github`, `gitlab`, `forgejo`) of a project with exactly one variant (`native` or `cli`), settled during project setup from the machine's provider defaults unless the project sets its own: the CLI variant where the integration's host tool is enrolled (once for the machine in `<PM_MCP_BASE>/host-tools.json`, or for the project), the native variant where not, and the operator's stored choice where the operator wants the other identity to act or the variant pinned; the choice is an operator wait of the setup or an operator act, never taken by a model or a content answer (`PM-SEC-3`, `PM-WF-12`), and it is required when the effective variant cannot serve the repository (a native variant facing a feature the derived `git_native_capability` reports). Different integrations may use different variants, one integration never mixes them, no git or provider operation of an integration runs while it has no valid variant (refusal `integration_variant_unset`), the variant is fixed for a running plan by its configuration snapshot and changes only through a setup run that reports and audits the change, and no operation falls back from one variant to the other.
* The system must execute native-variant operations in process (git through JGit over HTTPS only, GitHub, GitLab, and Forgejo (Codeberg and every Forgejo or Gitea forge) through `PM-MCP`'s own REST and GraphQL clients), authenticated with the Token Lane agent credential (`PM-CRED-1`), without starting any process (`PM-SEC-5`); a repository the native variant cannot serve (repository hooks, commit signing, filter drivers including LFS, submodules, SHA-256 object format, partial clone, sparse checkout, split index, per-worktree configuration (`extensions.worktreeConfig`), a remote reachable only over SSH) is refused with `capability_missing` naming the feature and the operator command that enrols the host tool, which selects the CLI variant.
* The system must execute CLI-variant git operations (status, log, diff, file-footprint capture, commit, push, fetch, merge, rebase, and worktree lifecycle) as verified `git` jobs invoking the host's enrolled `git` binary, preserving the developer's git configuration, credential helpers (except a helper or CLI login that works only over the user's session bus, which no job reaches, `PM-SEC-5`), SSH agent, commit signing, and repository hooks, and CLI-variant CI provider operations (pull/merge request management, check inspection by pull request or by commit SHA, review comment retrieval, issue reads and comments, and merges) as verified `ci` jobs invoking the provider's official CLI (`gh`, `glab`) under the developer's existing CLI authentication, by design and audited as `identity: operator_ambient`.
* The system must classify a provider's refusal of a requested operation (an HTTP `4xx` answer that carries a reason, other than an authentication or permission failure) as a domain outcome of the operation (its own refusal outcome where it has one, otherwise `rejected` with the provider's reason), never as a failure of the operation.
* The system must serve the organisation and foreign-repository reads of the CI provider contract (the repository list of an organisation or group, code search in an organisation or group, a file read from a repository outside the project, the label list of such a repository, and an issue or a pull request of another repository named as a source) only under an operator cross-project grant naming that organisation, group, or repository (`PM-SEC-2`), and must report with every result whether it is complete or which bound (pagination cap, provider result cap, repositories the credential cannot see) made it incomplete. A read the forge refuses for its rate limit fails with the cause `rate_limited` and the time the limit resets, and is not retried by itself.
* The system must post to an issue (`ci.issue-comment`) only for an issue of the project's own repository and only where the team configuration enables writing back (`issues.write_back`, off by default).
* The system must compose all `git` and `ci` argument vectors server-side from a closed set of operations, requesting structured JSON output (`--json`) where supported and prohibiting model-supplied CLI flags.
* The system must stream multi-line or model-authored text payloads (commit messages, pull-request bodies, issue bodies, review comments) of CLI-variant jobs exclusively in memory via standard input (`stdin` flags such as `git commit -F -`, `gh pr create --body-file -`, `gh pr comment --body-file -`), and pass them in native-variant operations only as in-memory request payloads, strictly prohibiting both command-line argument interpolation and temporary/scratch files on disk (such as `plan-marshall`'s `.plan/temp/` and `work/ci-bodies/`, or `/tmp/`).
* The system must produce identical commit metadata in both variants: the author from the operator's commit identity, the committer resolved from the agent credential (`PM-CRED-1`), and the commit trailer; the CLI variant sets them through `-c user.name`/`-c user.email` and `GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL`.

See the link:specification/module-structure.adoc[Module Structure Specification] and link:specification/job-runtime.adoc[Job Runtime Specification] for implementation details.

[#PM-EXEC-6]
=== PM-EXEC-6: Adaptive Build Timeouts, Coverage Parsing & Gate Honesty

Build execution must adapt timeouts from observed job durations, parse coverage reports natively, and verify that executed builds cover the full scope required by quality gates.

* The system must compute adaptive job budgets per canonical command from a max-biased learned baseline of observed durations, never below per-engine floors matching `plan-marshall`, fed by every finished run regardless of exit code; a `timed_out` run is a non-finish that never feeds the baseline but raises a one-shot escalation budget for the next run of that command that never lowers the budget, a finished run poisoned by build residue is not blended while clean observations exist, and `killed`/`cancelled` runs never feed it. An operator budget may exceed the escalation cap but never undercuts the engine floors. Formulas, floors, and caps are defined only in the link:specification/timeouts/01-job-budgets-and-waits.adoc#job-budgets[Timeouts & Budgets Specification].
* The system must apply the same budget model (operation classes with engine floors, learning, escalation, no-verdict rule) to git and provider operations whether they run as jobs of the CLI variant or in-process in the native variant; an in-process operation must be cancelled cooperatively at budget expiry, bound every HTTP request by a compiled connect and read timeout, discard its partial result, and get a job record without process fields.
* The system must record for every job budget how it was derived (`learned`, `escalated`, `operator`, or `floor_default`) in the job record and show it in `pm-operator status`, never in a model-facing representation; every `timed_out` job, whatever the derivation, is a no-verdict outcome that never fails a gate and counts as `no_verdict` in every roll-up, and the derivation only selects the retry it offers.
* The system must include native coverage report parsers (JaCoCo XML, Cobertura XML, LCOV, and Istanbul JSON) to enforce per-module and whole-tree coverage thresholds without external Python scripts.
* The system must enforce gate honesty checks (`examined_population`, `gate_coverage`, and test-scope divergence detection) so a quality gate passes only when the build actually compiled and tested the modules affected by the plan's realized file footprint.
* The system must separate a plan's own gate failures from failures already present on its base: a failing whole-tree gate is re-run on the plan's merge base in a scratch worktree (one detached worktree per plan and merge base, reused while the merge base is unchanged and removed with the plan's finalize, archive, or abort), diagnostics present on both sides are baseline (coverage shortfalls in modules whose main sources the plan did not change are non-blocking `baseline_debt`), a gate red only through baseline diagnostics yields `baseline_red`, a server rule without an operator decision: the server writes a `baseline_red` build row into the change ledger bound to the `worktree_sha`, the merge base, and the digest of the baseline diagnostics, the build-freshness gate accepts that row only for the same `worktree_sha`, the gate's step completes `done` with `assurance_verdict: degraded`, and the pull-request body and the landing record list the baseline failures; the plan never remediates them, and only a red that is not provably baseline-only calls the build or CI remediation policy (`PM-WF-7`). For a CI check, the provider's result of the same check on the base (the merge base, or the latest base-branch commit containing it) with the same failure fingerprints is the primary proof, and the local merge-base run is only the fallback for local gates or when no provider result exists.
