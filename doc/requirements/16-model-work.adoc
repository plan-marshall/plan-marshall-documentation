== Model Work: Roles, Tasks & Workers (PM-WORK)

[#PM-WORK-1]
=== PM-WORK-1: Roles as Configuration

Every piece of model work is done by a worker of a role, and a role is a configuration artifact, never code: the server knows no fixed role, and one abstract model caller acts on whatever the role's effective configuration says.

* The system must define every role by exactly one artifact (a JSON document with a closed schema and `format_version`) holding its description, its class (`writer`, `read_only`, or `zero_tool`), which bounds the tools it may have, and its exact tool set within that bound (the PM-MCP tools and the harness tools by their per-harness names, never a pattern), the harness, model, and effort it runs on, its form (`warm`: a supervised worker that takes task after task; `fresh`: one worker per task), how many of its workers run at once, its skills (compiled skills or extension skills, `PM-SKILL-5`; the role skill being its contract, `PM-SKILL-4`), its recycling rules (idle wake-ups, token budget, tasks per generation, `PM-WORK-3`), optionally the context budget of its workers, from which the per-envelope packing budget is derived (`PM-WF-14`; absent, the harness's fallback in its client profile applies), and the thresholds and actions of the off-track signals of its workers (`PM-WORK-7`).
* The roles that exist must be exactly the artifacts present in the effective role set: the shipped default set compiled into the release, overridden by the operator's machine set (`<PM_MCP_BASE>/roles/`) and the operator's per-project set (`<PM_MCP_BASE>/projects/<project_id>/roles/`), each artifact replacing the artifact of the same name in a lower set as a whole. The harness, model, and effort a role runs on are the effective values of one resolution order: the shipped artifact, the machine artifact, the machine's role assignment (`<PM_MCP_BASE>/role-assignments.json`, per role only `harness`, `model`, and `effort`), the project artifact, the project's role assignment (`<PM_MCP_BASE>/projects/<project_id>/role-assignments.json`), and the plan's override (`PM-WF-25`); an assignment or an override changes only these three fields of the artifact it lands on, and a role it does not name keeps the value of the level below. The operator writes the assignments in either client and may still write whole artifacts. Role artifacts, assignments, and overrides are operator files (`PM-EXT-6`): the system must never read a role, a harness, or a model pin from git-tracked configuration.
* The system must keep the models the operator allows per enrolled harness in a model catalogue of the machine (`<PM_MCP_BASE>/model-catalogue.json`, each model with its source, the harness's models probe or the operator, and the time it was recorded), which a project's own catalogue (`<PM_MCP_BASE>/projects/<project_id>/model-catalogue.json`), chosen from the models the enrolled harnesses offer, replaces for that project.
* The system must let workflow units name roles freely by name (the role-name grammar of the identifier registry) and must refuse to compose a plan instance or an epic workflow that names a role the effective set does not define, with `role_undefined` naming the role and the state, at composition, never when the state is reached (`PM-IMPL-5`). Every entity kind declares the role class its tasks require (a task envelope `writer`, the screener's kind and the judge's grading kind `zero_tool`, every other kind `writer` or `read_only` as its work needs), and a consulted role must not be `zero_tool`; the system must refuse a named role whose class does not fit its use with `class_mismatch`, at composition and again at task creation, where a role an edit made unfit closes its task without an attempt.
* The system must validate every artifact on load against its schema and against the client profile of its harness (`PM-CLIENT-2`): a harness that is not eligible as a worker host, lacks a capability the role's class needs, or does not accept a restricted tool set with the named model makes the artifact invalid, and so does a skill it names that does not resolve in the project's skill catalogue (`PM-SKILL-5`) and an effective model the effective catalogue (the project's, else the machine's) does not allow on its harness (`model_not_allowed`), reported to the operator with the reason; an invalid artifact counts as undefined. An override passes the same validation when the operator sets it.
* The system must run every model step of a workflow through a single model caller that reads the effective configuration of the role the state names and acts on it (a task for a warm worker of the role, or a fresh worker for the task), so that changing, adding, or moving a role to another harness is an edit of the role set or of an assignment, with its contract in an extension skill where no compiled role skill fits (`PM-SKILL-5`), and never a code change.
* The shipped default set must define every role the default workflow units name, among them the two quorum roles the quorum declarations of the shipped adjudication unit list (`PM-WF-18`), `quorum-a` and `quorum-b`, each on a model that accepts a restricted tool set and differs from the other's, so a quorum brings other models into a decision; the `zero_tool` role `judge` that grades the answers of role qualification; the `read_only` role `interpret` that interprets the operator's own words in a decision, qualified on its corpus topic `own_words`; and the `read_only` role `steward` that advises the operator on the machine's models and role assignment by a recommendation with its rationale, a departure from the default assignment with its reason and never a choice, which runs on the machine's default harness with the model its profile maps to the tier `standard`, outside the model catalogue (`model_not_allowed` never applies to it). `judge` and `steward` are exempt from qualification (`PM-WORK-6`). A listed quorum role whose harness is not yet eligible as a worker host is unavailable, and its quorum delivers its decision to the operator as an operator wait. The planning roles take the operator's chat tasks (`PM-WF-24`): `replan` for a plan, `decompose` for an epic, its decomposition, and its review, and `refine` for a plan's entry.
* The release must ship a default assignment per role: a model tier from a closed list, an effort, a preferred harness, and an advisory (what the role does, what it needs from a model, why this tier, and what is lost with a cheaper one), shown wherever a role's assignment is shown or changed and kept beside a value the operator changed. It must resolve on any machine without a model's advice, to the preferred harness when it is enrolled, else to the first enrolled harness that runs the role's class, and to the model the harness's profile maps the tier to when the catalogue allows it. The shipped set must run every role `fresh` except where a qualification record shows the warm form within its allowed gap (`PM-WORK-6`); its pinned configuration of every role, the quorum roles included, is the tier's model on the preferred harness: the configuration that passed its grading against the corpus before the release, or, for a role none of whose candidate configurations meets the level, its best-measured candidate (lower cost breaking ties), shipped unqualified with its record and graded again on the machine. A tier resolved to another model or harness carries no shipped qualification record and is graded like a changed assignment. The release must ship the qualification records of its pinned configurations and the calibration of its unit's quorum declarations, which the project setup grades again at install (`PM-WORK-6`), and calibrate the default assignment per release from the qualification records, its advisory naming the evidence.

[#PM-WORK-2]
=== PM-WORK-2: Task Protocol

A worker gets its work as tasks through one protocol: it waits, is offered a task, acknowledges it, executes it along the task's links, and submits a result. Every transition of the protocol is server logic; the model only follows the links it is offered.

* The system must turn every model step into a persisted task of the role the state names, queued per project and role, and must serve it to a worker of that role through the task protocol, a reusable sub-workflow of the workflow DSL compiled into the binary (`PM-IMPL-5`).
* A warm worker must receive tasks only as the answer to its pending wait call (`pm_wait`, `PM-TOOL-1`), which the server holds for at most the bounded wait of the worker's host with progress frames where the host needs them (`PM-IMPL-4`), and answers with a task, with "wait again", or with "end"; a fresh worker's one task is leased to its generation at spawn and offered in its launch prompt (`PM-SKILL-4`).
* A queued task must be offered only to a generation of its role started with the role's current configuration; a generation started with an outdated configuration gets no new offer and is recycled, and the configuration each attempt actually used is recorded with the attempt. An offer must lease the task to the worker's current generation and carry the skills the task requires that this generation has not yet received (`PM-SKILL-4`), its task identifiers first and, where the answer would exceed the per-tool-result limit of the worker's harness, the remaining content as resource reads below that limit (`PM-CLIENT-2`); a leased task must never be offered to a second concurrent wait of the same generation.
* The worker must acknowledge an offered task within the acknowledgement deadline of its host (`PM-CLIENT-2`), where a host's profile marks the acknowledgement informational, silence alone decides (`PM-WORK-3`).
* The worker must execute the task only along the links of the task's entity representation, and must deliver its result only through a submit link of that entity; the server must validate every submit against the link's closed schema (a submit that misses a required reference is refused with a reason the worker can act on), against the lease, and against the generation, and must refuse every call of a fenced generation with `generation_fenced`.
* A task must end only in one of its closed outcomes, recorded on the task: `submitted`, `asked` (a question record after which the task did not continue, `PM-WF-12`), `infeasible` (with its evidence), or `lost` (the worker was ended while holding it, or the task could not be served: its re-offers spent, its role undefined, of a class that does not fit, unqualified, or unavailable, or the task withdrawn because its state or scope ended, with the reason recorded); a task withdrawn by the operator's pause of its plan at once is not lost and is offered again when the operator starts the plan; a worker never ends a plan, though a decision it submits may select the state's fallback.
* A task whose worker asks a question must continue after the answer instead of being started again, where its state, its role, and the measured capability of its harness allow it (*resumability*): the worker holds its task until the answer within the role's hold limit, or ends with its harness session stored and a resumed session continues it within the role's resume window; otherwise, or when the limit passes or the resume is refused, the task ends `asked` and its work continues in a new task that carries the answer. The server, never the model, chooses the form; a worker must acknowledge a delivered answer within its host's acknowledgement deadline, and a missing acknowledgement ends it as lost. A harness's resumability must be measured by its profile verification before any role uses it (`PM-CLIENT-2`).
* When a worker is replaced, the server must release its lease at once and offer the task to the successor exactly once; the successor starts with an empty context, and nothing is handed over, because every task carries what its state needs.
* A task that ends without its required submission must be offered again within the compiled self-remedy budget of its state, after which the state takes its conservative fallback (`PM-WORK-6`); the task count, the attempts, and the generation of every attempt are recorded.

[#PM-WORK-3]
=== PM-WORK-3: Supervision & Recycling

Neither the transport nor the model reports that a worker is lost or about to give up; the server must detect it itself, end the worker, and replace it, and must recycle workers before they give up or their context grows too large.

* The system must run a supervisor per project and role that keeps a worker available for every queued task within the role's count and the machine's model slots (`PM-WF-14`), starting fresh workers per task and warm workers while the role has work.
* The supervisor must end a worker on any of these signals: its process exits without the server's instruction; no acknowledgement within its host's deadline after an offer (where the acknowledgement is not informational); silence, no open wait call and no other call for longer than the bounded wait plus the host's silence grace. A `zero_tool` worker has no connection: none of these signals and no start-failure count applies to it, and its exit and its budget alone decide its task. A live worker that makes no progress is noticed by the off-track signals of `PM-WORK-7`.
* The supervisor must recycle a warm worker after the idle wake-ups of its host without a task (lowered, never raised, by its role's `recycling.idle_wakeups`) and when its context, taken from the harness's per-turn usage, reaches the token budget of its role; a generation serves at least one task before the budget can recycle it.
* Ending a worker must be `SIGTERM`, then `SIGKILL` after the termination grace, then the fence: its job token is revoked, its generation fenced, and its lease released at once (`PM-WORK-2`); a successor is started when work remains. A terminated worker's usage is recorded as `unmeasured`.
* The supervisor must treat a worker that exits before its first call as a start failure, not as a lost worker; after a compiled number of consecutive start failures of a role on a harness it must stop starting workers there, report the harness's own error text (for example an account usage limit) to the operator in both clients and the audit log, and let the role's waiting tasks take their conservative fallback (`PM-WORK-6`).
* The per-host values (bounded wait, progress, acknowledgement deadline and whether it is informational, silence grace, idle wake-ups) must come from the client profile of the worker's harness (`PM-CLIENT-2`); the token budget and the recycling rules from the role's artifact.

[#PM-WORK-4]
=== PM-WORK-4: Consultation through the Server

A worker that needs another model's judgment must ask through the server, and only where the workflow provides for it, so that the flow stays deterministic, accounted, and within the single-level leaf constraint.

* A consultation must be declared by the workflow, never by a role: a model state declares the consultations it offers, each by a role name (DSL `consult role <role>`, for example `consult role triage-review`), and the server resolves the name in the effective role set like every other role name, refusing a unit that names an undefined role at composition (`role_undefined`, `PM-WORK-1`). A role artifact holds no consultation setting.
* The system must offer a worker exactly the consultation links its task's state declares, one per declared role and no other; following one submits a question and moves the asking task to the state `consulting`.
* The server must run a consultation as a task of the consulted role like any other task, and must deliver the answer as the answer to the asker's next wait, exactly once and only to the asking generation; a consultation of a fenced asker is answered to the successor's task facts instead.
* The asker must wait within its bounded wait with progress frames where its host needs them; its final submit must refer to the consultation, and a submit that omits the reference is refused.
* A consulted task must offer no consultation link of its own (consultation depth one), and no worker may start a model itself (`PM-WF-5`).
* The usage of a consultation must be accounted to the consulted role's task and linked to the asking task.

[#PM-WORK-6]
=== PM-WORK-6: Role Qualification

A role must run only on a configuration whose judgment has been shown to meet the operator's level; until one does, its tasks take a conservative server fallback, never a question to the operator.

* The system must run a role only on a configuration that has a valid qualification record, bound to the configuration's qualification digest over exactly the graded members, taken from the role's effective values (`PM-WORK-1`): the harness with its major and minor version, the model, the effort, the tool set, the class, and the skill digests, so that a changed assignment or override makes the record stale like a changed artifact; the other members of the role artifact never invalidate a record. A record is valid when the role's topics of the model verification corpus (the items whose `role` field names the role, plus, for `writer` and `read_only` roles, the generic `worker` items, each with review status `draft` or `confirmed`) were answered at or above the operator's current agreement level, and, for the warm form, within the operator's current allowed gap to the fresh form of the same configuration; the record stores the measurements, never a pass flag, so a changed level applies to every record at once; a warm role whose fresh form qualifies but whose warm form does not runs fresh, recorded as `form_downgraded`.
* The operator must be able to grade a role's configuration through the operator CLI (`pm-operator roles qualify <role>`), which runs the role's corpus topics as model jobs of that configuration, warm and fresh (a `zero_tool` role fresh only), has every answer graded by a task of the `judge` role through the model caller (`PM-WORK-1`), never by the graded model or a sibling of it (a `judge` configuration on either refuses the grading with `scorer_not_independent`), and records per item the answer, the agreement level, the warm-fresh gap, the tokens used, and the time; an item whose grading task is lost stays ungraded, a record with an ungraded item qualifies no form until that item is graded, and the record is bound to the configuration's qualification digest and the corpus revision.
* The system must invalidate a qualification record when a member of its qualification digest (the harness or its major or minor version, the model, the effort, the tool set, the class, or a skill digest) or the corpus revision changes, and report the role as unqualified to the operator until it is graded again.
* The system must treat the shipped qualification records as a starting point graded on the release's own harness versions: every project setup run, the first run and every reconcile run alike, must offer to grade each role of the effective set that has no valid record for its qualification digest on the machine's harness versions, so a record the machine's harness versions or a change invalidated is graded again, showing the expected tokens first and grading only on the operator's consent (`PM-EXT-8`); a declined grading is recorded as owed and its roles stay unqualified. Grading runs model jobs through the model slots, and the operator must be able to exclude a role from it, which then stays unqualified, and to exclude the calibration of the quorum declarations by a setting of its own, never by a role name.
* The `judge` and `steward` roles must be exempt from qualification: the model caller takes their tasks without the qualification check; the judge's independence from the graded model is its validation, and what the steward submits is a recommendation the operator confirms, never a choice.
* A plan's override to a configuration without a current qualification record must be shown to the operator as unqualified when it is set, and its tasks take the conservative fallback below until the project grades it.
* While a role is unqualified, the system must route its tasks to the conservative fallback of their state: the server takes `retry` once where the state's remedies include it, and otherwise, or after it, the remediation policy's `exhausted` outcome or the state's declared fallback; the task is recorded with the reason `role_unqualified`, and no task is routed to the operator.
* The release must ship the model verification corpus and the qualification records of its default role set (`PM-WORK-1`), and the build must validate every corpus item against its schema.
* The operator must be able to calibrate every quorum declaration that the project's adjudication unit or the binary's default unit uses (its decision kind, its listed roles with the qualification digests of their configurations, and its score) through the operator CLI (`pm-operator roles qualify --decisions`): the corpus items of closed decisions of its kind are run through the adjudication's decision rule with tasks of the listed roles, and one calibration record per declaration (identical declarations share one) stores the items graded, the share the declaration would decide automatically, and the share of those that disagree with the item's reference (false automatic decisions), bound to the declaration's digest and the corpus revision; a quorum declaration decides only while its false automatic share stays at or below the level the adjudication unit declares, otherwise its questions are delivered to the operator as operator waits, and the operator sees the calibration in `pm-operator roles show` and the web app. The shipped quorum declarations are the configuration that passed this calibration on the release's corpus.
* The corpus must grow from real plans: the operator exports judgment decisions with the decision finally taken as draft items (`PM-WF-19`), reviews them, and adds the ones worth keeping; an exported item counts towards a role's topics like every draft item once it is in the corpus.

[#PM-WORK-7]
=== PM-WORK-7: Worker Activity & Off-Track Signals

The operator must see what a worker does while it does it, and the server must notice a live worker that makes no progress, without a model judging it and without ever ending a plan for it.

* The system must map the output stream of every worker, through the client profile of its harness (`PM-CLIENT-2`), onto one closed, harness-neutral list of activity kinds (`text`, cut to a bound; `tool_call`, the tool's name and its target, never its whole arguments; `tool_result`, its size and whether it failed, never its content; `file_changed`; `turn`, with its usage), add what the server knows itself (the links the worker followed, the questions it asked, its answer acknowledgement), and never scrape a terminal or read a harness's session transcript; for a harness whose output gives no event stream only the server's entries are kept, and a line that matches no mapping is counted, not shown.
* The system must keep per task an append-only activity journal in the plan's store, written while the worker runs, masked like every job log before it is written, bounded per task (the oldest text entries giving way first, never a server entry), and archived and deleted with the plan, and must serve it with a live stream to both clients of the operator; its texts and targets are untrusted data, shown as plain text and never read by a model as instructions (`PM-SEC-1`).
* The system must compute off-track signals from the activity journal and the task's records, never by a model, each with a compiled threshold that a role artifact may lower and never raise: `repeating` (the same tool call with the same target a number of times in a row), `no_progress` (a number of turns without a link of the task followed), `over_size` (the tokens spent on the current plan task above a multiple of its predicted size), and `outside_footprint` (unplanned changes already recorded). A signal is no limit: it never ends a plan.
* The system must take, per signal, the action the role artifact chooses from a closed list: `show` (the default: the task and the plan say so), `nudge` (the worker's next tool result carries a server note naming the signal), `yield` (the attempt ends at the worker's next call and the remaining plan tasks go to the next envelope task), or `restart` (the worker is ended and its task offered again within its re-offer budget); every action is recorded in the activity journal and on the task with its signal, a `yield` or `restart` is reported to the operator (`PM-WF-21`), and no signal becomes a decision or waits for the operator.
