== Domain Extensions, Architecture & Recipes (PM-EXT)

[#PM-EXT-1]
=== PM-EXT-1: Four-Axis Domain Descriptors (Axes A–D)

In `plan-marshall`, domain bundles supply runtime Python classes (`extension.py`) loaded via `importlib`. Because `pm-mcpd` compiles to a closed-world GraalVM native binary (`PM-TECH-3`), domain extensions must be modeled as compiled sealed Java interfaces and declarative domain descriptors across four orthogonal axes (preserving `plan-marshall` ADR-004 and ADR-013).

* The system must define sealed Java interfaces and declarative domain descriptors partitioning domain responsibilities across four orthogonal axes:
** *Axis A (Skill Loading, Profile Mapping & Module Applicability)*: Maps domain profiles (`core`, `implementation`, `module_testing`, `integration_testing`, `quality`, `documentation`, `security`), triage (`skill://pm/triage/<domain>`), and outline guidance to static vocabulary skills (`skill://pm/domain/<domain>/<topic>`), and evaluates declarative module applicability rules (`applies_to_module` predicates over build system, packaging, dependency coordinates, module path, and file existence; AND within a rule, OR across rules) that decide which domains apply to a module. Each profile carries `defaults` and `optionals` skill lists, the `core` profile is merged into every profile, and an additive domain names the parent domain it extends (`additive_to`).
** *Axis B (File-to-Build Classification)*: Owned by build-system extensions (`maven`, `gradle`, `npm`, `pyproject`), never by language or content domains (`plan-marshall` ADR-004): declares explicit `(glob, role)` routes and classifies changed file paths into `(role, build_class)` build-map routes that resolve to canonical build verification commands.
** *Axis C (Module Dependency Edge Derivation)*: Derives inter-module dependency edges from build descriptors (Maven POM, Gradle, `package.json`, `pyproject.toml`), documentation cross-references, and warm LSP symbol queries.
** *Axis D (Path Attribution)*: Claims ownership over repository path prefixes (`claim_paths`, such as `.marshall/` or container directories) using constant prefix declarations.
* The system must never dynamically load arbitrary in-process Python or JVM bytecode from project or plugin directories at runtime.
* The system must keep the domain-detection glob dialect (Axis A) and the build-map `fnmatch` dialect separate so existing module routing behavior is preserved identically.
* The system must serve the AsciiDoc checks of the `documentation` domain as compiled domain verbs, never as scripts: `asciidoc.validate` runs the enrolled host tool `asciidoctor` through its enrolled interpreter as a confined job and parses its diagnostics into findings (ending `capability_missing` with the enrolment command when the tool is not enrolled), `asciidoc.verify-links` checks cross references, anchors, attribute references, and file links in compiled code, and `asciidoc.format` applies the compiled house rules as a job that writes the worktree; tone and content are judged only by a task of a review role.

See the link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/domain-extensions.adoc[Domain Extensions Specification] for implementation details.

[#PM-EXT-2]
=== PM-EXT-2: Provenance-Preserving Edge Derivation & Path Attribution Merges

When multiple domain resolvers contribute module dependency edges or path-prefix claims across a repository, the server must merge their outputs deterministically while preserving provenance and rejecting conflicting ownership claims (preserving `plan-marshall` ADR-014).

* The system must merge Axis C dependency edges across all active resolvers by set union while recording the contributing resolver provenance on every edge (`_derivation_merge`).
* The system must merge Axis D path-prefix claims (`_path_attribution_merge`) and resolve file ownership by longest-prefix match.
* When two domains claim the same normalized path prefix for different modules, the system must attribute no owner to that prefix (never an iteration-order winner) and report the collision as a provenance-carrying diagnostic; identical claims (same prefix, same module) must merge with combined producer provenance.
* Neither merge may throw or abort on a producer's output: every dropped edge or claim (self-edge, unknown module, malformed candidate, root-level or repository-escaping prefix) must be reported as a note on the producing resolver's or attributor's report, and a failing producer must be reported with an error status while its siblings still contribute. A second producer registered under an already-registered resolver or attributor ID must be dropped with a note (the first registration wins).

See the link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/domain-extensions.adoc[Domain Extensions Specification] for implementation details.

[#PM-EXT-3]
=== PM-EXT-3: Module Discovery, Build Map & Architecture Enrichment

Project setup, module discovery, verification derivation, and architectural enrichment must be managed as server-owned resources and state transitions rather than prose-driven wizard scripts.

* The system must discover project modules deterministically by parsing build descriptors and executing enrolled discovery jobs (cached per live descriptor-content hash, so uncommitted descriptors are discovered), exposing the module inventory, dependency graph, and impact neighborhood as read-only MCP resources (`PM-TOOL-3`).
* The system must maintain a write-once, fail-closed build map (`derive-verification`) mapping file globs, roles, and build classes to the required module and whole-tree verification set for any realized file footprint; users correct seeded entries directly, and the map is re-derived only by an explicit, user-confirmed reseed.
* The system must expose architectural enrichment (module responsibility, purpose, key packages, and rationale) as `submit` links of tasks of the enrichment role (class `read_only`, one task per module through the model slots, `PM-WF-5`), enforcing a completeness guard before setup completes: every discovered module is enriched, or listed as unenriched while the enrichment role is unqualified (`PM-WORK-6`) or while the operator declined the enrichment's model cost (`PM-EXT-8`), in which case it is recorded as owed and offered again by the next setup run. While the role is unqualified, its tasks take the conservative fallback like those of every role and setup completes; the unenriched modules are named in both clients of the operator and in the architecture facts (their `responsibility` absent), and the next setup reconcile run offers their enrichment again once the role qualifies. A failure of a qualified enrichment role is a setup repair condition, never a completion.
* The system must provide a dedicated project setup workflow state machine (`project-setup`, hosted by the project's workspace scope, `PM-ARCH-4`) taking over `plan-marshall`'s `marshall-steward` wizard and its upgrade flow, mapping every wizard step and upgrade gate to a setup state or retiring it with a stated reason; the workflow runs as the last part of the project's onboarding (`PM-EXT-8`), its choices operator waits served to both clients, creates `.marshall/` and `.marshall/config/` on first run without copying a default workflow unit (`PM-IMPL-5`), offers a new binary's default-unit changes as a diff for the units the project holds a copy of on later runs, runs one aspect alone on the operator's request with the current values as the proposal, and takes no input from a `plan-marshall` `.plan/` configuration (`PM-MIG-2`).

[#PM-EXT-4]
=== PM-EXT-4: Recipes as Workflows

Recipes represent repeatable, domain-invariant or domain-specific maintenance campaigns (such as `simplify-codebase`, `security-audit`, `code-review`, `agentfile-hygiene`, `lesson-cleanup`, `doc-verify`); each is a named workflow of its own, chosen by the operator.

* The system must represent every recipe as a declarative recipe descriptor (name, description, optional domain, the parameter input schema that the server validates `recipe_params` against, whose enumerations may name a server-resolved option source of the closed set `domains`, `profiles`, `skills:<domain>`, `modules`, `base_branches`, resolved before the plan exists, and whether it takes the sources of a request, `request_scoped`) beside its workflow: a unit of type `recipe` without entries and exits that starts at its starting point and ends the plan in its stop points, whose phases are sub-workflows, its own where it differs and the plan's shared ones (finalize, the landing) where it does not (`PM-IMPL-5`).
* The system must offer the recipes of the project's domains, of the machine (`<PM_MCP_BASE>/recipes/`, offered in every project on the machine), and of the project (`.marshall/recipes/`), a project's recipe taking the place of one of the same key in that project; a duplicate key of a built-in or domain recipe fails the build, and the operator's placing of a recipe with such a key is refused (`PM-WF-22`).
* Starting a recipe, the operator's choice at the start of a plan (`PM-WF-10`), must create a plan whose process is the recipe's workflow with the parameters given; no state of the plan's general workflow routes into a recipe, and no recipe is chosen for the operator.
* A recipe run whose harvest yields no targets must end as a completed plan without a pull request (`outcome: no_change`, `merge_outcome: no_pr`, fact `empty_harvest`), never with an empty pull request.
* During `phase-1-init`, the system must compute, without a model call, the request-aspect classification of the plan's sources.
* When a recipe plan is initialized, the system must derive its `plan_id` as `recipe-{recipe_key}-{yyyy-mm-dd-hh-mm-ss}` (UTC) to prevent git branch collisions across repeated runs of the same recipe; the id is not changeable at the start, the title is.

[#PM-EXT-5]
=== PM-EXT-5: Out-of-Process Project Script Jobs & Domain Workers

Projects may define custom finalize steps (`finalize-step-*`), project-local recipes (`recipe-*`), or domain workers (custom log parsers or module discovery for languages not compiled into the release binary).

* The system must execute project-local extension code exclusively out of process as enrolled `project_script` jobs (`PM-EXEC-2`) with a declared JSON input argument schema and a validated JSON output schema.
* The system must require explicit operator enrolment (script path and SHA-256 digest, interpreter, binding to one worker kind and target, argument schema, and maximum timeout in the project's enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json`) before any project script job or custom domain worker can execute, and must refuse a run whose use or arguments do not match the enrolled binding and schema.
* Domain-specific internal capabilities (such as marker scanning or OpenRewrite log parsing) must be invoked only when declared by an active domain descriptor and must remain invisible when absent (preserving `plan-marshall` ADR-010).
* The system must offer compiled domain extension points for the pre-submission self-review surfacer (`ext-self-review-<domain>`, whose outcome is `reviewed`, `not_covered` with the surfacer's reason, or `not_run` with reason `no_domain_surfacer`, never a clean result when no review happened), for retrospective aspects of the post-run quality report (observability only, never gating the merge), and for domain recipes compiled into the domain bundle (a duplicate recipe key fails the build).

See the link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/domain-extensions.adoc[Domain Extensions Specification] (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/domain-extensions/05-recipes-and-extension-points.adoc#self-review-surfacer[§ Pre-Submission Self-Review Surfacer Extension Point], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/domain-extensions/05-recipes-and-extension-points.adoc#retrospective-aspects[§ Retrospective Aspect Extension Point]) and link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/job-runtime.adoc[Job Runtime Specification] for implementation details.

[#PM-EXT-6]
=== PM-EXT-6: Configuration Split by Owner Class (Team, Operator, Server State)

In `plan-marshall`, `marshal.json` mixes git-tracked project preferences, operator posture, derived data, server bookkeeping, executable command strings, and local runtime state. In PM-MCP, every file has exactly one owner class, and configuration is partitioned by trust boundary so no model-writable file can influence what binary or command executes on the host.

* The system must partition configuration across disjoint owner classes, with no key in two of them:
** *Team configuration (`.marshall/config/`, git-tracked)*: four purpose files, each with its own closed schema and `format_version`: `project.json` (repository and collaboration policy, among them `issues.write_back`, whether the clarified request and the approved outline are posted back to a source issue of the project's own repository, default `false`), `workflow.json` (plan workflow policy, among them the project's variant of the landing axis, `landing`, which overrides the machine's default because how a repository lands is a convention of the repository, `PM-WF-25`), `domains.json` (overrides of the derived domain detection), and `build-map.json` (the seeded build map), plus the workflow units the team placed or changed (`*.pmwf`) and the project's recipes (`.marshall/recipes/`, `PM-EXT-4`); beside them, the project skill directory `.marshall/skills/` holds the team's extension skills (`PM-SKILL-5`), vocabulary that no gate, link, or workflow reads. The files are sparse: they hold only deviations from the derived and compiled defaults and never a default, a binary version, a fingerprint, a migration ledger, or an "offered" list.
** *Operator files (operator-only)*: the enrolment, one file per project with its own HMAC (security-critical execution bindings — the enrolled repository root, build wrappers, pinned host tool paths and SHA-256 digests, command templates, project scripts, and budgets); `machine-config.json` (machine resources and bounds, the outbound `proxy` setting, the web access setting `web` of `PM-SEC-7` with its two listeners, the client-profile connection overrides of `PM-CLIENT-5`, the interface language `language.interface` and the machine's model language `language.model`, the default harness `harnesses.default`, the credential store `credentials.store` (`os` or `file`, recorded only by the operator's choice, `PM-CRED-3`), the provider defaults `providers` (per provider whether it is available, its default variant, and its credential key), the plan defaults `plan_defaults` (the machine's variant of each plan behaviour axis, `PM-WF-25`, and the optional posture `plan_defaults.posture`, unset by default, `PM-WF-10`), how documents are taken as a source (`sources.documents_mode`), the cleanup durations `cleanup`, the console preferences `console.*`, and `project_defaults`, the machine's value of the operator keys of a project); the machine's `host-tools.json` (the CLI tools of the providers, enrolled once for the machine with path and digest and used by a project unless its enrolment enrols its own) and `consents.json` (the operator's remembered consents (`PM-SEC-8`), a consent of a project keyed by its `project_id` and, for running the checkout's scripts, by the digest of each script; never held in an enrolment); the machine role set `<PM_MCP_BASE>/roles/` and the per-project role set `<PM_MCP_BASE>/projects/<project_id>/roles/` with their qualification records, and the role assignments and model catalogues of the machine and of a project (`role-assignments.json`, `model-catalogue.json`; `PM-WORK-1`, `PM-WORK-6`); the machine skill directory `<PM_MCP_BASE>/skills/` (`PM-SKILL-5`); the harness enrolment `harnesses.json` (one file per machine with its own HMAC, `PM-EXEC-1`); and per project `<PM_MCP_BASE>/projects/<project_id>/local-config.json` (the operator's values of the project, each deferring to the machine's value where the project sets none: the native or CLI variant and the credential per git and provider integration, proposed from the machine's provider defaults and applied as `native` unless the derived `git_native_capability` finds a used feature the native variant cannot serve, which then requires the operator's choice, never by a model or a content answer (`PM-SEC-3`); the commit author identity, proposed from the machine's `project_defaults.commit_identity` where set, else from the global git identity; the optional posture of the project's plans (`plan_defaults.posture`, unset by default, `PM-WF-10`); the method and asking axes of the project's plans (`PM-WF-25`; the asking axis decides which phase transitions wait for the operator, among them the outline review and whether a plan stops before its merge); the model language `language.model` (`same`, the interface language, or a locale); the epic settings `epic.auto_start`, `epic.overlap_max_files` (within a compiled upper bound), and `epic.parallelization_scope`; the operator's qualification level and warm-fresh gap (`PM-WORK-6`); the commit trailer, the envelope budget override, resolver enablement, the cleanup durations of the project's plans, epics, and logs (`cleanup`), the retention of technical residue, and the upstream MCP allowlist `upstream_mcp` of `PM-SVC-3`). The integration variant decides whose credentials act (the agent identity of the token lane or the operator's ambient CLI authentication), so it must never be a team key or a derived value, and a variant other than `native` is never chosen without the operator.
** *Server State (`<PM_MCP_BASE>`, including the per-project machine store `<PM_MCP_BASE>/projects/<project_id>/`)*: Holds workflow status, derived facts, learned adaptive build timeouts, lock state, and audit logs.
* The system must derive every value it can observe (CI provider, merge queue and its check-response timeout, default merge method, default base branch, the provider's branch rules such as required checks, up-to-date and signed-commit requirements, the agent identity of the provider credential and whether it can see check runs, the repository features the native git variant cannot serve, domain activation, active profiles, cost calibration, envelope budget) and must offer an override only where a derivation input can be ambiguous (`ci_provider`, `domains.*`, `merge_method`, `envelope_budget_tokens`); derived values are cached with their inputs and state, and a gate that depends on a derivation that failed must evaluate `indeterminate`.
* The system must compute the effective configuration server-side (compiled default, derived value, the machine's value, the team file, the project's operator value, and a plan's own value; the nearest level wins, and a level that says nothing defers to the next) and publish it with the source of every value and what it overrides, as the resource `pm://project/config` and to both clients of the operator over the local API, where every value is set and unset per key and level. Every change of a recorded operator value (a machine setting, a project's operator value, a plan's own value) carries the revision of the settings it was made against, and a change against an older revision is refused with `conflict`, never merged or applied unseen.
* The system must keep two languages apart: the interface language governs every text shown to the operator, taken from the message catalogue (`PM-IMPL-1`); the model language governs what a model is told to write and given to read, defaults to the interface language, and is passed to a worker as an instruction to write in it through the writing skill (`PM-SKILL-2`), while model-facing instructions stay in English. Command names, options, identifiers, state ids, link relations, store keys, log messages, and the domain vocabulary of the glossary are never translated.
* Tuning values that calibrate server algorithms (thresholds, iteration caps, step wait timeouts) must be compiled constants, except the decision parameters a designable workflow unit declares (the decision declarations of the question adjudication, `ask` or a quorum with its listed roles and score per decision kind, `PM-WF-18`; the trigger thresholds, budget, and prerequisite wait of the re-planning unit, `PM-WF-17`): these are workflow configuration, team-owned and reviewed like code at the project level and the operator's at the machine level, each within compiled bounds (the re-planning bounds a unit can only tighten, never open; a quorum declaration decides only while its calibration on the corpus stays within the declared level); comparability across projects is kept because every decision record carries the threshold it applied and its source (the unit with its digest, or compiled, `PM-WF-19`). No decision parameter is an operator key, and options whose only effect is to weaken a guarantee must not exist.
* The system must never read executable paths, wrapper names, or shell command strings from a team configuration file or any other file in the repository working tree.

[#PM-EXT-7]
=== PM-EXT-7: Configuration Versioning, Validation & Zero-CoT Upgrades

Configuration and workflow units must stay current without migration machinery before 1.0, without silent rewrites, and without LLM-orchestrated multi-step CLI sequences.

* Every team configuration file, operator file, and workflow unit must declare its format version; before 1.0 the system must accept exactly the binary's current version of each file kind and must refuse any other with `format_outdated` or `format_newer` naming the file, never rewriting it on read and never migrating it at runtime start. There is no migration command chain, no seed fingerprint, and no `system` bookkeeping block; the migration mechanism for 1.0 and later is decided at 1.0.
* The system must validate every team file and the operator file against its closed schema on every computation of the effective configuration; an undeclared key must be reported (`unknown_config_key`) and never kept as an unread setting, and a team file that fails validation must refuse the project's plan starts and phase handshakes naming the file.
* The system must never read, convert, or upgrade a `plan-marshall` `.plan/marshal.json` (`PM-MIG-2`).
* The system must reach a project with a new binary only through: new compiled defaults for keys the sparse files do not set; release notes listing every format change with its keys, together with the drain rule for in-flight scopes (`pm-operator drain`); and the project setup workflow, which offers the changes of a default workflow unit for each unit the project holds a copy of as a three-way diff (from the default revision the copy derives from to the current one, so a removed step is never restored and a declined change is never re-offered) and a server-rendered rewrite of a refused JSON configuration file.
* Every designable workflow unit (the phase units, the sub-workflow units `git.commit_and_push`, `remediation.*`, `replan`, and `adjudicate.decisions`, the variants of the plan behaviour axes, and the recipes' workflows) must resolve by level, the project's copy over the machine's copy over the compiled default, a project holding a copy only of the units its team placed or changed (the compiled-only units stay compiled only, link:later-improvements.adoc#_l_5_team_overrides_of_templates_and_composition_rules[Later Improvements, L-5]), and every unit of the machine and project level must be verified on every load against the static verification rules and the compiled invariants of every phase (mandatory steps and states, the outline gate, Q-Gate presence, footprint checks, push and pre-merge barriers, finalize ordering bands, step completion exactly once, remediation policies that end in a defined fallback within the compiled budget caps, waivers written only by the operator channel, unchanged condition overlays, and no guarantee-weakening path); a violating unit must refuse the plan lifecycle of every project it reaches with its file and line and never fall back silently to the unit of another level. Project steps must bind only to enrolled project scripts.
* The system must prevent configuration upgrade clutter in the model's Chain of Thought (CoT) and codebase:
** Vocabulary skills and workflow prompts must never contain prose instructions for historical field migrations or multi-step CLI choreography (retiring separate model-invoked `sync-defaults`, `steps-sort`, `normalize-keys`, and `migrate-*` calls).
** When the digests of the configuration inputs match the last validated effective configuration, configuration verification at plan startup or phase handshakes must execute as a silent check emitting zero context tokens.
* The system must execute an in-flight plan against its plan instance (`PM-IMPL-5`), whose header records the digests of every configuration input (compiled defaults, derived facts, team files, the operator's values of the machine and the project, a plan's overrides, and the workflow units of every level), so a later change (edit, changed default, changed derived fact, adopted unit change) must never silently change what an in-flight plan does: the server composes a candidate instance at the next phase handshake, adopts it without interaction only when it equals the current instance, and otherwise raises the configuration-drift condition, which the server resolves in the same transaction: it adopts the candidate when it verifies and contains the current state and every state of the call stack, and keeps the current instance otherwise, audited (`PM-IMPL-5`).
* Automated build-time JUnit tests (`PM-TEST-3`) must verify that every configuration schema is closed and valid, that every default workflow unit satisfies the compiled invariants, and that the invariant checker refuses a fixture set of weakened units.

[#PM-EXT-8]
=== PM-EXT-8: Project Onboarding as One Process

A project is taken into use by one process the operator runs in either client, from its checkout to its completed setup, that asks before it reads or runs anything and records only what the operator changes.

* The system must onboard a project by one compiled unit in a scope of its own per project being onboarded (an entry until the enrolment, then the project's workspace scope), so that several projects are onboarded at once and the machine scope is never touched: the checkout, the detection, the identity, the enrolment, and then the project setup (`PM-EXT-3`). It starts only while the machine's onboarding is complete (`PM-WF-26`), its choices are operator waits served to both clients (`PM-WF-20`), the first answer winning, and no coding-agent session drives it (`PM-CLIENT-1`); `pm-operator enrol` stays the direct verb of the enrolment, its arguments the answers.
* The system must read the checkout and run the version probes of the host tools it finds only on the operator's consent (`inspect_checkout`, `PM-SEC-8`), changing nothing, and must run the checkout's own scripts only on a consent of their own (`run_checkout_scripts`) that names every script with its arguments before any of them runs; a _no_ to the scripts goes on without them, what needs them unknown. A remembered consent is kept in the machine's `consents.json` under the project's confirmed `project_id` and, for scripts, the digest of each script, so that a changed script is asked again; an onboarding that does not reach its enrolment remembers nothing. Every probe runs as a confined job, never in the runtime's own process.
* The system must propose the project's id from its remote's name, valid by the identifier grammar and unique on the machine, and its display name from the remote's owner and name; the operator may change both before the enrolment, and the display name later.
* The system must take a project's build environment from the operator's login environment as the terminal client captures and sends it, never from the runtime's own environment; a project onboarded from the web app takes the environment the terminal client last captured on the machine and says so, and without one names the terminal command that captures it.
* The system must show the expected tokens before a role task of the setup (the qualification of the roles, the enrichment of the modules) and run it only on the operator's consent (`model_cost`); a _no_ skips the step with its reason, records it as owed for a later run, and leaves the project ready without it (`PM-WORK-6`, `PM-EXT-3`).
* The system must show the operator's values of the project (the model language, the allowed models, the role assignment, the method and asking axes, the integration variant and credential of each provider, the commit identity, and the cleanup durations of its plans, epics, and logs) with the machine's value as the proposal and record a value for the project only when the operator changes it, and must keep the team's values (the landing axis, validated against the project, and the declaration of its providers) in `.marshall/config/` (`PM-EXT-6`).
* The system must let the operator run one aspect of a project's onboarding or setup alone later, with the current values as the proposal.
