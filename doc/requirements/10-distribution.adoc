== Distribution & Client Packaging (PM-DIST)

[#PM-DIST-1]
=== PM-DIST-1: Single Version Authority & Embedded Client Bundles

`PM-MCP` distributes a compiled software system rather than a generated markdown corpus, unifying server and client components under a single version authority: one release.

* The system must distribute one release of four native executables built from one version: `pm-mcp` (the worker-facing command line: the relay `pm-mcp serve --job` of a worker's connection), `pm-operator` (the operator's command line and terminal client, one of the operator's two clients), `pm-mcpd` (the runtime, started on demand by `pm-operator` and never by a worker's relay, which also serves the web app, the operator's other client), and `pm-exec` (the job launcher).
* Every artifact of the product (the module JARs, the parent POM, the native binaries, and the release) must be delivered through the package registry of the GitHub organisation `plan-marshall` and through no other place, never Maven Central or another public registry (`PM-IMPL-1`).
* The macOS release must ship `pm-mcpd` signed with a Developer ID and notarised (`PM-CRED-2`).
* The release must embed the client bundles (`classpath:/bundles/<client>/`) for every supported frontier coding agent runtime whose bundle has been delivered by the current stage (`PM-MIG-1`): Claude Code (`claude`), OpenCode (`opencode`), Antigravity (`antigravity`), and Codex (`codex`); full four-host coverage is reached at Stage 6. The bundle version is the release version.
* The system must eliminate separate client-side package downloads and repository distributions, ensuring that client-installed artifacts always originate directly from the installed release; no sub-agent or agent variant is installed into a host, because the runtime composes every worker's launch, its MCP connection included, from the role's effective configuration and the client profile at spawn (`PM-WF-5`, `PM-DIST-3`).
* A host is a worker host only, never a channel of the operator (`PM-CLIENT-1`): a client bundle installs no entry command, no MCP connection configuration of a host session, and no lifecycle hook. The system must embed the following artifacts within each client bundle:
** The shim skill of `PM-SKILL-4`, in the host's own skill format and directory, until the host supports the MCP Skills Extension.
** Permission deny rules for `<PM_MCP_BASE>/**` including its credential directory, and, as defence in depth, an enforcement rule that denies the whole operator binary `pm-operator` to the model, while `pm-mcp serve --job`, a worker's connection, stays allowed (`PM-SEC-3`).
* The system must structure the server filesystem installation using a clean separation between installation and instance directories:
** `<PM_MCP_HOME>/`: Read-only installation directory containing the four binaries (`bin/pm-mcp`, `bin/pm-operator`, `bin/pm-mcpd`, `bin/pm-exec`), beside `pm-mcpd` the Netty native transport library of the platform, which the runtime loads from there and never from the system temporary directory (`PM-TECH-1`, `PM-TECH-3`), the CycloneDX SBOM of the release (`sbom/`, covering the Java dependencies and the npm packages of the web application), and the release notes, and no configuration file (machine settings live in `<PM_MCP_BASE>/machine-config.json`). Unless the environment variable `PM_MCP_HOME` names it, it is resolved from the location of the running binary (`pm-mcp` or `pm-operator`) with symbolic links resolved.
** The binaries must start each other by absolute path from `<PM_MCP_HOME>/bin/`, never through `PATH`; the installation must put exactly two entries on `PATH`, the symbolic links `pm-mcp` and `pm-operator` in a user bin directory (or print the commands that create them).
** An upgrade, an operator act of either client (`PM-ARCH-7`), must be performed by the runtime: it fetches the release from the organisation's registry, verifies its digest, installs it into a new versioned installation directory beside the current one, switches the two `PATH` symlinks, and stops by its drain with a restart, its successor being the new `pm-mcpd`; a new runtime that does not start makes it switch the links back and start the previous version, whose directory stays as the way back until the next upgrade. An installation not laid out in versioned directories with the two links, or reached through `PM_MCP_HOME`, is not upgraded by the runtime and is upgraded by hand with the same steps. Which credential the runtime presents to the registry and the form of a release in it are open: see link:discussions/open-questions.adoc#registry-credential[Open Questions].
** `<PM_MCP_BASE>/`: Mutable instance directory (default `~/.plan-marshall-mcp/`, overridable only by the environment variable `PM_MCP_BASE`) that survives software upgrades, containing `enrolments/` (one enrolment file per project), `harnesses.json` (the enrolled harness command lines of workers), `host-tools.json` (the CLI tools of the providers enrolled for the machine), `roles/` (the operator's machine role set, `PM-WORK-1`), `role-assignments.json` and `model-catalogue.json` (the machine's role assignment and allowed models, `PM-WORK-1`), `consents.json` (the operator's remembered consents), `profiles/` (the operator's verified machine profiles of harnesses, `PM-CLIENT-5`), `icons/` (the fetched icons of harnesses), `skills/` (the machine skill directory of operator extension skills, `PM-SKILL-5`), `workflows/` and `recipes/` (the operator's machine level of workflow units and recipes, `PM-IMPL-5`, `PM-EXT-4`), `machine/` (the machine scope with its onboarding), `machine-config.json` (machine settings, the client-profile connection overrides included), `credentials/` (the file credential store, where the operator chose it), `logs/`, `locks/`, `run/` (runtime token, socket, and job-private directories), `web/` (files of the web access), `projects/` (the per-project machine stores with plans, archived plans, lessons, and scope state), and `state/` (runtime-owned machine state, whose contents the link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/filesystem-layout/02-machine-runtime.adoc#machine-layout[Filesystem Layout Specification, Machine Layout] alone defines).

[#PM-DIST-2]
=== PM-DIST-2: Embedded Bundle Extraction & Interactive Client Installer

Client configuration artifacts and bundles must be extracted directly from the release's embedded resources and applied via an interactive CLI installer without network access or a TCP listener.

* The release must embed one deterministic bundle manifest (`classpath:/bundles/<client>/bundle-manifest.json`) per supported client (`claude`, `opencode`, `antigravity`, `codex`), declaring the artifacts shared by both scopes once and one section per scope (`user`, `project`) with its target root, its shared host configuration files, and its scope-only artifacts, and defining target relative paths, file types, SHA-256 digests, file modes, owned configuration keys, and owned configuration elements.
* The installer must own shared host configuration at element level: host permission rules (`permission_rule`, in a deny, ask, or allow list, classed enforcement or convenience) are identified by their exact normalized value and recorded in the installation ledger; `install` appends missing elements, `update` replaces recorded elements, `remove` deletes recorded elements only, and a recorded element the user edited or deleted is changed only after an interactive `--force`.
* The system must provide a client installation tool (`pm-operator client install|update|remove|status`) whose changes are applied by the runtime as the single writer, that reads the embedded bundle manifest, compares it against the target filesystem and installation ledger, displays an interactive diff of files and permissions to be changed, and requires explicit operator confirmation on a TTY (`--yes` for non-interactive CI/automation).
* The client installer must require an interactive terminal and refuse `--yes` for `pm-operator client remove` and for any `install` or `update` change that removes or weakens an installed enforcement rule (including the `<PM_MCP_BASE>/**` and credential-directory deny rules, `PM-CRED-3`); `--yes` must be accepted only for changes that keep or strengthen every enforcement rule.
* The client installer must support two installation scopes, selected by `--scope` and recorded with the installation:
** `--scope user`: Installs the shim skill and the permission rules into the user-scope locations of the link:specification/host-integration/01-host-detection.adoc#host-integration-table[Host Integration Table].
** `--scope project`: Writes the shim skill and the permission rules into the project-scope locations of the link:specification/host-integration/01-host-detection.adoc#host-integration-table[Host Integration Table] (containing zero user-specific paths or secrets) for team version control; `pm-operator client install|update --scope project` must refuse while the project has non-terminal plans or epics, naming them (user scope is unaffected).

See the link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/client-profiles.adoc[Client Profiles Specification] and link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification] for implementation details.

[#PM-DIST-3]
=== PM-DIST-3: Worker MCP Connection per Launch

The system must give every worker its MCP connection through the worker's launch, never through a host's configuration file.

* The system must compose the MCP connection of every worker (`pm-mcp serve --job`, `PM-WF-5`) into its launch as the client profile of its harness declares it (a slot of the launch or a file in the worker's working directory, `PM-CLIENT-2`), and must write no MCP connection into a host's user or project configuration.
* Because `pm-mcp serve --job` runs only as a job of a running runtime and connects to it over its user-private Unix domain socket with the worker's job token, a worker's connection requires no runtime pre-start, bearer token helper, or TCP port.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work.adoc[Model Work Specification], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/client-profiles.adoc[Client Profiles Specification], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/workflow-dsl/02-units-jobs-decisions.adoc#clients-only[Workflow DSL & Engine Specification, All Interaction in the Operator's Clients], and link:specification/host-integration.adoc[Host Integration & Bundle Manifest Specification] for implementation details.

[#PM-DIST-4]
=== PM-DIST-4: Bundle Upgrade Detection & Atomic Reconciliation

The system must detect discrepancies between installed client bundles and the installed release, performing safe, idempotent updates.

* The system must detect bundle drift during `pm-operator client status`, issuing an actionable recommendation to run `pm-operator client update`: `bundle_outdated` when the recorded bundle version differs from the release version of `pm-operator` (every binary of a release carries the release version, which is the bundle version, `PM-DIST-1`), and `bundle_modified` when the recorded digest of an installed artifact or owned element differs from the disk (edited and missing entries listed).
* The system must record every installed file path, configuration key, and configuration element with its scope and digest in an installation ledger (`<PM_MCP_BASE>/state/install-records.json`); subsequent updates must modify or delete only recorded entries.
* The client updater must verify file digests and element values before overwriting; any file or element modified locally by the operator must be preserved and reported with a warning unless the operator confirms `--force` interactively.
* The client updater must merge shared host configuration files (per the link:specification/host-integration/01-host-detection.adoc#host-integration-table[Host Integration Table]) strictly at their owned keys and elements (e.g., the recorded permission rules), preserving all unowned configuration.
* When the release on disk differs from the running runtime's, the system must report the version mismatch to the operator in both clients, never in a model-facing representation, and let the operator stop or restart the runtime by its drain (`PM-ARCH-7`); installing or updating a client bundle must be refused until the old runtime is drained.

See the link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/client-profiles.adoc[Client Profiles Specification] and link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification] for implementation details.

[#PM-DIST-5]
=== PM-DIST-5: Multi-Host Concurrent Coexistence on One Machine

Multiple host connections across distinct coding agent hosts must operate simultaneously and safely across different projects or within the same project.

* The system must permit concurrent workers on any combination of enrolled harnesses (`claude`, `opencode`, `antigravity`, `codex`, and a harness the operator added) on the same machine, each with its `pm-mcp serve --job` relay, all served by the one runtime of the active `PM_MCP_BASE`.
* The system must install client bundles into host-specific directories without file name collisions, including with the artifacts of a `plan-marshall` plugin installed side by side.
* The system must coordinate machine-wide build slot caps (`build-slots.json`), per-repository merge queues (`merge-queue.json`), cross-plan review-bot rate windows (`review-bot-windows.json`), and per-plan locks fairly across all concurrent plans via `FileChannel.lock()`, taken by the runtime as the single writer (the verbs of `pm-mcp` and `pm-operator` are requests to the runtime).
* The system must permit `plan-marshall` and `PM-MCP` to be installed on the same machine and used in the same repository: `PM-MCP` keeps its state exclusively in `<PM_MCP_BASE>` and `.marshall/`, never reads or writes `~/.plan-marshall/` or `.plan/`, and never reads `PLAN_MARSHALL_HOME` or `PLAN_MARSHALL_CREDENTIALS_DIR`, without exception (`PM-MIG-2`).
* The system must support development and test isolation: setting `PM_MCP_BASE` to an alternate path must isolate the runtime instance, its socket, state locks, build slots, audit logs, and credential namespaces to that directory.
