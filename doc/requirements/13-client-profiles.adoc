== Client Profiles & Dynamic Translation (PM-CLIENT)

[#PM-CLIENT-1]
=== PM-CLIENT-1: Harnesses as Workers & Client Identity

A harness is a worker host only, never a channel of the operator: the operator acts only in the operator's two clients, and a worker's identity is its job record, its harness and client profile coming from its role.

* The system must take every input of the operator only through the operator's clients, the web app and the terminal client (`PM-ARCH-11`, `PM-WF-20`); no harness, host session, or model relays the operator's words or choices. The system must install no entry command into a host, run no relay of a host session, keep no session log, and open no entry, plan, or epic on a host's request; the only connection a harness makes to the runtime is a worker's (`pm-mcp serve --job`, `PM-WF-5`).
* The client identity (`claude`, `opencode`, `antigravity`, `codex`, or the client id of a harness the operator added, `PM-CLIENT-5`) must be treated strictly as advisory routing and rendering metadata used to format representations, skill syntax, and host tool names, never as an authenticated security credential.
* A worker's connection must take its client profile from the harness of its role's effective configuration (`PM-WORK-1`), recorded in its job record with the harness version probed at its spawn; it carries its `job_id`, role, and generation in its audit records.

See the link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/client-profiles.adoc[Client Profiles Specification], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/workflow-dsl/02-units-jobs-decisions.adoc#clients-only[Workflow DSL & Engine Specification, All Interaction in the Operator's Clients], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work.adoc[Model Work Specification], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas.adoc[Store Schemas Specification], link:specification/runtime-model.adoc[Runtime & Interaction Model Specification], and link:specification/host-integration.adoc[Host Integration & Bundle Manifest Specification] for implementation details.

[#PM-CLIENT-2]
=== PM-CLIENT-2: Data-Driven On-the-Fly Profile Translation

Instead of generating static per-runtime copies of the skill corpus at build time, `PM-MCP` must dynamically translate all model-facing artifacts per request using declarative client profiles for all supported coding agents (`claude`, `opencode`, `antigravity`, `codex`) and every harness the operator added (`PM-CLIENT-5`).

* The system must translate vocabulary skills, state representations, hypermedia links, and the launches and prompt files of workers on the fly according to the client profile of the worker's harness across the following dimensions:
** *Host Tool Names*: Translating canonical tool references to runtime-native names (e.g., `Read` -> `view_file` in Antigravity, `read` in OpenCode, or `read_file` in Codex _(provisional)_; `AskUserQuestion` -> `ask_question`, `question`, or `request_user_input` _(provisional)_).
** *Skill Load Directives*: Rendering skill invocation syntax for the client's native discovery mechanism (`pm_skill(plan_id="...", uri="...")` tool call or `resources/read` resource read).
** *Tool Idioms*: Rewriting, preserving, or rewording runtime-specific idioms according to registered profile dispositions.
** *Models & Effort*: Rendering the model and effort of a role's effective configuration (`PM-WORK-1`) into the harness's model identifier and effort arguments, and a model tier of the shipped default assignment into the harness's model through the profile's map of tiers to models.
** *Headless Model Jobs*: Composing a model job's launch (`PM-WF-5`) from the profile's `headless` block: an argument-vector template with typed slots (prompt file, model, effort, MCP configuration, result schema, tools, working directory), how the harness receives its MCP configuration (a slot of the launch or a file in the worker's working directory, exclusive or not), what it can run per role class (a `zero_tool` class only where it can be started with no tool and no MCP connection, which the screener and the judge require; for the `writer` and `read_only` classes whether it enforces the role's tool set or leaves the worker every tool of the harness, which is accepted), the declared capabilities (result schema, ephemeral run, usage and cost fields, reliable exit status, project-settings control), the supported harness version range, the writable harness paths and, where the harness's local state must not be shared between workers, a per-worker data directory (`PM-SEC-5`), the harness's per-tool-result limit (a task input or offer that would exceed it is delivered as resource reads below the limit, its identifiers first, so a harness that truncates a tool result never loses the task), the harness's MCP-resource-reading tools (allowlisted for the `writer` and `read_only` job classes, never for `zero_tool`), and `agent_mode` (`inline`: a per-job named agent rendered for Claude Code and OpenCode; `flags`: per-call flags for Codex). A harness lacking a capability that a role's class needs runs no worker of that role (`PM-WORK-1`).
** *Usage*: Reading every token figure the harness reports per turn (input, output, cache read, cache creation, and reasoning tokens) and its tool uses through the profile's usage pointers: a figure the harness does not report is recorded as unmeasured, one that does not exist for the harness by design as not applicable, never as a measured zero (input and output tokens are never not applicable); a cost the harness reports is recorded and never shown or read by a rule.
** *Activity Events*: Mapping a line of the harness's output stream onto the closed, harness-neutral activity kinds of `PM-WORK-7`, or none where the harness gives no event stream.
** *Worker Parameters & Eligibility*: The profile's `worker` block: whether the harness is eligible as a worker host (`worker.eligible`), which of its models accept an enforced tool set, the acknowledgement deadline and whether it is informational, the silence grace, and the idle wake-ups (`PM-WORK-3`); the bounded wait and whether progress resets the host's timeout are values of the profile's `connection` block, the host's timing facts. A harness is eligible only after its worker behaviour has been measured on it, under the target conditions, with every fault of the fault matrix passed: the Claude Code profile is eligible, the OpenCode profile is eligible with its per-worker data directory, and the Antigravity and Codex profiles are not eligible until then; the operator assigns their roles to an eligible harness.
* Dynamic profile rendering must compute deterministic per-client skill digests so each client runtime observes a stable, verifiable skill catalogue.
* The system must restrict profile translation to the vocabulary dimensions above; any per-client or per-model change of wording, emphasis, or scaffolding requires a behavioural signal for that client (`PM-TEST-6`) and a recorded decision before it ships.

See the link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/client-profiles.adoc[Client Profiles Specification] (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/client-profiles/01-profile-schema.adoc#token-usage[§ Tokens, Not Money], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/client-profiles/01-profile-schema.adoc#worker-activity[§ What a Worker Does]), link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work.adoc[Model Work Specification], and link:specification/mcp-tools.adoc[MCP Tools Specification] for implementation details. The measurements behind its values are recorded in the link:specification/evaluation.adoc[Evaluation Reference].

[#PM-CLIENT-3]
=== PM-CLIENT-3: Host Environment Detection

To keep the operator's commands out of a coding agent's reach, the system must recognise a coding agent's environment by fixed signals.

* The system must recognise a coding agent's environment from the inherited process environment by the per-client detection signals and their fixed precedence defined in the link:specification/host-integration/01-host-detection.adoc#host-integration-table[Host Integration Table] (primary signals `ANTIGRAVITY_AGENT`, `OPENCODE` / `OPENCODE_PID`, `CLAUDE_CODE_SESSION_ID`, checked in this order, then `CODEX_SANDBOX` / `CODEX_CI` / `CODEX_THREAD_ID` for Codex; secondary signals `CLAUDECODE` and the host prefix of `AI_AGENT`), treating values marked provisional there as unverified; `pm-operator` refuses an operator verb while any of them is present and names the detected host (`PM-SEC-3`). When the markers of more than one host are present (a host started inside another clears none of the other's markers), the host whose process-id marker names the nearest ancestor process must be detected, the fixed order deciding only when no such marker resolves.
* The system must perform no identity check per tool call: a worker's call is rendered from its job record (`PM-CLIENT-1`).

See the link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/client-profiles.adoc[Client Profiles Specification] and link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification] for implementation details.

[#PM-CLIENT-5]
=== PM-CLIENT-5: Versioned Client Profile Schema & Override Hierarchy

Client profiles must be governed as versioned, schema-validated data artifacts embedded in the binary and extensible via local configuration overrides.

* Every client profile definition must be a declarative JSON document carrying an explicit integer `schema_version` and minimum compatible server version (bundle versions and file digests live in the per-client `bundle-manifest.json`, `PM-DIST-2`).
* The profile must be the one configuration document of a harness and the only place the system describes it: the detection signals and identity probes, where its executable is found and how its login and models are probed, the vocabulary, the launch contract of its headless run, what it can run per role class, its map of model tiers, its usage and activity mappings, its icon, and its worker parameters. Production code must read profiles through one generic reader and must name no harness; a new harness is a new profile document, and a new measurement or a corrected value of a harness is a change of its profile, with no change of code unless the harness needs a mechanism the schema lacks.
* Each profile must state whether its harness can run the `zero_tool` class, that is be started with no tool and no MCP connection: only such a harness may be named by a screener or judge role (`PM-SEC-1`). For the other role classes the profile must state whether the harness enforces a role's tool set or leaves the worker every tool it has; both are accepted, and the operator must be able to see which roles run unrestricted.
* Each profile must declare supported protocol capabilities (progress notification idle-timer reset, tool-call timeout bounds), its `headless` and `worker` blocks (`PM-CLIENT-2`), and tool schema loading mode (resident vs on-demand preloading of `pm_state` and `pm_do`).
* Each profile must declare what the machine's onboarding needs to find and check its harness: the install locations searched beside the directories of the operator's login `PATH`, with an install hint; a version probe; a login probe (an argument vector, the exit codes that mean logged in and logged out, and the login command shown when logged out), or, without one, one minimal headless call whose token cost is shown before it runs; a models probe where the harness can list its models; and the map of the shipped model tiers to its models (`PM-WORK-1`). A scan runs nothing but the version probe on what it finds, every probe runs only on the operator's consent, and a found executable is enrolled only by the operator's choice, with its absolute path and digest (`PM-EXEC-1`).
* A profile may name its harness's icon: the maker's official icon file, fetched once by the runtime on the operator's consent, stored on the machine, and served to the web app from the runtime's own origin, never loaded by a browser from the maker; or an icon shipped in the binary. Without one, the harness is shown by a generated monogram, the same in both clients; an icon identifies its harness only where the harness is shown. Whether a maker's icon may be shown or shipped is open: see link:discussions/open-questions.adoc#harness-icons[Open Questions].
* The system must provide an operator-driven verification of a harness (`pm-operator profile verify`) that runs the harness on the machine through the real job launcher, relay, and supervisor, tests its capabilities in closed stages (identity, detection, launch, isolation, role classes with the `zero_tool` class of the screener, input limits, writable paths, and the fault matrix of `PM-TEST-4`), and emits a profile document with a verification record that states for every value whether it was measured, confirmed by the operator, or only declared. The stage of the activity events records per activity kind `reported` or `missing`; the usage stage records per token figure `reported`, `not_applicable`, or `missing`, a declared pointer that does not resolve fails it, and its result is kept with the harness enrolment as the harness's usage report, shown wherever the enrolled harnesses are listed; recorded outputs of each harness version are parsing fixtures. The shipped profiles must be the output of that verification, and a profile must claim worker eligibility or a runnable `zero_tool` class only where the verification measured it.
* The operator must be able to have a harness without a profile verified from a draft entered as a form in either client (the executable, a client id and name, and the interface statements the verification needs from the operator, prefilled from the profile of the closest known harness), on the operator's consent to its token cost, each failed stage naming the draft field it concerns; the verified profile is installed into the machine profile set and its harness enrolled like a found one, eligible as a worker host only where the verification shows it. No closed list of client ids may refuse a harness the operator added.
* The operator must be able to install such a profile through the operator channel for the machine or for one project (in the per-project machine store, never in the repository), replacing the profile of the next set as a whole; a machine profile may add a harness the release does not ship, and a project profile must keep the detection data and the executable of the harness it varies. An installed profile must be valid only with the verification record bound to its content, so that no profile is written or edited by hand or by a model.
* The verification record must track exactly what was measured: the release and commit of the runtime that ran the verification, the harness by executable name, exact version, and the digest of its executable, the models, and the platform with its confinement; it must hold no free text and no data of the machine or the user beyond these.
* Every profile, draft, and verification record must be validated as untrusted input against a closed schema with bounded sizes and patterned strings: no unknown member, no shell, no launch argument that names a URL or a path outside the declared ones, no loader or credential variable, and no text a model reads that could carry an instruction; no claim of eligibility, of a tool-free class, or of an enforced tool set may be taken from the document alone.
* The server must resolve client profiles using a four-tier override hierarchy (from lowest to highest precedence):
** Built-in profiles compiled into the `pm-mcpd` runtime binary (`classpath:/profiles/<client_id>.json` for `claude`, `opencode`, `antigravity`, and `codex`).
** Verified machine profiles `<PM_MCP_BASE>/profiles/<client_id>.json`, installed with `pm-operator profile install`, each replacing the built-in profile of its `client_id` as a whole.
** Verified project profiles `<PM_MCP_BASE>/projects/<project_id>/profiles/<client_id>.json`, installed with `pm-operator profile install --project`.
** Operator machine-level connection overrides in `<PM_MCP_BASE>/machine-config.json`: the closed object `client_profiles.<client_id>.connection` (`bounded_wait_seconds`, `idle_timeout_seconds`, `progress_resets_timeout`), set with `pm-operator config`; no other profile value can be overridden.
* The server must resolve harness, model, and effort only from the operator's role configuration (the role artifacts, the role assignments, and a plan's overrides, `PM-WORK-1`), and must never read client profile overrides or model pins from git-tracked configuration (`PM-EXT-6`).
* All profile documents must be validated against the closed client profile JSON Schema at startup, and the connection overrides against the closed schema of `machine-config.json`; a malformed profile or override must be rejected with a structured diagnostic error.
