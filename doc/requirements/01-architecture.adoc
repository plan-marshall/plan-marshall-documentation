== Core Architecture (PM-ARCH)

[#PM-ARCH-1]
=== PM-ARCH-1: Process Ownership & Always-On Runtime

The system must strictly divide responsibilities between deterministic process execution and probabilistic model judgment. All state tracking, transition sequencing, gate evaluations, and command assembly belong to the system, while the model is tasked exclusively with judgment-based contributions.

* The system must execute all workflow state machines, state transitions, quality gate evaluations, and command assembly inside the always-on runtime process (`pm-mcpd`), confining model contributions exclusively to the judgment artifacts that role tasks submit (`PM-WORK-1`; for example request clarification, solution outline authoring, code implementation, finding triage, and commit and pull request descriptions).
* The system must drive the interior of every plan and epic itself: every step that needs no model is server logic, and every step that needs one is a task of a role served by a supervised headless worker that the system starts as a model job (job kind `llm`) through the headless command line of an enrolled harness (`PM-WF-5`, `PM-WORK-1` to `PM-WORK-3`, `PM-EXEC-1`); it must never depend on a host dispatching a sub-agent or on a conversation calling it. A harness is a worker only and never acts for the operator: the operator works with the system only in the operator's two clients, the web app and the terminal client (`PM-ARCH-11`), and a state that needs the operator is an operator wait served to both (`PM-WF-20`).
* The system must run as a single always-on runtime process (daemon) per machine and `PM_MCP_BASE`, under the operating system privileges of the local developer user, whose lifetime and jobs are independent of any host conversation or host connection.
* The system must let workers reach the runtime exclusively through the thin job relay `pm-mcp serve --job`, which a worker's harness spawns from the strict per-call MCP configuration the runtime composes for it (`PM-WF-5`), never through a network port apart from the loopback fallback of `PM-SEC-4`; no host session connects to the runtime.
* The runtime must open no TCP or UDP listener, apart from the loopback fallback of `PM-SEC-4`, unless the operator enabled web access: without it its only listener is a user-private Unix domain socket that serves MCP (`/mcp`) to the job relays and the local REST API (`/api/v1`) to the terminal client and operator CLI `pm-operator`, and authenticates every request with the runtime token or, for a job relay, the job's own token (`PM-SEC-4`).
* The system must make the runtime the only writer of every store: the command-line binaries (`pm-mcp`, `pm-operator`) and a paired browser hold no store logic and change state only through requests to the local API, which the runtime validates, locks, audits, and executes. What only a client sees (its locale, the operator's login environment, an SSH session) reaches the runtime only in the client's request; the runtime's own process environment is never an input of a workflow, a detection, or a job's build environment.
* The command-line binaries must read directly only a closed list of files of `<PM_MCP_BASE>`, which they never write: `pm-operator` reads `state/runtime.json`, `run/runtime.token` (authentication), `state/install-records.json` with the target files recorded there (the drift check of `pm-operator client status`), and `machine-config.json` (for the drain bound of `pm-operator drain`); the job relay `pm-mcp serve --job` reads none of them, its job token coming from its environment. The terminal client's own files (its history and the overview's selection) live in its own state directory outside `<PM_MCP_BASE>`, are written only by it, and hold no state of the runtime. The list is the one in link:specification/cli-and-security/01-cli-and-installer.adoc#cli-file-reads[CLI, Coordination & Security Specification, Direct file reads]; the read-only codec for these files lives in `pm-api`. The only lock either binary takes is `runtime-start.lock`, and exactly three verbs work without a running runtime and never start one: `pm-operator status`, `pm-operator drain` (which waits at most the drain timeout plus the termination grace period plus the fixed margin of the link:specification/timeouts/02-runtime-leases-operator-web.adoc#drain-timeout[Timeouts & Budgets Specification, Drain Timeout]), and `pm-operator client status`.
* The runtime may serve web access itself, off by default and enabled only by operator verbs (`pm-operator web enable [--lan]`): the web listeners of `pm-mcpd`, a loopback listener and, beside it, a LAN listener, the only TCP listeners of the system apart from the loopback fallback of `PM-SEC-4`, which route only the web app and the local API, never serve MCP, and never accept the runtime token; no separate web server process exists (`PM-SEC-4`, `PM-SEC-7`).
* The system must enforce mutual exclusion across concurrent requests, jobs, and projects using OS-level `FileChannel.lock()` advisory locks and atomic write-then-rename operations within the per-project machine store `<PM_MCP_BASE>/projects/<project_id>/` and `<PM_MCP_BASE>/locks/`.
* The system must compile the default workflow definitions (the project-owned units are verified data, `PM-IMPL-5`), state stores, tools, client profiles, vocabulary skills, and background services into the four native binaries of one release (the relay binary `pm-mcp`, the terminal client and operator CLI `pm-operator`, the runtime `pm-mcpd`, and the job launcher `pm-exec`), installed side by side and starting each other by path, guaranteeing that all components operate on an identical release version without runtime drift.
* The system must reject any architecture where process ordering, transition permissions, or parameter assembly depend on prose instructions or client-side prompt compliance.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification], link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], and link:specification/mcp-tools.adoc[MCP Tools Specification] for implementation details.

[#PM-ARCH-2]
=== PM-ARCH-2: Local-by-Design & Zero External Cloud Dependency

The system must operate entirely on the developer's workstation, directly interacting with local repository trees and worktrees without reliance on cloud intermediaries.

* The system must execute all services, workflow transitions, and state management locally on the developer's workstation without requiring remote infrastructure, cloud-hosted backends, or telemetry reporting. Beyond the providers a project uses, the runtime makes an outbound request only on the operator's consent (`PM-SEC-8`): the fetch of a harness maker's icon and the check of the organisation's registry for a newer release, which sends nothing about the machine beyond the request itself; the runtime's metrics never leave the machine (`PM-ARCH-9`).
* The system must enforce workspace confinement, restricting all file reads, file modifications, and process executions strictly to the enrolled project root directory and its active linked worktrees, with exactly these exceptions:
** Jobs, confined per `PM-SEC-5`: they read the whole filesystem except `<PM_MCP_BASE>`, write only their own project root (with its worktrees), declared toolchain caches, `/tmp`, and `/dev`, and execute the enrolled toolchains; a `ci` job of the CLI variant additionally writes its CLI's configuration directory (`GH_CONFIG_DIR` / `GLAB_CONFIG_DIR`); a model job (job kind `llm`) additionally reads its own job-private directory `<PM_MCP_BASE>/run/jobs/<job_id>/` (the one exception to the rule that jobs never read `<PM_MCP_BASE>`; no job writes there), writes the sub-paths of the harness's home that its client profile declares (its login or credential file, caches, and session directory; never a settings, command, or skill file the client bundle manages), uses the network, and authenticates with the harness's own login, never with a PM-MCP credential.
** The runtime's own instance directory `<PM_MCP_BASE>`, which holds every file the runtime owns or trusts (the socket and the job-private directories included); the runtime keeps none of them in the system temporary directory.
** The installation root with its versioned installation directories and its two `PATH` symbolic links (or the installation directory `<PM_MCP_HOME>`), into which the runtime unpacks a release it upgrades to and whose links it switches (`PM-DIST-1`, `PM-ARCH-7`).
** The documents the operator chooses as a source of a plan or an epic, read from the checkout or the operator's home directory and, when the operator chooses to move them, deleted there (`PM-WF-10`); a move is the only deletion of the operator's files the runtime makes.
** The terminal client's own state directory, written only by `pm-operator` (`PM-ARCH-11`).
** The per-user service unit for the OS service manager, written by the runtime on the request of `pm-operator runtime install` and removed on `pm-operator runtime uninstall` (`PM-ARCH-7`).
** The client bundle installer's targets: the host configuration in the user's home directory and, for a project-scope install, the project's host configuration files (`PM-DIST-2`).
** The read of the user's global git configuration by the native git variant, as untrusted input (`PM-SEC-1`).
** The toolchains and JDKs that jobs execute.
* The system must reject any operation attempting to access or modify filesystem paths outside the enrolled project boundary unless explicitly authorized by the human operator through an operator act (`PM-SEC-3`).
* The system must never transmit lesson or finding content to a vendor or upstream issue tracker automatically; content classified for an upstream audience stays in the local store until an explicit, content-reviewed operator action releases it, and a lesson classified `local` must never be offered for upstream filing.

See the link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification], link:specification/filesystem-layout.adoc[Filesystem Layout Specification], and link:specification/store-schemas.adoc[Store Schemas Specification] for implementation details.

[#PM-ARCH-3]
=== PM-ARCH-3: STDIO Host Transport, Local Relay & Frontier Protocol Compliance

The harness of every worker must connect over the Model Context Protocol (MCP) `stdio` transport, relayed to the always-on runtime over a user-private local channel, targeting the frontier MCP `2026-07-28` specification.

* The system must communicate with the harnesses that run its workers (`claude`, `opencode`, `antigravity`, `codex`, and every harness the operator added) exclusively over standard input (`stdin`) and standard output (`stdout`) of the job relay `pm-mcp serve --job`.
* The relay must forward MCP messages in both directions (requests, responses, and notifications) between the host and the runtime without interpreting them beyond the closed relay rules (`PM-SEC-4`), preserving JSON-RPC `id` values. The runtime sends no elicitation: MCP elicitation is no channel of the operator (`PM-WF-20`).
* The runtime must send no message unrelated to a pending call: its tool, resource, and prompt surface is fixed per connection and every next step arrives in the answer to the host's own call, so it must never send a list-changed or resource-updated notification. It must acknowledge a host's `subscriptions/listen` at once and must send no further message on that stream for as long as the host holds it open.
* The runtime must serve MCP only over a Unix domain socket restricted to the owning OS user, never over a TCP or UDP listener apart from the loopback fallback of `PM-SEC-4`.
* The relay must reserve `stdout` strictly for newline-delimited JSON-RPC 2.0 MCP messages and route all diagnostic logging to `stderr`; the runtime logs to `<PM_MCP_BASE>/logs/daemon.log`.
* The runtime must speak the MCP `2026-07-28` protocol version only, without an MCP session (it must issue no `Mcp-Session-Id`, also not on `initialize`) and without fallbacks to legacy protocol versions. The relay must also accept the session-opening form of MCP `2025-11-25` from hosts that use it (OpenCode): it takes the protocol data of the host's `initialize` and forwards every later request as a sessionless request carrying that data; the protocol version `2024-11-05` is not accepted.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification] for implementation details.

[#PM-ARCH-4]
=== PM-ARCH-4: Stateless Requests & Explicit Scope Addressing

The system must operate without transport-level session state, evaluating every request entirely from explicit scope identifiers and persisted filesystem records.

* The system must process every MCP request statelessly, including at the transport: the runtime keeps no MCP transport session and no per-connection state. The relay attaches the host's `initialize` data (protocol version, capabilities, `clientInfo`) and its connection metadata to every forwarded request, so each request is self-describing and a runtime restart loses only the requests in flight.
* The system must require every stateful workflow invocation to carry an explicit logical scope identifier (`plan_id`, `epic_id`, or the reserved `plan_id` value `NO_PLAN` for the project's one workspace scope or, for a task of the machine scope, the machine scope, resolved from the job record, `PM-TOOL-1`) and, when addressing an entity-specific transition, the entity identifier within the link ID.
* The system must resolve the client profile of a worker's call from its job record and the target project root exclusively from the project's enrolment (the enrolled `project_root` of the per-project machine store the scope lives in), rejecting client-supplied working directory or client-type overrides.
* The system must answer every workflow query and validate every transition entirely from persisted filesystem state, guaranteeing zero state loss across host restarts, worker replacements, context compactions, or process restarts.
* The system must distinguish exactly three classes of MCP request, all of them a worker's and bound to its job, taking their project, role, and generation from the job record its job token resolves and never from a header or an argument (`PM-SEC-4`): *scope-addressed* requests carry `plan_id` (a plan id, or `NO_PLAN` for the project's workspace scope, which also hosts a pending entry of a start, addressed by its `entry_id` as `entity`, `PM-TOOL-1`) or `epic_id`, and the entity where applicable, and every call is checked against the task entities leased to its generation; *resource reads* (`resources/read`, `resources/list`, `resources/templates/list`) read only within the worker's own project and `skill://pm/...`; the one *connection-bound* request, `pm_wait`, takes no scope and resolves its caller, role, generation, and project from the calling connection (`PM-TOOL-1`, `PM-SEC-4`). There are no other requests without a scope; a scoped tool called without `plan_id` or `epic_id` is refused (`PM-TOOL-1`). The local API addresses a plan, an epic, and an entry at its top level by its id (an entry is created under its project), and a project by its `project_id` (`PM-ARCH-11`).
* The system must verify, for every request of a client of the operator that names a project or a checkout path, that it names an enrolled project (a checkout path resolved by the rule of `PM-SEC-2`), refusing the request with `project_not_enrolled` otherwise; the onboarding of a project is the one request that names a checkout not yet enrolled.

[#PM-ARCH-5]
=== PM-ARCH-5: Worktree-Bound Plan Execution & Main-Bound Epic Location

Plan state must live outside the repository and plan execution must be isolated inside worktrees to protect the main checkout; git-tracked epic state belongs to the repository's main branch, is edited only in the one shared epic worktree, and reaches the main branch only through a branch merge.

* The system must keep a plan's state directory in the per-project machine store `<PM_MCP_BASE>/projects/<project_id>/plans/<plan_id>/` for the plan's whole life and never move it; a plan worktree (`.marshall/local/worktrees/<plan_id>/`) is only a git checkout created for execution and finalize and removed afterwards, and the plan's `mcp/status.json` records its `worktree_path` (or `null` while none exists).
* The system must clear `worktree_path` in the same transaction that records a worktree's removal, so that no store keeps pointing at a removed worktree.
* The system must keep no state in the repository's git-ignored `.marshall/local/`, which holds only worktrees and temporary files, so that deleting it loses no plan data.
* The system must ensure that the repository's main checkout working tree remains clean and unaffected by uncommitted plan execution artifacts at all times.
* The system must isolate all mutations to git-tracked epic state (epic ledgers, inbox messages, landing records, and epic specifications) within one shared, long-lived epic worktree on one fixed branch, incorporating changes into the main branch strictly through a monitored branch landing that never removes that worktree.
* The system must resolve every read and write of git-tracked epic state, including those made on behalf of child plans, to the shared epic worktree copy, and must never treat the primary checkout's copy as authoritative while the epic worktree exists.
* The system must resolve any plan directory and its worktree from its `plan_id` without requiring the client or model to provide filesystem paths.
* The system must start every job in the working directory that matches the plan's worktree presence at job start (the worktree root while the plan's persisted `worktree_path` is set; the main checkout while it is `null` and for plan-less jobs; only the `zero_tool` workers, the injection screener (`PM-SEC-1`) and the qualification judge (`PM-WORK-6`), and the qualification items that carry their own corpus context (`PM-WORK-6`) run in an empty job-private directory); the system must never run a job that removes a worktree with a working directory inside that worktree, and scripts receive the plan identity only through their own arguments.

[#PM-ARCH-6]
=== PM-ARCH-6: Filesystem State Persistence & Cache-Only Process Memory

All durable workflow and coordinator data must reside in structured filesystem stores, with process memory functioning strictly as a transient cache.

* The system must persist all authoritative workflow states, tasks, findings, references, locks, build jobs, and audit events directly in filesystem files formatted as JSON or JSONL.
* The system must treat all in-memory process data structures as disposable caches, ensuring that any process exit, crash, or restart leaves persistent state intact and uncorrupted.
* The system must store credentials exclusively within the credential store the operator chose, the operating system credential store or the permission-guarded file store (`<PM_MCP_BASE>/credentials/`, `PM-CRED-2`), keeping secrets in process memory only for the duration of the active request.
* The system must include a mandatory `format_version` integer property in every persisted JSON and JSONL state file, including the operator files (`machine-config.json`, the per-project `local-config.json`, the enrolment files, the harness enrolment `harnesses.json`, the machine's host tools `host-tools.json`, the remembered consents `consents.json`, the model catalogues and role assignments of the machine and of a project, and the credential files of `PM-CRED-3`).
* The system must validate the `format_version` of every store it reads and accept exactly the binary's current version, refusing any other with a named reason (`format_outdated`, `format_newer`) and never migrating a store on runtime start; the git-tracked team configuration and workflow units are never rewritten by the runtime on its own: a new binary's default changes reach them only through the project setup workflow (`PM-EXT-7`), and a unit changes only when the operator places or removes it (`PM-WF-22`).

[#PM-ARCH-7]
=== PM-ARCH-7: Runtime & Relay Lifecycle, Crash Recovery & Job Drain

The runtime must run continuously and recover deterministically from crashes, while relays come and go with host connections without affecting runtime state or jobs.

* The system must start the runtime on demand when a command of `pm-operator` that needs it finds none running, detached from the command's process group and session so that nothing that ends the command terminates it, and must optionally support start at login through the per-user OS service manager; on-demand start stays the default on every platform.
* The system must ensure that relay termination (`stdin` EOF or signals) closes only that host connection and never cancels, drains, or kills jobs or alters persisted state.
* The system must provide the inspection and lifecycle verbs of the operator CLI: `pm-operator status` to inspect the runtime, active plans, build slots, and running jobs across the machine through the local API, reporting the runtime `running` only after an authenticated round trip and `not running` from the absent or dead runtime record without starting it; and `pm-operator drain` to stop the runtime gracefully before an upgrade by signalling the recorded runtime process after verifying its PID and start instant.
* The system must report to the operator as `stalled` (in both clients of the operator, `pm-operator status`, and the epic view) every non-terminal plan or epic that is neither paused nor in an operator wait, has no pending condition, awaits no event, and whose last transition or task progress is older than a compiled threshold, as a hold with its acts (`PM-WF-23`), record one `plan_stalled` audit record per stall episode, naming the cause, and never show it in a model-facing representation; a plan or an epic in an operator wait is shown as waiting for the operator, never as stalled; a role the supervisor stopped serving is reported to the operator by the start-failure guard (`PM-WORK-3`), and its tasks take their fallback.
* On `SIGTERM`/`SIGINT` (including via `pm-operator drain`), the runtime must stop admitting new jobs and offering new tasks, end idle warm workers, allow running jobs, tasks, and in-process operations to finish up to the configured drain timeout, record the remaining jobs as `killed`, release their build and model slots and task leases (their tasks are offered again after the next start) (merge-queue and review-bot leases are left in place, become orphaned at the next start, and are adopted or released by the recovery evidence rules exactly as after a crash), terminate warm LSP child processes, and exit cleanly.
* The system must detect a version mismatch between an installed binary and the running runtime during relay connection and `pm-operator status`, and recommend the restart of the runtime to the operator, never in a model-facing representation; a client of the operator compares its version with the runtime's on its first request and says so when they differ.
* The system must start the runtime in a fixed order: acquire the singleton lock first (a runtime that loses it exits immediately with status `0` without writing anything, audit records included), remove a stale socket and stale runtime record only while holding that lock, verify directories and permissions, run only bounded verification (audit chain head and incremental chain, workflow definitions), write a fresh runtime token, bind the socket, and become ready; no store is migrated at start (`PM-ARCH-6`), and enrolment integrity is verified per project in its recovery.
* The system must recover each project's state after bind, lazily on the first call addressing the project and in a background pass, and must never serve a call addressing a project before its recovery has finished: such a call waits for it, bounded, and on expiry returns the retryable error `runtime_recovering`. Recovery must mark leases served by a dead runtime instance as orphaned so that their owning scope (plan, epic, or workspace) adopts them on its next transition, releasing a lease only on positive evidence of abandonment, roll forward any interrupted per-scope transaction journal, and mark orphaned `running` jobs, workers included, as `killed` without blind re-execution, fencing their generations and returning their leased tasks to the queue, signalling nothing for a job spawned before the current system boot or whose record never received its PID (a job counts as running only after its record carries `pid` and `process_started_at`) and otherwise terminating its process group if still alive; a workflow state bound to such a job settles with the outcome `killed`, which its workflow routes explicitly, and no job is started again except through a declared transition. A paused plan stays paused and a pausing plan holds at the point its pause names (`PM-WF-23`).
* The system must let the operator stop the runtime by its drain or at once, withdraw a drain the operator asked while it runs, restart it, and upgrade it to a newer release from the organisation's registry, through operator endpoints of the local API usable from the operator CLI and from a paired device, tell every client of each step, and undo an upgrade whose new release does not start. A stop at once is the drain with its wait cut to zero, settled as after the drain timeout so that the recovery resumes what ran; a restart has the successor started by the on-demand start, or by the service manager where it runs the runtime; the check for a newer release runs only on the operator's consent (`PM-SEC-8`); `pm-operator drain` stays the signal that works in every state of the runtime, and a drain it starts cannot be withdrawn. The credential the runtime presents to the registry and the form of a release in it are open: see link:discussions/open-questions.adoc#registry-credential[Open Questions].

[#PM-ARCH-8]
=== PM-ARCH-8: Server-Driven Continuation & Connection Independence

A plan or epic is carried by persisted state and continued by the server, never by a connection or conversation.

* The system must identify a plan or epic solely by its `plan_id` or `epic_id` and represent it solely by that scope's persisted files.
* The system must execute every mutating call as exactly one state transition that is fully persisted before the response is returned, so that a lost response never loses or duplicates a transition.
* The system must continue every plan and epic by itself after its creation, whether or not a client of the operator is open, halting a scope only in an operator wait (`PM-WF-20`), a pause the operator set, or a hold (`PM-WF-23`), and must let either client view it over the local API at any time, with identical results for identical persisted state.
* The system must bind the connection of a worker to its job and generation: it is authenticated by the job's own token, may address only the task entities leased to its generation with its tools, reads resources only read-only and only of the worker's own project, and carries no other identity (`PM-SEC-4`, `PM-WORK-2`).
* The system must allow several workers and both clients of the operator to address the same scope concurrently, serializing mutations through the scope lock (`PM-WF-4`); of two operator acts on the same decision or setting the first valid one wins and a later one made against an older revision is refused (`PM-ARCH-11`).
* The system may vary connection-dependent rendering (bounded vs. progress waits) by the capabilities of the calling host connection, never by persisted state differences.

See the link:specification/runtime-model.adoc[Runtime & Interaction Model Specification] for implementation details.

[#PM-ARCH-9]
=== PM-ARCH-9: Runtime Metrics

The runtime must keep figures of its own, so that the operator sees in both clients what the machine runs and uses, now and over time, without the runtime reading its stores to answer.

* The system must keep the figures of the runtime as metrics, counters, gauges, and timers from a closed catalogue, each maintained where the event it counts happens and never computed by reading the stores on a request; must serve them to both clients of the operator as a snapshot and as live updates; must show a figure it cannot measure as unavailable, never as zero; and must keep them on the machine, never sending them anywhere.
* The system must keep one registry of named metrics, each name with exactly one writer, its unit, and its labels from the catalogue, covering the runtime itself (version, start, uptime, memory, CPU, disk use of the machine store, the listeners), the work (plans and epics by activity and project, tasks, workers, jobs, slots, locks and leases), and the models (calls, tokens with their split and coverage, errors and retries per model and role), and no money figure (`PM-WF-14`).
* The system must set the work's figures from the recovered state at every start and fill the models' figures from the task rows of the metrics stores and the machine's usage aggregate, which stay the truth (`PM-ARCH-6`); unmeasured usage is counted as unmeasured, never as `0`.
* The system may serve the metrics in the OpenMetrics text format, on the runtime's socket only, to a tool of the operator that holds the runtime token; it opens no listener of its own for them (`PM-SEC-4`). The library that implements the registry is open: see link:discussions/open-questions.adoc#metrics-library[Open Questions].

See the link:specification/runtime-model/01-processes-and-transport.adoc#runtime-metrics[Runtime & Interaction Model Specification, The Runtime's Metrics] and link:specification/timeouts.adoc[Timeouts & Budgets Specification] for implementation details.

[#PM-ARCH-10]
=== PM-ARCH-10: One Cleanup of Work History & Automatic Removal of Residue

Work history is the operator's and goes only on the operator's word; technical residue needs no judgement and goes by itself.

* The system must delete work history (archived plans, archived epics' machine stores, the logs of ended work, read reports, and the machine stores of unenrolled projects) only through one cleanup the operator confirms in either client: it must find once a day what has been ended for longer than its configured duration, tell the operator by one report (`PM-WF-21`), show what would be deleted as a summary and item by item, and delete, postpone, or keep it as the operator chooses, auditing every deletion; and it must remove technical residue by itself, each removal audited.
* The system must never count as due live work, a pending entry, an unread report, an archived plan with an undischarged owed item, an item the operator kept, or an item of an open or postponed cleanup; the durations are machine values with a project's own value for its plans, epics, and logs, each at least seven days or `never`.
* The system must leave a tombstone in place of a deleted archived plan or epic, so that its identifier is never allocated again and what refers to it resolves to its deletion, and must add what a deleted plan used to the machine's usage aggregate before its metrics rows go, so that no figure of the runtime's metrics goes down (`PM-ARCH-9`).
* The system must remove technical residue (the workspace's technical rows, retired lesson bodies, ended queue task records, daemon store directories no longer the project's, worker directories of ended jobs, stale leases, temporary files and caches, rotated audit files past their retention) in the periodic sweep, under the evidence rules of the removal sweeps (never on absence of evidence); `pm-operator sweep` lists or runs that pass at once and never offers work history.

See the link:specification/timeouts/03-retention-host-config.adoc#cleanup[Timeouts & Budgets Specification, One Cleanup], link:specification/filesystem-layout/03-project-store.adoc#archives[Filesystem Layout Specification, Plan & Epic Archives], link:specification/identifiers.adoc[Identifier Registry], link:specification/runtime-model/02-startup-recovery-drain.adoc#periodic-sweep[Runtime & Interaction Model Specification, Periodic Sweep], and link:specification/store-schemas/12-machine-stores.adoc#cleanup-journal[Store Schemas Specification, Cleanup Journal (`<PM_MCP_BASE>/state/cleanup.jsonl`)] for implementation details.

[#PM-ARCH-11]
=== PM-ARCH-11: The Operator's Two Clients & Their Contract

The operator works with the system in two clients, the web app and the terminal client, which show the same state and offer the same acts; the runtime gives them one contract over the local API, independent of any harness or model.

* The system must serve the operator only through the web app and the terminal client (`pm-operator`): every operator wait (`PM-WF-20`), operator act, and view is offered to both over the local API with the same state, proposal, and texts, a run started in one continues in the other, and every act is audited with its channel (`web` with the paired device, or `cli`); no harness, session, or model relays the operator's words or choices.
* The system must give the clients a representation of every state that needs the operator (its kind, facts, proposal, and the operator's links as operator endpoints of the local API) and of every resource they show, never a model-facing representation, and one closed catalogue of named events with their payloads, streamed per scope (the runtime, a plan, an epic, a project's workspace, the machine, an entry) with one envelope and one resume rule.
* The system must let both clients read, without reading a ledger or a store themselves: the projects of the machine with their display name, readiness, running work, and the operator's favourites and recent use; what needs the operator at a glance (`needs_operator`, derived on read per plan, epic, and project from a closed list of kinds); a plan's process as a structure with the state of every node, from the plan's append-only history; what each worker does (its activity, kept per task, `PM-WORK-7`, `PM-SEC-1`); the epic with its rows, registers, and sources; and the ended work of a project with its outcomes.
* The system must refuse a change of a recorded value (a machine setting, a project's operator value, a plan's own value) made against an older revision of it with the code `conflict`, never merging or overwriting a change unseen; of two answers to one decision the first valid one wins (`PM-WF-12`).
* The system must keep every text a client shows in one message catalogue per language in `pm-api`, with English complete and every other pack checked against it at build time, keep two languages apart (the interface language of every text shown to the operator and the model language a model is told to write and read in, defaulting to the interface language), carry every runtime text to the clients as a message key with its arguments, and carry external and model text (a provider's answer, a harness's error text, question content) verbatim and marked as such; identifiers, commands, options, and the domain vocabulary are never translated.
