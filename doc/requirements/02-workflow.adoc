== Hypermedia Workflow Engine (PM-WF)

[#PM-WF-1]
=== PM-WF-1: Hypermedia State Representation (HATEOAS)

The system must model all plan and epic workflows as hypermedia state machines adhering strictly to HATEOAS principles. Clients discover valid operations exclusively through server-generated representations and links.

* The system must return workflow states as TOON-formatted text representations containing: `scope` (`plan`, `epic`, `workspace` for the project's workspace scope hosting `project-setup`, `machine` for the machine's one scope hosting its onboarding (`PM-WF-26`), or `entity` for a task entity of a worker or a pending entry of a start addressed by its `entry_id`), `plan_id` or `epic_id` (neither for `workspace` and `machine`), `state` (dotted closed-enum), `summary` (single-line human-readable status), optional `skill` (URI to a static vocabulary skill), `facts` (minimal key-value pairs required for model judgment), and `links` (list of valid transitions).
* The system must drive every plan and epic itself (`PM-ARCH-1`): a state that needs no model is server logic, a state that needs one is a task of a role (`PM-WF-5`, `PM-WORK-2`), and a state that needs the operator is an operator wait (`PM-WF-20`). Model-facing links are offered only on a worker's task entities; the operator's links of an operator wait are operator endpoints of the local API served to the operator's clients (`PM-ARCH-11`), never part of a model-facing representation, and a plan or epic representation is otherwise a view whose `links` list is empty. Each followed link immediately returns the subsequent representation of the entity it addressed.
* The system must omit large artifacts, raw build outputs, and detailed task definitions from `facts`, exposing them instead as read-only MCP resource URIs (`pm://...`).
* A plan or epic must reach an immutable terminal state whose phase value is `completed` or `aborted` (terminal state identifiers always map to one of these two phase values); a task entity or a pending entry of a start (scope `entity`) ends in a terminal state of its entity unit, which never ends the scope that hosts it; the `integrity_breach` pause offers no model link, its only resolutions being operator acts (`PM-WF-3`); the workspace scope and the machine scope have no terminal state, because every setup run ends in the terminal `setup.completed` of the sub-workflow `project-setup`, which returns to the project's onboarding, and the project's workspace scope rests in `project.completed`, whose `reconcile` and `aspect` links start the next run, as the machine scope rests in `onboard.completed` (`PM-WF-26`); each scope type must have exactly one abort terminal state (`plan.aborted`, `epic.aborted`), reachable from every phase and entered only by an operator act that ends the scope (`PM-WF-23`: cancel, abandon, the integrity abort), the release of its project, or `delete-plan`, and no phase-specific abort terminal; a sub-workflow must be left early only with the control outcome `stepped_out`, returned to its caller by the server when the sub-workflow's attempts or bounded retries are exhausted, or by the implicit `step_out` link an operator wait of the sub-workflow offers (`PM-WF-16`), and never ends the plan or epic; a condition whose self-remedy budget is spent unwinds every call frame to the phase's fallback (`PM-WF-3`).
* The system must end every plan in exactly one outcome of a closed list. A plan that runs to its end takes one of four, each reached only through `finalize.archive-plan` after the post-run band: `merged` (the terminal `completed`, which always carries its `merge_outcome`, `PM-WF-13`: the work landed on the base branch, through its pull request by `landing.pull-request` or pushed onto the base branch by `landing.main`, `PM-WF-25`), `handed_back` (the work delivered as an open pull request, a draft after a fallback and ready for review when the plan's asking axis leaves the merge to the operator and the pre-merge barrier passed, as a branch where no pull request can exist, or, with `landing.files`, as uncommitted changes in the working tree, with the gaps documented), `returned` (the planning result only, nothing implemented), or `no_change` (the terminal `completed`: a recipe run whose harvest yielded no targets, without a commit or pull request, `merge_outcome: no_pr`); the terminal states of `handed_back` and `returned` map to the phase value `completed`. A plan ended by the operator or its project takes one of four more, each through `plan.aborted` with its reason and archived like a completed plan: `cancelled` and `abandoned` (the operator's end of a running and of a paused plan, `PM-WF-23`), `released` (the release of its project, whatever the plan's state), and `aborted` (the abort that resolves an integrity breach, `PM-WF-3`). Every blocking condition of a plan must end in a bounded self-remedy followed by a defined fallback to `returned` or `handed_back` (`returned` while the plan branch has no commit beyond the base and `handed_back` once it has, in every phase until the merge: the Phases 1–4 fallback `plan.return` forwards a plan with committed work to the hand-back, and the Phase 5 fallback returns a plan without; none after the merge). A plan halts only in an operator wait (`PM-WF-20`), which halts its own scope and nothing else, in a pause the operator set (`PM-WF-23`), or in an integrity breach (`PM-WF-3`). The landing record carries the outcome.
* The system must ensure that the model requires no advance knowledge of the state machine graph, never composes CLI commands from prose instructions, and never encounters transitions that are invalid in the current state.
* The process must stay server-enforced when the team owns its workflow units (`.marshall/config/*.pmwf`, `PM-IMPL-5`): the server executes only units that pass the static verification rules and the invariants compiled into the binary for every phase, and a unit can only compose compiled primitives and enrolled project scripts; a changed unit reaches a running plan only through a re-composition of the plan's instance that the server adopts (the audited `config_drift` condition, `PM-IMPL-5`).

[#PM-WF-2]
=== PM-WF-2: Closed Link Relation Grammar & Link Forms

State transitions must be structured as hypermedia forms using a closed vocabulary of link relations and typed parameter declarations.

* The system must restrict link relations (`rel`) strictly to the closed enumeration of 9 relations: `next` (default forward transition), `alt` (alternative forward path), `retry` (repeat after transient failure), `fix` (remediation sub-state), `loop_back` (bounded backward transition to an earlier phase), `submit` (hand a judgment artifact to the server), `escalate` (file a waiver request, which only the operator answers, `PM-WF-12`), `consult` (ask another role through the server, `PM-WORK-4`), and `abort` (leave a sub-workflow through `step_out`; ending a plan or an epic is only an operator act, `PM-WF-23`). Waiting on a job and cancelling it are engine events, never links.
* The system must structure each offered link using one of 2 closed interaction form shapes (`submit`, `noop`) consisting of: `rel` (relation from closed enumeration), `link` (transition identifier optionally qualified by entity, e.g. `submit:TASK-003`, `ask:TASK-003`), and `free` (comma-separated list of typed parameters required from model judgment); the options of a decision are defined once, in the representation that offers them.
* The system must execute all link transitions through a single uniform MCP tool verb: `pm_do(plan_id | epic_id, link, args?, scope?, entity?)`, where `plan_id` may be the literal `NO_PLAN` for the project's workspace scope or, for a task of the machine scope, the machine scope, resolved from the job record (`PM-TOOL-1`).
* The system must derive all execution context (worktree paths, git branch names, build commands, and upstream parameters) server-side from the `link` identifier and persisted state, requiring the model to supply only judgment values via `args`.
* The system must accept all model-authored multi-line text artifacts (commit messages, pull/merge-request bodies, review replies, clarified request documents, solution outlines, task descriptions, lesson bodies, and ADR bodies) directly in-band as typed UTF-8 string parameters in `args`, never through `plan-marshall`'s multi-step temp-file and path-allocation patterns (`.plan/temp/*-commit-msg.txt`, `work/ci-bodies/`, `work/pending-tasks/`, `work/lesson-body-*.md`, `prepare-body`, `prepare-comment`, `prepare-add`, and `resolve-path` followed by host `Write`).

[#PM-WF-3]
=== PM-WF-3: Capability Enforcement by Link Omission

The hypermedia engine must enforce workflow capabilities and security boundaries primarily by omitting forbidden transitions from state representations.

* The system must enforce capability and privilege boundaries by omitting unauthorized transitions from the `links` list of generated representations.
* The system must never emit operator-only transitions (answering an operator wait, setting or revoking or declining a waiver, pausing, starting, cancelling, or abandoning a plan, ending an epic, resolving an integrity breach or another hold, deleting plans, or modifying project enrolment) as links in model-facing representations.
* The system must restrict privileged and operator-only actions exclusively to the operator's two clients (`PM-SEC-3`: the terminal client and a paired web device, the CLI-only actions of `PM-SEC-7` excepted); MCP elicitation is never a channel of the operator.
* The system must independently evaluate and reject any transition call targeting an unoffered or omitted link, returning a structured rejection alongside the current valid representation.
* The system must record engine-raised conditions (a footprint violation, an indeterminate guard, an incomplete task, an unmet operator-side precondition such as a missing credential or a changed team configuration file, configuration drift, an integrity breach) as a condition overlay on the scope's current state, never as a state change: the current state and the sub-workflow call stack stay unchanged, and the representation names the condition; a condition that needs an act of the operator is a hold, which the clients show with its acts (`PM-WF-23`). Every condition except an integrity breach runs its self-remedy, bounded by a compiled budget per condition instance: the server retries where a retry can clear it, and where clearing it needs judgment or work, a task of the role whose work raised it (for example `fix` of a footprint violation by the plan's writer role); the operator may remove the cause at any time, and when the budget is spent the plan takes its phase's fallback (`PM-WF-1`) with the condition recorded as the gap; on the epic scope, which has no such fallback, the retries continue and the condition is held for the operator in both clients until it is repaired or the epic is cancelled; on the workspace scope a spent budget enters the setup's repair state (`setup.needs-repair`). An integrity breach (`integrity_breach`: a tampered plan, epic, or workspace store, a tampered lesson, or a tampered project enrolment; a tampered harness enrolment is no breach but an unmet precondition of the worker launch, `PM-EXEC-1`) pauses the affected scope (for an enrolment, every running plan of the project; for a lesson, the lesson source of every start fails with the reason) without a model link and without a bound, refusing every `pm_do` and offering no task of the scope, with `integrity_paused`, as a hold that shows the operator the tampered file with its recorded and current size and digest, never a restore or a diff, until the operator accepts the file as it is (`accept-edit`, after the engine re-verifies) or, for a plan or epic only, ends the scope by the abort (a plan with the outcome `aborted`, an epic as `cancelled`); a workspace store, a lesson, or an enrolment is resolved only by `accept-edit`, and a pending entry of a start by `accept-edit` or by abandoning the entry.

[#PM-WF-4]
=== PM-WF-4: Entity-Scoped Links & Fine-Grained Concurrency

Transitions operating on sub-components of a plan must address entities explicitly, ensuring safe concurrency across parallel workers and operator acts.

* The system must allow links to address specific sub-entities of a plan or epic by embedding the entity identifier within the link string (e.g. `submit:TASK-003`, `ask:TASK-003`).
* The system must execute validation, state mutation, and persistence as a single atomic operation under the mutual exclusion lock of the target plan or epic.
* The system must validate entity-scoped transitions against the current persisted state of that specific entity, rejecting stale transitions (such as submitting an already completed task) while allowing concurrent operations on distinct entities.
* The system must guarantee idempotent side effects for state transitions: attempting an already completed external action (such as pushing an up-to-date branch) must report success without redundant side effects, and requesting a build for a running worktree must join the active job.
* The system must handle replayed or stale links (from a compaction, a `/clear`, or a fenced worker generation) safely by rejecting the stale transition (`generation_fenced` for a fenced generation, `PM-WORK-2`) and, for `pm_do`, returning the current valid representation, without raising fatal MCP protocol errors.

[#PM-WF-5]
=== PM-WF-5: Model Work as Role Tasks & Single-Level Leaf Constraint

Every piece of model work inside a plan or an epic must be a task of a role (`PM-WORK-1`), done by a single-level leaf worker that the server itself launches through the headless command line of an enrolled harness, supervises, and bounds; the host never dispatches a sub-agent, and no model work runs outside a worker.

* The system must package tasks during Phase 4 (`plan`) into envelopes bounded by a configurable per-envelope token budget, delivering each envelope's current task within its task entity's representation (`PM-WF-14`).
* The system must bind every model step to a job state naming a role (DSL `job llm <entity_kind> role <role> [each <primitive_id>]`), whose completion is an engine event, never a link a model polls: a state declared with `each` fans out over a server-computed list into one task per element, each with its own entity, and completes when every entity has its required submission or its fallback.
* The system must compose every worker's launch server-side and record it in the worker's job record: the harness, model, and effort from the role's effective values (`PM-WORK-1`: its artifact, overlaid by the role assignments of the machine and of the project and by a plan override, `PM-WF-14`), the argument vector from the harness's client profile (`headless` template: an inline named agent where the harness offers one, per-call flags otherwise; nothing is installed), the working directory (the plan worktree, else the project checkout, so that project instructions and skills load natively), the server-composed launch prompt (`PM-SKILL-4`), a strict per-call MCP configuration that starts only the job relay `pm-mcp serve --job` (`PM-SEC-4`), and the job token and generation in the relay's environment.
* The system must give a worker exactly the tools its role artifact names, within the bound its role's class sets (`PM-WORK-1`): every role except `zero_tool` names the five protocol tools `pm_wait`, `pm_state` and `pm_do` (on its own task entities), `pm_skill`, and `pm_skill_file`; `writer` roles may additionally name `pm_build` and `pm_lsp`; `read_only` roles may name `pm_lsp` limited to its read operations (`rename` is refused with `invalid_arguments`) and never `pm_build`; `zero_tool` workers get no tool and no PM-MCP connection.
* The system must enforce the single-level leaf constraint: a worker reaches PM-MCP only through its job-bound connection, which offers its role's tool set, the links of the task entities leased to its generation, and read-only resource reads (`resources/read` and `resources/list`: every resource of the worker's own project plus `skill://pm/...`, the project boundary being the only read boundary, `PM-TOOL-3`), and never a scope-creating action, an operator action, or a link that starts a model; a consultation goes through the server (`PM-WORK-4`).
* The system must require a worker to persist deliverables only through its task entity's `submit` links and to raise a question only as a question record (`PM-WF-12`); the server evaluates a task only from persisted records, never from a worker's exit status or final output.
* The system must observe every worker's end itself and record its fate (`succeeded`, `failed`, `timed_out`, `killed`, `cancelled`, `indeterminate`, or `refused`) in its job record, bounded by a per-role budget learned above compiled floors; a fresh worker's job ends after its one task, a warm worker's job after its generation; a call carrying the token of an ended job is refused (`job_ended`).
* The system must run every `zero_tool` worker (the injection screener of `PM-SEC-1` and the qualification judge of `PM-WORK-6`) fresh, with the server-fixed prompt of its role, an empty job-private working directory, no PM-MCP connection, one turn, and project and user settings disabled where the harness allows, and must accept its structured final result only when it validates against its role's result schema.

[#PM-WF-6]
=== PM-WF-6: Independent Server-Side Transition & Parameter Validation

The workflow engine must strictly validate all transition attempts and free parameters server-side, treating client calls as untrusted input.

* The system must validate every incoming `pm_do` invocation against the persisted state of the addressed scope independently of how the client constructed the request.
* The system must verify that the requested link ID exists within the set of valid transitions for the current state and that any addressed entity is currently in an accepting sub-state.
* The system must validate all supplied free parameters (`args`) against the link's closed JSON schema, enforcing `additionalProperties: false` and strict type conformity.
* For `submit` transitions carrying document or prose payloads (such as `outline.md`, `request.md`, Conventional Commit messages, PR bodies, or ADR AsciiDoc), the system must run the domain validator (`OutlineValidator`, `AsciiDocValidator`, `ConventionalCommitValidator`) in-process on the submitted parameter before atomically persisting the target store, making unvalidated store writes structurally impossible.
* The system must reject any invalid transition, malformed parameter payload, or failed content validation with a structured validation error payload that includes the rejection cause and the current, unmutated state representation.

[#PM-WF-7]
=== PM-WF-7: Remediation Policies, Loop-Back & Iteration Bounds

Remediation loops from finalize back to execution must be strictly bounded and confined to active worktrees.

* The system must allow `loop_back` transitions returning a plan from Phase 6 (`finalize`) to Phase 5 (`execute`) only while the plan remains located within its dedicated worktree.
* The system must eliminate `loop_back` transitions by link omission immediately once the plan passes the pre-merge barrier and its worktree is removed.
* The system must allocate fresh, additive remediation tasks and envelopes within the worktree for each loop-back iteration, never reopening previously completed tasks, and must serve them as new tasks with their own task ids to preserve additive metric accounting.
* The system must bound a loop-back from Phase 5 or finalize to `phase-3-outline` (a re-planning decision, `PM-WF-17`) by a compiled loop-back budget of `1`, raisable only by an operator raise waiver of its own budget identifier (`fix_budget:outline-loop-back`): it returns to the lane's outline authoring state, keeps the plan's worktree and its committed work, composes new plan instance versions at the outline and plan events without rewriting history, and on exhaustion hands the plan back when Phase 5 committed work, otherwise returns it.
* The system must handle every failure class of a plan (Q-Gate findings, build failure, CI failure, analysis-provider failure, review findings and missing review evidence, merge conflict) through a remediation policy, a project-owned DSL sub-workflow unit per class (`remediation.qgate-findings`, `.build-failure`, `.ci-failure`, `.analysis`, `.review-findings`, `.merge-conflict`): the server gathers the evidence (structured failures with fingerprints, logs only as untrusted resource URIs) and composes the facts of the decision with the evidence it rests on, the policy's decide step is a task of the policy's role (`PM-WORK-1`), which chooses one action of a closed set the server validates (`retry` with a reason, bounded by the retry budget; `fix`, bounded by the fix budget, which is the loop limit; `loop_back`, the form of `fix` that runs as Phase 5 remediation tasks, bounded by the fix budget; `request_waiver` with a rationale, offered only for a waivable gate, whose waiver request is an operator wait answered by `waive` or `decline`, `PM-WF-12`), and the unit returns only its reachable outcomes of `resolved`, `waived`, `exhausted`, and `fix_requested`, plus the control outcome `stepped_out`; every remediation policy has a decision step whose role the unit names, and whether a task decides follows only from the bound actions and budgets: where they leave only one action, the server takes it without a task, and while the role is unqualified its tasks take the conservative fallback of `PM-WORK-6`; every caller routes `exhausted` and `stepped_out` to its phase's fallback (`PM-WF-1`), except that in Phase 5 and in finalize before the merge `exhausted` first raises re-planning (`PM-WF-17`; except in the `land` lane).
* The system must bind the budgets (retry and fix) as call arguments of the project-owned phase units, capped by compiled hard limits, with the shipped values and hard limits of the link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/timeouts/01-job-budgets-and-waits.adoc#remediation-budgets[Timeouts & Budgets Specification, Remediation Budgets]; budgets are counted per plan and failure class, persisted, and never reset; a re-planning that re-enters execution renews the allowance once, counted from the counter at the re-entry (`PM-WF-17`). The attempts of a server-rule retry and of a compiled condition budget counted outside a condition are persisted in the scope's status as well, in the same write as the retry they count, so a runtime restart or a drain never resets them; such a count is cleared only by the state that counts it, when its retry ends, and by the engine, when it leaves the sub-workflow call frame whose state counted it. A retry or fix budget beyond its bound value can only be raised by an operator waiver (`--raise`, `PM-SEC-3`), which never exceeds the compiled hard limit; revoking a raise lowers the ceiling at the next budget check.
* The system must require every workflow step or verification layer that invokes the model (Q-Gate, pre-submission self-review, simplify, finding triage, any judging model) to declare a design-time ceiling on its iterations and tasks in its step definition; no model-invoking loop may be unbounded, and no per-tool-call model gate may exist without a stated ceiling on its tasks.
* The system must hold no plan to a limit of the tokens it uses: no plan is re-planned, held, or handed back for what it used; usage is recorded and reported only (`PM-WF-14`).

[#PM-WF-8]
=== PM-WF-8: Asynchronous Job Links & Wait Transitions

Long-running subprocesses and external provider waits must be modeled as asynchronous jobs with bounded polling transitions.

* The system must transition immediately to a job state upon initiating a long-running subprocess or observation (builds, CI status checks, review-bot rate windows, merge queues, and workers, `PM-WF-5`), and must advance the workflow on the job's completion as an engine event; no model polls or cancels a job, and the plan representation shows the job's progress as a view.
* The system must implement the waits a model holds (a worker's `pm_wait`, `PM-WORK-2`, and a running `pm_build`, `PM-TOOL-2`) as bounded blocking calls that return a result or an answer to wait again before the host's limit (`PM-IMPL-4`).
* The system must observe provider state (CI checks, review-bot output, merge-queue membership) at a fixed compiled cadence, with conditional requests where the provider supports them and one shared observation per credential and resource; a provider rate limit must defer the next observation to the stated reset and be attributed as a wait reason, never as a timeout or failure.
* The system must support extended waits with periodic MCP progress notifications when the client profile indicates host support and the request includes a progress token.
* The system must restrict asynchronous job outcomes to a closed enumeration: `succeeded`, `failed`, `failed_unparsed` (build jobs only), `refused`, `cancelled`, `timed_out`, `killed`, and `indeterminate`.
* Composite and workflow primitives (such as the concurrent-wait region) must declare their own closed outcome enumerations per primitive; these are workflow outcomes, distinct from job outcomes, and are subject to exhaustive handling in the workflow DSL (`PM-IMPL-5`).

[#PM-WF-9]
=== PM-WF-9: Composite Wait States & Short-Circuit Failure Handling

Concurrent asynchronous operations during finalization must be coordinated through unified composite wait states with immediate failure short-circuiting.

* The system must represent concurrent finalize operations (such as parallel CI pipeline execution and automated review-bot analysis) as a single unified composite state (`finalize.concurrent-wait`).
* The system must display discrete progress facts for all concurrent operations within the composite representation's `facts` block (e.g. `ci_status: running`, `analysis_status: passed`, `bot_status: pending`, where `analysis_status` aggregates every configured code analysis provider) and complete the composite state as one engine event.
* The system must immediately short-circuit the composite wait upon detecting a hard failure in any constituent job (such as a red CI pipeline): cancel all remaining pending wait jobs and call the remediation policy of the failing class (`PM-WF-7`), one class at a time in the fixed order CI, analysis, review findings; after a `resolved` or `waived` outcome the wait re-observes every class whose verdict is stale at the new `HEAD`. A constituent job that is killed, times out, or ends indeterminate restarts the watch within a compiled restart budget, and then the plan is handed back.
* The system must classify every failed CI check deterministically by the provider's conclusion (failure class) and by the check's log parsed with the build output parsers (failure kind), file it as a finding of source `ci`, and treat a failed required check it cannot classify as blocking; it must not classify a failure as flaky (only the model's bounded `retry` names that reason). A failure is baseline-only, and never reaches the model, when the provider's CI result of the same check on the base (or, only where no provider result exists, a local build of the merge base) shows the same failure fingerprints (`PM-EXEC-6`).

[#PM-WF-10]
=== PM-WF-10: Phase 1–4 Planning Invariants, Lane Ratchet & Artifact Gates

Planning phases (`phase-1-init` through `phase-4-plan`) must enforce deterministic artifact gates, main-checkout cleanliness, and a one-way planning lane ratchet.

* The system must create a plan only through a start, an entry the operator opens in either client of a project (`PM-ARCH-11`) or the server opens for an epic's row, whose states are operator waits (`PM-WF-20`) and which never expires by time: it stays among the project's open entries until it is started, abandoned, or deleted with the release of its project. The start asks only for the plan's sources and its title and id proposed from them; every other option of the plan is asked where the plan first needs it (`PM-WF-25`). A plan starts from a list of sources, to which each source unit adds after gathering and verifying its source and from which the operator removes: `description` (the operator's text, stored by the start itself), `documents` (files or a directory of the checkout or of the operator's home directory, checked against bounds of size and count and never followed out of a directory by a link, copied or, on the operator's choice, moved, `PM-ARCH-2`), `issue` (named by its number in the project's repository or by its URL; another repository read only under the operator's grant, `PM-SEC-2`), `pr` (an existing pull request whose head branch the agent identity can push to, run through the finalize pipeline with the same states, gates, budgets, and landing as every other plan), `lesson` (an active, unclaimed lesson whose premise is checked before the plan exists: an invalid or resolved premise is an operator wait whose `retire` retires the lesson and adds no source, the start going on, and whose `use` carries the premise's refutation into the plan as an amendment of source `refutation`; the lesson is claimed when the plan is created and stays in the lesson store, retired when the plan lands its work (the merge of `landing.pull-request` or the push of `landing.main`) and released on every other end), `local_changes` (the operator's own current changes of the main checkout, captured when the plan is created as the plan's declared footprint, not offered while the project's landing in force is `landing.files`), and `epic_row` (the staged spec section of a queue row the server launches for its epic, `PM-WF-15`). Every source is gathered by the server into the entry's source directory, which moves into the plan at its creation: one manifest naming each source (its kind, its reference, for an issue or a pull request always its URL, its origin, trust, and digest), a source never changed once stored, and an external source fetched by a bounded job, cleaned by the level-1 validator, and stored before the screener reads it (`PM-SEC-1`). A recipe is no source: starting a recipe creates a plan whose process is the recipe's own workflow (`PM-EXT-4`), with parameters validated against the recipe's schema and a plan id derived with a deterministic timestamp suffix. The system must reject phantom plan IDs shaped like UUIDs or lesson IDs.
* The system must route a `local_changes` plan into the `land` lane, which skips refine, outline, plan, and execute task work, runs the verification and footprint checks of execute's exit over the captured changes, and then runs `phase-6-finalize` with every guarantee (step verdicts, pre-merge barrier, landing); the plan never changes the operator's code: its remediation policies are bound with the action `retry` only (no `fix`, no task allocation, no `loop_back`, pruned in its plan instance with reason `land_lane`), and a land plan whose policy is exhausted is handed back with the failure documented, so the operator fixes the branch after the run. The changes captured at entry are the plan's footprint, not entry dirt: the capture is taken once and never repeated, never touches the main checkout's index or refs, keeps a recoverable snapshot of the captured state until the plan's changes are merged (on every other ending the snapshot stays until the operator removes it, and the plan owes its removal), and returns only those captured paths of the main checkout to their committed state whose content is still the captured content, so edits made after the capture are never lost.
* The system must route a `pr` plan into the `adopt` lane, fixed at plan creation and outside the planning lane ratchet like `land`: it skips refine, outline, plan, and execute, composes its plan instance over the pull request's changed files, verifies through the finalize pipeline, and never rebases the adopted branch outside the merge gate; the pull request's changed files take part in the sibling collision check like the declared footprint of every other source.
* The system must record the primary checkout's porcelain state as an entry baseline when a plan is created. A plan writes its state only through server links into the per-project machine store, and server-owned repository writes happen only in worktrees (the plan worktree and the shared epic worktree), so any path modified, staged, or untracked in the main checkout since that baseline, outside the git-ignored `.marshall/local/`, violates the plan's rules: in every phase the server makes no further transition and raises a footprint-violation condition on the current state, attributed to the plan. Dirt present at entry is reported as a fact (`facts.baseline_dirty`), never blocks, and is never offered for revert. A file under `.marshall/config/` (team configuration or workflow unit) changed since entry raises the `precondition_unmet` condition (reason `config_changed`) on the current state, which names the file and the operator's remedy (commit or restore it) and runs only its bounded server `retry` (`PM-WF-3`); a dirty `.marshall/config/` keeps a start from creating its plan and is checked again when the plan is created (`config_dirty`), except for a `local_changes` plan, whose captured change set includes it.
* The system must refuse transitions out of `phase-2-refine`, `phase-3-outline`, or `phase-4-plan` unless the phase's required artifact exists and passes structural validation; no exemption exists.
* The system must route the planning pipeline by lane: a `light` plan skips the `phase-2-refine` states and runs one collapsed light envelope that folds refine without the confidence loop (clarified request, pull-request title), the simple outline, and deliverable derivation together, while a `deep` plan runs the full refine loop, outline, and plan pipeline. The light envelope must still satisfy the phase artifact gates (clarified request and pull-request title, validated outline, passed outline gate); the server records `phase-2-refine` completion when the envelope's submission carries them.
* The system must enforce a one-way planning lane ratchet (`light` -> `deep`): before the light envelope task starts, the server computes a deterministic budget over the declared affected files and their one-hop neighbours resolved from the architecture inventory (escalate when more than 25 files in total or more than 8 declared files), never from a worker's file-read counter; neighbours it cannot resolve send the plan `deep` with the recorded reason; the envelope task may escalate by judgment (false premise, cross-module ripple, public symbol deletion); unknown scope estimates bias to `deep`; and light-to-deep escalation executes as a first-class engine transition with no way back.
* The system must let the team require the deep lane for every plan (`minimum_lane: deep` in the team configuration); the router otherwise decides, the `light` -> `deep` ratchet always applies, and neither a forced `light` lane nor a disabled ratchet may exist.
* The system must let only the plan's asking axis (`PM-WF-25`) decide which phase transitions of a plan wait for the operator; no setting and no answer of the operator may pass a server gate (the outline gate, the pre-merge barrier) that its evidence does not pass; only an operator waiver (`PM-SEC-3`) admits a failing waivable gate.
* The system must ensure `phase-2-refine` only widens active skill domains, `phase-3-outline` narrows them at most once, and a pull-request title is present from `phase-2-refine` onward, describes the scope that actually ships, and is re-confirmed before pull-request creation whenever a scope-shrinking transition (domain narrowing, a deliverable removed after `infeasible`, a gate-removed deliverable) occurred after it was authored; an empty title is a hard error.
* The system must compute `phase-4-plan` task derivation (profile mapping, dependency DAG cycle detection, skill resolution, and atomic task creation) deterministically over structured deliverables, using the same resolver for every composition of the plan instance (`PM-IMPL-5`), whose steps pruned by the plan's posture (the plan's own value, else the project's, else the machine's optional `plan_defaults.posture`, unset by default, never asked during onboarding; while no level sets it, asked in the operator wait where the plan's lane is chosen; mandatory steps are never pruned) are shown with their reason in the first instance diagram, the posture preview (in general, every derived planning question such as epic linkage, worktree presence, freshness, or posture must have exactly one resolver); task dependencies must be persisted per task (`depends_on`) and checked by the server on every task creation (every reference exists, the graph is acyclic), and envelope packing and the order of the envelope tasks must follow them.

[#PM-WF-11]
=== PM-WF-11: Q-Gate Validation Loop, Change-Type & Unplanned-Change Recording

Quality gates, change-type classification, and scope-deviation handling must be governed by deterministic server validators and closed enumerations.

* The system must enforce a single writer for `change_type` (a closed enum of six values), falling back to a task of the classification role when the deterministic heuristic is ambiguous, and refusing transitions when plan-level scope and deliverable-level scope disagree.
* The system must run the Q-Gate of Phase 3 (deep lane only) and Phase 4, and for lesson-derived plans of Phase 2, as a task of the phase's Q-Gate role (class `read_only`) whose completion the server evaluates: the task submits assessments and findings, the server runs the compiled mechanical checks and decides `clean` or `blocking` from the persisted findings alone (no mode may switch the gate off or stop it after one pass), and a `blocking` verdict calls the Q-Gate remediation policy (`remediation.qgate-findings`, `PM-WF-7`; shipped fix budget `3`, no `retry`). Its `fix` returns to the phase's authoring state with the findings as facts (Phase 4 findings only through targeted per-task revision links that never change the task set; a structural change is a bounded loop-back to Phase 3), an unchanged artifact is refused as `fix_unchanged` instead of being re-validated, `resolved` or `waived` (waived findings recorded as accepted by waiver) exits the phase, and `exhausted` returns the plan (`returned`); the validator population per phase and a deterministic surgical-change bypass predicate are fixed in the specification.
* The system must pass the outline gate without an operator decision when the outline's Q-Gate returned `clean`, `resolved`, or `waived` (or does not apply: light lane, recipe, surgical bypass), the task derivation dry-run succeeds (checked on every outline submission, which is refused when the outline is not derivable), and no `3-outline` finding is pending; a review of the outline by the operator is a decision (`approve` or `revise`, the latter charged to the Q-Gate fix budget), asked when the outline is ready unless the plan's asking axis settles it (`PM-WF-12`, `PM-WF-25`).
* The system must accept and record unplanned changes, never review them: a writer worker may change files beyond the plan's declared footprint inside the plan's worktree without asking, the declared footprint stays the statement of intent, and the server records the realized minus the declared paths as unplanned changes with their provenance (task or loop-back) and lists them in the pull-request body and the landing record; only a boundary breach (a path outside the worktree, the main checkout, a protected path) is refused, by the non-waivable footprint guards (`PM-SEC-1`). For an epic plan, an overlap of unplanned paths with a sibling's declared surface is only noted in the landing record.
* The system must restrict task status to `pending`, `in_progress`, `completed`, `infeasible` (reported by the envelope task with evidence; tasks independent of it through `depends_on` continue), and `removed` (deliverable removed by the outline gate or by a re-planning). When nothing runnable remains and a deliverable is infeasible, the plan is re-planned with the trigger `infeasible` (`PM-WF-17`), whose facts carry the infeasible deliverables with their evidence and their server-computed transitive dependents; a deliverable it removes or defers is a recorded gap in the pull request and the landing record, the pull-request title is marked stale, and removing the last deliverable is refused. `phase-5-execute` must be left only when every task is in a terminal status and every `infeasible` or `removed` task carries its recorded disposition.

[#PM-WF-12]
=== PM-WF-12: Question Records vs Operator Overrides

The workflow engine must distinguish content questions, which reach the operator as decisions through one server mechanism, from operator overrides, which are operator acts of their own.

* The system must model every content question of a scope (the init classifier questions: sibling collision and domain choice; the batched refine and outline clarifications; the outline review; a Phase 5 task question; a question a worker raises before one of its judgments; the team-configuration choices of the workspace setup) as a server-owned question record in the scope's question store, created by a worker's `ask` link, by an envelope task's `ask:TASK-NNN` link (which records the question and ends the envelope task; the remaining tasks, the asking task included, go to the next envelope task with the answer in its facts), by the `decision` a refine or outline authoring task carries in its `submit` (each of its parts one record), or by a server classifier. The questions of one creation form one *decision*, addressed by its first question's id (`<scope_id>/<question_id>` across scopes) and carrying a revision: a title and header, a description with its evidence, what it blocks (the plan, a task, nothing), how reversible its outcome is, and its parts, each part one question with its answer type (one option, several options, or a value), its options (a stable key, a label, the trade-off, the consequences, an optional preview, and the support of a quorum where one voted), an optional dependency on another part's options, its recommendation (`PM-WF-18`), and whether the operator's own words are allowed. A decision the quorum does not decide (`PM-WF-18`) is an operator wait (`PM-WF-20`) of its scope, without a deadline and without a default taken by time; clarifications are asked in a single batch, and at most one refine task is served again for them. An option the plan's axes or the project or machine sets is never asked (`PM-WF-25`), and the posture is asked only where the plan's lane is chosen and the project and the machine leave it open (`PM-WF-10`).
* The system must validate every answer against its decision (an unknown option, a second answer, an answer to an older revision, and an answer to a part whose dependency is unanswered are refused), take per part the chosen options or the value with the operator's note, and for the whole decision also _later_ and, only where a role can ask anew or a quorum can vote again, _none fits_; record the answer with its channel (`web` with the paired device, `cli`, or `quorum`), keep open and answered questions in the scope's question store, and record an answer that changes the plan's intent as an amendment (source `user`, `quorum`, or `refutation`) listed in the pull-request body and the landing record. Where a part allows the operator's own words, a task of the interpreting role (`PM-WORK-1`), which never sees the recommendation or the votes, maps the words onto an option, an option with a condition, a new option in the operator's words, a delegation, or unclear, the server checks that the option exists and the quoted passages occur in the words, and nothing is recorded before the operator confirms the read-back; words that fit no option are recorded as the operator's own option, never replaced by the closest one.
* The system must deliver every decision of a plan, an epic, the workspace scope, and an entry to both clients of the operator (`PM-ARCH-11`), each of which announces it, answers it through the same scope-qualified answer endpoint, and withdraws it once it was answered in the other; the first valid answer wins and a later one is refused (`already_answered`). Nothing is decided by the passing of time or by a rule that asks no one: a decision is taken by the quorum its declaration names or by the operator.
* The system must treat operator overrides as never being content answers and accept them only as operator acts of the operator's clients (`PM-SEC-3`), never as a link and never relayed by a model: setting, revoking, and declining waivers, ending a plan or an epic (`PM-WF-23`), resolving an integrity breach (`accept-edit` or the abort), plan deletion, cross-project access grants (`PM-SEC-2`), and operator configuration. An override is never taken as a content answer, and a content answer is never an override. The choices of the project setup and of the onboarding are operator waits of their scope (`PM-WF-20`). No model ends a plan or an epic: a worker's task ends only in its closed task outcomes (`PM-WORK-2`).
* The system must let the operator influence a running plan only by operator acts: waivers, pausing and starting it, cancelling or abandoning it, a revision accepted in a chat (`PM-WF-23`, `PM-WF-24`), and the plan's own settings (`PM-WF-25`), each of which composes a new version of the plan instance where it changes the process (`PM-IMPL-5`). A waiver declares one gate of a closed list met or raises one budget (`--raise`), is plan-scoped with a mandatory reason, is recorded append-only in the plan's waiver record, may be set at any time until the gate's fallback is taken (and is refused afterwards), applies to every later evaluation of its gate, and is listed with every consumption in a pull-request comment and the landing record. Waivable are only review evidence (per bot), a named failing CI check, the quality gate of an analysis provider, the open findings of a class after triage, the Q-Gate findings of a phase, and the fix and retry budgets (`--raise`); integrity breaches, the footprint and main-checkout guard, job confinement, credentials, security findings, and the operator boundary are never waivable. A waivable gate admits a failure only through a waiver lookup that logs its consumption. A waiver request filed by a worker (`request_waiver`) is an operator wait announced in both clients, the plan view, and an idempotent pull-request comment with a label, answered only by `waive` or by `decline`, which records the outcome `declined` and lets the remediation unit take its next transition.
* Every third-party dependency a plan adds must be named in the solution outline that passed the outline gate (a per-deliverable `Added dependencies` section); before the merge the server must derive the added dependency coordinates from the build files the plan changed and file a blocking finding for every coordinate the outline does not name, and a changed build file it cannot parse must make the check indeterminate, never clean.

=== PM-WF-13: Finalize Step Ordering Bands, Verdict Currency & Pre-Merge Barrier

Phase 6 (`phase-6-finalize`) must execute steps according to compile-time-verified ordering bands, preserve valid step verdicts across rebases, and gate branch merge on a fail-closed barrier.

* The system must organize finalize steps into eight strict ordering bands of the integer `order` space, verified at build time against order collisions, read-after-destroy hazards, and mutual exclusions (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/phase-workflows/04-finalize-step-bands.adoc#finalize-step-bands[Phase Workflows Specification § Finalize Step Ordering Bands]):
** *Settle (`1..10`)*: `sync-baseline` (3), `simplify` (5), `security-audit` (7), `pre-submission-self-review` (8), `architecture-refresh` (9), `pre-push-quality-gate` (10), and project steps at the band's free orders.
** *Push (`11`)*: `push`, gated on working-tree build freshness.
** *Post-Push & Concurrent Wait (`12..69`)*: `create-pr` (20), `ci-verify` (22), `automatic-review` (30), `analysis-roundtrip` (40), unified finding triage (one triage task per gather firing), `adr-propose` (62), and project steps at the band's free orders.
** *Merge Gate (`70`)*: `branch-cleanup`.
** *Post-Merge Operational (`71..899`)*: project steps only.
** *Post-Run Review (`900..999`)*: `lessons-capture` (991), the optional `plan-retrospective` (995), `record-metrics` (998), `print-phase-breakdown` (999), and project steps (`900..989`).
** *Terminal Emission (`1000..1099`)*: `emit-landing` (1000).
** *Terminus (`1100`)*: `archive-plan`.
* The system must record `head_at_completion` for every completed `head_dependent` finalize step (refusing `done` without it) and evaluate verdict currency (`verdict_currency`) across rebases so a step verdict is retained when a `HEAD` advance does not touch its inputs; every `head_dependent` step must declare a server-validated `input_scope` (`remote_state`, `open_ended`, `plan_footprint`, or `declared` with non-empty `verdict_inputs`), and a missing scope must be a validation error, never a default.
* The system must enforce a fail-closed pre-merge review barrier in `branch-cleanup` (70) that no operator grant and no standing policy can pass: before it evaluates, the merge gate re-sends every triaged finding response that was not transmitted; open findings that are not triaged, and missing review evidence of a required bot, call the review-findings remediation policy (`PM-WF-7`), whose `exhausted` outcome raises the re-planning trigger `ceiling` (`PM-WF-17`), whose fallback is the hand-back; a failing waivable gate is admitted only by an operator waiver of the closed list (`PM-WF-12`), whose consumption is bound to the evaluated `HEAD` and to the findings it covered.
* The pre-merge barrier must treat a required review bot as having reviewed the merge candidate only on bot-authored review evidence (a review object, a declared clean verdict, or a completed check-run) that covers the current `HEAD`; a zero finding count, a refusal, a status placeholder, a trigger acknowledgement, or an empty or never-established required roster must never be rendered or evaluated as a completed review.
* The system must record on the merge record, the pull request, and the landing whether a merge was reviewed, merged over an answered empty required roster (`vacuous`), or merged under a consumed `review_evidence` waiver without a review covering the merge candidate (`unreviewed_by_waiver`).
* The system must rebase a plan branch onto its base at the merge gate only when the provider requires an up-to-date branch or the base changed a path of the plan's footprint, must bind every merge and merge-queue enqueue to the head commit the pre-merge barrier evaluated (a moved head re-enters the merge gate), must count a merge or an enqueue only from the provider's observed state, and must bound a merge-queue wait by observed progress (no progress for twice the queue's check-response timeout) rather than by a fixed budget. A rebase conflict, at the merge gate or already in `sync-baseline` when the upstream changes overlap the plan's paths, calls the merge-conflict remediation policy; every other failure of the merge path (lease interruption, a remote branch moved by others, a provider refusal to merge, a merge-queue exit) ends after its bounded retry in the `handed_back` fallback, a refusal by the provider's protection rules (required review, branch protection, draft, merge method) at once. No path may merge over a provider refusal (which is not waivable), and no path may force-push except a lease-protected push of the plan's own branch after a server rebase.
* The system must record on the terminal state of every plan that ends through `finalize.archive-plan` a required, server-derived `merge_outcome` (`merged`, `enqueued_not_landed`, `declined`, `no_pr`, `dequeued`, `local_only`, `handed_back`, or `awaiting_human_merge`), derived from one observation of the provider's pull-request state and git through the same single mapping that derives the landing's `merge_state`, never from a model argument; a failed observation never completes the plan. A plan whose pull request is open and unmerged when it takes its fallback is handed back (`finalize.hand-back`): the pull request stays open (opened as a draft when the fallback creates it) with an idempotent gap comment and the label `pm-mcp:handed-back`, and the post-run band and the archive still run; a plan without a push remote (derived, never configured) ends `handed_back` by design with `merge_outcome: local_only`, its plan branch kept. The plan's asking axis (`PM-WF-25`) decides only whether the plan merges itself: where it leaves the merge to the operator, the plan instance leaves out the merge execution, and a plan whose pre-merge barrier passed ends `handed_back` with its pull request ready for review (never a draft) and `merge_outcome: awaiting_human_merge`; the axis never passes a barrier predicate or a gate and is not a waiver. Every pull-request comment a plan posts must be posted at most once, also across retries. After the merge no fallback exists: a failing post-merge step is re-fired once and otherwise recorded as an owed item, and a merged plan (`merge_outcome: merged`) is always archived.
* The system must record every obligation a plan incurs but does not discharge as a typed owed-item record (kind, discharger `operator` or `plan_step`, discharge proof) written by the step that incurs it; owed items survive archival and are listable without reading prose, from the epic inbox for epic plans and from a project-level owed index for every plan, and a plan that owes nothing records an explicit empty set.
* The system must land a plan's work through the landing variant in force (`PM-WF-25`), a call site inside `phase-6-finalize`, after the phase's checks and reviews: `landing.pull-request` (the push, the pull request, its reviews, the pre-merge barrier, and the merge of the bullets above), `landing.main` (a commit pushed onto the base branch, without a pull request, refused for a protected base branch), or `landing.files` (no commit: the changes stay in the working tree and the plan ends `handed_back`).
* The system must keep archived plan and epic records readable by their `plan_id` or `epic_id` after archival, read-only, until the operator's cleanup deletes them (`PM-ARCH-10`), after which a tombstone records the deletion. Archived plans stay in the per-project machine store (`<PM_MCP_BASE>/projects/<project_id>/archive/<plan_id>/`), so each record keeps exactly one authoritative location and never leaves the workstation (`PM-ARCH-2`); reading another project's archived plans requires the operator's cross-project access grant (`PM-SEC-2`).

=== PM-WF-14: Task Envelopes, Model Slots & Usage per Task

Implementation tasks must be packed into budget-bounded envelopes, workers must run within machine-wide and per-plan concurrency bounds, and usage must be accounted per task from the harness's own output.

* The system must automatically bin-pack implementation tasks in-process upon `plan.describe-tasks` submission into budget-bounded *task envelopes* (`EnvelopePacker`), sizing each task with a deterministic rubric into a server-derived (calibrated) size-to-token table, labelling every prediction `uncalibrated` until the server recalibrates the table from measured metrics, and merging an envelope below the minimum work that justifies a task into a compatible neighbour; each task `submit` within an envelope must return the representation of the envelope's next pending task. Envelope tasks must run serially: a chain-tail submit, a question (`ask:TASK-NNN`), an infeasible report, or a `yield` ends the envelope task (a yield with the server-recorded reason `chain_tail`, `question`, or `context`) and hands the remaining tasks, the asking task included, to the next envelope task, and the plan reacts only to the envelope task's completion, whose outcome a server return-evaluation primitive derives from the persisted entity state in a fixed precedence (pending question, pending infeasible judgment, chain tail, continue, all complete).
* The system must lease a machine-wide model slot for every running worker, warm or fresh (`model-slots.json`, cap in `machine-config.json`): a warm worker holds its slot for its whole generation, idle or not; a task waiting for a worker is `queued`; a fresh worker's budget starts at spawn, a warm worker's per task at the offer. At most one worker of a `writer` role may run per plan, while `read_only` and `zero_tool` workers of the plan run beside it within the machine cap.
* The system must take token usage and duration from the harness's own output as the client profile's usage declaration maps it, never from a model's self-report: per task from the per-turn usage of a warm worker's turns that served the task, and per job from a fresh worker's run (population `model_job`, duration measured from spawn to exit), recording every figure the harness reports as reported (input, output, cache read, cache creation, and reasoning tokens, tool uses, and a cost where the harness reports one) together with the role, harness, harness version, model, and effort that produced it. A figure the harness does not report is recorded as `unmeasured` and a figure that does not exist for the harness by design as not applicable (counted `0`), three values distinct from a measured `0`; the one token total is the unweighted sum of the five token components when every applicable one is measured and `unmeasured` otherwise, shown with its split into tokens in and tokens out and with its coverage (a total over unmeasured rows only as a floor); a cost is recorded data that no view shows, no figure sums, and no rule reads; and a run-total record is never read as a context size.
* The system must derive from each task's records, beside its tokens, the figures that show what the work cost to navigate, each with its population: the cache-read share of its context tokens; revisits (a file the worker reads again after reading it earlier in the same plan task, from the activity's `tool_call` targets); the use of `pm_lsp` against the harness's own search tools; and the fallback-to-read rate (a `pm_lsp` lookup followed by a whole-file read of the same file in the same plan task); and must show them per task, per role, and per plan in the usage of the completion report (`PM-WF-21`).
* The system must take the harness, model, and effort of every worker from its role's effective values (`PM-WORK-1`): the role's artifact, which replaces a lower one as a whole, overlaid in this order by the machine's role assignment, the project's artifact and role assignment, and the plan's override, each assignment changing only these three fields; an effort the harness or model does not support narrows to the nearest supported value, never escalates, and is recorded. No agent variant is installed, and a change of an artifact, an assignment, or an override applies to the next worker generation.

=== PM-WF-15: Epic Creation, Server-Started Plans & Cross-Plan Merge Mutex

Epics and concurrent plans must come into existence through a server-side intake and coordinate safely without nesting a plan inside a task or racing merges.

* The system must create an epic only through a start of kind `epic` (`PM-WF-10`), an entry the operator opens in either client whose operator waits gather its sources (a description being one) and its title, and whose completion creates the epic scope with its header in one transaction; the epic's sources move into its git-tracked ledger with their manifest, so that every machine that adopts the epic and every later decomposition reads them, and its header takes `parallelization_scope`, `auto_start`, and `overlap_max_files` from the project's values, never asked at the start. The epic workflow then starts at decomposition: a task of the epic's planning role drafts workstreams and staged plan sections (a section of more than six deliverables is refused as `section_too_large`), the server checks the draft (surface disjointness, dependencies without a cycle, a workstream per plan), and the draft is an operator wait in which the operator keeps, edits, drops, or adds plans, chats with the role (`PM-WF-24`), or has it draft again; nothing is committed before the operator agrees and every check passes, the draft is kept in the epic's machine store until then, and the epic starts no plan before its first decomposition is committed.
* The system must adopt, never re-create, an epic whose git-tracked ledger exists without the epic's machine scope (for example after a clone): the start of an epic offers the adoption for such a ledger, and its completion creates only the machine scope from the ledger, the durable truth, which it never rewrites, entering decomposition only when the ledger has no queue row at all and the active state otherwise; an unreadable or invalid ledger ends the adoption in a failure state that names the reason.
* The system must start the launchable plans of an epic within its `parallelization_scope` and the machine's model slots, by itself while the epic's automatic mode (`auto_start`) is on and on the operator's _next plan_ while it is off, in which case the epic reports each row that became launchable (`PM-WF-21`): a staged row is launchable when its prerequisites have shipped and a re-grounding at the current `HEAD` did not judge its spec `stale`, and it is admitted beside the epic's running plans only while its declared surface shares at most the epic's `overlap_max_files` files with each running plan's declared surface and realized changes, otherwise it waits with the reason `overlap` until that plan has ended; a pausing or paused plan keeps its row's place. The server creates the plan through the `epic_row` source of a start, which stores the row's staged spec section as the plan's source, binds the plan to its row, and sets the row `running` once the plan exists, in the fixed write order of a cross-scope transaction (`PM-IMPL-7`). A task of the epic's re-grounding role judges every staged row whose spec predates the current `HEAD`, and a row judged `stale` is not launched until its section is submitted again.
* The system must map every plan outcome and activity onto its epic queue row: `merged` to `merged`, `no_change` to `completed`, a pausing or paused plan to `pausing` or `paused`, `cancelled` to `cancelled`, `abandoned` and `aborted` to `abandoned`, `handed_back` to the live status `handed_back` until the epic's landing reconciliation observes the pull request merged (`merged`) or closed (`abandoned`), and `returned` to the closed status `returned` (the work may be staged again only as a new row); the outcome `released` changes no row, because the release leaves the epic's ledger untouched; a prerequisite counts as shipped only as `merged` or `completed`. Every operator act on a plan of a live epic (pausing, starting, cancelling, abandoning, a revision in a chat, a change of its settings) is told to the epic's inbox with its reason and channel, and the epic decides on it as on every inbox message, never ending a plan itself. An epic that the operator cancels with its plans left running leaves them untouched: they run to their own outcomes as plans detached from the ended epic, emit no landing into its inbox, and their late findings are seeded as lessons.
* The system must treat surface disjointness as a modelling invariant of one epic, checked when the epic stages a plan rather than at emission: each staged plan declares its expected file/module surface, staging is refused with `surface_overlap` when that surface overlaps the declared surface of another non-terminal plan of the same epic that is not ordered with it through prerequisites, and with `surface_undeclared` when the surface cannot be declared; when a plan starts, the epic checks that its prerequisites have shipped, that the row's spec is not judged `stale`, and its admission (no more running plans than `parallelization_scope`, no overlap with a running plan beyond `overlap_max_files`). Plans of other epics and plans started without an epic are not checked (their conflicts surface at rebase or merge and are the operator's responsibility). A running plan whose realized changes come to overlap another running plan of its epic beyond `overlap_max_files` is recorded in the epic and reported to the operator (`PM-WF-21`), never stopped; the plan that lands second meets re-planning or its rebase (`PM-WF-17`).
* The system must let the epic react to every ended plan in both modes: for a landed plan it records the landing and judges its downstream impact, applying a re-cut that only re-orders staged rows or amends a staged row's surface or prerequisites once the server's checks pass, and reporting it, while a re-cut that adds, drops, or re-scopes a plan waits for the operator in the decomposition's review; for a plan that ended without landing it holds the rows that depend on it and asks the operator. The epic keeps two registers in its ledger, findings (problems no plan owns yet) and watches (observations re-checked when their trigger fires), which its tasks add to and the operator decides in a review whose every model-proposed change passes the operator's read-back; new findings need the operator. When every row is shipped or ended the epic is through: it runs its completion review (with automatic on at once, otherwise before the archive check) and reports it, and only the operator's _archive_ archives it.
* The system must serialize concurrent plan rebases and merges within a repository through a per-repo FIFO admission queue and merge lease persisted in `<PM_MCP_BASE>/state/merge-queue.json` and updated only under the short transaction lock `<PM_MCP_BASE>/locks/merge.lock` (cross-plan review-bot rate-window claims are coordinated separately via `<PM_MCP_BASE>/state/review-bot-windows.json` under `<PM_MCP_BASE>/locks/review-bot.lock`), where the lease is held across the rebase-to-merge critical section, automatically releases whenever the plan enters a wait state, and is reclaimed from stale holders via runtime liveness (PID plus start time) or expired lease budgets (`PM-IMPL-7`).
* The system must land git-tracked epic ledger changes through one repository-wide epic landing that serializes its git steps under its own repository-wide lock outside the plan merge queue, confines its diff to the epic ledger paths, reuses the open landing pull request, and never discards ledger writes made after its snapshot (the epic branch is resynced by merging the default branch into it, never by a reset).

[#PM-WF-16]
=== PM-WF-16: Reusable Compound Sub-Workflows & Config-Driven Git Commit/Push

Multi-step domain sub-processes must be modeled as reusable, parameterized compound sub-workflows (`scope subworkflow`) invoked over a persisted call stack rather than duplicated across phase state graphs.

* The system must support reusable compound sub-workflows (`scope subworkflow`) invoked via parameterized `call <subworkflow_id>(<param_bindings>)` states, persisting the active call stack (`call_stack`) in `mcp/status.json` so tasks, asynchronous job waits, and crash recovery inside a sub-workflow preserve the caller's phase, return state, and bound parameters.
* The system must verify at build time that the sub-workflow call graph across all `*.pmwf` definitions is a strict directed acyclic graph (DAG) with maximum call-stack depth $\le 5$ (a plan's phase sub-workflows, called by its plan unit, are the first level), and that every `call` state's `<outcome> -> <target_state>` clauses form an exact 1-to-1 bijection with the target sub-workflow's exit contract: `done` with a typed result record, domain outcomes only where callers genuinely continue differently (for a remediation policy the reachable subset of `resolved`, `waived`, `exhausted`, `fix_requested`), and the control outcome `stepped_out`.
* A sub-workflow must be left early only by the server (`stepped_out` when its attempts or bounded retries are exhausted) or by the implicit `step_out` link (with a reason) that an operator wait of a sub-workflow (a start's source units, the project setup, the onboarding's steps) offers the operator, which unwinds one call frame and returns `stepped_out` to its caller. A call makes the sub-workflow's first state current, the representation shows the call path, and each model step asks for exactly one piece of judgment through one link naming its skill section, never bundling unrelated inputs or asking for what the server can derive.
* The system must provide a canonical reusable `git.commit_and_push` sub-workflow (`git-commit-and-push.pmwf`) shared across Phase 5 (`execute` deliverable chain-tail and remediation commits), Phase 6 (`finalize` settle-step commit instrumentation, `push` barrier, and post-PR re-push, including the re-push of an adopted pull request of a plan of source `pr`), the in-branch fixes of the remediation units (`remediation.ci-failure`, `remediation.review-findings`, `remediation.analysis`), the epic ledger commit (`epic.commit-ledger`), the landing of the project-setup changes (`setup.land-changes`), the commit of `landing.main` (`PM-WF-25`), and the short landings of a project (`git.land-removal` for documents moved out of git, `git.land-unit` for a placed or removed workflow unit, `PM-WF-22`), each landed by the project's landing variant.
* The `git.commit_and_push` sub-workflow must execute the complete config-driven git commit and push lifecycle:
** Inspect working-tree changes (`git status --porcelain`) in the resolved worktree or primary checkout; when the working tree is clean, either return at once (`push_mode=never`) or proceed directly to the push barrier (`push_mode=if_push_remote` or `always`).
** Detect and clean build/temp artifacts against the compiled artifact pattern table (a classpath resource of `pm-core`, not a configuration file) while respecting `.gitignore` (failing closed if the `.gitignore` oracle fails), unconditionally excluding `.marshall/**` and nested git worktrees/submodules, auto-deleting `safe` untracked artifacts, and serving a task of the artifact-review role (`git.artifact-review`) only when `uncertain` tracked artifacts or prohibited secret files are detected.
** Resolve and validate the commit message in-memory (using either a caller-supplied deterministic template or a task of the commit-message role, `git.compose-message`, with diff-derived `type`/`scope` facts), validate Conventional Commits syntax, and deterministically append the configured `Co-Authored-By` trailer, read from the operator's `commit_trailer{name,email}` in the machine-local `<PM_MCP_BASE>/projects/<project_id>/local-config.json` (machine-wide default in `machine-config.json`, compiled default `Co-Authored-By: plan-marshall <noreply@cuioss.de>`) and never from a team configuration file.
** Stage the worktree's dirty paths that the artifact review did not classify as build or temporary artifacts (paths beyond the plan's declared footprint are staged and recorded as unplanned changes, `PM-WF-11`; a path outside the worktree or a protected path is never staged and fails the commit loudly, naming the path) and execute `git -C <tree> commit -F -` by streaming the UTF-8 commit message over `stdin`, capture the new `commit_sha` and git-sourced `changed_paths`, append a `kind="change"` entry to `change-ledger.jsonl`, and—when invoked from a Phase 6 `mutates_source: true` step—re-stamp the committing step's `head_at_completion` when it is `head_dependent: true` and record a `freshness_reconcile` entry for every commit made after the latest successful build.
** Evaluate push policy from caller parameters (`push_mode`: `never`, `if_push_remote`, `always`, `post_pr_conditional`) and the server-derived presence of a push remote (a local-only run is derived from its absence, never configured; a presence that cannot be determined raises the `precondition_unmet` condition with its bounded retry, then the fallback), enforce the `pre-commit-verify-freshness` gate before pushing, push unconditionally on the plan branch's first push (tracked by a persisted `branch_pushed_at` fact), and on re-entry decide by the `branch-sync-state` parity probe (`ahead` pushes; `synced` never pushes and counts as pushed; `remote_absent_landed` never pushes and returns `pushed: false` with `landed: true`; `rewritten_by_rebase`, a branch rewritten by a server rebase, pushes with the lease; `remote_absent_unverified` is first resolved by provider evidence: a merged pull request of the branch makes it landed, no pull request at all makes it never pushed, which pushes; an unverified state with an open or closed-unmerged pull request or an unobservable provider, and every unrecognised state, end in a server step-out with the cause `push_state_unknown`), force a push only as a lease-protected push (explicit expected remote SHA) of the plan's own branch after a server rebase, refusing every other force push, and handle its failures locally in structured recovery states (`git.commit-fix`, a task of the writer role the unit names (for a plan, the plan's writer role), on pre-commit hook failure, never bypassing the hook; `git.sync-required`, server logic, on non-fast-forward rejection; `git.resolve-conflicts`, a task of the same role, for a rebase conflict) before returning its exit contract to the caller state: `done` with the result record `{commit?, pushed, landed?, clean}` (`pushed`: the remote branch holds `HEAD` after the call), or `stepped_out` (by the server when the compiled attempt cap of a recovery loop, the bounded `.gitignore` oracle retry, or a push-state check ends it), on which callers branch by guards such as `result.pushed` and `result.landed`.
** Author every commit as the operator (the operator's configured commit identity) and commit it as the agent identity resolved from the provider credential (a fixed system identity when none resolves), identically in the native and the CLI variant, keeping the configured `Co-Authored-By` trailer.
* The per-deliverable verification verbs that Phase 5 runs after each deliverable's chain-tail commit must be configurable in the team configuration (`workflow.json` key `plan.phase-5-execute.per_deliverable_verbs`), defaulting to `compile` and `module-tests` (as `plan-marshall`'s `per_deliverable_build`); a failing per-deliverable build or verification sweep calls the build-failure remediation policy (`PM-WF-7`), whose `fix` allocates remediation tasks and whose `exhausted` outcome raises the re-planning trigger `ceiling` (`PM-WF-17`), whose fallback is the hand-back.
* The system must run a plan as a workflow of phases: its plan unit calls each of the six phases (`init`, `refine`, `outline`, `plan`, `execute`, `finalize`) as a sub-workflow that declares its entries and exits, a phase's outcome decides the plan unit's next call, a loop-back is a call of an earlier phase again, and a re-entry from finalize into execute is the finalize phase ending with that outcome; a lane is the plan unit's choice of the phases it calls (the `land` lane calls no refine, outline, or plan phase and runs its own states as a sub-workflow within `execute`; the `adopt` lane calls `init` and then `finalize`), and a plan's phase is the phase sub-workflow on its call stack, which every sub-workflow called within it shares, so that a phase can be shown, replaced, and extended on its own.

[#PM-WF-17]
=== PM-WF-17: Dynamic Re-Planning of a Running Plan

A plan is laid out against the project as it stood at planning time; when a premise changes while the plan runs, the server must reconsider the plan as a whole through one bounded re-planning mechanism, never by asking the operator mid-plan; a revision the operator starts in a chat is the operator's own act (`PM-WF-24`).

* The system must detect the re-planning triggers deterministically, at fixed server checkpoints and with the thresholds the project-owned re-planning unit declares within compiled bounds (`PM-IMPL-5`), recording every evaluation with the measured value against its threshold as a decision record (`PM-WF-19`), so the defaults are calibrated from recorded data: the base branch advanced with changes that overlap the plan's footprint; a trial merge of the plan branch with the base conflicts, with the conflicted file count; a downstream limit will be exceeded (the changed files or diff size of the plan against the structural caps of a required review bot); a loop budget of a remediation policy is spent (a loop-back ceiling reached, a review that does not converge); and a deliverable is infeasible with nothing runnable left. A trigger is raised at most once per kind and evidence (the same base commit, the same `HEAD`), so a judged situation is never judged again.
* The system must hand a raised trigger to one task of the plan's re-planning role (`PM-WORK-1`) whose facts carry the plan's outline, its plan tasks with their status, the done deliverables, the declared and realized footprint, the trigger's facts with the evidence the decision rests on, and the remaining budgets, and whose links offer the closed actions the trigger admits: re-integrate in this plan (amended or new deliverables and new plan tasks, re-entering execution, or the bounded loop-back to the outline), split the change (part of the deliverables to a follow-up plan that delivers them as a second pull request), defer the affected part to a follow-up plan, wait for a named prerequisite to land, rebase and re-verify only, or hand back.
* The system must validate a revised outline and its new plan tasks with the same server guards as a first plan (outline validation, the derivation dry-run, the declared-path discipline, the task graph, and the mechanical Q-Gate checks), add the tasks additively without reopening a completed one, compose a new plan instance version (composition event `replan`), and record every follow-up plan; a follow-up of a plan that belongs to an epic is staged as a new row of the epic ordered after the plan's row and started by the epic, a follow-up of any other plan is listed in the pull request and the landing record.
* The system must never ask the operator during re-planning: the re-planning task has no question link, a wait for a prerequisite is bounded by the unit's declared wait, and while the re-planning role is unqualified (`PM-WORK-6`), its task is lost, or the re-planning budget the unit declares is spent, the server takes the trigger's conservative fallback without a task: the existing remediation path (a trial-merge or base trigger continues into the rebase and `remediation.merge-conflict`; a size trigger continues the plan unchanged) or, for a spent loop budget and an infeasible deliverable, the hand-back.
* The system must keep one mechanism for every re-planning of a running plan: the infeasible review of Phase 5 is the trigger `infeasible`, the `exhausted` outcome of a remediation policy (outside the `land` lane) in Phase 5 and in finalize before the merge raises the trigger `ceiling` instead of handing the plan back at once, and a re-planning that re-enters execution renews the retry and fix budgets of the remediation policies once (the counters continue, the effective ceiling is counted from the re-entry), so the plan's loops stay bounded by the re-planning budget. A revision the operator accepts in a chat (`PM-WF-24`) is applied by the same apply path and guards, takes effect at the plan's next task boundary, records the operator's chat as the decider in its re-planning record, and spends no re-planning budget; the server never starts a chat.

[#PM-WF-18]
=== PM-WF-18: Question Recommendation Score & Decision Quorum

Most questions of a plan come with a recommendation that the operator follows; the server must state how sure each recommendation is, persist it with the question, and let the team declare per kind of decision whether the operator decides or a quorum of independent models may decide without the operator, so that by default every question of a kind that rests on facts or decisions only the operator holds still reaches the operator.

* The system must have every question an asking task creates (`PM-WF-12`) carry exactly one recommended option, a recommendation confidence (`0` to `100`), a short rationale, and a decision kind from the closed set `interpretation`, `approach`, `granularity`, `placement`, `test_strategy`, `scope`, `product_behaviour`, `assurance`, and `external_fact`; a question a server classifier raises carries the classifier's recommended option, its score mapped to `0` to `100` (`0` where the classifier computes none or recommends no option), and the kind the adjudication unit declares for it. The questions of one creation (one `ask`, one `submit` with its `decision`, or one server primitive) form a question set whose score is the lowest confidence of its questions. The recommendation (a field of its part, naming the option, its rationale, and who recommends it), its confidence, and its rationale must be persisted with the question record and shown in both clients; where a quorum voted, every option shows its support (how many votes chose it, from which roles and models, and the dissent with its reason), and a self-reported confidence is never presented as the probability that an option is right.
* The system must take the decision form of every decision kind from the adjudication unit, a project-owned workflow unit (`PM-IMPL-5`) that declares per kind either `ask` (the operator decides; the default of every kind) or `quorum(<role>, ..., <score>)` (the listed roles decide), together with the kind of every server-raised question, the vote wait, and the calibration level, each within compiled bounds (one to three distinct listed roles, a score of `50` to `100`); there is no operator key for any of them. The shipped unit declares `ask` for `scope`, `product_behaviour`, `assurance`, and `external_fact` and a quorum of shipped roles for the other kinds.
* The system must pass every question set, before it is delivered, through one sub-workflow, the adjudication, which acts as the declarations of the adjudication unit say and as nothing else. It decides a set automatically only when every question of the set is decided by its kind's quorum: every listed role chose the same option, each with a confidence at or above the declared score; the set is then answered with the channel `quorum`. In every other case, a question of an `ask` kind included, the whole set is delivered to the operator as a decision, an operator wait (`PM-WF-12`, `PM-WF-20`), with every listed role's answer and rationale shown; where the operator answers _none fits_ to a decision a server rule raised or a quorum escalated and a quorum is declared for it, the quorum votes again.
* The system must keep a quorum blind and independent: every listed role other than the asking role answers in a task of its own whose facts carry the questions, their options, and the facts and evidence of the asking state, never the asker's recommendation, confidence, rationale, or default assumption, nor another role's answer; the asking role votes only when the declaration lists it, its vote then being its recommendation with its confidence, and otherwise its recommendation is shown only to the operator. Each listed role is a `read_only` role run fresh (`PM-WORK-1`), and the listed roles of one declaration run on pairwise different models; the configuration is refused otherwise. A listed role whose harness is not eligible as a worker host or not enrolled, whose configuration is unqualified, or whose task ends without a valid answer makes the quorum fail, never counts as agreement, and escalates the set to the operator; the adjudication is bounded by its declared vote wait and by the model slots, and it never asks the operator anything of its own.
* The system must let a quorum declaration decide only while it is calibrated (`PM-WORK-6`): graded on the corpus items of its decision kind, its share of false automatic decisions must not exceed the level the adjudication unit declares; otherwise every question of the kind escalates to the operator until the declaration is graded again.
* The system must persist the adjudication of every set a quorum declaration covers as a decision record of each of its questions (`PM-WF-19`: every vote with its role, harness, model, chosen option, confidence, rationale, and task; the outcome `decided` or `escalated` with its reason, `disagreement`, `below_score`, `role_unavailable`, `role_unqualified`, `kind_ask`, `quorum_invalid`, or `calibration_failed`; the confidences against the declared score, with the adjudication unit's digest as their source), so an automatic decision is auditable and citable by its decision id, and must list every automatically decided question in the pull-request body and the landing record like every other answer, recording an answer that changes the plan's intent as an amendment of source `quorum`.

[#PM-WF-19]
=== PM-WF-19: Uniform Decision Records & Corpus Export

Thresholds and judgments decide the course of every plan; the server must record every decision in one auditable format, whoever takes it, so that every threshold is checked against the values it was applied to and real judgments with the decision finally taken can be reviewed into the model verification corpus.

* The system must append one decision record for every decision taken at a closed set of decision points, in the transaction that takes it, to an append-only decision store of the plan, epic, or workspace scope, or of the pending entry of a start before its scope exists (the store moves into the new scope at its creation): the server rules that compare a measured value with a threshold (the re-planning triggers and budget, the light gate of the planning lanes, the change-type heuristic, the refine confidence gate, the outline gate, the adjudication's quorum declarations, a remediation remedy the server takes alone, the posture projection, and the domain detection and narrowing), the decisions of role tasks (the remediation choice, the re-planning action, the triage disposition of a finding group, the change-type classification, the Q-Gate verdict, the votes of a quorum, the interpretation of the operator's own words), and the operator's answers to decisions, chosen, interpreted, or delegated, marking an answer that followed a chat. An override is never a decision: a waiver stays an operator act and is cited by a decision record only as the reference of a correction.
* Every decision record must name the decision point and the subject, the decision kind (`PM-WF-18`), the decider (a server rule with its rule, a role with its harness, model, effort, and task, a quorum with every vote, or the operator with the answer channel), the evidence (the digest of the facts the decider saw, kept as a snapshot for every judgment, and the `pm://` URIs of the evidence the decision rests on), the closed options, the decider's confidence (`0` to `100`, carried by every closing link of a role's decision task) or the measured values with the threshold applied and its source (compiled, the declaration of a project-owned workflow unit with the unit's digest, team configuration, operator configuration, a bound call argument, or a waiver), the choice, and the rationale. A question record keeps the question, its delivery, and its answer, and names the decision records of its adjudication and of the decision finally taken.
* The system must never rewrite a decision record: when a later decision of the same point on the same subject chooses otherwise, a re-planning names it as departed from, a question that reopens it is answered otherwise, or an operator waiver overrides the gate it closed, the server appends a correction naming the decision, the cause, the new choice, and its reference.
* The system must keep every threshold of a decision point a compiled default, a declaration of the project-owned workflow unit that takes the decision (within compiled bounds), or the configuration key it is; no threshold is read from decision records at run time, and every threshold's shipped value is a default whose calibration rests on the recorded measurements and corrections.
* The operator must be able to export decisions as draft items of the model verification corpus through the operator CLI, filtered by project, decision kind, decision point, and time: one item per judgment decision whose facts snapshot remains, with the question, the options, and the facts with the content of their evidence as input (never the recommendation, the confidence, or the choice), the decision finally taken as the reference (the operator's answer, or the correction where one exists; an operator override changes no reference), and the decider, confidence, and threshold as provenance; server-rule decisions are exported only as calibration rows, decisions of the kind `external_fact` are not exported, and every item is validated against the corpus schema. The export is never automatic, writes only to the directory the operator names, and transmits nothing (`PM-ARCH-2`).
* Decision records must be readable as a resource of the plan, the epic, and the workspace scope and in the web app, and must be kept, archived, and deleted with the records of their scope; the pull-request body and the landing record name the decision id where they list an answer or an amendment and list no other decision records.

[#PM-WF-20]
=== PM-WF-20: Waiting for the Operator

Waiting for the operator must be a normal behaviour of a state, defined once in the workflow language for every unit and every scope, so that every step that needs the operator has one shape and one rule.

* The system must let any state of any unit be an operator wait: it offers the operator's links as operator endpoints of the local API to both clients of the operator (`PM-ARCH-11`), holds no worker and no model slot (except a worker that holds its task for the answer to its own question, within its role's hold limit, `PM-WORK-2`), has no time limit, and ends only by an act of the operator through one of its links or by an override that ends the scope. Decisions (`PM-WF-12`), waiver requests, consents (`PM-SEC-8`), the options of a plan asked where it first needs them (`PM-WF-25`), the decomposition's review, and the choices of a start, of the project setup, and of the onboarding are operator waits; no unit defines a wait, a deadline, a mode, or a fallback of its own for them.
* The system must halt only the operator wait's own scope: a plan or an epic waits, and every other plan, epic, and project keeps running; the status shows it as waiting for the operator, never as stalled (`PM-ARCH-7`). The one wait that halts the system is the machine's onboarding (`PM-WF-26`): while it is not complete, no plan, epic, or project onboarding starts, while the onboarding itself and the operator's verbs work.
* The system must take every decision either by a quorum as its declaration says (`PM-WF-18`) or by the operator in an operator wait; nothing is decided by the passing of time or by a rule that asks no one.
* The system must make the operator's two clients the only place of interaction with the operator: a harness is a worker only and never acts for the operator, no session and no model relays the operator's words or choices, and MCP elicitation is never used. Interpreting the operator's own words (`PM-WF-12`) is no relaying: the operator wrote them in a client and confirms there what was understood.

[#PM-WF-21]
=== PM-WF-21: Reports to the Operator

What happened while no client was open must be kept for the operator, apart from what needs an act and apart from the audit log.

* The system must write a report for the operator whenever something happens in a plan, an epic, or a project that the operator should know without having to act, from a closed catalogue of kinds; keep every report in the machine scope, an unread one without expiry; serve the unread reports to both clients with where each comes from, its subject, when it happened and when it was sent, and a link to its detail where there is one; mark a report read, for every device of the machine, when the operator marks it read or opens its detail; and never ask anything through a report, so that what needs the operator stays a decision, an operator wait, or a hold.
* The system must append a report only after the transition it reports has committed, write a report a transition owed when the runtime stopped at its next start, carry the subject and body as message keys with their arguments (`PM-ARCH-11`), and keep read reports until the operator's cleanup deletes them (`PM-ARCH-10`).
* The system must give every ended plan a completion report, built from its archive and records: its outcome and reason, its pull request, the deliverables done, its re-planning records, the decisions taken, the tokens used with their split and coverage (`PM-WF-14`), and its duration.

[#PM-WF-22]
=== PM-WF-22: Designing a Process

The operator must be able to change the process a plan runs without editing files by hand, and to see the process a unit gives before it is in force.

* The system must let the operator design a workflow unit the operator may own, in the web app, starting from an uploaded file, a pasted text, or an installed unit; validate it on demand and before every placing exactly as it would load it, by parsing, static verification, the compiled invariants, and a composition dry run against a project that starts and stores nothing, reporting each finding with its rule, line, and column; place a valid unit at machine level or at project level, showing the difference against the unit it replaces first; and never place a unit with findings or replace a compiled-only unit.
* The system must resolve every unit by level, the project's copy over the machine's copy over the compiled default, a missing copy resolving to the next level and a present but invalid copy never replaced by another level; a project holds a copy only of the units its team placed or changed, and the setup copies no default unit into it. The effective configuration names the level of each unit, and its digests include the machine's units, so that a changed machine unit reaches a running plan only through the audited `config_drift` adoption (`PM-WF-1`).
* The system must offer the designer a catalogue of every element a unit can use in the machine or a project's scope, generated from the registries the parser, the static verification, and the composition use, so that it offers exactly what validation accepts; must land a placed or removed project unit by one commit through the project's landing (`git.land-unit`, `PM-WF-16`); must confine every route that names a unit to a unit name of the canonical grammar and to its target directory; and must refuse a placing whose replaced unit changed meanwhile.

See the link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/workflow-dsl/04-ast-node-model.adoc#process-designer[Workflow DSL Specification, Designing a Process] for implementation details.

[#PM-WF-23]
=== PM-WF-23: Operator Acts on Plans and Epics

The operator must be able to pause, start, and end a plan and to act on an epic in either client, and to resolve what holds a plan without a decision, each as an operator act the server validates.

* The system must keep a plan running, pausing (running until the point its pause names), or paused: a plan runs once it exists, by the operator's start or its epic's; the operator pauses it now (running tasks withdrawn and running jobs stopped, both run again on start), after the current task (the default), or after the current phase, and starts it again from its current state or withdraws a pause not yet reached. A pause and its point survive a restart of the runtime, and the plan's operator waits stay open while it is paused.
* The system must let the operator end a plan through `plan.aborted` with the operator's reason: cancel a running, pausing, waiting, or held plan (outcome `cancelled`) and abandon a paused one (outcome `abandoned`), choosing whether an open pull request of the plan is closed with a comment naming the reason or left open; the plan is archived like a completed plan and its lesson claim is released.
* The system must let the operator act on an epic: start its next launchable row now under the same admission tests, answering why per row where none is launchable and offering to raise `parallelization_scope` by one where the scope is full; have it decompose again; switch its automatic mode and change its `overlap_max_files`, each a ledger write of its header; archive it only after its completion review and an archive check (no plan running or paused, every row shipped or ended, no open finding, the ledger landed); and cancel it (`terminal_reason` `cancelled`), with its plans cancelled too or left running detached. An epic ends with `completed`, `cancelled`, or `released`.
* The system must record what holds a plan, an epic, or a landing without a decision as a hold of its scope, of a closed list of kinds (`stalled`, `condition`, `integrity_pause`, `held`, `landing_failed`), with its cause, since when, what was tried, and the acts that resolve it, each an operator endpoint of both clients; a hold that clears by itself ends its record, and every hold of a plan or an epic also offers its cancel. A paused plan is no hold: it shows by its state.
* The system must let the operator release or unenrol a project in either client, confirmed with what it ends: the release lets a running short landing of the project finish within a compiled bound and is refused otherwise, ends every plan of the project with the outcome `released` and every epic with the `terminal_reason` `released`, archives them in the project's machine store only, leaving the epics' ledgers untouched and writing to no repository, and deletes the project's pending entries and ends a running onboarding of the project.

See the link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/runtime-lifecycle/02-plan-pause-and-stalled-plans.adoc#plan-pause[Runtime Lifecycle Specification, Pausing and Starting a Plan], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/04-plan-finalize-terminal.adoc#plan-end[State Catalogue, Cancelling and Abandoning Archive], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/08-epic-coordination.adoc#epic-actions[Model Work Specification, An Epic's Actions], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/01-conventions-generic-conditions.adoc#holds[State Catalogue, Holds and Their Acts], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#project-release[Credentials & Enrolment Specification, Releasing Ends Work as the Operator Ends It], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/phase-workflows/07-questions-waivers-operator-influence.adoc#questions-waivers-operator-influence[Phase Workflows Specification, Questions, Waivers & Operator Influence], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/timeouts.adoc[Timeouts & Budgets Specification], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/workflow-dsl/02-units-jobs-decisions.adoc#waivers-and-integrity[Workflow DSL Specification, Waivers, Waiver Requests & the Integrity Pause], link:specification/runtime-model.adoc[Runtime & Interaction Model Specification], and link:specification/cli-and-security.adoc[CLI, Coordination & Security Specification] for implementation details.

[#PM-WF-24]
=== PM-WF-24: Chatting with the Planning Role

The operator must be able to talk over a plan, an epic, a decision, a start, or ended work with the role that plans it, and to steer the work only through changes the operator accepts.

* The system must offer a chat, one compiled sub-workflow, wherever the operator is shown a plan, an epic, the decomposition's draft, an epic's register or one of its items, a decision, a start's entry, or an ended plan or epic, routed to the subject's planning role (for a plan `replan`, for an epic `decompose`, for a start `refine` or `decompose`, for a decision a worker asked the role that asked) and offered disabled with its reason while no configuration of that role qualifies or no planning role exists.
* The system must give the chat's role the facts of its scope as data, an untrusted item still marked untrusted, and must change nothing without the operator's acceptance of each proposed change in a read-back; an accepted change goes through the caller's own path and checks (a plan's revision through the guards of a first plan at the next task boundary, `PM-WF-17`; an epic's change through its staging checks; a decision's proposed answer as the operator's own words through the interpretation, `PM-WF-12`; a start's one change, a description, as a new source).
* The system must keep the transcript with its subject for the audit and send it nowhere else; a chat about ended work is read-only over the archive, and its one proposal is a follow-up plan, a description that opens a new start naming the ended plan or epic.

[#PM-WF-25]
=== PM-WF-25: Plan Behaviour Axes & Plan Overrides

How a plan lands, the order in which it works, and how often it waits for the operator must be choices of workflow units, set at three levels and shown in the process in force.

* The system must model each plan behaviour axis as a choice between sub-workflow units, each variant one unit: landing (`landing.pull-request`, `landing.main`, `landing.files`, composed into the step list of `phase-6-finalize`, never the `land` lane), method (`method.test-first`, `method.tests-after`), and asking (`ask.every-phase`, `ask.key-points`, `ask.questions-only`, which phase transitions wait for the operator, including whether the outline is reviewed and whether the plan merges itself). The plan instance binds the chosen variant of each axis where the plan first needs it and prunes the others with the reason `plan_default`; a later change composes a new instance version.
* The system must resolve each axis by the nearest of three levels that sets it: the plan's own value, the project's (the landing a team value kept in the team configuration, the method and the asking the operator's), and the machine's default; must validate a landing variant where a project is known (at the project's choice and at a plan's start: `landing.pull-request` without a provider and `landing.main` on a protected base branch are refused with the reason), never the machine default against a repository; and must refuse `landing.files` for a plan from local changes.
* The system must let the operator set a plan's own values in either client where the plan first needs them or later from its settings (per role a harness, model, and effort; the variant of each axis; the posture and the base branch; the variant of an integration; the optional providers the plan uses), each validated like the machine's values, audited, and composing a new instance version with the composition event `override`; an override to a configuration without a current qualification record is shown as unqualified and its tasks take the qualification fallback (`PM-WORK-6`).

See the link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/workflow-dsl/09-plan-instance.adoc#plan-axes[Workflow DSL Specification, Plan Behaviour Axes], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/workflow-dsl/09-plan-instance.adoc#plan-overrides[Workflow DSL Specification, Plan Overrides], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/01-roles-and-configuration.adoc#role-assignment[Model Work Specification, Role Assignment], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/phase-workflows/01-planning-phases-1-2.adoc#_phase_14_planning_state_machines_guards[Phase Workflows Specification, Phase 1–4 Planning State Machines & Guards], link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/18-plan-unit-axes-short-landings.adoc#state-catalogue-axes[State Catalogue, Axis Variants], and link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/14-plan-instance-waivers-questions.adoc#plan-overrides-store[Store Schemas Specification, Plan Overrides (`overrides.json`)] for implementation details.

[#PM-WF-26]
=== PM-WF-26: Machine Onboarding & the Machine Scope

A freshly installed machine must be brought to a state on which projects can be set up in one guided process the operator runs in either client, and every aspect of it must be changeable alone later.

* The system must keep exactly one machine scope per machine, beside the plan, epic, and workspace scopes, whose compiled, never project-owned onboarding unit has no terminal state and rests when complete; each aspect (the harnesses, the model catalogue, the role assignment, the credential store, the providers, the plan defaults, the languages) is a sub-workflow called in the first run and called again alone from the machine's settings with its current values as the proposal.
* The system must ask before it looks at the machine, runs a program it found, or spends model tokens (`PM-SEC-8`); must start no role task before the harnesses are enrolled; and must offer an automatic run that accepts every proposal under one consent for that run, stops only at a state that cannot be decided without the operator (a login, a secret, no harness found), and ends with every value, its reason, and the check that confirmed it.
* The system must onboard a project as one process of its own per project, started only while the machine's onboarding is complete, from its checkout through detection, identity, and enrolment into the project setup (`PM-EXT-8`, `PM-EXEC-2`), with the project's operator values over the machine's values, so that several projects are onboarded at once and the machine scope is never touched.
