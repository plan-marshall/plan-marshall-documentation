[#web-server]
== Web Access & Pairing (`pm-operator web`)
_See Requirement link:../../Requirements.adoc#PM-SEC-7[PM-SEC-7: Optional Web Access, Device Pairing & Browser Channel Hardening]_

_See Requirement link:../../Requirements.adoc#PM-SEC-3[PM-SEC-3: Operator Channel Isolation (Operator CLI & Paired Web Devices)]_

_See Requirement link:../../Requirements.adoc#PM-SEC-4[PM-SEC-4: Local Transport Isolation, Operator-Gated Network Exposure & Stream Hygiene]_

_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-3[PM-WATCH-CLI-3]_

The optional web access gives a paired browser access to the runtime: the web app, one of the operator's two clients (xref:01-cli-and-installer.adoc#two-channels[Operator Choices in the Web App and the Terminal]). It is part of the runtime (`pm-mcpd`), not a binary and not a process of its own: the web adapter is a package of `pm-mcp-server` (`de.planmarshall.mcp.server.web`, link:../../Requirements.adoc#PM-IMPL-1[PM-IMPL-1]) beside the local adapter, and `pm-mcp-server` serves the web app `pm-web-app`, one of its dependencies. The web adapter owns every browser-facing concern (the TCP listeners, TLS, `Host` validation, security headers, the route restriction, the static web app, pairing redemption) and adds no store: the web device store and the pairing code are stores of the runtime. The runtime opens no TCP listener unless the operator enabled web access (`PM-SEC-4`), apart from the loopback listener fallback of the local API (link:../runtime-model/01-processes-and-transport.adoc#_transport_endpoint[Runtime & Interaction Model Specification, Transport Endpoint]). The consequence is stated in `PM-SEC-7` and in <<web-threats>>: browser-facing HTTP, TLS, and static serving run in the process that holds the credential store and the engine. The web adapter is the place the later OAuth iteration builds on (link:../../later-improvements.adoc#_l_2_oauth_for_the_web_adapter[Later Improvements, L-2]).

[#two-listeners]
=== Loopback and LAN Listeners Side by Side
_See Requirement link:../../Requirements.adoc#PM-SEC-7[PM-SEC-7: Optional Web Access, Device Pairing & Browser Channel Hardening]_

Web access has two listeners, which open and close independently, so that opening the network for another device never invalidates the loopback URL or the SSH forward the operator already holds:

* *The loopback listener*: plain HTTP on `127.0.0.1:<web.port>`, for the browsers of this machine and SSH forwards.
* *The LAN listener*: HTTPS on all interfaces on its own port `web.lan_port`, with the runtime's certificate and fingerprint (<<web-listener>>), for the operator's other devices. It opens and closes beside the loopback listener and never closes or changes it.
* *The setting*: the closed object `web` of `<PM_MCP_BASE>/machine-config.json` (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/12-machine-stores.adoc#machine-config[Store Schemas Specification, Machine Configuration Store]): `web.enabled` (boolean, default `false`) turns the loopback listener on and off, `web.lan` (boolean, default `false`) only the LAN listener, `web.port` (integer, default the compiled port `7420`) is the loopback listener's port, and `web.lan_port` (integer, default the compiled port `7421`) the LAN listener's. `web.lan` is `true` only while `web.enabled` is.
* *The acts*: `pm-operator web enable` opens the loopback listener and writes `web.enabled: true`, leaving the LAN listener as it is; `pm-operator web enable --lan` opens the LAN listener beside the loopback listener (opening that one too when it is closed) and writes `web.enabled: true` and `web.lan: true`; it is never refused because the other listener is open. The listeners are opened and closed through `PUT` and `DELETE /api/v1/web/listeners/{loopback|lan}` (link:../runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]). Turning the LAN listener off (`DELETE /api/v1/web/listeners/lan`; `pm-operator web devices listener-off`) closes only the LAN listener and writes `web.lan: false`; `pm-operator web disable` closes both and writes both `false`.
* *Judged by the listener*: a request is judged by the listener it arrived on: what is restricted to the loopback listener (<<web-proxy>>, loopback-only acts) is refused on the LAN listener, also when the request names a loopback address there.
* *Ports*: each listener applies the occupied-port rule to its own port (<<web-listener-bind>>); the ports are changed as operator configuration values (`pm-operator config`), and a changed port is used the next time its listener opens, an open listener never being re-bound.
* *Open on this machine*: `web open` and the entry on the desktop always open the loopback URL with `http` (<<web-open>>).

[#web-server-lifecycle]
=== Lifecycle (`pm-operator web enable|disable`)
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-21[PM-WATCH-CLI-21]_

* *Off by default*: Without an explicit `pm-operator web enable` (or a first `pm-operator web pair`, `pm-operator web open`, or the terminal client's entry, each of which enables the loopback listener) the runtime opens no web listener.
* *The verbs*: `pm-operator web enable [--lan]` is an operator verb (the operator checks, xref:02-operator-channel.adoc#operator-channel-isolation[Operator Channel Isolation & Operator Acts (`pm-operator`)]) and CLI-only (<<web-proxy>>). It starts the runtime on demand and sends one request; the runtime opens the listener, writes `web` (<<two-listeners>>), and the verb reports success only after a round trip on the opened listener. The verb has no port option; an occupied port fails it (`web_listener_conflict`) and leaves `web` unchanged, and another port is never chosen (<<web-listener-bind>>). `pm-operator web disable` (operator verb; also accepted from a paired device, since it narrows access) ends every open browser stream, closes both listeners, and writes `web.enabled: false` and `web.lan: false`. Paired devices stay paired; `web enable` later serves them again. No process record and no process lock exist for web access.
* *Audit*: Opening and closing a listener have no audit rule of their own. Like every operator act that changes `machine-config.json`, each appends one machine-level `operator` record with its channel (xref:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/credentials-and-enrolment/03-audit-and-outbound-https.adoc#_security_audit_trail_three_tier_identity_verification[Security Audit Trail]; link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/12-machine-stores.adoc#audit-log[Store Schemas Specification, Audit Log]).
* *Activation*: Opening and closing take effect immediately: the runtime opens or closes an HTTP server while it runs, without touching plans or jobs. Each listener is a Vert.x HTTP server beside the Unix-socket listener in the native image, with the route restriction of <<web-proxy>>; opening and closing one leaves the streams of the Unix-socket listener and of the other listener undisturbed (link:../evaluation.adoc#results[Evaluation Reference, Gate 15]).
* *At every start*: The runtime opens the loopback listener at every start while `web.enabled` is `true`, and the LAN listener while `web.lan` is `true`, each on its recorded port (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/runtime-lifecycle/01-startup-recovery-drain.adoc#_startup_sequence[Runtime & Interaction Model Specification, Startup Sequence]); a drain or stop closes them and leaves `web` unchanged. An occupied port at a runtime start leaves that listener closed: both clients of the operator report it, another port is never chosen, and the runtime still starts and serves its Unix socket. The live state of each listener (open or closed, its port, for the LAN listener the certificate fingerprint) is part of the runtime status.
* *Runtime not running*: The web listeners exist only while `pm-mcpd` runs. With the runtime stopped a browser gets a refused connection; no process answers in the runtime's place, and a browser request never starts the runtime. Under the on-demand start mode the listeners therefore return with the next command that starts the runtime; the service-managed start mode keeps them available from login (link:../runtime-model/01-processes-and-transport.adoc#_start_modes[Runtime & Interaction Model Specification, Start Modes]).

[#web-listener]
=== Listener Exposure

The web listeners are HTTP servers separate from the Unix-socket listener of the runtime's local clients (<<two-listeners>>):

* *Loopback listener*: plain HTTP on `127.0.0.1:<web.port>` only. Loopback is a secure context for the browser; nothing leaves the machine.
* *LAN listener*: HTTPS only, on all interfaces on `web.lan_port`, with a certificate the runtime generates itself the first time it opens the LAN listener: a self-signed ECDSA P-256 certificate whose subject alternative names are the host name, `<hostname>.local`, the interface addresses at generation, and the loopback addresses. Key and certificate are kept in `<PM_MCP_BASE>/web/tls/` (directory `0700`, key `0600`) and reused every later time, so paired devices keep a stable fingerprint. Its SHA-256 fingerprint (of the DER certificate) is shown by the terminal client when it opens the LAN listener or issues a code while it is open, in the runtime status, and on the pairing page, so the operator compares it with the browser's certificate details before accepting the warning. Plain HTTP is never served on a non-loopback address. A local certificate authority that removes the warning is deferred (link:../../later-improvements.adoc#_l_2_oauth_for_the_web_adapter[Later Improvements, L-2]).
* *IPv4 and IPv6*: The LAN listener is one dual-stack socket: it serves every IPv4 and every IPv6 address of the machine, the loopback addresses `127.0.0.1` and `::1` included, on its port. The certificate therefore names the addresses of both families, and the `Host` validation accepts an IPv6 address in the bracket form, in any spelling of the address (`[::1]:<port>`, <<web-security-headers>>). The loopback listener serves `127.0.0.1` only.
* [[web-listener-bind]]*Occupied port*: Each listener binds without address reuse (`SO_REUSEADDR` is not set). A port is occupied when another socket holds it on any local address: for the LAN listener on a loopback address of either family or on any other IPv4 or IPv6 address of the machine as well as on the wildcard address, for the loopback listener on `127.0.0.1` or the IPv4 wildcard address. An occupied port fails the open with `web_listener_conflict` and leaves that listener closed. A listener never opens beside another socket of the same port: on a system that lets a wildcard bind succeed beside a listener on one address when address reuse is set, the clients of that address would reach the other listener. The two listeners' ports must differ; equal ports refuse the open of the second (`web_listener_conflict`).
* *Port `0`*: A request to open a listener on port `0` (`PUT /api/v1/web/listeners/{loopback|lan}`) asks for any free port; `web.port` and `web.lan_port` of the configuration are never `0`. The listener takes a candidate port from the operating system and binds it explicitly, which applies the occupied-port rule to it; a rejected candidate is logged, and after a fixed number of candidates (8) the open fails with `web_listener_conflict`. The answer of the request and the `web` object of the runtime status carry the port the listener bound.

[#web-security-headers]
=== Request Validation & Security Headers
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-18[PM-WATCH-CLI-18], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-19[PM-WATCH-CLI-19]_

* [[loopback-host]]*`Host` validation*: Before routing, a web listener accepts a request only when its `Host` header names the listener's own origin, which defeats DNS rebinding. On the loopback listener a `Host` of `127.0.0.1`, `localhost`, or `[::1]` is accepted with any port or none: the check exists against foreign host names, and the port adds nothing to it, while an SSH forward to another local port sends that port. On the LAN listener the comparison is full: one of the certificate's names or addresses with `web.lan_port`. Every other `Host` is refused with `403` and reaches no route. An IPv6 address in `Host` (in brackets) and in `Origin` is compared by the address, not by its text: one address has many spellings, a browser sends the compressed one (`[2001:db8::1]:<port>`), and a certificate lists the full one. An IPv6 literal with a zone (`%en0`), an IPv4-mapped one, and a malformed one are refused. A name and an IPv4 address are compared without regard to case.
* *No CORS*: The web listeners send no `Access-Control-*` header on any response; a preflight `OPTIONS` request is refused. A state-changing request (`POST`, `PUT`, `PATCH`, `DELETE`) whose `Origin` header is present and differs from the listener's own origin is refused with `403`; the `Origin` is compared the same way as the `Host` (on the loopback listener `http://127.0.0.1`, `http://localhost`, or `http://[::1]` with any port or none, on the LAN listener in full with its port).
* *Security headers on every response* of a web listener (static files, API responses, event streams, errors, and `404`s alike):
** `Content-Security-Policy: default-src 'self'; script-src 'self'; connect-src 'self'; img-src 'self' blob:; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; require-trusted-types-for 'script'` (as an HTTP header, never a `<meta>` element);
** `X-Frame-Options: DENY` (anti-framing together with `frame-ancestors 'none'`);
** `X-Content-Type-Options: nosniff`;
** `Referrer-Policy: no-referrer`.
* *Harness icons*: The icon of a harness (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/client-profiles/01-profile-schema.adoc#harness-icons[Client Profiles Specification, Harness Icons]) is fetched by the runtime, never by the browser, and served from the runtime's own origin under `/api/v1/` with the device secret; the web app shows it through an object URL it creates from that answer (`img-src 'self' blob:`), so a browser never loads an image from another origin and never sends the operator's address to a maker's server. Without a fetched or bundled icon the app shows the generated monogram, the same in both clients. Whether a maker's icon may be shown or shipped at all is open: see link:../../discussions/open-questions.adoc#harness-icons[Open Questions].
* *Static web app*: A web listener serves the `pm-web-app` resource JAR (`META-INF/resources`) for every `GET` outside `/api/`; a path without a matching file returns the app's fallback page (client-side routing). No server-side rendering exists.

[#web-proxy]
=== API Access & Device Secret
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-16[PM-WATCH-CLI-16], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-20[PM-WATCH-CLI-20], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-21[PM-WATCH-CLI-21], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-26[PM-WATCH-CLI-26], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-27[PM-WATCH-CLI-27]_

The runtime serves its own local API to the browser on the web listeners, without an intermediary and without a forwarding header, restricted as follows.

* [[web-routes]]*Route restriction*: A web listener routes exactly two things, the static web app (<<web-security-headers>>) and the path prefix `/api/v1/`. `/mcp`, every other `/api/` path, and a path that changes under normalization (encoded `/`, `..`, duplicate `/`) are refused (`404`, `400`) before routing; `/mcp` is never reachable on a TCP listener. The restriction belongs to the listener: a route of the Unix-socket listener is not reachable on a web listener unless it lies under one of the two.
* *Device secret*: A browser authenticates with its device secret as `Authorization: Bearer pmw_…` (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/identifiers/02-registry-stores-to-web.adoc#id-device-secret[Identifier Registry, device secret]). The runtime checks it against the web device store on every request and every event-stream connect, without a cache, and ties the request to the device id (link:../runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]); a request without a secret, or with a malformed, unknown, revoked, or expired one, is answered `401`. Only two API endpoints are served without a device secret: the read of the message catalogue (link:../module-structure.adoc#i18n[Module Structure Specification, Languages and Internationalisation]), which the pairing page and the start view of an unpaired browser need for their texts, and pairing redemption (<<web-pairing>>).
* *No runtime token*: The runtime token is never accepted on a web listener, and neither is a job token: a request carrying one is answered `401` like any other value that is no paired device's secret. Conversely a device secret is accepted on the web listeners only. The listener a request arrived on decides which credential counts; no request header changes that.
* *CLI-only acts*: A request that arrives on a web listener is web-originated for the runtime. Issuing a pairing code, enabling web access, and opening the LAN listener refuse it with `403` (`cli_only`). Every act that narrows access is accepted from a paired device: turning the LAN listener off, `web disable`, and revoking devices.
* [[loopback-only]]*Loopback-only acts*: An act that needs the loopback listener is refused on the LAN listener with `403` (`loopback_only`), also when the request names a loopback address there: entering a credential secret (<<web-credentials>>), listing the operator's files, choosing documents outside the checkout, and moving documents (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/09-bootstrap-and-lessons.adoc#documents-source[State Catalogue Specification, Documents as a Source]). On the loopback listener a paired device may take them, like the terminal client.
* *The designer*: Every endpoint of the process designer (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/workflow-dsl/04-ast-node-model.adoc#process-designer[Workflow DSL Specification, Designing a Process]) is reached on the web listeners with the device secret; none of them is CLI-only or loopback-only.
* *Event streams*: The event streams of the local API (link:../runtime-model/01-processes-and-transport.adoc#event-streams[Runtime & Interaction Model Specification, Events per Scope]) are served unbuffered and uncompressed, honouring `Last-Event-ID`; the device is checked when a stream connects, and the runtime ends a device's open streams when the device is revoked or expired (<<devices>>) and the streams of the LAN listener when it closes, each with the last event `stream.closed` that carries the reason (`device_revoked`, `device_expired`, `listener_closed`).
* *Logging*: The runtime logs every request to open a listener and every close with what caused it, and a connection that fails before its first request (a failed TLS handshake included) as a warning of one line without a stack trace, since a client can cause it at will. The runtime logs no request header. The runtime token and every `pmw_` value are redacted by the `SecretRedactor` (xref:02-operator-channel.adoc#operator-credential-cli[Operator Credential Acts & Runtime Secret Redaction]): the runtime token by value, device secrets by their shape, because the runtime keeps only their hashes.

[#web-credentials]
=== Credentials in the Web App
_See Requirement link:../../Requirements.adoc#PM-CRED-4[PM-CRED-4: Operator-Only Secret Entry & Zero Model Exposure]_

A web-driven onboarding completes its credentials in the browser (link:../../use-cases/01-onboarding.adoc#UC-ONB-8[UC-ONB-8]):

* The credential endpoint (`PUT /api/v1/credentials/{credential_key}`) accepts a secret from a paired device on the loopback listener only; on the LAN listener it is refused with `loopback_only` (<<loopback-only>>), and the form names the terminal command that enters it (`pm-operator credentials set <credential_key>`) instead.
* The secret goes from the form straight to the credential store in the body of one request; the app keeps no copy, never shows it again, and it never reaches a model or a log (xref:02-operator-channel.adoc#web-credential-form[Operator Credential Acts]). A `github_app` entry runs its device flow in the form, which shows the verification URL and the user code.
* An act of the operator's own needs no consent; before the credential store is chosen the endpoint refuses with `onboarding_incomplete` (xref:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/credentials-and-enrolment/01-provider-credentials.adoc#credential-store-choice[Credential Store as an Operator Choice]).

[#web-pairing]
=== Pairing Protocol
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-15[PM-WATCH-CLI-15]_

Pairing follows the device-grant pattern: a short one-time code only authorizes; the browser receives a separate per-device secret.

. *Issue*: The terminal client asks the runtime for a pairing code (`POST /api/v1/web/pairings`, CLI-only): `pm-operator web pair [--label <label>]` (operator verb; enables the loopback listener when web access is not enabled), `web open` where it pairs, and the entry (xref:01-cli-and-installer.adoc#start[The Terminal Client as the Entry]). The code has 8 characters of the alphabet `BCDFGHJKLMNPQRSTVWXZ` (about 34.5 bits, link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/identifiers/02-registry-stores-to-web.adoc#id-pairing-code[Identifier Registry, pairing code]), is valid for the pairing code lifetime (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/timeouts/02-runtime-leases-operator-web.adoc#pairing-code-ttl[Timeouts & Budgets Specification, Pairing Code Lifetime]), single use, and allows a bounded number of failed redemptions (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/timeouts/02-runtime-leases-operator-web.adoc#pairing-attempt-limit[Timeouts & Budgets Specification, Pairing Failed-Attempt Limit]). At most one pairing is open at any time: a new one invalidates the previous. The runtime keeps only the code's SHA-256, the label, the issuing verb, the expiry, and the failure count, in memory (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/12-machine-stores.adoc#web-access-records[Store Schemas Specification, Web Access Records]). The code reaches only the terminal client that asked for it, in the answer to its request, and never a stream a browser reads.
. *Show*: The terminal client prints the code as `XXXX-XXXX`, the URL `http://127.0.0.1:<web.port>/pair#code=<code>` (on the LAN listener `https://<host>:<web.lan_port>/pair#code=<code>`), a QR code of that URL (Unicode half blocks, 4-module quiet zone, black on white), the expiry, and while the LAN listener is open the certificate fingerprint. The code travels in the URL fragment, which the browser never sends to a server, so it appears in no request line, log, or `Referer`.
. [[fresh-code]]*A fresh code after a redemption*: While the terminal client's console is open, a redeemed code is replaced at once by a new one: on the event of a pairing (`device.paired`, with the `device_id`, label, and `paired_from`, never a code; link:../runtime-model/06-event-catalogue.adoc[Runtime & Interaction Model Specification, Event Catalogue]) on the runtime-wide stream, the console asks for a new code as above and shows it with its URL and QR code on request (`web qr`); the operator can also replace it (`web pair`). The rule of one open code holds throughout, so the first device to pair never uses the code up for the other ways in the console still shows.
. [[web-open]]*Open on the same machine*: `pm-operator web open [--pair]` (operator verb) opens the web app in the default browser of the machine (`open` on macOS, `xdg-open` on Linux, started with an argument vector, never through a shell). It always opens the loopback URL (`http://127.0.0.1:<web.port>/…`), opening the loopback listener where it is closed, also while the LAN listener is open.
** *Pairing*: when the loopback listener was closed, when the web device store holds no device paired through `web open` or the entry on the desktop (`paired_by: open`), or with `--pair`, the verb issues a pairing code like `web pair` (label proposed from the browser and the machine) and opens the pairing URL; the device the redemption creates is recorded with `paired_by: open`. Opening a closed listener or issuing a code asks for confirmation when the verb runs as one shell command.
** *No pairing*: otherwise it opens the app's start URL without a code. It then changes no state, so it asks for no confirmation; the terminal and host-agent checks of an operator verb still apply. `pm-operator` reads the listener state from the runtime status and the devices from `GET /api/v1/web/devices`.
** *A browser that is not the paired one* (another browser, or one whose storage was cleared) gets the start URL without a code and holds no device secret: the app shows the pairing page, which names `pm-operator web open --pair` and the terminal client.
** *No browser*: when the browser cannot be started (the command is missing or exits with a failure, as on a machine without a desktop session), the verb prints the URL and reports that no browser was opened; an issued pairing code stays valid for its lifetime.
. *Redeem*: The web app's pairing page reads the code from the fragment (or from manual input, normalized to upper case without `-` and spaces) and removes the fragment with `history.replaceState`. An app that holds a device secret the runtime still accepts (a `200` on an authenticated request) does not redeem the code and shows its start view: the browser keeps its device, no second device is created for it, and the unredeemed code stays open for another device. Otherwise the page sends `POST /api/v1/pair` with `{code}` and the label it proposes from the browser and its machine. The runtime compares the SHA-256 in constant time; on success it consumes the code, generates the device secret (`pmw_` plus 256 bits from `SecureRandom`, base64url; link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/identifiers/02-registry-stores-to-web.adoc#id-device-secret[Identifier Registry, device secret]), stores only its SHA-256 with a new `device_id`, the label (the pairing's label where the terminal client named one, else the proposed one, else the `device_id`), the verb that issued the code (`paired_by`), and the listener the redemption arrived on (`paired_from`: `loopback` or `lan`), appends the audit record `web_device_paired`, announces `device.paired`, and returns `{device_id, label, device_secret}` once. The secret is opaque: the runtime is issuer and validator, so a self-contained token would add nothing and could not be revoked instantly.
. *Failure*: A wrong, expired, consumed, or superseded code yields the same `400` (`pairing_invalid`) without saying which, and appends `web_pairing_failed`. The failure that reaches the attempt limit invalidates the open pairing, so a later redemption fails even with the right code. A runtime restart discards the open pairing; the terminal client issues a new one.
. *Keep*: The web app stores the device secret and its `device_id` in `localStorage` and sends the secret as `Authorization: Bearer <device secret>` on every API request (<<web-app>>).

[#web-devices]
=== Paired Devices
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-17[PM-WATCH-CLI-17]_

* [[devices]]*Devices in both clients*: The list, rename, revoke, revoke all others, and turning the LAN listener off are operator endpoints of the local API for both clients (link:../../use-cases/02-entry.adoc#UC-ENT-2[UC-ENT-2]): `GET /api/v1/web/devices` (every paired device with `device_id`, label, `created_at`, `last_used_at`, `paired_by`, and `paired_from`), `PATCH /api/v1/web/devices/{device_id}` (a new label), `DELETE /api/v1/web/devices/{device_id}`, `DELETE /api/v1/web/devices?others` (every device but the one the request comes from), and `DELETE /api/v1/web/listeners/lan` (<<two-listeners>>; link:../runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]); the terminal client's verbs are `pm-operator web devices [list|rename <device_id> <label>|revoke <device_id>|revoke --others|revoke --all|listener-off]`. The web app marks the device it acts from by its own `device_id`; the terminal client acts from no device, so its _revoke all others_ and _revoke all_ both send `?others` and revoke every paired device.
* *Immediate revocation*: A revoked device's record is removed from `state/web-devices.json`; the runtime ends the device's open event streams at once, each with the last event `stream.closed` with the reason `device_revoked` (with the channel and device that revoked it and when; link:../runtime-model/06-event-catalogue.adoc[Runtime & Interaction Model Specification, Event Catalogue]), which the web app shows before it deletes its stored secret and shows the pairing page, and answers its next request `401`. Every revocation appends `web_device_revoked`.
* *Idle expiry*: A device whose `last_used_at` is older than the device idle expiry (compiled, link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/timeouts/02-runtime-leases-operator-web.adoc#device-idle-expiry[Timeouts & Budgets Specification, Device Idle Expiry]) is expired: its streams end with `stream.closed` with the reason `device_expired`, its next request is answered `401`, and its record is removed with `web_device_revoked` (`reason: idle_expired`). `last_used_at` is written at most once per write-granularity interval per device (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/timeouts/02-runtime-leases-operator-web.adoc#device-last-used-granularity[Timeouts & Budgets Specification, `last_used_at` Write Granularity]). Rotation and absolute expiry are deferred (link:../../later-improvements.adoc#_l_2_oauth_for_the_web_adapter[Later Improvements, L-2]).
* *Store damage*: An unreadable or invalid `state/web-devices.json` authenticates no device (every web-originated request `401`, reported by both clients' status) and leaves the CLI binaries unaffected; revoking all devices from the terminal client rewrites an empty store.

[#web-operator-channel]
=== Every Paired Device Is an Operator Channel

There are no device roles: every paired device may take every operator act of the local API (xref:02-operator-channel.adoc#operator-channel-isolation[Operator Channel Isolation & Operator Acts (`pm-operator`)]), except the CLI-only acts and, on the LAN listener, the loopback-only acts of <<web-proxy>>. A paired device answers every operator wait of the machine, a project, a plan, an epic, or an entry, decisions, waiver requests, consents, and the choices of an onboarding, a setup, or a start included, through the same endpoints as the terminal client; the first valid answer wins. The app keeps decisions and waiver requests apart, and an answer is never an override. Every act through a paired device is audited with channel `web` and the `device_id`. Pairing a device is an operator act for this reason, and every device secret is as powerful as the operator. Roles (`viewer`, `operator`) and step-up before operator acts from a browser are deferred (link:../../later-improvements.adoc#_l_1_operator_proof_beyond_the_cli_checks[Later Improvements, L-1]).

[#web-auth-seam]
=== Authentication Seam

The runtime uses Quarkus Security on every listener: one `HttpAuthenticationMechanism` (Bearer) and one `IdentityProvider` per token kind, and resources annotated only `@Authenticated` (`@RolesAllowed` once roles exist). Which token kind a request may present is fixed by the listener it arrived on: the Unix-socket listener has the providers for the runtime token and the job token, the web listeners only the provider for `pmw_` device secrets, which validates the secret against the web device store (<<web-proxy>>). The OAuth iteration adds a provider wrapping Token-Sheriff validation for three-part JWTs next to the `pmw_` provider, so paired devices keep working during the switch; `token-sheriff-bom` stays imported for it (link:../../later-improvements.adoc#_l_2_oauth_for_the_web_adapter[Later Improvements, L-2]).

[#web-app]
=== Web App (`pm-web-app`)

* *Build*: SvelteKit 3 (release candidate, pinned; moved to 3.0 final when released) with Svelte 5 and TypeScript, built as a static single-page app (`@sveltejs/adapter-static`, `ssr = false`, fallback page) by `frontend-maven-plugin` with pinned Node and npm (`npm ci` from `package-lock.json`), tested with Vitest, and packaged as a resource JAR (`META-INF/resources`) that `pm-mcp-server` depends on and `pm-mcpd` serves. The npm packages are covered by the CycloneDX SBOM. During development the Vite dev server proxies `/api` to the loopback listener of a running runtime.
* *Views*: The web app's views are its design (link:https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/design/web-app/README.adoc[`pm-mcp-clients`, Web App]): the entry and pairing, the machine's onboarding and settings, the projects with their onboarding, starting work, the overview of running and ended work, a plan's process and an epic, the decisions, the holds and the acts on plans and epics, the reports, the system view, the cleanup, the paired devices, and the process designer. Each reads the operator representations and event streams of the local API (link:../runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]), never a store and never a model-facing representation.
* *Dependable view and channel*: Both clients of the operator are dependable views of every plan, epic, worker, and task and dependable channels of every operator wait (`PM-SEC-7`, `PM-WF-12`, `PM-WF-20`). The web app shows every open operator wait with its facts, its proposal, and its operator links, a decision with its parts, options, support, and recommendation (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/06-envelopes-questions-deadlines.adoc#decision-structure[Model Work Specification, The Decision Structure]), and answers it through the scope-qualified answer endpoint of the local API (channel `web`; the first valid answer wins, a later one is refused `already_answered`). On the event of a newly opened decision or waiver request it raises a browser notification where the device granted the permission; a decision answered in the terminal client is withdrawn with a note that says so.
* *Texts*: The web app holds no text of its own besides its fallback for a failed load: it loads the message catalogue of the interface language from the runtime and renders every runtime text from its message key and arguments, and external and model text verbatim and as plain text (link:../module-structure.adoc#i18n[Module Structure Specification, Languages and Internationalisation]).
* *Live updates*: The app reads the event streams with `fetch()` and a `ReadableStream`, because `EventSource` cannot send an `Authorization` header; a credential never appears in a URL. It reconnects with `Last-Event-ID`.
* *Browser storage*: The device secret is kept in `localStorage`, so the pairing survives browser restarts; the app never uses cookies. Its exposure to injected script is contained by the security headers (<<web-security-headers>>), Trusted Types, no third-party scripts or origins, no `{@html}` or other raw-HTML sink (all server text, the activity of a worker included, is rendered as text), and lockfile-pinned dependencies; revocation and idle expiry are the recovery. Sender-constrained credentials (a non-extractable WebCrypto key, DPoP) are deferred (link:../../later-improvements.adoc#_l_2_oauth_for_the_web_adapter[Later Improvements, L-2]).

[#web-threats]
=== Threat Notes

* *Browser-facing surface inside the runtime*: HTTP parsing, TLS, and static serving for browsers run in the process that holds the credential store, the stores, and the engine; no process boundary stands between a flaw in that surface and the runtime. This is the accepted consequence of serving web access from the runtime (`PM-SEC-7`). The mitigations are: web access is off by default; the loopback listener serves `127.0.0.1` only, and the LAN listener opens only on the operator's act and only over TLS; every request passes the `Host` validation before routing and needs a device secret that the runtime checks on every request; the listeners route nothing but the web app and `/api/v1/`, never `/mcp`, and never accept the runtime token; the LAN listener can be turned off from either client, and `pm-operator web disable` closes both.
* *Cross-site scripting*: `script-src 'self'` with Trusted Types blocks injected and inline script and raw-HTML sinks; `connect-src 'self'` keeps script from sending the secret to another origin by `fetch`; `img-src 'self' blob:` admits only images of the app's own origin and object URLs the app created. Accepted residual: script that does run in the app's origin can read `localStorage` and act as the device until it is revoked (link:../../later-improvements.adoc#_l_2_oauth_for_the_web_adapter[Later Improvements, L-2]).
* *A same-user process beside an open listener*: The occupied-port rule holds at the open. On macOS a process of the same user that sets `SO_REUSEADDR` can afterwards bind one specific address (`127.0.0.1`, `::1`, an address of an interface) on the port of the open LAN listener and then receives the connections to that address; Linux refuses that bind. This is accepted: a process of the same user is no boundary (it can read the certificate key, the web device store, and the runtime token; _Same-user processes_ below), and on the LAN listener a client that is taken over this way fails the certificate check, since the other process does not hold the key unless it read it. The runtime adds no socket per address against it. Not verified: a process of another user (expected to be refused by the operating system; to be measured with a second account).
* *DNS rebinding*: A rebound page carries a foreign `Host` and is refused before routing; it also has no access to the app origin's `localStorage`, and the credential is never ambient.
* *Cross-site request forgery*: Not applicable: the credential is an explicit `Authorization` header, never a cookie; no CORS is granted.
* *Framing*: `frame-ancestors 'none'` and `X-Frame-Options: DENY` on every response prevent clickjacking of operator acts.
* *Code interception*: The pairing code is short-lived, single use, limited in failed redemptions (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/timeouts/02-runtime-leases-operator-web.adoc#pairing-attempt-limit[Timeouts & Budgets Specification, Pairing Failed-Attempt Limit]), carried in the URL fragment, reaches only the terminal client, and on the LAN listener only over TLS.
* *Same-user processes*: Web access adds no boundary against processes of the same OS user: any of them can read the runtime token and call the local API on the Unix socket directly, including operator endpoints (link:../../later-improvements.adoc#_l_1_operator_proof_beyond_the_cli_checks[Later Improvements, L-1]).
* *Model surface*: Nothing of the web access, the pairing, or the device store is reachable through an MCP tool or appears in a model-facing representation (link:../mcp-tools.adoc[MCP Tools Specification], Architectural Constraints; link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).
