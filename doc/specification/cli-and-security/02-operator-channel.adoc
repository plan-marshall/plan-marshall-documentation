[#operator-credential-cli]
== Operator Credential Acts & Runtime Secret Redaction
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-28[PM-WATCH-CLI-28]_

* *Entering a secret*: Credential mutations and verifications are operator acts of the operator's two clients, executed by the runtime through its local API (`PUT /api/v1/credentials/{credential_key}`, link:../runtime-model/01-processes-and-transport.adoc#api-no-secret-read[Runtime & Interaction Model Specification, Local API, Credential entries]):
** *The terminal client*: `pm-operator credentials set|status|verify|remove|rotate <credential_key> [--project]` and `pm-operator credentials migrate os|file` (operator verbs, <<operator-channel-isolation>>), and the credential states of the onboarding in its console. `set` and `rotate` always read the secret from the terminal with echo disabled into a `char[]`, never into a `String` (`System.console().readPassword()` for a verb run as one shell command; in the console, character by character from the terminal of its line editor, never through the line reader, whose result is a `String` and whose history must not see it), together with the non-secret fields (`url`, `auth_type`, header settings; for `github_app` the `client_id` and optional `installation_id`, the PKCS#1 or PKCS#8 `private_key` being read as a secret), and send them in the body of one request over the Unix domain socket; `pm-operator` keeps the secret only in a `char[]` that it clears after the request and never writes it anywhere.
** [[web-credential-form]]*The web app*: the credential form of a paired device on the loopback listener sends the secret in the body of one request straight to the credential store; the app keeps no copy and never shows it again (xref:03-web-server.adoc#web-credentials[Credentials in the Web App]). A request that arrives on the LAN listener is refused (`loopback_only`, `403`), and the form names the terminal command instead.
+
A credential the operator enters is stored on that act and needs no consent. The runtime writes the entry into the recorded store; for the file store it writes the complete credential file in the `PM-MCP` format (`format_version`, closed schema, link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/12-machine-stores.adoc#credential-store[Store Schemas Specification, Credential Store]) atomically with mode `0600`, under `<PM_MCP_BASE>/locks/credentials.lock`. For a `github_app` entry, `set` (and `rotate`) then runs the GitHub device flow: the runtime requests a device code for the `client_id` on the entry's `url` origin, the client shows the verification URL and the user code, the operator authorizes the App in the browser, and the runtime polls at the interval the provider names until it receives the user tokens or the code expires (the act then fails and writes nothing); it stores the refresh token with its expiry (`expires_at`) in the entry and never shows either token. The runtime is the only writer of credential files, on an operator act, a store move, and, for the rotated refresh token of a `github_app` entry, in its token refresh (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/credentials-and-enrolment/01-provider-credentials.adoc#user-access-token[user-access-token]): no placeholder file and no hand-edited file exists, and a file it did not write in the current format is refused (`credentials_file_invalid`). Secrets are never accepted from command-line arguments or environment variables.
* *Identity, Kind & Expiry*: For `github`, `gitlab`, and `forgejo` entries, setting and verifying call `ci.whoami` and record the token kind (`token_kind`) and, where the provider reports one, the expiry (`expires_at`; an operator-entered expiry otherwise); `verify` shows the resolved identity, its permissions on the enrolled repository, and whether it can read check runs (`checks_visible`), without revealing the secret. `status` reports per entry one of `present` (stored, not yet verified), `not_found`, `verified`, `unverified`, the serving store, plus `expiring` when `expires_at` lies within the credential expiry warning window (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/timeouts/02-runtime-leases-operator-web.adoc#credential-expiring-window[Timeouts & Budgets Specification]), and names an entry without a known expiry; neither is a refusal, and neither reaches a model-facing representation, since an expiring credential still works. No act shows a stored secret, and the runtime's API has no endpoint that returns one: `status` and `verify` read the entry inside the runtime and receive only its status and store (link:../runtime-model/01-processes-and-transport.adoc#api-no-secret-read[Runtime & Interaction Model Specification, Local API, Credential entries]). `rotate <credential_key>` replaces the secret of an existing entry, keeps its non-secret fields, and drops every token derived from the old secret (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/credentials-and-enrolment/01-provider-credentials.adoc#derived-tokens[Short-Lived Derived Tokens]); replacing a stored secret is always an operator act, and the only automatic replacement is the refresh-token rotation of the user access token (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/credentials-and-enrolment/01-provider-credentials.adoc#user-access-token[user-access-token]). For `gitlab`, `ci.whoami` reads `GET /personal_access_tokens/self`; for a token that endpoint refuses because it is no personal access token (an OAuth token, `400`), it falls back to `GET /user` for the identity and records `token_kind: gitlab_oauth_token`; GitLab reports neither scopes nor an expiry for such a token there, so its scopes stay unknown and its expiry is the operator-entered one or unknown. `migrate os|file` is the store move (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/credentials-and-enrolment/01-provider-credentials.adoc#credential-store-move[credential-store-move]); a failed write or read-back reports `credential_store_failed` (link:../runtime-model/01-processes-and-transport.adoc#api-error-codes[Runtime & Interaction Model Specification, Local API Error Codes]).
* *Zero Model Exposure & Redaction*: No MCP tool, resource, or state representation exposes credential values (`status` reports only metadata: provider name, scope, store, and configured status). Every secret value resolved for a request, and every value derived from one (a GitHub App JWT and installation token, link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/credentials-and-enrolment/01-provider-credentials.adoc#derived-tokens[Short-Lived Derived Tokens]; the `user:token` form of a git transport credential), is added to the in-memory redaction registry of the `SecretRedactor` filter, which keeps it for the runtime's lifetime solely to scrub matching byte/character sequences to `[REDACTED]` across tool results, representations, log records, activity journals, `audit.jsonl` entries, and error messages. The registry is never persisted and never exported to subprocess environments or logs; it is discarded when the runtime stops (`PM-CRED-5`).
* *Runtime Secrets*: The local-trust and web secrets are redacted the same way (`PM-SEC-6`): the runtime token (link:../runtime-model/01-processes-and-transport.adoc#runtime-token[Runtime & Interaction Model Specification, Runtime Token]) is registered by value when the runtime writes it and by `pm-operator` when it reads it; a worker's job token (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/identifiers/02-registry-stores-to-web.adoc#id-job-token[Identifier Registry, Job Token]) is registered by value when the runtime mints it and is also scrubbed by its `pmj_` shape, because only its SHA-256 survives a runtime restart; device secrets (`pmw_` values) and pairing codes are scrubbed by their shape (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/identifiers/02-registry-stores-to-web.adoc#id-device-secret[Identifier Registry, device secret]; link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/identifiers/02-registry-stores-to-web.adoc#id-pairing-code[Identifier Registry, pairing code]), because the runtime keeps only their SHA-256 hashes. None of them is written to a log, an audit record, a command-line argument, a process environment (the job token's relay environment excepted), or a representation; request headers are never logged (xref:03-web-server.adoc#web-proxy[API Access & Device Secret]). A pairing code reaches only the terminal client that asked for it, printed to the operator's terminal and never logged. No runtime secret other than a worker's own job token (in its relay's environment `PM_MCP_JOB_TOKEN`) is ever passed to a job: the runtime token file lies outside every job's Landlock read set (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/job-runtime/02-confinement-and-environment.adoc#_linux_filesystem_confinement_landlock[Job Runtime Specification]).

== Operator Channel Isolation & Operator Acts (`pm-operator`)
_See Requirement link:../../Requirements.adoc#PM-SEC-3[PM-SEC-3: Operator Channel Isolation (Operator CLI & Paired Web Devices)]_

_See Requirement link:../../Requirements.adoc#PM-WF-12[PM-WF-12: Question Records vs Operator Overrides]_

_See Requirement link:../../Requirements.adoc#PM-WF-23[PM-WF-23: Operator Acts on Plans and Epics]_

_See Requirement link:../../Requirements.adoc#PM-CLIENT-3[PM-CLIENT-3: Host Environment Detection]_

_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-3[PM-WATCH-CLI-3], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-14[PM-WATCH-CLI-14], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-22[PM-WATCH-CLI-22], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-24[PM-WATCH-CLI-24]_

Operator acts are unreachable from every MCP tool and every model-facing link. Each is an operator endpoint of the runtime's local API (link:../runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]), offered alike to the operator's two clients (xref:01-cli-and-installer.adoc#two-channels[Operator Choices in the Web App and the Terminal]): in the terminal client as a verb of `pm-operator`, given directly as `pm-operator <verb>` without an `operator` level or typed in its console, and in the web app on a paired device. The worker-facing binary `pm-mcp` (`serve --job`) has none of them. The runtime executes every act as an audited transaction, validates it, and answers with the new state; `pm-operator` writes nothing itself. The operator verbs of the terminal client (`status`, `system`, `drain`, `runtime start|install|uninstall`, and `client` are verbs of the same binary but not operator verbs, xref:01-cli-and-installer.adoc#command-tree[Command Tree]):

The machine settings also list the remembered consents, each withdrawn by an operator act of either client (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/12-machine-stores.adoc#consent[Store Schemas Specification, Consent Before Acting]); every grant and withdrawal is audited.

1. *Operator Channels*: Every operator act takes one of the two channels of the operator's clients: `cli`, the terminal client `pm-operator` (a verb, the console, the `pm-operator web ...` verbs included), or `web`, a paired web device (xref:03-web-server.adoc#web-operator-channel[Every Paired Device Is an Operator Channel]), which has operator rights because only an operator verb can pair it. The answers of operator waits (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]) are content answers of the channels `cli` and `web`: a decision of a plan or an epic, a consent, and every choice of an onboarding, a setup, or a start are answered in either client through the same endpoints, the first valid answer winning (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/14-plan-instance-waivers-questions.adoc#cli-answers[Store Schemas Specification, Answers from the Terminal Client]). The overrides (`waive`, `unwaive`, `decline`, the ends of a plan or an epic, `delete-plan`, `grant-access`, the integrity resolutions, operator configuration) are the operator's own acts in the same two channels. None of them routes through the model, and MCP elicitation carries no operator act; every act is audited with its channel (`cli`, or `web` with the `device_id`). An override is never taken as a content answer, and a content answer is never an override; an act relayed by the model (for example a "waive" typed into a harness's chat) is never accepted. Beside the answers, the operator acts on a running plan by waivers, access grants, pausing and starting it, ending it, `delete-plan`, the acts of a hold, and the plan's own settings, each on the operator's own initiative.
2. *CLI Operator Checks*: Before it sends an operator act, `pm-operator` verifies that it is attached to an interactive terminal (`System.console() != null && System.console().isTerminal()`) and that none of the coding-agent environment signals of the link:../host-integration/01-host-detection.adoc#host-integration-table[Host Integration Table] (primary and secondary) is present; either failure refuses the verb with a diagnostic naming the detected host before any request is sent (exit code `4`). The console runs the checks when it opens. Every act that cannot be undone then asks for interactive confirmation of the displayed change; a read-only verb (for example `waivers`, `roles list|show`, `audit verify`, or `sweep` without `--apply`) needs only these terminal and environment checks. The host deny rule installed with the bundles denies the whole binary `pm-operator` to the model (`Bash(pm-operator:*)`, no sub-command rule; `pm-mcp serve --job` stays allowed; link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/client-profiles.adoc[Client Profiles Specification]) and is defence in depth against a model shell. There is no passphrase, no operator session, and no operator credential or passphrase in the credential store (its only operator-lane entry is the enrolment integrity key, link:../../concepts/enrolment.adoc#integrity[Concepts § Enrolment, Integrity]): the operator proof of the first iteration is these checks alone.
3. *Accepted Risk*: The checks guard against accidental and naive invocation, not against a model shell that deliberately defeats them (a pseudo-terminal, a cleared environment, indirect invocation). The runtime cannot verify the checks of `pm-operator`, so any process of the same OS user that holds the runtime token can call the operator endpoints directly (for example with `curl --unix-socket`). This is accepted for the first iteration and documented as a residual risk (`PM-SEC-3`); a user proof the model cannot produce (an operator passphrase session, OS user presence) and device roles with step-up are deferred (link:../../later-improvements.adoc#_l_1_operator_proof_beyond_the_cli_checks[Later Improvements, L-1]). Every operator act stays recorded in the audit log (`PM-SEC-6`).
4. [[operator-integrity-pause]]*Integrity Pause*: The `integrity_breach` condition (a tampered plan, epic, or workspace store, a tampered pending entry record, or a tampered enrolment file, which pauses every running plan of the project; link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/13-leases-integrity-testing.adoc#store-digest-verification[Store Schemas Specification, Store Digest Verification]) holds its scope as a hold of kind `integrity_pause` (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/01-conventions-generic-conditions.adoc#holds[State Catalogue Specification, Holds and Their Acts]). The state and `call_stack` stay unchanged, the model-facing representation offers no link, no task of the scope is offered, and every `pm_do` is rejected with `integrity_paused`. The hold shows the tampered file with its recorded and current size and SHA-256; it restores nothing and shows no diff, because the prior content is not kept. Its acts are closed: *accept* (`accept-edit`, <<operator-accept-edit>>; the engine re-verifies before it clears the condition) and *cancel*, whose resolution is the integrity abort: a plan ends with the outcome `aborted`, an epic with the `terminal_reason` `cancelled` (<<operator-abort>>); the workspace scope has no cancel, so `accept-edit workspace <store>` is its only resolution. A tampered pending entry record holds only its entry, never the workspace scope's own state or its other entries, and ends by accepting the edit or by abandoning the entry. The hold has no time bound and no fallback, because a tampered store cannot be trusted to write a hand-back. A tampered harness enrolment (`harnesses.json`) is no pause: it refuses the worker launch (`harness_tampered`), which counts as a start failure of the role on that harness and ends, once the start-failure guard holds, in the conservative fallback of the role's tasks (<<operator-enrol-harness>>). Every other condition is bounded by its self-remedy budget and ends in the phase's fallback (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/timeouts/01-job-budgets-and-waits.adoc#condition-budget[Timeouts & Budgets Specification, Condition Budget]); one that needs the operator meanwhile is shown as a hold with its acts.
5. [[operator-drop-capture]]*Capture Ref Removal (`pm-operator drop-capture <plan_id>`)*: A `land` plan that ended without `merged` keeps its capture ref `refs/pm-mcp/captures/<plan_id>` in the enrolled repository as the user's recovery point and owes `capture_ref_retained` (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/phase-workflows/02-planning-lanes-phases-3-4.adoc#land-lane[Phase Workflows Specification, Land Lane, item 5]). The act shows the ref's snapshot commit and its paths, deletes the ref after confirmation, discharges the owed item `capture_ref_retained` (also for an archived plan), and appends an `audit.jsonl` record. `drop-capture` and `discharge-owed` (which records `discharge_proof` and `discharged_at` of an owed item whose discharger is `operator`, link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/03-findings-and-review-records.adoc#owed-item-record[Store Schemas Specification, Owed Item Record]) are the only writes an archived plan accepts. It is operator-only like every act of this section; no workflow state, recovery sweep, or MCP tool removes a retained capture ref.
6. [[operator-waive]]*Waivers (`pm-operator waive`, `decline`, `unwaive`, `waivers`)*: `waive <plan_id> <gate> --reason <text> [--reason-class <class>]` declares a waivable gate met (`review_evidence[:<bot_kind>]`, `ci_check:<name>`, `analysis_gate:<provider>`, `findings:<class>`, `qgate_findings:<phase>`, link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/identifiers/02-registry-stores-to-web.adoc#id-waivable-gate[Identifier Registry, Waivable Gate Identifier]); `waive <plan_id> --raise <budget>=<N> --reason <text>` sets the absolute ceiling of `fix_budget:<policy>` or `retry_budget:<policy>` for the plan, above the effective ceiling in force and at most the compiled hard cap. A waiver may be given at any time from plan start until the gate's fallback is taken, and it applies to every later evaluation of the gate; the client shows the plan, the gate, and the effect before the confirmation. `--reason-class` classifies the reason (`gate_false_positive`, `gate_not_applicable`, `tooling_unavailable`, `deliberate_deferral`, default `unknown`; link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/14-plan-instance-waivers-questions.adoc#waiver-record[Store Schemas Specification, Waiver Record]); it is mirrored into the audit log with the gate, where the Artifact Gate recurrence count and the lessons-capture signal read it. The runtime appends the record to `waivers.jsonl` (the only writer), mirrors it to `audit.jsonl`, and composes a new plan instance version. `unwaive <plan_id> <waiver_id>` revokes an unconsumed waiver; revoking a raise lowers the ceiling at the next budget check, where a counter already above it exhausts the budget and the fallback follows, without a refusal. Refusals: `not_waivable` (a gate outside the closed list, or on the non-waivable list of link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/14-plan-instance-waivers-questions.adoc#waiver-record[Store Schemas Specification, Waiver Record, Refusals]), `plan_ended` (the gate's fallback was taken or the plan ended), `already_consumed`, `raise_out_of_range`, `position_not_contained`. A waiver request filed by a worker's `request_waiver` in a remediation unit is an operator wait (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]) with no time limit: it ends by `waive` (naming the gate, optionally `--request <request_id>`) or by `decline <plan_id> <request_id> --reason <text>`, which records the outcome `declined` and lets the remediation unit take its next transition. Requests are shown in both clients, announced by the terminal client while it is open, shown in the plan's view as `facts.waiver_request` (link:../mcp-tools/01-core-workflow-tools.adoc#question-waiver-facts[MCP Tools Specification, Waiver Requests in Representations]), and posted as an idempotent pull request comment with the label `pm-mcp:waiver-requested`; the announcements are information only. Every waiver and consumption is listed in the pull request comment and the landing record.
7. [[operator-accept-edit]]*Accept-Edit (`pm-operator accept-edit`)*: The act of accepting a manual edit, in either client, shows the file's path and its recorded and current size and SHA-256 before the confirmation; there is no diff and no restore, because the prior content is not kept. On confirmation the runtime re-baselines the store's digest (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/13-leases-integrity-testing.adoc#store-digest-verification[Store Schemas Specification, Store Digest Verification]), the lesson's entry, or the enrolment file's HMAC sidecar (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#enrolment-integrity[Enrolment Integrity]), and appends an `audit.jsonl` record. The resolutions of an `integrity_breach` are those of the integrity pause (item 4). A workspace `<store>` is named relative to the project store root (`pending/<entry_id>/entry.json` for a pending entry record), a plan's or epic's relative to its scope directory (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/01-format-and-session-log.adoc#transaction-journal[Store Schemas Specification, Transaction Journal]).
8. [[operator-abort]]*Ending a Plan or an Epic*: The operator ends a plan through `plan.aborted` in the next transaction, an engine-owned scope-wide transition under the on-entry rule (every begun, unsettled step is recorded `failed`), with the operator's reason (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/04-plan-finalize-terminal.adoc#plan-end[State Catalogue Specification, Cancelling and Abandoning Archive]): *cancel* a running, pausing, waiting, or held plan (outcome `cancelled`), or *abandon* a paused one (outcome `abandoned`), choosing in the confirmation whether an open pull request of the plan is closed with a comment naming the reason or left open (its branch stays); `pm-operator abort plan <plan_id> --reason <text>` is the shell form of both, cancel or abandon by the plan's state. The plan is archived like a completed plan; open decisions and waiver requests are closed `cancelled`, and the plan's lesson claims are released. `plan.aborted` is also entered by the integrity abort (outcome `aborted`, item 4), by the release of the project (outcome `released`, link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#project-release[Releasing Ends Work as the Operator Ends It]), and by `delete-plan` (fixed reason `plan_deleted`), whose first transaction is this one and whose second, ordered after it, removes the plan directory; no model ends a plan: a worker's task ends only in its closed task outcomes, and a plan that cannot continue takes its phase's fallback (`returned` or `handed_back`), never `plan.aborted`. The operator *cancels* an epic (`pm-operator abort epic <epic_id> --reason <text>`, or its cancel act) with the choice for its plans, cancelled too or left running detached (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/08-epic-coordination.adoc#epic-actions[Model Work Specification, An Epic's Actions]): the epic takes the archive path in the next transaction (its open tasks withdrawn, then `epic.archive`, the ledger commit, and the epic landing; link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/06-setup-epic-other.adoc#state-epic.archive[State Catalogue Specification, `epic.archive`]) and ends in `epic.aborted` with the `terminal_reason` `cancelled`; a plan left running detached runs to its own outcome, and once the epic is terminal its epic linkage resolves to `detached`, which every consumer treats like `not_orchestrated` (no landing emission to an inbox, late findings seeded as lessons, no outbox link; link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/02-workflow-state-store.adoc#epic-linkage[Store Schemas Specification, Origin and Epic Linkage]). The release of the project ends its epics without this archive path (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#project-release[Releasing Ends Work as the Operator Ends It]). The reason is recorded in the landing record and the audit log.
9. [[operator-grant-access]]*Cross-Project Access (`pm-operator grant-access <plan_id> <project_id> read|read-write --reason <text>`)*: A plan works inside its own enrolled project (`PM-SEC-2`); access to another enrolled project, and the read-only provider reads of an organisation, group, or repository outside the project (`--org <owner>` or `--repo <owner>/<name>`, only with `read`; link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/credentials-and-enrolment/01-provider-credentials.adoc#cross-repository-reads[Cross-Repository Reads & Issues]), is granted only by the operator, in either client, on the operator's own initiative or as the act of the hold that asks for it. The act shows the plan, the target (a project identified by its remote owner and name, never by a checkout path; an organisation, group, or repository by its name at the plan's provider), and the access level before the confirmation; the runtime appends a grant record to the plan's append-only grant log in the plan store (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/15-screening-and-grants.adoc#grant-record[Store Schemas Specification, Grant Record]) and mirrors it to `audit.jsonl`. The grant applies from the plan's next transaction and holds until the plan ends; there is no revocation, and ending the plan (<<operator-abort>>) is the only way to stop it. An access to a project without a grant of the needed level raises `precondition_unmet` on the current state, held for the operator with the grant as its act; its `retry` re-checks the grants within the condition budget (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/timeouts/01-job-budgets-and-waits.adoc#condition-budget[Timeouts & Budgets Specification, Condition Budget]), after which the phase's fallback is taken with the access as the gap. No model-facing link requests a grant.
10. [[operator-enrol-harness]]*Harness Enrolment (`pm-operator enrol-harness <client>`)*: Workers run only through an enrolled harness (`PM-EXEC-1`). The harness step of the machine's onboarding (`harness.enrol`, after the scan, link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/client-profiles/01-profile-schema.adoc#harness-scan[Client Profiles Specification, Harness Scan]) and the verb enrol alike: they resolve the absolute path of the profile's `headless.executable`, run the profile's version probe as a probe job (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/job-runtime/02-confinement-and-environment.adoc#probe-jobs[Job Runtime Specification, Probe Jobs]), and record the path, version, and digest, and nothing else, in the machine's harness enrolment (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/11-enrolment-store.adoc#harness-enrolment-store[Store Schemas Specification, Harness Enrolment Store]); they show the path, version, and digest for confirmation; they refuse a client whose profile has `headless: null` or `worker.eligible: false` (`invalid_arguments`) and a version outside `headless.supported_versions` (`harness_version_unsupported`). `harness.enrol` also records the machine's default harness, `harnesses.default` of `machine-config.json`, a client id of `harnesses.json`; a harness that is the default cannot be removed before another is chosen. Neither captures an environment value: `PM-MCP` never stores or exports a harness's authentication. The harness CLI must already be authenticated by its own login, cached under its home; a worker of a harness that is not logged in fails to start, and the start-failure guard reports the harness's own error text to the operator (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/03-supervision-and-recycling.adoc[Model Work Specification, Supervision & Recycling]). Enrolling is also the re-baseline of a tampered harness enrolment: when the HMAC check of `harnesses.json` fails, every worker launch on that harness is refused before spawn (fate `refused`, reason `harness_tampered`, a `security` audit record `enrolment_tampered`) and counts as a start failure of the role on that harness; once the start-failure guard holds, the role's tasks close `lost` with `role_unavailable` and take their conservative fallback, and both clients offer the harness's enrolment again (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/04-worker-launch.adoc#harness-selection[Model Work Specification, Launch Refusals]). The act rewrites the file and its sidecar with the named client only after showing path, version, and digest; entries of other clients in the tampered file are not carried over, and each of those clients must be enrolled again. There is no pause and no `accept-edit` form for this file. A later change of the digest or version (the harness updates itself) is accepted while the version stays inside the range: in the accepting transaction the runtime rewrites `harnesses.json` and its HMAC sidecar under `locks/harnesses.lock` and appends the audit record `harness_updated`; outside it every worker launch on that harness is refused `harness_version_unsupported` until the operator enrols it again; a version change also invalidates the qualification records of the roles on that harness (`PM-WORK-6`) (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/client-profiles/01-profile-schema.adoc#headless-block[Client Profiles Specification, `headless`]).
11. [[operator-roles]]*Roles (`pm-operator roles`)*: Roles are configuration artifacts in the shipped, machine, and project role sets, and a role's harness, model, and effort are the effective values of its artifact overlaid by the machine's and the project's role assignment and a plan override (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/01-roles-and-configuration.adoc#role-assignment[Model Work Specification, Role Assignment]). The role assignment is written by the roles aspect of the machine's onboarding (`roles.write`, also `pm-operator config roles`) and, for a project, by its onboarding; the operator may still edit the artifacts of the machine or project set. The verbs below read and grade and never write an artifact or an assignment. The qualification semantics (validity, corpus topics, grading, conservative fallback) are in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/01-roles-and-configuration.adoc#qualification[Model Work Specification, Role Qualification].
* `roles list [--project <project_id>]`: every role of the effective set (of the project, or the machine and shipped sets without `--project`) with its source set, class, form, effective harness, model, and effort with the level each comes from, its qualification state (`qualified`, `qualified_fresh_only`, `unqualified` naming the changed input when a record no longer matches or the measurement below the project's current level, or `invalid` with the validation reason; an invalid artifact counts as undefined), and whether the start-failure guard of the role holds (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/03-supervision-and-recycling.adoc#start-failure-guard[Model Work Specification, Start-Failure Guard]). Read-only.
* `roles show <role> [--project <project_id>]`: the effective artifact, the artifacts of lower sets it replaces, the assignments that overlay it, its configuration digest and its qualification digest (over the effective values), its validation result, an effort narrowing the harness applies to it, and the summary of its qualification record. Read-only.
* `roles show --decisions [--project <project_id>]`: the decision declarations of the project's adjudication unit and of the binary's default unit (per decision kind `ask` or the quorum with each listed role's harness, model, availability, and qualification, and the validation result) and the calibration record of every quorum declaration: the items graded, the automatic share, the false automatic share against the declared level, and whether the declaration decides (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/10-decision-quorum.adoc#quorum-calibration[Model Work Specification, Quorum Calibration]). Read-only.
* `roles qualify --decisions [--project <project_id>] [--kind <decision_kind>] [--yes]`: calibrates every quorum declaration that the project's adjudication unit or the binary's default unit uses and that has no valid record, or the declarations of the named kind, on the corpus items of closed decisions of its kind, with the confirmation and progress of `roles qualify`, and has the runtime write one decision calibration record per declaration digest to the project set (identical declarations share one), bound to the corpus revision; it prints the measurements and the paths.
* `roles qualify <role> [--project <project_id>] [--yes]`: shows the configuration, the corpus topics, the item count per form, and the expected tokens and time from earlier records, and runs only after confirmation (`--yes` skips the confirmation, never the terminal check of item 2); it then grades the configuration warm and fresh (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/01-roles-and-configuration.adoc#grading[Model Work Specification, Grading]) and has the runtime write the qualification record to the project set, bound to the qualification digest (over the graded members `PM-WORK-6` names, link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/01-roles-and-configuration.adoc#qualification[Model Work Specification, Role Qualification]) and the corpus revision; its progress is shown like any other jobs in both clients, and it prints the record's measurements, whether they qualify each form at the project's current levels, and the path. While a role is unqualified its tasks take their conservative fallback with the reason `role_unqualified`; no task waits for a qualification. The project's setup runs the same grading for every role without a valid record, after its consent `model_cost` (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/domain-extensions/04-setup-state-machine.adoc#setup-qualification[Domain Extensions Specification, Role Qualification at Install]).
12. [[operator-decisions-export]]*Decision Export (`pm-operator decisions export`)*: Reads the decision records of the project (`--project`, else every enrolled project; live and archived plans, epics, and the workspace scope) and writes the selected judgment decisions as `draft` corpus items, and with `--calibration` the server-rule decisions as calibration rows, into `--out`, a directory the operator names; the selection, the target, the mapping, and the skip reasons are owned by link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/11-decision-records.adoc#corpus-export[Model Work Specification, Corpus Export]. It is read-only on every store, needs no confirmation, never overwrites a file, and sends nothing over the network (`PM-ARCH-2`); the runtime appends one audit record with the counts written and skipped. The items carry real code and facts of the project: the operator reviews them before anything enters the corpus.
