*Proven Write Credential for Upstream Filing*: A credential that an operator-confirmed filing job would use to write to a vendor tracker (the lesson Upstream Release, link:../store-schemas/10-job-and-lesson-records.adoc#lesson-record[Store Schemas Specification, Lesson Record]) is proven by a write-permission probe on the target tracker before the filing job is offered; without a passed probe the release action only renders the issue body for the operator to file.

=== Two-Lane Provider Architecture

External provider integrations are strictly partitioned into two authentication lanes. The provider operations of both lanes are contracts of the provider modules `pm-provider-git` and `pm-provider-ci` and the findings and code-analysis contracts of `pm-core`, implemented by `pm-provider-github`, `pm-provider-gitlab`, `pm-provider-forgejo`, and `pm-provider-sonar` (link:../../Requirements.adoc#PM-IMPL-1[PM-IMPL-1]; Forgejo: link:../module-structure.adoc#forgejo[Module Structure Specification, Codeberg and Forgejo]). For the integrations `git`, `github`, and `gitlab` each contract has two implementations, the *native variant* (in process) and the *CLI variant* (jobs of the enrolled `git`, `gh`, `glab`); `forgejo` and `sonar` have only the native variant. The lane of an integration follows its variant:

1. *System Lane (CLI variant of `git`, `github`, `gitlab`)*: Executed as verified subprocess jobs (`PM-EXEC-5`) that inherit the developer's existing CLI authentication (`~/.gitconfig`, credential helpers, SSH agent, `gh auth`, `glab auth`), by design (<<cli-variant-credentials>>). `PM-MCP` never reads, extracts, or stores CLI-lane tokens and never injects a Token Lane secret into such a job.
2. *Token Lane (SonarQube/SonarCloud, Forgejo, authenticated upstream MCP servers, and the native variant of the git HTTPS transport, GitHub, and GitLab)*: Executed directly by the runtime (`pm-mcpd`) in process: REST and GraphQL through `de.cuioss:cui-http`, git transport through JGit over HTTPS. Tokens are resolved per request by credential key (`PM-CRED-1`) from the credential store the operator chose (<<credential-store-choice>>): `<project>/<credential_key>` (project-scoped override) -> `<credential_key>` (global fallback), and sent only to the origin of the entry's `url` and, for `github` and `gitlab`, the API origin derived from it (<<agent-credentials>>, `PM-CRED-5`). That `url` belongs to the operator-owned credential entry; the team configuration (`.marshall/config/project.json`) may only reference a credential key and never decides where a token is sent. The native variant authenticates with the agent credential, never with the operator's ambient CLI login: for a GitHub App every write acts as the operator via the App (its user access token, <<user-access-token>>) and every read-only query as the App installation (<<agent-credentials>>).

*Variant selection*: The machine records per provider whether it is available, its default variant, and the credential key it uses (`providers` of `machine-config.json`, with the CLI tools enrolled for the machine in `host-tools.json`; link:../store-schemas/12-machine-stores.adoc#provider-defaults[Store Schemas Specification, Machine Provider Defaults]). A project takes them unless its own setup sets them: its onboarding shows the integration variant and the credential of each provider with the machine's value as the proposal, and records a value for the project only when the operator changes it (link:../store-schemas/08-project-configuration-local.adoc#project-levels[Store Schemas Specification, Project Values over Machine Values]; link:../domain-extensions/04-setup-state-machine.adoc#setup-integration-variants[Domain Extensions Specification, Integration Variants]). The CLI variant needs the integration's host tool enrolled for the machine or for the project; where the effective variant cannot serve the repository (the derived fact `git_native_capability`), the choice is an operator wait of the project's setup (link:../workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]), answered in either client, never by a model and never a decision of a plan; no git or provider operation runs before the variant is set. A project's own choice is stored in the operator's `local-config.json` (link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Local Configuration]), never in a team file, because it decides whose credentials act. One integration of a project uses exactly one variant for all its operations; different integrations may differ (for example the CLI variant of `git` with the native variant of `github`). The operator's ambient identity, with all of the operator's rights, therefore acts only where the operator chose the CLI variant with an enrolled tool, an operator act. No operation falls back from one variant to the other, and the variant changes only through an operator act that reports and audits the change. The variant that served an operation, the credential key and origin, and for the CLI variant `identity: operator_ambient` are written to the operation's audit record, never into a model-facing result (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).

=== Agent Credentials of the Native Variant
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-7[PM-WATCH-CLI-7]_

* *No refusal by credential kind*: Every listed credential kind is accepted on equal footing; neither the kind nor a missing expiry is refused or warned about in a workflow. Entering and verifying a credential determine the token kind from the provider and record it with the entry (<<operator-credential-cli>>).
* *Check visibility*: A credential that cannot read check runs (a GitHub fine-grained personal access token cannot call the Checks API) is detected up front by the derived network fact `checks_visible` (link:../store-schemas/09-derived-facts-and-build-timings.adoc#derived-facts[Store Schemas Specification, Derived Facts]); `ci.checks` then reads what the credential can see (commit statuses, check suites) and reports `completeness: incomplete`, which never counts as a green check.
* *Installation tokens*: For a `github_app` entry the runtime signs an RS256 JWT with the JDK (`iat` back-dated and `exp` bounded by the GitHub App JWT validity window, link:../timeouts/03-retention-host-config.adoc#github-app-jwt-window[Timeouts & Budgets Specification]; `iss` the `client_id`) and mints an installation token for the read-only query classes, narrowed to the one repository (or, for a granted cross-repository read, to the granted repositories, <<cross-repository-reads>>) and to the read-only permission set of the operation class, through `POST /app/installations/{id}/access_tokens`; every write operation uses the user access token instead (<<user-access-token>>). The App needs at most the repository permissions `contents: write`, `pull_requests: write`, `checks: read`, `actions: read`, `statuses: read`, `issues: write`, and `metadata: read`; a comment on a pull request needs `pull_requests: write` (`issues: write` alone is refused for it), and `issues: write` serves issue comments only. Administrative permissions are never required, because repository administration (such as enabling a merge queue) stays with the operator.
* [[user-access-token]]*User access token (writes)*: A `github_app` entry also holds a user refresh token of the App, obtained once by the device flow when the operator enters the credential (<<operator-credential-cli>>; the App must have the device flow enabled). Every write operation (push, pull-request creation and edit, comments and review replies, review triggers, thread resolution, merge and merge-queue enqueue, branch delete) runs with the user access token, which acts as the operator via the App (shown by the provider as the operator's login "via" the App) with the intersection of the App's and the operator's permissions; so the pull requests and review triggers the server writes are user-authored, which review bots that skip bot-authored pull requests and bot triggers require (link:../phase-workflows/05-finalize-review-metrics-descriptor.adoc#automatic-review[Phase Workflows Specification, Automatic Review]). The access token (valid 8 hours) is held in memory only, like an installation token (<<derived-tokens>>). Before it expires (link:../timeouts/03-retention-host-config.adoc#user-token-refresh-margin[Timeouts & Budgets Specification, User token refresh margin]) the runtime refreshes it with the refresh token and the `client_id`, without a client secret; the provider rotates both tokens on every refresh, revokes the old access token at once, and accepts each refresh token (valid about six months) once. The refresh is therefore atomic under `<PM_MCP_BASE>/locks/credentials.lock`: one refresh at a time per entry; the new refresh token is written to the recorded store and read back before the new access token is used, and every in-memory holder switches to the new access token in the same step. A refresh whose answer is lost, or a refused or expired refresh token, makes the entry `credential_check_failed`, held for the operator with the act that enters the credential again (a new device flow; link:../state-catalogue/01-conventions-generic-conditions.adoc#holds[State Catalogue Specification, Holds and Their Acts]); there is no fallback to the installation token for a write. A personal access token credential (GitHub, GitLab, or Forgejo) authors as its own user and needs none of this. _Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-30[PM-WATCH-CLI-30], link:../../implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-105[PM-WATCH-PHASE-105]_
* *Committer identity*: The committer of agent commits is the identity resolved from the agent credential through `ci.whoami` (a GitHub App: `<app-slug>[bot]` with the address `<id>+<app-slug>[bot]@users.noreply.github.com`; a token: the token's user), recorded as the operator-only derived fact `agent_identity`; without a Token Lane provider credential the committer is the fixed `plan-marshall-mcp` noreply identity. The author stays the operator (`commit_identity`, link:../store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas Specification, Local Configuration], proposed from the machine's `project_defaults.commit_identity` where set, else the global git identity). The identity appears in the operator's clients and the audit log, never in a model-facing representation.

[#derived-tokens]
=== Short-Lived Derived Tokens
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-2[PM-WATCH-CLI-2], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-5[PM-WATCH-CLI-5]_

A stored secret is read per request and never cached (`PM-CRED-5`). A token derived from it that expires by construction, a GitHub App installation token (valid one hour) or a GitHub App user access token (valid 8 hours, <<user-access-token>>), is the second named exception of `PM-CRED-5`:

* It is held in memory only, an installation token keyed by installation and permission set and reused until the derived token reuse margin before its expiry (link:../timeouts/03-retention-host-config.adoc#derived-token-reuse-margin[Timeouts & Budgets Specification]), then a new one is minted; a user access token keyed by its credential entry and refreshed at the user token refresh margin (link:../timeouts/03-retention-host-config.adoc#user-token-refresh-margin[Timeouts & Budgets Specification]). The user refresh token is the stored secret of that derivation: it is read only for a refresh and replaced in the store by its successor in the same refresh.
* It is registered with the redaction registry when minted (<<operator-credential-cli>>).
* It is never persisted, never exported to a subprocess environment or log, and never passed to the CLI variant.
* It is dropped when its credential entry is rotated, removed, or re-set, when a request with it fails with `auth_failed` (revocation), and when the runtime stops; a user access token is also replaced at once by its successor when it is refreshed.

[#cross-repository-reads]
=== Cross-Repository Reads & Issues
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-31[PM-WATCH-CLI-31]_

The CI provider contract (`pm-provider-ci`) has four read operations beyond the project's own repository, served by both variants and in the `ci` query operation class (link:../timeouts/01-job-budgets-and-waits.adoc#ci-query-budget[Timeouts & Budgets Specification]):

* `ci.org-repos`: the repositories of an organisation (GitHub, Forgejo) or group (GitLab);
* `ci.code-search`: a code search restricted to an organisation or group;
* `ci.repo-file`: one file of a repository outside the project, at a named ref;
* `ci.labels`: the label list of a repository.

Two issue operations serve the issue source of a start (link:../state-catalogue/09-bootstrap-and-lessons.adoc#issues[State Catalogue Specification, Issues by Number or URL]): `ci.issue-view` reads one issue by its URL (title and body as text, labels, milestone, assignees, state, and URL as structured fields), of the project's own repository or of another repository; `ci.issue-comment` posts a comment to an issue of the project's own repository only, and only while the team key `issues.write_back` enables it (link:../store-schemas/07-project-configuration.adoc[Store Schemas Specification, Project Configuration]).

Each read outside the project's own repository runs only under an operator grant that names its target: for a plan `pm-operator grant-access <plan_id> --org <owner> read` or `--repo <owner>/<name> read` (<<operator-grant-access>>), and for an issue named at a start the grant the source state asks for, once (for this start and the plan it creates) or for the project (every later read of that repository by the project's plans, until the operator withdraws it in the project's settings); `ci.labels` of the project's own repository needs none, and a public issue of another forge is read without a credential, every other with the credential of that forge. Without the grant the operation is refused with `grant_missing`: in a plan's step as the `precondition_unmet` condition, held for the operator with the grant as its act (link:../state-catalogue/01-conventions-generic-conditions.adoc#holds[State Catalogue Specification, Holds and Their Acts]), like every cross-project access (`PM-SEC-2`). In the native variant a GitHub App reads with an installation token narrowed to `metadata: read` and `contents: read` on the granted repositories; a repository outside the App's installation is not visible to it. Every result carries `completeness`: `complete`, or `incomplete` with the bounds that cut it (`page_cap`, the server's compiled page bound; `provider_result_cap`, for example the provider's cap on search results or its `incomplete_results` flag; `not_visible`, repositories the credential cannot see, where the provider reports them). An `incomplete` result is never read as "absent": a consumer that needs the whole population treats it as unknown. A read that the forge refuses for its rate limit fails with the cause `rate_limited` and the instant the limit resets (`resets_at`, from the forge's answer) and is not retried by itself. File contents, issue texts, and search excerpts are external text and pass the level-1 validator before they reach a model (`PM-SEC-1`).

[#native-confinement]
=== Native Operation Confinement
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-6[PM-WATCH-CLI-6], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-9[PM-WATCH-CLI-9], link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-28[PM-WATCH-EXT-28]_

A native operation runs inside the runtime process: it has no argument vector, no environment, and no Landlock ruleset. What it can do is bounded by the following rules, each enforced in the provider modules:

* *Paths*: It writes only inside the enrolled project root and its linked worktrees; every path it derives, including the `gitdir` targets of worktree administration files, passes the `PM-SEC-2` checks.
* *Origin check*: HTTP requests go through `cui-http` with origin pinning. The git transport resolves the effective fetch and push URL of the remote with every `url.<base>.insteadOf`/`pushInsteadOf` rewrite and `remote.<name>.pushurl`, maps an SSH remote of a known provider host (`github.com`, `gitlab.com`, `codeberg.org`, and hosts whose `ci_provider` is established) to its HTTPS form without changing the configured remote, and requires `https` and an origin equal to the credential entry's origin. A mismatch refuses the operation with `remote_origin_mismatch`, appends a `security` record to `audit.jsonl`, and sends nothing; every other SSH remote is `capability_missing{reason: ssh_only_remote}`. Its connection factory refuses every other host, so a redirect cannot carry the credential elsewhere.
* *Configuration allowlist*: From the repository configuration and the user's global configuration it reads only content-shaping keys: `core.autocrlf`, `core.eol`, `core.safecrlf`, `core.excludesFile`, `core.ignoreCase`, `core.precomposeUnicode`, `remote.<name>.url|pushurl|fetch`, `url.<base>.insteadOf|pushInsteadOf`, `branch.<name>.*`, `init.defaultBranch`, and, for capability detection only, `core.hooksPath`, `filter.<driver>.*`, `lfs.*`, `submodule.*`, and `extensions.*`. Every other key is ignored, among them `credential.*`, `core.sshCommand`, `core.fsmonitor`, `http.*` proxy settings, and `include.*`/`includeIf.*` targets outside the repository. A proxy is an operator setting, never a repository value or an environment variable: the closed object `proxy` of `machine-config.json` (`https_proxy`, a URL without embedded credentials, and `no_proxy`, a list of hosts; link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas Specification, Machine Configuration Store]), set as an operator configuration value and applied to every `cui-http` call and to the JGit transport of the native variant. Authenticated proxies are deferred (link:../../later-improvements.adoc#_l_8_authenticated_proxies[Later Improvements, L-8]).
* *No process execution*: A native operation never starts a process. JGit's process entry points (`FS.runInShell`, `FS.runHookIfPresent`, filter-driver execution) are served by a `pm-provider-git` subclass of JGit's `FS` that refuses with `capability_missing` instead of running anything, so no repository value can start a process in the runtime.
* *Selection criterion instead of fallback*: Repository hooks (non-sample files in `.git/hooks/`, `core.hooksPath`, `.husky/`, `lefthook.yml`, `.pre-commit-config.yaml`), required commit signing (`signed_commits_required`), filter drivers including LFS, submodules, SHA-256 object format, partial clone, sparse checkout, split index, and SSH-only remotes are detected by the derived fact `git_native_capability` (link:../store-schemas/09-derived-facts-and-build-timings.adoc#derived-facts[Store Schemas Specification, Derived Facts]). An operation that needs a missing capability is refused with `capability_missing{reason}` naming the feature and the operator act that enrols the integration's host tool and selects the CLI variant; no operation falls back on its own. A new capability finding invalidates an effective native variant, and the project's setup requires the operator's act for that integration.

[#cli-variant-credentials]
=== Credentials of the CLI Variant
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-8[PM-WATCH-CLI-8]_

The CLI variant runs the operator's enrolled `git`, `gh`, or `glab` with the operator's ambient authentication, by design: it is the variant of a project whose operator chose it with an enrolled tool, it needs no credential held by `PM-MCP`, and it serves the operator's own setup (signing, SSH remotes, hooks, special hosts).

* *Operator choice, audited*: The choice of the integration variant (link:../domain-extensions/04-setup-state-machine.adoc#setup-integration-variants[Domain Extensions Specification, Integration Variants]) shows on selection that the CLI variant of that integration acts with the operator's identity; every CLI job's audit record carries `identity: operator_ambient`.
* *No token injection*: An agent token is never passed to a CLI job, neither as `GH_TOKEN`, `GITHUB_TOKEN`, `GITLAB_TOKEN`, or another token variable, nor through a `GIT_ASKPASS` or `SSH_ASKPASS` helper, nor through a credential helper served by `PM-MCP`: every descendant of the job, including repository hooks, and every same-user process reading `/proc/<pid>/environ` could read it, which breaks `PM-CRED-5`.
* *Environment, write paths, `stdin`*: The job environment rows of CLI-variant `git` and `ci` jobs (configuration discovery, SSH agent socket, provider CLI configuration directories, non-interactive guards, committer variables), their additional write paths, and their `stdin` forms are specified in link:../job-runtime.adoc[Job Runtime Specification] (Job Environment; In-Memory `stdin` Streaming). `known_hosts` stays read-only: an unknown host key fails the job, it is never accepted.
* *Hooks and signing*: Repository hooks and signing programs run only here, started by `git` itself inside the CLI `git` job and therefore under that job's environment and Landlock confinement (`PM-SEC-5`).
* *No session bus*: A job never reaches the user's session bus (link:../job-runtime/02-confinement-and-environment.adoc#session-bus[Job Runtime Specification, Session Bus]), so on Linux a CLI job cannot use a login kept only in the Secret Service (the `libsecret` git credential helper, the keyring storage of `gh` or `glab`). The verification command of the integration (`gh auth status`, `glab auth status`, `git ls-remote`) then fails as a job, and the setup names the cause; the operator keeps that login in the tool's own file storage or an SSH agent, or selects the native variant.

[#os-keyring-backends]
=== Credential Stores
_See Requirement link:../../Requirements.adoc#PM-CRED-3[PM-CRED-3: Permission-Guarded File Credential Store]_

The `CredentialStore` service uses exactly one store per machine, the one the operator recorded (<<credential-store-choice>>); a secret never exists in two stores, and within the store the project entry `<project>/<credential_key>` is resolved before the global entry `<credential_key>` (`PM-CRED-2`). `<project>` is the project's enrolment identifier (`PM-CRED-3`), never derived from a remote URL or a checkout path. [[keyring-service-name]]Every keyring entry of `PM-MCP`, Token Lane credentials and the enrolment integrity key alike, is stored under one *service name* (`PM-CRED-2`): `de.planmarshall.mcp` for the default `PM_MCP_BASE`, and `de.planmarshall.mcp/<instance_hash>` for any other, where `<instance_hash>` is the first 16 hex characters of the SHA-256 of the canonical absolute path of `<PM_MCP_BASE>` (`PM-DIST-5`), so two instances never share an entry. The stores are:

* *macOS Keychain (`os` on macOS)*: Invokes macOS Security framework APIs (`SecItemAdd`, `SecItemCopyMatching`, `SecItemUpdate`, `SecItemDelete`) directly via Java 25's Foreign Function & Memory (FFM) API (`java.lang.foreign.Linker`). Items are stored under the <<keyring-service-name,service name>> with account `<credential_key>` or `<project>/<credential_key>` and a trusted-application ACL restricting unprompted read access to the runtime binary `pm-mcpd`, the only process that reads or writes credentials (neither CLI binary touches the credential store); another reader raises the OS access dialog. The ACL identifies the binary by its code signature: `pm-mcpd` of a macOS release is signed with a Developer ID and notarised in the macOS release job, so the ACL holds the designated requirement of that signature (the team identifier) and an upgraded `pm-mcpd` reads the items of its predecessor without a prompt. A locally built `pm-mcpd` is ad-hoc signed and trusted by its code-directory hash, so every rebuild loses unprompted access to the items the previous build stored (the OS asks once per item). The items live in the login keychain; the data-protection keychain refuses a binary without an entitlement and is not used.
* *Linux Secret Service (`os` on Linux)*: Communicates with `org.freedesktop.secrets` over the user session D-Bus (`gnome-keyring` / `KWallet`) storing attributes `service=<service name>` (<<keyring-service-name>>), `credential_key=<credential_key>`, and optional `project=<project>`. It is available while the session bus is reachable and the default collection is unlocked; a locked collection is never prompted for. The Secret Service has no per-application access control: every process of the user that reaches the session bus can read an unlocked collection. Jobs therefore never reach the session bus (link:../job-runtime/02-confinement-and-environment.adoc#session-bus[Job Runtime Specification, Session Bus]); an unconfined process of the user, such as a coding agent the operator runs, can, which is an accepted residual risk (`PM-SEC-5`).
* *Permission-Guarded File Store (`file`)*: Secrets are stored in the `PM-MCP` credential file format (`format_version`, closed schema, written only by the runtime on the operator's entry of a secret, a store move, or the token refresh of a `github_app` entry, `PM-CRED-3`) at `<PM_MCP_BASE>/credentials/<credential_key>.json` and `<PM_MCP_BASE>/credentials/<project>/<credential_key>.json` (directory mode `0700`, file mode `0600`, see link:../filesystem-layout.adoc[Filesystem Layout Specification] and link:../store-schemas.adoc[Store Schemas Specification]).

*A credential a step cannot use*: If the recorded store is unavailable (`credential_store_unavailable`), if ownership or permission checks on a credential file fail (`credentials_file_insecure`), if the credential is missing (`credential_missing`), if a credential file was not written by the runtime in the current format (`credentials_file_invalid`), or if a resolved credential's check against its provider fails (the step's provider call, or `ci.whoami` where the step verifies the identity, answers that the credential is rejected, revoked, or lacks a required permission: `credential_check_failed`), the runtime holds only the step that needs that credential: the engine raises the `precondition_unmet` condition on the step's current state with `facts.reason` set to the cause, held for the operator as a hold whose acts set, replace, or move the credential (link:../state-catalogue/01-conventions-generic-conditions.adoc#holds[State Catalogue Specification, Holds and Their Acts]; `PM-CRED-4`); its `retry` re-checks within the condition budget (link:../timeouts/01-job-budgets-and-waits.adoc#condition-budget[Timeouts & Budgets Specification, Condition Budget]), after which the phase's fallback is taken with the credential as the gap. The runtime itself keeps running; it exits with code `77` only for the causes of step 3 of the startup sequence (link:../runtime-model/02-startup-recovery-drain.adoc#_startup_sequence[Runtime & Interaction Model Specification, Startup Sequence]).

* *No Legacy Credential Access*: The `CredentialStore` never reads `plan-marshall` credentials (its keyring entries, `~/.plan-marshall/credentials/`, `PLAN_MARSHALL_CREDENTIALS_DIR`, `PLAN_MARSHALL_HOME`), and no act imports them (`PM-MIG-2`). Credentials enter the `PM-MCP` stores only through the operator's entry of a secret (<<operator-credential-cli>>), each entry operator-owned, including its allowed `url`.

[#credential-store-choice]
=== Credential Store as an Operator Choice
_See Requirement link:../../Requirements.adoc#PM-CRED-2[PM-CRED-2: Operator-Chosen Credential Store & Native Access]_

_See Requirement link:../../Requirements.adoc#PM-CRED-3[PM-CRED-3: Permission-Guarded File Credential Store]_

The operator chooses once for the machine which store holds the Token Lane secrets (link:../../use-cases/01-onboarding.adoc#UC-ONB-7[UC-ONB-7]); the runtime never chooses one by itself:

* *The setting*: `credentials.store` of `machine-config.json` (`os` or `file`; link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas Specification, Machine Configuration Store]) is written only by the credential-store aspect of the machine's onboarding, in its first or a later run, and by the store move (below). It is aspect-owned: the plain configuration endpoint refuses it (`aspect_owned`, xref:01-cli-and-installer.adoc#two-channels[Operator Choices in the Web App and the Terminal]). Before it is recorded, no credential can be entered: the entry is refused with `onboarding_incomplete`, naming the store step.
* *What each store protects against*: The choice shows it: the macOS Keychain lets only `pm-mcpd` read without a prompt; the Linux Secret Service lets every process of the user read an unlocked collection; the file store lets every process of the user read its files (`0600`). The residual risks of `PM-SEC-5` stay as they are. Before the OS store is recorded, the runtime checks it on the consent `check_credential_store` (link:../store-schemas/12-machine-stores.adoc#consent[Store Schemas Specification, Consent Before Acting]): it writes, reads back, and deletes one test entry, each reported as a check line.
* *The integrity key before the choice*: The harness enrolment and the audit head need the enrolment integrity key before the store is chosen, so until `credentials.store` is recorded the key is created where the runtime finds a store: in the OS store where one is available, else in the key file under `<PM_MCP_BASE>/state/` (link:../../concepts/enrolment.adoc#integrity[Concepts § Enrolment, Integrity]). The choice moves it like every other entry (below); nothing is re-signed.
* *One store, never another*: The runtime uses the recorded store and no other. When the recorded OS store is unavailable at start or later (a locked collection, a session without the user's session bus), the credentials are unavailable: both clients report it with the cause, a step that needs a credential is held with `credential_store_unavailable` (<<os-keyring-backends>>), and a request that writes an entry is refused (`credential_store_locked`, `423`); nothing is written to the file store in its place.
* [[credential-store-move]]*The move*: Changing the store is a move of every entry in either direction (OS to files and files to OS), an operator act of the credential-store aspect or of `pm-operator credentials migrate os|file`. The runtime records the move in the machine state records (from, to, started; link:../store-schemas/12-machine-stores.adoc#machine-state-records[Store Schemas Specification, Machine State Records]), then copies every Token Lane entry into the target store and reads each back, copies the enrolment integrity key last and verifies every HMAC sidecar (enrolment files, `harnesses.json`, `logs/audit.head`) under it in the target store, switches `credentials.store` in one write, deletes every entry from the old store, and ends the record. A failed copy or read-back before the switch ends the move with nothing switched and the copies deleted from the target (`credential_store_failed`). A move cut by a stop is resumed after the next start from its record: before the switch it starts again from the first entry, after the switch it finishes the deletion. The move is audited, and the runtime reads no store but the recorded one while it runs.

[#provider-verification]
=== Provider Verification
_See Requirement link:../../Requirements.adoc#PM-CRED-1[PM-CRED-1: Dual-Lane Credential Separation (System vs Token Lane)]_

A provider is verified as a whole when the operator configures it for the machine and again on the operator's request (link:../../use-cases/01-onboarding.adoc#UC-ONB-8[UC-ONB-8]):

* *The checks*: The providers aspect of the machine's onboarding runs, per selected provider and on the consent `verify_providers`, the checks of its kind, each reported as a check line: the origin is reachable; the credential authenticates (`ci.whoami`) and as whom; its permissions and its expiry; for the CLI variant the tool's version and that it is logged in as the same identity as the credential. A check line carries the check's name, `ok` or `failed`, a message key with its arguments, and the provider's or the tool's own answer verbatim where there is one.
* *A failed provider*: A provider whose checks fail is recorded only on the operator's word, and then as not available; it never serves a project in that state.
* *Again later*: The same verification runs from the machine settings on request (`pm-operator config providers --verify`) and after a credential is rotated or replaced there; it changes nothing unless a check fails. Its last result with its time is kept with the machine's provider defaults (link:../store-schemas/12-machine-stores.adoc#provider-defaults[Store Schemas Specification, Machine Provider Defaults]) and shown with each provider in both clients. Checks that need a repository (the permissions on it, check runs visible) stay in the project's setup (link:../domain-extensions/04-setup-state-machine.adoc#setup-verify-credentials[Domain Extensions Specification, Credential Verification]).
* `pm-operator credentials verify <credential_key>` checks one credential alone and records nothing of the provider (<<operator-credential-cli>>).

[#operator-credential-cli]
=== Operator Credential Acts & Runtime Secret Redaction
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-28[PM-WATCH-CLI-28]_

* *Entering a secret*: Credential mutations and verifications are operator acts of the operator's two clients, executed by the runtime through its local API (`PUT /api/v1/credentials/{credential_key}`, link:../runtime-model/01-processes-and-transport.adoc#api-no-secret-read[Runtime & Interaction Model Specification, Local API, Credential entries]):
** *The terminal client*: `pm-operator credentials set|status|verify|remove|rotate <credential_key> [--project]` and `pm-operator credentials migrate os|file` (operator verbs, <<operator-channel-isolation>>), and the credential states of the onboarding in its console. `set` and `rotate` always read the secret from the terminal with echo disabled into a `char[]`, never into a `String` (`System.console().readPassword()` for a verb run as one shell command; in the console, character by character from the terminal of its line editor, never through the line reader, whose result is a `String` and whose history must not see it), together with the non-secret fields (`url`, `auth_type`, header settings; for `github_app` the `client_id` and optional `installation_id`, the PKCS#1 or PKCS#8 `private_key` being read as a secret), and send them in the body of one request over the Unix domain socket; `pm-operator` keeps the secret only in a `char[]` that it clears after the request and never writes it anywhere.
** [[web-credential-form]]*The web app*: the credential form of a paired device on the loopback listener sends the secret in the body of one request straight to the credential store; the app keeps no copy and never shows it again (xref:03-web-server.adoc#web-credentials[Credentials in the Web App]). A request that arrives on the LAN listener is refused (`loopback_only`, `403`), and the form names the terminal command instead.
+
A credential the operator enters is stored on that act and needs no consent. The runtime writes the entry into the recorded store; for the file store it writes the complete credential file in the `PM-MCP` format (`format_version`, closed schema, link:../store-schemas/12-machine-stores.adoc#credential-store[Store Schemas Specification, Credential Store]) atomically with mode `0600`, under `<PM_MCP_BASE>/locks/credentials.lock`. For a `github_app` entry, `set` (and `rotate`) then runs the GitHub device flow: the runtime requests a device code for the `client_id` on the entry's `url` origin, the client shows the verification URL and the user code, the operator authorizes the App in the browser, and the runtime polls at the interval the provider names until it receives the user tokens or the code expires (the act then fails and writes nothing); it stores the refresh token with its expiry (`expires_at`) in the entry and never shows either token. The runtime is the only writer of credential files, on an operator act, a store move, and, for the rotated refresh token of a `github_app` entry, in its token refresh (<<user-access-token>>): no placeholder file and no hand-edited file exists, and a file it did not write in the current format is refused (`credentials_file_invalid`). Secrets are never accepted from command-line arguments or environment variables.
* *Identity, Kind & Expiry*: For `github`, `gitlab`, and `forgejo` entries, setting and verifying call `ci.whoami` and record the token kind (`token_kind`) and, where the provider reports one, the expiry (`expires_at`; an operator-entered expiry otherwise); `verify` shows the resolved identity, its permissions on the enrolled repository, and whether it can read check runs (`checks_visible`), without revealing the secret. `status` reports per entry one of `present` (stored, not yet verified), `not_found`, `verified`, `unverified`, the serving store, plus `expiring` when `expires_at` lies within the credential expiry warning window (link:../timeouts/02-runtime-leases-operator-web.adoc#credential-expiring-window[Timeouts & Budgets Specification]), and names an entry without a known expiry; neither is a refusal, and neither reaches a model-facing representation, since an expiring credential still works. No act shows a stored secret, and the runtime's API has no endpoint that returns one: `status` and `verify` read the entry inside the runtime and receive only its status and store (link:../runtime-model/01-processes-and-transport.adoc#api-no-secret-read[Runtime & Interaction Model Specification, Local API, Credential entries]). `rotate <credential_key>` replaces the secret of an existing entry, keeps its non-secret fields, and drops every token derived from the old secret (<<derived-tokens>>); replacing a stored secret is always an operator act, and the only automatic replacement is the refresh-token rotation of the user access token (<<user-access-token>>). For `gitlab`, `ci.whoami` reads `GET /personal_access_tokens/self`; for a token that endpoint refuses because it is no personal access token (an OAuth token, `400`), it falls back to `GET /user` for the identity and records `token_kind: gitlab_oauth_token`; GitLab reports neither scopes nor an expiry for such a token there, so its scopes stay unknown and its expiry is the operator-entered one or unknown. `migrate os|file` is the store move (<<credential-store-move>>); a failed write or read-back reports `credential_store_failed` (link:../runtime-model/01-processes-and-transport.adoc#api-error-codes[Runtime & Interaction Model Specification, Local API Error Codes]).
* *Zero Model Exposure & Redaction*: No MCP tool, resource, or state representation exposes credential values (`status` reports only metadata: provider name, scope, store, and configured status). Every secret value resolved for a request, and every value derived from one (a GitHub App JWT and installation token, <<derived-tokens>>; the `user:token` form of a git transport credential), is added to the in-memory redaction registry of the `SecretRedactor` filter, which keeps it for the runtime's lifetime solely to scrub matching byte/character sequences to `[REDACTED]` across tool results, representations, log records, activity journals, `audit.jsonl` entries, and error messages. The registry is never persisted and never exported to subprocess environments or logs; it is discarded when the runtime stops (`PM-CRED-5`).
* *Runtime Secrets*: The local-trust and web secrets are redacted the same way (`PM-SEC-6`): the runtime token (link:../runtime-model/01-processes-and-transport.adoc#runtime-token[Runtime & Interaction Model Specification, Runtime Token]) is registered by value when the runtime writes it and by `pm-operator` when it reads it; a worker's job token (link:../identifiers/02-registry-stores-to-web.adoc#id-job-token[Identifier Registry, Job Token]) is registered by value when the runtime mints it and is also scrubbed by its `pmj_` shape, because only its SHA-256 survives a runtime restart; device secrets (`pmw_` values) and pairing codes are scrubbed by their shape (link:../identifiers/02-registry-stores-to-web.adoc#id-device-secret[Identifier Registry, device secret]; link:../identifiers/02-registry-stores-to-web.adoc#id-pairing-code[Identifier Registry, pairing code]), because the runtime keeps only their SHA-256 hashes. None of them is written to a log, an audit record, a command-line argument, a process environment (the job token's relay environment excepted), or a representation; request headers are never logged (xref:03-web-server.adoc#web-proxy[API Access & Device Secret]). A pairing code reaches only the terminal client that asked for it, printed to the operator's terminal and never logged. No runtime secret other than a worker's own job token (in its relay's environment `PM_MCP_JOB_TOKEN`) is ever passed to a job: the runtime token file lies outside every job's Landlock read set (link:../job-runtime/02-confinement-and-environment.adoc#_linux_filesystem_confinement_landlock[Job Runtime Specification]).

The machine settings also list the remembered consents, each withdrawn by an operator act of either client (link:../store-schemas/12-machine-stores.adoc#consent[Store Schemas Specification, Consent Before Acting]); every grant and withdrawal is audited.

1. *Operator Channels*: Every operator act takes one of the two channels of the operator's clients: `cli`, the terminal client `pm-operator` (a verb, the console, the `pm-operator web ...` verbs included), or `web`, a paired web device (xref:03-web-server.adoc#web-operator-channel[Every Paired Device Is an Operator Channel]), which has operator rights because only an operator verb can pair it. The answers of operator waits (link:../workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]) are content answers of the channels `cli` and `web`: a decision of a plan or an epic, a consent, and every choice of an onboarding, a setup, or a start are answered in either client through the same endpoints, the first valid answer winning (link:../store-schemas/14-plan-instance-waivers-questions.adoc#cli-answers[Store Schemas Specification, Answers from the Terminal Client]). The overrides (`waive`, `unwaive`, `decline`, the ends of a plan or an epic, `delete-plan`, `grant-access`, the integrity resolutions, operator configuration) are the operator's own acts in the same two channels. None of them routes through the model, and MCP elicitation carries no operator act; every act is audited with its channel (`cli`, or `web` with the `device_id`). An override is never taken as a content answer, and a content answer is never an override; an act relayed by the model (for example a "waive" typed into a harness's chat) is never accepted. Beside the answers, the operator acts on a running plan by waivers, access grants, pausing and starting it, ending it, `delete-plan`, the acts of a hold, and the plan's own settings, each on the operator's own initiative.
2. *CLI Operator Checks*: Before it sends an operator act, `pm-operator` verifies that it is attached to an interactive terminal (`System.console() != null && System.console().isTerminal()`) and that none of the coding-agent environment signals of the link:../client-profiles/02-placeholders-and-detection.adoc#host-integration-table[Host Integration Table] (primary and secondary) is present; either failure refuses the verb with a diagnostic naming the detected host before any request is sent (exit code `4`). The console runs the checks when it opens. Every act that cannot be undone then asks for interactive confirmation of the displayed change; a read-only verb (for example `waivers`, `roles list|show`, `audit verify`, or `sweep` without `--apply`) needs only these terminal and environment checks. The host deny rule installed with the bundles denies the whole binary `pm-operator` to the model (`Bash(pm-operator:*)`, no sub-command rule; `pm-mcp serve --job` stays allowed; link:../client-profiles.adoc[Client Profiles Specification]) and is defence in depth against a model shell. There is no passphrase, no operator session, and no operator credential or passphrase in the credential store (its only operator-lane entry is the enrolment integrity key, link:../../concepts/enrolment.adoc#integrity[Concepts § Enrolment, Integrity]): the operator proof of the first iteration is these checks alone.
3. *Accepted Risk*: The checks guard against accidental and naive invocation, not against a model shell that deliberately defeats them (a pseudo-terminal, a cleared environment, indirect invocation). The runtime cannot verify the checks of `pm-operator`, so any process of the same OS user that holds the runtime token can call the operator endpoints directly (for example with `curl --unix-socket`). This is accepted for the first iteration and documented as a residual risk (`PM-SEC-3`); a user proof the model cannot produce (an operator passphrase session, OS user presence) and device roles with step-up are deferred (link:../../later-improvements.adoc#_l_1_operator_proof_beyond_the_cli_checks[Later Improvements, L-1]). Every operator act stays recorded in the audit log (`PM-SEC-6`).
4. [[operator-integrity-pause]]*Integrity Pause*: The `integrity_breach` condition (a tampered plan, epic, or workspace store, a tampered pending entry record, or a tampered enrolment file, which pauses every running plan of the project; link:../store-schemas/13-leases-integrity-testing.adoc#store-digest-verification[Store Schemas Specification, Store Digest Verification]) holds its scope as a hold of kind `integrity_pause` (link:../state-catalogue/01-conventions-generic-conditions.adoc#holds[State Catalogue Specification, Holds and Their Acts]). The state and `call_stack` stay unchanged, the model-facing representation offers no link, no task of the scope is offered, and every `pm_do` is rejected with `integrity_paused`. The hold shows the tampered file with its recorded and current size and SHA-256; it restores nothing and shows no diff, because the prior content is not kept. Its acts are closed: *accept* (`accept-edit`, <<operator-accept-edit>>; the engine re-verifies before it clears the condition) and *cancel*, whose resolution is the integrity abort: a plan ends with the outcome `aborted`, an epic with the `terminal_reason` `cancelled` (<<operator-abort>>); the workspace scope has no cancel, so `accept-edit workspace <store>` is its only resolution. A tampered pending entry record holds only its entry, never the workspace scope's own state or its other entries, and ends by accepting the edit or by abandoning the entry. The hold has no time bound and no fallback, because a tampered store cannot be trusted to write a hand-back. A tampered harness enrolment (`harnesses.json`) is no pause: it refuses the worker launch (`harness_tampered`), which counts as a start failure of the role on that harness and ends, once the start-failure guard holds, in the conservative fallback of the role's tasks (<<operator-enrol-harness>>). Every other condition is bounded by its self-remedy budget and ends in the phase's fallback (link:../timeouts/01-job-budgets-and-waits.adoc#condition-budget[Timeouts & Budgets Specification, Condition Budget]); one that needs the operator meanwhile is shown as a hold with its acts.
5. [[operator-drop-capture]]*Capture Ref Removal (`pm-operator drop-capture <plan_id>`)*: A `land` plan that ended without `merged` keeps its capture ref `refs/pm-mcp/captures/<plan_id>` in the enrolled repository as the user's recovery point and owes `capture_ref_retained` (link:../phase-workflows/02-planning-lanes-phases-3-4.adoc#land-lane[Phase Workflows Specification, Land Lane, item 5]). The act shows the ref's snapshot commit and its paths, deletes the ref after confirmation, discharges the owed item `capture_ref_retained` (also for an archived plan), and appends an `audit.jsonl` record. `drop-capture` and `discharge-owed` (which records `discharge_proof` and `discharged_at` of an owed item whose discharger is `operator`, link:../store-schemas/03-findings-and-review-records.adoc#owed-item-record[Store Schemas Specification, Owed Item Record]) are the only writes an archived plan accepts. It is operator-only like every act of this section; no workflow state, recovery sweep, or MCP tool removes a retained capture ref.
6. [[operator-waive]]*Waivers (`pm-operator waive`, `decline`, `unwaive`, `waivers`)*: `waive <plan_id> <gate> --reason <text> [--reason-class <class>]` declares a waivable gate met (`review_evidence[:<bot_kind>]`, `ci_check:<name>`, `analysis_gate:<provider>`, `findings:<class>`, `qgate_findings:<phase>`, link:../identifiers/02-registry-stores-to-web.adoc#id-waivable-gate[Identifier Registry, Waivable Gate Identifier]); `waive <plan_id> --raise <budget>=<N> --reason <text>` sets the absolute ceiling of `fix_budget:<policy>` or `retry_budget:<policy>` for the plan, above the effective ceiling in force and at most the compiled hard cap. A waiver may be given at any time from plan start until the gate's fallback is taken, and it applies to every later evaluation of the gate; the client shows the plan, the gate, and the effect before the confirmation. `--reason-class` classifies the reason (`gate_false_positive`, `gate_not_applicable`, `tooling_unavailable`, `deliberate_deferral`, default `unknown`; link:../store-schemas/14-plan-instance-waivers-questions.adoc#waiver-record[Store Schemas Specification, Waiver Record]); it is mirrored into the audit log with the gate, where the Artifact Gate recurrence count and the lessons-capture signal read it. The runtime appends the record to `waivers.jsonl` (the only writer), mirrors it to `audit.jsonl`, and composes a new plan instance version. `unwaive <plan_id> <waiver_id>` revokes an unconsumed waiver; revoking a raise lowers the ceiling at the next budget check, where a counter already above it exhausts the budget and the fallback follows, without a refusal. Refusals: `not_waivable` (a gate outside the closed list, or on the non-waivable list of link:../store-schemas/14-plan-instance-waivers-questions.adoc#waiver-record[Store Schemas Specification, Waiver Record, Refusals]), `plan_ended` (the gate's fallback was taken or the plan ended), `already_consumed`, `raise_out_of_range`, `position_not_contained`. A waiver request filed by a worker's `request_waiver` in a remediation unit is an operator wait (link:../workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]) with no time limit: it ends by `waive` (naming the gate, optionally `--request <request_id>`) or by `decline <plan_id> <request_id> --reason <text>`, which records the outcome `declined` and lets the remediation unit take its next transition. Requests are shown in both clients, announced by the terminal client while it is open, shown in the plan's view as `facts.waiver_request` (link:../mcp-tools/01-core-workflow-tools.adoc#question-waiver-facts[MCP Tools Specification, Waiver Requests in Representations]), and posted as an idempotent pull request comment with the label `pm-mcp:waiver-requested`; the announcements are information only. Every waiver and consumption is listed in the pull request comment and the landing record.
7. [[operator-accept-edit]]*Accept-Edit (`pm-operator accept-edit`)*: The act of accepting a manual edit, in either client, shows the file's path and its recorded and current size and SHA-256 before the confirmation; there is no diff and no restore, because the prior content is not kept. On confirmation the runtime re-baselines the store's digest (link:../store-schemas/13-leases-integrity-testing.adoc#store-digest-verification[Store Schemas Specification, Store Digest Verification]), the lesson's entry, or the enrolment file's HMAC sidecar (<<enrolment-integrity>>), and appends an `audit.jsonl` record. The resolutions of an `integrity_breach` are those of the integrity pause (item 4). A workspace `<store>` is named relative to the project store root (`pending/<entry_id>/entry.json` for a pending entry record), a plan's or epic's relative to its scope directory (link:../store-schemas/01-format-and-session-log.adoc#transaction-journal[Store Schemas Specification, Transaction Journal]).
8. [[operator-abort]]*Ending a Plan or an Epic*: The operator ends a plan through `plan.aborted` in the next transaction, an engine-owned scope-wide transition under the on-entry rule (every begun, unsettled step is recorded `failed`), with the operator's reason (link:../state-catalogue/04-plan-finalize-terminal.adoc#plan-end[State Catalogue Specification, Cancelling and Abandoning Archive]): *cancel* a running, pausing, waiting, or held plan (outcome `cancelled`), or *abandon* a paused one (outcome `abandoned`), choosing in the confirmation whether an open pull request of the plan is closed with a comment naming the reason or left open (its branch stays); `pm-operator abort plan <plan_id> --reason <text>` is the shell form of both, cancel or abandon by the plan's state. The plan is archived like a completed plan; open decisions and waiver requests are closed `cancelled`, and the plan's lesson claims are released. `plan.aborted` is also entered by the integrity abort (outcome `aborted`, item 4), by the release of the project (outcome `released`, <<project-release>>), and by `delete-plan` (fixed reason `plan_deleted`), whose first transaction is this one and whose second, ordered after it, removes the plan directory; no model ends a plan: a worker's task ends only in its closed task outcomes, and a plan that cannot continue takes its phase's fallback (`returned` or `handed_back`), never `plan.aborted`. The operator *cancels* an epic (`pm-operator abort epic <epic_id> --reason <text>`, or its cancel act) with the choice for its plans, cancelled too or left running detached (link:../model-work/08-epic-coordination.adoc#epic-actions[Model Work Specification, An Epic's Actions]): the epic takes the archive path in the next transaction (its open tasks withdrawn, then `epic.archive`, the ledger commit, and the epic landing; link:../state-catalogue/06-setup-epic-other.adoc#state-epic.archive[State Catalogue Specification, `epic.archive`]) and ends in `epic.aborted` with the `terminal_reason` `cancelled`; a plan left running detached runs to its own outcome, and once the epic is terminal its epic linkage resolves to `detached`, which every consumer treats like `not_orchestrated` (no landing emission to an inbox, late findings seeded as lessons, no outbox link; link:../store-schemas/02-workflow-state-store.adoc#epic-linkage[Store Schemas Specification, Origin and Epic Linkage]). The release of the project ends its epics without this archive path (<<project-release>>). The reason is recorded in the landing record and the audit log.
9. [[operator-grant-access]]*Cross-Project Access (`pm-operator grant-access <plan_id> <project_id> read|read-write --reason <text>`)*: A plan works inside its own enrolled project (`PM-SEC-2`); access to another enrolled project, and the read-only provider reads of an organisation, group, or repository outside the project (`--org <owner>` or `--repo <owner>/<name>`, only with `read`; <<cross-repository-reads>>), is granted only by the operator, in either client, on the operator's own initiative or as the act of the hold that asks for it. The act shows the plan, the target (a project identified by its remote owner and name, never by a checkout path; an organisation, group, or repository by its name at the plan's provider), and the access level before the confirmation; the runtime appends a grant record to the plan's append-only grant log in the plan store (link:../store-schemas/15-screening-and-grants.adoc#grant-record[Store Schemas Specification, Grant Record]) and mirrors it to `audit.jsonl`. The grant applies from the plan's next transaction and holds until the plan ends; there is no revocation, and ending the plan (<<operator-abort>>) is the only way to stop it. An access to a project without a grant of the needed level raises `precondition_unmet` on the current state, held for the operator with the grant as its act; its `retry` re-checks the grants within the condition budget (link:../timeouts/01-job-budgets-and-waits.adoc#condition-budget[Timeouts & Budgets Specification, Condition Budget]), after which the phase's fallback is taken with the access as the gap. No model-facing link requests a grant.
10. [[operator-enrol-harness]]*Harness Enrolment (`pm-operator enrol-harness <client>`)*: Workers run only through an enrolled harness (`PM-EXEC-1`). The harness step of the machine's onboarding (`harness.enrol`, after the scan, link:../client-profiles/01-profile-schema.adoc#harness-scan[Client Profiles Specification, Harness Scan]) and the verb enrol alike: they resolve the absolute path of the profile's `headless.executable`, run the profile's version probe as a probe job (link:../job-runtime/02-confinement-and-environment.adoc#probe-jobs[Job Runtime Specification, Probe Jobs]), and record the path, version, and digest, and nothing else, in the machine's harness enrolment (link:../store-schemas/11-enrolment-store.adoc#harness-enrolment-store[Store Schemas Specification, Harness Enrolment Store]); they show the path, version, and digest for confirmation; they refuse a client whose profile has `headless: null` or `worker.eligible: false` (`invalid_arguments`) and a version outside `headless.supported_versions` (`harness_version_unsupported`). `harness.enrol` also records the machine's default harness, `harnesses.default` of `machine-config.json`, a client id of `harnesses.json`; a harness that is the default cannot be removed before another is chosen. Neither captures an environment value: `PM-MCP` never stores or exports a harness's authentication. The harness CLI must already be authenticated by its own login, cached under its home; a worker of a harness that is not logged in fails to start, and the start-failure guard reports the harness's own error text to the operator (link:../model-work/03-supervision-and-recycling.adoc[Model Work Specification, Supervision & Recycling]). Enrolling is also the re-baseline of a tampered harness enrolment: when the HMAC check of `harnesses.json` fails, every worker launch on that harness is refused before spawn (fate `refused`, reason `harness_tampered`, a `security` audit record `enrolment_tampered`) and counts as a start failure of the role on that harness; once the start-failure guard holds, the role's tasks close `lost` with `role_unavailable` and take their conservative fallback, and both clients offer the harness's enrolment again (link:../model-work/04-worker-launch.adoc#harness-selection[Model Work Specification, Launch Refusals]). The act rewrites the file and its sidecar with the named client only after showing path, version, and digest; entries of other clients in the tampered file are not carried over, and each of those clients must be enrolled again. There is no pause and no `accept-edit` form for this file. A later change of the digest or version (the harness updates itself) is accepted while the version stays inside the range: in the accepting transaction the runtime rewrites `harnesses.json` and its HMAC sidecar under `locks/harnesses.lock` and appends the audit record `harness_updated`; outside it every worker launch on that harness is refused `harness_version_unsupported` until the operator enrols it again; a version change also invalidates the qualification records of the roles on that harness (`PM-WORK-6`) (link:../client-profiles/01-profile-schema.adoc#headless-block[Client Profiles Specification, `headless`]).
11. [[operator-roles]]*Roles (`pm-operator roles`)*: Roles are configuration artifacts in the shipped, machine, and project role sets, and a role's harness, model, and effort are the effective values of its artifact overlaid by the machine's and the project's role assignment and a plan override (link:../model-work/01-roles-and-configuration.adoc#role-assignment[Model Work Specification, Role Assignment]). The role assignment is written by the roles aspect of the machine's onboarding (`roles.write`, also `pm-operator config roles`) and, for a project, by its onboarding; the operator may still edit the artifacts of the machine or project set. The verbs below read and grade and never write an artifact or an assignment. The qualification semantics (validity, corpus topics, grading, conservative fallback) are in link:../model-work/01-roles-and-configuration.adoc#qualification[Model Work Specification, Role Qualification].
* `roles list [--project <project_id>]`: every role of the effective set (of the project, or the machine and shipped sets without `--project`) with its source set, class, form, effective harness, model, and effort with the level each comes from, its qualification state (`qualified`, `qualified_fresh_only`, `unqualified` naming the changed input when a record no longer matches or the measurement below the project's current level, or `invalid` with the validation reason; an invalid artifact counts as undefined), and whether the start-failure guard of the role holds (link:../model-work/03-supervision-and-recycling.adoc#start-failure-guard[Model Work Specification, Start-Failure Guard]). Read-only.
* `roles show <role> [--project <project_id>]`: the effective artifact, the artifacts of lower sets it replaces, the assignments that overlay it, its configuration digest and its qualification digest (over the effective values), its validation result, an effort narrowing the harness applies to it, and the summary of its qualification record. Read-only.
* `roles show --decisions [--project <project_id>]`: the decision declarations of the project's adjudication unit and of the binary's default unit (per decision kind `ask` or the quorum with each listed role's harness, model, availability, and qualification, and the validation result) and the calibration record of every quorum declaration: the items graded, the automatic share, the false automatic share against the declared level, and whether the declaration decides (link:../model-work/10-decision-quorum.adoc#quorum-calibration[Model Work Specification, Quorum Calibration]). Read-only.
* `roles qualify --decisions [--project <project_id>] [--kind <decision_kind>] [--yes]`: calibrates every quorum declaration that the project's adjudication unit or the binary's default unit uses and that has no valid record, or the declarations of the named kind, on the corpus items of closed decisions of its kind, with the confirmation and progress of `roles qualify`, and has the runtime write one decision calibration record per declaration digest to the project set (identical declarations share one), bound to the corpus revision; it prints the measurements and the paths.
* `roles qualify <role> [--project <project_id>] [--yes]`: shows the configuration, the corpus topics, the item count per form, and the expected tokens and time from earlier records, and runs only after confirmation (`--yes` skips the confirmation, never the terminal check of item 2); it then grades the configuration warm and fresh (link:../model-work/01-roles-and-configuration.adoc#grading[Model Work Specification, Grading]) and has the runtime write the qualification record to the project set, bound to the qualification digest (over the graded members `PM-WORK-6` names, link:../model-work/01-roles-and-configuration.adoc#qualification[Model Work Specification, Role Qualification]) and the corpus revision; its progress is shown like any other jobs in both clients, and it prints the record's measurements, whether they qualify each form at the project's current levels, and the path. While a role is unqualified its tasks take their conservative fallback with the reason `role_unqualified`; no task waits for a qualification. The project's setup runs the same grading for every role without a valid record, after its consent `model_cost` (link:../domain-extensions/04-setup-state-machine.adoc#setup-qualification[Domain Extensions Specification, Role Qualification at Install]).
12. [[operator-decisions-export]]*Decision Export (`pm-operator decisions export`)*: Reads the decision records of the project (`--project`, else every enrolled project; live and archived plans, epics, and the workspace scope) and writes the selected judgment decisions as `draft` corpus items, and with `--calibration` the server-rule decisions as calibration rows, into `--out`, a directory the operator names; the selection, the target, the mapping, and the skip reasons are owned by link:../model-work/11-decision-records.adoc#corpus-export[Model Work Specification, Corpus Export]. It is read-only on every store, needs no confirmation, never overwrites a file, and sends nothing over the network (`PM-ARCH-2`); the runtime appends one audit record with the counts written and skipped. The items carry real code and facts of the project: the operator reviews them before anything enters the corpus.

=== Enrolment Integrity

The enrolment file, its sidecar record with the HMAC under the enrolment integrity key, the key, the per-use checks, the check with its refusals, and the residual risk are implemented and documented in link:../../concepts/enrolment.adoc[Concepts § Enrolment] and link:../../developer/enrolment-store.adoc[Developer Guide § Enrolment Store] (link:../../Requirements.adoc#PM-EXEC-2[PM-EXEC-2], link:../../Requirements.adoc#PM-SEC-5[PM-SEC-5]). The operator is shown the refusal `enrolment_tampered` as a hold of the project with its act, and re-baselines the file interactively (accepting the edit, `pm-operator accept-edit enrolment <project_id>`, after reviewing the displayed recorded and current size and SHA-256 from the sidecar record, <<operator-accept-edit>>).

[#enrolment-lifecycle-release]
=== Enrolment, Lifecycle Gate & Release
_Implementation watch: link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-23[PM-WATCH-CLI-23], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-25[PM-WATCH-CLI-25], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-29[PM-WATCH-CLI-29]_

_See Requirement link:../../Requirements.adoc#PM-MIG-1[PM-MIG-1: Six-Stage Build-Out & Per-Project Plan Lifecycle]_

_See Requirement link:../../Requirements.adoc#PM-MIG-5[PM-MIG-5: Quantitative Triggers & Project Release]_

_See Requirement link:../../Requirements.adoc#PM-EXEC-2[PM-EXEC-2: Operator Enrolment & Verify-Not-Resolve Contract]_

`PM-MCP` and `plan-marshall` keep separate state trees (`PM-MIG-2`, link:../filesystem-layout/03-project-store.adoc#coexistence-lifecycle[Filesystem Layout Specification]). There is no crossing: `PM-MCP` imports nothing from `plan-marshall` (no configuration, lessons, `project-architecture/`, credentials, or learned build timeouts) and never reads or writes `.plan/` or `~/.plan-marshall/`. A project is taken into use as follows; each step is an operator act and writes an `audit.jsonl` record:

* *Enrolment*: The project's onboarding (<<project-onboarding>>) ends its detection and identity in `project.enrol`, which has the runtime write the project's enrolment (link:../../concepts/enrolment.adoc#enrolment-file[Concepts § Enrolment], link:../store-schemas/11-enrolment-store.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]) with the fields the onboarding detected and the operator confirmed: the project root (refused with `enrolment_root_conflict` when another enrolment file already names it, and with `project_store_root_mismatch` when the machine store of this `project_id` records a different `project_root`), wrappers with their `pinned_files` and interpreter, host tools (the machine's enrolled CLI tools of `host-tools.json` serve unless the project enrols its own), the canonical and discovery command templates it overrides, provider `verify_argv` overrides, project scripts with binding, argument schema (validated as a schema), and maximum timeout, command budgets, write paths, the captured build environment, language servers, `container_engine` (`docker` only after the operator has been told that the project's jobs then hold the authority of the Docker group, which reaches every host path including `<PM_MCP_BASE>`, and has confirmed it; audited as `container_engine_enabled`; link:../job-runtime/02-confinement-and-environment.adoc#container-engine[Job Runtime Specification, Container Engine]), and `pilot`. On first enrolment it creates the project's machine store `<PM_MCP_BASE>/projects/<project_id>/` (link:../filesystem-layout/03-project-store.adoc#machine-store[Filesystem Layout Specification, Per-Project Machine Store]) with its workspace scope. `pm-operator enrol [--pilot] [--container-engine docker]` stays the direct verb: a later run of `project.identity` to `project.enrol` with its arguments as the answers, run from the checkout's working directory.
* *Setup*: The project setup in the workspace scope (link:../domain-extensions/04-setup-state-machine.adoc#project-setup-state-machine[Domain Extensions Specification, Project Setup State Machine]) creates, on its first run, `.marshall/` with its `.gitignore` partition (link:../filesystem-layout/01-repository-workspace.adoc#repository-layout[Filesystem Layout Specification]) and `.marshall/config/`, which holds no copy of a default workflow unit: a project holds a copy only of the units its team placed or changed, and a unit absent there resolves to the machine's level, then to the compiled default (link:../workflow-dsl/04-ast-node-model.adoc#process-designer[Workflow DSL Specification, Designing a Process]); the JSON team files are sparse and start absent, and no `plan-marshall` input exists.
* *Lifecycle gate*: The compiled gate and its decision per project are implemented (link:../../concepts/enrolment.adoc#lifecycle-gate[Concepts § Enrolment, The Lifecycle Gate and Pilots]). Where the gate refuses a project, the opening of a start entry for a plan or an epic and `start.create-scope` refuse with `lifecycle_closed` and create nothing, while the orthogonal services and the workspace scope stay available; since the gate is asked at each start, enrolling again without `--pilot` refuses only later starts, and the project's live plans and epics continue.
* *Unenrolment* (`pm-operator unenrol <project_id>`, or the act of either client, confirmed with what it ends): refused with `scope_active` while the project has non-terminal plans or epics or running jobs, naming them; it removes the enrolment file and its sidecar and records `unenrolled_at` in the project store's `store.json` (link:../store-schemas/11-enrolment-store.adoc#project-store-identity[Store Schemas Specification, Project Store Identity]), leaving the store otherwise untouched. The store is then an item of the operator's cleanup, deleted as a whole only by it (link:../timeouts/03-retention-host-config.adoc#cleanup[Timeouts & Budgets Specification, One Cleanup]), and never a candidate of the periodic sweep, which removes only its technical residue. The store records its `project_root`; enrolling the same `project_id` again reuses the store only for the same root, removing `unenrolled_at`, and is refused otherwise (`project_store_root_mismatch`, a refusal naming both roots, not an MCP tool error).
* *Release*: the operator's switch-off for the `PM-MIG-5` triggers (<<project-release>>).

[#project-onboarding]
=== Onboarding a Project as One Process
_See Requirement link:../../Requirements.adoc#PM-EXT-8[PM-EXT-8: Project Onboarding as One Process]_

_See Requirement link:../../Requirements.adoc#PM-WF-26[PM-WF-26: Machine Onboarding & the Machine Scope]_

_See Requirement link:../../Requirements.adoc#PM-SEC-8[PM-SEC-8: Consent Before Acting]_

_See Requirement link:../../Requirements.adoc#PM-EXT-3[PM-EXT-3: Module Discovery, Build Map & Architecture Enrichment]_

A project is onboarded by one compiled unit, never project-owned, that runs from its checkout through detection, identity, and enrolment into the project setup (link:../../use-cases/04-projects.adoc#UC-PRJ-1[UC-PRJ-1]). Its states and their facts are in link:../state-catalogue/06-setup-epic-other.adoc#state-catalogue-setup[State Catalogue Specification, Setup States]; what the process guarantees:

* *A scope of its own*: Each onboarding runs in a scope of its own, an entry like a plan's start until `project.enrol` and then the project's workspace scope, so that several projects are onboarded at once and the machine scope's state is never touched. It starts only while the machine's onboarding is complete (`onboarding_incomplete` otherwise). Its choices are operator waits served to both clients, whichever answers first wins; no coding-agent session drives it (link:../workflow-dsl/02-units-jobs-decisions.adoc#clients-only[Workflow DSL Specification, All Interaction in the Operator's Clients]).
* *Where it starts*: `POST /api/v1/project-onboardings` (body: the checkout path; from the terminal client also its login environment, xref:01-cli-and-installer.adoc#client-environment[What the Terminal Client Sends]) opens the onboarding's entry, addressed like every entry at the top level as `/api/v1/entries/{entry_id}` with its events (link:../runtime-model/01-processes-and-transport.adoc#event-streams[Runtime & Interaction Model Specification, Events per Scope]), until `project.enrol` moves it into the project's workspace scope. `pm-operator project add [<path>]` opens it from the terminal, the working directory the proposed checkout. The checkout path must resolve canonically to a git top-level that no enrolment names (`enrolment_root_conflict`) and that lies under no project's `.marshall/local/worktrees/`.
* *Detection*: After the operator's consent `inspect_checkout` (link:../store-schemas/12-machine-stores.adoc#consent[Store Schemas Specification, Consent Before Acting]), the server reads the checkout and changes nothing: the remote with its owner and name, the base branch, the build wrappers with their pinned files, the host tools the project uses, the language servers, and the project scripts, each reported with a check line. What can be read is read (a build wrapper's version from its pinned properties); only host tools found in the directories of the operator's login `PATH` run their version probe, each as a probe job (link:../job-runtime/02-confinement-and-environment.adoc#probe-jobs[Job Runtime Specification, Probe Jobs]), never in the runtime's own process.
* *The checkout's own scripts*: Running them needs the operator's consent per project, `run_checkout_scripts`, asked in `project.run-consent` with every script and its arguments named, before any of them runs. It is the trust the enrolment grants anyway, since the enrolled wrapper runs in every build of the project's plans. Each script runs as a probe job with the confinement of a build job of the checkout. A _no_ goes on without the scripts, what needs them recorded as unknown, and is not asked again in that run. A remembered _yes_ is kept in `consents.json`, keyed by the project and the digest of each script, never in the enrolment, and a later run asks again only for a script that changed.
* *A consent remembered before enrolment*: Both checkout consents are asked before the project has its id. A remembered _yes_ is held with the onboarding's entry and written to `consents.json` under the project's `project_id` at `project.enrol`, the id the operator confirmed; an onboarding that does not reach `project.enrol` remembers nothing.
* *Identity*: The project's id is proposed from the remote's name, made valid by the identifier grammar (link:../identifiers.adoc[Identifier Registry]) and unique on the machine (a taken id gains the suffix `-2`, `-3`, …); the display name is proposed from the remote's owner and name. The operator may change both before the enrolment, the display name also later.
* *The build environment*: It is the operator's login environment as the terminal client captures and sends it, never the runtime's own (link:../runtime-model/01-processes-and-transport.adoc#runtime-environment[Runtime & Interaction Model Specification, Environment]). An onboarding run from the web app takes the build environment the terminal client last captured on the machine and says so with its time; with none, the state names the terminal command that captures it (`pm-operator project add`, or `pm-operator project setup <project_id>`), and the enrolment waits for it.
* *Enrolment*: `project.enrol` writes the enrolment the detection proposed and the operator confirmed (<<enrolment-lifecycle-release>>); the operator's values of the project follow in its setup with the machine's values as the proposal (link:../store-schemas/08-project-configuration-local.adoc#project-levels[Store Schemas Specification, Project Values over Machine Values]).
* *Model cost asked first*: After the setup's qualification probe reports `grade`, and after its enrichment probe reports `enrich`, a consent state of kind `model_cost` (`setup.qualify-consent`, `setup.enrich-consent`) shows the expected tokens; _no_ skips the step with its reason and records it as owed for a later run, and the project is ready without it (link:../domain-extensions/04-setup-state-machine.adoc#setup-qualification[Domain Extensions Specification, Role Qualification at Install]).
* *A later run of one aspect*: The setup takes an optional aspect (the operator values, the team settings, the build map, the providers, the finalize steps, the qualification, the architecture) and runs only that aspect's states, with the current values as the proposal; without an aspect it takes its reconcile path. `pm-operator project setup <project_id> [<step>]` starts it, or continues an onboarding still open.

=== Releasing Ends Work as the Operator Ends It
_See Requirement link:../../Requirements.adoc#PM-MIG-5[PM-MIG-5: Quantitative Triggers & Project Release]_

_See Requirement link:../../Requirements.adoc#PM-WF-23[PM-WF-23: Operator Acts on Plans and Epics]_

The release is the operator's switch-off for the `PM-MIG-5` triggers: an operator act of both clients (`POST /api/v1/projects/{project_id}/release` with the operator's reason; `pm-operator release-project <project_id>` its terminal form), confirmed with what it ends, listed before the confirmation: every non-terminal plan and epic of the project, its pending entries, and a running onboarding (link:../../use-cases/04-projects.adoc#UC-PRJ-3[UC-PRJ-3]). It runs in this order:

. *A short landing finishes first*: Before it ends anything, the release lets a running short landing of the project (`git.land-removal`, `git.land-unit`; link:../workflow-dsl/06-reusable-sub-workflows.adoc[Workflow DSL Specification, Reusable Sub-Workflows]) finish, within the compiled bound `release.landing_wait_seconds` (link:../timeouts/01-job-budgets-and-waits.adoc[Timeouts & Budgets Specification]). While it waits, the project admits no new start and no new short landing (each refused `lifecycle_closed`). When the landing does not finish within the bound, the release is refused (`release_landing_pending`, `409`, naming the landing), ends nothing, and the project admits starts again.
. *The release is recorded*: The runtime writes `released_at` (the release instant) into the project's enrolment file (link:../store-schemas/11-enrolment-store.adoc#enrolment-store[Store Schemas Specification, Project Enrolment Store]) and appends an `operator` audit record.
. *Every plan ends `released`*: Every plan of the project that has not ended, whatever its state (running, pausing, paused, waiting for the operator, or held), ends through `plan.aborted` with the outcome `released` and the operator's reason, never `cancelled` or `abandoned`, and is archived like a completed plan (link:../state-catalogue/04-plan-finalize-terminal.adoc#plan-end[State Catalogue Specification, Cancelling and Abandoning Archive]); its open decisions and waiver requests are closed `cancelled`, and its lesson claims are released.
. *Every epic ends `released`*: Every epic of the project that has not ended ends with the `terminal_reason` `released` and is archived in the project's machine store only (link:../filesystem-layout/03-project-store.adoc#archives[Filesystem Layout Specification, Archives]): its ledger stays in `.marshall/epics/<epic_id>/` untouched, without `epic.archive`, a ledger commit, or an epic landing. Its plans end with the release, so nothing is left to tell it.
. *Entries and onboarding*: The project's pending entries are deleted with their sources, and a running onboarding or setup run of the project is ended.
. *The report*: The runtime writes the report `project.released` (link:../runtime-model/01-processes-and-transport.adoc#reports[Runtime & Interaction Model Specification, Reports to the Operator]).

The release touches no repository: branches, worktrees, and pull requests stay as they are, the archived records stay readable in the project's machine store, nothing is converted, and the project can continue on `plan-marshall`, whose `.plan/` `PM-MCP` never touched. While `released_at` is set, the plan lifecycle is not offered: the opening of a start entry for a plan or an epic and `start.create-scope` refuse with `lifecycle_closed`; the workspace scope and the orthogonal services stay available. Enrolling the released project again clears `released_at` (audited), and the lifecycle is offered again under the lifecycle gate.

== Security Audit Trail
_See Requirement link:../../Requirements.adoc#PM-SEC-6[PM-SEC-6: Security Audit Trail & Tamper-Evident Logging]_

_See Requirement link:../../Requirements.adoc#PM-SEC-1[PM-SEC-1: Two-Boundary Security Model & Untrusted Content Containment]_

Every MCP tool call, state transition, job execution, credential lookup, consent, and operator act appends a structured JSONL record to `<PM_MCP_BASE>/logs/audit.jsonl` (mode `0600`, appended under the audit lock on the log file itself, a leaf of the lock order, schema defined in link:../store-schemas/12-machine-stores.adoc#audit-log[Store Schemas Specification, Audit Log]):

* *Identity per record*: A record carries the identity of the operation it audits, and no call is checked against an environment: an operator act its channel (`cli`, or `web` with the `device_id` of the paired device), a worker's operation its `job_id`, role, harness, and generation, and a machine-level record (runtime start, a sweep, a machine-scope transition) the operating system principal running the runtime (`System.getProperty("user.name")` / `geteuid()`).
* *Hash Chain*: Every record carries `prev_hash`, the lowercase hex SHA-256 of the previous record's canonical line (its exact UTF-8 bytes in the file, without the trailing newline). The first record of a new log carries the genesis value (64 `0` characters). Records are appended only by writers that hold the log's lock and read the current last line first.
* *Anchored Head (`logs/audit.head`)*: After every append the writer updates, under the same lock, the sidecar `logs/audit.head` with the current file name, record count, last `event_id`, and head hash (the hash of the last canonical line), protected by an HMAC-SHA-256 under the integrity key of the enrolment store (link:../../concepts/enrolment.adoc#integrity[Concepts § Enrolment, Integrity]). The chain alone proves only that the records present are consistent; the anchored head makes a deleted log, a reset to the genesis value, a truncated tail, and a consistently rewritten chain detectable.
* *Rotation & Checkpoints*: When `audit.jsonl` exceeds `audit_rotation.max_bytes` or `audit_rotation.max_days` (`machine-config.json`, link:../timeouts/03-retention-host-config.adoc#audit-rotation-age[Timeouts & Budgets Specification]), the writer appends a `checkpoint` record (record count, head hash, HMAC under the same key), renames the file to `audit-<first_event_id>.jsonl`, and starts the new `audit.jsonl` with a record whose `prev_hash` is the hash of that checkpoint line. Every rotated file is listed in the append-only index `logs/audit-index.jsonl` (file name, first and last `event_id`, record count, checkpoint hash), itself hash-chained and anchored in `audit.head`. The periodic sweep removes rotated files older than `audit_rotation.retain_days` (`machine-config.json`, link:../timeouts/03-retention-host-config.adoc#rotated-audit-files[Timeouts & Budgets Specification, Rotated Audit Files]) by itself, as technical residue (link:../store-schemas/13-leases-integrity-testing.adoc#evidence-based-removal-sweeps[Store Schemas Specification, Evidence-Based Removal Sweeps]), as whole files and never their index entries, one audit record each, so a removed file stays accounted for; `pm-operator sweep --machine` lists them and `--apply` runs that pass at once.
* *Chain Verification at Runtime Start*: The runtime verifies incrementally: the HMAC of `audit.head`, the index, and the records of the current file after its last checkpoint. A missing log, a reset to genesis, a record count below the anchored count, or a head mismatch is reported as `audit_chain_broken` with `reason` `missing`, `reset`, `truncated`, or `head_mismatch`; a broken link inside the verified range uses `reason: link_broken` and names the first broken line. The full chain across all rotated files is verified on demand by `pm-operator audit verify`. The same reporting rules apply to every result: on `stderr`, in both clients of the operator, and as an `audit_chain_broken` security record; the log is never rewritten or silently repaired, and the next record chains to the last line as found.
* *Residual Risk*: The anchoring is tamper-evident, not tamper-proof: a process that holds the integrity key (on macOS, anything that runs the `pm-mcpd` binary; with the file store or the key file, any process of the user) can forge a consistent head. This is accepted and documented with the enrolment integrity risk (link:../../concepts/enrolment.adoc#residual-risk[Concepts § Enrolment, Residual Risk]; `PM-SEC-6`).
* *Error Sanitization*: Unhandled exceptions or protocol errors return only a closed-enum error code to the MCP caller, plus the `audit_id` (a UUIDv7, link:../identifiers/02-registry-stores-to-web.adoc#id-audit-id[Identifier Registry]) only where the operator must look the error up (`internal_fault`, `file_unreadable`; link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]); stack traces and host filesystem paths are written exclusively to `<PM_MCP_BASE>/logs/daemon.log`.

== Outbound HTTPS Security (`cui-http`) & Native Runtime Stack
_See Requirement link:../../Requirements.adoc#PM-TECH-1[PM-TECH-1: Java 25+ & Quarkus MCP Runtime Foundation]_

_See Requirement link:../../Requirements.adoc#PM-TECH-2[PM-TECH-2: Outbound HTTPS Client, LSP Client & McpAssured Testing Libraries]_

_See Requirement link:../../Requirements.adoc#PM-TECH-3[PM-TECH-3: GraalVM Native Executable & Startup/Memory Bounds]_

_See Requirement link:../../Requirements.adoc#PM-TECH-4[PM-TECH-4: Operating System Platform Integration (macOS & Linux)]_

_See Requirement link:../../Requirements.adoc#PM-SVC-3[PM-SVC-3: Selective Upstream MCP Proxy & Provenance Tagging]_

_See Requirement link:../../Requirements.adoc#PM-TEST-5[PM-TEST-5: Security Boundary & Confinement Adversarial Testing]_

* *Outbound HTTPS Hardening (`de.cuioss:cui-http`)*: All outbound REST and GraphQL calls (SonarQube/SonarCloud, the native GitHub, GitLab, and Forgejo clients), remote upstream MCP calls, and the runtime's own fetches (a release from the organisation's registry, on the operator's upgrade or the consent `check_updates`; a harness icon, on the consent `fetch_icons`) use `de.cuioss:cui-http`'s `HttpHandler` and `ResilientHttpAdapter` with TLS 1.2+, mandatory certificate/hostname verification, HTTPS-only redirect following, and origin-pinned bearer token transmission (stripping `Authorization` headers on any cross-origin redirect). All URL/path/header parameters composed into outbound requests are validated through `de.cuioss.http.security` pipelines. The native git transport (JGit) uses a connection factory with the same TLS rules that connects only to the credential entry's origin (<<native-confinement>>). Both honour the operator's `proxy` setting of `machine-config.json` and no other proxy source (<<native-confinement>>, Configuration allowlist). An upstream MCP server is always a remote HTTPS server reached this way, and it is called by the runtime only, never re-exposed to a worker; no upstream server runs as a `stdio` subprocess (`PM-TECH-2`). Nothing about the machine is sent beyond the request itself (`PM-ARCH-2`).
* *GraalVM Native Image & Resource Bounds*: The runtime `pm-mcpd` is compiled as a standalone Quarkus native executable (`Java 25+`, `quarkus-mcp-server-http`, Virtual Threads); the two CLI binaries `pm-mcp` (the relay) and `pm-operator` and the launcher `pm-exec` are plain native images without Quarkus (xref:01-cli-and-installer.adoc#cli-implementation[CLI Implementation]). Startup and memory bounds for the runtime, the relay, and the operator CLI are defined in `PM-TECH-3` and verified as described in the link:../runtime-model/04-sessions-and-workers.adoc#_verification[Runtime & Interaction Model Specification, Verification].

fail-closed termination at runtime start (exit code `77`), that insecure permissions (`0644`) on one project's enrolment file block only that project (`enrolment_insecure`), that a project's enrolment
