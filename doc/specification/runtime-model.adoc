== Overview

This document is the single normative description of how *plan-marshall-mcp* (`PM-MCP`) runs, how the operator works with it, and how workers interact with it. It separates two models that must never be conflated:

* *Runtime model*: One always-on *runtime* process (the daemon, binary `pm-mcpd`) per machine and `PM_MCP_BASE` owns all workflow execution, jobs, workers, warm services, coordination, and every store write. Its lifetime is independent of every client and every worker.
* *Interaction model*: The runtime drives every plan and epic itself. A state that needs no model is server logic; a state that needs a model becomes a task of a role, which a *worker* (a headless harness process the runtime starts as a job of kind `llm`) receives through `pm_wait` and does along the task's links; a state that needs the operator is an *operator wait*, served to the operator's two clients, the web app and the terminal client, over the local API. A harness is a worker only: no harness, session, or model acts for the operator. Workers reach the runtime through a thin STDIO *relay* (`pm-mcp serve --job`) that carries their job token and generation; the clients reach it through the local API. A plan or epic is carried entirely by its persisted files, never by a connection.

One release delivers four native binaries, each with one direction (`PM-TECH-3`, link:../Requirements.adoc#PM-IMPL-1[PM-IMPL-1]):

[cols="1,1,3"]
|===
|Binary |Build |Role

|`pm-mcp`
|plain GraalVM native image, picocli
|The relay binary: only the worker relay `serve --job`, a client of the runtime's `/mcp`; holds no store logic and writes no store.

|`pm-operator`
|plain GraalVM native image, picocli
|The terminal client and the operator CLI: the entry without a verb, the operator's views, waits, and acts, and the operator verbs (`enrol`, `credentials`, `waive`, `config`, `roles`, `web`, `client`, `runtime`, `cleanup`, `sweep`, `drain`, `status`, and the others of the command tree), without an `operator` sub-level. A client of the runtime's Local API; holds no store logic and writes no store. The client bundles deny the whole binary to every worker's model (link:cli-and-security/02-operator-channel.adoc#operator-channel-isolation[CLI, Coordination & Security Specification, Operator Channel Isolation]).

|`pm-mcpd`
|Quarkus native
|The runtime (daemon). Started on demand by `pm-operator`, by its predecessor after a restart, or by the per-user service manager (link:runtime-model/01-processes-and-transport.adoc#_start_modes[Start Modes]); opens no TCP or UDP listener unless the operator enabled web access, apart from the loopback listener fallback (link:runtime-model/01-processes-and-transport.adoc#_transport_endpoint[Transport Endpoint]).

|`pm-exec`
|plain GraalVM native image
|The job launcher: process group and, on Linux, confinement before `execve` (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/job-runtime/01-pipeline-and-subprocesses.adoc#_process_group_creation_via_the_pm_exec_launcher[Job Runtime Specification]). Started only by the runtime.
|===

Web access is no binary and no process of its own: while the operator enabled it, the runtime serves the web app and the Local API to paired browsers on its web listeners, a loopback listener and, beside it, a LAN listener (link:cli-and-security.adoc[CLI, Coordination & Security Specification]). The web app and the terminal client are the operator's views of every plan, epic, worker, and task, and both are dependable. The binaries are installed side by side in `<PM_MCP_HOME>/bin/`; a binary starts a sibling by its path in that directory, never through `PATH`.

All other specifications reference this document for process topology, transport, the relay, the local API with its resources and events, and the lifecycle of the runtime instead of restating them; the engine side of that lifecycle (the startup sequence, recovery, the periodic sweep, drain, stop, restart and upgrade, the pause of a plan, stalled plans, and the metrics) is specified in the link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/runtime-lifecycle.adoc[Runtime Lifecycle Specification]. The task protocol, roles, supervision, and consultation are specified in the link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work.adoc[Model Work Specification].
