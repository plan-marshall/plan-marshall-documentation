== On-the-Fly Placeholder Rendering Rules
_See Requirement link:../../Requirements.adoc#PM-CLIENT-2[PM-CLIENT-2: Data-Driven On-the-Fly Profile Translation]_

_See Requirement link:../../Requirements.adoc#PM-SKILL-2[PM-SKILL-2: Per-Project Skill Generation & Digest Integrity]_

_Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-2[PM-WATCH-CLIENT-2]_

Vocabulary skill templates (`SKILL.md`), the launch prompts of workers, and the model-facing guidance strings of representations are authored once in canonical placeholder notation and rendered on the fly by `ClientProfileRenderer`. A worker's prompt and every call of its job connection render with the profile of the harness of its role's effective configuration, recorded in its job record (xref:01-profile-schema.adoc#headless-block[Client Profile Schema, `headless`]); a harness is a worker only, so every rendering is a worker's.

`{{tool:ask_user}}` names the harness's own tool that asks a human. It is rendered only where a skill tells a worker not to use it: a worker asks only through its task's `ask` links, the server delivers the decision to the operator's clients (link:../model-work/06-envelopes-questions-deadlines.adoc#question-delivery[Model Work Specification, Delivery to the Operator]), and the tool is never in a worker's tool set (`tool_not_permitted`, link:../model-work/01-roles-and-configuration.adoc#role-validation[Model Work Specification, Role Validation]).

In `{{skill_load:<uri>}}`, `<scope>` is the rendering scope's argument: `plan_id="<plan_id>"` (`plan_id="NO_PLAN"` for the workspace scope) or `epic_id="<epic_id>"`, because `pm_skill` requires exactly one of them (link:../mcp-tools/01-core-workflow-tools.adoc#_surface_design_context_budget_discipline[MCP Tools Specification, Architectural Constraints item 11]).

=== Rendering Invariants
_Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-1[PM-WATCH-CLIENT-1], link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-6[PM-WATCH-CLIENT-6], link:../../implementation-watch/domain-extensions.adoc#PM-WATCH-EXT-23[PM-WATCH-EXT-23]_

1. *Zero Unresolved Placeholders*: If any `{{...}}` token in a skill template fails to resolve against the active `ClientProfile`, `ClientProfileRenderer` fails closed and logs a template defect rather than emitting raw `{{...}}` syntax to the model.
2. *Per-Variant SHA-256 Digest (`PM-SKILL-2`)*: The digest `_meta["de.planmarshall.mcp/sha256"]` published by `pm_skills` / `pm_skill` and `resources/read` is the SHA-256 of the rendered bytes the client receives (after rendering for `(project_config, client_id, pm_mcp_version)`); it is stable while those bytes are unchanged, and a configuration or version change that leaves a skill's rendered bytes unchanged leaves its digest unchanged.
3. *No Worker Without an Eligible Harness (`PM-WF-5`, `PM-WORK-1`)*: Rendering never replaces a worker by inline work elsewhere. A role whose harness has `headless: null`, is not eligible (`worker.eligible: false`), lacks a capability the role's class needs, or runs a model not listed in `worker.restricted_models` is invalid on load and counts as undefined, so a unit naming it is refused `role_undefined` at composition (xref:01-profile-schema.adoc#worker-block[Client Profile Schema, Worker Block]; link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]).
4. *Vocabulary-Only Translation*: `ClientProfileRenderer` varies only the placeholder dimensions of `PM-CLIENT-2` (host tool names, skill load directives, tool idioms; model and effort enter only the launch argument vector). It never varies emphasis, scaffolding, structure, or format: rendered variants of one template are byte-identical outside resolved placeholders.
5. *Profile Completeness*: Every canonical placeholder, and every rendering dimension added later, has a resolution in every built-in profile and in every profile the operator installs, which profile validation checks. A build-time test renders every template for every built-in profile and fails on any unresolved or missing form.
6. *Technique Preconditions Rendered per Project*: A skill section whose technique precondition (link:../domain-extensions.adoc[Domain Extensions Specification], Core Architectural Invariants, Technique Preconditions) is unmet in the project is rendered with the marker "available technique, not adopted in this project" in place of binding wording; the precondition result is an input of the rendered variant and of its `_meta.sha256` digest. This is a project dimension, not a client dimension, so it does not break Rendering Invariant 4.

[#calibration-decision]
=== Calibration Decision
_Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-1[PM-WATCH-CLIENT-1], link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-2[PM-WATCH-CLIENT-2]_

Model-facing content is written once and rendered vocabulary-only (Rendering Invariant 4), the same for every model a role set names. Whether it is adequate for a model is what role qualification measures: a role whose configuration does not reach the agreement level on its corpus topics with this content is unqualified, and its tasks take the conservative fallback (link:../model-work/01-roles-and-configuration.adoc#qualification[Model Work Specification, Role Qualification]). A calibration axis of the content is keyed by the model of the role artifact, never by the `client_id`, because one client hosts several models; such an axis multiplies the rendered digests (`PM-SKILL-2`) and requires per-model content and a qualification of every role on each model it distinguishes before it ships.

[#host-resident-surface-inventory]
=== Host-Resident Surface Inventory
_Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-3[PM-WATCH-CLIENT-3]_

For every built-in profile, the build derives and publishes the resident surface of a worker: the bytes the harness injects into every turn of a worker by its registration mechanism (the MCP tool schemas and descriptions of the role's tool set when `schema_residency: resident`, the description of the shim skill where the bundle installed it in the project, and the `pm_skills` catalogue entries once loaded), per component and in total, together with the population it measured. The launch prompt and the skills the server delivers (`PM-SKILL-4`) are measured with the task, not as resident surface. Residency follows the actual injection mechanism, not file existence; the population is the served set for the profile (after domain filtering, `PM-SKILL-2`), not the set of files in the binary.

* *Derived Bounds*: Any length or shape bound on a description is derived from the measured distribution of the inventory and records that derivation; a build-time test enforces the bound.
* *Named Runtimes*: A description shape rule names the runtimes and models it was reasoned about; every runtime reads the descriptions byte-identically.

[#host-environment-detection]
== Host Environment Detection
_See Requirement link:../../Requirements.adoc#PM-CLIENT-1[PM-CLIENT-1: Harnesses as Workers & Client Identity]_

_See Requirement link:../../Requirements.adoc#PM-CLIENT-3[PM-CLIENT-3: Host Environment Detection]_

Client identity is advisory routing and rendering metadata, never a security credential. A harness is a worker only: a worker's connection takes its client profile from its job record, which names the harness of its role's effective configuration and the harness version probed at its spawn, and carries its `job_id`, role, and generation in its audit records (link:../mcp-tools/01-core-workflow-tools.adoc#job-bound-connections[MCP Tools Specification, Job-Bound Connections]); the system performs no identity check per tool call.

The one use of detection is the operator checks of `pm-operator`: they recognise a coding agent's environment from the process environment the verb inherited, by the detection signals and their precedence below, and refuse an operator verb while any signal is present, naming the detected host (link:../cli-and-security/02-credentials-and-operator.adoc#operator-channel-isolation[CLI, Coordination & Security Specification, Operator Channel Isolation]). Detection never selects a profile and never records an identity. No model-facing representation carries a detection result (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).

[#host-integration-table]
=== Host Integration Table (Normative)
_Implementation watch: link:../../implementation-watch/client-profiles.adoc#PM-WATCH-CLIENT-4[PM-WATCH-CLIENT-4]_

This table is the single source for host-specific values. Requirements, other specifications, and the roadmap reference it instead of repeating values. Values without a marker are verified against a local installation of the host and what it sends at `initialize` (Claude Code 2.1, OpenCode 1.18, Antigravity CLI `agy` 1.3), or backed by the evaluation (link:../evaluation.adoc[Evaluation Reference]) or by `plan-marshall` (`script-shared/scripts/marketplace_paths.py`, `platform-runtime/scripts/{opencode,antigravity}_runtime.py`, verified at commit `1d4a1da37`). Values marked _(provisional)_ are known from the host's documentation, source, or binary only and are verified against a live host before the profile ships: every Codex value, and the Antigravity values that only a live session shows.

*Detection precedence*: Primary signals are evaluated in the fixed order `antigravity` -> `opencode` -> `claude` (the order `plan-marshall` uses, `script-shared/scripts/target_context.py` `detect_target_from_env`), then `codex`; the first match wins. Secondary signals (`CLAUDECODE`, the `AI_AGENT` prefix) are consulted only when no primary signal matches.

[[nested-hosts]]*Nested hosts*: The signals are inherited, and a host started inside another clears none of the outer host's markers, so the fixed order alone attributes Claude Code started inside OpenCode to `opencode`. When the primary signals of more than one host are present, the detected host is therefore the one whose process-id marker names the nearest ancestor process of the checking `pm-operator`; the fixed order decides only among hosts for which no such marker resolves to an ancestor. Both nestings of two hosts are test cases of the detection.

[[ai-agent-mapping]]*`AI_AGENT`*: Of the four hosts only Claude Code sets `AI_AGENT` (in the form `claude-code_<version>_agent`), overwriting an inherited value. The mapped value is the prefix before the first `_` or `@` (`claude-code` -> `claude`). It is a secondary signal only, because a value inherited from an outer Claude Code survives in a host started inside it.

[[codex-environment]]*Codex environment*: Codex passes only a fixed list of variables to the MCP servers it starts (`HOME`, `PATH`, `SHELL`, `USER`, `LANG`, `TERM`, and a few more), so its markers never reach an MCP server it starts; only a command Codex runs through its shell tool, such as `pm-operator`, sees them, which is where detection happens for every host (<<host-environment-detection>>) _(provisional)_. The same signals are the host session markers that the job launcher never passes to a worker, so a harness started by the runtime never inherits the markers of the operator's host (link:../job-runtime/02-confinement-and-environment.adoc#_job_environment_pm_sec_5[Job Runtime Specification, Job Environment]).

*MCP tool names per host*: A host names the tools of the `plan-marshall` server `mcp__plan-marshall__<tool>` (`claude`), `plan-marshall_<tool>` (`opencode`), or reaches them through its built-in `call_mcp_tool` with server and tool name (`antigravity`; the direct name `mcp_plan-marshall_<tool>` was also observed in a worker's output). A role's tool set and every rendered tool reference use this form; a tool allowlist names every tool exactly, never by a wildcard (link:../model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]).

[[antigravity-environment]]*Antigravity environment*: Antigravity hands its own environment unchanged to the `stdio` server it starts and adds none of its `ANTIGRAVITY_*` variables, which it sets only for the commands it runs. Its markers therefore never reach an MCP server it starts; only a command it runs, such as `pm-operator`, sees them, as on Codex. Its tool calls carry the `_meta` keys `antigravity.google/conversation_id` and `antigravity.google/artifacts_dir`, which the server ignores.

*Shared skill directories*: `.agents/skills/` is read by `codex`, `antigravity`, and `opencode`, and `opencode` also reads `.claude/skills/`. A shim skill installed for one client in such a directory is therefore visible to the other hosts that read it.

[#host-detection-table]
*Host-detection table (compiled, `pm-api`)*: The host-detection data, that is the environment signals and their precedence and the version-probe argument vector with its pattern, is one compiled, data-only table in `pm-api` (link:../module-structure.adoc#module-pm-api[Module Structure Specification, `pm-api`]): the `detection` and `identity` objects of the profile documents, which are resources of `pm-api` (xref:01-profile-schema.adoc#harness-as-data[The Profile Is the Harness]). It is the single source and is read, never written in code: `pm-operator` (link:../module-structure.adoc#module-pm-operator[Module Structure Specification, `pm-operator`]) depends only on `pm-api` and reads the signals through its profile reader, which names no host, only for its operator checks, which refuse a verb while a coding-agent environment signal is present (link:../cli-and-security/02-credentials-and-operator.adoc#operator-channel-isolation[CLI, Coordination & Security Specification, Operator Channel Isolation]); the profile loader of `pm-core` reads the same documents whole, and the runtime runs their version probes (<<host-identity-probes>>). Operator overrides do not touch it (xref:01-profile-schema.adoc#_profile_override_hierarchy[Profile Override Hierarchy]).

*Codex tool names*: The Codex columns of the placeholder table above are _(provisional)_; in particular Codex has no `write_file` tool and writes files through `apply_patch`, so `{{tool:write_file}}` resolves to `apply_patch` like `{{tool:edit_file}}`.

*OpenCode tool names*: The `opencode` column follows `plan-marshall`'s `marketplace/targets/opencode/mapping.json` (at `969cbfeb5`). Its entry `"Write": "edit"` sits under `tool_permissions` and names the OpenCode permission category that governs writing, not the tool: the file-create tool is `write`, so `{{tool:write_file}}` resolves to `write`.

[#host-identity-probes]
==== Host Identity Probes (Normative)

The version probe of each harness is part of the Host Integration Table, compiled in the <<host-detection-table,host-detection table>>, and carried by each profile in `identity` (Normative Client Profile JSON Schema). The runtime runs it without a shell, as a confined job with a bounded timeout, and takes the first capture group of `version_pattern` over its standard output as the harness version: in the harness scan on what it finds (xref:01-profile-schema.adoc#harness-scan[Harness Scan]), at the enrolment, at a worker's spawn where the enrolled executable's digest changed (link:../store-schemas/11-enrolment-store.adoc#harness-enrolment-store[Store Schemas Specification, Harness Enrolment Store], Self-Update Within Range; the version in force at the spawn is the job record's `harness_version`, link:../model-work/04-worker-launch.adoc#launch-contract[Model Work Specification, Launch Contract]), and in the stage `identity` of the profile verification. A missing probe, a non-zero exit, a timeout, or no match yields no version, which the enrolment refuses. Values marked _(provisional)_ are verified per host like the other provisional host facts.
