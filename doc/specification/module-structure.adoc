== Overview

This document is the authoritative listing of the repositories and Maven modules of *plan-marshall-mcp* (`PM-MCP`): the repositories with their visibility and the artifacts each publishes, the aggregators, every module with its package namespace, its packages, responsibilities and allowed dependencies, the binary it builds, and the specification documents it implements. Every other document names modules only by reference to this listing and never repeats it; a module that is added, renamed or removed changes here first.

The listing is linked in both directions: the *Specified in* column of <<modules>> names the specification documents (or parts) each module implements, and every specification document names its implementing modules in its `Modules` section, linking back to the module's row here. A change to either side updates the other in the same change (link:../Specification.adoc#_traceability_requirements[Specification § Traceability Requirements]). When Milestone 1 implements the module structure, this listing moves into the module map of the developer documentation, which then takes over as the only listing (project skill `traced-implementation`).

[#repositories]
== Repositories
_Implementation watch: link:../implementation-watch/module-structure.adoc#PM-WATCH-MOD-5[PM-WATCH-MOD-5], link:../implementation-watch/module-structure.adoc#PM-WATCH-MOD-6[PM-WATCH-MOD-6]_

The product is built from five repositories of the GitHub organisation `plan-marshall`. The cut follows what a repository costs and what it must keep closed: the plain-Java modules live in repositories that stay public while the product is developed, where CI minutes, static analysis and review bots are free, and the repository that is closed first holds only the Quarkus assembly, the model-facing content and the tests that need all four binaries.

A repository listed as public is switched to private when the product is distributed; nothing in this structure depends on a repository being public. The switch changes one thing in the builds: the token with which the CI of its consumers resolves its packages (<<artifact-flow>>).

Every repository, public or private, is set up the way `cuioss/cuioss-organization` sets up a repository: its `.github/project.yml`, the reusable CI workflows pinned by full SHA, and the repository settings and the ruleset `main-branch-protection` with the merge queue applied by the scripts of that repository; the code repositories add the parent `pm-mcp-parent` and each has its own `CLAUDE.md`. All Maven artifacts carry the group id `de.planmarshall`, and every Java package and automatic module name lies below `de.planmarshall`. A module is named with its repository only in this document.

[#model-facing-content]
=== Model-Facing Content
_Implementation watch: link:../implementation-watch/module-structure.adoc#PM-WATCH-MOD-6[PM-WATCH-MOD-6]_

The mechanism may be public and the content is not: no model-facing content is committed to `plan-marshall-mcp` before that repository is private. The workflow language, the engine, the role and profile schemas and the skill rule checker are code of `pm-mcp-core`. What they run and serve is content of the private repository, packaged as classpath resources of `pm-mcp-server` and compiled into `pm-mcpd`: the default workflow units (`classpath:/workflows/`), the shipped role set with the default role assignment and its advisory (`classpath:/roles/`), the `skill://pm/**` corpus, and the client bundles (`classpath:/bundles/<client>/`). The modules of `pm-mcp-core` read these resources by their classpath location and carry none of them; their own tests run against fixture units and fixture roles in test scope. The client profiles (`classpath:/profiles/`) hold host facts and are public: they are resources of `pm-api`, read whole by the profile loader of `pm-core`. The message catalogue (`classpath:/messages/`, <<i18n>>) holds the texts of the clients and is public as well.

[#artifact-flow]
== Artifact Flow
_Implementation watch: link:../implementation-watch/module-structure.adoc#PM-WATCH-MOD-5[PM-WATCH-MOD-5], link:../implementation-watch/module-structure.adoc#PM-WATCH-MOD-7[PM-WATCH-MOD-7]_

* *One registry*: every artifact of every repository is deployed to the GitHub Packages Maven registry of the organisation `plan-marshall` (`https://maven.pkg.github.com/plan-marshall/<repository>`) and to no other place. No build deploys to Maven Central or to any other registry: the parent sets `distributionManagement` to the organisation registry and switches the Maven Central publishing of its own parent off. Third-party dependencies and `cui-quarkus-parent` are resolved from Maven Central as before, and from no other repository: the parent switches the snapshot repository of its own parent off. The coordinates of the product are resolved from the organisation registry, which is listed before Maven Central and is asked for the group `de.planmarshall` only.
* *Visibility*: a Maven package takes the visibility of the repository it is published from and follows every later switch of it. A package of a public repository can be downloaded by every authenticated GitHub account, in or outside the organisation; a package of a private repository only by an account or token with access to that repository, and every other request is answered as if the package did not exist.
* *Resolution*: the registry answers no anonymous request, for a public package either. Every developer machine and every CI job resolves through a Maven `settings.xml` that names the organisation registry (`https://maven.pkg.github.com/plan-marshall/*`) with a token: on a developer machine a personal token of an organisation member with package read permission; in CI the `GITHUB_TOKEN` of the workflow while the publishing repository is public. The `GITHUB_TOKEN` of one repository cannot read a package of another, private repository, so from the switch of a publishing repository to private on, the CI of its consumers resolves with a token that has access to that repository. The registry is named in the settings and not in a POM, because the parent POM itself is resolved from it.
* *Order*: `pm-mcp-parent` -> `pm-mcp-clients` -> `pm-mcp-core` -> `plan-marshall-mcp`. `pm-mcp-core` consumes `pm-api` of `pm-mcp-clients` (<<dependency-rules>>); the product consumes the modules of both.
* *Versions*: `pm-mcp-clients` and `pm-mcp-core` deploy `SNAPSHOT` versions only: a merge to `main` deploys the current `SNAPSHOT`, and neither repository is ever released, because an unversioned artifact is of use to the product alone. A consuming repository names each of the two by one version property in its root POM and always builds against the latest `SNAPSHOT`. Only `pm-mcp-parent` is released, since a parent is referenced by a fixed version; the registry accepts a release version once and refuses a second deploy of it. The release version of the product (`PM-DIST-1`) is the version of `plan-marshall-mcp`; every module JAR and every binary archive records the commit it was built from, and the release notes name the commits of the two upstream repositories the release was built from.
* *Propagation*: nothing is pushed from one repository of the product into another. A change merged in `pm-mcp-clients` or `pm-mcp-core` reaches a consumer with the consumer's next build, which resolves the newest `SNAPSHOT`; so that this next build does not wait for a pull request, `pm-mcp-core` and `plan-marshall-mcp` build and run their integration tests every night against the newest `SNAPSHOT` modules, and a break caused upstream shows as a failed nightly run by the next morning, not at once. A release of `pm-mcp-parent` reaches its consumers through Dependabot, whose configuration in each consumer names the organisation registry and reads it with an organisation Dependabot secret; a release of `cui-quarkus-parent` or of `cuioss-organization` opens the update pull request in each repository through the release propagation of `cuioss/cuioss-organization` across organisations, in which the repositories are listed as consumers. An immediate build of the consumers at an upstream merge is deferred (link:../later-improvements.adoc#_l_14_immediate_downstream_builds_at_an_upstream_merge[Later Improvements, L-14]).
* *Native binaries*: `pm-mcp-clients` builds `pm-mcp`, `pm-operator`, and `pm-exec` per platform and deploys each as an archive attached to its module under the platform classifier (`linux-x86_64`, `linux-aarch64`). `plan-marshall-mcp` builds only `pm-mcpd`, resolves the three other binaries by version and classifier, and assembles the release layout from them.

[#module-tree]
== Module Tree
_Implementation watch: link:../implementation-watch/module-structure.adoc#PM-WATCH-MOD-3[PM-WATCH-MOD-3]_

Every module is created when its first code arrives, each with minimal real code and tests, never an empty shell. Aggregators hold no code of their own.

[source,text]
----
pm-mcp-parent                   parent POM of all modules

pm-mcp-clients (root POM)
├── pm-api                      client contract of /api/v1
├── pm-exec                     job launcher        -> binary pm-exec
├── pm-relay                    job relay           -> binary pm-mcp
├── pm-operator                 terminal client     -> binary pm-operator
├── pm-mock-runtime             mock runtime for development and tests (never shipped)
└── pm-web-app                  SvelteKit SPA (resource JAR)

pm-mcp-core (root POM)
├── pm-core                     foundation: SPIs, contracts, stores, TOON
├── pm-workflow                 DSL, engine, hypermedia
├── pm-providers                aggregator: external integrations
│   ├── pm-provider-git              git contract, JGit + git CLI variants
│   ├── pm-provider-ci               CI contract and registry
│   ├── pm-provider-github           GitHub: ci + findings (core)
│   ├── pm-provider-gitlab           GitLab: ci + findings (core)
│   ├── pm-provider-forgejo          Forgejo and Codeberg: ci + findings (core)
│   └── pm-provider-sonar            Sonar: analysis + findings (core)
└── pm-runtime                  daemon logic without a framework

plan-marshall-mcp (root POM)
├── pm-mcp-server               Quarkus assembly, content -> binary pm-mcpd
├── pm-e2e                      release-shape end-to-end tests
└── pm-conformance              out-of-band behavioural conformance
----

[#i18n]
== Languages and Internationalisation
_See Requirement link:../Requirements.adoc#PM-ARCH-11[PM-ARCH-11: The Operator's Two Clients & Their Contract]_ +
_See Requirement link:../Requirements.adoc#PM-EXT-6[PM-EXT-6: Configuration Split by Owner Class (Team, Operator, Server State)]_ +
_See Requirement link:../Requirements.adoc#PM-IMPL-1[PM-IMPL-1: Decoupled Plain-Java Core Engine & Quarkus Assembly]_

* *Two languages, kept apart*: the *interface language* governs every text the system shows the operator (the web app, the messages and prompts of `pm-operator`, the facts a state shows); it is the machine's `language.interface`, a fact of the machine with no project value. The *model language* governs what a model is told to write and is given to read (task content, questions, answers, summaries): the project's `language.model`, else the machine's, `same` standing for the interface language (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/08-project-configuration-local.adoc#project-levels[Store Schemas § Project Values over Machine Values]). Model-facing instructions (the units' task texts, the role artifacts) stay in English whatever the model language; the launch of a worker carries the effective model language as an instruction to write in it (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/04-worker-launch.adoc[Model Work § Worker Launch]).
* *One source of texts*: every text has a key in one message catalogue per language, in `pm-api` (package `de.planmarshall.api.message`), which both the runtime and the command-line binaries depend on. A language pack is one file per language and area, `classpath:/messages/<area>.<locale>.properties` in UTF-8, an area per part of the clients (among them `decision` and `overview`). English is the complete base; every other pack is checked against it at build time: a key missing in a pack fails the build, and a key in a pack and not in English fails it too. English (`en`) and German (`de`) ship.
* *Arguments*: a message names its arguments (counts, names, values) and may select its wording by a count or a value. How the catalogue formats them is open (see link:../discussions/open-questions.adoc#message-format[Open Questions]); whatever the decision, `pm-api` keeps its one dependency rule of <<dependency-rules>> unless the operator allows another.
* *Where the texts are used*: the command-line binaries take their texts from the catalogue directly; `pm-operator` renders in the machine's `language.interface`, which the runtime status carries, and before the runtime answers in the locale the operator's environment sends, where a pack exists, else `en`. The runtime serves the catalogue to the web app per locale and area, `GET /api/v1/messages/{locale}/{area}`, and the list of the locales with a pack and their areas, `GET /api/v1/messages`; both are read only and served without a device secret, beside `POST /api/v1/pair`, so the pairing page and the start view of an unpaired browser have their texts (link:runtime-model/01-processes-and-transport.adoc#local-api[Runtime Model § Local API]). The web app holds no text of its own besides its fallback for a failed load.
* *Texts in representations*: a text of the runtime reaches a client as a message key with its arguments, never as prose; a text from outside (a provider's answer, a harness's error text, the content of a question or an answer, a reason the operator wrote, a title) is carried verbatim as an argument or a field marked verbatim and is never translated.
* *What is never translated*: command names, options, identifiers, state ids, link relations, store keys, log messages (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/LogMessages.adoc[Log Messages]), and the domain vocabulary of the glossary of the clients' design (_Request_, _Pull Request_, _Merge_, _Commit_, _Branch_, _Harness_, _Role_, _Plan_, and the others listed there) stay as they are in every language; identifiers and the commands and options of a client are the same in every language.


[#dependency-rules]
== Dependency Rules
_Implementation watch: link:../implementation-watch/module-structure.adoc#PM-WATCH-MOD-1[PM-WATCH-MOD-1], link:../implementation-watch/module-structure.adoc#PM-WATCH-MOD-3[PM-WATCH-MOD-3]_

Dependencies flow toward `pm-core`, and between repositories only in the order of <<artifact-flow>>: no module depends on a module of a repository later in that order. An automated build check in every code repository (Maven enforcer or an architecture test over the resolved dependency trees) enforces the rules below that concern its modules (`PM-IMPL-1`):

* `pm-core` depends on no other PM-MCP module except `pm-api`, whose host-detection table its client profiles read; `pm-workflow` on `pm-core` only. Neither depends on Quarkus, CDI, MCP libraries, JGit, or `cui-http`.
* `pm-provider-git` and `pm-provider-ci` depend on `pm-core`; `pm-provider-github`, `pm-provider-gitlab`, `pm-provider-forgejo`, and `pm-provider-sonar` on `pm-provider-ci` (its shared HTTP base) and `pm-core`. No provider module depends on `pm-workflow`: providers contribute primitives through the SPI in `pm-core` and never see engine internals.
* `pm-runtime` depends on `pm-core` and `pm-api` only among the PM-MCP modules (`pm-api` for the machine paths the start sequence and the credential stores share with the clients), never on `pm-workflow` or a provider module, and never on Quarkus, CDI, Vert.x, or an MCP library. It is the only module that depends on `org.commonmark:commonmark`, which its ingestion validator uses, and on LSP4J.
* `pm-mcp-server` depends on `pm-core`, `pm-workflow`, `pm-runtime`, every provider module, `pm-api`, and the resource JAR `pm-web-app`, and assembles them. It is the only module that depends on Quarkus, on `quarkus-security`, and on the Netty native transports, and no class of it exists without a Quarkus, CDI, Vert.x, or MCP type in its signature or its annotations, apart from the records those classes exchange.
* The client modules never depend on `pm-core`, `pm-workflow`, a provider module, `pm-mcp-server`, or Quarkus: `pm-relay` and `pm-operator` depend on `pm-api` only and never on each other, `pm-mock-runtime` depends on `pm-api` only and is a test-scoped dependency of `pm-operator`, and `pm-web-app` depends on no PM-MCP module (its unit tests read the scenario files of `pm-mock-runtime` from the sibling module's resources). `pm-api` depends on `jackson-core` only.
* `pm-exec` depends on no other PM-MCP module.
* `pm-conformance` and `pm-e2e` have no compile or runtime dependency on `pm-mcp-server`; they reach the product only through its built binaries. `pm-e2e` declares a test-scoped dependency of type `pom` on `pm-mcp-server`, which brings no class onto its classpath and only orders the reactor so that `pm-mcpd` is built before it is staged; the three other binaries are resolved as archives from the registry.

Provider resolution uses explicit registries (the CI registry of `pm-provider-ci` by CI provider, the findings registry of `pm-core` by the key `FindingSourceKey`, which is the store's source kind with the provider id for `analysis`, the analysis registry of `pm-core` by analysis provider) whose modules are passed to the registry's constructor: `pm-mcp-server` produces each registry through a CDI producer, and plain-Java tests construct it directly; no `ServiceLoader` or classpath discovery.

Which implementation of `pm-provider-git`, `pm-provider-github`, or `pm-provider-gitlab` serves a project is its effective integration variant (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/domain-extensions/04-setup-state-machine.adoc#setup-integration-variants[Domain Extensions Specification, Integration Variants]; link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/08-project-configuration-local.adoc#local-config[Store Schemas § Operator Local Configuration]): the project's own value, else the machine's default variant (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/12-machine-stores.adoc#provider-defaults[Store Schemas § Machine Provider Defaults]), else derived, the CLI variant where the integration's host tool is enrolled for the project or the machine and the native variant where not; a choice of the operator is required only while the effective variant cannot serve the repository. `pm-provider-forgejo` and `pm-provider-sonar` have only the native variant. One variant serves all operations of an integration, it is fixed for a running plan, and no operation falls back from one variant to the other (`PM-EXEC-5`).

[#findings-analysis-contracts]
== Findings & Code-Analysis Contracts

The findings and code-analysis contracts are provider-neutral and live in `pm-core` (packages `de.planmarshall.core.findings` and `de.planmarshall.core.analysis`), not in provider modules of their own, because their data is part of the foundation: the findings store persists the normalized findings (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/03-findings-and-review-records.adoc[Store Schemas § Findings & Review Records]), and the composite wait in `pm-workflow` evaluates the `analysis_status` dimension, so neither `pm-core` nor `pm-workflow` could reach them in a provider module. `core.analysis` depends on `core.findings` and never the reverse.

* *Scope*: `FindingScope(kind, commitSha, prNumber)`, a commit (`commit`, with its commit id) or a pull request at a commit (`pull_request`, with its number and head commit). It is the scope of `FindingSource.fetch` and the target of the analysis result and of both analysis operations.
* *Findings*: the normalized finding `Finding`, one record with the members of the findings ledger record (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/03-findings-and-review-records.adoc[Store Schemas § Findings Ledger Record]), and two contracts a provider module implements:
** `FindingSource` with `FindingSourceKey key()` and `List<Finding> fetch(FindingScope scope)`;
** `FindingResponder` with `FindingSourceKey key()` and `void respond(Finding finding, Disposition disposition, String reason)`, where `Disposition` is `FIX`, `ACCEPT`, or `SUPPRESS`.
+
Both are registered under the key `FindingSourceKey(kind, provider)`: `kind` is a value of the findings store's closed `source` vocabulary (`FindingSourceKind`), and `provider` is the id of the code analysis provider for `analysis` and absent for every other kind. The key mirrors the invariant of the store, so a finding is fetched and answered under the key it is stored under, and two analysis providers are two keys. The findings registry `FindingRegistry` holds at most one source and one responder per key and answers an unregistered key as empty. A finding of a code analysis provider carries `source: analysis` and the provider's id. Implemented by `pm-provider-github`, `pm-provider-gitlab`, and `pm-provider-sonar`.
* *Code analysis*: one provider kind of its own, the *code analysis provider* (Sonar, CodeQL, and others), which is not a CI provider. Its base has three parts, all in `de.planmarshall.core.analysis`:
** *Format*: the analysis result record `AnalysisResult` with its canonical JSON serialization `AnalysisResultCodec` (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/03-findings-and-review-records.adoc#analysis-result[Store Schemas § Analysis Result Record]): provider, target, the status mapped to the closed wait dimension `analysis_status` (`AnalysisStatus`), the quality gate result with its conditions, and the issue counts. New issues are findings with `source: analysis` and the provider's id; no store schema names a single provider.
** *Interface*: `CodeAnalysisProvider` with `String id()`, `AnalysisCallResult<AnalysisResult> status(FindingScope target)`, and `AnalysisCallResult<List<Finding>> issues(FindingScope target)` returning the provider's open issues on new code as normalized findings; and the registry of providers by id, `CodeAnalysisProviderRegistry`, which answers an unregistered id as empty (not an outcome). The result of a call, `AnalysisCallResult<V>(outcome, value, completeness)`, carries the closed outcome `AnalysisOutcome` (`ok` and the transport outcomes of the table below), the value for `ok` only, and the completeness `Completeness` (`complete`, `incomplete`) for an `ok` result of `issues` only. A provider is one implementation of this interface and needs nothing else: no new status value, no schema change, no change of the engine.
** *Contract*: each of the two reads is an operation contract like those of git and CI (`PM-IMPL-1`):
+
[cols="2,3,3,3"]
|===
|Operation |Input |Outcomes |Output

|`analysis.status`
|provider id; target (`commit` with its commit id, or `pull_request` with its number and head commit)
|`ok`, and the shared transport outcomes of link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/job-runtime/01-pipeline-and-subprocesses.adoc#outcome-derivation[Job Runtime § Outcome Derivation] (`auth_failed`, `permission_denied`, `provider_unavailable`, `malformed_response`)
|the analysis result record; a transport outcome yields no record and counts as `undecidable` in the wait

|`analysis.issues`
|provider id; target
|`ok` with `completeness: complete \| incomplete`, and the same transport outcomes
|normalized findings (`source: analysis`, `provider`, `provider_ref.issue_key`); `incomplete` makes the observation's `count_status` `indeterminate`
|===
+
An analysis provider has only a native variant and acts with its Token-Lane credential (link:cli-and-security/02-operator-channel.adoc[CLI & Security § Credentials & Operator]). Both outputs are rendered to TOON at the wire only where an operator surface serves them; a model-facing representation carries the aggregated `analysis_status` and nothing else of them. Implemented by `pm-provider-sonar`.

Nothing in `pm-core` names a provider. A class names a provider when it depends on a provider package (`de.planmarshall.provider..`) or when its name, its package name or the name of one of its members contains `github`, `gitlab`, `forgejo`, `sonar`, or `codeql`, ignoring case. The single exemption are the two constants `GITHUB_PR` and `GITLAB_MR` of `FindingSourceKind`: they are the values `github_pr` and `gitlab_mr` of the store's closed `source` vocabulary and name the kind of producer of a finding, not a provider identity; a member of the same name in any other type is not exempt. The two packages hold declarations, serialization and validation only: no class of them depends on a network or HTTP type (of `java.net` only `URI`), writes, creates, moves, copies or deletes a file, or depends on `de.planmarshall.core.store`. A build test of `pm-core` enforces both rules.

The CI contracts stay in the provider module `pm-provider-ci`, because they carry the shared HTTP base over `cui-http`, which `pm-core` must not depend on.

[#test-placement]
== Test Placement

* *Unit tests*: every module carries its own JUnit 5 suite and meets the coverage minimum on its own. The plain-Java library modules (`pm-api`, `pm-exec`, `pm-core`, `pm-workflow`, `pm-runtime`, the provider modules) run them on the JVM without Quarkus augmentation.
* *Integration tests* (`*IT`, `-Pintegration-tests`), four layers: `pm-mcp-server` (packaged daemon over MCP/HTTP on its Unix socket, including the web listener and pairing), `pm-relay` (the `pm-mcp serve --job` relay over real `stdio` against the stub MCP endpoint of its test scope), `pm-operator` (operator verbs against the mock runtime `pm-mock-runtime` with its scenarios), and `pm-e2e` (all four binaries in the release layout, the only layer in which the client binaries meet the real `pm-mcpd`). The MCP protocol layers (McpAssured) are the server and the end-to-end layer, which runs the relay against the real daemon; the relay layer of `pm-mcp-clients` verifies the forwarding against its stub, and the `pm-operator` layer serves no MCP (link:mcp-tools/04-errors-and-testing.adoc[MCP Tools § Errors & Protocol Testing]).
* *Native reflection*: a build test in `pm-mcp-server` verifies that every persisted record of `pm-core`, `pm-workflow`, `pm-runtime`, and the provider modules is registered for GraalVM native reflection.
* *Scenario replay* (`pm-scenario`, `PM-TEST-4`): test scope of `pm-workflow`, not a module.
* *Behavioural conformance* (`PM-TEST-6`): `pm-conformance`, out of band.

[#module-cuts]
== Module Cuts

A module exists where it separates a dependency boundary, a build type, or a binary; a subject area alone does not justify one.

* `pm-workflow` is separated from `pm-core` because the workflow language and the process it runs form the largest body of logic with its own verification (grammar, static verifier, property tests, drift tests, scenario replay), and the separation keeps the provider modules away from engine internals: they build against the foundation in `pm-core` only.
* The findings and code-analysis contracts are part of `pm-core` rather than provider modules of their own (<<findings-analysis-contracts>>): they are interfaces and registries without an external dependency, and their data belongs to the store and the workflow. A provider module is cut only where it holds an implementation or a dependency the foundation must not have (`pm-provider-git` with JGit, `pm-provider-ci` with its `cui-http` base, the provider adapters).
* The stores, configuration, domain extensions, client profiles, and parsers stay together in `pm-core`: each is consumed by the engine and by the assembly alike, none has a dependency the others lack, and splitting them would only add modules without a boundary to enforce.
* The CLI is cut in two modules by caller, not by subject: `pm-relay` builds `pm-mcp` with the one verb a worker's harness runs (`serve --job`), `pm-operator` builds the terminal client with every verb a human runs at a terminal. The cut makes the host deny rule a whole binary: a bundle denies `pm-operator` to the model as one executable and allows only `pm-mcp serve`, instead of sub-command rules inside one binary that every new verb would have to be sorted into. What the two share (the socket client and the codecs) lives in `pm-api`, their only dependency, beside what only the terminal client uses (the on-demand start, the direct file reads with the drift checks, the host-detection table, the message catalogue).
* The web adapter is a package of `pm-mcp-server`, not a module and not a binary: it has no dependency the daemon lacks (the second HTTP server is the daemon's own Quarkus/Vert.x stack) and no build type of its own, and the device store, the pairing codes, and the device-secret check it needs already live in the daemon. Only the web app is a module (`pm-web-app`), because its build type differs (npm, resource JAR).
* Model work is cut by what each part depends on: the role sets and the task queue store live in `pm-core` with the other stores and configuration, because the client profiles that validate a role and the lock order of the queue are there; the model caller and the task protocol unit live in `pm-workflow`, because they are workflow logic over persisted records; the supervisor lives in `pm-runtime` beside the job runner, because it starts, signals, and observes processes, which neither of the two may do.
* `pm-runtime` is separated from `pm-mcp-server` by the framework boundary: whatever the daemon does without a Quarkus, CDI, or Vert.x type is library code with plain JUnit tests in a public repository, and the assembly is the wiring that remains. It is separated from `pm-core` because it starts processes and carries dependencies the foundation must not have (LSP4J, `commonmark`, `cui-http`), and from `pm-workflow` because the engine decides and the runtime executes: the engine reaches it only through the service interfaces of `pm-core`.
* The repositories are cut along the two seams the dependency rules already draw. `pm-mcp-clients` holds what depends on `pm-api` at most; its wire contract changes rarely, so the step from one repository to the next costs little there. `pm-mcp-core` keeps `pm-core`, `pm-workflow`, the providers, and `pm-runtime` together, because most changes of the engine cross these modules and a repository boundary between them would turn each into two releases. The parent is a repository of its own so that a change of the shared build configuration is one release every repository takes, and the documentation is one, because a document describes modules of all of them.
* The hypermedia state engine stays in `pm-workflow`: it renders the links of the current workflow state and cannot be separated from the interpreter; only the generic TOON encoder, which the providers also use, lives in `pm-core`.
