== Server-Driven Scopes
_See Requirement link:../../Requirements.adoc#PM-ARCH-8[PM-ARCH-8: Server-Driven Continuation & Connection Independence]_

A scope is identified by its `plan_id` (or `epic_id`, or the project's workspace scope, addressed by the reserved `plan_id` value `NO_PLAN`, or the machine's one scope) and consists of its persisted files (`status.json`, the plan's history, and the stores in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas.adoc[Store Schemas Specification]). Nothing else carries workflow state: not a client of the operator, not a relay, not a worker, not the MCP transport, and not runtime memory, which is a cache that is revalidated against the files (`PM-ARCH-6`).

The runtime drives every plan and epic from its creation to a terminal state itself (`PM-ARCH-1`). It advances a scope on transitions and on engine events (a job's completion, a task's outcome, a deadline, an observed provider state, an act of the operator), never because a connection calls. A state that needs no model is server logic; a state that needs a model puts a task of the role it names into the task queue, which a worker of that role does along the links of the task's entity (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]); a state that needs the operator is an operator wait, served to both clients of the operator, which halts its own scope and nothing else (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]). An epic starts its launchable plans itself where its automatic mode is on (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/08-epic-coordination.adoc[Model Work Specification, Epic Coordination]). A plan or epic representation on the MCP surface is therefore a view whose `links` list is empty; the operator's links of an operator wait are operator endpoints of the local API (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/hypermedia-format/01-representation-and-link-forms.adoc#operator-links[Hypermedia Format Specification, Operator Links]).

=== Worker Connections
_See Requirement link:../../Requirements.adoc#PM-WORK-2[PM-WORK-2: Task Protocol]_

A worker connection is bound to its job and generation by the job token (link:01-processes-and-transport.adoc#job-token[Local Trust: Job Token]): its tool set is that of its role's class, its links are those of the task entities leased to its generation, and its resource reads are read-only within its own project (link:../mcp-tools/01-core-workflow-tools.adoc#job-bound-connections[MCP Tools Specification, Worker Connections]). Its audit records carry its `job_id`, role, and generation (`PM-SEC-6`). The supervisor watches it by the process, the acknowledgement, its calls, and its activity, never by the transport (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/03-supervision-and-recycling.adoc[Model Work Specification, Supervision & Recycling]).

=== Call Cycle

Every scoped call (`pm_state`, `pm_do`, `pm_build`, `pm_lsp`) and every `pm_wait` executes as:

. *Bind the connection*: Resolve the job from the token and check, in this order, the job and the generation: an ended job is refused `job_ended` (a worker's generation is fenced when its job ends, so this check comes first), a fenced generation of a running job `generation_fenced`, a task whose lease the generation held and released at the task's close `stale_entity` (with the entity's representation), and any other scope or entity that is not a task entity leased to the generation `job_scope_mismatch` (link:../mcp-tools/04-errors-and-testing.adoc[MCP Tools Specification, Errors]). The scope is the one of the leased task: a plan or an epic by its id, the project's workspace scope (`plan_id: NO_PLAN`, with its home `<PM_MCP_BASE>/projects/<project_id>/workspace/`, link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/filesystem-layout/03-project-store.adoc#workspace-home[Filesystem Layout Specification]), or the machine scope for a task of the machine scope (`PM-ARCH-4`).
. For mutating calls, acquire the scope lock (`PM-WF-4`) and load the current state from disk, discarding stale cache entries.
. Validate the link and arguments against the persisted state (`PM-WF-6`) and, on a task entity, against the lease and the generation (`PM-WORK-2`).
. Execute exactly one transition, including any auto-steps it chains, and persist all resulting state atomically before releasing the lock.
. Render the new representation with the links of the leased task entity for its generation, using the client profile of the worker's harness and the connection's capabilities.

Because the transition is persisted before the response is produced, the files always reflect every call whose effects happened, whether or not its response reached the caller. What follows a task's submission (the next state, the next task, a job) is the engine's work, not the caller's. An act of the operator over the local API runs the same cycle: bound to its channel and device instead of a job, validated against the state it acts on, and answered with the new state in the operator representation.

=== Continuation

* *By the server*: Plans and epics continue through engine events, tasks, and the operator's acts; no transition depends on a client or a worker being connected, and a job or task may complete while no client is open.
* *Viewing*: Either client views any scope over the local API at any time, with identical results for identical persisted state; a client that was closed reads its scopes again and, through the reports, learns what happened meanwhile (link:01-processes-and-transport.adoc#reports[Reports to the Operator]).
* *After worker replacement*: A successor worker starts with an empty context and receives the task again; nothing is handed over, because every task carries what its state needs (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]).
* *Concurrency*: Any number of workers and both clients may address the same scope concurrently. Concurrency is resolved by the scope lock and entity-scoped links (`PM-WF-4`); replayed or stale links are rejected with the current representation (`PM-TOOL-4`), every call of a fenced generation is refused, and of two operator acts on the same decision or recorded value the first valid one wins (link:01-processes-and-transport.adoc#local-api[Local API], Operator endpoints).

=== Connection-Scoped Rendering

Some rendering decisions depend on the calling worker connection, not on the scope:

* *Waiting*: The calls a model holds open are a worker's `pm_wait` and a running `pm_build` (`PM-IMPL-4`). A `pm_wait` always holds for at most `connection.bounded_wait_seconds`, with progress frames during it where the harness's timeout is reset by progress; a `pm_build` uses a progress wait only when the connection declared progress support, supplied a `progressToken`, and the client profile states that progress resets the harness's timeout (`connection.progress_resets_timeout`), and otherwise a bounded wait within `connection.bounded_wait_seconds` (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/timeouts/01-job-budgets-and-waits.adoc#bounded-wait[Timeouts & Budgets Specification]; link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/client-profiles/01-profile-schema.adoc[Client Profiles Specification, Profile Schema]).
* *Skill activation*: A connection whose harness declared the client capability of the MCP Skills Extension gets offers that name skills by URI and digest only (host activation); every other connection gets the required skills in-band (link:../mcp-tools/02-service-and-skill-tools.adoc[MCP Tools Specification, Skill Tools]).
* *Client profile*: A worker's calls render with the profile of its role's harness, recorded in its job record.

No rendering depends on the operator: what the operator is asked is never part of a worker's representation, and MCP elicitation is never used. The same scope may render differently for two connections at the same moment without any difference in persisted state.

=== Long-Running Work

Jobs run in the runtime, independent of any call. The engine awaits a job's completion as an event and advances the scope; a composite wait settles or short-circuits the same way, and cancelling a job is the engine's act, a pause's with the point _now_, or the effect of an operator act that ends the scope (`PM-WF-8`, `PM-WF-9`). No model polls or cancels a job; the plan's view shows a running job's progress. The only exception is `pm_build`, which continues a running build by its own `job_id` within the same bounded window (`PM-TOOL-2`).

== Failure Semantics

[cols="2,3"]
|===
|Event |Behaviour

|A worker's harness closes its relay (`stdin` EOF, `SIGTERM`, `SIGKILL`)
|The relay closes its runtime connection and exits. The runtime holds no state for the connection. Plans, epics, jobs, locks held by in-flight transitions (released at transition end), and persisted state are unaffected; the supervisor sees the worker's exit or silence and acts on it (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/03-supervision-and-recycling.adoc[Model Work Specification, Supervision & Recycling]).

|A harness kills and restarts a relay mid-task
|The new relay reads its token and generation from its environment again and binds to the same generation (link:03-relay.adoc#_generations_at_the_relay[Relay, Generations at the Relay]); the worker continues its task. A held call of the old relay is lost; the worker calls again.

|A worker's process exits, stalls, or stops acknowledging
|The supervisor ends it, fences its generation, revokes its job token, releases its lease at once, and offers its task to a successor exactly once; a worker that exits before its first call is a start failure (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/03-supervision-and-recycling.adoc[Model Work Specification, Supervision & Recycling]).

|Relay dies while a call is in flight
|The runtime completes and persists the transition; only the response is lost. An offer whose response is lost stays leased: the worker's next `pm_wait` receives the same offer again under the same lease (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/02-task-protocol.adoc#ack[Model Work Specification, Acknowledge]). A worker that makes no such call before its acknowledgement deadline (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/timeouts/01-job-budgets-and-waits.adoc#ack-deadline[Timeouts & Budgets Specification]) is ended and its task offered to a successor, except where its harness's acknowledgement is informational, where its silence limit (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/timeouts/01-job-budgets-and-waits.adoc#silence-limit[Timeouts & Budgets Specification]) decides.

|Runtime not running when a relay starts or reconnects
|A worker relay never starts the runtime. While the socket does not accept connections, the relay answers pending requests with `runtime_unavailable` (link:03-relay.adoc#relay-rules[Relay Rules]) and keeps retrying on subsequent requests. A worker whose runtime stopped is settled `killed` by the next start's recovery.

|A client of the operator finds no runtime
|`pm-operator` starts it on demand (link:01-processes-and-transport.adoc#_start_modes[Start Modes]); a browser gets a refused connection until the next runtime start opens the web listeners again. Because the runtime keeps no session, a request after a restart is served normally; an event stream reconnecting gets `reset`.

|Runtime crashes during a transition
|Atomic write-and-rename guarantees each store is either fully updated or unchanged, and the scope's transaction journal makes a multi-store transaction complete by roll-forward. The relay answers the in-flight request with `runtime_unavailable`; after restart, the project's recovery completes before its first call is served (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/runtime-lifecycle/01-startup-recovery-drain.adoc#per-project-recovery[Per-Project Recovery]).

|Runtime crashes while jobs and workers run
|After the next start, the project's recovery terminates the orphaned jobs and workers if still alive, records them `killed`, fences the worker generations, and returns their leased tasks to the queue, each offered again exactly once (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/runtime-lifecycle/01-startup-recovery-drain.adoc#per-project-recovery[Per-Project Recovery]); a paused plan stays paused.

|Runtime draining
|New calls receive representations with `facts.runtime: draining`, and no new task is offered; both clients show the drain and its deadline. After the exit, the next `pm-operator` command that needs the runtime brings up a new runtime, unless the drain was a restart, whose successor starts by itself (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/runtime-lifecycle/01-startup-recovery-drain.adoc#runtime-lifecycle-operations[The Runtime's Lifecycle]).

|Runtime stops or crashes while web access is enabled
|The web listeners end with the runtime: open browser streams end, and a browser gets a refused connection until the next runtime start opens the listeners again. Paired devices and the `web` setting are unaffected.
|===

== Client Interaction

Only the worker relays (`pm-mcp serve --job`) call the runtime's MCP endpoint; no command of `pm-mcp` or `pm-operator` writes a store. Every command of the terminal client that reads or changes state (the entry, the operator's views, waits, and acts, `pm-operator client` install records, `pm-operator web` pairing and devices, `pm-operator status`) is a request to the link:01-processes-and-transport.adoc#local-api[Local API], executed by the runtime as a locked, journaled, audited transaction; its effect reaches both clients through the event streams. A damaged store blocks only its scope or project, so repair acts run through the runtime as well. Only `pm-operator status` and `pm-operator system` (runtime not running), `pm-operator drain`, `pm-operator runtime stop`, and `pm-operator client status` work without a running runtime, and none of them writes (link:01-processes-and-transport.adoc#local-api[Local API], Availability).

[#cli-direct-reads]
*Files the client binaries read directly*: `pm-operator` reads files of `<PM_MCP_BASE>` only from this closed list and never writes any of them: `state/runtime.json` (liveness and the version check), `run/runtime.token` (authentication, under the client check of link:01-processes-and-transport.adoc#runtime-token[Local Trust: Runtime Token]), `state/install-records.json` with the target files recorded there (the drift check of `pm-operator client status`), and `machine-config.json` (the drain bound of `pm-operator drain`, and `language.interface` while no runtime answers). The worker relay reads none of them: its token comes from its environment. The terminal client's own files (its history and the overview's selection) live in its own state directory outside `<PM_MCP_BASE>`, are written only by it, and hold no state of the runtime. The normative list is link:../cli-and-security/01-cli-and-installer.adoc#cli-file-reads[CLI, Coordination & Security Specification, Direct file reads]. The read-only codec for these files, the client over the Unix socket, the on-demand start procedure (link:01-processes-and-transport.adoc#_start_modes[Start Modes]), and the drift check live in the contract module `pm-api`. The only lock a client binary takes is `runtime-start.lock`. Details of each verb are in link:../cli-and-security.adoc[CLI, Coordination & Security Specification].

== Verification
_Implementation watch: link:../../implementation-watch/runtime-model.adoc#PM-WATCH-RUN-3[PM-WATCH-RUN-3]_

* *Relay integration tests (`*IT`)*: `McpAssured.newStdioClient()` spawns `pm-mcp serve --job` with an isolated `PM_MCP_BASE` and the token and generation of a worker job the test's runtime launched for the fixture harness, against a runtime the test started before. Tests cover `id` preservation, the job token on every forwarded request (a request without it or with an unknown one is refused with `401`; a revoked one is answered `generation_fenced` or `job_ended`), the `Mcp-Method` and `Mcp-Name` headers on every forwarded request, both host protocol forms (`server/discover` with per-request `params._meta`, and `initialize` without a session in the response), a `subscriptions/listen` that is acknowledged at once and whose stream carries no further message while tool calls are served on other requests, and progress forwarding. The `McpAssured` STDIO client waits at most 10 s per response (its Awaitility default, without a setter).
* *Relay rule tests*: A notification for which the runtime's transport returns a body writes nothing to `stdout`; a killed runtime makes the relay answer every held request with `runtime_unavailable` within one second (a test bound of this check, not a runtime timeout); a `notifications/cancelled` for an answered request is dropped and changes nothing; a `tools/list` result shows no property of the identity set, and an identity argument a client sends is not forwarded; a relay killed under a held `pm_wait` and started again with the same environment binds the same generation; `pm-mcp serve` without `--job`, or without a job token in its environment, exits at once.
* *Runtime restart tests*: Kill the runtime during an active job, a leased task, and a pending transition; verify the job and worker are recorded `killed`, their generations fenced, their tasks offered again exactly once, stores consistent, and the plan continuing without a client; a paused plan stays paused and a pausing plan holds at its point.
* *Lifecycle tests*: A stop with `now` settles running work as after the drain timeout; a withdrawn drain returns to `running` and admits work again, and a withdrawal after the wait ended is refused `not_withdrawable`; a restart starts the successor, which takes the singleton lock after the predecessor's exit; an upgrade to a release whose `pm-mcpd` does not answer switches the links back, starts the previous version, and records `runtime.upgrade_failed`.
* *Pause tests*: a pause with each point holds where its point names (`after_phase` also when the phase ends in a loop-back), a pause with `now` withdraws a running task and offers it again on start without spending its re-offer budget, a paused plan holds no slot and is never reported `stalled`, and an answer to an operator wait of a paused plan is recorded and taken on start.
* *Startup order tests*: A second runtime started against a live one exits `0` at once and leaves `<PM_MCP_BASE>` byte-identical (no audit record, `runtime.json` and the socket unchanged); a stale socket and `runtime.json` left by a killed runtime are removed only after the lock is acquired; a restarted runtime writes a new `runtime.token` before its socket accepts a connection; a call addressing a project whose recovery exceeds the project recovery wait returns `runtime_recovering`, and the repeated call after recovery is served.
* *Socket path length tests*: A `PM_MCP_BASE` long enough to push `run/runtime.sock` over the platform `sun_path` limit makes the start refuse with a diagnostic naming the path on `stderr` and in `audit.jsonl` and with exit code `77`; no socket, token, or `runtime.json` is written, and nothing is created in the system temporary directory.
* *Cold-start measurement (`PM-TECH-3`)*: The ≤ 50 ms target is measured from process start to the socket accepting connections (step 7 of link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/runtime-lifecycle/01-startup-recovery-drain.adoc#_startup_sequence[Startup Sequence]) on a clean state (empty `PM_MCP_BASE`, no stale files, no projects to recover), excluding every per-project recovery.
* *First-request measurement (`PM-TECH-3`)*: Against a running runtime, the relay forwards the harness's first request, and every command of `pm-operator` sends its first request, within ≤ 50 ms of process start.
* *Idle memory measurement (`PM-TECH-3`)*: The resident set size of a fresh idle `pm-mcpd` (started on a clean state, socket bound, measured 10 s after ready, before any job, worker, git or provider operation, or language server has run) is ≤ 64 MB, excluding child jobs and language servers. The same test records the idle resident set size after work (after one and after two runs of the native git scenario, each followed by an idle period) without asserting a bound: the bound of a working runtime is set from these records together with the job runtime (link:../evaluation.adoc#platform-values[Evaluation Reference, Runtime per Platform]).
* *Isolation tests (`PM-TEST-5`)*: Verify that the runtime opens no TCP/UDP listener while web access is disabled (under listener fallback (1) only the loopback listener of link:01-processes-and-transport.adoc#_transport_endpoint[Transport Endpoint]), that the socket, `runtime.token`, and their directory have modes `0600`/`0600`/`0700`, that a client refuses a `run/` directory or token file with a foreign owner, a broader mode, or a symlink, that `/api/v1` refuses a request without the runtime token and `/mcp` one without a job token, that the runtime token is refused on `/mcp` and a job token on `/api/v1`, that the token appears in no log, audit record, or job environment, that a job cannot read `run/runtime.token` under Landlock, that a worker reads its own `run/jobs/<job_id>/` and neither writes it nor reads another job's, that `resources/read` on a worker connection serves a resource of the worker's project and refuses one of another project (`-32002`, `scope_not_found`), that a worker connection is refused `job_scope_mismatch` for a scope or entity not leased to its generation, `generation_fenced` after its generation was fenced, and `job_ended` after its job's fate (a revoked token is never answered `401`; an unknown or malformed one always is), and that every line the relay writes to `stdout` is a valid JSON-RPC 2.0 message.
* *Web listener tests*: With web access enabled the runtime opens the loopback listener on `127.0.0.1` and, when the LAN listener is opened, the LAN listener beside it, without closing the loopback one; on each `/mcp` and every path outside the web app and `/api/v1/` are unreachable, the runtime token and a job token are answered `401`, a device secret is checked on every request (a revoked one is refused on the next, and the device's open streams end with `stream.closed`), and a device secret is refused on the Unix socket; a loopback-only endpoint is refused `loopback_only` on the LAN listener, also when the request names a loopback address there; closing the LAN listener from a paired device leaves the loopback listener open, while a running job continues; a restart with web access enabled opens the listeners again, and a drained runtime leaves no listener behind.
* *Event stream tests*: every event a scenario produces is in the catalogue with its payload schema (link:06-event-catalogue.adoc[Event Catalogue]); a client reconnecting with a held `Last-Event-ID` receives exactly the events after it, and one reconnecting after a runtime start receives `reset`.
* *CLI availability tests*: With no runtime running, `pm-operator status` and `pm-operator system` report "not running", `pm-operator runtime stop` reports that there is nothing to stop, and `pm-operator client status` reports the install records, all without starting a runtime or writing a file; `pm-operator drain` exits `0`; every other command starts the runtime on demand and reports `running` only after an authenticated round trip; `pm-operator drain` never signals a process whose start instant differs from `runtime.json`.
* *Stalled tests*: An aged fixture (a non-terminal plan without pending condition or awaited event whose last transition is older than the stalled threshold) is reported as the hold `stalled` with cause `no_progress` in both clients and on the event stream, produces exactly one `plan_stalled` record per episode, and changes no model-facing representation; a plan in an operator wait is shown as waiting for the operator, and a paused plan by its activity, never as `stalled`.
* *Technical verification* (the techniques below are confirmed, link:../evaluation.adoc#results[Evaluation Reference]; each is re-verified by its integration tests on every platform and before a Quarkus or `quarkus-mcp-server` upgrade):
** The Quarkus HTTP server with `quarkus-mcp-server-http` and the `/api/v1` resources bound to a Unix domain socket under GraalVM native image on macOS and Linux, using the Netty native transport (`kqueue`/`epoll`), with the runtime-token and job-token authentication mechanisms, the security identity built from the connection metadata and read in a tool handler, SSE streaming, stale-socket handling, and the refusal of an over-long socket path; no listener fallback of link:01-processes-and-transport.adoc#_transport_endpoint[Transport Endpoint] is in use.
** The HTTP/1.1 and SSE client of `pm-api` over the JDK's `UnixDomainSocketAddress` `SocketChannel` in the plain native images of `pm-mcp` and `pm-operator` with picocli, and the startup budgets of `PM-TECH-3` for the relay and the other commands of both binaries.
** Further Vert.x HTTP servers on TCP beside the Unix-socket listener in the native image, opened and closed while the runtime runs, with their own route restriction (the web app and `/api/v1/` only, never `/mcp`) and TLS on the LAN listener, and the shared Quarkus Security chain and identity providers, in which each listener accepts only its own token kind (link:01-processes-and-transport.adoc#_transport_endpoint[Transport Endpoint], Web listeners).
** Detached start via FFM `posix_spawn` with `POSIX_SPAWN_SETSID` on both platforms.
** The real `pm-mcp serve --job` under every relay rule of link:03-relay.adoc#relay-rules[Relay Rules] on every eligible harness, with confined writer workers (`PM-WORK-2`, `PM-WORK-3`).
