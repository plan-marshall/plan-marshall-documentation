== Startup Sequence
_Implementation watch: link:../../implementation-watch/runtime-model.adoc#PM-WATCH-RUN-9[PM-WATCH-RUN-9], link:../../implementation-watch/runtime-model.adoc#PM-WATCH-RUN-14[PM-WATCH-RUN-14], link:../../implementation-watch/runtime-model.adoc#PM-WATCH-RUN-17[PM-WATCH-RUN-17]_

The steps run in this order; each later step runs only while the runtime holds the singleton lock. Steps 1 to 5 run in the runtime's `StartupEvent` observer, which Quarkus runs before its HTTP server binds the socket, so nothing can connect before the token exists; steps 6 and 7 follow the bind.

. *Singleton lock*: Acquire `<PM_MCP_BASE>/locks/runtime.lock` (link:01-processes-and-transport.adoc#_singleton_discovery[Singleton & Discovery]). A runtime that loses exits without writing anything, audit records included.
. *Stale-socket cleanup*: While holding the singleton lock, and never before, remove a stale `run/runtime.sock` and the stale `state/runtime.json`. Holding the lock proves that no live runtime owns them; a runtime that removed them without the lock could unlink the live holder's socket.
. *Directory & permission verification (`PM-SEC-4`)*: First the runtime creates the directories `run/`, `enrolments/`, `state/`, and `logs/` of `<PM_MCP_BASE>` where they are absent (mode `0700`, under `umask 077`; a client's on-demand start has created `logs/` before the spawn, link:01-processes-and-transport.adoc#_start_modes[Start Modes]); an existing directory is checked, never repaired. Then `<PM_MCP_BASE>`,`<PM_MCP_BASE>/enrolments/`, and `<PM_MCP_BASE>/run/` must be owned by the effective UID with mode `0700` and must not be symlinks, and `state/*` must be `0600`. Violations are written to `stderr` and `audit.jsonl` and the runtime exits with code `77` (`EX_NOPERM`). In the same step the length of the socket path is checked against the platform's `sun_path` limit; a path over it refuses the start like every other violation of this step (the diagnostic of link:01-processes-and-transport.adoc#_singleton_discovery[Singleton & Discovery], Socket, Path length, on `stderr` and in `audit.jsonl`, exit code `77`), before a token is written or a socket bound. A single enrolment file is not part of this check: its permissions and integrity are verified per project (<<per-project-recovery>>), and a failure blocks only that project. Credential files under `<PM_MCP_BASE>/credentials/` are not part of this check: an insecure credential file blocks only the step that needs it (`PM-CRED-4`, link:../cli-and-security.adoc[CLI, Coordination & Security Specification]).
. *Bounded verification*: The step, with its seam for the audit chain, the `audit_chain_broken` record of a broken chain that is never repaired and never stops the start, and no store or unit work, is implemented (link:../../concepts/runtime-lifecycle.adoc#startup[Concepts § Startup]). Remaining: the audit chain verification (`PM-SEC-6`) that the audit trail fills the seam with verifies the HMAC-anchored head `logs/audit.head`, the rotation index, and the `prev_hash` chain of `logs/audit.jsonl` from its last checkpoint (incremental; a full verification is the operator command `pm-operator audit verify`), and a broken chain is also reported on `stderr` and in `pm-operator status`. A project's workflow units are verified when they are loaded (link:../workflow-dsl/04-ast-node-model.adoc#project-owned-units[Workflow DSL Specification, Project-Owned Workflow Units], `PM-IMPL-5`), and a failure refuses only that project's plan lifecycle; every store's `format_version` is checked when it is read, and a mismatch refuses only what reads it (link:../store-schemas/01-format-and-session-log.adoc#format-versioning[Store Schemas Specification, Format Versioning]).
. *Runtime token*: Write a fresh runtime token to `run/runtime.token` (link:01-processes-and-transport.adoc#runtime-token[Local Trust: Runtime Token]), replacing the previous instance's token, before anything can connect.
. *Bind the socket*: Bind the socket path (link:01-processes-and-transport.adoc#_singleton_discovery[Singleton & Discovery], Socket), restrict the socket created under the process `umask` to mode `0600` and verify its owner, mode, and file type (a failed check exits with code `77` like step 3), and only then write `state/runtime.json` with it.
. *Ready*: Begin accepting connections and start the background recovery pass over all enrolled projects (<<per-project-recovery>>). A project's supervisor starts workers only after its recovery has finished.
. *Web listener*: When `web.enabled` of `machine-config.json` is `true`, open the web listener with the recorded `web.lan` and `web.port` (link:01-processes-and-transport.adoc#_transport_endpoint[Transport Endpoint], Web listener). An occupied port leaves it closed, is reported by `pm-operator status`, and never stops the start or the socket listener; another port is never chosen.

The cold-start target of `PM-TECH-3` (≤ 50 ms) covers steps 1 to 7 on a clean state: socket bound and ready, without any per-project recovery and without the web listener, which is off by default.

[#per-project-recovery]
=== Per-Project Recovery
_Implementation watch: link:../../implementation-watch/model-work.adoc#PM-WATCH-DISP-61[PM-WATCH-DISP-61]_

The per-project crash recovery (`PM-ARCH-7`) with its two triggers after bind, its once-per-instance rule, its bounded wait, its restriction to enrolled projects, and its step order is implemented (link:../../concepts/runtime-lifecycle.adoc#per-project-recovery[Concepts § Per-Project Recovery]); the runtime wires it to the bind and to its calls. The answer on expiry of the wait is the retryable error `runtime_recovering` (link:../mcp-tools/04-errors-and-testing.adoc[MCP Tools Specification], closed error codes). A link:01-processes-and-transport.adoc#local-api[Local API] request addressing the project waits the same way and is answered with the same retryable error code `runtime_recovering` of the `pm-api` error codes (link:01-processes-and-transport.adoc#api-error-codes[Local API, Error codes]). The per-project machine store an unenrolled project leaves behind is not touched (retention through `pm-operator sweep`), and it is used again only when the same `project_id` is re-enrolled for the `project_root` the store records (link:../store-schemas/11-enrolment-store.adoc#project-store-identity[Store Schemas Specification, Project Store Identity]). The project's recovery comprises these steps; what a step states is still to be built unless it says otherwise:

. *Enrolment integrity verification (`PM-SEC-5`)*: The verification of the enrolment file and its sidecar, with the settlement of a stopped write of the pair before it and the audit record of every refusal, as a failed step that blocks only its project, is implemented (link:../../concepts/runtime-lifecycle.adoc#per-project-recovery[Concepts § Per-Project Recovery]). Remaining: the uniqueness of `project_root` among the enrolment files (`enrolment_root_conflict`), and the report of a failure on `stderr` and in `pm-operator status`. Verify the project's enrolment file `<PM_MCP_BASE>/enrolments/<project_id>.json`: mode `0600` and owner, schema and exact `format_version`, its HMAC-SHA-256 sidecar `<project_id>.json.hmac` (link:../cli-and-security/02-credentials-and-operator.adoc#enrolment-integrity[CLI, Coordination & Security Specification]), and the uniqueness of its `project_root` among the enrolment files. On a failure the runtime records the audit record (`enrolment_tampered`, `enrolment_insecure`, `enrolment_invalid`, or `enrolment_root_conflict`), reports it on `stderr` and in `pm-operator status`, and refuses every enrolment-dependent operation of this project with that reason until the operator repairs or re-baselines the file through the operator CLI; the other projects and the runtime are unaffected.
. *Owed enrolment audit records*: The step, with the background pass for the intents of projects no longer enrolled, is implemented (link:../../concepts/runtime-lifecycle.adoc#per-project-recovery[Concepts § Per-Project Recovery]). Hand over the audit records an earlier enrolment write of the project still owes in `<PM_MCP_BASE>/enrolments/<project_id>.json.audit-intent` (a refused or stopped hand-over left them there), in their order and with their transaction ids, under the project's enrolment lock (link:../../concepts/store-integrity.adoc#audit-delivery[Concepts § Store Integrity, Audit Records of a Store Change]). The background pass does the same for an intent whose project is no longer enrolled, which an `unenrol` with a refused hand-over leaves behind. A record the audit log refuses again stays owed; the recovery is not refused for it.
. *Jobs and workers*: Mark every job record (`jobs/<job_id>.json`, link:../store-schemas/10-job-and-lesson-records.adoc#job-record[Store Schemas Specification, Job Record]) of the project left `queued` by a previous runtime instance as `status: ended`, `fate: killed` without signalling anything (it never started), and every record left `running`, workers included, as `killed`, by the first matching rule: a record with `execution: in_process` (an in-process operation of the native variant, which died with the previous runtime) is settled without signalling anything and without the orphan note; a record whose `spawned_at` lies before the system boot time is settled without signalling anything; a record with `pid: null` is settled without signalling anything, with the audit note `orphan unidentifiable`; otherwise, if the job's process group is still alive (probed with `kill(-pgid, 0)`, also when its leader has exited), it is terminated first (`SIGTERM`, then `SIGKILL` after the grace period, link:../timeouts/01-job-budgets-and-waits.adoc#grace-period[Timeouts & Budgets Specification]; link:../job-runtime/01-pipeline-and-subprocesses.adoc#_process_termination_cancellation_protocol[Job Runtime Specification, Process Termination], step 6). The generation of every worker settled here is fenced and its job token revoked; its usage is recorded `unmeasured`. The job-private directory `<PM_MCP_BASE>/run/jobs/<job_id>/` of every worker whose job record has `status: ended` is removed, whatever its fate, those settled here included (a crash between the recorded fate and the removal leaves it behind), and with it the data directory of a worker whose harness has a per-worker data home and the copy of the harness's login file in it, which a runtime that died while the worker ran left behind (link:../job-runtime/02-confinement-and-environment.adoc#worker-data-home[Job Runtime Specification, Per-Worker Data Home]) (link:../filesystem-layout/02-machine-runtime.adoc#job-private-directories[Filesystem Layout Specification, Job-Private Directories]). Jobs are never re-executed blindly.
. *Leases and the task queue*: The selection of the project's leases by the `project_id` of their `LeaseOwner`, the orphan marking of those whose holder is no longer alive, and the release of an orphaned lease only on positive evidence are implemented (link:../../concepts/runtime-lifecycle.adoc#per-project-recovery[Concepts § Per-Project Recovery]); the lease stores themselves (merge-queue holders, review-bot claims, build slots, model slots) come with their packages. Release a build or model slot at once (its job is recorded as `killed`). Release every task lease (recorded in its queue task record, never as a `LeaseOwner`) at once, whether held by a worker generation or a session generation, by the queue recovery rule (link:../store-schemas/16-task-queue.adoc#task-queue[Store Schemas Specification, Task Queue], Recovery: the attempt ends `restart`, uncounted, and the task is queued again); a late call of the earlier holder about that task is refused. The positive evidence of abandonment of any other orphaned lease is: owning scope terminal, archived, or gone, or lease expiry passed without adoption; the owning scope adopts its orphaned leases on its next transition (link:../store-schemas/13-leases-integrity-testing.adoc#machine-lease-stores[Store Schemas Specification, Machine Lease Stores]). Session generations stay valid: a session that reconnects continues in its generation.
. *Journal roll-forward*: The roll-forward of the interrupted journal of every scope given to the step is implemented (link:../../concepts/runtime-lifecycle.adoc#per-project-recovery[Concepts § Per-Project Recovery]); the per-project machine store supplies the scopes: the project's plan, epic, and workspace scopes and its lesson store (link:../store-schemas/01-format-and-session-log.adoc#transaction-journal[Store Schemas Specification, Transaction Journal]). Store digests are compared only after this step.
. *Cross-scope reconciliation*: Running the reconcilers registered for the project after the roll-forward is implemented (link:../../concepts/runtime-lifecycle.adoc#per-project-recovery[Concepts § Per-Project Recovery]). The orders and the recovery rule of each transaction that writes outside its scope (`start.create-scope`, job states, worker end, queue tasks, plan end, late findings, `pm-mcp enter`) are listed once in link:../store-schemas/01-format-and-session-log.adoc#transaction-journal[Store Schemas Specification, Transaction Journal] and come with their stores as reconcilers; a job state whose `active_job` was settled `killed` routes that outcome. Each reconciliation appends one audit record `cross_scope_reconciled` (the same record as in the Transaction Journal); the task queue is reconciled by the same rule (link:../store-schemas/16-task-queue.adoc#task-queue[Store Schemas Specification, Task Queue], Recovery).
. Reconcile the recorded worktree presence of every plan whose `worktree_path` is set, lazily on the first transition of that plan: a recorded worktree that no longer exists is cleared (`worktree_path: null`) with an audit record and never followed (link:../filesystem-layout/01-repository-workspace.adoc#worktree-lifecycle[Filesystem Layout Specification, Worktree Lifecycle]). Plan directories never move, so there is no directory move to complete or roll back.
. *Engine deadlines*: After the roll-forward, re-arm the deadline timer from the persisted `expires_at` of the project's open waiver requests and question records and the persisted `deadline_at` of every open prerequisite wait, and process every deadline that passed while no runtime ran (held while the scope is under an integrity pause, link:../job-runtime/01-pipeline-and-subprocesses.adoc#engine-deadlines[Job Runtime Specification, Engine Deadlines]). A waiver wait and a prerequisite wait have no process, so they are re-armed, never settled `killed`.
. *Resume the drive*: Every non-terminal plan and epic of the project continues from its persisted state: a job state whose job was settled `killed` routes that outcome, and a state waiting on a task offers the requeued task (link:../workflow-dsl/02-units-jobs-decisions.adoc#job-state-binding[Workflow DSL Specification, Job State Entry & Binding]).
. *Pending-record sweep*: Pending entry records (`<PM_MCP_BASE>/projects/<project_id>/pending/<entry_id>.json`) older than the compiled pending entry record maximum age (link:../timeouts/02-runtime-leases-operator-web.adoc#pending-entry-max-age[Timeouts & Budgets Specification]) are removed and audited; the runtime keeps no connections, so age is the only evidence.
. *Baseline worktree sweep*: A baseline scratch worktree `.marshall/local/worktrees/baseline-<plan_id>-<sha12>/` whose plan no longer resolves or is terminal (archived or aborted) is removed from the main checkout (`git.worktree-remove`) and audited; one whose plan is live is kept (link:../filesystem-layout/01-repository-workspace.adoc#worktree-lifecycle[Filesystem Layout Specification, Worktree Lifecycle]; link:../job-runtime/03-parsers-and-gates.adoc#_gate_honesty_verification[Job Runtime Specification, Gate Honesty Verification], item 4).

*Sweep rule*: Every sweep (leases, jobs, pending entry records, baseline scratch worktrees, archived plans and archived epics' machine directories, job logs, workspace rows) selects candidates only from positive evidence of abandonment (a dead owner identified by PID plus start instant, a terminal state, or an expired lease or retention period), never from a name that fails to parse as an identifier. Each swept directory declares its reserved entries (for example the shared epic worktree `_epics` under `.marshall/local/worktrees/`), which are excluded by construction.

[#periodic-sweep]
=== Periodic Sweep

The periodic sweep over the enrolled projects at the fixed periodic sweep interval and its two steps are implemented (link:../../concepts/runtime-lifecycle.adoc#periodic-sweep[Concepts § Periodic Sweep], https://github.com/plan-marshall/pm-mcp-core/blob/main/pm-runtime/doc/developer/runtime-start.adoc[Sweep Steps Developer Guide]): one removes the pending entry records older than the pending entry record maximum age (link:../timeouts/02-runtime-leases-operator-web.adoc#pending-entry-max-age[Timeouts & Budgets Specification]) in one transaction of the workspace scope, with one audit record `pending_entry_removed` each, under the sweep rule above; in the same pass the other removes the fenced entries of the session generation record that are older than the same maximum age (link:../store-schemas/16-task-queue.adoc#session-generation-record[Store Schemas Specification, Session Generation Record]), under the queue lock. The runtime registers both steps when it builds the sweep; that wiring into `pm-mcpd` is still to come. The bootstrap performs no age check of its own; a call naming a swept `entry_id` is answered `scope_not_found`.

== Drain, Stop & Upgrade
_Implementation watch: link:../../implementation-watch/runtime-model.adoc#PM-WATCH-RUN-6[PM-WATCH-RUN-6], link:../../implementation-watch/runtime-model.adoc#PM-WATCH-RUN-9[PM-WATCH-RUN-9], link:../../implementation-watch/runtime-model.adoc#PM-WATCH-RUN-13[PM-WATCH-RUN-13], link:../../implementation-watch/runtime-model.adoc#PM-WATCH-RUN-15[PM-WATCH-RUN-15]_

* On `SIGTERM`/`SIGINT` (sent by `pm-operator drain`, the service manager, or the OS), the runtime drains. The drain with its order, its drain timeout (`drain_timeout_seconds` in `machine-config.json`, link:../timeouts/02-runtime-leases-operator-web.adoc#drain-timeout[Timeouts & Budgets Specification]), the removal of `runtime.json`, `run/runtime.token`, and the socket, the release of the singleton lock, the exit code `0`, and the merge-queue and review-bot leases left in place is implemented, with jobs, workers, the LSP pool, and the web listener joining it as participants (link:../../concepts/runtime-lifecycle.adoc#drain[Concepts § Drain]). The participants still to be built do this: a job a transition creates during drain is recorded `queued`, never admitted, and settled with the other queued jobs below; a `pm_build` call during drain is answered with that queued job; a held `pm_wait` is answered `end`; idle warm workers end; running jobs and the tasks in progress finish up to the drain timeout. After it the remaining job process groups are terminated and recorded `killed`, the generations of the remaining workers are fenced, which revokes their job tokens (link:01-processes-and-transport.adoc#job-token[Local Trust: Job Token]), and every job still `queued` is recorded as `status: ended`, `fate: killed` without signalling anything. The task leases of the fenced generations are released (their tasks are offered again exactly once after the next start, <<per-project-recovery>>), warm LSP servers shut down, and the build and model slots released (their jobs are settled `killed`). The merge-queue and review-bot leases left in place become orphaned at the next start and are adopted or released there by the evidence rules of <<per-project-recovery>>, exactly as after a crash. The web listener closes last if it is open; `web.enabled` is unchanged, so the next start opens the listener again.
* *`pm-operator drain`* is a signal, never an API request, so it works whatever state the runtime is in: it reads `pid` and `start_instant` from `runtime.json`, confirms that the process with that PID has that start instant (never signalling a reused PID), sends `SIGTERM`, and waits for the process to exit, bounded by the wait of `pm-operator drain` defined with the drain timeout, which it reads from `machine-config.json` (link:../timeouts/02-runtime-leases-operator-web.adoc#drain-timeout[Timeouts & Budgets Specification, Drain Timeout]); it has no timeout option of its own. It reports the exit, or, when the bound passes first, that the runtime is still draining, with the recorded PID. Without a live `runtime.json` it reports that no runtime is running and exits `0`; it never starts the runtime.
* *`pm-operator status`* is an API request (`GET /api/v1/status`, link:01-processes-and-transport.adoc#local-api[Local API]): it reports `running` only from a successful authenticated round trip, never from the presence of `runtime.json`. When no live runtime is recorded (no `runtime.json`, or its `pid` and `start_instant` do not match a live process) it reports "not running" without starting the runtime; when a live runtime does not answer within the runtime start timeout it reports "not responding" with the recorded PID.
* Calls arriving during drain receive a normal representation with `facts.runtime: draining`; the entry session's bootstrap links that would commit a scope are not offered.
* *Upgrade*: A new release is installed into a new versioned directory and activated by switching the `PATH` symlinks of `pm-mcp` and `pm-operator`; `pm-operator drain` then stops the old runtime, and the next command that needs the runtime starts the new `pm-mcpd` from the new directory. The old installation directory stays until that drain has completed, because the old runtime starts its jobs through its own `pm-exec` until it exits (link:../cli-and-security/01-cli-and-installer.adoc#installation-layout[CLI, Coordination & Security Specification, Installation Layout]). A relay whose own version differs from `runtime.json -> version` forwards normally. The runtime's comparison of the relay's `PM-MCP-Relay-Version` header with its own version, its audit record with both versions, and the status data with the recommended `pm-operator drain` command are implemented (link:../../user/operator.adoc#relay-version-mismatch[User Guide § Relay Version Mismatch]). The mismatch is operator-only (`PM-DIST-4`): it is shown by `pm-operator status` with the recommended command and printed as a terminal notice by `pm-mcp enter`; no representation carries it (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).
