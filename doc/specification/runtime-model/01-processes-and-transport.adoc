== Terminology

[cols="1,3"]
|===
|Term |Definition

|Runtime (daemon)
|The always-on `pm-mcpd` process. Exactly one per machine and `PM_MCP_BASE`. Hosts the MCP server of the workers, the <<local-api>> of the operator's clients, the workflow engine, the stores (their only writer), the job runner, the task queue and the worker supervisor, the build- and model-slot scheduler, the warm LSP pool, the upstream proxy, the metrics registry, and the audit writer.

|Operator's clients
|The web app in a paired browser and the terminal client `pm-operator`, the only places where the operator is asked, chooses, answers, views, and acts (link:../cli-and-security/01-cli-and-installer.adoc#two-channels[CLI, Coordination & Security Specification, Operator Choices in the Web App and the Terminal]). Both are clients of the <<local-api>>; they show the same state, the same proposal, and the same texts, and a run started in one continues in the other. No harness, session, or model acts for the operator (link:../workflow-dsl/02-units-jobs-decisions.adoc#clients-only[Workflow DSL Specification, All Interaction in the Operator's Clients]).

|Operator wait
|A state of any unit and scope that waits for an act of the operator, offered to both clients as operator links of the <<local-api>> without a time limit (link:../workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]).

|Relay (`pm-mcp serve --job`)
|The process a worker's harness spawns over `stdio`, the `serve` command of the relay binary `pm-mcp`. Copies JSON-RPC messages between its `stdin`/`stdout` and the runtime's socket and carries the worker's job token and generation (link:03-relay.adoc[Relay]). Contains no workflow or store logic. No other process reaches `/mcp`.

|Runtime token
|A fresh 256-bit secret the runtime writes at every start to `<PM_MCP_BASE>/run/runtime.token`; every local request of the <<local-api>> presents it (<<runtime-token>>).

|Scope
|A plan (`plan_id`), an epic (`epic_id`), the project's workspace scope (`plan_id: NO_PLAN`), or the machine's one scope, which hosts its onboarding and its settings (link:../workflow-dsl/01-grammar.adoc#machine-scope[Workflow DSL Specification, Machine Scope]). Identified solely by its id and carried solely by its persisted files; the runtime drives a plan or an epic from its creation to a terminal state whether or not a client is open (link:04-sessions-and-workers.adoc#_server_driven_scopes[Workers & Operator Acts, Server-Driven Scopes]). An *entry* (a start's or a project onboarding's, `entry_id`) is an entity of a workspace scope until it starts its scope.

|Epic
|A multi-plan initiative (scope `epic`) with its git-tracked ledger. The word *epic* names only this tier.

|Worker
|A headless harness process of a role that the runtime launches as a job of kind `llm` through the headless CLI of an enrolled harness (link:../model-work/04-worker-launch.adoc[Model Work Specification, Worker Launch]). It connects back through its own relay with a job token, receives tasks through `pm_wait` (a fresh worker its one task in its launch prompt, link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]), and is bound to its job and generation (<<job-token>>; link:../model-work/03-supervision-and-recycling.adoc[Model Work Specification, Supervision & Recycling]). A harness is a worker only.

|Generation
|The identity of one worker: its `job_id` (link:../identifiers/01-general-rules-and-registry.adoc#id-generation-id[Identifier Registry, `generation_id`]). Tasks are leased to a generation, and every call of a fenced generation is refused (link:03-relay.adoc#_generations_at_the_relay[Relay, Generations at the Relay]).

|Queue task
|One unit of model work for a role, persisted in the project's task queue (or the machine's, for a task of the machine scope), leased to one generation, and ended in a closed outcome (link:../model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]). Not to be confused with a plan task (`TASK-NNN`).

|CLI
|The short-lived commands of the two client binaries. `pm-operator` is the terminal client and the operator CLI; `pm-mcp` has only the worker relay. Every command that reads or changes state is a request to the <<local-api>>, apart from the closed list of direct file reads (link:04-sessions-and-workers.adoc#cli-direct-reads[Workers & Operator Acts, Client Interaction]); neither binary ever writes a store.
|===

Workers are children of the runtime, started through `pm-exec` like every job; their relays connect back to the same socket. No client of the operator starts a worker, and no worker reaches the <<local-api>>.

== Runtime

=== Responsibilities

The runtime is the only process that executes workflow transitions, runs jobs (workers included: it starts, supervises, recycles, and replaces every worker itself, `PM-WF-5`, `PM-WORK-3`), keeps the task queue and offers its tasks, holds the warm LSP pool, schedules build and model slots, calls upstream MCP servers server-side, keeps the metrics (<<runtime-metrics>>), writes the reports (<<reports>>), runs the cleanup (link:../timeouts/03-retention-host-config.adoc#cleanup[Timeouts & Budgets Specification, One Cleanup]), writes audit records (`PM-ARCH-1`), and, while the operator enabled web access, serves the web app and the <<local-api>> to paired browsers (<<_transport_endpoint,Transport Endpoint>>, Web listeners). It is the only writer of every store under `<PM_MCP_BASE>` and `.marshall/`: operator acts, entries, client install records, and the web device store are written by the runtime on a request of the <<local-api>>, never by a client process, so there is one lock owner, one validation path, and one audit path. Jobs are children of the runtime (link:../job-runtime.adoc[Job Runtime Specification]). Outside its stores and the client bundle targets the runtime writes only the service unit (<<_start_modes,Start Modes>>), a new installation directory and the two `PATH` links of an upgrade (link:02-startup-recovery-drain.adoc#runtime-lifecycle-operations[The Runtime's Lifecycle]), and deletes only the operator's documents a move of a document source takes, on the operator's choice (link:../state-catalogue/09-bootstrap-and-lessons.adoc#documents-source[State Catalogue Specification, Documents as a Source]).

=== Singleton & Discovery
_Implementation watch: link:../../implementation-watch/runtime-model.adoc#PM-WATCH-RUN-7[PM-WATCH-RUN-7], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-28[PM-WATCH-JOB-28]_

* *Singleton lock*: On start the runtime acquires `<PM_MCP_BASE>/locks/runtime.lock` (`FileChannel.tryLock()`, held for the process lifetime) before anything else (link:02-startup-recovery-drain.adoc#_startup_sequence[Startup Sequence], step 1). A second runtime for the same `PM_MCP_BASE` fails to acquire it and exits with code `0` immediately; the losing runtime writes nothing: no audit record, no runtime record, no socket or stale-file removal, no store access. Only the successor of a restart waits for the lock instead (link:02-startup-recovery-drain.adoc#runtime-lifecycle-operations[The Runtime's Lifecycle]).
* *Runtime record*: `<PM_MCP_BASE>/state/runtime.json` (mode `0600`) records `pid`, `start_instant` (`ProcessHandle.info().startInstant()`), `version`, `listener` (the listener in use, <<_transport_endpoint,Transport Endpoint>>, Listener fallback order), `socket_path` (the socket path, see *Socket*), and `started_at`. It is written when the socket is bound (link:02-startup-recovery-drain.adoc#_startup_sequence[Startup Sequence], step 6). The web listeners have no record: their setting is the `web` object of `machine-config.json`, and their live state (each listener's state and port, the certificate fingerprint) is part of the runtime status (<<local-api>>). Liveness checks compare both `pid` and `start_instant` to rule out PID reuse.
* *Socket*: `<PM_MCP_BASE>/run/runtime.sock` (default `~/.plan-marshall-mcp/run/runtime.sock`) inside the `0700` directory `run/`. Vert.x creates the socket under the process `umask` (on a common `umask 022` with mode `0755`); right after the bind, and before `state/runtime.json` is written, the runtime restricts it to mode `0600` and verifies owner, mode, and file type with `lstat`; a socket that fails the check refuses the start like every violation of the permission step (`stderr`, `audit.jsonl`, exit code `77`; link:02-startup-recovery-drain.adoc#_startup_sequence[Startup Sequence], step 6).
** *Path length*: The socket has no other location. If the path would exceed the platform's `sun_path` limit (104 bytes including the terminating NUL on macOS, 108 on Linux), the runtime refuses to start with a diagnostic naming the path and telling the operator to choose a shorter `PM_MCP_BASE` (link:02-startup-recovery-drain.adoc#_startup_sequence[Startup Sequence], step 3: `stderr`, `audit.jsonl`, exit code `77`); nothing the runtime trusts ever lies in the system temporary directory, which every job can write.
** *Discovery*: Every `pm-operator` command derives the socket path from `PM_MCP_BASE`; `socket_path` in `state/runtime.json` records it for `pm-operator status` and names the loopback address under listener fallback (1) of <<_transport_endpoint,Transport Endpoint>>. A worker's relay takes the path from its MCP configuration instead (<<job-token>>). Before connecting, a client runs the same owner, mode, and no-symlink check on the directory `run/` that the runtime runs at bind, so a squatting process cannot impersonate the runtime.
* *Runtime token*: `<PM_MCP_BASE>/run/runtime.token` (mode `0600` in the `0700` directory `run/`), rewritten at every start before the socket is bound (<<runtime-token>>).

=== Transport Endpoint
_Implementation watch: link:../../implementation-watch/runtime-model.adoc#PM-WATCH-RUN-17[PM-WATCH-RUN-17]_

* The runtime's listener for its local clients is the Quarkus/Vert.x HTTP server bound exclusively to the Unix domain socket (`quarkus.http.domain-socket-enabled=true`, `quarkus.http.domain-socket=<socket_path>`, `quarkus.http.host-enabled=false`); the socket's mode is set after the bind (*Socket* in <<_singleton_discovery,Singleton & Discovery>>). Unix domain sockets in Vert.x require the Netty native transport (`kqueue` on macOS, `epoll` on Linux), a runtime dependency of `pm-mcpd`.
** *Native transport in the native image*: Quarkus native replaces Vert.x's native transport by the JDK transport, so `pm-mcpd` provides the `kqueue` or `epoll` transport itself as a Vert.x `Transport` service, with the JNI reachability metadata of each platform in its build.
** *Transport library location*: The Netty transport library (`libnetty_transport_native_kqueue_<arch>.jnilib` on macOS, `libnetty_transport_native_epoll_<arch>.so` on Linux) ships beside `pm-mcpd` in `<PM_MCP_HOME>/bin/` (link:../cli-and-security/01-cli-and-installer.adoc#installation-layout[CLI, Coordination & Security Specification, Installation Layout]), and the runtime loads it from there. Netty's own fallback extracts the library into the system temporary directory on every start, which costs about 250 ms of the cold-start bound of `PM-TECH-3` and executes native code from a directory every job can write; the native `pm-mcpd` never uses it, and a missing library refuses its start with a diagnostic naming the expected path.
* The Quarkus management interface is disabled. No TCP or UDP listener exists in any production profile unless the operator enabled web access (`PM-SEC-4`, *Web listeners* below), apart from listener fallback (1) below.
* The socket serves two endpoints: MCP (`2026-07-28`) at `/mcp` over the Streamable HTTP transport of `io.quarkiverse.mcp:quarkus-mcp-server-http` for the job relays, and the <<local-api>> at `/api/v1` for `pm-operator` and a tool of the operator that holds the runtime token. `/mcp` accepts only a job token (<<job-token>>) and `/api/v1` only the runtime token (<<runtime-token>>); a request without a token, with an unknown or malformed one, or with the token of the other endpoint is answered `401` and audited; a revoked job token is still resolved and answered by the tool handler (<<job-token>>).
* *Idle timeouts*: `quarkus.http.idle-timeout` and `quarkus.mcp.server.connection-idle-timeout` are set to the runtime HTTP idle timeout (link:../timeouts/02-runtime-leases-operator-web.adoc#runtime-http-idle-timeout[Timeouts & Budgets Specification]), which lies above the longest bounded or progress wait any client profile allows, so the runtime never ends a held `pm_wait` or `pm_build` call itself; an event stream of the <<local-api>> sends a comment line within that timeout, so an idle stream is never closed by it.
* The peer UID (`SO_PEERCRED` on Linux, `LOCAL_PEERCRED` / `getpeereid` on macOS) is checked in addition where the listener exposes it cheaply; a mismatch is refused and logged. It is never required: the runtime token carries the same-user proof.
* *Listener fallback order*: The Quarkus domain-socket listener is the listener: it is verified under native image on macOS and Linux (SSE streaming, stale-socket handling, the refusal of an over-long socket path; link:../evaluation.adoc[Evaluation Reference]), and no fallback is in use. Should a later Quarkus, Vert.x, or platform version break it, the fallback is, in this order: (1) a loopback TCP listener on `127.0.0.1` with the same tokens, rejecting every request whose `Host` is not the loopback address and port or that carries an `Origin` header, never bound to another interface; (2) an own JDK `ServerSocketChannel` on `UnixDomainSocketAddress` (virtual threads) bridging requests in process to the Quarkus router. The listener in use is recorded in `runtime.json` and reported by `pm-operator status`; fallback (1) is the only case in which the runtime opens a TCP listener while web access is disabled (`PM-SEC-4`).
* *Web listeners*: While the operator enabled web access in the `web` object of `machine-config.json` (link:../store-schemas/12-machine-stores.adoc#machine-config[Store Schemas Specification, Machine Configuration Store]), the runtime opens up to two HTTP servers beside the socket listener, each a Vert.x HTTP server of its own: the loopback listener, plain HTTP on `127.0.0.1:<web.port>`, and, beside it, the LAN listener, HTTPS on all interfaces on `web.lan_port` with the runtime-generated self-signed certificate under `<PM_MCP_BASE>/web/tls/`. Which listener is open, the occupied-port rule of each, and what each accepts are specified in link:../cli-and-security/03-web-server.adoc#two-listeners[CLI, Coordination & Security Specification, Loopback and LAN Listeners Side by Side].
** *Shared router*: Each web listener delegates `/api/v1/` to the root handler of the Quarkus HTTP router (an internal Quarkus API, pinned by the web-listener tests of link:04-sessions-and-workers.adoc#_verification[Verification]), so every listener shares the routes, the security chain, and the identity providers. The token kind a request may present, and which endpoints it may reach, are decided by the listener the connection arrived on, never by the token: the runtime token and the job token only on the Unix socket, a device secret only on a web listener, and the loopback-only endpoints only on the socket and the loopback listener (<<local-api>>, Authentication).
** *Routes*: A web listener routes only the static web app and `/api/v1/`. `/mcp` and every other path are never reachable there, and neither the runtime token nor a job token is accepted there: a browser authenticates with its device secret (<<local-api>>, Authentication). `Host` validation, the Origin check, the security headers, and the absence of CORS are those of link:../cli-and-security/03-web-server.adoc#web-security-headers[CLI, Coordination & Security Specification, Request Validation & Security Headers].
** *Lifetime*: The operator's acts open and close a web listener while the runtime runs, without touching plans, jobs, or workers; closing one ends every open browser stream on it (verified under native image on both platforms, link:../evaluation.adoc[Evaluation Reference]). A web listener exists only while `pm-mcpd` runs: without a runtime a browser gets a refused connection, and nothing answers "runtime not running". The web listeners are independent of listener fallback (1), which serves the local clients with their tokens and never a browser.
* Any process of the same OS user can read the runtime token and so reach `/api/v1` on the socket, including a model-driven shell; the runtime token is not accepted on `/mcp`. On `/api/v1` it reaches the operator endpoints, whose proof is checked by `pm-operator` only; this is the accepted risk of the operator channel (link:../cli-and-security/02-credentials-and-operator.adoc#operator-channel-isolation[CLI, Coordination & Security Specification, Operator Channel Isolation]; link:../../later-improvements.adoc#_l_1_operator_proof_beyond_the_cli_checks[Later Improvements, L-1]).

[#runtime-token]
=== Local Trust: Runtime Token
_Implementation watch: link:../../implementation-watch/runtime-model.adoc#PM-WATCH-RUN-4[PM-WATCH-RUN-4]_

The runtime token gives the same boundary as a peer-UID check (only the owning OS user can read it) through the ordinary HTTP authentication seam, independent of the listener's ability to expose peer credentials (`PM-SEC-4`):

* *Creation*: At every start, after the singleton lock and before the socket is bound (link:02-startup-recovery-drain.adoc#_startup_sequence[Startup Sequence]), the runtime generates 256 bits from `SecureRandom`, encodes them base64url, and writes them atomically (`*.tmp` with mode `0600` + `fsync` + `ATOMIC_MOVE`) to `<PM_MCP_BASE>/run/runtime.token`. A restart always replaces the token; a token never outlives its runtime instance.
* *Presentation*: Every request of `pm-operator`, and of a tool of the operator, on `/api/v1` carries `Authorization: Bearer <runtime token>`. The runtime checks it with one Quarkus `HttpAuthenticationMechanism` (Bearer) and an `IdentityProvider` for the runtime token, in constant time; resources are only `@Authenticated`. A browser never holds the runtime token: on a web listener the same Bearer seam carries its device secret, with an `IdentityProvider` of its own (<<local-api>>; link:../cli-and-security/03-web-server.adoc#web-auth-seam[CLI, Coordination & Security Specification, Authentication Seam]).
* *Client check*: Before reading the token, a client verifies with `lstat` that `run/` and `runtime.token` are owned by the effective UID, have modes `0700` and `0600`, and are no symlinks; otherwise it refuses with a diagnostic naming the path. On a `401` a client re-reads the file once (the runtime restarted) and retries the request once.
* *Secrecy*: The token is registered with the redaction registry (link:../cli-and-security/02-credentials-and-operator.adoc#operator-credential-cli[CLI, Coordination & Security Specification, Runtime Secret Redaction]); it never appears in logs, the audit log, command-line arguments, representations, or job environments. The whole of `<PM_MCP_BASE>`, `run/runtime.token` included, lies outside every job's Landlock read set, apart from a worker's own job-private directory `run/jobs/<job_id>/` (link:../job-runtime/02-confinement-and-environment.adoc#_linux_filesystem_confinement_landlock[Job Runtime Specification]), and the file-tool deny rules of the client bundles for `<PM_MCP_BASE>/**` cover it.
* *Boundary*: Same-user processes cannot be kept out; the token only makes the same-user boundary explicit and portable (to the loopback fallback and to future platforms). It grants nothing a same-user process could not already reach through the files the runtime writes.

[#job-token]
=== Local Trust: Job Token

A worker never receives the runtime token; it reaches the runtime with a job token bound to its job and generation (link:../model-work/04-worker-launch.adoc[Model Work Specification, Worker Launch]). At the transport:

* *Creation and revocation*: 256 bits from `SecureRandom`, minted at spawn; only its SHA-256 is stored (job record). It is valid while the job runs and its generation is not fenced. It is revoked in the transaction that settles the job's fate or fences the worker's generation. Revocation never forgets the token: its SHA-256 stays on the job record, so a later request with it is still resolved to its job and answered by the tool handler, which checks the job before the generation (link:04-sessions-and-workers.adoc#_call_cycle[Call Cycle]): `job_ended` when the job has ended, otherwise `generation_fenced` when the generation was fenced, never `401`, which is reserved for an unknown or malformed token. A runtime restart therefore revokes every job token, since recovery settles those jobs `killed` and fences their generations (link:02-startup-recovery-drain.adoc#per-project-recovery[Per-Project Recovery]).
* *Delivery*: The worker's composed MCP configuration starts `<PM_MCP_HOME>/bin/pm-mcp serve --job --socket <socket_path>`, the `pm-mcp` of the running runtime's own installation by absolute path, never through `PATH` (link:../cli-and-security/01-cli-and-installer.adoc#installation-layout[CLI, Coordination & Security Specification, Installation Layout]); the token and the generation reach that relay only in its environment (`PM_MCP_JOB_TOKEN`, beside `PM_MCP_JOB_ID`, which is the worker's generation), never in an argument, a file, or the prompt. A `zero_tool` worker (the screener, the grading judge `judge`) has no MCP configuration and no token.
* *Presentation*: The relay sends `PM-MCP-Job-Token` in place of `Authorization` and the generation as `PM-MCP-Generation` (link:03-relay.adoc#_connection_metadata[Relay, Connection Metadata]). The runtime accepts the token on `/mcp` only (`/api/v1` answers `401`), resolves the job from the token's SHA-256 in constant time on every request, keeps no connection state, and binds the request, a tool call or a resource request alike, to the worker's project (or, for a task of the machine scope, the machine scope), role, generation, and the task entities leased to that generation (link:../mcp-tools/01-core-workflow-tools.adoc#job-bound-connections[MCP Tools Specification, Worker Connections]). A generation header that differs from the job's is refused like a fenced generation. `resources/list` and `resources/read` work on a worker connection read-only, for every resource of the worker's own project plus `skill://pm/…`; the project boundary is the only read boundary.
* *Secrecy*: The token is registered with the redaction registry like the runtime token and never appears in logs, the audit log, command-line arguments, or representations.

[#local-api]
=== Local API (`/api/v1`)
_See Requirement link:../../Requirements.adoc#PM-ARCH-11[PM-ARCH-11: The Operator's Two Clients & Their Contract]_

_Implementation watch: link:../../implementation-watch/runtime-model.adoc#PM-WATCH-RUN-5[PM-WATCH-RUN-5], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-20[PM-WATCH-CLI-20], link:../../implementation-watch/runtime-model.adoc#PM-WATCH-RUN-12[PM-WATCH-RUN-12]_

The runtime serves one versioned REST API at `/api/v1`: on its Unix domain socket (or the loopback listener fallback of <<_transport_endpoint,Transport Endpoint>>) for `pm-operator`, and, only while web access is enabled, on the web listeners for paired browsers; nowhere else. It is the one contract of the operator's two clients (`PM-ARCH-11`): every operator wait, operator act, and view is served to both, with the same state, proposal, and texts. Its resources in their representation for a client (link:../hypermedia-format/01-representation-and-link-forms.adoc#operator-representation[Hypermedia Format Specification, Operator Representation]), the operator links, the error codes, the event catalogue, the message catalogue, and the JSON/TOON codecs are the contract module `pm-api` (link:../../Requirements.adoc#PM-IMPL-1[PM-IMPL-1]). `/mcp` for the job relays is served on the same socket and never on a web listener; the API never replaces an MCP tool, and nothing of it reaches a model-facing representation (link:../hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]).

* *Authentication*: Every request on the socket carries the runtime token (<<runtime-token>>). A request on a web listener carries the browser's device secret directly, as `Authorization: Bearer pmw_…` (link:../cli-and-security/03-web-server.adoc#web-auth-seam[CLI, Coordination & Security Specification, Authentication Seam]); there is no forwarding header and no intermediary. The runtime checks the secret against the web device store on every such request, without a cache, so a revocation takes effect with the next request. A request on a web listener with an unknown, revoked, or expired secret, or with the runtime token, is answered `401` and audited. The device id of a valid secret is recorded in the audit record of every act taken on its behalf. Two endpoint classes are restricted by the listener a request arrived on, never by what it names: the *CLI-only* endpoints (issuing or replacing a pairing code, enabling web access, opening the LAN listener) refuse every web listener with `403` (`cli_only`); the *loopback-only* endpoints (entering a credential secret, the listing of files, a move of documents, documents outside the checkout) refuse the LAN listener with `403` (`loopback_only`), also when the request names a loopback address there (link:../cli-and-security/03-web-server.adoc#web-credentials[CLI, Coordination & Security Specification, Credentials in the Web App]). The message routes and `POST /api/v1/pair` are the only endpoints a web listener serves without a device secret.
* [[client-inputs]]*What only the client sees*: The runtime's own environment is never an input (<<runtime-environment>>); what only a client sees travels in its request. The client's *locale* is the `Accept-Language` header of every request: the texts the runtime serves are in the machine's `language.interface` of `machine-config.json`, and only while none is set does the runtime choose the message pack by this locale (link:../module-structure.adoc#i18n[Module Structure Specification, Languages and Internationalisation]). The operator's *login environment* (`PATH` and the variables the build environment allowlists) is captured by the terminal client in the operator's login shell and carried by the requests that need it (link:../cli-and-security/01-cli-and-installer.adoc#client-environment[CLI, Coordination & Security Specification, What the Terminal Client Sends]); the runtime keeps the one captured last on the machine with its time, and a project onboarding started from the web app takes that one and says so (link:../cli-and-security/02-credentials-and-operator.adoc#project-onboarding[CLI, Coordination & Security Specification, Onboarding a Project as One Process]). An *SSH session* is the terminal client's own observation (link:../cli-and-security/01-cli-and-installer.adoc#start[CLI, Coordination & Security Specification, The Terminal Client as the Entry]); it reaches the runtime only as the pairing request it leads the client to make.
* *Endpoint names*: One naming scheme holds for every client. * *Operator endpoints*: Every act of the operator is an endpoint of this API, accepted from `pm-operator` after its operator checks passed and from a paired device; the runtime cannot verify the checks of `pm-operator`, which is the accepted risk stated in link:../cli-and-security/02-credentials-and-operator.adoc#operator-channel-isolation[CLI, Coordination & Security Specification, Operator Channel Isolation], where the privileged acts are listed. Every act is audited with its channel (`cli`, or `web` with the device id), validated against the state it acts on, and answered with the new state; an act the state does not offer is refused `act_not_available`, and of two acts on the same decision or recorded value the first valid one wins and a later one made against an older revision is refused `conflict` (`PM-ARCH-8`).
* [[api-no-secret-read]]*Credential entries*: The API writes, deletes, and reports a credential entry and never returns its secret. `PUT /api/v1/credentials/{credential_key}` stores or replaces the secret of an entry (`204`; loopback-only; the secret travels in the request body, link:../cli-and-security/02-credentials-and-operator.adoc#operator-credential-cli[CLI, Coordination & Security Specification, Operator Credential CLI]), `DELETE` on the same path removes it (`204`, whether or not it existed), and `GET` answers the entry's status with `200` and `{"status": "present" | "not_found", "store": "keychain" | "secret-service" | "file"}`: an absent entry is a status and no refusal, as in `pm-operator credentials status`, so it is not answered `404`. The status is decided by the chosen store's own read of the entry, whose result the runtime drops at once; a store that cannot read (a locked keyring, an insecure or invalid credential file) therefore answers its error code and no status. No endpoint, no error answer, and no log line carries a secret: a secret enters the runtime in the body of a write and never leaves it through the API, because the runtime token that authenticates a local request is readable by every process of the user (<<runtime-token>>), a model-driven shell included.
* [[api-error-codes]]*Error codes*: A refused API request is answered with an HTTP status and one code of the closed list of `pm-api`; an unauthenticated request is answered `401` without a code (*Authentication* above). A code's detail is shown to the operator only, as a message key with its arguments (link:../hypermedia-format/01-representation-and-link-forms.adoc#runtime-texts[Hypermedia Format Specification, Texts of the Runtime]), and never reaches a model-facing representation. The list:
** `400`: `invalid_arguments` (the request body or a parameter violates the endpoint's schema, for example `enrol-harness` for a client whose profile has `headless: null`), `invalid_answer` (an answer whose option, value, or own words the decision's part does not allow), `dependency_unanswered` (an answer to a part whose dependency on another part is unanswered), `pairing_invalid` (link:../cli-and-security/03-web-server.adoc#web-pairing[CLI, Coordination & Security Specification, Pairing Protocol]), `unit_name_invalid` (link:../workflow-dsl/04-ast-node-model.adoc#process-designer[Workflow DSL Specification, Designing a Process]).
** `403`: `cli_only` (a CLI-only endpoint on a web listener), `loopback_only` (a loopback-only endpoint on the LAN listener).
** `404`: `project_not_enrolled` (the named project or checkout path resolves to no enrolled project, `PM-ARCH-4`), `scope_not_found` (an unknown plan, epic, decision, report, cleanup job, or entry id), `target_not_found` (an unknown waiver, owed item, retained capture ref, credential entry, consent, or paired device).
** `409`: `act_not_available` (an act the addressed state does not offer: a pause of a paused plan, an abandon of a running one, an operator link of a state left meanwhile); `conflict` (an act made against an older revision of a decision or a recorded value; the answer carries the current revision); `already_answered` (a decision answered in the other client first); `onboarding_incomplete` (a verb that needs a step of the machine's onboarding not done yet, a credential entered before a store is chosen included; `plan_ended`, `already_consumed`, `not_waivable`, `raise_out_of_range`, `position_not_contained` (the waiver verbs, link:../cli-and-security/02-credentials-and-operator.adoc#operator-waive[CLI, Coordination & Security Specification, Waivers]; === Start Modes
_Implementation watch: link:../../implementation-watch/runtime-model.adoc#PM-WATCH-RUN-1[PM-WATCH-RUN-1], link:../../implementation-watch/runtime-model.adoc#PM-WATCH-RUN-7[PM-WATCH-RUN-7], link:../../implementation-watch/runtime-model.adoc#PM-WATCH-RUN-14[PM-WATCH-RUN-14], link:../../implementation-watch/runtime-model.adoc#PM-WATCH-RUN-18[PM-WATCH-RUN-18]_

. *On demand (default)*: When a command of `pm-operator` that needs the runtime (every command that sends an API request, and `pm-operator runtime start`) finds no live runtime, it creates `<PM_MCP_BASE>`, `<PM_MCP_BASE>/locks/`, and `<PM_MCP_BASE>/logs/` where they are absent (mode `0700`, under `umask 077`; `logs/` because the spawn appends the runtime's output to `logs/daemon.log`, which needs its directory; the runtime creates every other directory, link:02-startup-recovery-drain.adoc#_startup_sequence[Startup Sequence], step 3), acquires `<PM_MCP_BASE>/locks/runtime-start.lock`, re-checks liveness, and starts `<PM_MCP_HOME>/bin/pm-mcpd` by its path (never through `PATH`) detached into a new OS session, with `stdin` from `/dev/null` and `stdout`/`stderr` appended to `logs/daemon.log` (mode `0600`).
** *Detached spawn*: `posix_spawn` through Java FFM with the attribute flag `POSIX_SPAWN_SETSID` (`setsid` semantics), whose value is platform-specific: `0x0400` on macOS and `0x80` on Linux (glibc). No descriptor of the client except the three standard streams reaches the runtime: on macOS through `POSIX_SPAWN_CLOEXEC_DEFAULT` (`0x4000`), on Linux through the file action `posix_spawn_file_actions_addclosefrom_np` from descriptor `3` (glibc 2.34 or later, the minimum glibc of the Linux binaries). It then waits, bounded by the runtime start timeout (link:../timeouts/02-runtime-leases-operator-web.adoc#runtime-start-timeout[Timeouts & Budgets Specification]), for an authenticated round trip (<<runtime-token>>) to succeed, and holds `runtime-start.lock` until that round trip succeeds or the timeout expires; only after the round trip does it treat the runtime as running. `runtime-start.lock` is the only lock a client binary takes; the procedure (start lock, detached spawn, runtime-token file checks) is one implementation in `pm-api`. Detaching guarantees that nothing that ends the command terminates the runtime. A worker's relay never starts the runtime, and the five commands that work without it (*Availability* above) never start it either. The exiting runtime runs the same procedure to start its successor after a restart (link:02-startup-recovery-drain.adoc#runtime-lifecycle-operations[The Runtime's Lifecycle]).
. *Service-managed (optional)*: `pm-operator runtime install` registers a per-user service that starts `pm-mcpd` at login and restarts it on failure; `pm-operator runtime uninstall` removes it. Both are API requests the runtime executes, and like every request they start the runtime on demand. The runtime writes the unit file: on macOS the `launchd` LaunchAgent `~/Library/LaunchAgents/de.planmarshall.mcpd.plist`, on Linux the `systemd --user` unit `$XDG_CONFIG_HOME/systemd/user/pm-mcpd.service` (default `~/.config/systemd/user/`), naming `<PM_MCP_HOME>/bin/pm-mcpd` by its absolute path. On-demand start stays available and is the default on every platform; the service is never the only supported start mode. A runtime the service manager runs is restarted through the service manager, so its successor runs under the service unit. Filesystem confinement of jobs is independent of the start mode (link:../job-runtime.adoc[Job Runtime Specification]).
** *Install*: the runtime writes the unit, replacing an existing one, so `install` run again after an upgrade updates it, and then loads it: on macOS `launchctl bootout gui/<uid>/de.planmarshall.mcpd` (a job that is not loaded is no failure) followed by `launchctl bootstrap gui/<uid> <unit>`, on Linux `systemctl --user daemon-reload` followed by `systemctl --user enable --now pm-mcpd.service`. When loading fails the unit stays written and the failure is reported; `install` can be run again.
** *Uninstall*: without a unit nothing is done and nothing fails. Otherwise the runtime disables the unit while its file is present (on Linux `systemctl --user disable pm-mcpd.service`, which leaves the service running; on macOS removing the file is what disables the job), removes the file, and only then unloads the unit (on macOS `launchctl bootout gui/<uid>/de.planmarshall.mcpd`, on Linux `systemctl --user stop pm-mcpd.service` followed by `systemctl --user daemon-reload`; a unit that is not loaded is no failure). A failing step is reported, and the file is removed all the same, so a later `install` starts clean; only a file that cannot be removed keeps the unit loaded.
** *A runtime started by the service*: both requests run inside the runtime, so when the service started that runtime, the step that stops the service ends it. The file work therefore comes before every step that can stop the service, and an ended runtime leaves neither a stale nor a missing unit behind. On macOS a reinstall issued from such a runtime ends it after the old job is unloaded and before the new one is loaded, so the job stays unloaded until the next login or the next `install` (link:../../implementation-watch/runtime-model.adoc#PM-WATCH-RUN-18[PM-WATCH-RUN-18]).

The runtime never exits because it is idle. It stops only on the operator's stop (link:02-startup-recovery-drain.adoc#runtime-lifecycle-operations[The Runtime's Lifecycle]), `pm-operator drain`, `SIGTERM`/`SIGINT`, OS shutdown, or a crash. Since the runtime drives plans and epics itself, the service-managed mode keeps them moving while no command has started the runtime since login.

[#runtime-environment]
=== Environment

The runtime's own environment is that of whichever process started it and is therefore never an input to a workflow, a detection, or a job's build environment. Jobs, workers included, receive an explicitly constructed allowlisted environment (`PM-SEC-5`), whose build variables come from the login environment a client sent (<<client-inputs>>). A worker's harness is the one its role's effective values name, recorded in its job record, never taken from the runtime's environment (link:03-relay.adoc#_connection_metadata[Relay, Connection Metadata]).

== Resources of the Operator's Clients
_See Requirement link:../../Requirements.adoc#PM-ARCH-11[PM-ARCH-11: The Operator's Two Clients & Their Contract]_

Every resource below is derived by the runtime on read from the persisted state, never stored as a view of its own, and served to both clients in the operator representation (link:../hypermedia-format/01-representation-and-link-forms.adoc#operator-representation[Hypermedia Format Specification, Operator Representation]): each names the resources it refers to by a link, so a client leads from one to another in one step, and every figure of tokens carries its split and coverage (link:../client-profiles/01-profile-schema.adoc#token-usage[Client Profiles Specification, Tokens, Not Money]). A plan or an epic is *active* while it is not in a terminal state, and a project has *running work* as link:../state-catalogue/04-plan-finalize-terminal.adoc#running-work[State Catalogue Specification, Running Work] defines it.

[#event-streams]
=== Events per Scope
_See Requirement link:../../Requirements.adoc#PM-ARCH-11[PM-ARCH-11: The Operator's Two Clients & Their Contract]_


The runtime streams its events as Server-Sent Events, one stream per scope, all with the same envelope, the one closed catalogue of named events (link:06-event-catalogue.adoc[Event Catalogue]), and the same resume rule:

* *The streams*: `GET /api/v1/events` (runtime-wide), `GET /api/v1/plans/{plan_id}/events`, `GET /api/v1/epics/{epic_id}/events`, `GET /api/v1/projects/{project_id}/workspace/events`, `GET /api/v1/machine/events`, `GET /api/v1/entries/{entry_id}/events`, and beside them `GET /api/v1/reports/events` (<<reports>>) and the activity stream of one task (link:../client-profiles/01-profile-schema.adoc#worker-activity[Client Profiles Specification, What a Worker Does]), which a client opens only while it shows the task. The runtime-wide stream announces every scope's start and end, every change of running work, and every change of a `needs_operator` summary, so that the overview needs no other stream.
* *Entries*: a start's entry is created under its project (`POST /api/v1/projects/{project_id}/entries`) and a project onboarding's at the top level (`POST /api/v1/project-onboardings`); each is addressed at the top level by its id, `/api/v1/entries/{entry_id}`, with its events at `/api/v1/entries/{entry_id}/events`. When an entry starts its scope, its stream announces the new scope with its link and ends; a project onboarding's entry moves into the project's workspace scope at `project.enrol`, and its stream announces the workspace stream to follow.
* *Envelope*: each event carries the SSE `event` field with its catalogue name, an `id` that increases within its stream, and `data`, a JSON object with `event`, `at` (RFC 3339 UTC), `scope` (`kind`, `id`, `project_id`), and the payload the catalogue names: identifiers, states, counts, and message keys with their arguments, never a model-facing representation and never a secret. A client that needs more reads the resource the event names.
* *Resume*: a client that reconnects with `Last-Event-ID` receives the events after it that the runtime still holds for that stream (link:../timeouts/02-runtime-leases-operator-web.adoc#event-buffer[Timeouts & Budgets Specification, Event Buffer]); otherwise, and always after a runtime start, it receives one `reset` event, which tells it to read the scope's resources again. The runtime keeps no subscription: an event is sent unbuffered to the streams open when it happens.
* *Ending a stream*: a stream on a web listener is checked against the device secret on connect; a revocation of the device, a closed listener, and the runtime's stop end it with the event `stream.closed` and its reason, which the web app shows (link:../cli-and-security/03-web-server.adoc#devices[CLI, Coordination & Security Specification, Devices in Both Clients]). `pm-operator` uses the same streams (`pm-operator status --watch`, and the terminal client while it is open).

[#process-resource]
=== The Plan's Process as a Structure
_See Requirement link:../../Requirements.adoc#PM-ARCH-11[PM-ARCH-11: The Operator's Two Clients & Their Contract]_


`GET /api/v1/plans/{plan_id}/process` answers the composed process of the plan instance in force (link:../workflow-dsl/09-plan-instance.adoc#plan-instance[Workflow DSL Specification, Plan Instance]) as a tree: the plan, its phases (link:../store-schemas/03-findings-and-review-records.adoc#phase-sub-workflows[Store Schemas Specification, Phases as Sub-Workflows]), every workflow's states in their order, and every call with the sub-workflow it calls, expanded, down to the leaves. It never answers DSL text; the instance text stays the resource `pm://plan/{plan_id}/instance` of the workers' surface.

* *Node*: each node has its `node_id` (the path of state ids from the plan unit, unique in the tree), its kind (`phase`, `sub_workflow`, `state`, and for a state its kind: server step, task, job, operator wait, decision, terminal), and its *state*, derived by the runtime from the plan's history (link:../store-schemas/02-workflow-state-store.adoc#plan-history[Store Schemas Specification, The Plan's History]): `done`, `running`, `planned`, `waiting_for_operator`, `failed`, `not_taken`, or `not_in_plan` with its prune reason; how often it ran and the run it is in; its first and last entry and exit times; and for a leaf its job or its tasks, each task with a link to its activity.
* *Position*: the path of `node_id` values to the plan's current position is part of the answer, so a client marks it and jumps to it.
* *Context*: the answer names the plan's project (`project_id` with its `display_name`) and its epic, where it has one (`epic_id` with its title), each with a link to its resource, the plan's activity (`running`, `pausing` with its point, `paused`), its `needs_operator` summary (<<needs-operator>>), and the tokens it used so far with their split and coverage.
* *Version*: the answer carries the plan's `instance_version`; a new instance version is announced on the plan's stream (<<process-events>>), after which a client reads the process again.

The validation of a designed unit answers its composed process in the same form, its nodes `planned` or `not_in_plan` (link:../workflow-dsl/04-ast-node-model.adoc#process-designer[Workflow DSL Specification, Designing a Process]).

[#process-events]
=== Events of the Process
_See Requirement link:../../Requirements.adoc#PM-ARCH-11[PM-ARCH-11: The Operator's Two Clients & Their Contract]_


The plan's stream announces each change of a node with the node's `node_id` and its new state, so a client updates the node without reading the process again: a state entered and left (`state.entered`, `state.left` with its outcome), a sub-workflow called and returned (`subworkflow.called`, `subworkflow.returned` with its outcome), a step firing opened and closed (`step.opened`, `step.closed`), a new instance version (`instance.changed`, after which the client reads the process again), the plan's activity (`activity.changed`), and the tokens used so far (`tokens.changed`, at most once per metrics event interval). Their payloads are listed in the link:06-event-catalogue.adoc[Event Catalogue].

[#needs-operator]
=== What Needs the Operator, at a Glance
_See Requirement link:../../Requirements.adoc#PM-ARCH-11[PM-ARCH-11: The Operator's Two Clients & Their Contract]_

_See Requirement link:../../Requirements.adoc#PM-WF-23[PM-WF-23: Operator Acts on Plans and Epics]_


The runtime derives for every plan, epic, and project a `needs_operator` summary on read, never stored, like `stalled`: whether anything needs the operator, how many items, and per item its kind and a link to it. The kinds form a closed list, in this order:

. `decision`: an open decision (link:../model-work/06-envelopes-questions-deadlines.adoc#decision-structure[Model Work Specification, The Decision Structure]);
. `waiver_request`: a waiver request (link:../workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]);
. `operator_wait`: any other operator wait: a consent, a decomposition or its review, an option asked when needed;
. `integrity_pause`, `stalled`, `condition`, `held`, `landing_failed`: the holds (link:../state-catalogue/01-conventions-generic-conditions.adoc#holds[State Catalogue Specification, Holds and Their Acts]); `landing_failed` covers an epic's landing, the removal from git of moved documents (`git.land-removal`), and the landing of a placed workflow unit (`git.land-unit`);
. `findings`: new findings of an epic (link:../model-work/08-epic-coordination.adoc#findings-watches[Model Work Specification, Findings and Watches]);
. `setup`: a project's setup repair or a step its onboarding owes.

The holds are resolved by their acts; the other kinds are answered where they are asked. A paused plan is no kind: pausing is the operator's own choice, and a paused plan shows by its activity. An epic's summary includes its plans'; a project's its plans', epics', and workspace scope's. A change of a summary is announced on the runtime-wide stream (`needs_operator.changed`).

=== The Overview Resource and Its Events
_See Requirement link:../../Requirements.adoc#PM-ARCH-11[PM-ARCH-11: The Operator's Two Clients & Their Contract]_


* `GET /api/v1/projects` lists the projects with running work, each with its `display_name`, its `needs_operator` summary, and its counts of active plans and epics.
* `GET /api/v1/projects/{project_id}` adds its active plans (each with its title, phase, activity, `created_at`, `phase_entered_at`, task progress, `needs_operator`, `off_track` with its signal (link:../model-work/03-supervision-and-recycling.adoc#worker-off-track[Model Work Specification, A Worker Off Track]), and the epic it belongs to), its active epics (each with its title, `created_at`, its counts of running and staged plans, and `needs_operator`), its open entries, and its running short landings; titles and times are those of the stores (link:../store-schemas/02-workflow-state-store.adoc#titles[Store Schemas Specification, Titles and Names]; link:../store-schemas/02-workflow-state-store.adoc#phase-start[The Start of the Current Phase]).
* The runtime-wide stream announces a project gaining or losing running work, a plan or epic starting or ending, a phase change, a plan's activity, a condition raised or cleared, an epic's plan changing its status, and a hold opened or cleared, each with the ids a client needs to update its overview without reading everything again (link:06-event-catalogue.adoc[Event Catalogue]).

=== The Projects of the Machine

* `GET /api/v1/projects?all` lists every enrolled project with its `display_name`, its remote, whether it is ready (its setup completed, or what it needs), its `needs_operator` summary, its counts of active plans and epics, its last activity, and whether it is released.

Beside them the runtime records per project, from the operator's acts in either client (opening a project, starting an epic or a plan, answering a decision, changing its configuration), when the operator last worked in it and how often over the last 30 days; the list carries both, for the clients' recent and most used.

[#epic-resource]
=== The Epic as a Resource
_See Requirement link:../../Requirements.adoc#PM-ARCH-11[PM-ARCH-11: The Operator's Two Clients & Their Contract]_


* `GET /api/v1/epics/{epic_id}` answers the header (title, state, automatic mode, `parallelization_scope`, `needs_operator`, its project by `project_id` and `display_name` with a link to the project's resource), the workstreams with their rows (status, what a row waits for with since when, the plan of a running row with its link), the sources' manifest, the landings, the counts of the registers, and the tokens the epic used (the sum of its plans, archived ones included, and of its own tasks).
* Sub-resources: `…/registers/findings` and `…/registers/watches` (link:../model-work/08-epic-coordination.adoc#findings-watches[Model Work Specification, Findings and Watches]), `…/decomposition` while a draft is open (link:../model-work/08-epic-coordination.adoc#decomposition-review[The Decomposition Is Reviewed]), `…/archive-check`, and `…/history`, the epic's events in order.
* The operator's acts on an epic are endpoints below it: `POST …/next-plan`, `…/decompose`, `…/archive`, `…/cancel` (with the choice for its plans), `PUT …/auto` (its automatic mode), `PUT …/settings`, and the review's dispositions (link:../model-work/08-epic-coordination.adoc#epic-actions[Model Work Specification, An Epic's Actions]; link:../model-work/08-epic-coordination.adoc#epic-auto[An Epic Runs by Itself]; link:../model-work/08-epic-coordination.adoc#epic-review[The Review]), each validated like every operator act and answered with the new state.
* The MCP resources `pm://epic/{epic_id}/*` stay the workers' read of the epic (link:../mcp-tools/03-resource-uris.adoc[MCP Tools Specification, Resource URI Surface]); a client of the operator reads the epic only here.

[#ended-work]
=== Ended Work
_See Requirement link:../../Requirements.adoc#PM-ARCH-11[PM-ARCH-11: The Operator's Two Clients & Their Contract]_

_See Requirement link:../../Requirements.adoc#PM-WF-13[PM-WF-13: Finalize Step Ordering Bands, Verdict Currency & Pre-Merge Barrier]_


* `GET /api/v1/projects/{project_id}/ended` lists the project's ended plans and epics, newest first, paged by a cursor, each with its outcome, reason, and end time: a plan's outcome is `merged`, `no_change`, `handed_back`, `returned`, `cancelled`, `abandoned`, `released`, or `aborted` (the abort that resolves an integrity pause, with the operator's reason); an epic's is its `terminal_reason`, `completed`, `cancelled`, or `released`.
* Each ended plan resolves, read from its archive (link:../filesystem-layout/03-project-store.adoc#archives[Filesystem Layout Specification, Archives]), to its process and history as it ended (`/plans/{plan_id}/process`), its completion report (<<reports>>), its decisions, its re-planning records, and its events; an ended epic to its header, rows, registers, landing record, and completion review. Everything of an archived plan or epic is read-only. A plan or an epic the cleanup deleted is left out of the list, and a link to it resolves to its tombstone, "deleted" with the date (link:../timeouts/03-retention-host-config.adoc#cleanup[Timeouts & Budgets Specification, One Cleanup]).
* Each ended plan or epic offers a read-only chat over its archived record with its planning role, whose one proposal is a follow-up plan that opens the start of a new plan naming the ended one (link:../state-catalogue.adoc#chat[State Catalogue Specification, Chatting with the Planning Role]).

[#reports]
=== Reports to the Operator
_See Requirement link:../../Requirements.adoc#PM-WF-21[PM-WF-21: Reports to the Operator]_

A report tells the operator what happened in a plan, an epic, a project, or the machine that the operator should know without having to act. It never asks anything: it has no operator link but _read_, changes no state, and adds nothing to `needs_operator`, so what needs the operator stays a decision, an operator wait, or a hold. The word _message_ stays with the outbox, inbox, and mailbox of plans and epics.

* *Record*: a report is a record of the machine scope: `report_id` (store-assigned, `rep-NNNN`, never reused, link:../identifiers/02-registry-stores-to-web.adoc#id-report-id[Identifier Registry, `report_id`]); `from`, the project (`project_id`), or `machine` for a report of the machine itself, with the epic (`epic_id`) and the plan (`plan_id`) where there are, each resolved to its resource; `kind`, from the catalogue below; `subject`, one line, and `body`, a short text, each a message key of the area `report` with its arguments; `created_at`, when it happened; `sent_at`, when the runtime made it available (later than `created_at` where it was written after a restart); `read_at` with the channel and device that read it; and `detail`, a link to its detail, where there is one. A reason the operator wrote, a provider's text, or a title is an argument, carried verbatim (link:../hypermedia-format/01-representation-and-link-forms.adoc#runtime-texts[Hypermedia Format Specification, Texts of the Runtime]).
* *Catalogue*, closed, each kind with the transition that writes it:
+
[cols="1,3"]
|===
|Kind |Written by, and its detail

|`plan.started` |the start transaction of a plan (`start.create-scope`), naming who started it: the operator, an epic, or a recipe; a plan an epic starts gives this one report, whose `from` names the epic
|`plan.ended` |a plan's terminal state, with its outcome; detail: its completion report, which for a plan of an epic leads on to the epic's landing record
|`plan.revised` |a re-planning applied (`replan.apply`) or a chat's revision (`chat.apply`); detail: the plan at the re-planning
|`plan.hold_released` |a hold ended, by an act or by itself
|`epic.launchable` |with the epic's automatic mode off, a row became launchable (written by `epic.next-work`); detail: the epic with its _next plan_
|`epic.waits_overlap`, `epic.overlap_found` |the overlap wait at admission and an overlap found while running (link:../model-work/08-epic-coordination.adoc#epic-auto[Model Work Specification, An Epic Runs by Itself])
|`epic.recut_applied` |a re-cut applied without the operator
|`epic.through` |every row shipped or ended; detail: the completion review, or, with automatic off, the epic with its _archive_
|`epic.ended` |`epic.archived` or `epic.aborted`, with its `terminal_reason`
|`project.onboarded`, `project.released` |the project's onboarding complete; the release of the project
|`source.flagged` |the screening flagged a stored source
|`decision.closed_elsewhere` |a decision answered in the other client or withdrawn
|`task.off_track` |the server took `yield` or `restart` on a worker off track; detail: the task's activity
|`system.cleanup_due` |work history became due; `from` the machine; detail: the cleanup job
|===
* *Store*: one append-only journal of the machine scope, `<PM_MCP_BASE>/state/reports.jsonl` (link:../filesystem-layout/02-machine-runtime.adoc#machine-layout[Filesystem Layout Specification, Machine-Wide Runtime Layout]), with the events `report` and `read`; a report's state (unread, read) is the fold of its events, like an inbox message's, and the journal has its own leaf lock, taken on the file like the audit log's. A report is appended after the transition it reports has committed, outside that transaction; a report that a committed transition owed when the runtime stopped is written at the next start from the transaction journal of its scope, with that `sent_at`. Unread reports never expire; read ones are kept until the cleanup deletes them on the operator's word.
* *Local API*: `GET /api/v1/reports?state=unread` answers the unread reports, newest first, with their count, grouped by project, then epic and plan (`?state=all` pages through the read ones as well); `POST /api/v1/reports/{report_id}/read` marks one read, and `POST /api/v1/reports/read` marks read exactly the reports whose ids the request names, so a report that arrived since stays unread; a client that opens a report's detail marks it read the same way. Each read records its channel and device and is idempotent, and a report read once is read for every device of the machine. `GET /api/v1/reports/events` announces `report.sent` and `report.read` with the ids.
* *Representation*: a report links its project, its epic, and its plan, and its detail with the relation `detail`, an operator resource of this API, never model-facing.
* [[completion-report]]*Completion report of a plan*: `GET /api/v1/plans/{plan_id}/completion` answers a view of an ended plan built from its archive and its records: the outcome and its reason, its pull request, the deliverables done, the re-planning records, the decisions taken, its duration, and its section _tokens_: the total with its split and the plan's wall time, per phase, per role, per model and harness, the waste (the tokens of tasks that produced nothing, spend class `no_product`, and of retries and remediation per cause class), and the coverage (link:../client-profiles/01-profile-schema.adoc#token-usage[Client Profiles Specification, Tokens, Not Money]). An epic's details are its landing record and its completion review.

[#runtime-metrics]
=== The Runtime's Metrics
_See Requirement link:../../Requirements.adoc#PM-ARCH-9[PM-ARCH-9: Runtime Metrics]_

The runtime keeps its figures as metrics in one registry of named counters, gauges, and timers. Each metric has one writer, its unit, and its labels from a closed set (`project`, `role`, `harness`, `model`, `kind`, `state`); its name is distinct from the names of the metrics store, whose rule of one writer per name it follows. No figure is computed by reading the stores on a request, and none ever leaves the machine (`PM-ARCH-2`). Which library implements the registry is open: see link:../../discussions/open-questions.adoc#metrics-library[Open Questions].

[cols="2,2,3"]
|===
|Metric |Unit, labels |Kept by

|`runtime.version`, `runtime.started_at`, `runtime.uptime` |text, instant, seconds |the start sequence
|`runtime.memory.heap`, `runtime.memory.resident`, `runtime.cpu` |bytes, bytes, percent |read from the process at a snapshot (`/proc` on Linux, the task information on macOS)
|`runtime.disk.machine_store` |bytes, with when it was measured |the periodic sweep (link:02-startup-recovery-drain.adoc#periodic-sweep[Periodic Sweep])
|`runtime.listeners` |state per listener |the transport
|`work.scopes` |count; `kind` (plan, epic), `state` (an activity, waiting for the operator, held), `project` |the transitions
|`work.tasks` |count; `state` (queued, running), `role` |the task queue
|`work.workers` |count; `role`, `harness`, `model`, `state` (busy, idle) |the supervisor
|`work.jobs` |count; `kind`, `state` (running, queued) |the job runner
|`work.slots` |count and cap; `kind` (build, model) |the slot scheduler
|`work.locks`, `work.leases` |count |the lock manager and the lease stores
|`models.calls`, `models.tokens_in`, `models.tokens_out`, `models.total_tokens` |count per hour, with the coverage of the hour; `model`, `role` |the transaction that writes a task row
|`models.errors`, `models.retries` |count per hour; `model`, `role`, cause class |the transaction that ends an attempt
|===

* *Where they come from*: the work's gauges are kept by the transitions, the queue, the supervisor, and the slots where things happen, and set from the recovered state at every start (link:02-startup-recovery-drain.adoc#per-project-recovery[Per-Project Recovery]); the models' hourly figures are filled at the start from the task rows of the metrics stores and the machine's usage aggregate `state/usage-aggregate.jsonl` (link:../timeouts/03-retention-host-config.adoc#cleanup[One Cleanup]), which stay the truth (`PM-ARCH-6`). Unmeasured usage is counted as unmeasured, never as `0`, and the models' figures are tokens only, never money. A figure the platform does not give is `unavailable`, never `0`.
* *Local API*: `GET /api/v1/system` answers the snapshot of the system view, with the window (`hour`, `today`, `7d`) and the project as parameters; `GET /api/v1/system/metrics` answers every metric of the registry with its labels. Both never wait for a project's recovery and mark a recovering project. The runtime-wide stream carries `system.metrics` with the figures that changed, at most once per metrics event interval (link:../timeouts/02-runtime-leases-operator-web.adoc#metrics-event-interval[Timeouts & Budgets Specification, Metrics Event Interval]). A paired device reads them like every resource.
* *Exposition*: `GET /api/v1/system/metrics` with `Accept: application/openmetrics-text` may answer the OpenMetrics text format, for a tool of the operator that holds the runtime token, on the socket only; the runtime opens no listener of its own for it (`PM-SEC-4`).
