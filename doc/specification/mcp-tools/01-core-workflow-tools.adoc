=== Architectural Constraints
_Implementation watch: link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-13[PM-WATCH-TOOL-13]_

1. *Small, Stable Verb Set*: PM-MCP exposes a fixed set of top-level MCP tools (`pm_state`, `pm_do`, `pm_wait`, `pm_build`, `pm_lsp`, `pm_skills`, `pm_skill`, `pm_skill_file`) rather than one tool per workflow step or script, and no other tool; no tool creates a scope (<<bootstrap-entries>>), lists plans or epics, or acts for the operator, whose views and acts are the local API's (link:../runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]). Each worker sees the `PM-MCP` tools its role artifact names, within the set its role's class allows (<<session-and-worker-surfaces>>); across all phases and domains these sets stay constant, and privileged operator acts are strictly excluded from the MCP surface (`PM-SEC-3`). Upstream MCP servers are called only server-side and never passed through (xref:02-service-and-skill-tools.adoc#_selective_upstream_mcp_proxy_meta_provenance_pm_svc_3[Selective Upstream MCP Proxy & `_meta` Provenance (`PM-SVC-3`)]). The set has no exception: no tool runs `plan-marshall` scripts (xref:02-service-and-skill-tools.adoc#no-script-execution[No Script Execution Surface]).
2. *Portable Naming Convention*: Every tool name conforms to the link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/identifiers/02-registry-stores-to-web.adoc#id-core-tool-name[core tool name grammar] (Identifier Registry), ensuring identical identifiers across Claude Code, OpenCode, Antigravity, Codex, and raw model tool-calling APIs without escaping or translation.
3. *Closed, Host-Portable Flat Schemas*: Every tool `inputSchema` conforms to JSON Schema Draft 2020-12 and declares `"additionalProperties": false` at the top-level object boundary. It uses only the subset every supported host and provider API accepts: a top-level `type: object` with `properties`, `required` (only parameters that are always required), and `additionalProperties`; per property `type`, `enum`, `pattern` without lookaround, `minimum`/`maximum`, `minLength`/`maxLength`, `default`, and `description`. Top-level `oneOf`/`anyOf`/`allOf`, `if`/`then`/`else`, `not`, and `const` are never used; the `$schema` and `title` members shown in this specification are documentation only and are not sent in `tools/list`. Rules the subset cannot express (mutually exclusive scope parameters, per-operation required parameters, path shape) are enforced by the server's argument validation and answered with the closed error of xref:04-errors-and-testing.adoc#protocol-errors-vs-domain-workflow-failure-states[Protocol Errors, Tool Execution Errors (`isError: true`) & Domain Workflow Failure States (`isError: false`)]; each such rule is stated in one line of the affected property's `description`. The final schemas are registered and called on a host before its client profile ships (Requirements appendix, gate 11).
4. *TOON Text Output Only (No `outputSchema`)*: Tools intentionally omit `outputSchema` and `structuredContent`. Every tool result is returned in a single MCP `TextContent` block (`type: "text"`) encoded in deterministic TOON (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/hypermedia-format.adoc[Hypermedia Format Specification]). This avoids resident output-schema token overhead while optimizing token density on every turn.
5. *Zero Client-Supplied Filesystem Paths*: No workflow or service tool accepts absolute filesystem paths or worktree locations from the model. Worktrees, branches, and configuration files are resolved server-side from `plan_id` or `epic_id`.
6. *Tool Loading*: A worker's launch loads the tools of its role artifact directly, with no deferred tool loading (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/04-worker-launch.adoc[Model Work Specification, Worker Launch]). No other preload rule exists.
7. *No Identity Arguments*: No tool schema declares an identity, role, or generation argument. The identity, role, and generation of the caller come from its connection (the job token and the relay's headers, link:../runtime-model/03-relay.adoc#_connection_metadata[Runtime & Interaction Model Specification, Connection Metadata]); the relay hides any such argument from the schemas the host sees and never forwards one a model invents (link:../runtime-model/03-relay.adoc#relay-rules[Runtime & Interaction Model Specification, Relay Rules]).
8. *Canonical Identifiers*: Every identifier property (`plan_id`, `epic_id`, `entity` including an `entry_id`, `link`, `job_id`, `module`, skill `uri` and `section`) and every identifier in link `args` (`lesson_id`, recipe key, `plan_slug`) uses the grammar of the link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/identifiers.adoc[Identifier Registry] (`plan_id` and `epic_id`: link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/identifiers/01-general-rules-and-registry.adoc#id-plan-id[`plan_id`]; the derivation rules stay in link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/phase-workflows/01-planning-phases-1-2.adoc#_plan_id_derivation_phantom_id_refusal_guard[Phase Workflows Specification, Plan ID Derivation]); every `pattern` below equals the registry grammar, and every example in this specification conforms to it.
9. *Model-Facing Minimality*: Every tool result and error payload, like every representation, carries only fields with an operational purpose for the model (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/hypermedia-format/01-representation-and-link-forms.adoc#model-facing-minimality[Hypermedia Format Specification, Model-Facing Minimality]). Implementation variants, derivation sources, internal versions and digests, confinement, timing, leases, generations, and audit identifiers (outside `internal_fault` and `file_unreadable`) are recorded in `audit.jsonl`, the job record, the queue task record, or the metrics store and served to the operator's clients over the local API; `ModelFacingFieldAuditTest` checks every result record against the registry of model-facing fields.
10. *MCP Is Not the Operator's Surface*: The MCP endpoint `/mcp` and the Local API `/api/v1` are separate surfaces on the runtime's Unix socket (link:../runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]); `/mcp` accepts only a job token. No MCP tool, resource, or link reaches an `/api/v1` endpoint, an operator wait, a decision, the web device store, pairing, or the web access settings, and no `pm_do` argument selects one; `/mcp` is never served over TCP: the web listeners route only the web app and `/api/v1/` and never accept the runtime token (link:../cli-and-security/03-web-server.adoc#two-listeners[CLI, Coordination & Security Specification, Loopback and LAN Listeners Side by Side]).
11. *Explicit Scope on Every Scoped Tool (`NO_PLAN` Sentinel)*: `pm_state`, `pm_do`, `pm_build`, `pm_lsp`, `pm_skill`, `pm_skills`, and `pm_skill_file` require exactly one of `plan_id` or, where the tool accepts epics, `epic_id`. `plan_id` is a real plan id or the literal `NO_PLAN`, a reserved value that cannot match the `plan_id` grammar (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/identifiers/01-general-rules-and-registry.adoc#id-plan-id[Identifier Registry, `plan_id`]) and addresses the scope without a plan of the worker's leased task: the project's workspace scope and its main checkout, or, for a task of the machine scope, the machine scope (`PM-ARCH-4`), resolved from the job record, never from a header. A call without a scope is refused with `invalid_arguments`; no tool infers a scope from an omitted parameter, and no tool takes a `scope: "workspace"` input (the `scope` enum stays in returned representations). Under `NO_PLAN`, `pm_state` and `pm_do` with `entity` address a task entity of the workspace or machine scope, a task of a start's entry by the `entry_id` its offer names (<<bootstrap-entries>>). `pm_wait` takes no scope: its offers name the scope and entity of the task. The sentinel mirrors `plan-marshall`'s `NO_PLAN` convention, applied to every scoped tool.

[#bootstrap-entries]
=== Starting a Scope Without a Creation Tool
_Implementation watch: link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/implementation-watch/store-schemas.adoc#PM-WATCH-STORE-2[PM-WATCH-STORE-2], link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-22[PM-WATCH-TOOL-22]_

No tool creates a scope. A plan or an epic is created by the start sub-workflow of its kind (`bootstrap-plan`, `bootstrap-epic`; link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue.adoc[State Catalogue], Bootstrap), a compiled-only entity unit hosted by the project's workspace scope. A client of the operator opens one over the local API (`POST /api/v1/projects/{project_id}/entries` with the kind, link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/09-bootstrap-and-lessons.adoc#start-from-clients[State Catalogue Specification, Starting from the Clients]); the runtime writes the pending entry directory `<PM_MCP_BASE>/projects/<project_id>/pending/<entry_id>/` with its record `entry.json`, its `sources/`, and its `chat/` (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/01-format-and-session-log.adoc#pending-entry-record[Store Schemas Specification, Pending Entry Record]). The entry's states are operator waits served to both clients (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/workflow-dsl/02-units-jobs-decisions.adoc#operator-wait[Workflow DSL Specification, Waiting for the Operator]); a worker of one of its tasks (the screening of a stored source) addresses it with the ordinary verbs and the `entry_id` as entity of the workspace scope: `pm_state(plan_id: "NO_PLAN", entity: "<entry_id>")` and `pm_do(plan_id: "NO_PLAN", entity: "<entry_id>", link, args)`, within the task entities leased to its generation. Concurrent entries never share a state position, and nothing is created under `plans/` or `epics/` before the commit, so an abandoned entry leaves no scope. An entry never expires: it stays among the project's open entries until it is started or abandoned, or deleted with the release of its project.

* *Ways to start are operator links*: What to work on is chosen through the operator links of the start's states (a plan from sources, a recipe, an epic); each source is gathered by a sub-workflow unit of its kind into the entry's list of sources, and the operator's description is stored by the start itself (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/09-bootstrap-and-lessons.adoc#start-from-clients[State Catalogue Specification, Starting from the Clients]). Every argument of an operator link is validated against its closed schema. No tool parameter and no CLI flag enumerates sources: a new way to start is one more unit and one more operator link.
* *Plans of an epic*: The runtime creates a plan of an epic itself, by running the plan's start with the source unit `source-epic-row` for a launchable queue row of the epic (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/08-epic-coordination.adoc[Model Work Specification, Epic Coordination]); no client offers this source.
* *Commit in the `start.create-scope` transaction*: When the start commits (the `create` link of `start.ready` or `start-epic.ready`, whose primitive `start.create-scope` returns `created`, entering the terminal `start.committed` or `start-epic.committed`, or `refused{reason}`, returning to the ready state), the engine creates the scope from the gathered record. It composes and checks the scope's plan instance or epic workflow (every role it names must be defined, `role_undefined`, fit its use, `class_mismatch`, and every skill its `skill` clauses name must resolve, `skill_unresolved`), takes the local-changes snapshot, and re-observes a pull request's head. The writes span several stores and follow a fixed order, the new scope first because it is the authoritative store: (1) the new scope in its own transaction (a plan's directory built complete in the sibling temporary directory `plans/.init-<entry_id>/` and published by one atomic directory rename to `plans/<plan_id>/`; `mcp/status.json` initialized with its `title` and `created_at`, `origin.epic_id` bound for an epic row, the entry's sources moved into the scope's source directory (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/filesystem-layout/03-project-store.adoc#source-directory[Filesystem Layout Specification, The Source Directory]) and its chat transcript beside them; for a new epic its git-tracked ledger is written before its machine scope, so a crash between them leaves a ledger the start adopts, link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/09-bootstrap-and-lessons.adoc#state-catalogue-bootstrap-epic[State Catalogue Specification, Bootstrap of an Epic]); (2) for a `local_changes` plan, the capture ref `refs/pm-mcp/captures/<plan_id>` at the recorded `captured_changes.snapshot_sha`; (3) for an epic row, the queue row set `running` with `started_at`; (4) the claim of a lesson source (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/10-job-and-lesson-records.adoc#lesson-record[Store Schemas Specification, Lesson Record, Claim]); (5) the deletion of the pending entry directory. A plan is live when `plans/<plan_id>/mcp/status.json` exists, and every enumeration of live plans lists only such directories. The project's startup recovery deletes an orphaned temporary init directory `plans/.init-*`, re-creates a missing capture ref of a non-terminal plan at its `snapshot_sha`, and derives every other later write from the existing scopes, by the rules of link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/01-format-and-session-log.adoc#transaction-journal[Store Schemas Specification, Transaction Journal] (Writes outside the scope), run as a step of link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/runtime-lifecycle/01-startup-recovery-drain.adoc#per-project-recovery[Runtime & Interaction Model Specification, Per-Project Recovery]. After the commit the report `plan.started` is written (link:../runtime-model/01-processes-and-transport.adoc#reports[Runtime & Interaction Model Specification, Reports to the Operator]), the entry's stream announces the new scope, and the runtime drives it. A later request naming the consumed `entry_id` is answered `scope_not_found`.
* *Epic adoption*: An `epic` entry whose id names an existing git-tracked ledger (`.marshall/epics/<epic_id>/` with `epic.json`) without machine scope is adopted (the operator link `adopt:<epic_id>`, or directly for a requested id): the adoption's `start.create-scope` transaction (outcome `adopted`) consumes the pending entry as above and creates only the machine scope from the ledger, which it never rewrites (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/state-catalogue/09-bootstrap-and-lessons.adoc#state-start-epic.adopt[State Catalogue, `start-epic.adopt`]).
* *Epic membership*: A plan whose `plan_id` equals a non-terminal queue row of an epic is created only by the runtime's start of that row; an operator's entry deriving that `plan_id` is not committed (`epic_pointer_mismatch`, <<bootstrap-commit-recheck>>).

[#bootstrap-commit-recheck]
==== Start Commit Re-Check
_Implementation watch: link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-15[PM-WATCH-TOOL-15]_
The checks the start made while gathering can be invalidated before the commit (a concurrent plan takes the identifier, the operator releases the project, a team file or a role set is edited). The `start.create-scope` transaction therefore re-checks them under the workspace lock; a failing check creates nothing, keeps the pending entry, and returns the entry to its ready state with the refusal (`reason`, `detail` as a message key) and the server-computed alternatives, shown to both clients, so the operator corrects the input (a new identifier) or takes the act the refusal names, and commits again. For a plan of an epic, the runtime records the refusal on the epic's queue row and launches nothing (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/08-epic-coordination.adoc[Model Work Specification, Epic Coordination]). The closed reasons:

[cols="1,3"]
|===
|`reason` |Check and `facts`

|`plan_id_taken`
|The derived `plan_id` (or `epic_id`) names a live or archived scope, or (`epic_id`) an existing ledger, which is adopted instead of re-created (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/phase-workflows/01-planning-phases-1-2.adoc#_plan_id_derivation_phantom_id_refusal_guard[Phase Workflows Specification, Plan ID Derivation]); `facts` name where it exists and a free alternative slug. An archived identifier is never reused.

|`lifecycle_closed`
|The plan lifecycle is not offered in the project: the lifecycle gate, a compiled constant of the release, is closed and the project is not enrolled as a pilot (`pm-operator enrol --pilot`), or the project was released (its store records the release, link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/credentials-and-enrolment/02-enrolment-and-project-lifecycle.adoc#enrolment-lifecycle-release[CLI, Coordination & Security Specification, Enrolment, Lifecycle Gate & Release]).

|`config_dirty`
|A file under `.marshall/config/` (a team file or a workflow unit) is modified, staged, or untracked in the main checkout; the refusal names the porcelain state and the resolutions (commit or restore; after a stepped-out setup commit, `retry` of `setup.commit-changes`). A local-changes source is exempt: the file is then part of the captured change set.

|`config_invalid`, `format_outdated`, `format_newer`
|A team configuration file or a project workflow unit fails validation or has an unsupported `format_version` (xref:04-errors-and-testing.adoc#rejection-reasons[Closed Rejection Reasons]); the refusal names the file and the finding.

|`role_undefined`
|The plan instance or epic workflow composed for the commit names a role that the effective role set does not define, or whose artifact is invalid (`PM-WORK-1`, link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/01-roles-and-configuration.adoc[Model Work Specification, Roles & Configuration]); the refusal names the role, the state that names it, and links the role set in the machine's settings.

|`class_mismatch`
|The plan instance or epic workflow composed for the commit names a role whose class does not fit its use: the class the state's entity kind requires, or a `zero_tool` role in a `consult role` clause (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/01-roles-and-configuration.adoc#role-composition[Model Work Specification, Composition Check]); the refusal names the role, its class, the state, and the required class, and links the role set.

|`skill_unresolved`
|The plan instance or epic workflow composed for the commit has a `skill` clause naming a skill that does not resolve in the project's skill catalogue (absent, or an extension skill that is missing or refused; `PM-SKILL-5`, link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/workflow-dsl/04-ast-node-model.adoc#static-verification-rules[Workflow DSL Specification, Rule 14]); the refusal names the skill and the state that names it.

|`quorum_invalid`, `quorum_not_diverse`
|A quorum declaration of the plan instance or epic workflow composed for the commit fails its check against the effective role set (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/10-decision-quorum.adoc#decision-declarations[Model Work Specification, Decision Declarations]; link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/workflow-dsl/04-ast-node-model.adoc#static-verification-rules[Workflow DSL Specification, Rule 13]); the refusal names the declaration, the rule, and the role, and links the role set.

|`integration_variant_unset`
|An integration whose used features the `native` variant cannot serve has no operator choice of its variant; the refusal names the integrations and links the project setting that chooses the variant.

|`lesson_unavailable`
|The source lesson was claimed by another plan, retired, or no longer resolves `found` since `source-lesson` checked it; the refusal names its state.

|`no_local_changes`
|The local-changes snapshot taken at commit is empty (no dirty or staged path, no commit ahead of the base branch); the refusal names the base branch.

|`pr_not_open`, `head_not_writable`
|The re-observed pull request is no longer open, or its head branch can no longer be pushed to by the agent identity; the refusal names the pull request.

|`epic_pointer_mismatch`
|An operator's entry derives a `plan_id` that equals a non-terminal queue row of an epic; the refusal names the epic and the row. A refused server start of a row is no tool error: it marks the row `held` (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/08-epic-coordination.adoc#server-started-plans[Model Work Specification, Server-Started Plans]).
|===

The re-check is a transition of the start, not a rejection: the operator link's answer is the entry's ready state with the refusal. Its reasons belong to the failure class `precondition` and, since no plan exists, are recorded in the audit log only and never counted per plan (xref:04-errors-and-testing.adoc#rejection-reasons[Closed Rejection Reasons & Failure Classes]). Parameter names follow the `<entity>_id` naming rule of the link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/identifiers.adoc[Identifier Registry] (`plan_slug`, `epic_id`, `plan_id`); this is a PM-MCP rule and deliberately differs from `plan-marshall`'s proposed ADR-023, which names the epic with the bare entity noun (`--epic`).

=== `pm_state` — Query Authoritative Hypermedia State

Returns the current hypermedia representation (`state`, `summary`, `skill` URI, domain `facts`, and valid `links`) of a task entity leased to the calling worker's generation (e.g., task envelope `envelope-2` or finding `F-12`, <<job-bound-connections>>), within the scope its offer names: a plan or an epic by its id, or, with `plan_id: "NO_PLAN"`, the workspace scope or the machine scope of the worker's task (`PM-ARCH-4`), a task of a start's entry by its `entry_id` (<<bootstrap-entries>>). A plan or epic representation without `entity` is a view with no links (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/hypermedia-format/01-representation-and-link-forms.adoc[Hypermedia Format Specification]).

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "pm_state",
  "description": "Return the current TOON hypermedia representation and valid links of a task entity offered to you, or the view of its plan or epic.",
  "type": "object",
  "properties": {
    "scope": {
      "type": "string",
      "enum": ["plan", "epic", "entity"],
      "description": "Optional explicit scope discriminator (inferred from plan_id/epic_id/entity when omitted)."
    },
    "plan_id": {
      "type": "string",
      "pattern": "^([a-z0-9][a-z0-9-]{1,62}[a-z0-9]|NO_PLAN)$",
      "description": "Identifier of the target plan scope, or the literal NO_PLAN for the project's workspace scope, or for the machine scope where the worker's task is of the machine scope (resolved from the job record). Exactly one of plan_id or epic_id is required (server-enforced)."
    },
    "epic_id": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$",
      "description": "Identifier of the target epic scope. Mutually exclusive with plan_id."
    },
    "entity": {
      "type": "string",
      "pattern": "^[A-Za-z0-9][A-Za-z0-9_.-]{0,63}$",
      "description": "Optional entity identifier: a task entity as its offer names it, such as 'envelope-1', 'F-12', 'enrich-core', or a consultation_id (a worker may name only an entity offered to it, server-enforced); with plan_id NO_PLAN also an entry_id its offer names."
    }
  },
  "additionalProperties": false
}

[#question-waiver-facts]
==== Decisions & Waiver Requests in Representations

A decision and a waiver request are operator waits: they are served to the operator's clients over the local API (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/06-envelopes-questions-deadlines.adoc#decision-structure[Model Work Specification, The Decision Structure]; link:../runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]) and never to a model as a link or as a fact to relay (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/hypermedia-format/01-representation-and-link-forms.adoc#operator-command-relay[Hypermedia Format Specification, No Operator Relay]). The records are readable by a worker of the project as the resources `pm://plan/{plan_id}/questions` (`pm://epic/{epic_id}/questions` for the epic scope, `pm://workspace/questions` for the workspace scope) and `pm://plan/{plan_id}/waivers` (xref:03-resource-uris.adoc#_normative_resource_uri_templates[Resource URI Surface]); `pm_state` and `pm_do` render them only as far as a worker acts on them:

* *A worker's own question*: the `ask` link of a task creates the decision; where the task continues it rests in `awaiting_answer` and receives the answer in `facts.answers`, otherwise the task of the state re-entered after the answer receives it there (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/hypermedia-format/01-representation-and-link-forms.adoc#answers-facts[Hypermedia Format Specification, `facts.answers`]).
* *A quorum's vote*: while a quorum adjudicates a decision, a listed role votes through the links of its own vote task entity, blind to the recommendation (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/10-decision-quorum.adoc#adjudication[Model Work Specification, Ask or Quorum]).
* *A waiver request*: the `request_waiver` link files it and ends the task; the unit's operator wait offers no model link, and a view of the plan shows nothing of it.

The channels of answers, the answering devices, the interpretation of own words, waiver consumptions, and the operator identity are recorded, never rendered. Answered decisions reach a worker only through their effect (an amendment, the next state) and, for the task that continues an asking task, as `facts.answers`.

=== `pm_do` — Follow a Hypermedia Link
_Implementation watch: link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-1[PM-WATCH-TOOL-1]_

The sole state transition verb of the MCP surface. Executes the transition identified by `link` from the current representation of a task entity leased to the calling worker's generation, in the scope its offer names (`plan_id`, `epic_id`, or `plan_id: "NO_PLAN"` for the workspace or machine scope), passing any judgment parameters in `args`. Its links are those of the leased task entity (the acknowledgement `ack` and the `consult:<role>` links included). No link waits on or cancels a job: waiting on a job and cancelling it are engine events (`PM-WF-8`).

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "pm_do",
  "description": "Follow a hypermedia link from the current representation with its required free parameters.",
  "type": "object",
  "properties": {
    "scope": {
      "type": "string",
      "enum": ["plan", "epic", "entity"],
      "description": "Optional explicit scope discriminator."
    },
    "plan_id": {
      "type": "string",
      "pattern": "^([a-z0-9][a-z0-9-]{1,62}[a-z0-9]|NO_PLAN)$",
      "description": "Identifier of the target plan scope, or the literal NO_PLAN for the project's workspace scope, or for the machine scope where the worker's task is of the machine scope (resolved from the job record). Exactly one of plan_id or epic_id is required (server-enforced)."
    },
    "epic_id": {
      "type": "string",
      "pattern": "^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$",

    },
    "entity": {

      "description": "Optional entity identifier: the task entity whose link is followed, as its offer names it (a worker may name only an entity offered to it, server-enforced); with plan_id NO_PLAN also an entry_id its offer names."
    },
    "link": {
      "type": "string",
      "pattern": "^[a-z][a-z0-9_-]{0,31}(:[A-Za-z0-9][A-Za-z0-9_.-]{0,63})?$",

==== Two-Stage Schema Validation for `pm_do`

1. *Stage 1 (Tool Argument Validation)*: The server's own argument validator (plain Java over the flat schema and the rules stated in the property descriptions; no JSON Schema library) checks the payload: `additionalProperties: false`, valid `plan_id`/`epic_id`, exactly one scope, syntactic `link` pattern, `args` is a JSON object. A violation is a tool execution error: `isError: true`, `error_code: invalid_arguments`, the offending `parameter`, and the violated `rule` (xref:04-errors-and-testing.adoc#protocol-errors-vs-domain-workflow-failure-states[Protocol Errors, Tool Execution Errors (`isError: true`) & Domain Workflow Failure States (`isError: false`)]). The Quarkus MCP server runs with `quarkus.mcp.server.tools.input-validation-error=TOOL`, so its own parameter binding reports the same way.
2. *Stage 2 (Workflow Engine Link Schema)*: Under the scope's exclusive lock, the engine resolves the active `LinkSpec` for `link` in the current state and validates `args` against the link's dynamically derived closed JSON Schema (`additionalProperties: false`, exact required free parameter keys, closed enum values, string length bounds, and integer ranges); on a task entity it also checks the lease and the generation (`PM-WORK-2`). If `args` fails Stage 2 validation or `link` is not offered in the current state, the engine returns `isError: false` with a structured `rejected` block and the fresh representation (see xref:04-errors-and-testing.adoc#protocol-errors-vs-domain-workflow-failure-states[Protocol Errors, Tool Execution Errors (`isError: true`) & Domain Workflow Failure States (`isError: false`)]). A submit that misses a required reference (for example to a consultation it made) is refused this way with a reason the worker can act on.

=== `pm_wait` — Receive a Task
_See Requirement link:../../Requirements.adoc#PM-WORK-2[PM-WORK-2: Task Protocol]_
_Implementation watch: link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/implementation-watch/hypermedia-format.adoc#PM-WATCH-HYP-9[PM-WATCH-HYP-9]_

_See Requirement link:../../Requirements.adoc#PM-IMPL-4[PM-IMPL-4: Bounded Long-Poll & Progress-Reset Waiting Primitives]_

The only way a worker receives work. The semantics (offer, lease, acknowledgement, the task's states and outcomes, fencing, consultation answers) are those of the task protocol (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/02-task-protocol.adoc[Model Work Specification, Task Protocol]); this section defines the tool.

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "pm_wait",
  "description": "Wait for the next task. Answers with an offered task, with wait_again, or with end. Call it again after wait_again and after each submitted task.",
  "type": "object",
  "properties": {},
  "additionalProperties": false
}
----

* *No arguments*: `pm_wait` takes no scope and no identity argument. The caller's identity, role, and generation come from its connection (link:../runtime-model/03-relay.adoc#_connection_metadata[Runtime & Interaction Model Specification, Connection Metadata]); a call with any argument is refused with `invalid_arguments`.
* *Bounded*: The call blocks at most the bounded wait of the caller's harness (`connection.bounded_wait_seconds` of its client profile), with progress frames where the connection supplied a `progressToken` and the profile states that progress resets the host's timeout (link:../runtime-model/04-sessions-and-workers.adoc#_connection_scoped_rendering[Runtime & Interaction Model Specification, Connection-Scoped Rendering]; link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/timeouts/01-job-budgets-and-waits.adoc#bounded-wait[Timeouts & Budgets Specification]). It returns before the host's limit in every case.
* *Answer `offer`*: `answer: offer`, followed by the representation of the offered task entity, identifiers and links first: `queue_task_id`, the scope and `entity`, and `links` stand before `state`, `summary`, `skill`, `facts`, and the skills, so a host that cuts a long tool result never cuts the task's address. Where the whole answer would exceed the tool-result limit of the worker's harness, it ends after the identifiers and links with `parts[N]{uri}`, the remaining content as resources in reading order (xref:03-resource-uris.adoc#task-part-resource[Resource URIs]; link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/02-task-protocol.adoc#offer[Model Work Specification, Offer]). The representation is that of the offered task entity (scope, `plan_id` or `epic_id` (neither for a task of the workspace scope, which the worker addresses with `plan_id: "NO_PLAN"`), `entity`, `state`, `summary`, `skill`, `facts`, and its links: while offered only `ack`), and the required skills: `skills_in_band[]{uri, section, content}` for the skills this generation has not received yet, and `skills_named[]{uri}` for the others, whose digests travel in the result's `_meta`, never in the model-facing payload (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/04-worker-launch.adoc#skill-delivery[Model Work Specification, Skill Delivery]). A submit is refused `skills_not_loaded` until every named skill was loaded (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/04-worker-launch.adoc#skills-loaded-at-submit[Model Work Specification, Loaded before Submit]). The task is leased to the caller's generation when the offer is written, never before; a cancelled wait consumes no task. The answer to a consultation the caller asked arrives the same way, as the asking task with the answer in its `facts`, exactly once and only to the asking generation (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/05-consultation.adoc[Model Work Specification, Consultation]).
* *Answer `wait_again`*: `answer: wait_again` and nothing else: the bounded wait passed without a task; the caller calls `pm_wait` again.
* *Answer `end`*: `answer: end` and nothing else: the caller ends (a fresh worker after its task, a recycled warm worker, a draining runtime, a worker whose plan was paused).
* *Refusals*: A call of a fenced generation is refused `generation_fenced`, a call carrying the token of an ended job `job_ended` (xref:04-errors-and-testing.adoc[Errors]). A task leased to a generation is never offered to a second concurrent `pm_wait` of the same generation.

=== Worker Connections
_Implementation watch: link:../../implementation-watch/mcp-tools.adoc#PM-WATCH-TOOL-16[PM-WATCH-TOOL-16]_

_See Requirement link:../../Requirements.adoc#PM-SEC-3[PM-SEC-3: Operator Channel Isolation (Operator CLI & Paired Web Devices)]_

Every worker is a job of kind `llm` that the runtime launches through the headless CLI of an enrolled harness (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/04-worker-launch.adoc[Model Work Specification, Worker Launch]); the host never starts one. The worker connects back through the relay `pm-mcp serve --job`, which presents the job token and the generation instead of the runtime token (link:../runtime-model/01-processes-and-transport.adoc#job-token[Runtime & Interaction Model Specification, Local Trust: Job Token]). The runtime resolves the job from the token on every request and binds the call to its job and generation, without connection state:

* *Tool set*: The `PM-MCP` tools its role artifact names, within its class's column (<<session-and-worker-surfaces>>).
* *Resources*: `resources/list` and `resources/read` work read-only for every resource of the worker's own project and `skill://pm/…` (for a task of the machine scope only `skill://pm/…`) (xref:03-resource-uris.adoc#_normative_resource_uri_templates[Resource URI Surface]). The project boundary is the only read boundary; the task binding below applies to tools, not to resources. A URI carries no project: the runtime resolves it in the worker's project, taken from the job record, so a URI that names a plan or epic of another project is the resource read error `-32002` with `error_code: scope_not_found`, (xref:04-errors-and-testing.adoc[Errors & Testing]).
* *Task binding*: The scope argument (`plan_id`, `epic_id`, or `NO_PLAN` for a task of the workspace or machine scope, whose representation carries neither identifier) and, for `pm_state` and `pm_do`, the `entity` argument must name a task entity leased to the worker's generation, by the scope and `entity` of its offer (the scope entity such as `envelope-3`, for a task whose state names no scope entity its `queue_task_id`, for a consultation task its `consultation_id`; a `queue_task_id` is never passed otherwise); `pm_build` and `pm_lsp` must name the scope of such a task. Any other value is refused with `job_scope_mismatch` (`isError: true`), audited.
* *Links*: The worker's representation renders only the links of its leased task entity, and never a link whose target starts a model (the leaf rule, `PM-WF-5`); a consultation goes through the server as a `consult:<role>` link (`PM-WORK-4`). A `pm_do` naming any other link is rejected `link_not_available`. Deliverables reach the server only through the entity's `submit` links.
* *Fencing and end*: A call of a fenced generation is refused `generation_fenced`; the token is revoked with the fence or the job's fate, and a call carrying the token of an ended job is refused `job_ended` (`isError: true`).
* *Identity*: A worker connection carries no identity but its job's: it takes its client profile from its role's harness, recorded in the job record, and its audit records carry its `job_id`, role, and generation.
