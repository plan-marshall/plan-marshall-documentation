This is not a summary of the article. It keeps what is useful for PM-MCP and says where it touches our documents. The
article is an opinion piece; most of its evidence is cited, not its own, and it says itself that no study measures the
maintainability of code written entirely by agents.

== What Is Interesting for Us

=== Clean code buys cost, not success

The one hard number comes from a controlled study (arXiv:2605.20049): 660 trials of the same tasks on clean and
deliberately messy versions of behaviourally identical repositories.

* The pass rates are the same (91.3 % clean, 92.1 % messy).
* The clean repositories cost 7–8 % fewer tokens and about a third less re-reading of files the agent had already
  opened.
* The saving comes almost entirely from tasks that span several modules. A task inside one complex function shows no
  saving.

The paper itself is a little more mixed than the article says: on single-function tasks the cleaner side used slightly
_more_ tokens. See xref:clean-code-to-clean-spec-cleanliness-study.adoc[the analysis of the study].

So structure matters to an agent as navigation cost: a name or a module boundary that lets the agent skip reading a
body saves tokens. Readability inside one function, which is what Clean Code mostly optimises, saves nothing.

=== Which rules still serve an agent reader

The article reads Clean Code as a compression scheme for human working memory. With an agent as the reader, it sorts
the rules as follows:

* *Names survive, for a new reason.* An intention-revealing name lets the agent skip the implementation. Agents default
  to generic names (`data`, `handler`, `result`), which force the next agent to read what it could have skipped. So
  naming is now about machine legibility, not courtesy to colleagues.
* *Extreme decomposition works against it.* Following Ousterhout's _shallow modules_, many tiny functions with
  interfaces as complex as their bodies scatter one piece of logic over many places. For a human that was a cognitive
  tax; for an agent it is a context tax. Deep modules (a small interface over a substantial implementation) fit an
  agent better than small functions.
* *Comments move to where the agent reads them.* "Comments are a failure" becomes: write the constraints that the code
  cannot show (limits, envelopes, settled assumptions) where the agent will read them.

=== Local quality is not global quality

The opening failure: every diff passed the Clean Code checklist, yet the agent had implemented the same retry logic in
four modules. Two production failures followed. The article cites commit-mining data showing the same pattern: the
debt of agent-written code gathers in duplication, error paths, shallow happy-path tests, stale API calls and
architectural placement. Those are exactly the places where a human reading every line used to be the only check.

A review that looks only at the diff cannot see this. The check has to compare the change with the rest of the
system.

=== Verification replaces reading

Robert C. Martin no longer reads his agents' code. He enforces cleanliness through measurements instead: cyclomatic
complexity, module size, dependency structure, acceptance tests and mutation testing. TDD survives as the guard against
an agent that makes a failing test pass by deleting it, a known form of reward hacking.

=== The six-element framework (Clean Spec)

Spec Kit, Kiro and OpenSpec agree on six things a spec must pin down:

. *Outcomes*: the success scenarios and the behaviour at the end.
. *Scope boundaries*: what is explicitly in and what is out. The article calls this the cheapest control against
  hallucination.
. *Constraints*: limits and assumptions that the code does not show.
. *Decisions already made*: the settled architecture, so the agent stops re-arguing it on every feature.
. *Task decomposition*: deterministic stages, each sized to fit a context window.
. *Verification criteria*: validation steps and edge cases. This is the element most often missing.

The article notes that none of these tools has an agreed enforcement standard. The one pattern that already works like
a rule is the _constitution file_: rules for the whole project that an agent may not break, set once before any
feature work.

== Where It Touches Our Documents

=== Our planning pipeline is a Clean Spec with server enforcement

checked by the server, not by a reviewer.

=== Steering the coding agents through skills

Skills are our lever on how the agents write code. Domain standards are vocabulary skills
(xref:../Requirements.adoc#PM-SKILL-1[PM-SKILL-1]), the server delivers each task the skills it needs and checks that
they were delivered (xref:../Requirements.adoc#PM-SKILL-4[PM-SKILL-4]), the team adds its own as extension skills
(xref:../Requirements.adoc#PM-SKILL-5[PM-SKILL-5]), and a role is graded against a corpus before it runs
(xref:../Requirements.adoc#PM-WORK-6[PM-WORK-6]). The article suggests what those skills should say:

* *Write the domain standards for an agent reader.* Use the article's test for every rule: does it protect the intent
  of the system, or the comfort of a human reader? Keep and sharpen the first kind: intention-revealing names (no
  `data`, `handler`, `result`), deep modules with small interfaces, comments for contracts and constraints the code does
  not show. Drop or soften the second kind: function-length limits, "one level of abstraction", "no comments". The
  standards we bring over from plan-marshall (the `pm-dev-*` skills) should get this review when they become the
  domain skills of PM-MCP.
* *Reuse before writing.* The retry-logic failure is the main risk for a writer worker with an empty context. Two
  places could counter it: the outline could name the existing facility a deliverable reuses for a cross-cutting
  concern (retry, error handling, validation), and the implementing role's skill could make looking it up a step before
  writing.
* *Expect the token gain only across modules.* The study found no gain inside one function. If we measure the effect
  of a skill change, deep-lane plans across several modules are where it can show, not surgical or light-lane plans.

=== Measuring the saving

We already record the usage of every turn and every task and compare it with the predicted cost of the task
(xref:../Requirements.adoc#PM-WORK-7[PM-WORK-7],
link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/09-completion-usage-and-spend.adoc[Model Work, Completion, Usage & Spend]).
The study's second measure, re-reading files already read, is not computed today. It can be derived from the
`tool_call` entries the activity already records
(xref:clean-code-to-clean-spec-cleanliness-study.adoc#_the_revisit_measure_is_already_in_our_activity_records[the analysis of the study]).
As a measure per project it would show how legible a codebase is to the agents, and whether a change of the domain
skills makes it cheaper to work in. That would make skill tuning evidence-based, the same way role qualification
works.

=== Verification over reading

Much of Martin's move is already ours:

* A test that pins a defect is rewritten, never deleted
  (xref:../implementation-watch/cross-cutting.adoc#PM-WATCH-GEN-30[PM-WATCH-GEN-30]), and a test that simplify deleted
  is verified again
  (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/implementation-watch/phase-workflows.adoc#PM-WATCH-PHASE-61[PM-WATCH-PHASE-61]).
  These are the guards against the test-deleting reward hack.
* The finalize pipeline runs the project's quality gate and polls the code analysis providers, and a self-review
  surfacer that did not run is never `clean`
  (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/domain-extensions/05-recipes-and-extension-points.adoc#self-review-surfacer[Self-Review Surfacer]).

Missing:

* Mutation testing appears nowhere in our documents.
* Complexity and module-size thresholds are left to the project's own tools.
* The self-review surfacers look only at the plan's diff. A re-implementation of something that already exists
  elsewhere in the codebase is out of their sight, and that is exactly the article's failure.

== Candidates for a Change

Nothing is applied. None of these corrects an existing requirement; each one is new scope for the operator to decide.

. *Structured acceptance criteria and explicit out-of-scope items per deliverable* in the outline. `OutlineValidator`
  would check their presence, and `review-requirement` would judge the change against them. This would be a change of
  the outline format in
  link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/phase-workflows/02-planning-lanes-phases-3-4.adoc#outline-validation-gate[Phase Workflows, Outline Validation Gate].
. *A named home for the settled decisions of a project* (the constitution): document the project extension skill with
  `domains` as that place, perhaps with a template that onboarding offers. This affects
  xref:../Requirements.adoc#PM-SKILL-5[PM-SKILL-5] and xref:../Requirements.adoc#PM-EXT-8[PM-EXT-8].
. *Machine-legibility rules in the domain skills*, as a content guideline for the domain standards under
  xref:../Requirements.adoc#PM-SKILL-1[PM-SKILL-1].
. *A detector for re-implementations*: a self-review surfacer detector that compares new code of the diff against the
  existing codebase (cross-cutting concerns first).
. *Mutation testing as an optional verification verb* of a domain, configurable like the other per-deliverable verbs.
. *Re-reads as a usage measure* per task and per project, beside the token columns, derived from the activity
  records.

The analyses of the sources below add further candidates.
