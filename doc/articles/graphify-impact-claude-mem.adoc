This is not a summary of the tool. It keeps what is useful for PM-MCP and says where it touches our documents. It is
based on the README, which does not describe its compression step, its token budgets or how it keeps memories
correct. Its only figure ("~10× token savings") has no method behind it.

== What Claude-Mem Does

* *Captures everything through hooks*: session start, prompt submit, before and after every tool use, stop and session
  end. Tool use becomes an _observation_.
* *Compresses with a model* into semantic summaries. The model is a hosted observer, the user's own key, or the user's
  plan.
* *Stores* sessions, observations and summaries in SQLite with full-text search, plus a vector index, combined into a
  hybrid search. A local worker serves an HTTP API and a viewer. Cloud sync is optional.
* *Injects context at session start*, limited by a count of observations.
* *Retrieves by progressive disclosure*: a search returns a compact index (about 50–100 tokens per hit), a timeline
  gives the context around a hit, and full observations (about 500–1,000 tokens each) are fetched only by id.
* *Excludes* content wrapped in `<private>` tags.
* *Keeps nothing correct*: no detection of outdated memories, no resolution of contradictions, no expiry. Observations
  have ids that can be cited, and that is all.

== Where It Touches Our Documents

=== We remember differently, on purpose

Claude-Mem assumes one long-lived assistant whose sessions should continue each other. PM-MCP does the opposite. A
successor worker starts with an empty context and "nothing is handed over, because every task carries what its state
needs" (xref:../Requirements.adoc#PM-WORK-2[PM-WORK-2]). What lasts beyond a task is written by the server as records:

* *Within a plan*: the clarified request, the outline, the decision records with their corrections
  (xref:../Requirements.adoc#PM-WF-19[PM-WF-19]), and the facts of each state.
* *Across plans*: lessons (with category, rule and sources), the architecture inventory
  (xref:../Requirements.adoc#PM-EXT-3[PM-EXT-3]), and the project's extension skills
  (xref:../Requirements.adoc#PM-SKILL-5[PM-SKILL-5]).

That is not something to give up. A captured memory that nobody checks is the failure Claude-Mem has no answer to: an
outdated or wrong observation gets injected into every later session and is trusted. Our lessons have that answer. A
lesson's premise is checked before a plan is made from it, and an invalid or resolved premise retires the lesson
(xref:../Requirements.adoc#PM-WF-10[PM-WF-10]).

=== What it does better: cheap retrieval by index

Claude-Mem's progressive disclosure is the same pattern our skills use: catalogue entries, then the skill, then its
supporting files (xref:../Requirements.adoc#PM-SKILL-1[PM-SKILL-1]). For skills we deliver what is needed instead of
waiting for a fetch (xref:../Requirements.adoc#PM-SKILL-4[PM-SKILL-4]). For lessons and the decisions of earlier plans,
a worker gets what its state's facts carry and can read `pm://` resources, but it has no cheap search over them. An
index of short entries (title, category, component), searched by the worker and fetched by id, would let a worker find
"we decided this before" without the server guessing which past records matter.

=== Captured automatically versus written deliberately

Claude-Mem records every tool use and lets a model summarise it. Our records come from transitions, and a lesson is
written by a task whose submit names its category and sources. The automatic capture catches what nobody thought to
write down, at the price of noise and unchecked content. Our activity records already capture every tool call of
every worker (xref:../Requirements.adoc#PM-WORK-7[PM-WORK-7]); they serve supervision, not memory. Turning them into
memory would bring Claude-Mem's correctness problem with it. Learning from them belongs in the retrospective that
writes lessons, where a lesson still gets its premise and its sources.

=== A dense context document is cheap after its first read

The article's observation that a 379-line `MEMORY.md` costs little after its first read is a caching effect, and it
holds for our skills too: a stable skill delivered in-band at the start of a launch is served from cache by the next
worker of the role (xref:graphify-impact.adoc#_prompt_caching_depends_on_a_stable_prefix[Graphify Impact, stable
prefix]). A project's settled decisions in an extension skill bound to its domains (the "constitution" of the
xref:clean-code-to-clean-spec.adoc[Clean Spec analysis]) would be cheap for the same reason.

=== Local by design

The default observer is hosted, and cloud sync sends memories off the machine. PM-MCP keeps everything local
(xref:../Requirements.adoc#PM-ARCH-2[PM-ARCH-2]). Its `<private>` exclusion has no counterpart for us because
nothing leaves the machine except what a provider call or a model call needs.

== Candidates for a Change

Nothing is applied:

. *A searchable index of lessons and decision records* for workers: short entries, a search, and full records by id,
  read-only and confined to the project.
. *Learning from the activity records only through lessons*: if the retrospective ever mines worker activity, its
  result is a lesson with premise and sources, never memory injected unchecked.
